# v14.4 Wave 1: Platform, Application, and Interfaces

Wave 1 establishes enforceable contracts between the shared platform,
application orchestration, and external interfaces. It does not add product
features or change public CLI/API behavior.

## Scope

- Recursive JSON contracts for values crossing platform, application, and
  interface boundaries.
- Explicit application use cases for the core Program list/create/get flow.
- Dependency injection for maintenance release checks and generation state.
- Bounded API/CLI composition roots with typed constructor providers.
- Removal of dynamic symbol forwarding and interface-to-domain implementation
  imports outside composition.
- Static CLI command-package ownership without rewriting callable `__module__`
  metadata to simulate parser/handler colocation.
- Explicit Any rejection in `platform`, `application`, and `interfaces`.

## JSON Contract

`song_agent/platform/contracts/documents.py` defines `JsonPrimitive`, recursive
`JsonValue`, and `JsonDocument` types. `is_json_value()` and
`is_json_document()` validate untrusted values recursively. The normalization
helpers return fresh JSON-compatible structures and convert path and tuple
values only through explicitly supported conversions. Unknown
objects, byte strings, non-string mapping keys, recursive structures, and
non-finite floats fail validation; arbitrary `__str__` output is never treated
as JSON.

## Dependency Direction

The enforced direction remains:

```text
interfaces -> application -> domains -> platform
```

Concrete Store dependencies may be constructed only in the declared interface
composition roots:

- `song_agent/interfaces/api/server.py`
- `song_agent/interfaces/bootstrap/`

API/CLI handlers outside these roots may depend on application ports and typed
bootstrap bindings, but may not import domain implementations or construct
`*Store` classes. Application modules may not construct Stores or import
`song_agent.release_check`.

Fifty-seven historical Interface files still import a bootstrap or Application
namespace that exposes concrete Stores. Each file is frozen by normalized
source identity: it may remove the namespace dependency, but any edit that
retains it fails. New code must import an explicit typed factory or port symbol;
it cannot import the containing namespace and recover a Store through aliases,
wrappers, or reflection.

The gate resolves absolute and relative imports through the complete production
module graph. Outside composition, the only new Application/Interface imports
from Domain are the reviewed symbols below; module imports, wildcard imports,
and other symbols from the same module fail closed:

- `song_agent.domains.creation.provider_contracts.ProviderConfig`
- `song_agent.domains.program.model.ProgramComponent`
- `song_agent.domains.program.ports.ProgramReleaseStore`

Twelve pre-Wave-1 Application files still import Domain implementations. Each
file is frozen by a normalized source hash. A later wave may remove all of its
implementation imports, but any edit that retains them fails the gate. This is
an explicit migration ratchet, not a claim that Application migration is
already complete.

Program verifier and lifecycle capability metadata are assembled explicitly in
the composition-only modules
`song_agent/interfaces/bootstrap/api/program_verifier_capabilities.py` and
`song_agent/interfaces/bootstrap/api/program_lifecycle_capabilities.py`.
Platform registries contain only generic models and injected module references;
Platform does not import or dynamically resolve Domain implementations.

The bootstrap constructor helper preserves each concrete constructor signature
with `ParamSpec`; arbitrary `*args: object` or `**kwargs: object` service-locator
factories are forbidden.

Dynamic module resolution is denied by capability rather than call spelling.
`imp`, `importlib`, `pkg_resources`, `pkgutil`, `pydoc`, `runpy`, `zipimport`,
`__import__`, loader protocols, and module-registry access are forbidden in
Wave 1 roots. The only
allowlisted loader import is inside
`song_agent/platform/resource_access.py`; it exposes fixed resource IDs and a
path-contained Studio script reader. Trusted production source is forbidden from
recovering callable internals through `__globals__`, `__closure__`, `__code__`,
`__builtins__`, or `__func__`, including `getattr` and statically evaluable key
aliases. The two Program capability assemblers may import only
`inspect.getsourcefile`; frame and namespace introspection remain denied.

This is an architecture gate for reviewed source, not a Python process sandbox.
Code that is not trusted must run in a separately isolated process; Python
reflection cannot provide an in-process security boundary.
Module namespace mutation through
`globals()`/`locals()`, PEP 562 module hook binding, and runtime metadata
rewriting is forbidden. `__all__` must be one static string tuple/list and
cannot be read back for alias-based mutation.

Approved contracts, immutable legacy debt, and the attack corpus live in the
packaged `song_agent/release_check/v14_wave1_policy.json` resource. Its exact
bytes are bound to a SHA-256 anchor in the gate, and the isolated-wheel test
proves that an installed distribution uses the same policy outside the source
repository.

## Application Use Cases

The Program application service owns explicit `list_programs`,
`create_program`, and `get_program` operations. It no longer uses generic
operation-name dispatch or dynamic `getattr` forwarding.

Maintenance receives a release-check executor through its application port.
Generation receives a NodeStore factory from the API or CLI composition root.
Neither application path constructs its infrastructure dependency directly.

This wave intentionally does not convert every historical handler workflow to
an application use case. Remaining direct Store method orchestration is frozen
and must move during the later bounded-context waves.

`ProgramApplicationService` also retains a typed-enum keyed component container
whose values are represented as `object` and narrowed at its use-case boundary.
That service-locator-shaped compatibility is recorded as later Program
migration debt; Wave 1 does not claim that every application component is fully
strongly typed.

## Static Gates

`v144.wave1_platform_application_interfaces_smoke` fails on:

- interface-to-domain imports outside a composition root;
- unapproved Domain modules/symbols in Application and edits to frozen legacy
  implementation dependencies;
- Platform imports or dynamic loading of Domain/Application/Interface code;
- central dependency-direction violations, including Application or Domain
  imports of Interface/release-check modules;
- Store construction in application or non-composition interfaces;
- application imports of release-check implementation;
- `__getattr__`, `exec`, mutable module forwarding, or dynamic module-class
  replacement in Wave 1 roots;
- forbidden dynamic resolver/reflection capabilities and non-static `__all__`
  exports;
- composition modules over 400 lines, 24,000 normalized UTF-8 bytes, or 1,200
  AST nodes, and new composition lines over 2,000 UTF-8 bytes;
- untyped object-passthrough factories;
- missing recursive JSON contracts or Program use cases;
- missing maintenance/generation injection;
- missing Explicit Any mypy configuration or a failing mypy run.

Nine generated bootstrap facades and the historical API server still exceed
the single-line limit. Their exact source identities are frozen; any edit must
first split the long line below the limit. This debt exception cannot authorize
a new file or a changed façade.

The mypy override applies `disallow_any_explicit` to:

- `song_agent.platform.*`
- `song_agent.application.*`
- `song_agent.interfaces.*`

This is an Explicit Any ban, not a claim that mypy strict mode is enabled.
`follow_imports = "skip"` and other project-wide typing debt remain visible for
later waves.

The bootstrap override additionally enables `disallow_untyped_defs` and
`disallow_incomplete_defs`. This narrower rule covers functions, methods, and
callable providers in composition without claiming project-wide strict mypy.

## Frozen Surface Migration

Wave 1 changes source locations and typed expressions without adding a product
surface. `tools/migrate_v144_wave1_surfaces.py` records and validates the
one-time migration against fixed input and output hashes:

- 78 CLI registrations retain the same source, function, command, and
  capability owner while their source lines move;
- 164 package writer observations retain the same source expression and owner;
- 12 observations are explicit typed semantic rewrites, including one
  three-to-one duplicate-site consolidation;
- 9 unresolved or duplicate legacy observations are retired;
- package writer sites decrease from 2,687 to 2,676, with zero additions;
- the only release-check surface addition is
  `v144.wave1_platform_application_interfaces_smoke`.

The migration rebuilds capability, package, state, catalog, baseline, and the
three runtime projections in one transaction. It verifies the independent
Package Registry and State Authority anchors before writing, and rolls every
file back if either Wave 0 or Wave 1 validation fails. The complete mapping is
stored in `architecture-v14.4-wave1-surface-migration.json`.

## Accurate Closure

Wave 1 closes the Platform/Application/Interfaces boundary work described
above. It does not close global ARCH-014 module-size debt, global TYPE-003 type
precision debt, or later domain migration waves. No ceiling, suppression, or
check exclusion is introduced by this wave.

# v4.10.0 Knowledge-assisted Fix Planning 知识辅助修复计划施工图

日期：2026-05-21

当前稳定基线：v4.9.1

目标版本：v4.10.0

建议版本主题：Knowledge-assisted Fix Planning / 知识辅助修复计划

---

## 1. 背景

v4.7 到 v4.9 已经形成了完整的验收知识链路：

```text
Acceptance Analytics
  -> Acceptance Fix Sprint
  -> Recheck / Delta / Closeout
  -> Acceptance Knowledge Base
```

v4.9.1 之后，系统已经能把 closed 且非 stale 的 Fix Sprint 沉淀为 Knowledge Entry，并能提供 search / recommend。

但现在 KB 还是一个“查询系统”：

- 开发需要自己看 KB recommendation。
- 创建 Fix Sprint 时不会自动引入 KB evidence。
- Fix item 排序仍主要来自 analytics weakness。
- 对历史低效修法没有明确 warning。
- 对历史有效修法没有转成计划建议。
- Release / Project 侧能看到 KB summary，但它不参与修复计划。

v4.10.0 要做的是把 KB 从“事后知识库”接到“事前修复计划”里。

目标闭环：

```text
Fresh Acceptance Analytics
  + Acceptance Knowledge Base
  -> Fix Plan Report
  -> ranked fix items
  -> risk warnings
  -> suggested recheck strategy
  -> Create Acceptance Fix Sprint with KB evidence
```

---

## 2. 版本定位

一句话定位：

> v4.10.0 用 Acceptance Knowledge Base 辅助创建下一次 Acceptance Fix Sprint，让系统能根据历史修复效果排序、解释风险、建议复验策略，但不自动执行任何修复。

它不是自动修歌。

它也不是新的 AI agent。

它是一个 deterministic planning layer。

---

## 3. 明确不做什么

本版不做：

- 不自动创建 ReviewTask，除非用户继续显式点击已有 Fix Sprint 动作。
- 不自动 apply candidate。
- 不自动修改 Project version。
- 不调用 provider。
- 不使用 LLM。
- 不使用向量库。
- 不把 KB plan 作为 Release Signoff 强制 gate。
- 不让 stale KB entry 参与计划。
- 不让 hidden KB entry 默认参与计划。
- 不把 force_closed / waived-heavy 历史当作强正向样本。

本版允许：

- 基于 fresh analytics report 和 KB entries 生成 Fix Plan Report。
- 对 analytics recommendations 重新排序。
- 给每个计划项附加 KB evidence。
- 给低效历史修法打 warning。
- 给 recheck profile / manual review 策略建议。
- 在创建 Fix Sprint 时把 Fix Plan Report 绑定进去。
- 在 Studio 创建 Fix Sprint 前展示 plan。

## 4. 核心用户故事

### 4.1 开发人员

开发人员希望：

- 创建 Fix Sprint 前知道哪些问题历史上最难修。
- 知道哪些 issue/style 有有效修法。
- 知道哪些 recommendation 应该优先处理。
- 避免再次使用历史低效路径。
- 让 Fix Sprint item 自动带上 KB evidence 和 planning reason。

### 4.2 Reviewer

Reviewer 希望：

- 看到 Fix Sprint 不是只按 weakness 排序，而是结合历史修复效果。
- 看到风险项为什么排在前面。
- 看到被 waiver 多次的问题是否被提示。

### 4.3 业务方

业务方希望：

- 看到修复计划是否基于历史经验。
- 看到哪些风格进入稳定状态，哪些还需要专项处理。

## 5. 新增概念

### 5.1 Fix Plan Report

修复计划报告。

输入：

- fresh Acceptance Analytics report
- Acceptance Knowledge Base report / entries
- optional scope: project / release / suite

输出：

- ranked recommendations
- KB matches
- risk warnings
- suggested actions
- suggested recheck strategy
- source hash

### 5.2 Planned Fix Item

计划化的 fix item。

它不是实际 Fix Sprint item，但可以转换为 Fix Sprint item。

### 5.3 Planning Score

综合排序分数。

来源：

- analytics weakness_score
- analytics severity
- KB effectiveness for similar issue/style/song
- recurring issue risk
- waiver risk
- force_closed risk
- manual coverage risk

### 5.4 Planning Evidence

计划证据。

包括：

- matched KB entry summaries
- issue pattern
- style pattern
- song pattern
- suggested next actions

## 9. Planning Score 规则

必须 deterministic。

建议：

```text
score = 0
+ analytics weakness_score * 0.55
+ 15 if analytics severity == high
+ 10 if latest_status == rejected
+ 8  if latest_status == needs_fix
+ 10 if KB has matching ineffective/mixed history
+ 8  if recurring issue count > 1
+ 6  if style pattern stability_status == watch
- 8  if KB matching effective score >= 80
- 10 if open ReviewTask already exists

clamp 0..100
```

解释：

- KB 有有效修法时，不是降级不处理，而是说明风险更可控，所以排序稍降。
- KB 有低效历史时，说明问题难，排序提高。
- open ReviewTask 已存在时，避免重复堆任务。

## 10. Risk 规则

风险标签建议：

```text
no_kb_history
history_mixed_effectiveness
history_ineffective
waiver_heavy_history
force_closed_history
manual_coverage_incomplete
synthetic_only_history
open_task_exists
stale_kb_report
hidden_entries_excluded
```

风险等级：

```text
high:
  history_ineffective
  or waiver_heavy_history
  or force_closed_history

medium:
  history_mixed_effectiveness
  or style watch
  or no_kb_history

low:
  effective history and no warnings
```

## 15. Source Hash / Stale

Plan source hash 应绑定：

- analytics report source hash
- selected analytics recommendations payload
- KB report source hash
- selected KB entry summaries
- planning rules version

不绑定：

- generated_at
- UI state
- report file path

Stale 行为：

- analytics report stale：plan stale，不能 create Fix Sprint。
- KB report stale：plan warning；如果 planned items 依赖的 KB entries changed，不能 create Fix Sprint。
- hidden entry changed：如果 include_hidden_kb=false，不影响。
- hidden entry included：source hash 必须绑定。

## 17. 安全与脱敏

必须复用 redaction。

不能导出：

- 完整人工 notes
- provider raw response
- 本机路径
- token / secret
- hidden KB entry 的完整 payload

允许导出：

- entry_id
- issue_type
- score
- risk
- summary

所有 free text 限制 300 字符。

## 20. P1 风险清单

必须防：

- stale analytics report 还能生成可执行 plan。
- stale plan 还能 create Fix Sprint。
- hidden KB entry 默认参与 plan。
- force_closed / waiver-heavy history 被当成强正向样本。
- KB report stale 但 plan 没 warning。
- open ReviewTask 已存在但 plan 仍建议重复创建。
- plan source hash 绑定 generated_at 导致每次刷新都 stale。
- create Fix Sprint from plan 自动创建 ReviewTask。
- export 泄露完整 KB entry 或人工 notes。

1. fresh analytics + KB 能创建 plan。
2. hidden KB 默认不参与。
3. include_hidden_kb=true 有 warning 且 source hash 绑定 hidden entry。
4. plan score deterministic。
5. low-effectiveness history 提高风险。
6. high-effectiveness history降低风险但仍保留 evidence。
7. stale analytics 后 create-fix-sprint 返回 409。
8. plan 创建的 Fix Sprint 带 plan/kb evidence。
9. 不自动创建 ReviewTask。
10. Export 只有 summary。

## 23. v5 前瞻

v4.10 完成后，v4 线的质量闭环基本完整：

```text
验收 -> 分析 -> 知识 -> 计划 -> 修复 -> 复验 -> 交付
```

下一阶段可以进入 v5：

```text
v5.0.0 Real Audio / Vocal / Mixing Path
```

但 v5 的第一步建议仍然保守：

- 先接入真实音频渲染和听审基线。
- 不直接上复杂 vocal generation。
- 所有真实音频能力必须走 Acceptance / Human Review / KB / Fix Planning 闭环。

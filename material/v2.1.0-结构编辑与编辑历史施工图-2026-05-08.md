# MusicForge v2.1.0 施工图：结构编辑与编辑历史

> 基线版本：v2.0.1  
> 当前目标：在 Visual SongPlan Editor 已经可做 section 字段、track 字段、note 级 patch 的基础上，新增 section/track 结构编辑、编辑历史和更完整的 Studio 编辑体验。  
> 执行原则：全部先本地化验证；每完成一个边界清晰的功能包，测试通过后提交并推送 GitHub；最终再 tag / Release。  
> 范围判断：v2.1.0 不做完整 DAW、不做 MIDI import merge、不做 arranger solver，先把 SongPlan 内部结构操作做稳。

---

## 1. 背景

v2.0.1 之后，MusicForge 已经有一个可用的 Visual SongPlan Editor：

- `editor-state` 可读取 Project Version 的 section / track / note 状态。
- Editor Patch 支持：
  - `set_section_chords`
  - `set_section_lyrics`
  - `set_track_instrument`
  - `add_note`
  - `update_note`
  - `delete_notes`
  - `move_notes`
  - `transpose_notes`
  - `quantize_notes`
  - `scale_velocity`
- Preview 不覆盖 parent version。
- Apply 创建新的 Project Version。
- Apply 已修复为只信任 `parent_plan + patch -> result.plan`，不再信任 preview `song-plan.json`。
- Project diff / Compare / Export / release-check 已接入 visual editor metadata。

这说明 v2.0 已经补上了“能手工改一首歌”的关键闭环。

但它仍然偏向“在既有结构里改字段和音符”。用户还不能做这些常见动作：

- 复制一个 chorus。
- 删除过短的 intro。
- 把 bridge 移到 chorus 前。
- 延长某个 section。
- 新增一个空白 section。
- 新增一条 pad 轨道。
- 删除一个空轨道。
- 复制 melody 轨道变成 counter melody 草稿。
- 在 Studio 中查看 preview 历史并重新应用某个 preview。

所以 v2.1.0 应该做“结构编辑与编辑历史”。

这版的重点不是继续增加 AI 能力，而是把 SongPlan 的结构层编辑做成受控、可测试、可回滚的 patch 操作。

---

## 2. 一句话目标

v2.1.0 的一句话目标：

> 扩展 Visual Editor Patch，让用户可以安全新增、复制、删除、移动、调整 section 和 track，并在 Studio 里管理 editor preview 历史。

落地后，用户应能做到：

1. 新增 section。
2. 复制 section。
3. 删除 section。
4. 调整 section bars。
5. 移动 section 顺序。
6. 新增 track。
7. 复制 track。
8. 删除 track。
9. 重命名 track。
10. 在 Studio 里看到 editor preview 历史。
11. 删除未应用 preview。
12. 重新打开历史 preview 查看 patch summary。
13. Apply 历史 preview 成新版本。
14. Project Compare 能清楚展示结构变化。
15. Project Export / Final Export 能写入脱敏结构编辑摘要。
16. release-check 覆盖 v2.1 structure editor 主链路。

---

## 3. 非目标

v2.1.0 不做以下事情：

- 不做完整 DAW。
- 不做浏览器合成器。
- 不做实时播放头。
- 不做拖拽 piano-roll。
- 不做 MIDI import merge。
- 不做 audio-to-MIDI。
- 不做 arranger constraint solver。
- 不做自动补全复杂编曲。
- 不做跨版本自动 merge。
- 不做多人协同。
- 不做无限 undo/redo。

原因：

- v2.1.0 的风险集中在结构变更会影响所有 note 的时间轴。
- 先把 deterministic patch engine、数据一致性和版本化做稳。
- 更复杂的交互式拖拽和 arranger 可以放到 v2.2+。

---

## 4. 核心原则

结构编辑和 v2.0 的 note 编辑不一样，它会改变全局时间线。

必须遵守：

1. Parent version 永远不被覆盖。
2. Patch 仍绑定 `base_plan_hash`。
3. 所有 section 操作后必须重新规范化 `start_bar`。
4. section resize / delete / move 必须同步调整或处理受影响 notes。
5. track delete 必须拒绝删除最后一个有音符轨道，除非明确 `allow_empty_song=true`。
6. track name 必须唯一。
7. preview/apply 仍只使用 `parent_plan + patch -> result.plan` 的可信路径。
8. preview 历史不能绕过 stale 检查。
9. Apply 仍必须只能成功一次。
10. 所有新元数据都必须脱敏。

## 6. Section 结构操作

### 6.1 add_section

```json
{
  "op": "add_section",
  "after_section_id": "section-002",
  "name": "bridge",
  "bars": 8,
  "chords": ["Fmaj7", "G7", "Am7", "Cmaj7"],
  "lyrics": ""
}
```

允许：

- `after_section_id` 存在时插入到该 section 后。
- `after_section_id` 为空时追加到结尾。

限制：

- `name` 必须非空，最长 40。
- section name 必须唯一。
- `bars` 1..64。
- `chords` 非空，最多 16 个。
- chords 仍用当前白名单。
- lyrics 最多 2000 字符并脱敏。
- 总 bars 不超过 256。

时间线处理：

- 新 section 插入后，后续 section 的 `start_bar` 自动后移。
- 新增 section 默认不自动生成 notes。
- 可以返回 warning：`Section was added without notes.`

### 6.2 duplicate_section

```json
{
  "op": "duplicate_section",
  "section_id": "section-003",
  "name": "chorus 2",
  "copy_notes": true,
  "after_section_id": "section-003"
}
```

限制：

- source section 必须存在。
- 新 name 必须唯一。
- `copy_notes` 默认 true。
- 总 bars 不超过 256。

时间线处理：

- 复制 section 元数据。
- 如果 `copy_notes=true`，复制所有 track 中落在 source section 范围内的 notes，并平移到新 section 起点。
- 后续 section 和 notes 后移。

### 6.3 delete_section

```json
{
  "op": "delete_section",
  "section_id": "section-001",
  "note_policy": "delete"
}
```

`note_policy` 支持：

```text
delete
shift_left
keep_absolute
```

v2.1.0 推荐只开放 UI 默认 `delete` 和 `shift_left`。

语义：

- `delete`：删除该 section 范围内 notes，后续 notes 左移。
- `shift_left`：同 `delete`，但命名更直观；二者可先等价。
- `keep_absolute`：删除 section，但 notes 不移动；容易造成结构和 notes 脱节，v2.1.0 API 可以支持但 Studio 不展示。

限制：

- 至少保留 1 个 section。
- 删除后总 bars >= 1。

### 6.4 resize_section

```json
{
  "op": "resize_section",
  "section_id": "section-002",
  "bars": 12,
  "note_policy": "scale"
}
```

`note_policy` 支持：

```text
scale
crop
shift_tail
```

v2.1.0 建议先实现：

- `shift_tail`：section 内 notes 不缩放，只调整后续 section/notes 位置。
- `crop`：缩短 section 时删除超出新区间的 notes。

`scale` 可以预留但不在 UI 暴露，除非实现很稳。

限制：

- bars 1..64。
- 总 bars 不超过 256。
- 如果缩短导致 notes 超界，必须按 policy 处理。

### 6.5 move_section

```json
{
  "op": "move_section",
  "section_id": "section-004",
  "after_section_id": "section-001",
  "move_notes": true
}
```

限制：

- source section 必须存在。
- target 不能等于 source。
- `move_notes=true` 时，section 内 notes 跟随 section 移动。
- 所有 section `start_bar` 重新规范化。

建议算法：

1. 把所有 sections 转成 ordered blocks。
2. 每个 block 记录：
   - section metadata
   - old_start_beat
   - old_end_beat
   - new_start_beat
3. 重排 blocks。
4. 对每个 note 找旧 block。
5. 如果 note 属于被移动 block，按 offset 平移。
6. 对后续 block 的 notes 按 block 新旧 start delta 平移。

## 7. Track 结构操作

### 7.1 add_track

```json
{
  "op": "add_track",
  "name": "pad",
  "instrument": "warm pad",
  "role": "harmony"
}
```

限制：

- track name 必须唯一。
- name 最长 40。
- instrument 最长 80。
- track 总数不超过 32。
- 新 track 默认 notes 为空。

### 7.2 duplicate_track

```json
{
  "op": "duplicate_track",
  "track_id": "track-001",
  "name": "counter melody",
  "instrument": "soft lead",
  "transpose": 12
}
```

限制：

- source track 必须存在。
- 新 name 必须唯一。
- transpose -24..24。
- 复制后 notes 仍在 0..127。
- track 总数不超过 32。

### 7.3 delete_track

```json
{
  "op": "delete_track",
  "track_id": "track-004"
}
```

限制：

- 不能删除不存在 track。
- 不能删除最后一个 track。
- 如果删除的是最后一个有 notes 的 track，默认拒绝。
- 如果 payload 显式 `allow_empty_song=true`，可以删除，但要 warning。

### 7.4 rename_track

```json
{
  "op": "rename_track",
  "track_id": "track-001",
  "name": "lead melody"
}
```

限制：

- 新 name 必须唯一。
- 最长 40。
- 不改变 notes。

## 8. Timeline Normalization

新增内部工具：

```python
normalize_sections(sections: list[SongSection]) -> list[SongSection]
```

规则：

- 第一段 `start_bar=1`。
- 后续 section 的 start_bar = 前一段 start_bar + bars。
- bars 必须 >= 1。
- section name 唯一。

新增内部工具：

```python
shift_notes_after_beat(tracks, beat, delta)
delete_notes_in_range(tracks, start_beat, end_beat)
copy_notes_in_range(tracks, start_beat, end_beat, target_start_beat)
move_section_notes(...)
```

所有结构操作后必须：

- notes 不小于 0。
- notes 不超过新 song length。
- notes 排序。
- quality 重新计算。
- SongPlan.validate。

## 9. Editor Preview History

v2.0 有 preview store，但 Studio 主要是当前 preview 操作。

v2.1.0 增加 preview 历史 API：

```text
GET /api/projects/<project-id>/editor-previews
```

返回：

```json
{
  "ok": true,
  "previews": [
    {
      "preview_id": "preview-001",
      "parent_version_id": "v003",
      "status": "completed",
      "label": "duplicate chorus",
      "operation_count": 2,
      "changed_sections": ["chorus", "chorus 2"],
      "changed_tracks": ["melody"],
      "applied_version_id": null,
      "created_at": "2026-05-08T00:00:00Z"
    }
  ]
}
```

排序：

- updated_at desc。
- preview_id desc。

新增 preview summary：

```text
GET /api/projects/<project-id>/editor-previews/<preview-id>/patch
```

只返回脱敏 patch summary，不一定返回完整 patch operations。

如果要返回完整 patch，需要 query：

```text
?include_operations=true
```

默认不返回完整 operations，避免大 patch 影响 UI。

## 10. Preview Cleanup

新增：

```text
POST /api/projects/<project-id>/editor-previews/cleanup
```

请求：

```json
{
  "delete_unapplied_older_than_days": 7,
  "keep_latest": 20
}
```

限制：

- 只删除未 applied previews。
- applied preview 不删除。
- `keep_latest` 最小 5，最大 200。
- 删除时做路径边界和 symlink 拒绝。

release-check 不需要真的等 7 天，可以构造旧 timestamp。

## 13. release-check 增强

新增 smoke：

```text
v2.1 structure editor smoke
```

流程：

1. 创建临时 root。
2. 创建 Project 和 parent version。
3. build editor state。
4. 创建 structure patch：
   - duplicate chorus -> chorus 2。
   - resize verse。
   - add pad track。
   - duplicate melody -> counter melody。
   - rename track。
5. preview。
6. 确认 preview state 中：
   - section_count 增加。
   - track_count 增加。
   - start_bar 规范。
   - copied notes 已平移。
7. apply。
8. 确认 parent 不变。
9. 确认 child version `manual_editor_edit`。
10. Project Compare 有结构变化。
11. Project Export 有 structure edit summary。
12. Final Export manifest 有 structure edit summary。
13. Preview History 能列出 preview。
14. Cleanup 不删除 applied preview。
15. secret scan 不泄露污染 label。

输出示例：

```text
v2.1 structure editor smoke: ok
  preview=preview-001, version=v002, sections=6, tracks=6, operations=5
```

```powershell

git status --short --branch
```

最终必须是：

```text
## master...origin/master
```

## 17. reviewer 重点检查点

### P1：Section resize 是否导致 notes 越界

复现：

1. 缩短 verse。
2. verse 尾部有 note。

预期：

- 按 policy crop 或 shift。
- 最终 no note end > song length。

### P1：Move section 是否破坏 start_bar

复现：

1. bridge 移到 intro 后。
2. 读取所有 sections。

预期：

- 第一段 start_bar=1。
- 后续连续。
- 无重叠。

### P1：Duplicate section notes 是否平移正确

复现：

1. duplicate chorus copy_notes=true。
2. 比较 source notes 和 copied notes。

预期：

- pitch/duration/velocity 相同。
- start_beat 按新区间平移。

### P1：Delete track 是否能删掉整首歌

复现：

1. 删除所有有 note 的 tracks。

预期：

- 默认拒绝。
- 如果 allow_empty_song=true，必须 warning。

### P1：Preview cleanup 是否删除 applied preview

复现：

1. preview。
2. apply。
3. cleanup。

预期：

- applied preview 仍存在。

### P1：历史 preview 是否能绕过 stale

复现：

1. preview。
2. 修改 parent song-plan。
3. apply old preview。

预期：

- 409 stale。

### P2：Studio patch summary 是否可读

预期：

- 不只展示 JSON。
- 用户能看到具体结构操作。

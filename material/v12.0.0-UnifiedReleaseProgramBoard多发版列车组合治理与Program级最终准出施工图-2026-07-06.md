# v12.0.0 Unified Release Program Board 多发版列车组合治理与 Program 级最终准出施工图

> 目标读者：开发执行人员、测试验收人员、后续 reviewer  
> 当前稳定基线：v11.9.1  
> 建议下一版：v12.0.0  
> 核心目标：把 v11.6-v11.9 已经闭环的单个 Release Train 提升到 Program 层，管理多个 Train Handoff 的组合准出、跨 Train 依赖、延期/例外、组合风险、Program 级签核和最终交接包。v12.0 不再继续给单个 Train 加小补丁，而是做 Train-of-Trains 的统一发布计划与最终准出。

---

## 1. 背景

v11 已经把“单个 Release Train”做到了可用闭环：

- v11.0 Unified Command Center：统一汇总 release、audio、trust、maintenance、delivery 等证据。
- v11.1 UCC Signoff / Archive / Handoff：单个 UCC 的签核、归档和交接。
- v11.2 Continuous Review：已签核后的持续复核。
- v11.3 Drift Response：漂移响应和受控修复。
- v11.4 Evidence Review / Replay：证据复盘、外部审查和 accepted evidence。
- v11.5 Reviewer Decision Board：多 reviewer 决策委员会。
- v11.6 Release Train：把多个 UCC 组成一个发版列车。
- v11.7 Change Control：签核后变更必须走 approved CR reset。
- v11.8 Lifecycle Audit：把 train 的 reset / signoff succession / archive-history 收成生命周期总账。
- v11.9 Final Handoff Board：把 Train、Change Control、Lifecycle、外部 response、accepted evidence 汇成最终交接层。
- v11.9.1 修复 accepted evidence quorum：role / organization / decision 必须从 response sidecars 反查，不能信 public summary。

到这里，单个 train 已经可以独立做到：

1. 创建。
2. 聚合多个 UCC。
3. 签核。
4. 受控 reset。
5. 生命周期审计。
6. 外部验收。
7. 最终 handoff。

但项目真实发布不会永远只有一个 train。下一阶段的问题是：

1. 一个版本线可能拆成多个 train：audio train、trust train、delivery train、public transparency train。
2. 多个 train 之间有顺序依赖：例如 Audio Certification train 必须在 Distribution train 前完成。
3. 有些 train 是 blocker，有些是 advisory。
4. 某个 train 可能 deferred 到下一轮，但 Program 仍希望签核本轮。
5. Program owner 需要一个整体 readiness，而不是逐个打开 Train Handoff ZIP。
6. 外部业务验收需要“这组 trains 共同构成本次发布”的证据包。
7. GA / Release gate 需要判断的是 Program 是否 ready，而不是单个 train 是否 ready。

因此 v12.0 建议进入 **Unified Release Program Board**：

> 多个已签核 Release Train Handoff 组成一个 Release Program。Program 有自己的依赖图、readiness matrix、risk register、defer/exception 决策、最终签核、固定结构 Program ZIP 和离线 verifier。Program 不修改任何 train，只做组合治理和最终准出。

## 2. 版本定位

### 2.1 命名

英文名：

**Unified Release Program Board**

中文名：

**统一发布 Program Board / 多发版列车组合治理与 Program 级最终准出**

### 2.2 一句话定位

v12.0 是 Train-of-Trains：它把多个 v11.9 Train Final Handoff 组合成一个 Program 级发布计划，提供跨 Train 依赖、组合准出、风险/延期治理、Program 签核和最终交接包。

### 2.3 v12.0 要解决什么

必须解决：

1. Program 创建 / 列表 / 详情。
2. 添加多个 Release Train Handoff 作为 Program item。
3. 每个 item 绑定外部 Handoff ZIP、Handoff verification report、Handoff signoff binding。
4. 可选绑定 accepted evidence dir。
5. Program dependency graph。
6. Program readiness matrix。
7. Program risk register。
8. Program defer / exception register。
9. Program final handoff report。
10. Program signoff。
11. Program signoff binding summary。
12. Program history hash-chain。
13. Program fixed-layout ZIP。
14. Program offline verifier。
15. Release signoff / GA readiness gate。
16. CLI / API / Studio 接入。
17. release-check v12.0 smoke。

### 2.4 v12.0 不做什么

不做：

1. 不自动修改任何 Release Train。
2. 不自动 reset Train。
3. 不自动 approve Program exceptions。
4. 不自动发布 GitHub Release。
5. 不把 Train Handoff ZIP 嵌入 Program ZIP。
6. 不支持 Program signoff reset。
7. 不做跨机器公钥签名。
8. 不做长期公开 Portal。

如果 Program 签核后需要改动：

- v12.0 只允许新建 Program 或新建 Program revision。
- 不允许删除 `program-signoff.json` 后复用旧 Program。
- 后续 v12.1 可以单独设计 Program Change Control / approved CR reset。

## 3. 核心原则

### 3.1 Program 只引用 Train Handoff，不复制 Train ZIP

Program item 的来源必须是 v11.9 Train Final Handoff：

- handoff ZIP
- handoff verification report
- handoff signoff binding
- external evidence manifest fingerprint
- optional accepted evidence dir fingerprint

Program ZIP 中不允许嵌入：

- release-train-final-handoff.zip
- release-train.zip
- change-control.zip
- lifecycle.zip
- UCC archive ZIP
- nested `.zip`

Program 只导出 public-safe summary 和 fingerprint。

### 3.2 Program verifier 必须 runtime 复验每个 Train Handoff

不能只信 Program ZIP 内部的 `train-items.json`。

Verifier 必须在 `--require-current` 下使用外部 manifest：

- 每个 Program item 的 Handoff ZIP。
- 每个 Handoff verification report。
- 每个 Handoff signoff binding。
- 每个 item 的 accepted evidence dir，如果 policy 要求。

并调用：

```python
verify_unified_command_center_release_train_handoff_package(...)
```

每个 item 必须按：

```text
program_id + item_id + train_id + handoff_id + evidence_type
```

匹配，不能依赖 CLI 参数顺序。

### 3.3 Program signoff binding 必须签核时落盘

`program-signoff-binding-summary.json` 必须在 Program signoff 创建时生成。

不能在 export / ZIP / verifier 时从 signoff 现算。

它必须绑定：

- signer / role / reason / signed_at
- signoff hash
- latest history event hash
- program report hash
- readiness matrix hash
- train item index hash
- dependency graph hash
- risk register hash
- exception register hash
- external evidence manifest hash
- per-train handoff fingerprints

### 3.4 Program exceptions 必须显式且受约束

Program 可以允许非 blocker train 被 deferred。

但：

- blocker item 不能 deferred 后仍 Program ready。
- high / critical risk exception 必须有 explicit waiver reason。
- waiver 必须写入 exception register。
- waiver 不等于修改底层 train。
- accepted response 的 required role 仍必须从 Handoff accepted evidence sidecars 反查。

### 3.5 Program item 类型

建议支持：

```text
required
optional
advisory
deferred
```

规则：

- `required` 未 ready => Program blocked。
- `optional` 未 ready => warning / manual_required。
- `advisory` 未 ready => warning，不阻断。
- `deferred` 必须有 defer_reason、target_program_id 或 target_train_id，可阻断也可不阻断，取决于 original type 和 policy。

### 3.6 不信内部自证

不能信：

- program-report.json 自称 ready。
- train-items.json 自称 handoff passed。
- risk-register.json 自称 no blocker。
- exception-register.json 自称 waived。
- program-signoff.json 自称签核。

必须通过：

- integrity hash。
- history hash-chain。
- external handoff runtime verifier。
- external signoff binding。
- allowed ZIP entries。
- redaction scan。

## 7. Store API

新增：

```python
class UnifiedReleaseProgramStore:
    def create_program(self, payload: dict[str, Any]) -> dict[str, Any]: ...
    def list_programs(self) -> list[dict[str, Any]]: ...
    def get_program(self, program_id: str) -> dict[str, Any]: ...
    def add_train_item(self, program_id: str, payload: dict[str, Any]) -> dict[str, Any]: ...
    def remove_train_item(self, program_id: str, item_id: str) -> dict[str, Any]: ...
    def refresh_report(self, program_id: str, payload: dict[str, Any]) -> dict[str, Any]: ...
    def approve_exception(self, program_id: str, payload: dict[str, Any]) -> dict[str, Any]: ...
    def export_program(self, program_id: str) -> dict[str, Any]: ...
    def build_zip(self, program_id: str) -> dict[str, Any]: ...
    def verify_package(self, program_id: str, payload: dict[str, Any]) -> dict[str, Any]: ...
    def signoff(self, program_id: str, payload: dict[str, Any]) -> dict[str, Any]: ...
    def gate(self, payload: dict[str, Any]) -> dict[str, Any]: ...
```

### 7.1 create_program()

输入：

- `program_id` optional
- `name`
- `policy`

行为：

1. 创建 draft Program。
2. 不自动添加 train。
3. 不自动 signoff。

### 7.2 add_train_item()

输入：

- `item_id`
- `train_id`
- `handoff_id`
- `type`
- `lane`
- `wave`
- `depends_on`
- external evidence paths

规则：

- `item_id` 必须唯一。
- `train_id + handoff_id` 默认必须唯一。
- 如果 Program 已 signed，返回 409。
- 添加后不自动 signoff，只更新 draft source。

### 7.3 refresh_report()

行为：

1. 规范化 external evidence manifest。
2. 对每个 item 调用 Train Handoff verifier。
3. 建 dependency graph。
4. 检查 cycle。
5. 生成 readiness matrix。
6. 生成 risk register。
7. 合并 exception register。
8. 生成 gap plan。
9. 生成 program report。

签核后：

- 返回 409，不允许静默刷新。

### 7.4 approve_exception()

用于 optional/advisory/defer 场景。

限制：

- signed Program 不允许新增 exception。
- required item 的 critical failed 默认不能 exception。
- 如果要支持 required exception，v12.0 不做，留 v12.1 设计。

### 7.5 signoff()

前置：

- Program report ready。
- all required train items runtime verified。
- dependency graph acyclic。
- no critical risk。
- exceptions valid。
- required Program signer role。

行为：

1. 写 `program-signoff.json`。
2. append `program-history.jsonl`。
3. 写 `program-signoff-binding-summary.json`。
4. Program status -> signed。

签核后：

- add/remove item 409。
- refresh 409。
- approve exception 409。
- export/zip 只能使用冻结 docs。
- 删除 signoff 文件不能绕过，因为 history 中有 signoff event。

### 7.6 gate()

Release / GA 使用。

要求：

- Program ZIP 存在。
- Program verification report 存在。
- Program signoff binding 存在。
- runtime verify current passed。
- external evidence manifest present。
- 如果 require_signed，必须 signed。

## 8. Offline Verifier

新增：

```python
verify_unified_release_program_package(...)
```

CLI：

```powershell
python -m song_agent.cli verify-unified-release-program-package <program.zip> `
  --strict `
  --require-current `
  --require-signed `
  --external-evidence-manifest <program-external-evidence-manifest.json> `
  --program-signoff-binding <program-signoff-binding-summary.json>
```

### 8.1 External evidence

Verifier 主路径必须用 manifest：

```powershell
python -m song_agent.cli verify-unified-release-program-package <program.zip> `
  --strict `
  --require-current `
  --require-signed `
  --external-evidence-manifest <program-external-evidence-manifest.json> `
  --program-signoff-binding <program-signoff-binding-summary.json>
```

Repeat 参数可以作为便捷输入：

```powershell
--train-handoff-zip ...
--train-handoff-verification-report ...
--train-handoff-signoff-binding ...
```

但内部必须转换成 manifest，再按 item_id 匹配。

### 8.2 Verifier checks

必须检查：

1. ZIP fixed allow-list。
2. duplicate entries。
3. dangerous paths。
4. backslash entries。
5. `.musicforge` / `.MusicForge` case-insensitive block。
6. nested `.zip` block。
7. manifest package_type。
8. manifest.files exact allow-list。
9. file-index exact allow-list。
10. per-file sha256。
11. program-report integrity。
12. train-items integrity。
13. external-evidence-manifest integrity。
14. dependency-graph integrity。
15. readiness-matrix integrity。
16. risk-register integrity。
17. exception-register integrity。
18. gap-plan integrity。
19. program-history hash-chain。
20. signoff integrity。
21. signoff binding integrity。
22. external signoff binding required when `require_signed`。
23. external signoff binding equals ZIP sidecar。
24. each train item external handoff runtime verifier passed。
25. each train item fingerprint matches Program summary。
26. dependency graph has no cycle when policy requires。
27. required item not deferred unless policy explicitly allows and exception approved。
28. critical risk not waived silently。
29. redaction scan on all JSON / TXT / MD。

### 8.3 require_current

When `--require-current`:

- external evidence manifest required。
- all required items must have external Handoff ZIP/report/binding。
- runtime Handoff verification must pass。
- Program source fingerprints must match runtime results。

### 8.4 require_signed

When `--require-signed`:

- `program-signoff.json` required。
- `program-signoff-binding-summary.json` required。
- external program signoff binding required。
- signoff event must be latest relevant signoff event in history。
- delete signoff file cannot pass。

## 20. 风险清单

### P1: Program 自证

风险：

- Program report / train-items 被全量重签后声称 ready。

要求：

- verifier runtime 调用 Handoff verifier。

### P1: 签核伪造

风险：

- 篡改 signed_by + history + manifest 全量重签。

要求：

- external program-signoff-binding-summary required。

### P1: 依赖绕过

风险：

- dependency cycle 或缺前置 train 仍 ready。

要求：

- dependency graph verifier 重算 cycle / order。

### P1: required train 被静默 defer

风险：

- required item 改成 deferred 后 Program passed。

要求：

- required defer blocked，除非后续版本设计强 CR waiver。v12.0 不支持。

### P1: wrong handoff binding

风险：

- item A 绑定 item B 的 Handoff ZIP。

要求：

- verifier 检查 item_id / train_id / handoff_id / fingerprint。

### P2: API 任意路径读

风险：

- API payload 传本机敏感路径。

要求：

- API 限制 evidence 必须来自 workspace registered proof 或上传记录。

## 21. 给开发的执行口径

这版是 v12.0，不是 v11.10。目标是把 v11 的“单 Train 闭环”升级到“多 Train Program 准出”。

不要做成普通汇总 report。核心是：

1. Program item 必须是 v11.9 signed Train Handoff。
2. Program verifier 必须 runtime 复验每个 Handoff。
3. Program ZIP 不嵌套底层 ZIP。
4. Program signoff binding 必须签核时落盘。
5. signed Program 不可 mutation。
6. dependency / defer / risk 必须影响 readiness。
7. Release / GA gate 必须反查外部 Program package。

开发顺序：

1. 先 Store + verifier。
2. 再 dependency/risk/exception。
3. 再 signoff。
4. 再 CLI/API。
5. 最后 Studio 和 docs。

不要先做 UI。UI 最后接，避免核心证据边界被弱化。

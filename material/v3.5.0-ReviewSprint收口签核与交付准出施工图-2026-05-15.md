# v3.5.0 Review Sprint 收口签核与交付准出施工图

日期：2026-05-15

当前稳定基线：v3.4.1

目标版本：v3.5.0

定位：在 v3.4.1 已经完成 Review Sprint Dashboard / Metrics / Provider Judge 的基础上，新增 Review Sprint Closeout / Signoff / Delivery Readiness 层，把一轮反馈从“可执行、可评审、可统计”推进到“可正式收口、可签核、可进入最终交付”。v3.5.0 仍然不做自动 apply、不做自动 final、不做自动发布，只提供本地可验证、可审计的准出报告和人工确认流程。

---

## 1. 背景

当前 MusicForge 已经形成完整的创作反馈闭环：

```text
Project
  -> Version
  -> Visual Editor / Audition
  -> Review Board
  -> ReviewTask
  -> ReviewCandidate
  -> Decision Report
  -> ReviewSprint
  -> Recommendation Report
  -> Action Queue
  -> Provider Judge
  -> Metrics Dashboard
  -> Manual Apply
  -> Project Export / Final Export
```

v3.0.0 到 v3.4.1 解决的是：

- 能把多个反馈组织成 Sprint。
- 能推荐下一步。
- 能把建议拆成安全动作队列。
- 能用 Dashboard 观察进度。
- 能用 Provider Judge 辅助评审候选。
- 能把 judge / metrics / queue / recommendation 写进导出和最终交付摘要。

但目前还有一个明显缺口：Sprint 的“关闭”太轻。

现在已有 `close_sprint()`，但它只是把 status 改成 `closed`。它没有回答这些问题：

- 这轮 Sprint 关闭前是否真的没有阻断风险？
- 是否还有 open / candidate_ready / needs_more_work task？
- 是否有 pending / failed / provider_safe action queue item？
- 是否有 stale judge report / stale recommendation / stale metrics？
- 这轮改动是否真的被人工确认过？
- 哪个 Project Version 是本轮推荐的交付候选？
- 最终交付包需要附带哪些签核信息？
- 用户为什么可以放心关闭这轮反馈？

v3.5.0 要补的是“收口层”。

---

## 2. 一句话目标

v3.5.0 要让 Review Sprint 从“能推进反馈”升级为“能被正式收口和交付准出”：

```text
Sprint data
  -> Closeout Report
  -> Readiness Gate
  -> Signoff Record
  -> Manual close / override
  -> Project / Final Export provenance
```

核心不是替用户决定，而是把关闭前需要看的风险集中成一份本地报告。

## 4. 核心原则

### 4.1 Closeout 是门禁，不是执行器

Closeout Report 可以阻止 Sprint close。

Closeout Report 不允许：

- 创建 candidate。
- 执行 action queue。
- apply candidate。
- resolve task。
- archive task。
- 修改 project final version。
- 生成 final export。

它只读取当前状态，写一份 closeout report。

### 4.2 Close 必须人工确认

即使 closeout gate passed，也只能由用户点击 Close Sprint。

Action Queue 不能自动 close sprint。

Recommendation Report 不能自动 close sprint。

Provider Judge 不能自动 close sprint。

### 4.3 Force Close 必须可审计

允许用户在 gate failed 时强制关闭，但必须：

- `force=true`
- `override_reason` 非空
- 写入 signoff record
- 写入 project event
- closeout report 标记 `forced=true`
- Final Export 保留 forced closeout provenance

### 4.4 Closeout 必须可重复生成

Closeout Report 是派生报告。

可以删除后重建。

但 Signoff Record 是审计事实，不应该被 refresh 覆盖。

### 4.5 导出必须脱敏

Closeout / Signoff 里不能写入：

- provider key
- access token
- 本机绝对路径
- raw prompt
- raw provider response
- 未脱敏 reference 原文
- `.musicforge/provider.json`
- `.musicforge/renderer.json`

## 6. Closeout Gate 规则

### 6.1 状态枚举

`CloseoutReport.status`：

```text
passed
warning
failed
stale
not_ready
```

`readiness`：

```text
ready_to_close
needs_review
needs_candidates
blocked
stale
no_data
```

### 6.2 blocking checks

以下任一命中，默认 close 应返回 409：

| check_id | 条件 |
| --- | --- |
| open_tasks | 存在 open / candidate_ready / needs_more_work task |
| stale_tasks | 存在 stale task |
| blocking_conflicts | conflict report 有 blocking conflict |
| pending_queue_items | Action Queue 有 pending / running executable item |
| failed_queue_items | Action Queue 有 failed item |
| stale_recommendations | Recommendation Report source stale |
| stale_judge_reports | Judge Report stale |
| metrics_not_ready | Metrics readiness 不是 ready_to_close |
| missing_applied_version | Sprint 没有任何 applied candidate version，且无 selected_version_id |

### 6.3 warning checks

以下只产生 warning，不阻止 close：

| check_id | 条件 |
| --- | --- |
| unresolved_manual_required | 有 manual_required item |
| judge_local_disagreement | judge 推荐和 local ranking 不一致 |
| high_risk_judge_candidate | judge high risk candidate count > 0 |
| provider_tokens_high | 本轮 provider tokens 超过阈值 |
| quality_not_improved | quality_delta <= 0 |
| failed_candidates_present | 有 failed candidates |
| unrendered_audio | final candidate 没有 WAV |
| unrendered_stems | final candidate 没有 stems |

### 6.4 force close

默认：

```http
POST /close
{}
```

如果 `close_allowed=false`：

```json
{
  "error": "Review Sprint closeout gate failed. Refresh closeout report or pass force=true with override_reason."
}
```

强制关闭：

```json
{
  "force": true,
  "override_reason": "已人工试听确认，剩余 judge stale 为非阻断旧候选。",
  "selected_version_id": "v004",
  "notes": "Accepted for delivery."
}
```

强制关闭必须返回 200，并写入 signoff。

## 9. API 设计

### 9.1 Get Closeout

```http
GET /api/projects/<project-id>/review-sprints/<sprint-id>/closeout
```

行为：

- 如果 closeout-report.json 存在，返回。
- 如果不存在，构建但不强制写盘，或者写盘均可；建议写盘，便于 UI 首次展示。
- 不调用 provider。
- 不执行 queue。

返回：

```json
{
  "ok": true,
  "sprint": {},
  "closeout_report": {},
  "summary": {}
}
```

### 9.2 Refresh Closeout

```http
POST /api/projects/<project-id>/review-sprints/<sprint-id>/closeout/refresh
```

行为：

- 重新读取最新 tasks / candidates / conflicts / recommendations / queues / judge / metrics。
- 如 metrics 或 judge summary 缺失，可以读取已有，不要调用 provider。
- 写 closeout-report.json。

### 9.3 Get Signoff

```http
GET /api/projects/<project-id>/review-sprints/<sprint-id>/signoff
```

无 signoff 时返回：

```json
{
  "ok": true,
  "signoff": {},
  "summary": {
    "status": "not_signed"
  }
}
```

### 9.4 Close Sprint

现有：

```http
POST /api/projects/<project-id>/review-sprints/<sprint-id>/close
```

v3.5.0 改造 body：

```json
{
  "force": false,
  "override_reason": "",
  "selected_version_id": "v004",
  "notes": "Accepted after local playback."
}
```

逻辑：

1. 读取 / 刷新 closeout report。
2. 如果 closeout `close_allowed=false` 且 `force=false`，返回 409。
3. 如果 `force=true` 且 `override_reason` 为空，返回 400。
4. 写 signoff.json。
5. 关闭 sprint。
6. 刷新 project metrics 可选，建议做。
7. 返回 sprint + closeout + signoff。

响应：

```json
{
  "ok": true,
  "sprint": {},
  "closeout_report": {},
  "signoff": {},
  "summary": {}
}
```

## 13. 安全与边界

### 13.1 路径安全

Closeout 不应复制任何文件。

只读：

- `.musicforge/projects/<project-id>/...`
- runs 下版本产物的 metadata summary

不要打开候选 artifact 路径做复制。

### 13.2 脱敏

所有 closeout/signoff 写盘前调用 `sanitize_metadata()`。

blocked keys 参考现有 asset/final export 规则：

```text
api_key
token
secret
authorization
raw_prompt
raw_response
provider_snapshot
local_path
path
```

### 13.3 并发

SprintStore 已有 lock。新增 closeout/signoff 写入也必须在同一 lock 下。

Close 和 Refresh Closeout 并发时：

- close 写 signoff 后，不允许 refresh 覆盖 signoff。
- closeout report 可以刷新，但 signoff record 保持历史。

### 13.4 stale

Closeout Report 必须有 `source_hash`。

source 需要包含：

- sprint.to_dict()
- task summaries
- candidate summaries
- conflict report summary/hash
- recommendation report hash
- action queue summaries
- judge summary
- metrics summary
- project selected/final/latest version id

GET closeout 如果发现 source hash 不一致：

- 返回 `stale: true`
- `status: stale`
- 不自动 close

POST refresh 才更新。

## 18. 验收标准

v3.5.0 合格必须满足：

- 用户可以刷新 Sprint Closeout Report。
- closeout 能列出 blockers/warnings。
- gate failed 时普通 close 被 409 阻止。
- force close 必须带 override reason。
- force close 写 signoff。
- gate passed 时普通 close 成功。
- signoff 不被 closeout refresh 覆盖。
- Project Export 有 closeout/signoff summary。
- Final Export 有 closeout summary。
- Studio 能看到 Closeout 和 Signoff。
- release-check v3.5 smoke 通过。
- 全量测试通过。
- secret/path scan 通过。
- `.musicforge/provider.json`、`.musicforge/renderer.json` 不被提交。

## 19. Reviewer 重点检查点

开发完成后 reviewer 要重点看：

1. Close route 是否真的被 gate 拦住。
2. Force close 是否必须有 override reason。
3. Signoff 是否可能被 refresh 覆盖。
4. Closeout source hash 是否包含足够输入。
5. Project Export / Final Export 是否脱敏。
6. Final Export 多 Sprint latest 选择是否正确。
7. Closeout 是否意外调用 provider。
8. Action Queue 是否能绕过 close gate。
9. 已 closed sprint 是否还能被继续生成 candidates。
10. release-check 是否覆盖失败 close + force close + export。

## 20. 风险清单

### 风险 1：Closeout gate 太严，用户无法关闭

缓解：

- 支持 force close。
- override reason 必填。
- UI 清晰展示 blockers。

### 风险 2：Closeout gate 太松，失去意义

缓解：

- open task、stale judge、pending queue、blocking conflict 必须阻断。
- release-check 覆盖阻断。

### 风险 3：Signoff 被刷新覆盖

缓解：

- signoff 单独文件。
- closeout refresh 只写 closeout-report.json。
- 测试覆盖。

### 风险 4：Final Export 摘要混用多个 Sprint

缓解：

- 参考 v3.4.1 的 latest_sprint_id 修复方式。
- 多 Sprint 回归测试。

### 风险 5：UI 又变复杂

缓解：

- Closeout 只做一块面板。
- 列出 blockers/warnings 即可。
- 不做复杂图表。

## 22. 给开发的执行口径

这版不要追求“更智能”，要追求“更可靠地收口”。

开发时优先保证：

- close 不会误放行。
- force close 可审计。

# v5.6.0 Encoded Audio Acceptance 编码格式验收与交付听审施工图

日期：2026-05-31

角色定位：reviewer / planner

当前稳定基线：v5.5.1

目标版本：v5.6.0

---

## 1. 背景

v5.5.1 已经把 Distribution Audio Formats 的两个关键漏洞收住：

- 公开 API / Studio 不能再持久化 `fake_runner`。
- Release gate、Distribution gate、`verify-release`、`verify-distribution-package` 会拒绝 fake encoder evidence。
- Distribution package layout 会按 `audio_format_profiles` 生成包内 encoded audio entry。
- Distribution verifier 在 `--require-encoded-audio` 下会要求 encoded layout entries，并逐 profile / track 校验文件、manifest、hash、header。

所以现在系统已经能回答：

> 发行包里的 MP3 / FLAC / AAC 是否来自当前 Release Export？文件 hash / header / manifest 是否对得上？是不是 fake encoder 伪造？

但这还不是“可交付音频格式验收”。

真实交付时，客户或平台关心的不只是“文件存在”和“hash 对得上”：

- MP3 是否能被普通播放器打开？
- AAC/M4A 是否是真的 m4a，而不是只有 header 的伪文件？
- FLAC 是否完整，不是截断文件？
- 编码后音量、时长、声道、头尾静音是否明显偏离母带 WAV？
- 每个要交付的格式是否都被人实际抽听或逐曲听审？
- 如果某个格式听审失败，是否能回流到 Audio Revision / Fix Sprint？
- 如果编码 profile 被修改，旧的听审证据是否 stale？
- 如果 Distribution Target 要求某些格式，Release Signoff / Distribution Signoff 是否能强制要求这些格式的听审证据？

v5.6.0 要补的就是这一层：**Encoded Audio Acceptance，编码格式验收与交付听审**。

---

## 2. 版本定位

v5.6.0 是 v5.5.1 之后的质量层，不是再做一个编码器。

它的目标是：

> 对每个 Release 的每个 encoded audio profile 建立可审计的格式级健康报告、人工听审证据、问题回流和签核 gate。

一句话：

> v5.5 解决“MP3/AAC/FLAC 是否能生成并被包正确引用”，v5.6 解决“这些交付格式是否真的通过验收”。

---

## 3. 明确不做

v5.6.0 不做以下内容：

- 不做云转码。
- 不上传平台。
- 不做平台官方提交。
- 不做 DRM / 水印。
- 不做专业音频解码器全量兼容矩阵。
- 不做真正 LUFS / true peak 标准测量，除非本地已有可用工具；默认仍使用项目现有 proxy 指标。
- 不做自动替代人工听审。自动 health 只能辅助，release-ready gate 必须能要求 manual review。
- 不把 fake / fixture runner 的结果作为正式验收证据。
- 不把外部播放器日志伪装成系统自动判断。外部人工听审只能通过明确的 review import 或 Studio 手工录入。

注意：如果开发想用 FFprobe 做更强的格式探测，可以作为可选增强，但不能让 v5.6 强依赖它。没有 FFprobe 时，应输出 `warning` 或 `skipped_probe`，不能崩溃。

---

## 4. 为什么现在做

v5.0 到 v5.5.1 已经形成一条完整交付链：

```text
Project Version
  -> Final Export
  -> Release
  -> Audio QA
  -> Per-track Audio Review
  -> Mix / Audio Revision
  -> Mastering QA
  -> Encoded Audio
  -> Distribution Package
```

当前缺口在最后一步：

```text
selected mastered WAV
  -> MP3 / FLAC / AAC
  -> header / hash passed
  -> ? 是否能播放
  -> ? 是否听起来正常
  -> ? 是否和母带一致
  -> ? 是否有人确认
  -> ? 是否能进入签核 gate
```

v5.6 不做“更多生成能力”，而是继续把交付风险往前拦。

---

## 5. 核心目标

v5.6.0 完成后，系统必须支持：

1. 对 Release encoded audio 生成格式级 health report。
2. 对每个 `profile_id + track_id` 记录人工听审 review。
3. Review 绑定 encoded audio manifest hash、track output hash、source WAV hash、profile hash。
4. Release Signoff 可以要求 encoded audio manual acceptance。
5. Distribution Signoff 可以要求 target 所需格式全部有 current manual review。
6. `verify-release` 可以离线验证 encoded acceptance summary。
7. `verify-distribution-package` 可以离线验证包内 encoded acceptance evidence。
8. Studio 提供 Encoded Audio Review Board。
9. 失败 review 可以生成 ReviewTask / Audio Revision issue / Acceptance Fix Sprint 入口。
10. release-check 覆盖 happy path、stale、tamper、fake、missing review、synthetic-only、Distribution package 外部验证。

## 6. 新增模块建议

建议新增：

```text
song_agent/encoded_audio_health.py
song_agent/encoded_audio_reviews.py
song_agent/encoded_audio_acceptance.py
```

职责拆分：

- `encoded_audio_health.py`
  - 只负责格式级自动检查。
  - 输入 encoded manifest + 实际 encoded file。
  - 输出 health report。

- `encoded_audio_reviews.py`
  - 管理人工听审记录。
  - 管理 marker / issue / status / stale。
  - 不做 Release gate 判断。

- `encoded_audio_acceptance.py`
  - 汇总 health + review。
  - 提供 Release / Distribution gate summary。
  - 提供 export / verifier payload hash。

如果开发希望减少文件数量，可以先合并为 `encoded_audio_acceptance.py`，但 reviewer 建议拆开，避免 v5.6 后续继续膨胀。

## 7. 落盘结构

建议 Release 目录下新增：

```text
.musicforge/releases/<release-id>/encoded-audio/
  formats/<profile-id>/
    manifest.json
    tracks/<track-id>/song.<ext>
  acceptance/
    health/
      <profile-id>.json
      <profile-id>.<track-id>.json
    reviews/
      <profile-id>.<track-id>.json
    markers/
      <profile-id>.<track-id>.<marker-id>.json
    summary.json
    events.jsonl
```

说明：

- health report 可以按 profile 聚合，也可以每 track 一个文件。
- review 必须逐 track / profile 记录，不能只写 profile 级一句“通过”。
- summary 是派生结果，必须可由 health + reviews 重算。
- events 记录 create/update/import/delete/reset。
- 所有 JSON 写入必须走现有原子写入方法。
- 所有路径必须限制在 release encoded-audio/acceptance/ 内。

建议字段：

```json
    "encoded_manifest_hash": "...",
    "encoded_source_hash": "...",
    "profile_hash": "...",
    "runner_kind": "ffmpeg"
  },
  "summary": {
    "status": "passed",
    "track_count": 10,
    "passed_count": 10,
    "warning_count": 0,
    "failed_count": 0
  },
  "tracks": [
    {
      "track_id": "track-000001",
      "status": "passed",
      "path": "formats/mp3_320/tracks/track-000001/song.mp3",
      "file_size_bytes": 1234567,
      "sha256": "...",
      "format": "mp3",
      "extension": "mp3",
      "header_status": "passed",
      "duration_seconds": 184.2,
      "source_wav_duration_seconds": 184.1,
      "duration_delta_seconds": 0.1,
      "channels": 2,
      "sample_rate": 44100,
      "probe_status": "skipped_probe",
      "warnings": [],
      "failures": []
    }
  ],
  "integrity_hash": "..."
}
```

必须检查：

- file exists
- not symlink
- path within encoded-audio formats dir
- output hash matches manifest
- header matches expected format
- file size over profile-specific minimum
- duration roughly matches source WAV when duration can be known
- source manifest is current
- fake evidence rejected

建议最小大小阈值：

```text
mp3: 16 KiB
flac: 16 KiB
aac/m4a: 16 KiB
wav: 44 bytes minimum, but release-ready 应该远大于 44 bytes
```

阈值不要写死成唯一标准，应该 profile 可配置，默认保守。

## 9. Source Hash 设计

Encoded Audio Review 的 source hash 必须绑定：

- release_id
- profile_id
- track_id
- encoded manifest integrity hash
- encoded manifest source hash
- encoded track output sha256
- profile hash
- health report hash
- source WAV sha256

不能绑定：

- review notes
- reviewer
- markers
- created_at / updated_at
- events

原因：

- review 写入后不能让自己 stale。
- 但 encoded file、profile、source WAV、health report 变化必须让 review stale。

Acceptance summary source hash 必须绑定：

- required profiles
- current encoded manifest hashes
- current health hashes
- current review hashes
- review stale flags

## 10. 自动 Health 检查

### 10.1 Header 检查

复用 v5.5 的 `detect_audio_format_bytes()`：

- MP3: `ID3` 或 frame sync
- FLAC: `fLaC`
- WAV: `RIFF...WAVE`
- AAC/M4A: `ftypM4A` / `ftypisom` 等

### 10.2 Size 检查

不能再接受只有 header 的假文件。

建议增加 profile 默认最小大小：

```json
{
  "mp3_320": {"min_bytes": 16384},
  "mp3_v0": {"min_bytes": 16384},
  "flac_lossless": {"min_bytes": 16384},
  "aac_256": {"min_bytes": 16384}
}
```

如果 track 很短，仍可 warning，而不是硬失败。建议：

```text
duration < 5s: min_bytes 降级为 warning
duration >= 5s: min_bytes failed
```

### 10.3 Duration 检查

如果能从 manifest/source 获取 duration：

```text
abs(encoded_duration - source_wav_duration) <= max(1.0, source_duration * 0.01)
```

没有 FFprobe 时：

- WAV 可用本地 wave 模块读 duration。
- MP3/AAC/FLAC duration 可以 `skipped_probe`。
- skipped 不应默认 failed，但 release-ready profile 可以要求 probe。

### 10.4 Format Compatibility

检查：

- profile.format 和 file extension 一致。
- manifest format 和 package audio_format 一致。
- track output path extension 和 profile extension 一致。
- Distribution package 中实际 entry extension 和 profile extension 一致。

### 10.5 Fake Evidence

任何 health / acceptance / verifier 遇到：

```json
"fake_evidence": true
```

或：

```json
"encoder": {"runner": {"kind": "fake"}}
```

必须 failed，不能 warning。

## 11. API 设计

### 11.1 Release Encoded Health

```http
POST /api/releases/<release-id>/encoded-audio/health
GET  /api/releases/<release-id>/encoded-audio/health
GET  /api/releases/<release-id>/encoded-audio/health/<profile-id>
```

POST payload：

```json
{
  "profile_ids": ["mp3_320", "flac_lossless"],
  "force": false
}
```

行为：

- signed release 默认只读，除非已有 reset 流程允许。
- health refresh 不应修改 encoded audio 文件，只写 health report。
- 如果 encoded manifest missing/stale/fake，返回 409 或 health failed report，二者择一，但 release-check 必须固定口径。

建议：

- API 返回 200，report status failed，适合 Studio 展示。
- 只有路径越界、release missing、profile invalid 才 400/404。

### 11.2 Review Board

```http
GET  /api/releases/<release-id>/encoded-audio/reviews
POST /api/releases/<release-id>/encoded-audio/reviews
GET  /api/releases/<release-id>/encoded-audio/reviews/<review-id>
PATCH /api/releases/<release-id>/encoded-audio/reviews/<review-id>
DELETE /api/releases/<release-id>/encoded-audio/reviews/<review-id>
```

POST payload：

```json
{
  "profile_id": "mp3_320",
  "track_id": "track-000001",
  "status": "accepted",
  "rating": 5,
  "review_mode": "manual",
  "reviewer": "developer",
  "playback_confirmed": true,
  "notes": "Checked in VLC and browser preview.",
  "markers": []
}
```

规则：

- `review_mode=manual` 必须有 `reviewer`。
- `accepted` 必须 `playback_confirmed=true`。
- `rating` 范围 1..5。
- `needs_fix/rejected` 可以带 markers。
- PATCH 后必须重算 `integrity_hash`。
- DELETE 只允许未签核 Release，或改成 `hidden=true`，不要物理删除审计证据。

### 11.3 Acceptance Summary

```http
POST /api/releases/<release-id>/encoded-audio/acceptance/refresh
GET  /api/releases/<release-id>/encoded-audio/acceptance
```

payload：

```json
{
  "required_profiles": ["mp3_320", "flac_lossless"],
  "require_manual_review": true
}
```

### 11.4 Marker 回流

```http
POST /api/releases/<release-id>/encoded-audio/reviews/<review-id>/markers/<marker-id>/review-task
POST /api/releases/<release-id>/encoded-audio/reviews/<review-id>/markers/<marker-id>/audio-revision
```

第一阶段可以只做 ReviewTask：

- task title 包含 profile / track / marker label。
- task source 写 `encoded_audio_review_marker`。
- task context 带 profile_id、track_id、seconds、severity。
- 防重复 open task。

## 16. Release Signoff Gate

Release signoff payload 新增：

```json
{
  "require_encoded_audio": true,
  "required_audio_format_profiles": ["mp3_320"],
  "require_encoded_audio_review": true
}
```

Gate 规则：

1. `require_encoded_audio=true` 仍沿用 v5.5.1 encoded gate。
2. `require_encoded_audio_review=true` 时，必须先满足 encoded gate。
3. 每个 required profile / track 必须有 current review。
4. review 必须 manual/external_import accepted。
5. health failed 不允许签核。
6. health warning 可否 force，需要明确：
   - 默认 warning 阻断。
   - `force=true` + `override_reason` 可以覆盖 warning。
   - fake/stale/missing/integrity failed 不能 force。

Signoff evidence 写入：

```json
"encoded_audio_acceptance": {
  "status": "passed",
  "summary_hash": "...",
  "required_profiles": ["mp3_320"],
  "manual_review_count": 10,
  "warning_override": false
}
```

## 19. Redaction 与安全

Review notes / device / reviewer / marker notes 都必须脱敏：

- API key
- token
- Bearer
- Windows path
- UNC path
- local absolute path
- provider raw response

下载 encoded audio 文件时：

- 只允许 manifest 中当前 track 的 output path。
- path 必须解析到 `.musicforge/releases/<release-id>/encoded-audio/formats/<profile-id>/tracks/<track-id>/` 内。
- stale/fake manifest 不能下载。

Review JSON export：

- 不写本机绝对路径。
- 不写 raw config path。
- 不写 ffmpeg full path，只写 basename / command hash。

---

## 20. Integrity 与 Tamper

必须补以下篡改检测：

1. 改 review status 从 `needs_fix` 到 `accepted` -> verifier failed。
2. 改 `review_mode` 从 synthetic 到 manual -> verifier failed。
3. 改 review `source.encoded_track_hash` -> verifier failed。
4. 改 health summary status -> verifier failed。
5. 删除某个 profile review -> signoff 409 / verifier failed。
6. 替换 package MP3 文件但不改 manifest -> verifier failed。
7. 替换 package MP3 文件并同步改 manifest，但不改 review source -> verifier failed。
8. fake encoder summary -> signoff 409 / verifier failed。
9. signed Release 后尝试改 review -> 409，或要求 reset signoff 后才能改。

## 21. 测试计划

### 21.1 单元测试

## 25. 风险点

### 25.1 不要把 header 检查当成播放成功

header 只能证明格式大致正确，不能证明普通播放器一定能播。

所以 v5.6 必须把 manual playback review 放进 gate。

### 25.2 不要让 synthetic review 混进正式签核

自动测试可以用 synthetic，但 release-ready 必须 manual/external_import。

### 25.3 不要让 review 更新污染 source hash

review notes / marker 更新不应让 review 自己 stale。

source hash 只绑定音频和 profile 证据。

### 25.4 不要让 Distribution target 漏 profile

如果 target 要 `["mp3_320", "flac_lossless"]`，package 和 review 都必须覆盖两者。

### 25.5 不要把 fixture runner 结果误认为真实编码

测试里可以注入 fixture runner，但 manifest 必须标明 runner kind。如果不是真实 ffmpeg/passthrough evidence，正式 gate 要拒绝。

# v14.2.0 MusicForge 类型精度收敛与大模块职责拆分施工图

日期：2026-07-19

当前稳定基线：v14.1.2

基线提交：`b824bb132fa7c573929532cf03a2c08a8c31c038`

版本性质：架构清债版本，不新增产品功能

目标版本：v14.2.0

## 1. 文档目的

v14.0 完成了领域纵向迁移和兼容层退出，v14.1 建立了全活跃树 mypy、全仓 Ruff、Explicit `Any` 和逐文件复杂度 ratchet，但当前代码仍存在两类明确债务：

1. TYPE-003：活跃树仍有大量 Explicit `Any`，接口装配和领域文档尤其集中。
2. ARCH-014：137 个生产模块超过 600 行，其中 37 个超过 1000 行。

v14.2.0 的任务不是继续增加新的 Board、Center、Hub、Vault、Archive 或业务 gate，而是把已经建立的模块化单体架构变得可维护：

- 先把 Explicit `Any` collector 升级为不能通过作用域导入或类型别名绕过的 schema v3。
- 再替换机械生成的接口装配和不透明动态文档。
- 按 bounded context 拆分承担多种职责的大模块。
- 保持 CLI、API、Studio、证据包、签核、迁移和离线 verifier 行为兼容。
- 用可重复的机器指标证明债务下降，禁止靠移动文件、改名或拆成无语义小文件获得数字改善。

本施工图是 v14.2.0 的唯一执行范围。开发可以分阶段提交，但在所有最终门禁通过前不得创建 v14.2.0 tag 或 GitHub Release。

## 2. Reviewer 结论与基线

v14.1.2 可以作为 v14.2 开发基线：

- HEAD、`origin/master`、annotated tag 和 Release target 均绑定 `b824bb132...`。
- 当前活跃树 mypy 为 0 error，Ruff 全仓通过。
- Explicit `Any` schema v2 已正确覆盖直接 `Any`、typing 模块、顶层导入别名、模块别名、嵌套注解和字符串注解。
- 当前 schema v2 实测与策略中的总量、层级和逐文件预算完全一致。
- 复杂度 ratchet 已按逐文件 ceiling 阻断增长，不能跨文件对冲。
- v14.1.2 Release reviewer package、Quality 和 Nightly LTS 已通过。

但 schema v2 仍存在两个未来绕过形式，必须在任何 Any 削减前修复：

```python
if TYPE_CHECKING:
    from typing import Any as Alias

value: Alias
```

```python
from typing import Any, TypeAlias

Alias: TypeAlias = Any
value: Alias
```

当前活跃树没有这两类写法，所以 v14.1.2 基线数字有效；但若不先升级 collector，后续代码可以在不触发 ratchet 的情况下重新引入动态类型。

## 5. 版本边界

### 5.1 本版必须完成

- Explicit `Any` collector schema v3，并关闭本施工图列出的所有绕过形式。
- 类型预算按 schema v3 重新生成，迁移只能发生一次且必须可审计。
- 清除机械 CLI adapter 中的大规模 `_InterfaceType` / `_InferenceType` 动态注解。
- 将 API route context 改为按 use case 划分的 typed Protocol/context，不再使用一个巨型 `Any` inventory。
- 将不可信 JSON 在边界解析为 typed DTO、TypedDict、dataclass 或明确的 `Mapping[str, object]`。
- 拆分所有超过 1000 行的模块，任何生产模块不得继续超过 1000 行。
- 优先拆分 trust、quality、program 的 orchestration/store/verifier 混合模块。
- 保持依赖方向 `interfaces -> application -> domains -> platform`。
- 保持所有公开 CLI 命令、参数、HTTP 路由、响应语义和 Studio 控件兼容。
- 保持 signed evidence、history、binding、manifest、ZIP、migration 和 rollback 语义兼容。
- 更新 ADR、DEBT、CURRENT、TARGET、quality policy、README 和 CHANGELOG。
- 新增 v14.2 release-check smoke，并进入 v14、latest、ga、security 和 full profiles。

### 5.2 本版禁止

- 新增产品功能或新的治理产品名词。
- 新增第七个 bounded context。
- 用 `Any` 改成 `object` 但继续无验证地调用、索引或转换，冒充类型精度提升。
- 用 `cast(Any, ...)`、`# type: ignore`、动态 `getattr`、`globals()` 或 import alias 隐藏债务。
- 用 `Alias = Any`、`Alias: TypeAlias = Any`、条件导入或字符串注解绕过 collector。
- 将大模块机械切成 `part_01.py`、`helpers_2.py`、`misc.py`、`common.py` 等无职责文件。
- 新增只做 wildcard re-export 或动态转发的大型 facade。
- 为降低行数复制代码、压缩多条语句到一行、删除注释/测试或移动到 tests/tools。
- 放宽 mypy、Ruff、coverage、architecture、performance 或 security 门禁。
- 缩小 mypy roots、coverage roots、active suite 或 release-check profile。
- 改写历史已签核证据或静默迁移持久化数据。
- 自动 approve、signoff、reset、publish、upload 或生成伪造人工证据。

### 5.3 非目标

- 不引入微服务、网络队列、远程数据库或分布式事务。
- 不重做 Studio 视觉设计。
- 不改变 Renderer、Provider、音频验收和发布业务规则。
- 不要求把合法的外部反序列化边界伪装成完全静态；合法动态边界必须显式登记和收窄。

## 7. Phase 0：Explicit Any Collector Schema v3

Phase 0 是独立发布阻断项。未完成时不得开始重新生成预算，也不得把 Any 削减计入成绩。

### 7.1 统计语义

schema v3 必须同时输出：

- `syntactic_any_count`：注解和类型别名声明中直接出现或通过 import alias 出现的 Any leaf 数量。
- `effective_any_annotation_count`：类型别名展开后，实际包含 Any 的注解 leaf 数量。
- total、layer、file、symbol 四级明细。
- approved dynamic boundary 与 unapproved dynamic usage 的分离统计。
- collector schema/version、source tree hash 和 policy integrity。

### 7.2 必须识别

- `Any`
- `typing.Any`
- `typing_extensions.Any`
- `from typing import Any as Alias`
- `from typing_extensions import Any as Alias`
- `import typing as t; t.Any`
- `import typing_extensions as tx; tx.Any`
- module、class、`if TYPE_CHECKING` 等合法作用域中的导入。
- `Alias = Any`
- `Alias: TypeAlias = Any`
- `type Alias = Any`，在当前 Python AST 支持时。
- `Alias = list[Any]`、别名链和嵌套 generic。
- 字符串/forward-ref 注解。
- function 参数、返回值、变量、class attribute、type alias。

### 7.3 解析约束

- 使用 lexical scope symbol table，不能简单把全文件所有 alias 合并后造成无关 shadowing 误报。
- 类型别名展开必须有 cycle detection 和最大深度保护。
- 同名普通 class/variable 不得被误认为 `typing.Any`。
- 解析失败必须产生 blocker，不能返回 0。
- Python 3.11、Windows 和 Linux 行为必须一致。

### 7.4 策略迁移

- `explicit_any_collector_schema_version` 从 2 升到 3。
- updater 只能显式允许 `2 -> 3`；任意其他 mismatch 必须 fail closed。
- 增加显式 `--accept-collector-migration 2:3` 或等价受控参数。
- 迁移必须绑定 ADR-016 hash 和旧/新统计摘要。
- schema 升级只允许一次，后续仍执行 total/layer/file/symbol no-growth。
- 禁止因为 schema mismatch 自动接受任意新预算。

### 7.5 必测攻击样例

- 条件导入 alias 增加 100 个 annotation，必须触发 total/layer/file blocker。
- class scope import alias。
- Python 3.11 `Alias: TypeAlias = Any`。
- chained alias：`A = Any; B = list[A]; value: B`。
- quoted chained alias。
- alias cycle，必须安全失败而不是 hang。
- shadowed `Any` 普通 class，不得误报。
- policy schema downgrade/upgrade spoof。
- 仅修改 policy 预算并重签 integrity，仍必须被迁移 authority 阻断。

## 8. Phase 1：接口层类型收敛

这是 TYPE-003 的第一大削减波次，优先处理约 4,949 个 interface Any。

### 8.1 CLI 装配

当前多个 CLI adapter 通过超长 tuple assignment 从 `dependencies` 注入数百个符号，并用 `_InterfaceType` 标注。v14.2 必须：

- 按 creation、quality、delivery、trust、program、maintenance、release-check 建立小型 typed command context。
- command handler 只声明自己需要的 Protocol/Callable/Store interface。
- 使用静态 import 或显式 dataclass/context，不再一次绑定数百个名字。
- parser builder、command executor、presenter、verifier adapter 分开拥有职责。
- 保持现有 command name、argument、default、exit code、stdout JSON schema 不变。
- 删除已无引用的 generated adapter，不保留兼容 wrapper 供 active code 使用。

### 8.2 HTTP route context

当前 `CoreRouteContext` 等类把 handler、server、store、response writer 全部标成 `Any`。v14.2 必须：

- 按 route family 定义最小 Protocol，而不是一个全局 Server Protocol。
- 将 auth、request decode、response writer、download、store access 分为独立 typed capability。
- route handler 依赖 application command/query，不直接写 Store。
- framework 原始 request/body 先作为 `object` 进入 parser，成功校验后才进入 typed DTO。
- 保持 route count、method/path、status code、error code 和 redaction 行为兼容。

### 8.3 Web/Studio

- 不新增视觉功能。
- 保持已有 endpoint 和 control marker。
- 若接口类型迁移改变生成数据，必须通过 public contract snapshot 证明语义一致。

## 9. Phase 2：领域文档与内部契约收敛

### 9.1 允许使用的类型

- immutable dataclass：稳定领域实体和值对象。
- `TypedDict`：固定 JSON sidecar/report schema。
- `Protocol`：Store、verifier、clock、renderer、provider 等行为依赖。
- `Mapping[str, object]`：只读未知键边界。
- `Sequence[T]` / `Iterable[T]`：无需 mutation 的集合。
- discriminated union：status/event/action 的有限集合。

### 9.2 禁止的替代方式

- 不允许全仓机械替换 `Any -> object`。
- 不允许创建新的万能 `Document = dict[str, object]` 后继续任意索引。
- 不允许为通过 mypy 到处 `cast()`。
- 不允许把 runtime validation 删掉后只依赖静态类型。

### 9.3 优先领域

1. trust：GA readiness、Public Trust Center、Trust Operations。
2. program：Unified Program、Continuity、Handoff、Acceptance。
3. quality：Review Tasks、Audio Revision、Music Acceptance。
4. delivery：Release verifier、Submission Evidence、Rights。
5. studio：Song Editor、Project Repository。
6. creation：Encoded Audio Acceptance、Final Export。

每个领域先定义 contract，再迁移 parser/normalizer，再迁移 service/store，最后收紧 public return type。不得先删除旧类型再补验证。

## 10. Phase 3：大模块职责拆分

### 10.1 通用拆分规则

Store 模块应拆为：

- model/schema
- repository/persistence
- command/service
- query/projection
- policy/state transition
- export/package assembly

Verifier 模块应拆为：

- package contract/allow-list
- structural checks
- source/external binding checks
- semantic reconstruction
- redaction/path security checks
- report writer/exit code adapter

Orchestrator 模块应拆为：

- input contract
- evidence loader
- policy evaluation
- decision/result projection
- application service

拆分后的 domain 模块之间不能通过反向 import 或运行时 mutation 重新耦合。

### 10.2 Wave A：trust

- `ga_readiness.py`：拆分 request contract、evidence loading、gate orchestration、summary projection。
- `ga_readiness_verifier.py`：拆分 report contract、external evidence binding、requirement checks、CLI adapter。
- `public_trust_center.py`：拆分 source collection、readiness projection、sidecars/fingerprints、package assembly、sanitization。
- 其他超过 1000 行 trust 模块按 lifecycle、verification、publication、portfolio 子域拆分。

准出：trust 不得有超过 1000 行模块，且 trust oversized 总行数至少下降 60%。

### 10.3 Wave B：quality

- `review_tasks.py`：拆分 task model/store、candidate generation、scoring、decision、summary、validation。
- `audio_revision.py`：拆分 issue/session、candidate render、review/select、apply/recheck、closeout。
- `music_acceptance.py`：拆分 profile/case、evidence collection、evaluation、summary/export。
- 保持人工听审、真实 WAV、fake/test guard 和 stale source 行为不变。

准出：quality 不得有超过 1000 行模块，且相关 audio/review 定向测试必须保持行为一致。

### 10.4 Wave C：program

- 拆分 Continuity Command Center Acceptance、Handoff、Program lifecycle 大模块。
- 将 source binding、review response、quorum、signoff、reset、archive 分为独立职责。
- 必须继续使用共享 verification/lifecycle/persistence kernel，禁止复制 hash-chain 或 ZIP 检查。

准出：program 不得有超过 1000 行模块，双 reset、successor signoff、external proof 和 signed mutation 回归保持通过。

### 10.5 Wave D：delivery

- `release_verifier.py` 拆为 package contract、audio/metadata/rights checks、external evidence checks 和 report projection。
- Submission Evidence 与 Rights Clearance 分离 source discovery、policy evaluation 和 export。

准出：delivery 不得有超过 1000 行模块，Release/Distribution/Submission verifier 结果与基线一致。

### 10.6 Wave E：studio 与 creation

- `song_editor.py` 拆为 command model、edit operations、validation、preview、event persistence。
- Project Repository 保留 persistence authority，不把业务规则塞回 repository。
- Encoded Audio Acceptance 与 Final Export 分离 format health、review evidence、manifest/export。

准出：编辑、preview、candidate apply、audio health、final export 的 contract tests 和 artifact hash 行为一致。

## 11. 数据、证据和迁移安全

- 本版默认不改变持久化 schema。
- 如果拆分导致存储路径或文档结构变化，必须注册显式 migration，并提供 byte-identical rollback rehearsal。
- 已签核 report、history、binding 和 ZIP 不得因代码重构被静默重写。
- verifier 必须继续从外部 proof/runtime source 重建事实，不能退回 package-internal self-consistency。
- fixed allow-list、duplicate/raw-backslash/trailing-data/path traversal/.MusicForge/redaction 检查必须保留。
- migration 前后 current pointer、immutable artifact 和 logical state 都必须验证。

## 12. 兼容性要求

### 12.1 CLI

- command/subcommand 名称不变。
- 参数名称、required/default、可重复参数和 exit code 不变。
- `--json` schema 和 redaction 不变。

### 12.2 API

- method/path 不变。
- success/error status code 不变。
- `ok`、`status`、`blockers` 等公共字段语义不变。
- force 不能绕过 hard gate。

### 12.3 Python imports

- 公开 import 若需移动，使用显式静态 facade。
- facade 只能 re-export，不得承载业务逻辑。
- active tree 不得反向 import compatibility/archive。

### 12.4 Evidence packages

- package type、entry allow-list、manifest semantics 和 external binding 不变。
- 任何有意 schema bump 必须 versioned，并提供旧包 differential verifier 测试。

## 18. 发布流程

1. 开发完成后保持工作区未发布，先提交 reviewer report。
2. 修完 reviewer P1/P2 后再形成 release candidate commit。
3. 在已提交且干净的工作区运行最终 GA；`git.status` 必须通过。
4. 推送 master。
5. 等待 final SHA Quality 全绿。
6. 手动运行 final SHA Nightly LTS 并确认全绿。
7. 创建 annotated tag `v14.2.0`，解引用必须等于 final SHA。
8. 创建 GitHub Release，并上传 reviewer package、SHA256 和 verification JSON。
9. 从 GitHub Release 重新下载资产并离线验证。
10. 核验 HEAD、origin/master、tag、Release target、Latest Release 完全一致。

不得先 tag 再继续修代码；任何 final SHA 变化都必须重新生成 reviewer evidence 并重跑 final gates。

## 19. 准出判定

v14.2.0 只有同时满足以下条件才能发布：

- schema v3 全部绕过回归通过。
- Any 和复杂度达到第 6 节硬上限。
- 所有剩余动态边界和大模块例外逐项登记。
- active dependency violations、cycles、compatibility imports 均为 0。
- mypy 0 error、Ruff 0 error、public dynamic 0、untyped public 0。
- 所有公开 CLI/API/Web contract 兼容。
- evidence package 和 signed lifecycle 兼容。
- migration 可验证、rollback byte-identical。
- active pytest、v14/latest/security/ga/full、Quality、Nightly 全绿。
- reviewer package 下载复验通过。
- 工作区干净，版本、tag、Release target 一致。

如果只完成 schema v3 而未完成实质 Any/复杂度削减，不得发布 v14.2.0；应继续开发或缩小为明确的 v14.1.x hotfix。若达到削减目标但仍有 residual exception，发布说明必须准确保留 TYPE-003/ARCH-014 状态，不能宣称全部清零。

## 20. 给开发的执行说明

本版不是继续堆功能，也不是数字美化。先用测试把 collector 的剩余绕过固定下来，再升级 schema；之后从 CLI/API 机械装配和六个领域最大的职责混合模块开始清债。每一波都要先建立 contract 和 differential tests，再移动实现。不要用 `Any -> object`、`part_01.py` 或万能 facade 换取指标下降。

开发完成后先提交未发布的 reviewer 候选，并附完整 before/after 指标。Reviewer 确认没有类型绕过、职责假拆分、兼容回归和证据语义变化后，才能提交最终 release candidate、运行干净工作区 GA、推送、打 tag 和发布。

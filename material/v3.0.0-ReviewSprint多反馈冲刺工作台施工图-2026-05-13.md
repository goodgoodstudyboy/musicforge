# v3.0.0 Review Sprint 多反馈冲刺工作台施工图

日期：2026-05-13

当前稳定基线：v2.9.0

目标版本：v3.0.0

定位：在 v2.8.0 到 v2.9.0 已经完成“单条 ReviewTask 的本地/provider 候选与决策报告”后，把 MusicForge 推进到项目级多反馈管理。v3.0.0 的目标不是让 AI 自动改完整首歌，而是建立一个 Review Sprint 工作台，让用户把多个 ReviewTask 放进一个可排序、可批量生成候选、可检测冲突、可逐项 apply/resolve 的创作冲刺。

---

## 1. 背景

到 v2.9.0，单条反馈闭环已经很完整：

```text
Audition Review
  -> ReviewTask
  -> Local Candidates
  -> Provider Candidates
  -> Decision Report
  -> User Apply One Candidate
  -> Resolve or Needs More Work
```

这解决了“一条反馈怎么修”的问题。

但真实创作不是只有一条反馈。用户通常会对同一首歌提出很多 review：

- intro 太长。
- verse bass 太满。
- pre chorus 过渡不够强。
- chorus hook 要保留但能量要更高。
- bridge 情绪不够明显。
- drums 在第二段太密。
- 某个候选修完后又产生新的 follow-up task。

如果继续只围绕单个 ReviewTask 做增强，系统会变成很多孤立任务：

- 用户不知道先修哪个。
- 多个 task 可能同时改同一 section/track。
- 批量生成 candidates 没有统一进度。
- 已 resolved / needs_more_work / stale 的任务混在一起。
- Project Export 有 task 列表，但没有阶段性“这一轮评审冲刺”的视角。
- Review Workbench 会越来越长，难以管理。

所以 v3.0.0 要引入 `ReviewSprint`。

---

## 2. 一句话目标

v3.0.0 要把 MusicForge 从“单条反馈工作台”升级成“项目级反馈冲刺工作台”：

```text
Project Reviews
  -> Create Review Sprint
  -> Select / Prioritize ReviewTasks
  -> Detect Conflicts
  -> Batch Generate Local/Provider Candidates
  -> Inspect Decision Reports
  -> Apply Candidates One By One
  -> Track Sprint Progress
  -> Close Sprint
```

关键原则：

- Sprint 只是组织层，不绕过 ReviewTask 状态机。
- Sprint 不自动 apply。
- Sprint 不自动 resolve。
- Sprint 可以批量 generate candidates，但 apply 仍必须用户逐项确认。
- Sprint 需要检测 task 间冲突，但不强行自动合并冲突。
- Sprint 关闭后可以导出 sprint summary，进入 Project Export / Final Export provenance。

---

## 3. 版本边界

### 3.1 v3.0.0 必须做

- 新增 `ReviewSprint` 数据模型和持久化。
- 支持从已有 ReviewTask 创建 Sprint。
- 支持添加/移除 Sprint task。
- 支持 Sprint task 排序和优先级。
- 支持 Sprint progress summary：
  - total tasks
  - open/candidate_ready/applied/resolved/needs_more_work/stale/archived count
  - local/provider candidate count
  - ready candidate count
  - conflict count
- 支持 Sprint conflict detection：
  - 同 section 冲突
  - 同 track 冲突
  - 同 section + same role 冲突
  - 同 target marker 附近冲突
  - stale task 冲突
  - parent version 不一致冲突
- 支持 Sprint batch local candidate generation。
- 支持 Sprint batch provider candidate generation，使用 mock provider 测试。
- 支持 Sprint decision rollup，把每个 task 的 Decision Report 汇总。
- Studio 新增 Review Sprints 工作区。
- Review Workbench 里可以把 task 加入 Sprint。
- Project Compare / Project Export / Final Export summary 纳入 Sprint provenance。
- release-check 增加 v3.0 Review Sprint smoke。
- README / CHANGELOG / version bump。

### 3.2 v3.0.0 可以做，但不强制

- Sprint template：Mix polish / Hook polish / Arrangement pass。
- Sprint 自动推荐 task 顺序。
- Sprint bulk archive resolved tasks。
- Sprint export 单独 JSON。
- Sprint duplicate。
- Sprint filtering：source/local/provider/conflict/priority。

### 3.3 v3.0.0 不做

- 不做自动 apply 多个 task。
- 不做自动 resolve 多个 task。
- 不做自动合并多个 candidate patch。
- 不做“one click fix all”。
- 不做跨 Project Sprint。
- 不做多人协作。
- 不做云同步。
- 不做 provider 自动判断最终版本。
- 不做音频理解、BPM/key 检测、音频转 MIDI。
- 不做大型 scheduler 或 workflow engine。

## 4. 核心判断

v3.0.0 不应该继续往单个 ReviewTask 里加复杂功能。

原因：

- v2.8 已经有 local candidates。
- v2.9 已经有 provider candidates 和 Decision Report。
- 一条 task 的能力足够完整。
- 下一阶段真正的瓶颈是多个 task 的组织、冲突、进度和批量生成。

`ReviewSprint` 应该是轻量组织层：

```text
ReviewSprint
  contains ReviewTask refs
  reads ReviewTask state
  invokes existing ReviewTask candidate generation APIs
  never bypasses ReviewTask apply guards
```

不要把 Sprint 做成新的编辑执行引擎。

## 5. 数据结构设计

### 5.1 存储目录

```text
.musicforge/projects/<project-id>/review-sprints/
  sprint-001/
    sprint.json
    events.jsonl
    summary.json
    conflict-report.json
```

不要把 candidate 或 SongPlan 复制进 Sprint。Sprint 只引用 ReviewTask。

### 5.2 ReviewSprint

```python
@dataclass(frozen=True)
class ReviewSprint:
    schema_version: int
    sprint_id: str
    project_id: str
    name: str
    description: str
    status: str
    parent_version_id: str | None
    task_refs: list[dict[str, Any]]
    settings: dict[str, Any]
    counts: dict[str, int]
    selected_task_id: str | None
    created_at: str
    updated_at: str
    closed_at: str | None = None
```

Status：

```text
open
in_progress
blocked
closed
archived
```

task_refs：

```json
[
  {
    "task_id": "review-task-001",
    "order": 1,
    "priority": 80,
    "lane": "arrangement",
    "included": true,
    "notes": "Fix first",
    "added_at": "2026-05-13T..."
  }
]
```

settings：

```json
{
  "local_candidate_strategies": ["balanced"],
  "provider_candidate_count": 2,
  "provider_template_id": "provider-review-candidates",
  "generate_provider": false,
  "render_midi": true,
  "stop_on_conflict": false
}
```

### 5.3 Sprint Summary

`summary.json`：

```json
{
  "schema_version": 1,
  "sprint_id": "sprint-001",
  "project_id": "project-001",
  "status": "in_progress",
  "task_count": 6,
  "counts": {
    "open": 2,
    "candidate_ready": 2,
    "applied": 1,
    "resolved": 1,
    "needs_more_work": 0,
    "stale": 0,
    "archived": 0,
    "ready_candidate_count": 9,
    "provider_candidate_count": 4,
    "conflict_count": 2
  },
  "recommended_order": [
    "review-task-003",
    "review-task-001",
    "review-task-002"
  ],
  "updated_at": "2026-05-13T..."
}
```

Summary 可以每次 API 请求时派生，也可以写盘。建议写盘，方便 export 和 release-check 验证。

### 5.4 Conflict Report

`conflict-report.json`：

```json
{
  "schema_version": 1,
  "sprint_id": "sprint-001",
  "created_at": "2026-05-13T...",
  "conflicts": [
    {
      "conflict_id": "conflict-001",
      "severity": "warning",
      "kind": "same_section_track",
      "task_ids": ["review-task-001", "review-task-002"],
      "section_name": "chorus",
      "track_name": "bass",
      "message": "Two tasks target chorus / bass. Apply one and refresh the other before continuing."
    }
  ],
  "stale_task_ids": [],
  "blocked_task_ids": []
}
```

Severity：

```text
info
warning
blocking
```

Blocking conflicts：

- stale task。
- task parent_version_id 和 Sprint parent_version_id 不一致且 settings 要求 same parent。
- task 已 archived。
- task 已 selected/applied 但 Sprint 试图 batch generate。

Warning conflicts：

- same section。
- same track。
- marker global beat 距离小于 4 beats。
- provider/local candidates 都准备好了但 task 未 apply。

## 6. Store 设计

新增文件建议：

```text
song_agent/review_sprints.py
tests/test_review_sprints.py
tests/test_server_review_sprints.py
```

`ReviewSprintStore`：

```python
class ReviewSprintStore:
    def create_sprint(...)
    def list_sprints(...)
    def read_sprint(...)
    def update_sprint(...)
    def add_tasks(...)
    def remove_task(...)
    def reorder_tasks(...)
    def refresh_summary(...)
    def detect_conflicts(...)
    def close_sprint(...)
    def archive_sprint(...)
```

并发要求：

- 使用 project_dir 级别 `RLock`。
- sprint id 分配和目录创建必须在 lock 内。
- 目录创建使用 `mkdir(exist_ok=False)` 原子占位。
- 写 JSON 用现有 `write_json()` 原子替换。

ID 规则：

```text
sprint-001
sprint-002
...
```

校验：

- `sprint_id` 只能匹配 `^sprint-[0-9]{3,6}$`。
- task_id 必须是当前 project 下存在的 ReviewTask。
- task_refs 不允许重复 task_id。
- description / notes 需要脱敏。
- settings 只能接收白名单字段。

```http

```

```json

  "render_midi": true,
  "skip_existing_ready": true
}
```

```json
{
  "candidate_count": 2,
  "template_id": "provider-review-candidates",
  "render_midi": true,
  "skip_existing_provider": true,
  "stop_on_conflict": false
}
```

Response：

```json
{
  "ok": true,
  "sprint": {},
  "results": [
    {
      "task_id": "review-task-001",
      "status": "generated",
      "created_candidate_count": 2,
      "error": null
    },
    {
      "task_id": "review-task-002",
      "status": "skipped",
      "reason": "task already has ready candidates"
    }

  "summary": {},
  "conflict_report": {}
}
```

状态码：

- `202`：批量操作执行完成或后台启动。
- v3.0.0 建议先同步执行，避免新增 job runner。
- 如果后续性能问题，再拆 v3.0.1 做后台 sprint runner。

## 8. 状态机

### 8.1 Sprint status

```text
open
  -> in_progress
  -> blocked
  -> closed
  -> archived
```

规则：

- 创建后 `open`。
- 执行 generate 后变 `in_progress`。
- 检测到 blocking conflicts 后可变 `blocked`。
- 用户手动 close 后变 `closed`。
- closed sprint 可以 archive。
- archived sprint 不允许 add/remove/generate。

### 8.2 不改变 ReviewTask 状态机

Sprint 操作只能调用已有 ReviewTask 逻辑：

- local candidate generation。
- provider candidate generation。
- decision report refresh。

Sprint 不直接改：

- selected_candidate_id。
- applied_version_id。
- resolved_at。

这些仍由 ReviewTask apply/resolve/needs_more_work API 控制。

## 9. Batch generation 规则

### 9.1 Local batch

对每个 task：

1. 读取 task。
2. 校验 task open for generation。
3. 校验 parent plan hash。
4. 如果 `skip_existing_ready=true` 且已有 ready candidate，跳过。
5. 调用现有 local candidate generation。
6. 刷新 decision report。
7. 写 sprint event。

遇到失败：

- 不回滚其他 task。
- 记录 item-level error。
- sprint summary 记录 failed count。

### 9.2 Provider batch

对每个 task：

1. 校验 provider config。
2. 校验 task open/stale。
3. 如果 `skip_existing_provider=true` 且已有 provider candidate，跳过。
4. 调用 v2.9 provider candidate generation。
5. 刷新 decision report。
6. 写 provider usage。

Provider 失败：

- 不删除 local candidates。
- 不删除已有 provider candidates。
- item result 标为 failed。

### 9.3 不做 batch apply

v3.0.0 不提供：

```http
POST /api/projects/<id>/review-sprints/<id>/apply-all
```

原因：

- 多个 task 可能改同一 section/track。
- apply 一个 task 后其他 task 可能 stale。
- 自动 apply 会破坏人审链路。

UI 可以提供 “Open Task / Apply Candidate” 快捷入口，但 apply 仍是单 task 操作。

## 10. Conflict Detection

### 10.1 输入

从 ReviewTask 读取：

- `parent_version_id`
- `status`
- `target.section_name`
- `target.track_name`
- `target.role`
- `target.global_marker_beat`
- `selected_candidate_id`
- `applied_version_id`
- `counts`

### 10.2 检测规则

Blocking：

- task stale。
- task archived。
- Sprint parent_version_id 不为空，task parent_version_id 不一致。
- task 已 applied/resolved，但仍被标记需要 generate。

Warning：

- 两个 open/candidate_ready task 同 section。
- 两个 open/candidate_ready task 同 track。
- 两个 task 同 section + 同 track。
- marker global beat 距离小于 4 beats。
- task 已 needs_more_work 且 follow_up_task_id 不在 sprint。

Info：

- task 已 resolved。
- task candidate_ready 但无 decision report。
- task 只有 local candidates，没有 provider candidates。

### 10.3 冲突处理方式

v3.0.0 只报告冲突，不自动解决冲突。

UI 提供：

- Open Task。
- Refresh Decision Report。
- Add Follow-up Task to Sprint。
- Remove from Sprint。

## 13. 安全与一致性

### 13.1 Sprint 不保存敏感内容

必须脱敏：

- sprint description。
- task ref notes。
- event payload。
- conflict message。

不得保存：

- API key。
- Authorization。
- raw prompt。
- raw provider response。
- 本地路径。

### 13.2 Sprint 不绕过现有 guard

所有 batch generation 必须调用已有 task 级逻辑：

- `_ensure_task_open_for_generation()`。
- `ensure_task_current()`。
- provider output validation。
- candidate artifact guard。

不要为了批量而新写一套 generate candidate 逻辑。

### 13.3 并发

同一 project 下两个 batch generate 同时执行时：

- 不得分配重复 sprint id。
- 不得分配重复 candidate id。
- 不得破坏 ReviewTask events。
- Store 使用 project-level lock。

### 13.4 stale

如果 batch 过程中某个 task stale：

- 该 task 标为 failed/skipped。
- sprint 可进入 blocked。
- 其他 task 可以继续，除非 `stop_on_conflict=true`。

## 17. Reviewer 检查重点

Reviewer 要重点看：

- Sprint 是否只是组织层，没有绕过 ReviewTask apply guard。
- Batch generate 是否复用现有 candidate generation。
- Sprint 是否提供 batch apply，如果有，要求删除。
- Conflict detection 是否覆盖 stale、same section、same track、parent mismatch。
- archived/closed sprint 是否禁止变更。
- Sprint summary 是否准确反映 task 状态。
- Project Export / Final Export 是否脱敏。
- provider batch 是否不会删除 local candidates。
- provider batch 是否不会保存 raw prompt/raw response。
- release-check 是否覆盖 Review Sprint。
- 并发创建 sprint 是否不会重复 id。

## 20. 最终判断

v3.0.0 最应该做 Review Sprint。

原因：

- v2.8/v2.9 已经把单条反馈修正做完整。
- 真正的下一层瓶颈是多反馈组织。
- Sprint 可以提高创作效率，但不破坏人工 apply 和本地校验边界。
- 它为后续全项目质量审计、最终交付 readiness、批量反馈管理打基础。

做完 v3.0.0 后，MusicForge 的反馈链路会从：

```text
我逐条处理反馈，每条都有候选和报告
```

升级为：

```text
我把一轮评审里的多个反馈组织成 Sprint，按冲突和优先级逐项推进，批量生成候选，但仍由我决定每一步是否应用
```

这才是从“创作工作台”走向“项目制作管理台”的关键一步。

# v2.9.0 Provider 评审候选与决策报告施工图

日期：2026-05-13

当前稳定基线：v2.8.0

目标版本：v2.9.0

定位：在 v2.8.0 已经完成 Review Workbench 本地多候选闭环后，把 provider 能力接入 ReviewTask，但只作为“候选来源”和“解释辅助”。v2.9.0 不让 AI 自动决定最终版本，不让 provider 输出绕过本地 patch 校验、SongPlan 校验、质量评分、stale guard 和用户 apply。

---

## 1. 背景

v2.8.0 已经完成了关键闭环：

```text
Audition Review
  -> ReviewTask
  -> local conservative / balanced / bold candidates
  -> MIDI/WAV audition
  -> apply one candidate
  -> resolve or needs_more_work follow-up task
```

这个版本把 MusicForge 从“根据评审做一次编辑”推进到了“围绕一条反馈生成多个可听候选，然后人选一个”的工作台。

但 v2.8.0 也明确留下了几个后续方向：

- Provider review candidates 暂未实现。
- ReviewTask filtering 还比较基础。
- ReviewTask 与 Context Pack / Asset / Reference 的推荐还没有连起来。
- 多候选之间的解释、差异和决策报告还不够完整。
- Review Workbench 里用户能看到排名，但不能清楚知道“为什么这个 candidate 排第一”。

v2.9.0 应该先补“智能候选和决策解释”这一层，而不是继续做更复杂的编辑器 UI。

---

## 2. 一句话目标

v2.9.0 要把 Review Workbench 从“本地多候选工具”升级成“本地候选 + Provider 候选 + 可解释决策报告”的评审决策台。

最终工作流：

```text
ReviewTask
  -> Generate Local Candidates
  -> Generate Provider Candidates
  -> Local validate / quality / scoring
  -> Candidate Decision Report
  -> User audition and apply one candidate
  -> Resolve or Needs More Work
```

关键原则：

- Provider 只生成受控 patch candidates。
- Provider patch 必须转换成本地 `EditIntent` 或复用 provider edit patch apply 逻辑。
- 每个 provider candidate 都必须本地 apply 到 parent SongPlan。
- 每个 candidate 都必须本地 validate、attach quality、score、render MIDI。
- Provider 失败不能破坏已有 local candidates。
- Provider usage、request id、template id、model 需要脱敏记录。
- 决策报告可以推荐，但不能自动 apply。

---

## 3. 版本边界

### 3.1 v2.9.0 必须做

- 在 ReviewTask 下新增 provider candidate generation。
- 新增 prompt template：`provider-review-candidates`。
- 复用现有 `ProviderEditPatch` / `generate_provider_edit_candidates()` 能力，或封装 review 专用入口。
- Provider candidate 写入现有 ReviewCandidate 数据结构，`candidate_type="provider_review_patch"`。
- Provider candidate 必须有：
  - `source.provider=true`
  - `source.template_id`
  - `source.model`
  - `source.request_id`
  - `source.usage`
  - `source.provider_snapshot`，但不能包含明文 API key。
- Provider candidate 生成失败时，ReviewTask 仍可保留 local candidates。
- ReviewCandidate ranking 支持 local/provider 混排。
- 新增 ReviewTask Decision Report：
  - candidate 汇总
  - ranking breakdown
  - local/provider 对比
  - risk flags
  - recommended_candidate_id
  - recommendation_reason
  - user must still apply manually
- Studio Review Workbench 增加：
  - Generate Provider Candidates
  - Provider status / usage / model
  - Candidate source badge
  - Decision Report panel
  - ranking breakdown 展示
- Project Compare / Project Export / Final Export summary 纳入 provider review candidate 和 decision report 摘要。
- release-check 增加 v2.9 provider review candidate smoke，使用 mock provider。
- README / CHANGELOG / version bump。

### 3.2 v2.9.0 可以做，但不强制

- ReviewTask list 高级筛选：status、source、priority、has_provider_candidates、needs_attention。
- Provider candidate re-generate 指定 count/template。
- Decision Report 导出为单独 JSON artifact。
- Provider candidate 和 local candidate 的“差异摘要”更细化到 section/track 级。
- ReviewTask 一键创建 Context Pack 推荐。

### 3.3 v2.9.0 不做

- 不做自动 apply。
- 不做自动 resolve。
- 不做 provider whole SongPlan candidate。
- 不做音频理解、BPM/key 检测、音频转 MIDI。
- 不做多人协作、云同步、权限模型扩展。
- 不做通用 CandidateStore 大重构。
- 不改 v1.4 provider edit candidate group 的存储结构。
- 不让 provider 写入任意文件路径。
- 不把 provider raw response 放进 Final Export。
- 不在 ReviewTask 里允许多次 apply；仍然遵守 v2.8.0 的“一 task 一 apply”规则。

## 4. 核心判断

v2.9.0 最重要的不是“接上 provider”四个字，而是让 provider 在 MusicForge 的安全边界里工作。

已有能力：

- `song_agent/provider_edits.py` 已有 `ProviderEditPatch`。
- 已有 `generate_provider_edit_candidates()`。
- 已有 prompt template store。
- 已有 mock provider。
- 已有 provider usage / provider snapshot 的脱敏经验。
- v2.8.0 的 `ReviewCandidate` 已经预留 `candidate_type="provider_review_patch"`。

因此 v2.9.0 不应该新造一套 provider 输出格式。应该复用 provider edit patch schema，但 prompt 语义改成 review task context。

## 5. 数据结构设计

### 5.1 ReviewCandidate 扩展

现有 `ReviewCandidate` 已包含：

```python
candidate_type: str
strategy: str
source: dict
intents: list[dict]
patch: dict | None
validator: dict
scores: dict
warnings: list[str]
artifacts: dict[str, str]
hashes: dict[str, str]
```

v2.9.0 不需要破坏 schema，只需要规范 provider candidate 字段。

Provider candidate 示例：

```json
{
  "candidate_id": "revcand-004",
  "candidate_type": "provider_review_patch",
  "strategy": "provider",
  "status": "ready",
  "source": {
    "source_type": "provider_review_candidate",
    "provider": true,
    "template_id": "provider-review-candidates",
    "wire_api": "mock",
    "model": "mock-review",
    "request_id": "req_xxx",
    "usage": {
      "prompt_tokens": 1200,
      "completion_tokens": 500,
      "total_tokens": 1700
    },
    "candidate_index": 1
  },
  "patch": {
    "schema_version": 1,
    "summary": "Lift chorus energy while preserving the hook",
    "confidence": 0.78,
    "operations": []
  },
  "intents": [],
  "scores": {
    "combined": 86,
    "review_fit": 92,
    "quality_overall": 88,
    "target_precision": 90,
    "risk": 12,
    "source_bonus": 0
  }
}
```

规则：

- `patch` 保存 provider patch 的脱敏版本。
- `intents` 保存 patch 转换后的本地 `EditIntent`。
- 正式 apply 时继续从 parent + `intents` 或 `patch` 重新计算。
- 不能信任 candidate 目录中的 `candidate-song-plan.json`。
- `source.usage` 只能是数值 token/cost 信息。
- `source` 不能包含 API key、Authorization、local path、raw prompt、raw provider response。

### 5.2 ReviewTask provider summary

ReviewTask 可以通过 `counts` 或新增 summary 字段表达 provider 状态。优先不改 task schema，大部分状态从 candidates 聚合。

建议在 task detail response 里增加派生字段：

```json
{
  "provider_summary": {
    "candidate_count": 2,
    "ready_count": 2,
    "failed_count": 0,
    "templates": ["provider-review-candidates"],
    "models": ["mock-review"],
    "usage": {
      "prompt_tokens": 1200,
      "completion_tokens": 500,
      "total_tokens": 1700,
      "estimated_cost": null
    }
  }
}
```

不要把这个字段写死进 `task.json`，除非实现上已经有清晰聚合函数。优先作为 API response derived view。

### 5.3 Decision Report

新增文件：

```text
.musicforge/projects/<project-id>/review-tasks/<task-id>/decision-report.json
```

结构：

```json
{
  "schema_version": 1,
  "task_id": "review-task-001",
  "project_id": "project-001",
  "parent_version_id": "v001",
  "parent_song_plan_hash": "abc",
  "created_at": "2026-05-13T...",
  "candidate_count": 5,
  "recommended_candidate_id": "revcand-004",
  "recommendation_reason": "Best review_fit with low risk and no validator warnings.",
  "requires_manual_apply": true,
  "ranking": [
    {
      "candidate_id": "revcand-004",
      "candidate_type": "provider_review_patch",
      "rank": 1,
      "combined": 86,
      "review_fit": 92,
      "quality_overall": 88,
      "target_precision": 90,
      "risk": 12,
      "warnings": []
    }
  ],
  "source_breakdown": {
    "local_review_intents": 3,
    "provider_review_patch": 2
  },
  "risk_flags": [
    {
      "candidate_id": "revcand-002",
      "severity": "warning",
      "message": "Quality score dropped by 6 points."
    }
  ],
  "notes": [
    "Provider recommendation is advisory only."
  ]
}
```

安全规则：

- 不写 raw provider response。
- 不写 full prompt。
- 不写完整 SongPlan。
- 不写本机路径。
- 所有自由文本用 `sanitize_sensitive_text()` 或 `sanitize_metadata()`。
- 如果 task stale，decision report 标记 stale 或拒绝生成。

## 6. Prompt Template

### 6.1 新增 built-in template

在 `song_agent/prompt_templates.py` 增加：

```text
template_id: provider-review-candidates
task: provider_review_candidates
```

输出 schema 复用 `PROVIDER_EDIT_CANDIDATES_SCHEMA`。

System prompt 要求：

- Return one JSON object only.
- Use only supported operations and chord names.
- Do not include file paths, URLs, secrets, credentials, or free-form code.
- Treat hook/keep markers as preserve signals unless explicitly asked to alter them.
- Produce distinct candidates with conservative/balanced/bold style variation if useful.
- Candidate patches must stay small and targeted.

Context 应包含：

```json
{
  "review_task": {},
  "review_snapshot": {},
  "target": {},
  "parent_song_plan": {},
  "local_candidate_summaries": [],
  "supported_operations": [],
  "supported_chords": [],
  "candidate_count": 2,
  "asset_references": [],
  "reference_references": [],
  "context_pack_summary": {}
}
```

注意：

- `parent_song_plan` 可以给，但后续如果 prompt 太大，改成 sections/tracks summary。
- review notes 必须脱敏。
- asset/reference/context pack summary 必须走已有脱敏函数。

### 6.2 Provider model 选择

优先使用：

```python
config.review_model or config.light_model or config.model
```

如果当前 ProviderConfig 只有 `model`，也要能跑。

不要在 v2.9.0 新增复杂 provider profile。

## 7. 后端模块设计

### 7.1 建议新增函数

在 `song_agent/review_tasks.py` 或新增 `song_agent/review_provider_candidates.py`：

```python
def generate_provider_review_candidates(
    *,
    store: ReviewTaskStore,
    task: ReviewTask,
    parent_plan: SongPlan,
    template: PromptTemplate,
    config: ProviderConfig,
    candidate_count: int,
    local_candidates: list[ReviewCandidate],
    asset_references: list[dict[str, Any]] | None = None,
    reference_references: list[dict[str, Any]] | None = None,
    context_pack: dict[str, Any] | None = None,
    client: Any | None = None,
) -> list[ReviewCandidate]:
    ...
```

内部流程：

1. `_ensure_task_open_for_generation(task)`。
2. 校验 task parent hash 未 stale。
3. 构建 review prompt context。
4. 调用 provider candidate 生成。
5. 对每个 `ProviderEditPatch`：
   - 转成本地 intents。
   - 用 parent plan 本地 apply。
   - attach quality。
   - validate song plan。
   - score review candidate。
   - render MIDI。
   - 写 candidate JSON、candidate-song-plan JSON、validator、quality。
6. 重算 ranking。
7. 写 decision report 或至少触发 decision report refresh。
8. 返回 candidates。

### 7.2 不要直接复用 CandidateGroupStore

原因：

- CandidateGroup parent 是 Project Version。
- ReviewCandidate parent 是 ReviewTask。
- ReviewTask 有 resolved / needs_more_work / archived / stale 状态机。
- ReviewTask 有一 task 一 apply 规则。
- ReviewTask 有 follow-up chain。

可以复用 scoring 辅助、provider patch schema、usage 聚合，但不要把两个 store 合并。

### 7.3 失败策略

Provider generation 有三类失败：

1. provider config 缺失。
2. provider request 失败。
3. provider output invalid。

API 返回：

- config 缺失：`400`
- request timeout/network：`502` 或 `503`
- output invalid：`422`
- task stale/closed：`409`

如果 local candidates 已存在，失败不能删除它们。

如果 provider 一次返回多个 candidate，其中部分无效：

- 推荐策略：整批校验，能用的保留，失败的写 failed candidate 或 report risk。
- 但为了实现简单，v2.9.0 可以先采用整批失败。
- 如果采用部分成功，必须测试 ranking 和 counts。

建议 v2.9.0 第一版：**整批失败**，避免半写状态复杂。

## 8. API 设计

### 8.1 生成 Provider Candidates

```http
POST /api/projects/<project-id>/review-tasks/<task-id>/provider-candidates
```

Request:

```json
{
  "candidate_count": 2,
  "template_id": "provider-review-candidates",
  "include_local_context": true,
  "context_pack_id": null,
  "asset_refs": [],
  "reference_refs": []
}
```

Response:

```json
{
  "ok": true,
  "task": {},
  "candidates": [],
  "decision_report": {},
  "provider_summary": {}
}
```

Status:

- `201` created if candidates written.
- `400` bad payload/provider config incomplete.
- `409` closed/stale/applied task.
- `422` invalid provider output.
- `502/503` provider request failure.

### 8.2 Decision Report

```http
GET /api/projects/<project-id>/review-tasks/<task-id>/decision-report
POST /api/projects/<project-id>/review-tasks/<task-id>/decision-report/refresh
```

GET:

- 如果 report 不存在，可以即时生成 derived report，也可以返回 `404`。
- 建议即时生成，只要 candidates 存在。

POST refresh:

- 重新基于当前 candidates 计算，不调用 provider。
- stale task 返回 `409`。

### 8.3 ReviewTask list filters

可以轻量扩展：

```http
GET /api/projects/<project-id>/review-tasks?status=candidate_ready&source=provider&include_archived=0
```

可选字段：

- `status`
- `source=local|provider|mixed`
- `needs_attention=1`
- `has_provider_candidates=1`

v2.9.0 如时间紧，可以只做 `has_provider_candidates` 和 `source`。

### 8.4 Artifact safety

Provider candidate 的 MIDI/WAV 下载继续走 v2.8 的 candidate artifact guard：

- path 必须在当前 candidate `renders/`。
- 文件名只能是 `song.mid` 或 `song.wav`。
- stale task/candidate 返回 `409`。
- closed task 不影响已生成 artifact 下载，但 stale 必须挡。

## 9. Scoring 与 Ranking

### 9.1 现有评分继续保留

v2.8 已有候选评分维度：

- combined
- review_fit
- quality_overall
- target_precision
- risk

v2.9 增加：

- provider_confidence
- novelty
- local_provider_consensus
- quality_delta
- warning_penalty

### 9.2 combined 建议公式

不要大改旧分数，只微调：

```text
combined =
  review_fit * 0.35
  + quality_overall * 0.25
  + target_precision * 0.20
  + novelty * 0.10
  + provider_confidence * 0.05
  + local_provider_consensus * 0.05
  - risk_penalty
  - warning_penalty
```

如果是 local candidate：

- `provider_confidence = 0`
- 不惩罚 source，只是没有该加成。

如果 provider candidate quality 明显下降：

- `quality_delta < -5` 给 risk flag。
- `quality_delta < -10` 直接 warning penalty。

### 9.3 决策报告 recommendation

推荐候选规则：

1. 只考虑 `status="ready"`。
2. 排除 validator error。
3. 排除 stale。
4. 排除 combined 低于阈值的候选，例如 `< 55`。
5. 取 ranking 第一。

决策报告必须写：

```json
"requires_manual_apply": true
```

UI 文案不要暗示 AI 已经替用户决定。

## 13. 安全要求

### 13.1 Provider 输出不能直接执行

所有 provider output 必须经过：

```text
ProviderEditCandidateSet.from_dict
  -> ProviderEditPatch.from_dict
  -> provider_patch_to_intents
  -> validate_edit_intent
  -> apply_edit_intent / apply_provider_edit_patch
  -> SongPlan.validate
  -> quality attach
```

任何一步失败，candidate 不得 ready。

### 13.2 Blocked keys

Provider patch 当前已有 blocked keys：

```text
path, file, absolute_path, local_path, token, api_key, secret, password, credential
```

v2.9.0 要保留，并补测试：

- provider candidate 包含 `api_key` 失败。
- provider candidate 包含 `local_path` 失败。
- provider candidate 包含 unsupported op 失败。
- provider candidate 包含 unsupported chord 失败。

### 13.3 Review notes 脱敏

Review notes、markers、tags、source notes 进入 provider prompt 前必须脱敏。

测试：

- review note 包含 `sk-...`
- review note 包含 `D:\Music\demo.wav`
- review note 包含 `Bearer xxx`

Provider prompt context 和 candidate source/export 都不得出现这些值。

### 13.4 Stale guard

以下场景必须返回 `409`：

- parent SongPlan hash 改变后 generate provider candidates。
- stale task render provider candidate MIDI/WAV。
- stale task apply provider candidate。
- task 已 `needs_more_work` 后 generate/apply provider candidate。
- task 已 selected_candidate_id 后再 apply 另一个 provider candidate。

### 13.5 一 task 一 apply

继续遵守：

```text
one ReviewTask -> at most one selected candidate -> at most one applied child version
```

Provider candidate 不得绕过 `_ensure_task_open_for_apply()`。

## 14. 测试计划

### 14.1 单元测试

新增或扩展：

```text
tests/test_review_tasks.py
tests/test_server_review_tasks.py
tests/test_provider_edits.py
tests/test_prompt_templates.py
tests/test_project_compare.py
tests/test_final_export.py
tests/test_webui.py
```

必须覆盖：

- provider review candidate 生成成功。
- provider candidate 写入 `candidate_type="provider_review_patch"`。

### 14.2 Server API 测试

```http

GET /api/projects/<id>/review-tasks/<task>/decision-report
```

## 18. 风险清单

### 18.1 Provider output 太自由

风险：

- Provider 返回未知操作或危险字段。

防护：

- 只接受 `ProviderEditPatch`。
- blocked keys scan。
- operation whitelist。
- chord whitelist。
- patch size limit。
- operation count limit。

### 18.2 Provider candidate 破坏 ReviewTask 状态机

风险：

- 旧 task 已 needs_more_work 后仍继续 provider generate/apply。

防护：

- generation 和 apply 都调用 task open guard。
- selected_candidate_id 存在后禁止 apply 其他 candidate。
- 回归测试覆盖。

### 18.3 Decision Report 被误解成自动决定

风险：

- 用户以为系统已经选定最终版本。

防护：

- report 字段写 `requires_manual_apply=true`。
- Studio 显示 Manual apply required。
- 不自动 apply。

### 18.4 Provider prompt 泄漏敏感信息

风险：

- review note、asset/ref/context pack summary 里含 secret/path。

防护：

- prompt context builder 统一脱敏。
- 测试污染 secret/path。

### 18.5 release-check 过慢

风险：

- 全量 release-check 已经较长。

防护：

- v2.9 smoke 使用 mock provider。
- 不真实渲染 WAV。
- 只下载 provider MIDI。

## 19. Reviewer 检查重点

开发完成后 reviewer 要重点看：

- Provider candidate 是否真的不信任 cached candidate SongPlan。
- Apply 是否从 parent + patch/intents 重新计算。
- `_ensure_task_open_for_apply()` 是否覆盖 provider candidate apply。
- Provider generation 是否会在 closed/stale task 上被挡住。
- provider usage 是否脱敏。
- decision-report 是否包含 raw prompt/raw response。
- Project Export / Final Export 是否二次脱敏。
- artifact path guard 是否对 provider candidate 仍有效。
- release-check 是否包含 provider candidate unsafe path 污染测试。
- mock provider smoke 是否能稳定跑。

## 21. 最终判断

v2.9.0 应该做 Provider 评审候选和决策报告。

原因很明确：

- v2.8.0 已经有 ReviewTask 和本地候选工作台。
- provider edit candidate 的基础设施已经存在。
- Review Workbench 的下一层价值是“更多候选来源 + 更清楚的决策解释”。
- 这能显著提升创作效率，但不会破坏本地可验证、安全、可追踪的核心架构。

这版做完后，MusicForge 的反馈链路会从：

```text
我围绕一条反馈生成几个本地修正方案，然后自己判断
```

升级为：

```text
我围绕一条反馈生成本地和 provider 两类修正方案，系统给出可解释排名，我试听后手动应用并进入下一轮
```

这才是 Review Workbench 真正成为“创作决策台”的关键一步。

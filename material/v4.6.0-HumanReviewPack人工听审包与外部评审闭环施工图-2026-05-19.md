# v4.6.0 Human Review Pack 人工听审包与外部评审闭环施工图

目标版本：v4.6.0

基线版本：v4.5.1

角色定位：Reviewer 施工图 / 开发执行指南 / 自测验收规范

文档日期：2026-05-19

---

## 1. 背景

v4.4.0 到 v4.5.1 已经把 MusicForge 从“能生成音乐”推进到了“能做工程化音乐验收”：

- v4.4.0 建立 Music Acceptance Lab。
- v4.4.1 修正 MIDI-only 自测在本机 renderer 配置存在时的误伤。
- v4.5.0 引入 Acceptance Profiles 和 12 首 Regression Songbook。
- v4.5.1 收紧 release-ready profile，要求完整覆盖 12 首内置曲库，不能只验 1 首就 release-ready。

现在的系统已经可以回答：

> 自动体检是否通过？固定曲库是否完整？synthetic 是否不能冒充人工？Release Signoff 是否绑定真实 release-ready Acceptance Suite？

但还缺一个关键产品能力：

> 非开发人员、业务人员、音乐负责人如何方便地听完整曲库、打分、写意见，并把这些意见安全地回流到系统？

当前 Studio 内部可以人工 review，但这要求评审者打开本地服务、理解项目面板、逐个进入 Acceptance case。对于真实业务验收来说，这还不够顺。

所以 v4.6.0 要做：

> Human Review Pack：把 Acceptance Suite 导出成可携带、可离线打开、可回收评审结果的人工听审包，并把外部听审结果导入回 Acceptance / ReviewTask / Release gate。

---

## 2. v4.6.0 定位

v4.6.0 是“人工验收闭环”版本。

它不是继续做更多自动打分，也不是接入外部音乐平台 API，而是把人工听审这件事产品化、可审计化、可重复化。

目标：

1. 从 Acceptance Suite 生成 Human Review Pack。
2. Pack 可以在浏览器离线打开。
3. Pack 内包含曲目信息、MIDI/WAV 下载或播放入口、评分表、问题标记说明。
4. 评审者可以填写评分、状态、tags、notes、markers。
5. Pack 导出 review response JSON。
6. MusicForge 可以导入 response JSON。
7. 导入结果写回 Acceptance listening-review.json。
8. 差评或 needs_fix 自动生成 ReviewTask。
9. Release Signoff 可以引用 Human Review Pack evidence。
10. release-check 覆盖 pack 生成、离线校验、导入、差评转任务、脱敏、安全路径。

一句话：

> v4.5.1 解决“必须听哪些歌”；v4.6.0 解决“怎么让人真正听、怎么证明听过、怎么把意见变成下一步工作”。

---

## 3. 不做什么

v4.6.0 明确不做：

1. 不做真实外部分享服务。
   - 不上传云端。
   - 不生成公网链接。
   - 不做账号邀请。

2. 不做浏览器内复杂音频编辑。
   - Pack 只负责试听和填写意见。
   - 不做剪辑、混音、编辑器。

3. 不做 AI 判断音乐好坏。
   - 只做自动 health / quality 摘要。
   - 人工评分仍由人填写。

4. 不做 MP3 转码。
   - 继续使用现有 MIDI/WAV。
   - 如果 WAV 不存在，Pack 允许 MIDI-only，但要明确标识。

5. 不绕过 Acceptance Signoff。
   - Human Review Pack 是人工 evidence 来源。
   - 最终是否 release-ready 仍由 Acceptance Report / Release Gate 判断。

6. 不把 response JSON 当可信输入。
   - 导入时必须校验 suite hash、case hash、pack hash、schema、脱敏、安全字段。

## 4. 核心用户流程

### 4.1 开发人员生成听审包

在 Studio Acceptance Workspace：

1. 选择一个 Acceptance Suite。
2. 确认 cases 已 generate + health passed。
3. 点击 `Build Human Review Pack`。
4. 系统生成：

```text
.musicforge/
  acceptance/
    suite-000001/
      human-review-packs/
        pack-000001/
          pack.json
          index.html
          response-template.json
          manifest.json
          assets/
            case-000001.mid
            case-000001.wav
            ...
          checksums.json
          events.jsonl
```

5. 下载 zip：

```text
human-review-pack-suite-000001-pack-000001.zip
```

### 4.2 评审者离线听审

评审者解压 ZIP，打开：

```text
index.html
```

页面显示：

- suite name
- profile
- songbook coverage
- case list
- 每首歌的 title / style / theme
- health summary
- quality overall
- MIDI / WAV 播放或下载
- rating 1-5
- status：accepted / needs_fix / rejected / waived
- playback confirmed
- tags
- notes
- marker list

评审者填写后，点击 `Export Review Response`。

浏览器下载：

```text
human-review-response-suite-000001-pack-000001.json
```

### 4.3 开发人员导入听审结果

回到 Studio：

1. 选择 Acceptance Suite。
2. 点击 `Import Review Response`。
3. 上传 response JSON。
4. 系统校验：
   - suite_id 是否一致。
   - pack_id 是否存在。
   - pack source hash 是否一致。
   - case_id 是否存在。
   - case content hash 是否一致。
   - review 字段是否合法。
   - notes 是否脱敏。
   - marker 是否在曲长范围内。
5. 导入成功后：
   - 写入每个 case 的 listening-review.json。
   - 写入 import event。
   - 生成 import summary。
   - 对 needs_fix / rejected case 创建 ReviewTask。
6. 重新 build Acceptance Report。

### 4.4 Release Signoff 使用听审证据

Release Signoff 绑定 Acceptance Suite 时，Acceptance Report summary 应带：

```json
{
  "human_review_pack": {
    "pack_id": "pack-000001",
    "response_import_id": "review-import-000001",
    "reviewer_count": 1,
    "manual_accepted_count": 12,
    "needs_fix_count": 0,
    "rejected_count": 0,
    "source_hash": "..."
  }
}
```

Release Signoff 写入：

```json
{
  "acceptance_gate": {
    "status": "passed",
    "suite_id": "suite-000001",
    "profile_id": "release_candidate",
    "songbook_coverage_status": "complete",
    "human_review_pack_id": "pack-000001",
    "human_review_import_id": "review-import-000001"
  }
}
```

  "songbook_id": "builtin_v1",
  "songbook_version": "2026-05-19",
  "created_at": "2026-05-19T00:00:00Z",
  "created_by": "developer",
  "source_hash": "hash-of-suite-cases-health-artifacts",
  "case_count": 12,
  "cases": [
    {
      "case_id": "case-000001",
      "song_id": "upbeat_pop_001",
      "title": "Neon Morning",

- 不允许本机路径、token、api key、provider raw response。
- response 不允许覆盖 pack.json。

## 7. Pack Source Hash

Pack 必须绑定 Acceptance Suite 当前状态。

source hash 建议包含：

- suite.to_dict()
- case list
- case request summary
- case song_id
- case health summary
- case artifact hash：
  - song.mid sha256
  - song.wav sha256 if exists
- acceptance profile
- songbook version

不应包含：

- pack created_at
- reviewer response
- mutable notes

如果 suite 重新 generate / rerun health / 修改 case，旧 pack 应 stale。

导入 response 时：

- response.pack_source_hash 必须等于 pack.source_hash。
- pack 当前 verify 必须 passed。
- stale pack response 导入返回 409。

---

## 8. HTML Pack 要求

`index.html` 必须是静态文件。

允许：

- HTML
- CSS
- 本地 JS
- `<audio controls>`
- download link
- JSON export

不允许：

- 远程 JS
- CDN
- 外部字体
- 上传请求
- fetch 远程地址
- eval
- inline 读取本机路径

HTML 里嵌入的数据应是脱敏后的 pack public payload。

导出的 response JSON 可以由浏览器 JS 生成，但字段必须被导入端再次校验。

## 9. Pack ZIP 安全

生成 ZIP：

- entry name 使用 `/`。
- 禁止 `\`。
- 禁止 `..`。
- 禁止绝对路径。
- 禁止重复 entry。
- 限制 entry 数。
- 限制 ZIP 总大小。
- 记录每个 entry 的 size / sha256。

manifest：

```json
{
  "schema_version": 1,
  "pack_id": "pack-000001",
  "suite_id": "suite-000001",
  "source_hash": "...",
  "entries": [
    {
      "path": "index.html",
      "size": 12345,
      "sha256": "..."
    }
  ],
  "zip": {
    "entry_count": 20,
    "total_uncompressed_size": 1234567,
    "sha256": "..."
  }
}
```

## 10. Response 导入校验

导入时必须拒绝：

1. suite_id 不一致。
2. pack_id 不存在。
3. pack stale。
4. response schema_version 不支持。
5. review case_id 不存在。
6. review song_id 与 case song_id 不一致。
7. rating 不在 1..5。
8. status 不在 accepted / needs_fix / rejected / waived。
9. playback_confirmed 不是 true。
10. notes 超长。
11. notes 包含 token、本机路径、provider raw data。
12. markers beat 越界。
13. response 包含未知危险字段：
    - api_key
    - token
    - raw_provider_response
    - local_path
    - source_path
    - absolute_path

导入错误返回：

- 400：schema / field 错误。
- 409：pack stale / suite signed / source mismatch。
- 413：response too large。

## 11. needs_fix / rejected 自动生成 ReviewTask

导入 response 后，如果某首歌：

- status = needs_fix
- status = rejected
- rating < suite.min_rating
- marker severity = warning / blocking

则创建 ReviewTask。

ReviewTask 内容建议：

```json
{
  "source_type": "acceptance_human_review",
  "suite_id": "suite-000001",
  "pack_id": "pack-000001",
  "import_id": "review-import-000001",
  "case_id": "case-000004",
  "song_id": "rock_chorus_001",
  "title": "Fix acceptance issue: Signal Fire",
  "description": "Human reviewer marked chorus transition as weak.",
  "markers": [...],
  "priority": "high"
}
```

如果该 case 来自 Project Version，需要把 task 绑定到 project/version。

如果 case 是 generated_request，没有 project version，则先只写 task summary，不自动 apply。

## 17. 安全要求

### 17.1 脱敏

必须使用现有 redaction：

- Windows path
- UNC path
- GitHub token
- OpenAI key
- Bearer token
- raw_provider_response
- local_path
- source_path

Pack 和 response import 都要二次脱敏。

### 17.2 签核只读

如果 Acceptance Suite 已 signoff：

- 不能 build 新 pack。
- 不能 import response。
- 不能修改 review。
- 必须 reset signoff 后操作。

### 17.3 Pack stale

如果 case artifact 变了：

- Pack verify 返回 stale。
- Response import 返回 409。
- Release Signoff 不能使用 stale import 作为 evidence。

### 17.4 HTML 安全

index.html 不应含：

- `<script src="http...">`
- `<link href="http...">`
- `eval(`
- `new Function`
- remote image
- remote audio

## 19. release-check v4.6 smoke

必须新增：

```text
v4.6 human review pack smoke
```

流程：

1. 创建 release_candidate Acceptance Suite。
2. 添加完整 12 首 songbook case。
3. generate + health。
4. build human review pack。
5. verify pack passed。
6. 复制 ZIP 到外部 temp 目录 verify passed。
7. 构造 response JSON：
   - 11 accepted
   - 1 needs_fix
8. import response。
9. Acceptance Report failed / manual_required 或 needs_fix。
10. 确认创建 ReviewTask。
11. 修改 response 为 12 accepted。
12. import response。
13. Acceptance Report release_ready_passed。

# v11.3.0 Unified Command Center Drift Response 统一总控漂移响应、受控重基线与闭环归档施工图

> 基线版本：v11.2.1  
> 目标版本：v11.3.0  
> 日期：2026-07-02  
> 施工目标：把 v11.2 Continuous Review 发现的 drift / incident，变成可审计、可复验、可签核前置的响应闭环。

---

## 1. 当前状态

MusicForge 现在已经走到 v11.2.1，核心能力是：

1. v11.0 有 Unified Command Center，聚合 Release Audio Command Center、Trust Operations、Public Trust Center、Maintenance、Delivery 等大链路。
2. v11.1 有 UCC Signoff / Archive / Handoff，能把总控状态签核成不可变交付证据。
3. v11.2 有 UCC Continuous Review，能在签核后持续复核 Archive / Handoff / UCC ZIP / GA / release-check / external evidence。
4. v11.2.1 已修复关键缺口：失败的 GA、release-check、external evidence 会变成 blocking drift，不再只是记录在 source 里。

这意味着现在系统能回答：

> 签核后的 UCC 当前还可信吗？

但还没有完整回答：

> 如果不可信，应该如何受控处理、如何证明处理完成、如何重新进入可签核状态？

v11.3.0 要补的就是这个闭环。

---

## 2. v11.3.0 定位

v11.3.0 建议命名：

**Unified Command Center Drift Response**

中文定位：

**统一总控漂移响应、受控重基线与闭环归档**

一句话定义：

> 从 v11.2 Continuous Review 的 failed drift / incident 出发，创建 response case，生成 response plan 和 action queue，只执行安全动作，要求人工 Change Request 处理高风险变更，重新运行 Continuous Review，最后生成不可变 Response Archive，并把它接入 Release / GA gate。

---

## 3. 为什么下一版必须做这个

现在 v11.2 的能力像“报警器”：

1. 能发现 archive / handoff / UCC / GA / release-check / external evidence 变化。
2. 能生成 drift report / incident board。
3. 能阻断 gate。

但是没有“处置流程”：

1. drift 发生后，谁来处理？
2. 哪些可以自动刷新，哪些必须人工审批？
3. 处理后怎么证明 drift 已经解决？
4. 是否允许重新签核或重建 Archive / Handoff？
5. 旧 failed review 和新 clear review 之间如何建立因果链？
6. reviewer 离线拿到 response ZIP 时，如何确认它不是自证、不是伪造、不是跳过了必要审批？

如果不补 v11.3，v11.2 的持续复核会停在“发现问题”，无法支撑长期运营。

---

## 4. 本版边界

### 4.1 本版要做

v11.3.0 做完整 response workflow：

1. 从 failed Continuous Review 创建 Drift Response Case。
2. 绑定原始 Continuous Review ZIP、verification report、drift report、incident board。
3. 生成 Response Plan。
4. 生成 Action Queue。
5. 区分 safe action 和 manual_required action。
6. 支持 safe action 执行。
7. 支持人工 Change Request evidence 绑定。
8. 支持重新运行 Continuous Review 作为 recheck。
9. 支持 closeout。
10. 支持 Response Archive / ZIP。
11. 支持离线 verifier。
12. 接入 Release signoff gate。
13. 接入 GA readiness gate。
14. 接入 CLI / API / Studio。
15. 接入 release-check v11.3 smoke。

### 4.2 本版不做

v11.3.0 不做这些：

1. 不自动 approve Change Request。
2. 不自动 reset UCC Signoff。
3. 不自动重新签核 UCC。
4. 不自动修改已签核 Archive / Handoff。
5. 不自动修改外部 delivery / trust / audio / maintenance 证据。
6. 不做 provider 调用。
7. 不做多人权限系统。
8. 不做远程发布。
9. 不做复杂图数据库 UI。

所有会改变签核状态、重建签核归档、接受风险、关闭高危漂移的动作，都必须是 manual_required 或显式 approved Change Request 驱动。

## 5. 目标用户流程

### 5.1 正常 clear 流程

1. 用户已有 signed UCC。
2. 用户运行 Continuous Review。
3. Review 结果为 passed。
4. 无需创建 Response。
5. Release / GA gate 可通过。

### 5.2 drift 响应流程

1. 用户已有 signed UCC。
2. 用户运行 Continuous Review。
3. Review 结果为 failed。
4. 用户点击 Create Drift Response。
5. 系统创建 Response Case。
6. 系统生成 Response Plan。
7. 系统生成 Action Queue。
8. 用户运行 safe actions。
9. 系统对需要人工介入的项生成 manual_required。
10. 用户处理外部 evidence 或 approved Change Request。
11. 用户提交 Change Request binding。
12. 系统重新运行 Continuous Review recheck。
13. recheck 必须 clear。
14. 用户 closeout response。
15. 系统生成 Response Archive ZIP。
16. Release / GA gate 使用 Response Archive + verification report 放行。

### 5.3 high-risk drift 流程

如果 drift 类型是：

1. UCC Archive 当前验证失败。
2. Handoff 当前验证失败。
3. UCC ZIP 当前验证失败。
4. GA readiness failed。
5. release-check failed。
6. external evidence failed。
7. verification report 绑定不一致。
8. source hash 不一致。

则 closeout 必须满足：

1. 有对应 action item。
2. action item 不得被静默跳过。
3. 如果 action 是 manual_required，必须绑定 approved Change Request evidence。
4. 必须有 recheck Continuous Review。
5. recheck status 必须 passed。
6. recheck verifier 必须 passed。

Closeout rules:

1. Cannot close if response source is stale.
2. Cannot close if any critical/high drift remains unresolved.
3. Cannot close if manual_required action lacks approved CR.
4. Cannot close if recheck is missing.
5. Cannot close if recheck verifier failed.
6. Cannot close if recheck still has blocking drift.
7. `force=true` must not bypass stale source or missing recheck.
8. `force=true` may only override low severity non-blocking warnings, and must record reason.

## 14. release-check

新增 smoke：

```text
v113.unified_command_center_drift_response_smoke
```

Profiles：

```text
v11
latest
ga
full
quick
```

Smoke 覆盖：

1. 创建 signed UCC。
2. 生成 clear Continuous Review。
3. 生成 failed Continuous Review：污染 external evidence / GA / release-check 至少一类。

## 20. Reviewer 必查清单

Reviewer 检查时重点看：

1. Response 是否只能从 failed Continuous Review 创建。
2. Response source 是否绑定原始 Continuous Review ZIP/report。
3. Plan 是否覆盖所有 blocking drift。
4. Safe actions 是否真的只执行安全动作。
5. Manual required 是否不会被自动执行。
6. Closeout 是否要求 recheck clear。
7. Closeout 是否要求 approved CR。
8. Force 是否不能绕过 stale source。
9. Force 是否不能绕过 missing recheck。
10. Verifier 是否固定 allow-list。
11. Verifier 是否能挡 full resign。
12. Release gate 是否要求 current response evidence。
13. GA gate 是否要求 current response evidence。
14. 删除 closeout/export/zip 是否不能绕过状态。
15. 文档是否没有承诺未实现的 reset 或 automatic apply。

## 21. 给开发的话

这版不是再堆一个报表，而是把 v11.2 的“发现漂移”变成“处理漂移并证明处理完成”。开发时请按这个顺序做：

1. 先把 Store 和数据模型打稳。
2. 再做 closeout gate，不要先做 UI。
3. verifier 必须跟 Store 同步设计，不能最后补。
4. 所有能改变签核状态的动作都必须 manual_required。
5. 每完成一个可独立验收的阶段就提交并推 GitHub。
6. 不要把本地 token、绝对路径、provider config、renderer config 写入仓库。
7. release-check smoke 必须覆盖 reviewer 真实会打的攻击：stale、full resign、declared extra、missing CR、missing recheck、force bypass。

交付标准很简单：

> reviewer 拿到 failed Continuous Review、Response ZIP、外部证据和 verifier 后，能独立证明：问题是什么、谁处理了、用什么 CR 处理、处理后 recheck 是否 clear、最终是否可以重新进入 Release / GA gate。

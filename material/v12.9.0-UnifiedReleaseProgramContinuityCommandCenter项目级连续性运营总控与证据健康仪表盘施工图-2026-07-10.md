# v12.9.0 Unified Release Program Continuity Command Center 项目级连续性运营总控与证据健康仪表盘施工图

日期：2026-07-10

目标版本：v12.9.0

当前基线：v12.8.0 Unified Release Program Continuity Acceptance Change Control 稳定基线

## 1. 背景

v12.0 到 v12.8 已经把 Unified Release Program 推进到项目级发布组合治理、证据总库、长期托管、连续性恢复、外部分发验收，以及签核后的变更控制：

- v12.0：Unified Release Program Board，聚合多个 Release Train Handoff，形成 Program 级准出。
- v12.1：Unified Release Program Operations，提供 Program CR、reset、runbook、continuous review 和 lifecycle archive。
- v12.2：Unified Release Program Final Handoff Board，完成 Program 最终交接验收。
- v12.3：Unified Release Program Evidence Vault，聚合 Program / Operations / Handoff / accepted evidence。
- v12.4：Unified Release Program Vault Operations，完成证据总库长期托管、转移和签核归档。
- v12.5：Unified Release Program Continuity Recovery，完成项目级只读恢复演练和连续性恢复签核。
- v12.6：Unified Release Program Continuity Distribution Kit，把 Continuity Archive、Vault Operations Archive、Evidence Vault 打包给外部灾备接收方。
- v12.7：Unified Release Program Continuity Acceptance Board，多接收方、多组织、多角色验收 Continuity Distribution Kit。
- v12.8：Unified Release Program Continuity Acceptance Change Control，支持 signed Acceptance Board 的 approved CR reset、successor signoff 和生命周期审计。

这些模块已经具备强安全边界，但使用上开始变得分散：

- Release / GA 需要同时传入 Vault、Vault Operations、Continuity、Distribution Kit、Acceptance Board、Change Control 等多份证据。
- 审查人需要从多个目录里判断哪一份是 current、哪一份 stale、哪一份只是历史 generation。
- Change Control reset 后，旧 Acceptance Archive、旧 verification report、旧 signoff binding 仍然存在，人工判断 current generation 容易出错。
- 每个模块都有自己的 verifier，但缺少一个统一入口复跑所有 runtime verification，并生成清晰的 readiness matrix。
- 当前缺少一个“如果现在不能准出，下一步应该做什么”的 deterministic gap plan。

v12.9 的目标是新增 **Unified Release Program Continuity Command Center**：不是再增加一个孤立签核层，而是把 v12.3-v12.8 的连续性证据链统一收束成一个 Program 级运营总控视图、离线包和门禁证据。

## 2. 版本目标

v12.9 新增 **Continuity Command Center**，重点交付：

1. 聚合 Program Evidence Vault、Vault Operations、Continuity Recovery、Continuity Distribution Kit、Continuity Acceptance Board、Continuity Acceptance Change Control 的当前证据。
2. 对所有底层证据执行 runtime verification，不信旧 verification report 自证。
3. 生成 Evidence Inventory，明确每个 component 的 package hash、manifest hash、verification hash、runtime status、current generation 和 blockers。
4. 生成 Readiness Matrix，区分 missing、stale、runtime_failed、verification_failed、reset_pending、manual_required、ready。
5. 生成 Gap Plan，把下一步动作按风险排序，例如 rebuild kit、rerun acceptance board、re-sign successor board、refresh change lifecycle、rerun vault deep verify。
6. 生成 Safe Runbook，只执行只读或局部安全动作，不自动 reset、signoff、approve CR、import response、accept evidence。
7. 导出固定结构 Command Center ZIP，并提供 standalone offline verifier。
8. Release signoff / GA readiness 可要求 Continuity Command Center ready，减少调用方直接拼接多份底层证据的复杂度。

这一版是 v12 连续性治理的第一次整合层，目标是从“很多强证据包”推进到“一眼看清当前 Program 连续性状态，并能离线复验”的状态。

## 3. 非目标

v12.9 不做以下内容：

- 不替代 v12.3-v12.8 的底层 verifier。
- 不新增第三方 CA、公钥基础设施或外部登记锚点。
- 不自动批准或执行任何 Change Request。
- 不自动 reset Acceptance Board 或 Program signoff。
- 不自动 import receiver response，不自动生成 accepted evidence。
- 不自动重新签核 Vault Operations、Continuity、Acceptance Board 或 Change Control。
- 不删除历史 archive，不覆盖历史 generation。
- 不把本机绝对路径写入 Command Center ZIP。
- 不做完整 Studio UX 重构，只接入必要的状态、按钮和下载入口。

说明：

```json
  "created_at": "2026-07-10T00:00:00Z",
  "updated_at": "2026-07-10T00:00:00Z",
  "source_hash": "sha256...",
  "inventory_hash": "sha256...",
  "readiness_hash": "sha256...",
  "runtime_index_hash": "sha256...",
  "gap_plan_hash": "sha256...",
  "current_generation": 2,
  "component_count": 6,
  "ready_component_count": 6,
  "blocked_component_count": 0,
  "manual_required_count": 0,
  "warnings": []
}
```

### 6.2 ComponentEvidence

每个底层证据用统一结构表示：

```json
{
  "component_id": "continuity-acceptance",
  "component_type": "evidence_vault|vault_operations|continuity|continuity_distribution_kit|continuity_acceptance|continuity_acceptance_change_control",
  "required": true,
  "generation": 2,
  "package_type": "musicforge_unified_release_program_continuity_acceptance",
  "package_path_ref": "local-ref-only",
  "package_sha256": "sha256...",
  "package_size_bytes": 12345,
  "manifest_hash": "sha256...",
  "verification_report_hash": "sha256...",
  "signoff_binding_hash": "sha256...",
  "anchor_hash": "sha256...",
  "runtime_status": "passed|failed|warning|missing|stale",
  "runtime_blockers": [],
  "current_status": "current|historical|reset|superseded|unknown",
  "public_summary": {
    "status": "ready",
    "signed": true,
    "verified": true
  }
}
```

规则：

- `component_id + component_type + generation` 是匹配主键，不能靠数组顺序。
- `package_path_ref` 只能是本地 manifest 的引用，不进入 public ZIP。
- `runtime_status=passed` 必须来自本轮 runtime verifier，不是读取旧 report。
- 如果底层组件没有 package，例如缺少 current successor Acceptance Board，状态必须是 `missing` 或 `reset_pending`。

```json
{
  "schema_version": 1,

  "requirements": [
```

- `current_evidence_vault`

- `current_continuity_distribution_kit`

- `current_continuity_acceptance_change_control`
- `current_generation_consistency`
- `runtime_verification_all_passed`
- `no_reset_pending`
- `no_missing_external_binding`
- `no_redaction_findings`

```json
{
  "schema_version": 1,
  "program_id": "urp-000001",
```

```json

    {
      "item_id": "item-000001",
      "action": "verify_evidence_vault",
      "safe": true,
      "status": "pending|completed|failed|manual_required|skipped_unsupported",
      "result_ref": "runtime/vault-verification-report.json"
    }
  ],
  "manual_actions": [
    {
      "action": "approve_change_request",
      "reason": "Reset is required and cannot be automated."
    }
  ],
  "integrity_hash": "sha256..."
}
```

允许自动执行的 safe actions：

- `refresh_command_center`
- `verify_evidence_vault`
- `verify_vault_operations`
- `verify_continuity_recovery`
- `verify_continuity_distribution_kit`
- `verify_continuity_acceptance`
- `verify_continuity_acceptance_change_control`
- `export_command_center`
- `zip_command_center`
- `verify_command_center_zip`

必须 `manual_required` 的动作：

- approve CR
- reset signoff
- signoff
- import receiver response
- create accepted evidence
- revoke / supersede package
- modify policy
- provider action
- destructive restore

## 7. Store API

建议类名：

```python
class UnifiedReleaseProgramContinuityCommandCenterStore:
    def __init__(self, project_root: Path | str = ".") -> None: ...

    def refresh(
        self,
        program_id: str,
        *,
        evidence_manifest: Path | str | dict[str, object] | None = None,
        require_all: bool = True,
        deep: bool = True,
    ) -> dict[str, object]: ...

    def get_report(self, program_id: str) -> dict[str, object]: ...
    def get_inventory(self, program_id: str) -> dict[str, object]: ...
    def get_readiness_matrix(self, program_id: str) -> dict[str, object]: ...
    def get_gap_plan(self, program_id: str) -> dict[str, object]: ...

    def create_runbook(self, program_id: str, *, include_safe_actions: bool = True) -> dict[str, object]: ...
    def run_safe(self, program_id: str, runbook_id: str) -> dict[str, object]: ...

    def gate(
        self,
        program_id: str,
        *,
        require_ready: bool = True,
        evidence_manifest: Path | str | dict[str, object] | None = None,
    ) -> dict[str, object]: ...

    def export_package(self, program_id: str) -> dict[str, object]: ...
    def build_zip(self, program_id: str) -> dict[str, object]: ...
    def verify_zip(self, program_id: str, *, strict: bool = True, require_ready: bool = False) -> dict[str, object]: ...
```

Store 层要求：

- `refresh()` 必须执行底层 runtime verification。
- `export_package()` 和 `build_zip()` 必须重新校验 source 没有变化。
- 如果底层 ZIP 被污染但旧 verification report 还在，Command Center 必须标记 `runtime_failed`。
- 如果 Acceptance Board 被 reset 后尚未 successor signoff，Command Center 必须 `blocked`。
- 如果 Change Control lifecycle audit 失败，Command Center 必须 `blocked`。
- 如果只有历史 generation 通过，而 current generation 不通过，Command Center 必须 `blocked`。

## 8. 离线 verifier

新增：

```python
verify_unified_release_program_continuity_command_center_package(
    zip_path,
    *,
    strict=False,
    require_ready=False,
    evidence_manifest=None,
    evidence_root=None,
    deep=True,
)
```

CLI：

```powershell
python -m song_agent.cli verify-unified-release-program-continuity-command-center-package <zip> --strict --require-ready --evidence-manifest evidence.json --json
```

Verifier 必须检查：

1. ZIP central directory raw name，不允许反斜杠 entry。
2. 固定 allow-list，不允许 declared extra。
3. 不允许 `.musicforge/`、`.MusicForge/`、绝对路径、`..`、控制字符。
4. 不允许 trailing data。
5. 不允许 duplicate entry。
6. manifest.files 必须和固定结构一致。
7. report / inventory / readiness / runtime-index / gap-plan / runbook hash 必须匹配 manifest。
8. package_type 必须是 `musicforge_unified_release_program_continuity_command_center`。
9. external evidence manifest 必须按 `component_type + component_id + generation` 匹配，不依赖顺序。
10. `require_ready=True` 时所有 required component 必须 runtime passed。
11. current generation 必须和 Change Control lifecycle / Acceptance Board current signoff 一致。
12. redaction scan 必须覆盖 raw JSON / README / report / matrix。

`deep=True` 时：

- 重新调用底层 verifier。
- 如果 Command Center ZIP 自身已有 blocking failure，先停止 deep extraction。
- deep extraction 必须使用临时目录 containment，所有解压路径必须保持在 temp root 内。
- 不允许把 package-index 声明的任意 nested ZIP 当作 allow-list。

## 9. 固定 ZIP 结构

Command Center ZIP 只允许：

```text
manifest.json
README.txt
command-center-report.json
evidence-inventory.json
readiness-matrix.json
runtime-verification-index.json
gap-plan.json
safe-runbook.json
external-evidence-manifest.json
```

不允许放入底层 nested ZIP。原因：

- v12.3 Evidence Vault 已经负责深度聚合和嵌套复验。
- v12.9 Command Center 是运营总控摘要，不应再次复制大包，避免包内自证和重复污染面。
- 离线 verifier 通过 external evidence manifest 定位外部证据，再做 deep verification。

如果需要“一包交付所有内容”，后续版本应做独立 Distribution Bundle，不在 v12.9 混入。

## 10. Runtime verification 绑定

每个 component 的 runtime verification report 必须写入：

```json
{
  "component_type": "continuity_acceptance",
  "component_id": "continuity-acceptance",
  "generation": 2,
  "package_type": "musicforge_unified_release_program_continuity_acceptance",
  "zip_sha256": "sha256...",
  "zip_size_bytes": 12345,
  "manifest_hash": "sha256...",
  "verification_report_hash": "sha256...",
  "signoff_binding_hash": "sha256...",
  "source_hash": "sha256...",
  "status": "passed"
}
```

Command Center 不接受：

- package_type 错误的 verification report。
- component_id 不匹配的 report。
- generation 不匹配的 report。
- stale report。
- failed report。
- 缺少 `zip_sha256` / `zip_size_bytes` / `manifest_hash` 的 report。
- 只由 Command Center ZIP 内部 sidecar 自证的 report。

## 11. Current generation 规则

v12.9 必须严格区分历史和当前：

- Acceptance Board 未 reset：current generation 来自当前 signed Acceptance Archive。
- Acceptance Board 已 reset：旧 Archive 是 historical，current status 为 `reset_pending`，直到 successor Board 重新 signoff / archive / verify。
- 多次 reset：current generation 必须等于 lifecycle audit 的 latest generation。
- Change Control lifecycle audit failed：Command Center blocked。
- 历史 archive 可以出现在 inventory，但不能满足 current ready。

## 16. 安全边界

### 16.1 不信包内自证

Command Center ZIP 内的 report、inventory、readiness 都只是摘要。Verifier 必须使用 external evidence manifest 和外部底层证据重新验证。

### 16.2 固定 allow-list

ZIP 只允许固定 9 个文件。manifest.files 和 ZIP entries 必须完全一致。

### 16.3 raw central directory 检查

必须扫描 raw central directory entry name，阻断：

- `foo\bar.json`
- `.MusicForge/internal.json`
- `nested/evil.zip`
- `../outside.txt`

### 16.4 trailing data

ZIP 文件尾部追加任意字节必须 failed。

### 16.5 runtime verification 优先

如果旧 verification report 是 passed，但底层 ZIP 已被污染，Command Center 必须 runtime_failed。

### 16.6 current generation 优先

历史 generation passed 不等于 current ready。

### 16.7 runbook 安全

Runbook 不能做：

- reset
- approve
- signoff
- import response
- create accepted evidence
- delete archive
- provider call

不支持的 action 必须 `skipped_unsupported`，不能假装 completed。

## 22. 风险清单

### P1：Command Center 只信旧 report

风险：底层 ZIP 被污染，旧 verification report 仍 passed，Command Center 误判 ready。

要求：refresh / verify / gate 必须 runtime re-verify。

### P1：历史 generation 被当成 current

风险：Acceptance Board reset 后，旧 Archive 仍被当作 current ready。

要求：必须读取 Change Control lifecycle，确认 latest generation。

### P1：external evidence 按数组顺序匹配

风险：manifest reorder 导致错配或漏检。

要求：按 `component_type + component_id + generation` 匹配。

### P1：ZIP allow-list 不固定

风险：manifest.files 声明 extra 后 verifier 放行。

要求：固定 entry set，manifest.files 必须等于 allow-list。

### P1：runbook 假完成

风险：不支持的 safe action 被标 completed。

要求：必须 `skipped_unsupported`，不计 completed。

### P2：diagnostic package 与 release-ready package 混淆

风险：blocked Command Center ZIP 被误用为 Release ready。

要求：允许 blocked diagnostic ZIP 存在，但 `--require-ready` 和 Release / GA gate 必须 failed。

### P2：Studio 显示过度承诺

风险：UI 文案暗示自动修复。

要求：UI 只说 refresh / verify / gap plan，不说自动 reset / signoff。

## 23. 给开发的落地提醒

这版重点不是再造一个签核包，而是把 v12.3-v12.8 的底层证据重新跑一遍、聚合成一个可信的当前状态。实现时优先顺序是：

1. Store runtime verification 和 current generation 判断。
2. Offline verifier 固定结构和 external evidence 反查。
3. reset_pending / runtime_tamper / wrong_package_type 回归。
4. Release / GA gate。
5. CLI / API / Studio。

不要为了 UI 或命令便利牺牲证据边界。尤其不要只读旧 verification report，不要按数组顺序匹配 evidence，不要让历史 generation 通过 current gate。

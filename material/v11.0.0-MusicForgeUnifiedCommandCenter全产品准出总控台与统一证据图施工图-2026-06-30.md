# v11.0.0 MusicForge Unified Command Center 全产品准出总控台、统一证据图与一键准出编排施工图

## 0. 给开发的话

v10.15.1 已经把 Release Audio Command Center 修到了一个可靠状态：音频准出链路不再只依赖旧 verification report，而是在 Command Center refresh / inventory 阶段实时跑底层 runtime verifier，并把 missing / stale / verification_failed / runtime_failed / manual_required / ready 区分清楚。

这说明 v10 音频准出链路已经可以作为稳定基线。下一步不要继续在 v10.x 里零碎加一个小面板、一个小 ZIP、一个小 gate。现在 MusicForge 最大的问题不是缺某个局部能力，而是：

- v8 有 Public Trust Center。
- v9 有 Trust Operations Hub。
- v10 有 Release Audio Command Center。
- v10.0 有 GA readiness。
- v10.1 有 LTS Maintenance。
- Release / Distribution / Submission / Evidence / Operations 也都有自己的 verifier、ZIP、gate、signoff。

这些模块都很强，但对真实使用者来说已经过于分散。业务要问的不是“哪个模块能生成哪个 ZIP”，而是：

```text
这个版本到底能不能交付？
如果不能，卡在哪里？
下一步应该点哪个按钮？
哪些是机器可以安全重建的？
哪些必须人工听审、签核、确认？
如果我要把整个项目交给 reviewer 或备份到外部，我应该给哪一个包？
```

因此 v11.0.0 应该做一次大整合：

> 建立 MusicForge Unified Command Center，作为全产品准出总控台，把音频准出、公开信任、运营信任、交付提交、维护健康、GA readiness 和 release-check 汇成一个统一 Evidence Graph、Readiness Matrix、Gap Plan、Safe Runbook 和固定结构离线验收包。

这版是一个大跨步，但仍要遵守两个原则：

1. **只整合和编排，不替代底层证据链。**  
   Unified Command Center 不能绕过 Audio Command Center、Trust Operations Hub、Public Trust Center、Release/Distribution/Submission verifier。它必须调用底层 verifier、读取底层 package fingerprint，并把结果绑定到统一证据图。

2. **只自动执行 safe action，不自动做人工决策。**  
   可以自动 refresh / export / zip / verify / doctor / release-check / maintenance check。不能自动 signoff、reset、approve、manual review、submit、accept、publish、provider generation。

开发时请把这版理解成：

```text
不是再新增一个局部包
而是把 MusicForge 从“很多强模块”升级成“一个可以操作的产品系统”
```

## 2. 为什么 v11 要做“大整合”

### 2.1 v8 / v9 / v10 已经形成三条强链路

#### 2.1.1 v8：Public Trust Center 公开信任链

v8 系列已经覆盖：

- Public Trust Center。
- Anchor Registry。
- Anchor Transparency。
- Distribution Kit。
- Distribution Kit Acceptance。
- Acceptance Board。
- Acceptance Board Signoff。
- Publication Channels。
- Publication Monitoring。

它解决的是：

```text
外部 reviewer / 接收方 / 公开镜像如何验证当前证据链没有被伪造或撤销？
```

#### 2.1.2 v9：Trust Operations Hub 运营信任链

v9 系列已经覆盖：

- Trust Operations Hub。
- Hub delivery verification。
- Runbook。
- Incidents。
- Incident Knowledge。
- Control Catalog。
- Control Signoff。
- Continuous Assurance。
- Assurance Watch。
- Watch Signoff。
- Final Readiness / Final Handoff。

它解决的是：

```text
交付、公开证明、运营、事故、控制、持续保障是否整体 ready？
```

#### 2.1.3 v10：Release Audio Command Center 音频准出链

v10 系列已经覆盖：

- GA / LTS。
- Maintenance。
- Audio Lab。
- Audio Fix Sprint。
- Audio Campaign。
- Audio Campaign Governance。
- Release-driven Audio Campaign。
- Campaign Remediation。
- Release Audio Certification。
- Timeline。
- Regression Guard。
- Baseline Governance。
- Regression Response。
- Quality Observatory。
- Quality Action Queue。
- Action Queue Signoff。
- Release Audio Command Center。

它解决的是：

```text
当前 Release 的音乐音频质量是否真实听审、修复闭环、回归防护、可签核？
```

### 2.2 当前真实痛点

系统能力已经强，但入口已经过多：

- Studio 顶层区域很多，用户不知道应该先去哪个面板。
- CLI 子命令很多，开发不知道要传哪些外部 evidence 参数。
- Release signoff / GA readiness 已经能挡住问题，但错误原因分散。
- release-check 很强，但更像开发验证工具，不是业务操作台。
- Public Trust Center、Trust Operations Hub、Audio Command Center 三个“中心”之间还缺一个总中心。
- 每个模块都有自己的 ZIP / verification report / source hash；缺一个统一 evidence graph。
- 运维人员想备份或交付项目时，不知道应该拿哪一组包。

### 2.3 v11.0.0 的定位

v11.0.0 是 MusicForge 的产品级总控层：

```text
MusicForge Unified Command Center
    ├── Workspace Health
    ├── Release Delivery Readiness
    ├── Audio Readiness
    ├── Trust Operations Readiness
    ├── Public Trust Readiness
    ├── Distribution / Submission Readiness
    ├── Maintenance / Backup / Upgrade Readiness
    ├── GA / release-check Readiness
    ├── Evidence Graph
    ├── Gap Plan
    ├── Safe Runbook
    └── Unified Command Center ZIP + offline verifier
```

一句话：

> v11.0.0 要把 MusicForge 从“模块集合”变成“有统一作战室的产品系统”。

- 只有全部 required ready，允许 optional warning => overall `ready`

### 10.4 run-safe

`run_safe()` 行为：

- 检查 source hash。
- 如果 source stale，返回 409。
- 只执行 safe=true 的 item。
- 对 manual_required item 写入结果，但不执行。
- 所有结果写入 `runbook-result.json`。
- runbook-result 进入 export / ZIP / verifier。

## 21. 安全红线

### 21.1 禁止自证

Unified Command Center verifier 不得只信：

- Unified report。
- Unified evidence graph。
- Unified inventory。
- Unified component fingerprint。

能传外部底层 ZIP/report 的地方，必须用外部真实文件反查。

### 21.2 禁止路径泄漏

所有导出和 ZIP：

- 不得写入本机绝对路径。
- 不得写入 token 文件路径。
- 不得写入 provider key。
- 不得写入 renderer soundfont 绝对路径。
- 不得写入 raw source_path。

### 21.3 敏感文本脱敏

所有用户输入字段：

- name
- reason
- note
- signed_by
- reviewer
- organization
- comment

必须走现有 `sanitize_sensitive_text()` 或同等 redaction。

### 21.4 ZIP 固定结构

不要允许“为了方便”把任意 evidence copy 进 Unified ZIP。

Unified ZIP 只放 summary / graph / fingerprint / report，不嵌套底层 ZIP。

底层 ZIP 通过 fingerprint 和外部 verifier 参数绑定。

### 21.5 run-safe 边界

run-safe 不能调用：

- signoff
- reset
- approve
- manual review
- provider
- submit
- accepted
- publish
- revoke
- delete

4. Gap Plan 是否真的给出下一步。
5. run-safe 是否没有越界执行人工动作。
6. ZIP 是否固定 allow-list。
7. Verifier 是否能挡 full-resign。
8. 底层 ZIP 被污染但旧 report 仍在时，Unified verifier 是否 failed。
9. Release signoff / GA readiness 是否能 require Unified Command Center。
10. Studio 是否成为更好的入口，而不是又多一个乱面板。

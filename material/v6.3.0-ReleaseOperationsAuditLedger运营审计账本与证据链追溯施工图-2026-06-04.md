# v6.3.0 Release Operations Audit Ledger 运营审计账本与证据链追溯施工图

日期：2026-06-04
基线版本：v6.2.1
目标版本：v6.3.0
角色定位：Reviewer / Planner / Release Operations Governance Architect
项目：MusicForge / song-agent

---

## 1. 背景

MusicForge 到 v6.2.1 已经把“本地自动化生成音乐”推进到了完整发行运营阶段：

- v6.0.0：Release Operations Dashboard，聚合 Release / Metadata / Audio / Rights / Format / Distribution / Submission / Submission Evidence / Verifier 状态。
- v6.1.0：Release Operations Runbook，把 next_actions 转成安全执行队列，只自动执行 refresh / export / zip / verify。
- v6.1.1：阻断已签核对象被 Runbook 静默重导出。
- v6.2.0：Release Operations Signoff / Archive / Change Request，把 accepted 后的运营证据归档签核。
- v6.2.1：修复 Operations Signoff reset 必须走 approved Change Request，并且 Change Request reset 后会变成 applied，不能复用。

现在主流程已经可以做到：

1. 生成音乐。
2. 编辑、混音、母带、格式编码。
3. 人工听审、修复、验收。
4. 元数据、版权、发行格式、分发包、提交包、提交证据归档。
5. Operations Dashboard 汇总状态。
6. Runbook 安全推进。
7. Operations Signoff 归档签核。
8. Change Request 控制签核后的 reset。

但还有一个结构性缺口：

> 证据都存在，但证据链还没有被串成一条“可审计、可追溯、可离线复核”的运营账本。

现在证据分散在这些位置：

- `.musicforge/releases/<release-id>/events.jsonl`
- `.musicforge/releases/<release-id>/operations/operations-report.json`
- `.musicforge/releases/<release-id>/operations/release-operations-package.zip`
- `.musicforge/releases/<release-id>/operations/runbooks/`
- `.musicforge/releases/<release-id>/operations/operations-signoff.json`
- `.musicforge/releases/<release-id>/operations/change-requests/`
- `.musicforge/releases/<release-id>/operations/archive-export/`
- `.musicforge/releases/<release-id>/distribution/`
- `.musicforge/releases/<release-id>/submissions/`
- `.musicforge/releases/<release-id>/submission-evidence/`
- Release Export / Distribution Export / Submission Export / Evidence Export / Operations Archive ZIP

这些单个文件和包都能验证，但外部 reviewer 仍然很难回答：

- 这个 Release 是按什么顺序推进到 accepted / archived 的？
- 哪些签核发生在前，哪些导出发生在后？
- Operations Signoff 之前是否真的有 current Operations Report、current Runbook、current verifier evidence？
- v6.2.1 的 Change Request 是否真的覆盖了 reset 操作？
- 签核后有没有未被 Change Request 覆盖的写操作？
- 某个 package hash 对应的是哪个时间点、哪个 verifier、哪个 signoff？
- 如果有人篡改某个 JSONL event、删掉某个 event、调换 event 顺序，能不能被发现？
- 一个 ZIP 离开本机后，除了能验证包本身，能不能验证“包是从哪个运营证据链来的”？

所以 v6.3.0 应该做：

> Release Operations Audit Ledger：把 Release 运营阶段的关键事件、签核、Runbook、Change Request、Package verifier、Archive evidence 串成 hash-chained 审计账本，并提供可导出、可离线验证、可在 Studio 查看时间线和证据图的审计层。

## 2. v6.3.0 总目标

新增 Release Operations Audit Ledger。

一句话目标：

> 对一个 Release 的运营闭环生成机器可验证的审计账本，证明它从 Dashboard readiness、Runbook safe execution、package verifier、Operations Signoff、Archive Export、Change Request reset 到最终 archived 的证据链是完整、未篡改、无越权变更的。

完成后，用户应该能：

- 在 Studio 的 Release Operations 页面看到 `Audit Ledger` tab。
- 点击 `Refresh Audit Ledger`，生成当前 Release 的运营审计报告。
- 看到 stage timeline、critical milestones、Change Request lifecycle、Runbook execution、package verifier、signoff/reset/archive 的完整顺序。
- 看到每个 ledger entry 的 hash、previous_hash、source_ref、evidence_ref、risk、actor、event_type。
- 导出 `Release Operations Audit Package`。
- 在外部干净目录用 CLI 验证：

```powershell
python -m song_agent.cli verify-release-operations-audit-package path\to\operations-audit.zip --json --strict --require-signed --require-archive
```

- 如果有人篡改 ledger entry、删掉 entry、重排 entry、污染本机路径、伪造 manifest.zip.entries、插入危险 ZIP entry，离线 verifier 必须 failed。
- 如果 Operations Signoff reset 没有 approved/applied Change Request，Audit Ledger 必须 failed 或 blocked。
- 如果签核后出现新导出、新 ZIP、新 reset、新 accepted 状态变更，但没有 Change Request 证据，Audit Ledger 必须 failed 或 blocked。

---

## 3. 非目标

v6.3.0 不做：

- 不做区块链、公证处、第三方时间戳服务。
- 不接真实 DSP / distributor API。
- 不做多人权限系统，不做用户登录权限矩阵。
- 不自动 approve Change Request。
- 不自动 reset、signoff、archive。
- 不把真实音频大文件、提交包大 ZIP、分发包大 ZIP 复制进 Audit Package。
- 不复制 provider response、token、cookie、平台后台链接、本机路径。
- 不要求所有历史 v1-v6 Release 都完全兼容。旧 Release 可以生成 partial / warning ledger，但 v6.3 新链路必须完整。

### 5.1 Ledger Entry

每条 ledger entry 是一个 canonical JSON object：

```json
{
  "schema_version": 1,
  "entry_id": "olae-000001",
  "release_id": "rel-000001",
  "sequence": 1,
  "occurred_at": "2026-06-04T10:00:00Z",
  "domain": "operations",
  "event_type": "operations_report_refreshed",
  "actor": "local-user",
  "risk": "read_only",
  "mutation_kind": "refresh",
  "source_ref": {
    "source_type": "operations_report",
    "source_id": "operations-report",
    "path_hint": "operations/operations-report.json",
    "payload_hash": "..."
  },
  "evidence_ref": {
    "artifact_type": "json",
    "artifact_id": "operations-report",
    "payload_hash": "...",
    "source_hash": "...",
    "integrity_ok": true,
    "stale": false
  },
  "causal_refs": [],
  "warnings": [],
  "previous_hash": null,
  "entry_hash": "..."
}
```

字段规则：

- `entry_id`：按 ledger 构建顺序生成，`olae-000001` 起。
- `sequence`：从 1 递增。
- `occurred_at`：来自源事件；没有源事件时使用文件记录中的 `generated_at` / `signed_at` / `updated_at`。
- `domain`：固定枚举。
- `event_type`：稳定枚举，不允许自由文本。
- `actor`：脱敏后的 actor；没有则 `local-user` 或 `unknown`。
- `risk`：`read_only` / `auto_safe` / `manual_required` / `signed_mutation` / `external_state` / `change_control`。
- `mutation_kind`：`refresh` / `export` / `zip` / `verify` / `signoff` / `reset` / `change_request` / `external_record` / `archive`。
- `source_ref.path_hint` 只能是相对提示，不能写绝对路径。
- `payload_hash` 使用 `stable_hash()` 或文件 sha256，必须明确口径。
- `previous_hash`：上一条 entry 的 `entry_hash`。
- `entry_hash`：`stable_hash(entry_without_entry_hash)`。

### 5.2 Ledger Report

`operations-audit-report.json`：

```json
{
  "schema_version": 1,
  "release_id": "rel-000001",
  "generated_at": "...",
  "status": "passed",
  "readiness": "archivable",
  "source_hash": "...",
  "ledger_hash": "...",
  "integrity_hash": "...",
  "summary": {
    "entry_count": 42,
    "domain_count": 8,
    "critical_milestone_count": 12,
    "blocker_count": 0,
    "warning_count": 1,
    "change_request_count": 1,
    "applied_change_request_count": 1,
    "signed_mutation_count": 0
  },
  "stage_timeline": [],
  "critical_milestones": [],
  "change_control": {},
  "package_verifiers": {},
  "coverage": {},
  "blockers": [],
  "warnings": []
}
```

`integrity_hash` 覆盖 report 的派生证据，排除：

```python
{"integrity_hash", "generated_at", "updated_at"}
```

### 5.3 Audit Manifest

`operations-audit-manifest.json`：

```json
{
  "schema_version": 1,
  "release_id": "rel-000001",
  "generated_at": "...",
  "app_version": "6.3.0",
  "summary": {
    "status": "passed",
    "entry_count": 42
  },
  "audit_report": {
    "integrity_hash": "...",
    "source_hash": "...",
    "ledger_hash": "..."
  },
  "files": [
    {
      "path": "operations-audit-report.json",
      "size_bytes": 1234,
      "sha256": "..."
    }
  ],
  "zip": {
    "path": "operations-audit.zip",
    "size_bytes": 12345,
    "sha256": "...",
    "entries": []
  },
  "integrity_hash": "..."
}
```

注意：

- Verifier 不能信 `manifest.zip.entries` 来放行文件。
- 允许 entry 只能来自 `manifest.files[].path` 加合法 sidecar。
- `manifest.zip.path` 只能是文件名，不能写绝对路径。

## 6. Ledger 来源

Audit Ledger 不直接信任单个事件文件。它从“源事件 + 当前证据文件 hash + integrity check”组合生成。

### 6.1 必纳入来源

必须纳入：

- Release document summary。
- Release events。
- Operations Report。
- Operations Export manifest。
- Operations Package verifier summary。
- Latest Runbook summary。
- Runbook events / result summary。
- Operations Signoff。
- Operations Signoff history。
- Operations Archive manifest。
- Operations Archive verifier summary。
- Operations Change Requests。
- Change Request events。
- Distribution signoff summaries。
- Submission signoff summaries。
- Submission Evidence signoff summaries。
- Release ZIP / Distribution ZIP / Submission ZIP / Evidence ZIP verifier summaries。

### 6.2 可选来源

可以纳入，但缺失不能直接 failed：

- Release Metadata QA summary。
- Audio QA summary。
- Mastering QA summary。
- Format Decision summary。
- Rights Clearance summary。
- Acceptance / Human Review evidence summary。
- Release Operations Runbook ZIP verifier summary。

这些在 Operations Report 中已有摘要，Audit Ledger 只做二次引用。

### 6.3 排序规则

Ledger entry 排序必须 deterministic：

1. `occurred_at`。
2. `domain_priority`。
3. `event_type`。
4. `source_id`。
5. `payload_hash`。

如果时间戳缺失或相同，不能导致不稳定排序。

### 6.4 domain priority

建议顺序：

```text
release
release_export
metadata
audio
rights
format_decision
distribution
submission
submission_evidence
operations_report
operations_runbook
operations_signoff
operations_change_request
operations_archive
operations_audit
```

## 7. Gate 和异常检测

Audit Report 必须输出 blockers / warnings。

### 7.1 Blockers

以下必须 failed：

- Ledger entry hash chain 断裂。
- Ledger entry 被删除、重复、重排后 hash 不一致。
- Audit Report integrity failed。
- Operations Report integrity failed。
- Operations Signoff payload hash failed。
- Operations Archive manifest integrity failed。
- Operations Archive verifier status failed。
- 已存在 Operations Signoff，但没有纳入 Signoff entry。
- 已存在 Operations Signoff reset，但没有 approved/applied Change Request。
- Change Request integrity failed。
- Change Request reset hash 与 reset signoff payload_hash 不一致。
- Signed/archived 后出现 export/zip/reset 类 mutation，但没有 applied Change Request 作为 causal_ref。
- Package ledger 缺 Release ZIP。
- Verifier summary 中出现 failed。
- Redaction scan failed。
- Source hash stale 且要求 `require_current=True`。

### 7.2 Warnings

以下可以 warning：

- 旧版本 Release 缺少某些事件来源。
- Runbook 不存在，但 Operations Signoff 也不存在。
- 部分 optional domain summary missing。
- Verifier summary 为 missing，但当前 stage 未要求。
- 事件时间戳缺失。
- actor 缺失。

### 7.3 Change Request 特别规则

v6.2.1 已经修复 reset 强制 approved CR。v6.3 必须继续强化：

- Audit Ledger 中每个 `operations_signoff_reset` entry 必须有 `causal_refs` 指向一个 `operations_change_request_applied` entry。
- 被引用 CR 必须：
  - `status == "applied"`。
  - `integrity_ok == true`。
  - `applied_signoff_reset_hash == reset.payload_hash`。
  - `scope` 包含 `operations` 或相关影响域。
- 同一个 CR 只能应用一次。
- 如果 reset 记录里 `change_request_id` 缺失，Audit Report 必须 failed。
- 如果 CR 是 `draft` / `submitted` / `rejected` / `cancelled`，Audit Report 必须 failed。

## 10. 离线 Verifier

新增：

```text
song_agent/release_operations_audit_verifier.py
```

必须检查：

- ZIP 可打开。
- ZIP size limit。
- total uncompressed size limit。
- entry count limit。
- raw central directory entry name。
- unsafe path：
  - `../`
  - absolute path
  - Windows drive path
  - UNC path
  - backslash entry
  - empty segment
- duplicate entry。
- required entries。
- manifest integrity hash。
- manifest.files shape。
- manifest.files hash 和 ZIP bytes 对账。
- extra entries：
  - strict 下 failed。
  - 非 strict 下 warning。
- 不能信 `manifest.zip.entries` 扩权。
- ledger chain：
  - sequence 连续。
  - previous_hash 正确。
  - entry_hash 正确。
  - ledger_hash 正确。
- report integrity hash。
- report ledger_hash 与 ledger JSONL 匹配。
- signoff summary hash。
- change request applied reset hash。
- redaction scan。
- blocked key scan。
- require_signed：
  - 必须有 signed / force_signed operations signoff evidence。
- require_archive：
  - 必须有 operations archive manifest / verifier summary。
  - verifier summary 不能 failed。
- require_current：
  - 如果 package 内记录 stale=true，则 failed。

Verifier 输出：

```json
{
  "schema_version": 1,
  "generated_at": "...",
  "status": "passed",
  "summary": {
    "release_id": "rel-000001",
    "entry_count": 42,
    "blocker_count": 0,
    "warning_count": 0
  },
  "checks": [],
  "blockers": [],
  "warnings": [],
  "redaction_findings": []
}
```

## 13. 安全与脱敏

必须继续沿用：

- `sanitize_metadata()`
- `sanitize_sensitive_text()`
- `SENSITIVE_VALUE_PATTERNS`
- `LOCAL_PATH_VALUE_PATTERNS`

Audit Package 不能包含：

- token
- api_key
- bearer
- GitHub token
- provider raw response
- 本机绝对路径
- UNC path
- source_path / local_path / file_path
- cookie
- platform account secret

`path_hint` 必须是相对路径提示。即使源文件在本机，导出时也不能写真实绝对路径。

ZIP 写入必须使用 list/Path API，不使用 shell。

## 18. Reviewer 验收重点

Reviewer 不只看测试通过，还要重点看：

- Ledger 是否真的 hash-chained。
- Verifier 是否不信 `manifest.zip.entries`。
- Raw central directory backslash entry 是否被抓。
- CR reset 是否必须 approved + applied。
- Signed/archived 后 mutation 是否能被 audit 抓到。
- Audit source hash 是否避免和 Operations Report summary 循环。
- Audit Package 是否不包含本机路径和敏感字段。
- `allow_signed=True` 是否没有被外部 API 暴露。
- Studio 按钮是否不会绕过后端 gate。
- release-check 是否覆盖 tamper / delete / reorder / duplicate / dangerous / backslash / spoof / redaction。

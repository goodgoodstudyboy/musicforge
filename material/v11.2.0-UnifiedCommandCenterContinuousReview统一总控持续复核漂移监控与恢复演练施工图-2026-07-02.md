# v11.2.0 Unified Command Center Continuous Review 统一总控持续复核、漂移监控与恢复演练施工图

## 0. 给开发的话

v11.1.1 已经把 v11.1.0 的关键安全缺口修住：UCC Archive 不再只信包内 signoff / history / manifest 自证，而是通过 `signoff-binding-summary.json` 绑定签核创建时的原始签核摘要。Reviewer 复现的“同步重签 signoff/history/manifest 伪造 signed_by”现在会失败。

当前稳定基线：

- v11.1.1
- Commit：`ca8d47465d30eea930e321362268c6c8cee0603e`
- GitHub Release：https://github.com/goodgoodstudyboy/musicforge/releases/tag/v11.1.1
- `release-check --profile ga --skip-tests --json`：`27/27 passed`
- forged signer 复现：`tampered=failed`

这说明 v11.1.1 已经可以作为当前稳定基线。

下一步不要再往 UCC 里塞一个局部小 ZIP。v11.0 / v11.1 已经完成了：

```text
统一总控台
统一证据图
统一 readiness
统一 safe runbook
统一 signoff
统一 archive
统一 handoff
```

现在真正缺的是“签核之后怎么办”。

真实项目里，签核不是终点。签核后仍然会发生：

- 某个底层 Release ZIP 被重建。
- 某个 Distribution / Submission evidence 被替换。
- Public Trust Center anchor 被更新。
- Maintenance backup 过期。
- GA readiness 报告变 stale。
- UCC Archive 还在，但底层外部 evidence 已经不再匹配。
- 交付负责人想知道：已签核系统是否仍然可信？

所以 v11.2.0 的定位是：

> 建立 Unified Command Center Continuous Review，定期复核已签核 UCC Archive / Handoff / 底层外部证据，生成 drift report、incident board、recovery drill evidence 和离线可验证的持续复核包。它不自动重开签核，不自动修复，只把“签核后的可信状态”变成可审计、可复验、可演练的长期运营证据。

一句话：

```text
v11.1 证明“这一刻可以签核”。
v11.2 证明“签核之后还能持续知道它是否仍然可信”。
```

## 2. 为什么需要 v11.2.0

### 2.1 v11.1.1 解决的是静态签核

v11.1.1 能回答：

- 这个 UCC 是否 ready。
- 这个 UCC 是否被签核。
- 这个 Archive 是否和签核绑定。
- 这个 Handoff 是否和 Archive 绑定。
- 是否有人篡改了 Archive 内的签核人。

但它不能持续回答：

- 一周后底层 evidence 是否变化。
- UCC Archive 是否仍然对应当前底层 evidence。
- Handoff 是否仍然可以代表当前交付状态。
- 如果 drift 发生，是否已记录 incident。
- 是否已经演练过从 Archive / Handoff 恢复验证。

### 2.2 不能只靠重新跑 GA

`release-check --profile ga` 是发布时门禁，不是持续运营状态。

持续复核需要：

- 有复核对象。
- 有复核时间。
- 有复核输入。
- 有复核结果。
- 有 incident / drift 分类。
- 有手动动作清单。
- 有恢复演练证据。
- 有离线 verifier。

### 2.3 这版要避免重复造轮子

v11.2.0 不重做：

- UCC verifier。
- Archive verifier。
- Handoff verifier。
- Release / Distribution / Submission verifier。
- Maintenance backup verifier。

它调用这些底层 verifier，记录结果和漂移。

## 3. v11.2.0 目标

### 3.1 必须完成

1. 新增 UCC Continuous Review Store。
2. 支持对 signed UCC 创建 review plan。
3. 支持 refresh / run review。
4. 复核对象包括：
   - UCC Archive ZIP
   - UCC Archive verification report
   - Final Handoff ZIP
   - Handoff verification report
   - UCC ZIP
   - UCC verification report
   - 底层外部 evidence reports
   - release-check / GA report
5. 生成 Drift Report。
6. 生成 Incident Board。
7. 支持 Recovery Drill：
   - verify archive
   - verify handoff
   - verify UCC
   - verify selected external evidence
   - dry restore / backup verification if maintenance evidence exists
8. 支持 Incident -> Change Request draft。
9. 新增 Continuous Review ZIP。
10. 新增 `verify-unified-command-center-continuous-review-package`。
11. 接入 CLI / API / Studio。
12. 接入 Release signoff / GA readiness 可选 gate：
    - `require_unified_command_center_continuous_review=true`
13. release-check 新增 `v112.unified_command_center_continuous_review_smoke`。
14. README / CHANGELOG / version bump 到 `11.2.0`。

### 3.2 不做

v11.2.0 不做：

- 自动 reset signoff。
- 自动 approve CR。
- 自动修复底层 evidence。
- 自动重建 signed Archive / Handoff。
- 云端定时器。
- 后台常驻 scheduler。
- 多用户权限。
- 第三方签名服务。

### 3.3 复核原则

1. 只复核，不自动改变 signed evidence。
2. signed UCC 不可被 review 隐式刷新。
3. drift 只生成 incident / CR draft，不自动 reset。
4. Recovery Drill 是 dry-run 和 verifier-based，不覆盖现有文件。
5. ZIP 固定结构。
6. verifier 不信包内自证。

## 7. Store 行为

### 7.1 `create_plan()`

输入：

- `center_id`
- optional scope
- optional requirements
- created_by

前置：

- Center 必须 signed。
- Archive ZIP 必须存在。
- Archive verification report 必须 passed。
- Handoff ZIP 可选，但如果 scope 要求 handoff，则必须存在且 passed。

输出：

- `review-plan.json`

### 7.2 `run_review()`

行为：

1. 读取 plan。
2. 收集当前 source。
3. 运行 archive verifier。
4. 运行 handoff verifier。
5. 运行 UCC verifier。
6. 校验外部 evidence verification report。
7. 比较 plan source 和 current source。
8. 生成 drift report。
9. 根据 drift 生成 incident board。
10. 生成 recovery drill report。
11. 生成 review runbook。

注意：

- 不允许修改 signed UCC。
- 不允许自动 reset。
- 不允许自动 rebuild archive/handoff。

### 7.3 `create_change_request_drafts()`

从 critical / high drift 生成 CR draft。

这只是 draft，不写入 UCC 正式 CR 目录，除非用户显式 apply。

字段：

- title
- reason
- source drift id
- recommended action
- component type/id

### 7.4 `apply_change_request_draft()`

可选：v11.2 可以先不做 apply，只输出 draft。

如果做：

- 必须仍是 draft。
- 必须让用户显式确认。
- 只能创建 UCC Change Request draft，不能 approve。

建议 v11.2 只做 draft export，不做 apply，减少风险。

### 7.5 `export_package()` / `build_zip()`

导出固定结构 package。

构建前：

- 重建 source。
- 如果 source 变化，必须 409：`Continuous review source is stale. Run review again.`
- 如果 plan integrity broken，failed。

### 7.6 `verify_package()`

调用离线 verifier。

## 11. Verifier 设计

### 11.1 固定 allow-list

Continuous Review ZIP entries：

```text
README.txt
manifest.json
review-plan.json
review-source.json
drift-report.json
incident-board.json
recovery-drill-report.json
review-runbook.json
review-runbook-result.json
change-request-drafts.json
package-fingerprints.json
```

不允许额外 entry。

### 11.2 必查项

`verify-unified-command-center-continuous-review-package` 必须检查：

1. ZIP exists。
2. fixed allow-list。
3. duplicate entry。
4. raw backslash entry。
5. dangerous path。
6. `.musicforge/` case-insensitive。
7. nested ZIP 禁止。
8. manifest package_type。
9. manifest integrity。
10. manifest files exact match。
11. all JSON integrity。
12. source hash binding。
13. drift report source binding。
14. incident board source binding。
15. recovery drill source binding。
16. external archive verification binding。
17. external handoff verification binding。
18. if `--require-clear`，incident board 必须 clear。
19. if `--require-recovery-drill`，recovery drill 必须 passed。
20. redaction scan。

### 11.3 不能只信包内自证

Verifier 必须能接收外部：

- archive ZIP
- archive verification report
- handoff ZIP
- handoff verification report
- UCC ZIP
- UCC verification report

至少 archive / handoff 要作为 v11.2 必需外部绑定。

不能只信：

- drift-report 自己写 no drift。
- incident-board 自己写 clear。
- recovery-drill 自己写 passed。
- manifest 自己写 source hash。

### 11.4 全量重签攻击回归

必须覆盖：

1. 篡改 `drift-report.json` 把 critical drift 改成 clear。
2. 同步重算 drift integrity。
3. 同步重算 incident board。
4. 同步重算 manifest。
5. 不更新外部 archive/handoff verification binding。

Verifier 必须 failed。

## 13. release-check 规划

新增：

```text
v112.unified_command_center_continuous_review_smoke
```

profiles：

- v11
- latest
- ga
- quick
- full

### 13.1 Happy path

Smoke 应覆盖：

1. 创建 ready UCC。
2. signoff。
3. archive。
4. handoff。
5. create continuous review plan。
6. run review。
7. drift report passed / no drift。
8. recovery drill passed。
9. build continuous review ZIP。
10. verify passed。
11. GA gate passed。

### 13.2 Failure path

必须覆盖：

1. archive ZIP tamper -> review detects drift。
2. handoff ZIP tamper -> review detects drift。
3. external verification report stale -> drift。
4. drift report full resign -> verifier failed。
5. incident board full resign -> verifier failed。
6. recovery drill full resign -> verifier failed。
7. declared extra entry -> failed。
8. dangerous path -> failed。
9. raw backslash entry -> failed。
10. `.MusicForge/` -> failed。
11. nested ZIP -> failed。
12. redaction pollution -> failed。

Detail 示例：

```text
review=passed, drift=0, incidents=clear, drill=passed, verify=passed, archive_tamper=failed, full_resign=failed, declared_extra=failed
```

## 20. 完成定义

v11.2.0 完成后，用户应该能做到：

```text
我已经签核 UCC。
我已经生成 Archive / Handoff。
我现在可以运行 Continuous Review，证明签核后的证据仍然可信。
如果底层 evidence 漂移，系统会生成 drift / incident / CR draft。
我可以运行 Recovery Drill，证明 Archive / Handoff / UCC 仍能离线复验。
我可以导出 Continuous Review ZIP 给 reviewer。
GA / Release 可以要求 Continuous Review clear。
```

这版的价值不是“又多一个报告”，而是让 MusicForge 从一次性准出系统升级为长期可运营、可复核、可恢复的本地音乐发布系统。

# 音乐生成项目接手方案

日期：2026-05-05

## 当前共识

这个项目要做的是自动化生成音乐，定位可以参考本机相邻的 `book` 项目里的 NovelForge：NovelForge 是自动化写小说的工程化流水线，这个项目则是自动化生成歌曲/音乐的工程化流水线。

核心原则是先本地化验证，再逐步接入真实模型和更复杂的渲染能力。也就是说，第一阶段不能依赖外部黑盒音乐生成 API，也不能要求真实 LLM 一定可用才算跑通。最小闭环必须在本地稳定完成：

```text
song_request.json
  -> song.json
  -> song.mid
```

当前项目已经有清晰方向，但还处在脚手架阶段：

- `SongRequest` 输入 schema 已有基础校验。
- CLI 已支持 `--dry-run`。
- `SongAgent.generate()` 还没有实现。
- `render_midi()` 还没有实现。
- Provider 只有协议接口，没有真实适配器。
- `SongPlan` 目前只是 dataclass，还缺少 from_dict、to_dict 和 validator。

## 参考 NovelForge 的项目组织

NovelForge 的结构值得参考，不是照搬小说业务，而是参考它的工程形态：

```text
novelforge/
  cli.py
  client.py
  codex.py
  pipeline.py
  projectio.py
  prompts.py
  quality.py
  server.py
  webui.py
examples/specs/
tests/

material/
```

音乐项目可以逐步演进成类似结构：

```text
song_agent/
  cli.py              # 命令行入口
  agent/
    pipeline.py       # 歌曲生成主流程
  providers/
    base.py           # Provider 协议
    openai_compatible.py
  renderers/

    audio.py          # 后续 FluidSynth/FFmpeg
  schemas/
    song.py           # SongRequest/SongPlan/NoteEvent 等数据合同
  prompts/
    song_plan.md      # 生成结构化歌曲计划的 prompt

  projectio.py        # 后续统一处理输出目录和产物命名

  song_request.json
tests/
runs/                 # 后续生成结果
material/             # 交互记录、方案、调研、对比报告
```

`material/` 以后专门放过程文档，包括：

- 接手方案
- 需求讨论记录
- 调研报告
- 横向对比
- MVP 验证记录
- 质量评审记录
- 开发任务拆解

`docs/` 更适合放稳定设计文档，`material/` 更适合放迭代过程和交互沉淀。

## MVP 目标

第一个可交付版本只做一件事：

```text
输入 JSON brief
  -> 生成结构化 SongPlan
  -> 校验 SongPlan
  -> 输出 song.json
  -> 渲染 song.mid
```

暂时不做：

- 不接 Suno、Udio、Mureka、ElevenLabs Music 等闭源音乐生成 API。
- 不做真人演唱。
- 不做 Web UI。
- 不做 WAV/MP3。
- 不做复杂 DAW 集成。
- 不把真实 LLM 调用作为本地 MVP 的前置条件。

MVP 的交付标准：

```powershell
python -m song_agent.cli examples\song_request.json --out runs\demo
```

运行后应生成：

```text
runs/demo/song.json
runs/demo/song.mid
```

并且 `song.mid` 能被常见 MIDI 播放器、MuseScore 或 DAW 打开。

## 阶段 1：补齐数据模型和确定性校验

目标：让系统有一个可信的中间格式边界。

修改重点：

- `song_agent/schemas/song.py`
- 可新增 `song_agent/quality.py` 或 `song_agent/schemas/validation.py`

要实现：

- `SongPlan.from_dict()`
- `SongPlan.to_dict()`
- `SongPlan.validate()` 或独立 `validate_song_plan(plan)`
- `NoteEvent` 校验：
  - `pitch` 必须在 0 到 127。
  - `velocity` 必须在 1 到 127。
  - `start_beat >= 0`。
  - `duration_beats > 0`。
- `SongSection` 校验：
  - `start_bar >= 1`。
  - `bars > 0`。
  - `chords` 非空。
- `SongPlan` 校验：
  - `tempo_bpm` 必须在 40 到 240。
  - MVP 阶段 `meter` 先只支持 `4/4`。
  - 至少包含 melody、chords、bass、drums 四类轨道。
  - 所有 note 时间不能明显超出歌曲总长度。

测试要求：

- 合法 `SongPlan` 能通过。
- 非法 pitch 会失败。
- 非法 duration 会失败。
- 缺少 chords 或 drums 轨道会失败。
- 空 section 或无和弦 section 会失败。

验收命令：

```powershell
python -m pytest -q
```

## 阶段 2：实现本地 deterministic generator

目标：不依赖 LLM，先本地生成一首可验证的 demo 歌曲。

修改重点：

- `song_agent/agent/pipeline.py`

实现要求：

- `SongAgent.generate(request)` 返回有效 `SongPlan`。
- provider 可以暂时为空，或者使用固定本地 provider。
- 结构可以先固定：
  - intro：4 bars
  - verse：8 bars
  - chorus：8 bars
  - outro：4 bars
- 默认：
  - key：优先使用 request.key，否则 `C major`
  - tempo：优先使用 request.tempo_bpm，否则 92
  - meter：`4/4`
- 至少生成四类轨道：
  - melody：简单主旋律或音阶动机。
  - chords：每小节柱式和弦。
  - bass：根音低音。
  - drums：kick、snare、hat。

验收命令：

```powershell
python -m song_agent.cli examples\song_request.json --out runs\demo
```

本阶段至少应能输出：

```text
runs/demo/song.json
```

## 阶段 3：实现 MIDI 渲染

目标：把 `SongPlan` 转成真实 `.mid` 文件。

修改重点：

- `song_agent/renderers/midi.py`
- `pyproject.toml`

建议依赖：

- `mido`

MVP 阶段不需要复杂音色，只要能输出标准 MIDI。

实现要求：

- melody、chords、bass、drums 分 track 或分 channel。
- tempo 要写入 MIDI meta message。
- 默认 PPQ 可以用 480 ticks per beat。
- drums 使用 General MIDI drum channel，也就是 MIDI channel 9。
- 常用鼓音：
  - kick：36
  - snare：38
  - closed hat：42
- 非鼓轨按 `NoteEvent.pitch` 输出 note_on/note_off。
- 每个轨道内部要按 `start_beat` 排序，转换成 delta time。

验收输出：

```text
runs/demo/song.mid
```

验收方式：

- 文件存在且大小大于 0。
- 可以被 MIDI 播放器、MuseScore 或 DAW 打开。
- 听感上至少有旋律、和弦、低音和鼓。

## 阶段 4：CLI 串完整流程

目标：一条命令完成本地闭环。

修改重点：

- `song_agent/cli.py`

CLI 行为：

- `--dry-run`：只验证并打印 `SongRequest`。
- 默认模式：
  - 读取 request JSON。
  - 生成 `SongPlan`。
  - 校验 `SongPlan`。
  - 写出 `song.json`。
  - 渲染 `song.mid`。
  - 打印输出路径。

建议默认输出目录改成 `runs/<request-title-slug>` 或保留用户传入 `--out`。长期可以参考 NovelForge，把每次运行独立落盘，避免覆盖。

错误处理要求：

- JSON 解析失败要给出清楚提示。
- schema 校验失败要说明字段。
- MIDI 渲染失败要返回非零退出码。

验收命令：

```powershell
python -m song_agent.cli examples\song_request.json --dry-run
python -m song_agent.cli examples\song_request.json --out runs\demo
python -m pytest -q
```

## 阶段 5：接入 OpenAI-compatible Provider

只有本地 deterministic 闭环跑通后，再接真实模型。

修改重点：

- `song_agent/providers/base.py`
- `song_agent/providers/openai_compatible.py`
- `song_agent/prompts/song_plan.md`
- `song_agent/agent/pipeline.py`

实现要求：

- provider 只负责返回 JSON dict，不直接写文件，不直接生成 MIDI。
- provider 输出必须经过 `SongPlan.from_dict()` 和 validator。
- JSON 解析失败不能继续渲染。
- 保留 deterministic fallback，方便无网络、本地测试。
- API key 和 base URL 只从环境变量或项目本地配置读取。

建议环境变量：

```text
OPENAI_API_KEY
OPENAI_BASE_URL
OPENAI_MODEL
```

建议 CLI：

```powershell
python -m song_agent.cli examples\song_request.json --out runs\local-demo
python -m song_agent.cli examples\song_request.json --out runs\llm-demo --provider openai-compatible
```

## Reviewer 检查清单

每次开发交付时重点检查：

- 是否仍然可以无网络、本地跑通。
- 是否保留了 `song_request.json -> song.json -> song.mid` 的闭环。
- 是否所有模型输出都经过 schema 和 validator。
- 是否把创意生成和确定性渲染分清楚。
- 是否没有提前引入 Web UI、WAV/MP3、DAW 集成等非 MVP 内容。
- 是否新增了必要测试。
- 是否 CLI 错误信息足够清楚。
- 是否输出目录不会误覆盖重要产物。
- 是否没有引入过重依赖。
- 是否文档同步说明当前能力和限制。

## 给开发的第一批任务

建议第一批任务拆成 4 个 PR 或 4 次提交：

1. 补 `SongPlan` 序列化、反序列化和 validator，并增加测试。
2. 实现 deterministic `SongAgent.generate()`，让它生成固定但完整的 `SongPlan`。
3. 实现 `render_midi()`，输出可打开的 `song.mid`。
4. 改造 CLI，默认模式生成 `song.json` 和 `song.mid`，并把输出目录改为 `runs/` 下的可审计产物目录。

第一批任务完成后，项目才算从“脚手架”进入“本地 MVP 可验证”阶段。

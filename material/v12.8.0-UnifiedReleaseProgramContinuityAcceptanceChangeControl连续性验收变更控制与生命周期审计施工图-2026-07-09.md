# v12.8.0 Unified Release Program Continuity Acceptance Change Control 连续性验收变更控制与生命周期审计施工图

日期：2026-07-09

目标版本：v12.8.0

当前基线：v12.7.0 Unified Release Program Continuity Acceptance Board 稳定基线

## 1. 背景

v12.0 到 v12.7 已经把 Unified Release Program 推进到项目级交付、证据保险库、连续性恢复、外部灾备交付套件和外部验收委员会：

- v12.0：Unified Release Program Board，把多个 Release Train Handoff 聚合成 Program 级准出。
- v12.1：Unified Release Program Operations，提供 Program CR、reset、runbook、continuous review 和 lifecycle archive。
- v12.2：Unified Release Program Final Handoff Board，完成 Program 最终交接验收。
- v12.3：Unified Release Program Evidence Vault，聚合 Program / Operations / Handoff / accepted evidence。
- v12.4：Unified Release Program Vault Operations，完成证据保险库长期托管和签核归档。
- v12.5：Unified Release Program Continuity Recovery，完成项目级只读恢复演练和连续性恢复签核。
- v12.6：Unified Release Program Continuity Distribution Kit，把 Continuity Archive、Vault Operations Archive、Evidence Vault 打包给外部灾备接收方。
- v12.7：Unified Release Program Continuity Acceptance Board，多接收方、多组织、多角色验收 Continuity Distribution Kit，并生成 signed immutable acceptance archive。

v12.7 解决了“外部灾备接收方是否可信验收当前 Kit”的问题。但签核后真实运营里仍有几个未闭合点：

- 如果验收委员会签核后发现接收方组织、角色、接收范围或 Kit evidence 需要调整，当前只能新建一套流程，没有受控 reset / successor Board。
- v12.7 明确不做 approved Change Request reset，导致签核后的改动没有可审计的因果链。
- 多轮签核、reset、继任签核之间缺少生命周期报告，Release / GA 只能看当前 Board Archive，不能说明历史上发生了几次受控变更。
- 外部审计时需要证明：历史 Archive 没有被删除覆盖，reset 是由 approved CR 触发，当前签核是 reset 后的新一代有效签核。

v12.8 的目标是补上 **Continuity Acceptance Change Control + Lifecycle Audit**：对 v12.7 Acceptance Board 的签核后变更进行受控管理，并为 Release / GA 提供当前 generation 的有效性和完整历史审计证据。

## 2. 版本目标

v12.8 新增 **Unified Release Program Continuity Acceptance Change Control**，重点交付：

1. 为已签核的 Continuity Acceptance Board 提供 approved CR reset。
2. reset 后原签核不再作为 current acceptance evidence，但历史 Archive 必须保留。
3. reset 必须绑定 approved、single-use、action-scoped Change Request，不能通过删除 signoff 文件、篡改 history 或重复使用 CR 绕过。
4. reset 后必须重新 refresh Board、重新满足 quorum、重新 signoff、重新 archive、重新 verify，才能恢复 Release / GA ready。
5. 新增 Lifecycle Audit，把多 generation Board / signoff / archive / reset proof 串成可离线验证的生命周期证据。
6. Release signoff / GA readiness 可要求 current Acceptance Board + Change Control / Lifecycle Audit 同时通过。

这一版不是小修，而是把 v12.7 的外部灾备验收从“单次签核”提升为“可长期运营、可变更、可审计的连续性验收治理层”。

## 3. 非目标

v12.8 不做以下内容：

- 不重新设计 v12.7 response / accepted evidence / Board quorum 规则。
- 不自动生成外部 receiver response。
- 不自动批准 Change Request。
- 不自动修改 Continuity Distribution Kit、Continuity Archive、Vault Operations Archive 或 Evidence Vault。
- 不删除历史 Acceptance Archive；reset 只改变 current 状态，不清除历史。
- 不做第三方 CA、公钥基础设施或链上登记。
- 不做完整 Studio UX 优化，只接入必要操作入口和状态信号。

## 7. 数据模型

### 7.1 Change Control State

```json
{
  "schema_version": 1,
  "package_type": "musicforge_unified_release_program_continuity_acceptance_change_control",
  "program_id": "urp-000001",
  "status": "current_signed",
  "current_generation": 2,
  "current_acceptance_archive_hash": "...",
  "current_acceptance_verification_hash": "...",
  "current_signoff_hash": "...",
  "reset_count": 1,
  "open_change_requests": 0,
  "used_change_requests": 1,
  "warnings": [],
  "integrity_hash": "..."
}
```

`status` 取值：

```text
no_acceptance
current_signed
reset_applied
needs_resignoff
stale_acceptance
blocked
```

规则：

- `current_signed` 只在当前 generation 有 signed Acceptance Board、Archive ZIP、verification report、external signoff binding 且 runtime verify passed 时成立。
- `reset_applied` 表示已执行 reset，但尚未完成新一代 signoff。
- `needs_resignoff` 表示 reset 后 Board 已重建但未签核。
- `stale_acceptance` 表示 current Acceptance Archive 或 Kit evidence 已过期。
- `blocked` 表示 Change Control 自身证据不完整或冲突。

### 7.2 Change Request

```json
{
  "schema_version": 1,
  "package_type": "musicforge_unified_release_program_continuity_acceptance_change_request",
  "program_id": "urp-000001",
  "change_request_id": "urpcacr-000001",
  "change_type": "reset_continuity_acceptance_signoff",
  "target_generation": 1,
  "target_acceptance_signoff_hash": "...",
  "target_acceptance_archive_hash": "...",
  "target_acceptance_verification_hash": "...",
  "allowed_actions": ["reset_continuity_acceptance_signoff"],
  "requested_by": "operator",
  "reason": "Receiver requested updated custody contact.",
  "status": "pending",
  "created_at": "...",
  "payload_hash": "...",
  "integrity_hash": "..."
}
```

P1 约束：

- `change_type` 必须等于 `reset_continuity_acceptance_signoff`。
- `allowed_actions` 必须包含 `reset_continuity_acceptance_signoff`。
- `target_acceptance_signoff_hash` 必须匹配当前 signed Board。
- `target_acceptance_archive_hash` 和 `target_acceptance_verification_hash` 必须匹配当前 Archive ZIP / verification report。
- CR 只能 single-use。

### 7.3 Approval

```json
{
  "schema_version": 1,
  "package_type": "musicforge_unified_release_program_continuity_acceptance_change_approval",
  "program_id": "urp-000001",
  "change_request_id": "urpcacr-000001",
  "status": "approved",
  "approved_by": "program_owner",
  "role": "continuity_governance_owner",
  "approved_at": "...",
  "approved_actions": ["reset_continuity_acceptance_signoff"],
  "change_request_payload_hash": "...",
  "change_request_integrity_hash": "...",
  "approval_payload_hash": "...",
  "integrity_hash": "..."
}
```

P1 约束：

- approval 的 `change_request_payload_hash` 必须反查当前 CR。
- approval 的 `approved_actions` 必须覆盖 reset action。
- status 必须是 `approved`。
- approval 不能被复用到另一个 CR 或另一个 generation。

### 7.4 Reset Proof

Reset 执行时必须立刻落盘 reset proof，而不是 export/archive 时现算：

```json
{
  "schema_version": 1,
  "package_type": "musicforge_unified_release_program_continuity_acceptance_reset_proof",
  "program_id": "urp-000001",
  "reset_id": "urpcar-000001",
  "change_request_id": "urpcacr-000001",
  "reset_generation_from": 1,
  "reset_generation_to": 2,
  "reset_by": "operator",
  "reset_at": "...",
  "reason": "Approved continuity acceptance reset.",
  "previous_signoff_hash": "...",
  "previous_archive_hash": "...",
  "previous_verification_hash": "...",
  "change_request_hash": "...",
  "approval_hash": "...",
  "binding_hash": "...",
  "payload_hash": "...",
  "integrity_hash": "..."
}
```

Reset proof 必须绑定：

- 当前 signed Acceptance signoff。
- 当前 Acceptance Archive ZIP。
- 当前 Acceptance verification report。
- 当前 external signoff binding。
- approved CR。
- approval payload。
- reset 前 generation。
- reset 后 generation。

## 8. 核心流程

### 8.1 创建 Change Request

CLI：

```bash
python -m song_agent.cli unified-release-program-continuity-acceptance-change create-cr \
  --program-id urp-000001 \
  --change-type reset_continuity_acceptance_signoff \
  --reason "Receiver requested updated continuity custody contacts"
```

Store：

```python
store.create_change_request(program_id, payload)
```

规则：

- Program 必须存在。
- 当前 Continuity Acceptance Board 必须 signed。
- 当前 Archive ZIP 和 verification report 必须 runtime passed。
- 当前 signoff binding 必须存在并匹配 Archive。
- 如果已有 open CR 指向同一个 current signoff，默认返回 existing，不能重复创建。

### 8.2 Approve CR

CLI：

```bash
python -m song_agent.cli unified-release-program-continuity-acceptance-change approve-cr \
  --program-id urp-000001 \
  --change-request-id urpcacr-000001 \
  --approved-by alice \
  --role continuity_governance_owner
```

规则：

- 只能 approve `pending` CR。
- approval 必须绑定 CR payload hash。
- approval 不能由 import 端补 source binding。
- approval 不能覆盖 CR 的 `allowed_actions`。

### 8.3 Reset Acceptance Signoff

CLI：

```bash
python -m song_agent.cli unified-release-program-continuity-acceptance-change reset-signoff \
  --program-id urp-000001 \
  --change-request-id urpcacr-000001 \
  --reset-by alice \
  --reason "Approved reset for updated receiver proof"
```

Store：

```python
store.reset_acceptance_signoff(program_id, change_request_id, payload)
```

P1 行为：

- reset 前必须 runtime verify current Acceptance Archive。
- reset 前必须 verify external signoff binding。
- reset 前必须确认 CR/approval 是 current、approved、single-use、action-scoped。
- reset 成功后：
  - CR 标记 `applied`。
  - reset proof 写入 `reset-proofs/`。
  - lifecycle event 写入 `lifecycle-event-log.jsonl`。
  - current generation +1。
  - v12.7 Board 当前状态变成非 signed ready。
  - Release / GA gates 必须失败，直到新 generation 重新签核。

禁止行为：

- 不能通过删除 `continuity-acceptance-signoff.json` 重开。
- 不能 force reset。
- 不能重复使用同一个 CR。
- 不能用 `allowed_actions` 不含 reset 的 CR reset。
- 不能用 target signoff hash 不匹配的 CR reset。

### 8.4 Successor Board

Reset 后，开发不需要新增另一套 response 模型，沿用 v12.7：

```bash
python -m song_agent.cli unified-release-program-continuity-acceptance import-response ...
python -m song_agent.cli unified-release-program-continuity-acceptance create-accepted-evidence ...
python -m song_agent.cli unified-release-program-continuity-acceptance refresh-board ...
python -m song_agent.cli unified-release-program-continuity-acceptance signoff ...
python -m song_agent.cli unified-release-program-continuity-acceptance archive-zip ...
python -m song_agent.cli unified-release-program-continuity-acceptance verify-archive ...
```

v12.8 需要保证：

- Successor Board 的 source generation 是 reset 后 generation。
- 新 signoff 不能复用旧 signoff binding。
- 新 Archive verification report 必须绑定新 Archive ZIP。
- Lifecycle Audit 能同时验证旧 generation 和新 generation。

## 10. Archive ZIP

Change Control Archive ZIP 固定 allow-list：

```text
README.txt
manifest.json
change-control-state.json
change-request-index.json
reset-proof-index.json
lifecycle-report.json
lifecycle-event-log.jsonl
current-generation.json
change-requests/<cr-id>.json
change-requests/<cr-id>-approval.json
change-requests/<cr-id>-binding-report.json
reset-proofs/<reset-id>.json
reset-proofs/<reset-id>-binding-summary.json
generations/generation-000001/acceptance-archive-verification-summary.json
generations/generation-000001/signoff-binding-summary.json
generations/generation-000001/source-summary.json
generations/generation-000002/acceptance-archive-verification-summary.json
generations/generation-000002/signoff-binding-summary.json
generations/generation-000002/source-summary.json
```

Verifier 必须拒绝：

- ZIP duplicate entry。
- raw backslash entry。
- `.musicforge/` 或大小写变体。
- nested ZIP，除非未来明确 allow-list；v12.8 不允许。
- manifest.files[] 声明额外文件。
- package-index 或 file-index 自报额外文件。
- ZIP trailing data。
- redaction 扫描失败。

- 如果 `require_unified_release_program_continuity_acceptance_change_control=true`，不能把 `not_configured` 当 passed。
- Change Control Archive verification 必须 `passed`。
- Current Acceptance Archive verification 必须 `passed`。
- Current generation 必须 signed。
- reset_applied / needs_resignoff / stale_acceptance 都必须 hard block。
- force signoff 不能绕过 stale current acceptance 或 failed lifecycle audit。

## 18. 安全边界

P1 必须写死：

1. reset proof 必须在 reset 执行时独立落盘，archive/verifier 不能现算。
2. Change Control Archive verifier 必须通过外部 current Acceptance Archive、verification report、signoff binding 反查 current generation。
3. CR 必须 approved、single-use、action-scoped。
4. reset 后 Release / GA 必须失败，直到 successor Board 重新 signed + archive verified。
5. signed 后 export/zip 前必须 runtime verify source，不能生成一个离线失败包。
6. lifecycle audit 不能信 report 自证，必须从 event log / CR / approval / reset proof / generation summaries 重建。
7. ZIP verifier 必须固定 allow-list，不能信 manifest 自报。
8. raw ZIP central directory 必须扫描反斜杠 entry。
9. trailing data 必须 failed。
10. force signoff 不得绕过 stale / reset_applied / failed lifecycle。

- CLI repeat 参数只作为便捷输入；主路径使用 manifest 或明确的 keyed 参数。
- smoke 中 detail 输出要包含 reset_count、current_generation、gate_after_reset。

## 22. 交付标准

v12.8 完成后，应满足：

- 外部灾备验收不再只是单次 signed Board。
- 签核后的 reset 有 approved CR、reset proof、history 和 lifecycle audit。
- reset 后旧签核不能继续作为 current ready。
- successor Board 能恢复 current ready，但必须重新满足 quorum。
- Release / GA 能要求 current Acceptance + Change Control lifecycle 同时通过。
- 离线 verifier 能发现 CR 伪造、reset proof 伪造、history full-resign、current archive 替换、manifest extra、raw path 攻击和 trailing data。

## 23. 给开发的话

这版不要急着先堆 API。先把 Store 和 verifier 的因果链做实：current Acceptance Archive、external verification report、external signoff binding、approved CR、reset proof、successor signoff、lifecycle event log 这几件事必须能互相反查。只要有一个环节只能靠 ZIP 内部 JSON 自证，就会被 reviewer 打回。

优先写这些回归：

- reset 后 gate 必须 failed。
- successor signoff 后 gate 才能恢复 passed。
- wrong action / unapproved / reused CR 都必须 409。
- reset proof full-resign 必须 failed。
- signed source tamper 后 export/zip 必须 409。
- lifecycle report 改 reset_count 后，即使重算 integrity，也必须 failed。

v12.8 的判断标准不是“能生成一个包”，而是“经历多轮 reset 和 successor signoff 后，仍能离线证明每一次变更都是受控、授权、单次使用、不可伪造的”。

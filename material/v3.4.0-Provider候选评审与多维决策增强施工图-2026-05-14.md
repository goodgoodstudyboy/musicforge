# v3.4.0 Provider 候选评审与多维决策增强施工图

日期：2026-05-14

当前稳定基线：v3.3.1

目标版本：v3.4.0

定位：在 v3.3.1 已经完成 Review Sprint Dashboard / Metrics 的基础上，引入 Provider Judge 评审层，对 ReviewTask candidates 和 ReviewSprint candidates 做可解释、多维度、可审计的候选评审。v3.4.0 只增强“判断依据”和“决策报告”，不自动 apply，不自动 resolve，不自动 close sprint。

---

## 1. 背景

当前系统已经具备完整反馈推进链路：

```text
ReviewTask
  -> local/provider candidates
  -> Decision Report
  -> ReviewSprint
  -> Recommendation Report
  -> Action Queue
  -> Metrics Dashboard
```

v2.9.0 已经有 provider review candidates。

v3.0.0-v3.2.1 已经能把多个 task 组织成 Sprint，并推荐/执行安全动作。

v3.3.1 已经能复盘 task、candidate、queue、provider usage、quality delta 和 readiness。

但当前候选评审仍有几个弱点：

- Decision Report 主要基于本地规则和候选已有 score。
- Provider 生成了候选，但没有独立的“评委视角”。
- 多个候选之间缺少结构化对比解释。
- 当前只能看到 combined/rank，很难知道为什么推荐这个候选。
- Dashboard 能统计结果，但不能解释“这个候选为什么值得 apply”。
- 用户面对多个 provider/local candidate 时，仍然需要自己通读候选差异。

v3.4.0 要补的是“评审层”。

---

## 2. 一句话目标

v3.4.0 要让系统从“生成候选并本地排序”升级为“候选可被独立评审、解释、比较”：

```text
ReviewTask candidates
  -> Local scoring
  -> Provider Judge scoring
  -> Risk / fit / novelty / musicality explanation
  -> Judge Report
  -> Decision Report uses judge summary
  -> User manually apply
```

核心边界：

- Provider Judge 只评审，不改谱。
- Provider Judge 不创建 candidate。
- Provider Judge 不 apply candidate。
- Provider Judge 不 resolve task。
- Provider Judge 不 close sprint。
- Provider Judge 输出必须可审计、可脱敏、可回放。

---

- Judge report diff。

- 不做 batch apply。

- 不做多模型投票。
- 不做 embedding similarity。
- 不做在线数据库。
- 不做付费成本策略优化器。

## 4. 核心原则

### 4.1 Judge 是评审，不是执行

Provider Judge 输出只能进入：

- judge-report.json
- decision-report.json summary
- Sprint metrics summary
- Export / Final Export summary
- WebUI 展示

不能直接调用 apply。

任何推荐候选都必须继续由用户手动点击 apply，并走现有 ReviewTask candidate apply 守卫。

### 4.2 Judge 必须可本地关闭

没有 provider key 时，系统仍可运行。

行为：

- 本地 Decision Report 继续可用。
- Judge API 返回 provider not configured 的明确错误。
- Dashboard 显示 judge unavailable。
- release-check 使用 mock provider。

### 4.3 Judge 输出必须结构化

不要让 provider 只返回一段自然语言。

必须要求 JSON：

```json
{
  "recommended_candidate_id": "revcand-002",
  "candidate_scores": [],
  "comparison_summary": {},
  "risk_flags": [],
  "manual_review_required": true
}
```

解析失败必须失败，不要猜。

### 4.4 Judge 必须绑定输入 hash

Judge Report 必须绑定：

- task source hash
- parent song plan hash
- candidate ids/hash
- prompt template id/version

任何输入变化后，旧 judge report 应标记 stale。

### 4.5 Judge 不应泄露上下文

Provider prompt 可包含候选摘要、task 摘要、target、scores、validator warnings、quality summary。

不要发送：

- 本机路径。
- provider key。
- raw full project export。
- 过大的 MIDI binary。
- 完整 private references 原文。

## 6. Provider Prompt Template

### 6.1 新增模板 id

```text
provider-review-judge
```

### 6.2 Prompt 输入

建议传入：

```json
{
  "task": {
    "task_id": "review-task-001",
    "notes": "...",
    "target": {},
    "markers": [],
    "priority": 80
  },
  "parent_song": {
    "title": "...",
    "style": "...",
    "quality": {},
    "sections": []
  },
  "candidates": [
    {
      "candidate_id": "revcand-001",
      "source": "local",
      "scores": {},
      "summary": {},
      "validator": {},
      "changed_sections": [],
      "changed_tracks": []
    }
  ],
  "instruction": {
    "judge_dimensions": [
      "review_fit",
      "target_precision",
      "musicality",
      "novelty",
      "risk"
    ],
    "output_json_only": true
  }
}
```

不要发送完整 MIDI 或 WAV。

### 6.3 Prompt 输出 schema

要求 provider 输出：

```json
{
  "recommended_candidate_id": "revcand-002",
  "candidate_scores": [
    {
      "candidate_id": "revcand-002",
      "overall": 88,
      "review_fit": 90,
      "target_precision": 86,
      "musicality": 88,
      "novelty": 76,
      "risk": 12,
      "confidence": 0.84,
      "reason": "...",
      "risks": []
    }
  ],
  "comparison_summary": {
    "best_candidate_id": "revcand-002",
    "reason": "...",
    "tradeoffs": []
  },
  "manual_review_required": true,
  "warnings": []
}
```

校验规则：

- `recommended_candidate_id` 必须在 ready candidate ids 内。
- `candidate_scores[].candidate_id` 必须存在。
- 每个 ready candidate 最好都有 score；缺失 candidate 要补 warning。
- 分数超范围要 clamp 或 reject。建议 v3.4.0 选择 reject，避免 provider 输出不可信。
- reason 截断到 1000 字符。
- warnings 截断数量和长度。

## 8. API 设计

### 8.1 Task Judge GET

```text
GET /api/projects/<project-id>/review-tasks/<task-id>/judge-report
```

行为：

- 如果 report 存在，返回。
- 如果 stale，返回 `stale: true`，但不自动刷新。
- 不调用 provider。

返回：

```json
{
  "ok": true,
  "task": {},
  "judge_report": {},
  "summary": {}
}
```

### 8.2 Task Judge Refresh

```text
POST /api/projects/<project-id>/review-tasks/<task-id>/judge-report/refresh
```

payload：

```json
{
  "template_id": "provider-review-judge",
  "candidate_ids": ["revcand-001", "revcand-002"],
  "include_failed": false,
  "note": "Focus on chorus bass risk."
}
```

行为：

- 校验 provider config。
- 校验 template enabled。
- 读取 parent SongPlan。
- 读取 ready candidates。
- 调 provider。
- 写 judge-report.json。
- 写 judge-provider-usage.json。
- append task/project event。
- 不 apply。

### 8.3 Sprint Judge Summary GET

```text
GET /api/projects/<project-id>/review-sprints/<sprint-id>/judge-summary
```

行为：

- 读取 Sprint 内 task judge reports。
- 返回汇总。
- 不调用 provider。

### 8.4 Sprint Batch Judge Refresh

```text
POST /api/projects/<project-id>/review-sprints/<sprint-id>/judge-summary/refresh
```

payload：

```json
{
  "template_id": "provider-review-judge",
  "task_ids": ["review-task-001"],
  "skip_existing_current": true,
  "max_tasks": 5
}
```

行为：

- 对每个 task 执行 provider judge refresh。
- 默认只处理有 ready candidates 的 task。
- task 无 ready candidates -> skipped。
- provider 不可用 -> failed。
- 写 sprint judge-summary.json。
- 不 apply。

这是 provider-safe 动作，WebUI 必须明确让用户点击。

### 8.5 Action Queue 接入

新增 action：

```text
refresh_judge_report
```

safety：

```text
provider_safe
```

来源：

- Recommendation action 为 `apply_ready_candidate` 时，可以附加 `refresh_judge_report`。
- Decision report 缺 judge summary 时，也可附加。

run 行为：

- 默认不执行。
- 必须 include_provider=true。
- 执行 task judge refresh。

## 9. Decision Report 接入

### 9.1 Decision Report 增加字段

```json
{
  "judge_summary": {
    "status": "completed",
    "recommended_candidate_id": "revcand-002",
    "top_overall": 88,
    "top_confidence": 0.84,
    "manual_review_required": true,
    "risk_flags": []
  }
}
```

### 9.2 排序策略

v3.4.0 不建议让 provider judge 完全覆盖本地 rank。

建议 Decision Report 里同时展示：

```json
{
  "recommended_candidate_id": "revcand-002",
  "local_recommended_candidate_id": "revcand-001",
  "judge_recommended_candidate_id": "revcand-002",
  "recommendation_reason": "Provider judge prefers revcand-002 because..."
}
```

如果 judge 和 local 不一致：

```json
{
  "warnings": [
    "Provider judge recommendation differs from local ranking."
  ],
  "manual_review_required": true
}
```

不要悄悄覆盖。

### 9.3 Apply metadata

手动 apply 后，edit metadata 增加：

```json
{
  "review_judge": {
    "task_id": "review-task-001",
    "judge_report_created_at": "...",
    "judge_recommended_candidate_id": "revcand-002",
    "applied_matches_judge": true,
    "top_overall": 88,
    "confidence": 0.84
  }
}
```

如果 apply 时 judge report stale：

- metadata 记录 `judge_stale_at_apply: true`
- 不阻止 apply，除非后续版本明确做 gate。

## 13. 安全与脱敏

### 13.1 不允许泄露

Judge report / API / export / events 中不能出现：

- provider api key
- `sk-...`
- GitHub token
- Bearer token
- `api_key`
- raw provider response
- 本机路径
- SoundFont path
- `.musicforge/provider.json`
- 完整 reference 原文

### 13.2 Provider 输出清洗

Provider 返回的所有文本字段：

- sanitize sensitive values。
- 截断长度。
- 限制数组长度。
- 拒绝控制字符。

### 13.3 Candidate id 校验

Provider 返回的 candidate id 必须属于当前 task candidates。

不能让 provider 注入：

```text
../../provider.json
```

或不存在 id。

### 13.4 Stale guard

Judge report stale 条件：

- parent SongPlan hash 变化。
- task status/source hash 变化。
- candidate list 变化。
- candidate score/summary/intents 变化。
- prompt template id/version 变化。

Stale report：

- GET 可以返回，但标记 stale。
- Decision Report 可以显示 stale warning。
- Apply 不阻止，但 metadata 记录 stale。

    - `C:\Users`
    - tmp path

## 18. 风险清单

### 风险 1：Provider Judge 被误当成最终决定

应对：

- UI 写 advisory。
- manual apply 仍独立。
- Decision Report 同时展示 local/judge。
- release-check 验证不自动 apply。

### 风险 2：Provider 输出不稳定

应对：

- JSON schema 严格校验。
- mock provider 覆盖测试。
- stale/source hash 绑定输入。
- 不把 judge 分数作为唯一排序来源。

### 风险 3：成本不可控

应对：

- provider-safe 默认不执行。
- Sprint batch judge 支持 max_tasks。
- provider usage 单独记录。
- Dashboard 显示 judge tokens。

### 风险 4：泄露敏感信息

应对：

- prompt payload 只用 summary。
- output sanitize。
- export 只放 summary。
- release-check secret/path scan。

### 风险 5：Decision Report 口径混乱

应对：

- 明确 local vs judge。
- mismatch 只 warning，不自动覆盖。
- README 写清楚 judge 是 advisory。

## 19. v3.4.0 完成定义

v3.4.0 完成后，用户应该能做到：

```text
生成多个 Review Candidates
  -> 请求 Provider Judge 评审
  -> 查看每个候选的 fit / precision / musicality / novelty / risk
  -> 看到 local ranking 和 judge recommendation 是否一致
  -> 手动选择是否 apply
  -> Export / Final Export 保留 judge summary
  -> Metrics Dashboard 统计 judge 使用和采纳情况
```

并且系统满足：

- 不自动 apply。
- 不自动 resolve。
- 不自动 close sprint。
- provider 默认不调用。
- provider 输出严格校验。
- judge report 可判断 stale。
- secret/path 不泄露。
- release-check 全绿。

做到这里，MusicForge 的反馈闭环会从“能生成和执行安全动作”进一步变成“能解释候选质量和决策依据”。这为后续 v3.5 的作品交付流水线或 v3.5 的质量门禁增强提供更坚实的决策层。

# MusicForge v0.3.0 施工图：多 Agent 音乐生成后端

日期：2026-05-05

## 0. 当前状态

截至 v0.2.1，MusicForge 已经具备：

- 本地 Studio 面板。
- local / provider 两种生成模式。
- ProviderConfig、本地 `.musicforge/provider.json`、mock provider、OpenAI-compatible client。
- provider-backed `SongPlan` pipeline。
- masked provider snapshot。
- job hide/unhide/cancel/delete/retry。
- heartbeat、watchdog、stalled 状态。
- Timeline / Tracks / Validator / SongPlan JSON / Logs / Artifacts tabs。
- 测试基线：`106 passed`。

当前还不是“音乐生产系统”。它仍然是：

```text
SongRequest -> 单个 composer -> SongPlan -> MIDI
```

v0.3.0 要把它升级为：

```text
SongRequest
  -> Brief Planner
  -> Style / Sonic Palette
  -> Structure Planner
  -> Lyrics Planner
  -> Harmony Planner
  -> Melody Planner
  -> Arrangement Planner
  -> Critic
  -> Repair
  -> SongPlan
  -> MIDI
```

但不要一口吃成复杂多 agent。v0.3.0 应该先做“节点化、可落盘、可预览、可重试”的音乐生成后端，再逐步接 provider。

## 1. v0.3.0 目标

v0.3.0 的目标是从“单 pipeline”升级为“多节点音乐生成 pipeline”。

完成后必须具备：

- 每个音乐 agent 节点有明确 schema。
- 每个节点输出落盘到 `runs/<job-id>/data/nodes/<node>.json`。
- job detail API 能列出所有节点。
- 面板能查看每个节点的输入摘要、输出摘要、状态、错误和 JSON。
- local deterministic mode 能跑完整多节点 pipeline。
- provider mode 能至少跑一部分 provider-backed 节点。
- 最终仍然输出兼容当前 `SongPlan` 的 `song-plan.json`。
- 当前 MIDI render、runtime views、retry、watchdog 继续可用。
- critic 能生成结构化 review。
- repair 能基于 critic report 做一次修复或明确跳过。
- 所有测试不依赖真实网络。

## 2. v0.3.0 不做什么

明确不做：

- 不做 batch。
- 不做多首歌队列。
- 不做音频 WAV/MP3。
- 不做浏览器真实 MIDI/audio 播放器。
- 不做复杂权限/远程鉴权。
- 不引入数据库。
- 不引入 Redis/Celery。
- 不要求真实 provider 自动测试。
- 不做无限 critic/repair 循环。
- 不做复杂 DAW 编曲导出。

如果开发发现必须扩大范围，应先汇报。

## 4. 核心概念

### 4.1 Node

一个 node 是一个可落盘、可检查、可失败、可重试的音乐生成步骤。

节点必须记录：

- node name
- status
- started_at
- finished_at
- input summary
- output summary
- output object
- error
- provider snapshot
- attempt count

### 4.2 Node artifact

文件路径：

```text
runs/<job-id>/data/nodes/<node-name>.json
```

示例：

```json
{
  "node": "harmony_planner",
  "status": "completed",
  "started_at": "2026-05-05T00:00:00+00:00",
  "finished_at": "2026-05-05T00:00:01+00:00",
  "attempt_count": 1,
  "provider_snapshot": {
    "mode": "local"
  },
  "input_summary": {
    "title": "Rainy Convenience Store",
    "style_tags": ["city pop", "soft rock"],
    "sections": 5
  },
  "output_summary": {
    "progression_count": 5,
    "primary_key": "C major"
  },
  "output": {
    "key": "C major",
    "progressions": []
  },
  "error": null
}
```

### 4.3 Node status

允许值：

```text
pending
running
completed
failed
skipped
repaired
```

注意：

- job status 和 node status 分开。
- node failed 可以让 job failed。
- repair node 成功后，critic 节点仍保留原始报告。

## 5. Schema 设计

新增：

```text
song_agent/schemas/agent_nodes.py
```

### 5.1 SongBrief

用途：把用户原始请求规整成生产 brief。

字段建议：

```python
@dataclass(frozen=True)
class SongBrief:
    title: str
    language: str
    style: str
    theme: str
    duration_seconds: int
    vocal_mode: str
    tempo_bpm: int | None
    key: str | None
    target_listener: str | None = None
    use_case: str | None = None
    mood_tags: list[str] = field(default_factory=list)
    must_include: list[str] = field(default_factory=list)
    avoid: list[str] = field(default_factory=list)
```

输出示例：

```json
{
  "title": "Rainy Convenience Store",
  "language": "zh",
  "style": "city pop, soft rock",
  "theme": "rainy city memory",
  "duration_seconds": 120,
  "vocal_mode": "guide_melody",
  "tempo_bpm": 92,
  "key": "C major",
  "mood_tags": ["nostalgic", "warm", "urban"]
}
```

### 5.2 SonicPalette

用途：定义音色、配器、节奏质感。

字段：

```python
@dataclass(frozen=True)
class SonicPalette:
    genre_tags: list[str]
    instrumentation: list[str]
    lead_instrument: str
    bass_style: str
    drum_style: str
    texture_notes: list[str]
    mix_notes: list[str]
```

示例：

```json
{
  "genre_tags": ["city pop", "soft rock"],
  "instrumentation": ["electric piano", "clean guitar", "synth bass", "drums"],
  "lead_instrument": "lead synth",
  "bass_style": "syncopated warm synth bass",
  "drum_style": "tight 80s pop groove",
  "texture_notes": ["warm pads", "short guitar fills"],
  "mix_notes": ["clean midrange", "soft high end"]
}
```

### 5.3 StructurePlan

用途：定义歌曲段落。

字段：

```python
@dataclass(frozen=True)
class StructureSectionPlan:
    name: str
    start_bar: int
    bars: int
    energy: str
    purpose: str

@dataclass(frozen=True)
class StructurePlan:
    meter: str
    sections: list[StructureSectionPlan]
```

示例：

```json
{
  "meter": "4/4",
  "sections": [
    {"name": "intro", "start_bar": 1, "bars": 4, "energy": "low", "purpose": "set mood"},
    {"name": "verse", "start_bar": 5, "bars": 8, "energy": "medium", "purpose": "tell story"},
    {"name": "chorus", "start_bar": 13, "bars": 8, "energy": "high", "purpose": "main hook"}
  ]
}
```

### 5.4 LyricPlan

用途：规划歌词或 guide lyric。

字段：

```python
@dataclass(frozen=True)
class LyricSection:
    section_name: str
    lyrics: str | None
    syllable_notes: str | None = None

@dataclass(frozen=True)
class LyricPlan:
    language: str
    rhyme_style: str
    sections: list[LyricSection]
```

instrumental 时：

```json
{
  "language": "instrumental",
  "rhyme_style": "none",
  "sections": []
}
```

### 5.5 HarmonyPlan

用途：为每个 section 生成和弦。

字段：

```python
@dataclass(frozen=True)
class SectionHarmony:
    section_name: str
    chords: list[str]

@dataclass(frozen=True)
class HarmonyPlan:
    key: str
    progressions: list[SectionHarmony]
```

### 5.6 MelodyPlan

用途：生成主旋律草稿。

字段：

```python
@dataclass(frozen=True)
class MelodyPhrase:
    section_name: str
    notes: list[NoteEvent]

@dataclass(frozen=True)
class MelodyPlan:
    lead_instrument: str
    phrases: list[MelodyPhrase]
```

`NoteEvent` 可复用现有 `song_agent.schemas.song.NoteEvent`。

### 5.7 ArrangementPlan

用途：把 melody/harmony/palette 变成多 track 草稿。

字段：

```python
@dataclass(frozen=True)
class ArrangementTrack:
    name: str
    instrument: str
    role: str
    notes: list[NoteEvent]

@dataclass(frozen=True)
class ArrangementPlan:
    tracks: list[ArrangementTrack]
```

### 5.8 CriticReport

用途：检查当前生成结果是否符合基础音乐规则。

字段：

```python
@dataclass(frozen=True)
class CriticIssue:
    severity: str
    code: str
    message: str
    target: str | None = None

@dataclass(frozen=True)
class CriticReport:
    passed: bool
    score: int
    issues: list[CriticIssue]
```

severity：

```text
info
warning
error
```

### 5.9 RepairPlan

用途：记录修复动作。

字段：

```python
@dataclass(frozen=True)
class RepairAction:
    target: str
    action: str
    reason: str

@dataclass(frozen=True)
class RepairPlan:
    applied: bool
    actions: list[RepairAction]
```

## 6. NodeStore 设计

新增：

```text
song_agent/node_store.py
```

建议 API：

```python
class NodeStore:
    def __init__(self, run_dir: Path) -> None: ...
    def node_path(self, node_name: str) -> Path: ...
    def write_node(self, record: NodeRecord) -> Path: ...
    def read_node(self, node_name: str) -> NodeRecord: ...
    def list_nodes(self) -> list[NodeRecord]: ...
```

`NodeRecord`：

```python
@dataclass
class NodeRecord:
    node: str
    status: str
    started_at: str | None = None
    finished_at: str | None = None
    attempt_count: int = 0
    provider_snapshot: dict[str, Any] = field(default_factory=dict)
    input_summary: dict[str, Any] = field(default_factory=dict)
    output_summary: dict[str, Any] = field(default_factory=dict)
    output: dict[str, Any] = field(default_factory=dict)
    error: str | None = None
```

路径安全：

- node name 只允许 `[a-z0-9_-]`。
- 不允许 `..`。
- 不允许路径分隔符。
- 所有 node 文件都必须在 `data/nodes/` 下。

## 7. Multi-node pipeline 设计

新增：

```text
song_agent/agent/multinode_pipeline.py
```

核心函数：

```python
def generate_multinode_song_plan(
    request: SongRequest,
    *,
    provider_config: ProviderConfig | None = None,
    provider_snapshot: dict[str, Any] | None = None,
    node_store: NodeStore,
    control: Callable[[str, str], None] | None = None,
) -> SongPlan:
    ...
```

第一版节点顺序：

```text
brief_planner
style_planner
structure_planner
lyric_planner
harmony_planner
melody_planner
arrangement_planner
critic
repair
song_plan_builder
```

### 7.1 Deterministic path

第一阶段必须先做 deterministic multi-node。

要求：

- 不访问网络。
- 输入同一个 request，输出稳定。
- 最终 SongPlan 和当前 deterministic composer 类似。
- 每个节点都写 node record。

这样可以先验证落盘、API、UI、retry/watchdog，不被 provider 不稳定干扰。

### 7.2 Provider path

第二阶段再接 provider。

建议先只让这些节点可 provider-backed：

- `brief_planner`
- `style_planner`
- `structure_planner`
- `lyric_planner`
- `harmony_planner`

`melody_planner`、`arrangement_planner` 第一版仍可 deterministic，避免模型直接输出过多 note event 造成不稳定。

### 7.3 Critic / repair

critic 第一版可以 deterministic：

检查：

- 是否有 sections。
- 是否有 tracks。
- 是否至少有 melody/chords/bass/drums。
- pitch 是否在 0-127。
- duration 是否大于 0。
- note 是否超出总小节太多。
- MIDI render 是否可能成功。

repair 第一版可以只修常见问题：

- 缺 drums：补 drums。
- 缺 bass：补 bass。
- velocity 超出范围：clamp 到 1-127。
- pitch 超出范围：clamp 到 0-127。
- duration <= 0：改为 1。

如果没有可修问题：

```json
{
  "applied": false,
  "actions": []
}
```

## 8. 与现有 generate_request 集成

当前 `generate_request()` 支持：

- local deterministic composer。
- provider-backed SongPlan pipeline。
- GraphRunner control callback。

v0.3.0 建议增加参数：

```python
pipeline_mode: str = "single"
```

允许值：

```text
single
multinode
```

也可以把 `generation_mode=provider` 与 `pipeline_mode=multinode` 分开：

- `generation_mode`: local/provider
- `pipeline_mode`: single/multinode

这样用户能选择：

```text
local + single
local + multinode
provider + single
provider + multinode
```

默认建议：

```text
generation_mode=local
pipeline_mode=single
```

v0.3.0 发布后，可以把面板默认改成：

```text
generation_mode=local
pipeline_mode=multinode
```

但前提是 multinode 稳定性足够。

## 9. Server API

新增：

```text
GET /api/jobs/<job-id>/nodes
GET /api/jobs/<job-id>/nodes/<node-name>
POST /api/jobs/<job-id>/nodes/<node-name>/retry
```

### 9.1 GET /api/jobs/<id>/nodes

响应：

```json
{
  "job_id": "demo",
  "nodes": [
    {
      "node": "brief_planner",
      "status": "completed",
      "started_at": "...",
      "finished_at": "...",
      "output_summary": {}
    }
  ]
}
```

列表响应不要默认返回完整 output，避免过大。

### 9.2 GET /api/jobs/<id>/nodes/<node>

响应完整 NodeRecord：

```json
{
  "job_id": "demo",
  "node": {
    "node": "brief_planner",
    "status": "completed",
    "output": {}
  }
}
```

### 9.3 POST /api/jobs/<id>/nodes/<node>/retry

v0.3.0 可以先不做真实 node-level retry，只返回 501 或 409。

建议：

- 先实现接口占位。
- 真正 node-level retry 放 v0.3.1。

原因：

- node retry 涉及下游节点失效和重新计算，范围较大。

## 11. Provider prompt 设计

如果 provider-backed nodes 需要 prompt，建议新增：

```text
song_agent/prompts/nodes/
  brief_planner.md
  style_planner.md
  structure_planner.md
  lyric_planner.md
  harmony_planner.md
```

每个 prompt 要求：

- 只输出 JSON。
- 不输出 Markdown。
- 不输出解释。
- 明确 schema。
- 明确字段约束。

不要让模型直接一次输出完整复杂 SongPlan。v0.3.0 的重点是可控节点输出。

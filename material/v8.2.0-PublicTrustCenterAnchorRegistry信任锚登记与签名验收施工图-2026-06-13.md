# v8.2.0 Public Trust Center Anchor Registry 信任锚登记与签名验收施工图

> 本文是给开发执行的 v8.2.0 施工图。当前稳定基线是 v8.1.3。
>
> v8.1.3 已经修复 Public Trust Center delivery 自证问题：当 verifier 启用显式 delivery require 时，不能只信 PTC ZIP 内部的 delivery summary / fingerprint sidecar，而必须校验同目录外部 `*.delivery-anchor.json`。旧 anchor 可以挡住“篡改 ZIP 后整体重签 report/source/data/html/manifest + delivery sidecar + fingerprint sidecar”的攻击。
>
> v8.2.0 的目标，是把这个同目录 anchor 继续升级成可登记、可发布、可轮换、可签名、可审计、可离线验证的 Public Trust Center Anchor Registry。也就是说，v8.1.3 解决“有外部 anchor 时能挡篡改”，v8.2.0 解决“外部 anchor 自己如何被管理、证明和交付”。

---

## 1. 背景

v8.0 到 v8.1 已经把 MusicForge 的公开信任中心做成了一个可导出 ZIP、可静态浏览、可离线验证的公共入口。

当前链路大致是：

1. Registry / Portal / Transparency / Acknowledgement 等 v7 公开证明包产出各自 verification report。
2. Public Trust Center 聚合这些公开证明包，形成一个 `public-trust-center.zip`。
3. v8.1 增加 Release / Distribution / Submission / Submission Evidence / Operations delivery 聚合。
4. v8.1.3 增加外部 `public-trust-center.delivery-anchor.json`，显式 delivery require 时必须用它绑定：
   - 当前 PTC ZIP sha256。
   - 当前 PTC ZIP size。
   - 当前 manifest hash。
   - 当前 source hash。
   - 当前 delivery fingerprint sidecar 指纹列表。

v8.1.3 的边界是明确的：

- 如果攻击者只篡改 ZIP，不同步替换外部 anchor，verifier 会失败。
- 如果攻击者能同时替换 ZIP 和同目录 anchor，纯本地离线校验仍然无法判断哪个 anchor 才是可信版本。

这个边界不是 bug，而是所有离线 hash anchor 都会遇到的信任根问题。v8.2.0 要做的是把 anchor 从“散落在 ZIP 旁边的 JSON 文件”升级成“可登记和可追溯的信任锚登记册”。

---

## 2. v8.2.0 定位

v8.2.0 是 Public Trust Center 的信任锚治理层。

一句话：

> 把 v8.1.3 的 delivery anchor 变成一个有历史、有当前版本、有撤销替换、有签名摘要、有离线验证包的 Anchor Registry，让外部方不只验证 ZIP 和 anchor 是否匹配，还能验证 anchor 是否来自当前登记链路。

这版不是继续扩展业务域，而是增强信任根。

---

## 3. v8.2.0 不做什么

明确不做，避免开发发散：

1. 不接入真实 CA / 证书链。
2. 不做在线服务端发布平台。
3. 不要求访问 GitHub API 才能验证。
4. 不把私钥、token、GitHub key 写进仓库。
5. 不把 `.musicforge/` 内部目录打进公开 ZIP。
6. 不改变 v8.1 Public Trust Center ZIP 的基本结构。
7. 不自动修改 Release / Distribution / Submission / Operations 底层状态。
8. 不做区块链、公证处、第三方 timestamp 服务。
9. 不做真实密码学签名的最终形态，除非能完整处理 key lifecycle；v8.2 先做 deterministic local signature envelope / key fingerprint 结构，为 v8.3+ 留口。

## 4. 核心目标

v8.2.0 必须交付 8 件事。

### 4.1 Anchor Registry Store

新增本地持久化目录：

```text
.musicforge/public-trust-center-anchor-registry/
  registry.json
  history.jsonl
  exports/
  packages/
```

或者按现有 store 风格放到 `.musicforge/public-trust-centers/<center-id>/anchor-registry/`，由开发结合现有目录结构选择，但必须满足：

- 支持多 center。
- 支持 current anchor entry。
- 支持历史 entry 保留。
- 支持 revoke / supersede。
- 支持 export / ZIP / verification report。
- 不污染 Git，仍在 `.musicforge/` 下。

### 4.2 Anchor Entry

每次 PTC ZIP build 后，如果生成了 delivery anchor，允许把 anchor 登记成 entry。

建议结构：

```json
{
  "schema_version": 1,
  "entry_id": "ptcar-entry-000001",
  "center_id": "ptc-default",
  "status": "draft|published|current|superseded|revoked",
  "created_at": "2026-06-13T...Z",
  "published_at": null,
  "superseded_at": null,
  "revoked_at": null,
  "reason": "v8.2 anchor publication",
  "anchor": {
    "package_type": "musicforge_public_trust_center_delivery_anchor",
    "center_id": "ptc-default",
    "zip_sha256": "...",
    "zip_size_bytes": 12345,
    "manifest_hash": "...",
    "source_hash": "...",
    "fingerprint_sidecars": []
  },
  "anchor_hash": "stable_hash(anchor_without_anchor_hash)",
  "zip_fingerprint": {
    "zip_sha256": "...",
    "zip_size_bytes": 12345,
    "manifest_hash": "...",
    "source_hash": "..."
  },
  "delivery_fingerprint_summary": {
    "count": 5,
    "fingerprint_sidecars_hash": "..."
  },
  "signature": {
    "mode": "local_deterministic",
    "key_id": "local-anchor-key-default",
    "key_fingerprint": "...",
    "signed_payload_hash": "...",
    "signature_hash": "..."
  },
  "integrity_hash": "..."
}
```

说明：

- `signature.mode=local_deterministic` 不是强密码学签名，不要宣传成不可抵赖签名。
- 它的作用是建立签名 envelope 和 key fingerprint 结构，为后续真实签名替换留接口。
- 真实安全仍依赖 registry ZIP / registry verification / GitHub Release asset hash / 后续 v8.3 外部发布索引。

### 4.3 Anchor Registry Report

新增 report：

```text
anchor-registry-report.json
```

报告应包含：

- current anchor hash。
- current PTC ZIP hash。
- entry count。
- published count。

```text

```

新增 ZIP：

```text

```

ZIP 规则：

- 不能包含 nested zip。
- 不能包含 `.musicforge/`。
- 不能包含反斜杠 entry。

### 4.6 Public Trust Center Verifier 支持 Anchor Registry

扩展现有 PTC verifier：

```powershell
python -m song_agent.cli verify-public-trust-center-package public-trust-center.zip \
  --require-delivery-readiness \
  --delivery-anchor public-trust-center.delivery-anchor.json \
  --anchor-registry public-trust-center-anchor-registry.zip \
  --require-anchor-registry-current \
  --json
```

新增参数建议：

- `--anchor-registry <zip>`
- `--require-anchor-registry-current`
- `--require-anchor-published`
- `--require-anchor-not-revoked`

校验逻辑：

1. 先执行现有 PTC ZIP verifier。
2. 如果启用了 delivery require，继续要求 delivery anchor。
3. 如果提供 `--anchor-registry` 或启用 `--require-anchor-registry-current`：
   - 验证 anchor registry ZIP 自身 passed。
   - 从 registry current entry 提取 anchor。
   - 检查它与 `--delivery-anchor` 内容一致。
   - 检查它与当前 PTC ZIP hash/manifest/source/fingerprint sidecar 一致。
   - 检查 current entry status 是 `current` 或 `published`。
   - revoked/superseded entry 不能用于验收。

## 6. 安全边界

### 6.1 外部 Anchor 的边界声明

v8.2 应在 README / verifier 输出里明确：

- `delivery-anchor.json` 是 PTC ZIP 的外部绑定文件。
- `anchor-registry.zip` 是 anchor 历史和当前状态的公开登记包。
- 如果攻击者能同时替换 PTC ZIP、delivery anchor、anchor registry ZIP，纯本地离线 verifier 无法判断哪个版本真实。
- 要进一步增强，需要把 registry ZIP hash 发布到 GitHub Release asset、透明度日志、人工邮件、第三方 timestamp 或真实签名系统。

这段话要写清楚，不能把 deterministic local signature 说成强签名。

### 6.2 Redaction

所有输出都要复用 `redaction.py`。

禁止泄漏：

- `C:\Users\...`
- `D:\...`
- UNC path
- `githubkey.txt`
- `sk-...`
- GitHub token
- Bearer token
- provider response raw content
- source_path/local_path/file_path

### 6.3 ZIP 安全

沿用所有现有 verifier 规则：

- raw central directory backslash 检查。
- duplicate entry 检查。
- path traversal 检查。
- absolute path 检查。
- colon drive 检查。
- nested zip 禁止。
- `.MusicForge` 大小写变体禁止。
- total uncompressed size 上限。
- entry count 上限。

## 13. 给开发的话

这版别再继续往 Public Trust Center ZIP 里塞“自证 sidecar”。v8.1.3 已经证明：只要证据和被验证对象在同一个 ZIP 里，攻击者完整重签就能绕过。v8.2.0 的重点是建立 Trust Center 外部锚的治理层。

你实现时要一直抓住这条线：

> PTC ZIP 证明内容，delivery anchor 证明 ZIP，anchor registry 证明 anchor 的当前性和历史。

每一层都要能回答：

1. 我是谁？
2. 我绑定了哪个对象？
3. 我是不是当前版本？
4. 我有没有被撤销或替换？
5. 我能不能被离线 verifier 复算出来？

做完以后，必须用测试证明以下攻击失败：

- 篡改 PTC ZIP 并重签 ZIP 内所有 JSON。
- 篡改 delivery anchor。
- 用 revoked anchor 验收。
- 用 superseded anchor 验收。
- 篡改 registry current entry。
- 篡改 chain-of-custody。

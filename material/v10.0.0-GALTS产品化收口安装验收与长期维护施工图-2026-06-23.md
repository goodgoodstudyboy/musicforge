## 1. 版本定位

v0.1 到 v9.9 已经走完了从“本地生成 MIDI”到“Trust Operations 最终准出移交”的完整长链路：

- 本地生成、Provider 生成、多节点 Agent、节点重试。
- Batch、Renderer、Audio、Stem、Project、Edit、Candidate、Reference、Asset、Library。
- Visual Editor、Clip、Template、Audition、Review、Sprint、Action Queue。
- Acceptance、Human Review、Analytics、Fix Sprint、Knowledge、Rule Governance。
- Release、Distribution、Submission、Evidence、Operations。
- Public Trust Center、Anchor、Transparency、Publication、Acceptance Board。
- Trust Operations Hub、Incident、Knowledge、Control、Continuous Assurance、Assurance Watch、Final Readiness。

v9.9.0 已经把 Trust Operations 的最终准出证书和移交包做完。  
v10.0.0 不应该再继续“新建一个更上层证明包”。这版要做产品化 GA/LTS 收口。

v10.0.0 的目标：

> 让一个新开发、业务方或接手维护者，可以从干净机器开始，按一份 Runbook 完成安装、启动、生成、试听、人工验收、Release/Distribution/Submission/Trust 验证、最终准出、GitHub 发布和长期维护。

这版要把 MusicForge 从“工程功能完整”收成“可交付、可维护、可复验”的稳定产品。

## 2. 为什么现在做 v10.0

继续推进局部证明包的边际收益已经下降。现在真正的风险变成：

- 新开发不知道从哪里开始。
- 环境依赖、renderer、provider、token、GitHub 推送方式散落在历史对话里。
- release-check 已经很大，但不同 profile 的使用边界没有形成 GA 级准则。
- README 很长，但缺一条“从 0 到最终交付”的强路径。
- Studio 功能很多，但缺少“首次运行向导”和“健康状态入口”。
- 音乐质量验收虽然已有 Acceptance / Human Review，但人工听审流程需要被产品化约束。
- v9.9 的 Final Handoff 是最终证据，但用户需要知道什么时候必须用它，什么时候不能绕过它。
- 当前 GitHub 连接经常不稳定，开发需要固定的发布 fallback 流程。

v10.0 要解决的是“项目能不能被别人稳定接手”的问题。

## 3. 本版一句话

> v10.0.0 = GA/LTS Readiness：安装向导 + 一键本地验收 + Studio 首屏健康面板 + 人工音乐验收 Runbook + 发布/回滚/维护准则 + 文档重组。

## 4. 本版不做什么

明确不做：

- 不新增音乐生成模型。
- 不新增 provider 类型。
- 不做云端托管。
- 不做第三方账号 OAuth。
- 不做真实平台自动投稿 API。
- 不做商业计费。
- 不继续新增 Trust Operations 证明包层级。
- 不把 synthetic auto-review 伪装成人工听审。
- 不删除历史功能。
- 不重构全项目目录。

v10.0 是收口，不是扩张。

## 5. 成功标准

v10.0 完成后，应满足：

1. 新开发可以按 `docs/GETTING_STARTED.md` 在本地跑起来。
2. 新开发可以按 `docs/LOCAL_ACCEPTANCE_RUNBOOK.md` 完成 12 首 Regression Songbook 验收。
3. 新开发可以按 `docs/RELEASE_RUNBOOK.md` 完成版本发布、tag、GitHub Release。
4. 新开发可以按 `docs/TROUBLESHOOTING.md` 处理常见 GitHub 443、renderer、provider、Windows 路径问题。
5. Studio 首页能清楚显示系统健康、版本、运行路径、必要配置、下一步动作。
6. CLI 提供一个 GA 级总入口：`python -m song_agent.cli ga-check`。
7. `ga-check` 能聚合 doctor、release-check profiles、renderer/profile 状态、acceptance 状态、Trust Operations final readiness 状态。
8. release-check profile 明确分层：`quick`、`latest`、`v9`、`v8`、`full`、新增 `ga`。
9. README 顶部从“功能堆叠说明”调整为“快速开始 + 常用路径 + 深入文档索引”。
10. v10.0 发布前必须有干净工作区、版本一致、tag/Release 对齐。

### 7.2 新增 docs/GETTING_STARTED.md

必须覆盖：

- Python 版本要求。
- Windows PowerShell 基础命令。
- clone 项目。
- 创建虚拟环境，或直接使用本机 Python。
- 安装测试依赖。
- 启动 Studio：

```powershell
python -m song_agent.cli serve --host 127.0.0.1 --port 8787
```

- 生成一首歌：

```powershell
python -m song_agent.cli examples\song_request.json --out runs\quickstart --force
```

- 跑 doctor：

```powershell
python -m song_agent.cli doctor
```

- 跑 quick release-check：

```powershell
python -m song_agent.cli release-check --profile quick --skip-tests --json
```

- 常见输出怎么判断。

### 7.3 新增 docs/MUSIC_REVIEW_GUIDE.md

这是给“开发自己确认生成音乐没问题”的手册。

必须明确：

- synthetic auto-review 只代表自动体检，不代表人工听过。
- release_candidate / audio_required 必须人工听审。
- 人工听审至少检查：
  - 是否能正常播放。
  - 是否不是空音频。
  - 是否没有明显爆音、削波、长静音。
  - 主旋律是否可感知。
  - 鼓、贝斯、和声是否没有明显错位。
  - section 结构是否能听出 intro/verse/chorus/outro 等变化。
  - 同一批 12 首 Regression Songbook 是否没有全部听起来一样。
- 如何在 Studio 里记录 manual accepted / needs_fix / rejected。
- 如何从 marker 生成 ReviewTask / Mix Patch / Audio Revision。

### 7.4 新增 docs/LOCAL_ACCEPTANCE_RUNBOOK.md

必须覆盖完整本地验收：

```powershell
python -m song_agent.cli acceptance-check --profile midi_smoke --auto-review --render-audio never --report-out runs\acceptance-midi-smoke.json
python -m song_agent.cli acceptance-check --profile developer_manual --render-audio auto --report-out runs\acceptance-developer-manual.json
python -m song_agent.cli acceptance-check --profile release_candidate --render-audio auto
```

要求说明：

- `midi_smoke` 可以 synthetic。
- `developer_manual` 需要开发人工听至少代表性曲目。
- `release_candidate` 必须覆盖 12 首内置 Regression Songbook。
- `release_candidate` 不能用重复 song_id 冒充覆盖。
- 如果 renderer 不可用，不能宣称 audio release-ready。
- 如果没有真实 WAV，Release/Distribution 的 audio gate 不得通过。

## 8. Phase B：GA Readiness 模块

### 8.1 新增 song_agent/ga_readiness.py

职责：

- 聚合当前项目 GA 状态。
- 不生成新业务产物。
- 不自动签核。
- 不自动 reset。
- 不调用 provider。
- 不联网。

数据结构：

```json
{
  "schema_version": 1,
  "package_type": "musicforge_ga_readiness_report",
  "generated_at": "...",
  "app_version": "10.0.0",
  "status": "ready|blocked|warning",
  "summary": {
    "doctor_status": "passed|failed|unknown",
    "release_check_latest_status": "passed|failed|unknown",
    "release_check_ga_status": "passed|failed|unknown",
    "acceptance_status": "passed|failed|missing|synthetic_only",
    "renderer_status": "configured|missing|failed|unknown",
    "provider_status": "configured|mock|missing|unknown",
    "trust_final_readiness_status": "passed|failed|missing|unknown",
    "git_status": "clean|dirty|ahead|behind|unknown"
  },
  "checks": [
    {
      "check_id": "ga.version_consistency",
      "status": "passed|failed|warning",
      "severity": "blocking|warning|info",
      "message": "..."
    }
  ],
  "next_actions": [],
  "source": {},
  "integrity_hash": "..."
}
```

### 8.2 GA checks

至少包含：

- `ga.version_consistency`
  - `song_agent.__version__` 与 `pyproject.toml` 一致。
- `ga.git_clean`
  - 默认要求工作区干净。
  - `--allow-dirty` 才允许 warning。
- `ga.doctor`
  - 调用 doctor 内部逻辑或轻量复用。
- `ga.release_check_latest`
  - 可读取外部 report，也可由 CLI 触发。
- `ga.release_check_ga`
  - 新 profile。
- `ga.acceptance_manual`
  - 如果是 release-ready，要找 manual acceptance evidence。
- `ga.renderer_audio`
  - 如果要求 audio，则 renderer/profile/WAV gate 必须 ready。
- `ga.trust_final_readiness`
  - 如果传入 Final Handoff verification report，必须 status passed。
- `ga.docs_present`
  - docs 下关键 Runbook 存在。
- `ga.secret_scan`
  - 复用 release-check secret scan。

### 8.3 输出路径

默认写：

```text
runs/ga-readiness/ga-readiness-report.json
```

支持：

```powershell
python -m song_agent.cli ga-check --json
python -m song_agent.cli ga-check --report-out runs\ga-readiness.json
python -m song_agent.cli ga-check --strict
python -m song_agent.cli ga-check --require-manual-acceptance
python -m song_agent.cli ga-check --require-audio
python -m song_agent.cli ga-check --final-handoff-verification-report path\to\final-handoff-verification-report.json
```

## 12. Phase F：人工音乐验收产品化

### 12.1 Acceptance 面板强化

Acceptance 工作台需要让开发能完成：

- 选择 profile：midi_smoke / developer_manual / release_candidate / audio_required。
- 生成 Regression Songbook。
- 对每首歌播放 MIDI/WAV。
- 填写 manual review：
  - accepted
  - needs_fix
  - rejected
  - rating
  - notes
  - markers
- 导出 Human Review Pack。
- 导入 review response。
- 生成 Fix Sprint。
- recheck。

### 12.2 强制文案

界面和文档必须明确：

- `auto-review` 是 synthetic。
- release_candidate 不接受 synthetic-only。
- audio_required 需要真实 WAV。
- 没有 renderer 时可以做 MIDI smoke，但不能做 audio release-ready。

### 12.3 GA Check 与 Acceptance 关系

`ga-check --require-manual-acceptance` 必须识别：

- suite 是否 signed。
- profile 是否 release_candidate 或 audio_required。
- 12 首 Regression Songbook 是否完整覆盖。
- 每首是否 manual accepted。
- 是否存在 stale health/report。

如果只能找到 synthetic suite，应 failed。

## 13. Phase G：长期维护策略

### 13.1 新增 docs/MAINTENANCE_POLICY.md

内容：

- v10.0 后进入 LTS 维护。
- patch 版本只修：
  - 安全 verifier 绕过。
  - 数据污染。
  - 签核不可变绕过。
  - release-check 错误。
  - 安装/运行阻断。
- minor 版本才新增能力。
- 不再随意新增顶层证明包。
- 每次 patch 必须有：
  - 复现描述。
  - 回归测试。
  - release-check smoke。
  - CHANGELOG。

### 13.2 Hotfix 模板

文档中给出：

```text
问题：
影响：
复现：
修复：
回归：
验证：
发布：
```

### 13.3 Reviewer 准则

Reviewer 后续重点看：

- 是否有包内自证。
- 是否缺外部 current evidence。
- 是否签核后仍可静默重建。
- 是否 reset 绕过 Change Request。
- 是否 source_path/local_path/file_path 泄漏。
- 是否 synthetic 被当成人工验收。
- 是否 release-check 空集合假绿。

## 16. 风险清单

### P1 风险

- GA Check 只读本地状态，结果被误当成签核证据。
  - 处理：GA Check 是 readiness，不是 signoff。Release/Trust signoff 仍走原 gate。
- synthetic auto-review 被当成人工听审。
  - 处理：manual gate 必须识别 review_mode。
- Studio 显示本机绝对路径或 token 文件路径。
  - 处理：统一 masked path / basename。
- release-check `ga` profile 空集合假绿。
  - 处理：沿用 v7.5.1 空集合失败规则。
- v10.0 文档写入用户本机 token path。
  - 处理：只写通用描述，不写本机 token 文件绝对路径。

### P2 风险

- README 继续变长导致新开发看不懂。
  - 处理：README 顶部短路径，详细内容转 docs。
- ga-check 运行太慢。
  - 处理：默认轻量；长跑必须显式参数。
- full pytest 太慢影响发布。
  - 处理：可选长跑，不再作为每次 hotfix 必选。

### P3 风险

- Studio 文档链接在不同 cwd 下失效。
  - 处理：API 返回 repo-relative docs 路径。
- Windows 换行提示被误判失败。
  - 处理：Troubleshooting 说明。

## 18. 给开发的执行说明

开发不要再发散做新的证明链路。v10.0 的重点是让项目能被人顺利接手、能在本地稳定跑、能完成真实人工音乐验收、能按 Runbook 发布。

优先顺序：

1. 先补 docs，把新开发从 0 到运行写清楚。
2. 再做 `ga-check`，把当前健康状态聚合出来。
3. 再接 Studio 首页健康面板。
4. 再加 `release-check --profile ga`。
5. 最后 bump 版本、跑验收、发布 v10.0.0。

遇到任何“想新增一个更上层 verifier / package / proof”的冲动，先停下来。除非 reviewer 明确要求，否则 v10.0 不新增证明包层级。

## 19. Reviewer 验收口径

Reviewer 通过标准：

- 文档能让新人独立启动项目。
- `ga-check` 能给出可信的 readiness 状态。
- synthetic 与 manual review 区分清楚。
- Studio 有清晰系统健康入口。
- `release-check --profile ga` 不为空且能失败。
- v10.0 发布状态 clean：HEAD、origin/master、v10.0.0 tag、GitHub Release 对齐。

Reviewer 不接受：

- “full pytest 超时”写成通过。
- synthetic acceptance 写成人工听审。
- 文档出现本机 token 路径。
- remote URL 写 token。
- `.musicforge/provider.json` 或 `.musicforge/renderer.json` 被提交。
- GA Check 靠伪造 report 自证。

# v2.8.0 评审候选工作台与多轮反馈闭环施工图

日期：2026-05-12

当前稳定基线：v2.7.1

目标版本：v2.8.0

定位：在 v2.5.0 到 v2.7.1 已经完成“编辑试听、试听评审、评审驱动单次编辑”的基础上，把 MusicForge 的反馈链路升级为“评审任务 -> 多候选修正 -> A/B 试听 -> 选择应用 -> 标记解决 -> 沉淀复用”的完整工作台。v2.8.0 的核心不是增加更多零散按钮，而是让用户围绕一条具体评审反馈进行可追踪、多候选、多轮打磨。

关键收紧：v2.8.0 的“多轮”不要做成一个 ReviewTask 里反复 apply。一个 ReviewTask 只允许 apply 一个 candidate；如果用户标记 `needs_more_work`，系统创建一个 linked follow-up ReviewTask，新的 task 以已应用版本作为 parent，继续下一轮候选生成。这样 hash/stale 判断、target section/track 坐标和版本 provenance 都更清楚。

---

## 1. 背景

到 v2.7.1，MusicForge 已经具备一条很完整但仍偏“单次动作”的创作链：

- v2.5.0 引入 Editor Preview / Parent / Audition 的试听能力。
- v2.5.1 修复 Preview WAV 可信链路，Preview WAV 重新从父版本 SongPlan + patch 计算，不信任缓存。
- v2.6.0 引入 Audition Review Board，支持 rating、status、favorite、notes、tags、markers 和 audition asset 沉淀。
- v2.7.0 引入 Review Edit，把 audition review 转成安全的本地 `EditIntent`，并可创建 child Project Version。
- v2.7.0 还引入 provider review edit preview 和 review-to-context-pack。
- v2.7.1 修复 `custom` 和 `changed_sections` audition marker 的 beat 坐标映射问题，marker 本地 beat 会先加上 `range.start_beat`，再映射父版本 section。
- release-check 已覆盖 v2.7 review edit smoke。

这说明 MusicForge 已经能完成：

```text
编辑 -> 试听 -> 评审 -> 根据评审创建一个新版本
```

但现在的链路还没有达到“创作工作台”的程度：

- 一条 review 只能比较直接地生成一个 local edit 结果。
- provider review edit 当前偏 preview，不形成候选池。
- 用户听完修正结果后，没有明确的“这条反馈是否解决”的状态。
- 多次 review edit 会分散成版本和 preview，不容易从 review 视角追踪。
- candidate group 已经存在于 provider edit 工作流，但 review 场景还没有复用候选思想。
- 评分、marker、notes 已经结构化，但没有变成一个长期可追踪的 task。
- 用户无法对同一条反馈生成 conservative / balanced / bold 等不同修正策略。
- 用户无法把“这条 feedback 的最佳修正候选”沉淀成稳定 provenance。

v2.8.0 要补齐这一层。

---

## 2. 一句话目标

v2.8.0 要把 MusicForge 从“评审驱动一次编辑”推进到“评审驱动多候选打磨工作台”：

- 从 audition review 创建持久化 `ReviewTask`。
- 围绕一个 `ReviewTask` 生成多个本地 deterministic review candidates。
- 支持 provider review candidates 作为可选增强，但 local candidates 必须独立可用。
- 每个 candidate 有 SongPlan、validator、summary、score、MIDI、可选 WAV。
- Studio 增加 Review Workbench，用户可以听、看 diff、比较 ranking、应用最佳候选。
- 应用候选后创建正式 child Project Version。
- ReviewTask 不自动 resolved，必须用户明确标记 resolved / needs_more_work / archived。
- 如果需要继续打磨，needs_more_work 创建 linked follow-up ReviewTask，不在旧 task 内二次 apply。
- Project Compare、Project Export、Final Export、release-check 记录 review task 和 selected candidate provenance。

最终工作流：

```text
Audition Review
  -> Create Review Task
  -> Generate Local Candidates
  -> Listen / Compare / Inspect
  -> Apply Candidate
  -> Resolve or Needs More Work
  -> Save useful material as Asset / Context Pack
```

## 3. 版本边界

### 3.1 v2.8.0 必须做

- `ReviewTask` 数据模型和持久化。
- `ReviewCandidate` 数据模型和持久化。
- 从 audition review 创建 review task。
- 从 review task 生成 2 到 4 个 local review candidates。
- 每个 candidate 使用现有安全 edit engine 生成 candidate SongPlan。
- 每个 candidate 进行 SongPlan validate 和 quality attach。
- 每个 candidate 计算 review-fit ranking。
- candidate MIDI 渲染和下载。
- candidate WAV 渲染和下载，继续依赖本地 renderer 配置。
- 从 candidate apply 成正式 Project Version。
- ReviewTask 状态机：open、candidate_ready、applied、resolved、needs_more_work、archived、stale。
- Studio Review Workbench。
- release-check 增加 v2.8 review task smoke。
- README、CHANGELOG、测试补齐。

### 3.2 v2.8.0 可以做，但可拆到 v2.8.1

- Provider review candidates。
- ReviewTask 批量生成。
- ReviewTask filtering 高级筛选。
- ReviewTask 与 Context Pack 的自动推荐。
- Candidate crossfade 或试听播放队列。

如果开发过程中发现 v2.8.0 范围过大，优先保 local candidate 闭环，把 provider review candidates 放 v2.8.1。

### 3.3 v2.8.0 不做

- 不做自动无限迭代。
- 不做 AI 自己选择最终版本并自动发布。
- 不做自动 resolved 判断。
- 不做实时浏览器混音器。
- 不做 waveform 编辑。
- 不做音频转 MIDI。
- 不做 BPM/key 自动检测。
- 不做 MP3/FLAC 导入。
- 不做云同步。
- 不做多人协作评论。
- 不把 audition WAV 或 candidate WAV 默认复制进正式版本。
- 不把 provider 输出当作可信执行逻辑。
- 不把 review notes 原文大段放进 Final Export。
- 不做大规模 candidate group 抽象重构。
- 不做“一个 ReviewTask 多次 apply”的内嵌 round 模型；多轮通过 linked task chain 表达。

## 4. 核心判断

v2.8.0 不应该继续在 Review Board 上堆孤立按钮。

正确方向是增加一个新的工作流层：

```text
Review Board 负责收集反馈
Review Workbench 负责解决反馈
Project Version 负责保存正式结果
Assets / Context Packs 负责沉淀复用
```

原因：

- Review Board 是列表，不适合承载多轮候选对比。
- Candidate Group 是 provider edit 场景的候选容器，不应该直接硬塞 review 语义。
- Review Edit 是单次 edit intent，不应该承担 task 状态机。
- Project Version 是结果，不应该记录未解决 feedback 的全过程。

所以 v2.8.0 需要新增 `ReviewTask` 作为中间层。

## 5. 用户价值

### 5.1 典型工作流 A：修复一个有问题的 bass

1. 用户在 Project Editor 中创建 Preview。
2. 用户创建 `changed_sections` audition，只听改动 section。
3. 用户听到 verse 的 bass 太满。
4. 用户给 audition 写 review：
   - rating = 3
   - status = needs_fix
   - notes = `verse bass 太满，鼓和低频挤在一起`
   - marker = `fix @ beat 1`
5. 用户点击 `Create Review Task`。
6. 系统创建 `review-task-001`，记录 marker 本地 beat 和全局 beat。
7. 用户点击 `Generate Local Candidates`。
8. 系统生成：
   - `revcand-001` conservative：bass density 降低 10 到 15%
   - `revcand-002` balanced：bass density 降低 25 到 30%
   - `revcand-003` bold：bass density 降低并提升 section energy
9. 用户依次试听 MIDI/WAV。
10. 用户选择 `revcand-002`。
11. 系统 apply 成 `v002`。
12. 用户听完后点击 `Resolve Task`。
13. Project Export 记录：`v002` 解决了 `review-task-001`，来源 audition 是 `audition-001`。

### 5.2 典型工作流 B：保留 hook，但加强 chorus

1. 用户在 chorus audition 上打 marker：
   - `keep @ beat 2` label=`这个 hook 保留`
   - `fix @ beat 8` label=`第二遍需要更炸`
2. 系统创建 ReviewTask。
3. candidate inference 必须识别：
   - keep marker 是 preserve signal，不是 edit target。
   - fix marker 才是 edit target。
4. conservative candidate 只提升 section energy。
5. balanced candidate 加 melody variation，但避开 keep hook。
6. bold candidate 加 arrangement variation。
7. ranking 会惩罚破坏 keep marker 的 candidate。

### 5.3 典型工作流 C：provider 增强候选

1. 用户创建 ReviewTask。
2. local candidates 先生成成功。
3. 用户配置 provider 后点击 `Generate Provider Candidates`。
4. provider 返回多个 constrained patch candidates。
5. 系统本地 apply patch、validate、score。
6. provider candidates 和 local candidates 放在同一个 task 下比较。
7. provider 失败不影响 local candidates。

## 6. 核心设计原则

### 6.1 ReviewTask 是反馈工单，不是音乐版本

ReviewTask 记录“要解决什么问题”，不是“已经改了什么歌”。

它可以有多个 candidate，可以被应用，也可以被 resolved 或 archived。

它不能直接修改：

- parent SongPlan
- preview SongPlan
- audition SongPlan
- Project Version
- final version

### 6.2 Candidate 是候选产物，不是正式版本

ReviewCandidate 可以有：

- candidate SongPlan
- MIDI
- WAV
- score
- validator report
- summary

但它仍然不是 Project Version。

只有用户明确 apply 后，才创建正式 child Project Version。

同一个 ReviewTask 下可以有多个 ReviewCandidate，但只能有一个 candidate 被 apply。需要继续修改时，不要在原 task 里再次 apply；创建 linked follow-up task，让新的 parent version 指向刚应用出来的 child version。

### 6.3 Apply 时仍然不信任 candidate 缓存

candidate 目录里的 `candidate-song-plan.json` 可以用于展示和试听，但 apply 时建议重新走安全路径：

- 读取 parent version SongPlan。
- 读取 candidate 的 intents 或 patch。
- 重新 apply。
- validate。
- 写新 job / version。

如果为了复用 candidate SongPlan，也必须校验：

- parent version hash 未变。
- candidate source hash 未变。
- candidate validator passed。
- candidate plan hash 和 candidate metadata 一致。

优先建议 v2.8.0 apply 重新计算，降低缓存污染风险。

### 6.4 Local first

v2.8.0 核心必须不依赖 provider。

没有 OpenAI、Claude、mock provider 之外的任何配置，也必须能完成：

```text
review task -> local candidates -> render MIDI -> apply -> resolve
```

### 6.5 Provider 只是候选来源之一

provider candidate 的地位和 local candidate 一样：

- 需要本地 apply。
- 需要本地 validate。
- 需要本地 score。
- 需要本地 sanitize。
- 不能绕过 operation whitelist。

### 6.6 坐标系必须显式

v2.7.1 刚修复 marker beat 坐标问题，v2.8.0 必须把坐标系写进数据模型。

ReviewTask target 中必须保留：

- `local_marker_beat`
- `range_start_beat`
- `global_marker_beat`
- `target_section_name`
- `target_section_start_beat`
- `target_section_end_beat`

这样后续排查不会再出现“marker 明明在 verse，却命中 intro”的问题。

### 6.7 Review notes 不可信

review notes、marker label、tags 都是用户自由输入。

必须继续：

- sanitize。
- 截断。
- 不当作路径。
- 不当作 operation。
- 不直接塞进 provider prompt 的敏感字段。
- 不原样进入 export。

### 6.8 不做危险抽象

虽然 provider candidate group 和 review candidate 有相似点，但 v2.8.0 不建议立刻抽象一个大一统 CandidateStore。

原因：

- provider candidate group 的 parent 是 Project Version。
- review candidate 的 parent 是 ReviewTask。
- review task 有 resolved / needs_more_work 状态。
- review candidate 的 ranking 需要 review_fit 和 target_precision。
- 贸然抽象容易影响 v1.4 到 v1.5 已经稳定的 candidate group。

v2.8.0 可以复用小 helper，但不要做大重构。

### 8.2 ReviewTask status

允许状态：

```text
open
candidate_ready
applied
resolved
needs_more_work
archived
stale
```

状态含义：

- `open`：task 已创建，但还没有 ready candidate。
- `candidate_ready`：至少有一个 ready candidate。
- `applied`：某个 candidate 已应用成 Project Version。
- `resolved`：用户确认反馈已解决。
- `needs_more_work`：用户认为应用后的版本仍需继续修改。
- `archived`：用户手动归档，不再处理。
- `stale`：父版本或来源 hash 不匹配，不能继续 apply。

状态转移：

```text
open -> candidate_ready
candidate_ready -> applied
applied -> resolved
applied -> needs_more_work
open -> archived
candidate_ready -> archived
applied -> archived
open -> stale
candidate_ready -> stale
```

禁止状态转移：

```text
resolved -> applied
archived -> applied
stale -> applied
resolved -> candidate_ready
needs_more_work -> applied
needs_more_work -> candidate_ready
```

`needs_more_work` 是原 task 的终态之一，不是“旧 task 继续生成并再次 apply”的中间态。进入 `needs_more_work` 后，服务端应创建 follow-up ReviewTask，并在新 task 的 `source.previous_task_id` / `source.previous_candidate_id` / `source.previous_applied_version_id` 中记录上一轮来源。

如果要从 resolved task 继续做新一轮，应该创建新的 task，或明确 `reopen`。v2.8.0 可以不做 reopen。

### 8.4 Candidate type

允许：

```text
local_review_intents
provider_review_patch
manual_override
```

v2.8.0 主线只要求 `local_review_intents`。

`provider_review_patch` 可以在 v2.8.0 实现，也可以放 v2.8.1。

`manual_override` 暂时只作为保留值，不一定开放 UI。

### 8.5 Candidate status

允许：

```text
queued
ready
failed
applied
stale
deleted
```

说明：

- `queued`：生成请求已接收，但未完成。v2.8.0 可以同步生成，不一定真的使用 queued。
- `ready`：candidate SongPlan 可用，validator passed 或 warning-only。
- `failed`：生成失败，记录 error。
- `applied`：该 candidate 已被应用。
- `stale`：parent hash 不匹配。
- `deleted`：逻辑删除。v2.8.0 可以先做物理删除或不做删除。

### 8.6 文件布局

建议：

```text
.musicforge/projects/<project-id>/review-tasks/
  review-task-001/
    task.json
    events.jsonl
    candidates/
      revcand-001/
        candidate.json
        review-edit.json
        candidate-song-plan.json
        validator-report.json
        summary.json
        renders/
          song.mid
          song.wav
      revcand-002/
        candidate.json
        review-edit.json
        candidate-song-plan.json
        validator-report.json
        summary.json
        renders/
          song.mid
```

路径规则：

- `task_id` 必须匹配 `^review-task-[0-9]{3,6}$`。
- `candidate_id` 必须匹配 `^revcand-[0-9]{3,6}$`。
- 所有路径必须 resolve 后仍在 project review-tasks root 内。
- download route 不得使用请求 path 拼任意文件。
- MIDI/WAV 下载必须通过 manifest/candidate metadata 找路径。
- MIDI/WAV 下载还必须校验最终文件位于当前 `review-tasks/<task-id>/candidates/<candidate-id>/renders/` 目录内。
- 下载只允许固定文件名：`song.mid` 和 `song.wav`。即使 candidate metadata 被污染到同一 review-tasks root 下的别的文件，也必须返回 409/404。
- 下载前必须重新检查 candidate stale 状态；stale candidate 不能下载、不能重渲染、不能 apply。

## 9. ReviewTask 推断逻辑

### 9.1 从 audition review 创建 task

输入：

- project_id
- preview_id
- audition_id
- parent_version_id
- parent SongPlan
- audition manifest
- audition SongPlan

输出：

- ReviewTask

流程：

```text
1. 读取 audition manifest。
2. 校验 audition 属于 preview。
3. 校验 preview 属于 project。
4. 读取 parent version SongPlan。
5. 读取 audition review。
6. 如果 review 为空，返回 409。
7. 如果 status=reject 且 rating<=2，允许创建 archived/open task 需要谨慎。
8. 构造 review_snapshot。
9. 根据 marker + range 映射 target section。
10. 根据 track_mode / track_ids / notes keyword 推断 target track。
11. 计算 priority。
12. 写 task.json。
13. 写 event：review_task_created。
```

### 9.2 Target section 推断

优先级：

1. 如果 audition range mode 是 `section`，优先使用该 section。
2. 如果有 marker kind 是 `fix` / `issue` / `drop`，优先使用这些 marker 的 global beat 映射父版本 section。
3. 如果没有 fix/issue/drop marker，但有普通 note marker，使用第一个普通 marker 的 global beat。
4. `keep` / `hook` marker 默认是 preserve signal，不应该作为 edit target，除非 review status 明确是 `needs_fix` 且没有其他 marker。
5. 如果 range mode 是 `changed_sections` 且只有一个 section，使用该 section。
6. 如果 review text 包含 chorus / 副歌 / 高潮，优先 chorus。
7. 如果 review text 包含 verse / 主歌，优先 verse。
8. fallback：第一个包含 chorus 的 section。
9. fallback：第一个包含 verse 的 section。
10. fallback：parent_plan.sections[0]。

### 9.3 Marker global beat 规则

必须显式函数：

```python
def global_marker_beat(range_data: dict[str, Any], marker_beat: float) -> float:
    start = _float_or_none(range_data.get("start_beat"))
    if start is None:
        return marker_beat
    return start + marker_beat
```

适用：

- `custom`
- `changed_sections`
- `section`
- `full_song`

注意：

- 如果 `section` range 有 start_beat，也应该加。
- 如果历史数据没有 start_beat，保持兼容，直接使用 marker beat。
- task target 中同时记录 local 和 global，避免后续误解。

### 9.4 Target track 推断

优先级：

1. 如果 audition `track_mode=solo` 且只有一个 track_id，使用该 track。
2. 如果 review text 提到 bass / 低音 / 贝斯，使用 bass role track。
3. 如果 review text 提到 drums / 鼓 / kick / snare，使用 drums role track。
4. 如果 review text 提到 melody / hook / 旋律，使用 melody role track。
5. 如果 review text 提到 chord / harmony / pad / 和弦 / 和声，使用 chords role track。
6. 如果 marker label 提到上述关键词，同样参与推断。
7. fallback：None，表示 section-level edit。

### 9.5 Priority 计算

priority 用于 Review Workbench 排序，不用于自动应用。

建议：

```text
priority =
  rating_score
  + status_score
  + marker_score
  + favorite_score
  + specificity_score
```

规则：

- rating 5：+30
- rating 4：+24
- rating 3：+12
- status needs_fix：+30
- status maybe：+12
- status keep：+8
- status reject：+0
- marker kind fix/issue：+18
- marker kind hook/keep：+8
- favorite true：+8
- 有明确 section：+6
- 有明确 track：+6

封顶 100。

## 10. Local Review Candidates

### 10.1 候选策略

v2.8.0 默认生成 3 个 local candidates：

```text
conservative
balanced
bold
```

可选第 4 个：

```text
targeted
```

策略含义：

- `conservative`：最小修改，只处理最明确问题。
- `balanced`：接近 v2.7 默认 review edit 行为。
- `bold`：更明显修正，可能加入 energy / arrangement variation。
- `targeted`：只动 marker 所在 section 和 target track，不做额外 section-level 改动。

### 10.2 Strategy 到 intent 的映射

对于 `bass 太满`：

```text
conservative:
  track_density density_scale=0.86 strength=3

balanced:
  track_density density_scale=0.72 strength=4

bold:
  track_density density_scale=0.62 strength=5
  section_energy strength=6 if status=needs_fix

targeted:
  track_density density_scale=0.78 strength=4
  preserve includes "section_energy"
```

对于 `chorus 更强`：

```text
conservative:
  section_energy strength=5

balanced:
  section_energy strength=7

bold:
  section_energy strength=8
  arrangement_variation strength=6
```

对于 `hook 不够`：

```text
conservative:
  melody_variation strength=3

balanced:
  melody_variation strength=5

bold:
  melody_variation strength=7
  section_energy strength=6
```

对于 `过渡不自然`：

```text
conservative:
  arrangement_variation strength=4

balanced:
  arrangement_variation strength=6

bold:
  arrangement_variation strength=7
  section_energy strength=6
```

### 10.3 Keep marker 处理

marker kind：

```text
hook
keep
```

是 preserve signal，不是 edit target。

规则：

- 如果只有 keep/hook marker，没有 fix/issue/drop marker，candidate 应偏保守。
- melody_variation 不应默认改 keep marker 所在区域。
- candidate warnings 应显示：`Hook/keep markers were treated as preserve signals.`
- score 中 `safety` 对保留 keep marker 的候选加分。
- 测试必须覆盖“第一个 marker 是 keep，第二个 marker 是 fix”时，target section 使用 fix marker，而 keep marker 只影响 preserve/safety。

### 10.4 Candidate 生成流程

伪流程：

```text
1. 读取 ReviewTask。
2. 校验 task status 不是 resolved/archived/stale/needs_more_work/applied。
3. 读取 parent version SongPlan。
4. 校验 parent_plan_hash。
5. 为每个 strategy 生成 ReviewEditIntent。
6. validate intents。
7. apply intents 到 parent plan。
8. attach_quality。
9. validate final SongPlan。
10. 写 candidate-song-plan.json。
11. 写 validator-report.json。
12. 写 review-edit.json。
13. 写 candidate.json。
14. render candidate MIDI，失败不应使 candidate failed，除非 SongPlan 不可渲染。
15. rank candidates。
16. 更新 task counts 和 status。
17. 写 event：review_candidates_generated。
```

### 10.5 Candidate 去重

多个 strategy 可能生成相同 intents。

必须去重：

- `json.dumps(intents, sort_keys=True)`
- 或 candidate_plan_hash

如果去重后只剩 1 个候选，也可以接受，但 summary 要说明。

建议：

- 至少尝试 4 个 strategy。
- 去重后如果 ready candidate 数小于 2，添加一个 `targeted` fallback。

### 10.6 Candidate failure

单个 candidate 失败不能导致整个 task 失败。

例子：

- bold candidate validator failed。
- provider candidate patch invalid。
- MIDI render failed。

处理：

- 写 `candidate.status=failed`。
- 写 `candidate.error`。
- task 只要有一个 ready candidate，就进入 `candidate_ready`。
- 所有 candidate 都 failed，task 保持 `open` 或进入 `needs_more_work`，返回 409/207 需要二选一。

建议 API 返回 201，并在 body 中包含 ready 和 failed 列表。

## 11. Scoring 与 Ranking

### 11.1 总体原则

ranking 是建议排序，不是自动决策。

UI 文案应使用：

```text
Suggested Rank
```

不要写：

```text
Best
AI Selected
Final
```

### 11.2 Score 字段

建议：

```json
{
  "combined": 84,
  "review_fit": 90,
  "target_precision": 95,
  "quality_delta": 4,
  "quality_overall": 82,
  "novelty": 62,
  "safety": 100
}
```

### 11.3 combined 公式

建议：

```text
combined =
  review_fit * 0.30
  + target_precision * 0.20
  + quality_component * 0.20
  + validation_component * 0.15
  + novelty * 0.10
  + safety * 0.05
```

其中：

- `quality_component` 可取 `quality_overall`，或 `50 + quality_delta * 5` 后 clamp。
- `validation_component` passed=100, warning=75, failed=0。
- `novelty` 要 bounded，不鼓励为了新奇破坏目标。

### 11.4 review_fit

规则：

- review 有 reduce/太满/太密，candidate 有 target track density reduction：+35。
- review 有 stronger/更强/高潮/能量，candidate 有 section_energy：+30。
- review 有 hook/melody/旋律，candidate 有 melody_variation：+25。
- review 有 arrangement/transition/过渡/drop，candidate 有 arrangement_variation：+25。
- status=needs_fix 且 candidate 至少一个 fix intent：+15。
- marker kind=fix/issue 且 candidate 命中 marker section：+15。
- review 提到 bass 但 candidate 改 drums：-25。
- review 提到 section A 但 candidate 改 section B：-20。

clamp 到 0 到 100。

### 11.5 target_precision

规则：

- candidate section == task target section：+45。
- candidate track == task target track：+35。
- candidate 只动一个 section：+10。
- candidate 只动一个 track：+10。
- candidate 改动非目标 section：-20。
- candidate 改动非目标 track：-15。
- bold strategy 最多扣到 70，不要完全惩罚大胆候选。

### 11.6 safety

规则：

- validator passed：+40。
- no unknown edit type：+20。
- preserve contains tempo/key/structure：+15。
- keep/hook marker 未被当成 edit target：+15。
- sanitized text 无敏感内容：+10。
- provider candidate 未通过本地 validate：0。

### 11.7 novelty

不要用复杂音频分析。

简单规则：

- candidate_plan_hash 不同于 parent：基础 40。
- changed_sections 非空：+15。
- changed_tracks 非空：+15。
- melody variation：+15。
- arrangement variation：+15。
- 改动过多 section：-20。

### 12.12 Needs more work

```text

```

body：


- task status 变 `needs_more_work`。
- 该 task 不能再次 apply，也不能在原 task 内继续生成用于 apply 的新 candidates。
- 服务端创建一个 linked follow-up ReviewTask。
- follow-up task 的 parent version 必须是上一轮的 `applied_version_id`。
- follow-up task 的 `source.previous_task_id`、`source.previous_candidate_id`、`source.previous_applied_version_id` 必须写入。
- 返回 body 应包含旧 task 和新 task，方便 Studio 直接跳转。

建议返回：

```json

  "task": {},
  "follow_up_task": {},
  "summary": {

```

```json
      "confidence": 0.74,
      "strategy": "conservative"
    }
  ]
}
```

### 17.2 Provider 输入上下文

只给 provider：

- sanitized review snapshot。
- target section/track。
- parent SongPlan summary。
- allowed operations。
- constraints。
- candidate_count。

不能给：

- 本地绝对路径。
- provider key。
- 原始完整 notes，如果包含敏感内容。
- audition WAV path。

### 17.3 Provider 输出验证

每个 candidate：

1. parse JSON。
2. validate schema。
3. validate patch。
4. apply patch locally。
5. validate SongPlan。
6. score。
7. 写 candidate。

任何失败 candidate 都记录 failed，不影响其他 candidate。

## 24. Stale 检测

ReviewTask 和 Candidate 都必须防 stale。

### 24.1 Task stale

如果 parent version SongPlan hash 与 task `hashes.parent_plan_hash` 不一致：

- task 应视为 stale。
- 不能 generate new candidates。
- 不能 apply existing candidates。
- 可以查看历史。
- 可以 archive。

### 24.2 Candidate stale

如果 candidate parent hash 与当前 parent hash 不一致：

- candidate MIDI/WAV download 返回 409。
- render MIDI/WAV 返回 409。
- apply 返回 409。

如果 candidate metadata 中的 MIDI/WAV path 被污染：

- path 指向别的 candidate：409。
- path 指向别的 task：409。
- path 指向 review-tasks root 下的非 renders 文件：409。
- path 指向 project 目录外：409。
- path 是 symlink 且目标不在当前 candidate renders 目录：409。

### 24.3 为什么必须严格

因为 review target section/track 是基于某个 parent SongPlan 计算的。

一旦父版本变化：

- section start beat 可能变化。
- track order 可能变化。
- target track 可能被删除或重命名。
- candidate SongPlan 不再可解释。

- 新增 strategy 函数，不改默认。

### 33.3 Candidate 缓存被当作正式版本

风险：

- apply 直接复制 candidate-song-plan。

- apply 重新从 parent + intents/patch 计算。
- 校验 hash。

### 33.3.1 Candidate artifact path 污染

风险：

- candidate metadata 被污染到同一 project 下的其他文件。
- 下载接口只做 review-tasks root 检查，误把别的 candidate 或内部 JSON 当作 MIDI/WAV 发出去。

防护：

- 下载路径必须落在当前 candidate 的 `renders/` 目录。
- 只允许 `song.mid` / `song.wav`。
- stale、symlink、跨 candidate、跨 task 都返回 409。
- release-check 人为污染 path 后验证下载失败。

### 33.3.2 多轮状态语义混乱

风险：

- `needs_more_work` 后继续在旧 task 生成并 apply candidate，导致 selected_candidate/applied_version 覆盖、hash 失真。

防护：

- 一个 ReviewTask 只允许 apply 一次。
- `needs_more_work` 创建 linked follow-up ReviewTask。
- follow-up task 使用上一轮 `applied_version_id` 作为 parent。
- Project Export 展示 task chain，而不是把多轮塞进一个 task 的扁平字段里。

### 33.4 Provider 输出绕过安全

风险：

- provider candidate 产生未知 op。

防护：

- 本地 patch validation。
- failed candidate 不 ready。
- provider route 不 auto apply。

### 33.5 UI 变复杂

风险：

- Review Board、Candidate、Project Editor 挤在一个页面难用。

防护：

- Review Board 只保入口。
- Workbench 独立区域。
- candidate card 简洁。
- JSON 默认折叠或放 pre。

### 33.6 release-check 过慢

风险：

- release-check 已经 2 分钟以上，再加 v2.8 过慢。

防护：

- v2.8 smoke 不依赖真实 WAV renderer。
- MIDI render 可跑。
- audio renderer missing 只测 400。
- 不生成 provider candidates，除非 mock provider 很快。

---

## 34. 建议开发顺序

第一阶段只做后端本地闭环：

```text
ReviewTask -> Local Candidates -> Apply -> Resolve
```

第二阶段加 UI：

```text
Review Workbench
```

第三阶段加 export/release-check：

```text
Compare / Project Export / Final Export / release-check
```

第四阶段再考虑 provider：

```text
Provider Review Candidates
```

不要先做 provider。

不要先做大 UI。

不要先做抽象重构。

---

## 35. 最终判断

v2.8.0 最有价值的方向是“评审候选工作台”，因为它把已有能力串成了一个真正的创作闭环。

它承接：

- v2.5 的试听。
- v2.6 的评审。
- v2.7 的评审驱动编辑。
- v1.4/v1.5 的候选思想。
- v1.9 的上下文沉淀。

但它不冒进：

- 不自动改歌。
- 不依赖 provider。
- 不做 DAW。
- 不做音频理解。
- 不做大重构。

做完 v2.8.0 后，MusicForge 的核心体验会从：

```text
我听了一个结果，然后点一下生成新版本
```

升级为：

```text
我围绕一个明确反馈，生成几种修正方案，听完选择一个，应用并标记这条反馈是否解决
```

这是从“生成工具”走向“创作工作台”的关键一步。

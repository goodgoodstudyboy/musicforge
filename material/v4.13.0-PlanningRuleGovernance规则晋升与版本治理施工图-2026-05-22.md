# v4.13.0 Planning Rule Governance 规则晋升与版本治理施工图

当前基线：v4.12.0

目标版本：v4.13.0

建议版本主题：Planning Rule Governance / 规则晋升、版本冻结与回滚治理

编写时间：2026-05-22

适用对象：

- 接手 MusicForge 的开发人员
- reviewer
- 后续负责验收、发布、回滚的开发人员

---

## 1. 背景

MusicForge 到 v4.12.0 已经完成了一条非常完整的本地质量闭环：

```text
Acceptance
  -> Human Review
  -> Acceptance Analytics
  -> Acceptance Fix Sprint
  -> Acceptance Knowledge Base
  -> Knowledge-assisted Fix Plan
  -> Fix Sprint
  -> Outcome Review
  -> Planning Rule Simulation
```

v4.12.0 的 Planning Rule Simulation 已经能做到：

- 创建 Planning Rule Set。
- 用历史 Fix Plan Outcome Review 回放候选规则。
- 输出 baseline score、simulated score、alignment delta、rule effects、recommendation。
- 用 source hash 防止 stale simulation 进入 signoff。
- 接入 CLI、API、Studio、Project Export、Release Export、Final Export、Release Signoff。

但是 v4.12.0 仍然是沙箱。

它明确不做：

- 不激活规则。
- 不修改 production planning rule。
- 不让 Fix Plan 自动使用候选规则。
- 不记录“当前生产规则版本”。
- 不支持规则回滚。

这很安全，但也带来一个问题：

```text
开发能看到某个 ruleset 在历史回放中更好，
但是系统里还没有“把它正式晋升为生产规则”的治理流程。
```

所以 v4.13.0 要补的不是“更多 simulation”，而是规则治理层：

```text
候选规则 -> 模拟证据 -> 人工批准 -> active version -> Fix Plan 引用 -> 版本审计 -> 回滚
```

---

## 2. v4.13.0 的一句话目标

v4.13.0 要新增一个本地 deterministic Planning Rule Governance 层，让 Planning Rule Set 可以在充分 simulation evidence 和人工签核后晋升为 active planning rule version，并让后续 Fix Plan 明确记录所用规则版本；系统必须支持冻结、回滚、审计、导出和 release signoff evidence，但仍然不自动应用编辑、不自动关闭 sprint、不自动签核 release。

---

## 3. 为什么下一版应该做这个

### 3.1 现在已经不缺生成链路，缺“可控地变聪明”

系统已经能：

- 生成音乐。
- 编辑音乐。
- 做候选。
- 做人工听审。
- 做验收。
- 做修复冲刺。
- 做知识库。
- 做计划。
- 做复盘。
- 做规则模拟。

现在最大风险不是“没有功能”，而是：

```text
系统积累了大量经验，但规则是否应该改变，仍然靠人脑记忆。
```

如果没有规则治理，就会出现：

- 某个 ruleset 被证明更好，但没人知道是否已经用于后续计划。
- 开发临时改了权重，后续 Fix Plan 结果变了，却无法追溯。
- Release Signoff 只知道有 simulation，不知道当前生产规则是不是已经按 simulation evidence 晋升。
- 出问题时无法回滚到上一版 active rules。

### 3.2 v4.12 不能直接跳到 v5

v4.12 文档里提到下一步可以考虑 v5 Real Audio / Vocal / Mixing Path。

但 reviewer 建议先做 v4.13，原因是：

- v5 真实音频会显著提高验收成本。
- 真实音频问题会大量反馈到 Acceptance / Fix Plan / KB。
- 如果 planning rules 没有版本治理，v5 的问题会更难复盘。

所以 v4.13 是进入 v5 前的治理收口：

```text
先把“系统如何学习和改变规则”收紧，再扩展真实音频能力。
```

## 4. 核心原则

### 4.1 人工晋升，不自动晋升

Simulation recommendation 即使是 `candidate_better`，也不能自动成为 active rules。

必须有人工动作：

```text
approve / promote / signoff
```

### 4.2 晋升必须绑定 simulation evidence

不能凭空把一个 ruleset 晋升为 active。

晋升时必须绑定：

- ruleset_id
- simulation_id
- simulation source_hash
- simulation recommendation
- review_count
- item_count
- alignment_delta
- approving actor
- approval note

### 4.3 stale simulation 不能晋升

只要 simulation stale：

- promote 返回 409
- signoff gate 返回 failed
- export summary 标 stale

### 4.4 active version 必须冻结

一旦 ruleset 被晋升为 active version：

- active record 不允许被修改。
- 原始 ruleset 可以 archive，但 active version 仍要保留完整 frozen payload。
- active version 的 hash 必须稳定。

### 4.5 Fix Plan 必须可追溯规则版本

从 v4.13 开始，Acceptance Fix Plan 的 source/summary 需要记录：

- planning_rule_version_id
- ruleset_id
- ruleset_hash
- governance_status
- generated_with_active_rules: true/false

如果没有 active rules，继续使用 legacy default，但要明确写：

```json
{
  "planning_rule_version_id": null,
  "governance_status": "legacy_default"
}
```

### 4.6 回滚是显式版本切换，不删除历史

Rollback 不删除坏版本。

Rollback 应该创建一个 governance event：

```text
active version changed from prgv-000004 to prgv-000003
reason = ...
```

### 4.7 不做自动修复

v4.13 仍然不做：

- 自动创建 Fix Plan。
- 自动创建 Fix Sprint。
- 自动 apply edits。
- 自动 close sprint。
- 自动 sign release。

---

## 5. 建议版本定位

```text
v4.12.0 = 规则模拟沙箱
v4.13.0 = 规则晋升治理
v5.0.0 = 真实音频能力的起点
```

v4.13 做完后，v4 质量治理线才算真正闭环：

```text
经验 -> 知识 -> 计划 -> 执行 -> 复验 -> 复盘 -> 模拟 -> 晋升 -> 新计划
```

## 6. 不做范围

v4.13.0 明确不做：

- 不接外部 AI 自动改规则。
- 不做 provider judge 自动 approve rules。
- 不做在线 A/B 实验。
- 不做跨机器协作锁。
- 不做数据库。
- 不做复杂权限系统。
- 不重构 Acceptance Fix Plan 核心算法。
- 不改变已有 v4.12 simulation 的安全口径。
- 不把 ruleset 明文敏感字段写入 Release Export。

## 7. 新增模块建议

新增文件：

```text
song_agent/planning_rule_governance.py
```

职责：

- 管理 active planning rule versions。
- 管理 promotion request。
- 管理 approval/signoff。
- 管理 rollback。
- 输出 governance summary。
- 给 Fix Plan 提供当前 active rules。

不建议把这部分继续塞进 `planning_rule_simulation.py`，原因：

- simulation 是沙箱计算。
- governance 是状态治理。
- 两者生命周期不同。
- 分文件更利于 reviewer 查安全边界。

## 10. Promotion 创建规则

新增方法：

```python
PlanningRuleGovernanceStore.create_promotion(payload)
```

payload：

```json
{
  "ruleset_id": "afprs-000001",
  "simulation_id": "afpsim-000001",
  "scope": {"type": "global"},
  "created_by": "developer",
  "note": "Candidate after synthetic strict replay."
}
```

必须校验：

- ruleset 存在。
- simulation 存在。
- simulation.ruleset_id == ruleset_id。
- simulation 非 stale。
- simulation.status in `ready`, `warning`。
- simulation.status 不能是 `blocked`, `archived`, `stale`。
- simulation recommendation 不能是 `insufficient_data`。
- simulation source_hash 记录进 evidence。

如果 recommendation 是 `candidate_worse`：

- 可以创建 promotion，但 risk_assessment.status = `blocked`。
- approve/promote 必须 force，并写 override_reason。

如果 recommendation 是 `candidate_mixed`：

- risk_assessment.status = `warning`。
- approve 允许，但要 approval_note。

## 11. Promotion approve / reject

### 11.1 approve

新增方法：

```python
PlanningRuleGovernanceStore.approve_promotion(promotion_id, payload)
```

payload：

```json
{
  "approved_by": "developer",
  "approval_note": "Accepting mixed result because manual recheck coverage is strong.",
  "force": false,
  "override_reason": ""
}
```

校验：

- promotion 必须 pending。
- promotion source simulation 仍非 stale。
- recommendation = candidate_better 时可正常 approve。
- recommendation = candidate_mixed 时必须有 approval_note。
- recommendation = candidate_worse 时必须 force=true 且 override_reason 非空。
- approve 不等于 promote，只是批准候选。

### 11.2 reject

新增方法：

```python
PlanningRuleGovernanceStore.reject_promotion(promotion_id, payload)
```

payload：

```json
{
  "rejected_by": "developer",
  "reason": "Insufficient manual coverage."
}
```

校验：

- reason 必填。
- rejected promotion 不能再 promote。

## 12. promote 为 active version

新增方法：

```python
PlanningRuleGovernanceStore.promote(promotion_id, payload)
```

payload：

```json
{
  "promoted_by": "developer",
  "activation_note": "Use for next acceptance fix planning cycle."
}
```

校验：

- promotion 必须 approved。
- promotion source simulation 仍非 stale。
- ruleset 当前 payload hash 必须等于 promotion evidence 中的 ruleset hash。
- 旧 active 标记 superseded。
- 新建 `prgv-xxxxxx` version。
- 写 `ruleset-frozen.json`。
- 写 `active.json`。
- 写 governance event。

返回：

```json
{
  "ok": true,
  "version": {...},
  "active": {...},
  "summary": {...}
}
```

## 13. rollback

新增方法：

```python
PlanningRuleGovernanceStore.rollback(payload)
```

payload：

```json
{
  "target_version_id": "prgv-000001",
  "rolled_back_by": "developer",
  "reason": "New rule caused low confidence plans."
}
```

校验：

- target version 存在。
- target version 不能 archived。
- reason 必填。
- rollback 后 `active.json` 指向 target。
- 当前 active 标记 rolled_back 或 superseded。
- 写 rollback event。

不允许：

- 删除 version。
- 覆盖 frozen ruleset。

## 14. Planning Fix Plan 接入

v4.13 必须让新的 Fix Plan 知道自己用的是什么规则。

需要改：

```text
song_agent/acceptance_fix_planning.py
```

创建 Fix Plan 时：

- 读取 `PlanningRuleGovernanceStore.active_version()`。
- 如果存在 active version：
  - 把 active version summary 写入 plan.source。
  - 把 ruleset weights/penalties/confidence 作为 scoring context。
- 如果不存在：
  - 保持旧逻辑。
  - source 标记 `governance_status=legacy_default`。

建议 plan.source 增加：

```json
{
  "planning_rule_governance": {
    "status": "active",
    "version_id": "prgv-000001",
    "ruleset_id": "afprs-000001",
    "ruleset_hash": "...",
    "active_at": "...",
    "source": "planning_rule_governance"
  }
}
```

注意：

- v4.13 不要求重写所有 planning score 算法。
- 第一版可以只把 active rules 作为 metadata evidence 接入。
- 如果要真正影响 score，必须非常保守，只允许影响 v4.12 已有的同类 penalty/bonus。

建议分两档实现：

### 14.1 必做

- Fix Plan 记录 active version。
- Export / Signoff 能看到 plan 用了哪版规则。
- stale/rollback 后旧 plan 不被改写。

### 14.2 可选增强

- Fix Plan scoring 可使用 active rules 的部分权重。
- 必须有测试证明 active rules 改变后新 plan score 改变，旧 plan 不变。

如果开发时间紧，v4.13 先做必做，不做实际 score 影响。

## 19. Release Signoff gate

新增可选 gate 参数：

```json
{
  "require_planning_rule_governance": true,
  "planning_rule_version_id": "prgv-000001"
}
```

逻辑：

- 如果 require=true 但没有 active version：409。
- 如果指定 version_id：
  - 必须存在。
  - 必须等于 active version，除非 force=true。
- active version 的 promotion simulation 必须非 stale。
- active version 的 ruleset frozen hash 必须匹配 version.ruleset_hash。
- 如果 version 是 rolled_back/archived：failed。

force 规则：

- missing active 不能 force 通过。
- stale promotion evidence 不能 force 通过。
- version mismatch 可以 force，但必须写 override_reason。

建议 evidence：

```json
{
  "planning_rule_governance": {
    "status": "passed",
```

## 20. Source hash 和 stale guard

PlanningRuleVersion source hash 应覆盖：

- frozen ruleset core
- promotion evidence core
- simulation source_hash
- approval core

Promotion stale 判断：

- simulation_is_stale(simulation) == true => promotion stale。
- ruleset current hash != promotion ruleset_hash 且 promotion 未 promoted => stale。
- promoted version 使用 frozen ruleset，不因原 ruleset archive 变 stale。

Active version integrity 判断：

- `ruleset-frozen.json` stable_hash == version.ruleset_hash。
- promotion evidence simulation_id 仍可读。
- 如果 simulation 已 stale：
  - active version 不自动失效。
  - governance summary 标 `evidence_stale=true`。
  - release signoff require gate 时 failed，要求重新 simulation / promotion。

这个点很重要：

```text
已经使用过的历史 active version 不能被自动篡改，
但新的 release signoff 不能拿 stale evidence 当新证据。
```

## 24. 安全与脱敏要求

### 24.1 不输出完整 ruleset 到 release 包

Release Export 只能写 summary。

完整 frozen ruleset 留在本地 `.musicforge/planning-rule-governance/`。

### 24.2 所有 note 都要 sanitize

字段：

- note
- approval_note
- override_reason
- rejection reason
- rollback reason

必须过统一 redaction：

- token
- Bearer
- GitHub token
- Windows path
- UNC path
- provider raw response

### 24.3 路径安全

所有 id 目录必须：

- 固定 prefix。
- 只允许数字尾缀。
- resolve 后必须在 governance root 内。

### 24.4 签核后不静默改证据

如果 Release 已 signed：

- 不能 rebuild export。
- 不能让 governance summary 静默变化。
- 必须 reset signoff 后重新 export/signoff。

## 25. 并发要求

PlanningRuleGovernanceStore 必须使用 RLock。

以下操作必须在锁内完成：

- id 分配。
- mkdir exist_ok=False。
- active pointer 更新。
- version 写入。
- promotion status 更新。
- rollback。

避免：

- 两个 promote 同时创建两个 active。
- active.json 指向不存在 version。
- promotion 被 approve/reject race。

测试建议：

- 16 并发 create promotion，id 唯一。
- 8 并发 promote 同一个 approved promotion，只允许一个成功，其余 409。

如果时间紧，并发测试至少覆盖 active pointer 原子性。

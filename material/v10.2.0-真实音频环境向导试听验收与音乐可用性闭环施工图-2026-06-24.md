> 目标读者：MusicForge 开发执行人员  
> 当前稳定基线：v10.1.1  
> 规划角色：Reviewer / Planner  
> 计划版本：v10.2.0  
> 文档日期：2026-06-24

---

## 1. 背景

MusicForge 已经从最初的本地 MIDI MVP，推进到完整的生成、编辑、项目、发行、分发、公开证明、Trust Operations、GA/LTS 和 Maintenance Center。v10.1.1 已经把长期维护里的备份、恢复、升级预检、周期复验补齐，并且修掉了 restore overwrite 与 backup verifier 的安全缺口。

现在系统的证明链、验收链、发布链已经非常完整，继续堆新的信任包收益会下降。下一步应该回到音乐业务本身：开发必须能够在本机真实地生成可听 WAV，能够组织人工试听，能够记录问题，能够把问题转成修复任务，并且能用可复现报告证明“这批歌不是只通过了结构校验，而是真的经过听审”。

v10.2.0 的定位是：

- 把 renderer / SoundFont / audio profile 配置从“懂的人会配”变成“开发按向导一步一步配”。
- 把 acceptance-check 从“能生成报告”推进到“能形成可播放、可记录、可复验的试听工作流”。
- 把人工试听从零散备注变成可追踪的 Listening Session。
- 把发现的问题直接接入 ReviewTask / Audio Revision / Mix Patch 等既有修复链路。
- 让开发本地就能完成“生成、渲染、播放、听审、标注、修复入口、复验”的闭环。

这版不是新增外部音乐 API，不是接 Suno / Udio，也不是要求第三方云服务。它仍以本地 deterministic composer、现有 MIDI/WAV renderer、现有人工审查链路为基础。

---

## 2. v10.2.0 总目标

v10.2.0 的核心目标可以一句话概括：

> 建立一个本地 Audio Lab，把真实音频环境配置、WAV 渲染、人工试听、A/B 对比、问题标注和修复入口串成完整业务闭环。

完成后，开发应能做到：

1. 运行命令检查本机是否具备真实 WAV 渲染条件。
2. 用 Studio 向导配置 renderer profile 和 audio profile。
3. 生成一组代表性试听歌曲，并真实渲染 WAV。
4. 在 Studio 里播放 WAV，逐首填写人工听审结果。
5. 对问题点打 marker，选择 issue taxonomy。
6. 一键生成 ReviewTask / AudioRevision / MixPatch draft，但不自动 apply。
7. 对修复前后做 A/B 对比，记录偏好和原因。
8. 输出 Audio Lab Report，供 release_candidate / GA / 维护复验引用。

## 3. 不做什么

为了避免 v10.2.0 范围失控，本版明确不做：

- 不接外部生成音乐 API。
- 不做云端音频渲染。
- 不做真实音频指纹版权检测。
- 不做自动主观审美评分替代人工试听。
- 不把 synthetic review 伪装成人工 review。
- 不让 provider 自动决定 release-ready。
- 不新增大型公开证明包链路。
- 不要求开发上传本机 SoundFont 或私有音频文件到仓库。
- 不提交 `.musicforge/renderer.json`、`.musicforge/audio-profiles/`、真实 WAV、真实 SoundFont。

## 7. Audio Environment Wizard

### 7.1 目标

开发进入系统后，应先看到一个明确状态：

- 当前有没有 renderer config。
- 当前有没有 audio profile。
- FluidSynth 可执行文件是否存在。
- SoundFont 是否存在。
- renderer test 是否通过。
- WAV 渲染是否能产出合法 WAV。
- 音频健康检查是否通过。

### 7.2 CLI

新增：

```bash
python -m song_agent.cli audio-lab status --json
python -m song_agent.cli audio-lab detect --json
python -m song_agent.cli audio-lab test-profile --profile default --json
python -m song_agent.cli audio-lab setup-report --json
```

### 7.3 API

新增：

```text
GET  /api/audio-lab/environment
POST /api/audio-lab/environment/detect
POST /api/audio-lab/environment/test-profile
GET  /api/audio-lab/environment/report
```

### 7.4 Detect 规则

Detect 不应该全盘扫描，避免慢和隐私风险。

只检查：

- 已配置路径。
- PATH 中可执行文件。
- 常见 FluidSynth 命令名。
- 用户明确传入的候选路径。
- 项目本地文档提示路径。

SoundFont 候选路径只检查用户明确输入或已配置路径，不递归扫描磁盘。

### 7.5 输出要求

对外 API / Studio 展示必须脱敏：

- 不直接暴露完整本机绝对路径。
- 可以展示 basename、exists、size、sha256 prefix。
- report 中本机路径统一走现有 redaction。

内部 `.musicforge` 本地配置可以保存真实路径，但这些文件必须继续被 `.gitignore` 覆盖。

### 7.6 风险点

不要把 fake runner 当真实 renderer。v5.5.1 已明确禁止公开 API / Studio 持久化 fake_runner。v10.2 不得绕回去。

## 8. Audio Smoke Run

### 8.1 目标

让开发快速生成一组“代表性可听样本”，用于验证本机生成链路和音频链路。

### 8.2 CLI

新增：

```bash
python -m song_agent.cli audio-lab smoke --cases 3 --render-audio required --profile default --json
python -m song_agent.cli audio-lab smoke --songbook regression --cases 5 --json
python -m song_agent.cli audio-lab smoke-report <smoke-run-id> --json
```

### 8.3 Smoke case 来源

优先复用 Regression Songbook。

最小用例建议：

- 短歌，验证速度。
- 中速 pop，验证常规编曲。
- 高密度 groove，验证鼓和 bass。
- 情绪型 ballad，验证 section 能量变化。
- instrumental，验证无歌词场景。

### 8.4 输出

每个 smoke item 至少有：

```json
{
  "item_id": "smoke-001",
  "song_id": "regression_pop_midtempo",
  "generation_status": "passed",
  "midi_status": "passed",
  "audio_status": "passed",
  "audio_health_status": "passed",
  "song_plan_hash": "...",
  "midi_hash": "...",
  "wav_hash": "...",
  "renderer_profile_id": "default",
  "audio_profile_id": "wav_default",
  "warnings": []
}
```

### 8.5 失败语义

`--render-audio required`：

- renderer 未配置：failed。
- SoundFont 不存在：failed。
- WAV header 不合法：failed。
- WAV silent / clipped 超阈值：failed。

`--render-audio auto`：

- renderer 缺失可以 warning / skipped，但报告必须明确 `audio_status=skipped_renderer_not_configured`。

`--render-audio never`：

- 明确记录 `audio_status=skipped_by_request`。

不要把 skipped 误写成 passed。

## 9. Listening Session

### 9.1 目标

人工试听必须成为可追踪对象。一个 Listening Session 表示一次明确的听审活动，可以来自：

- Audio Smoke Run。
- Acceptance Suite。
- Release tracks。
- Project versions。
- Candidate previews。
- Audio Revision candidates。
- Mastering candidates。
- Encoded audio profiles。

### 9.2 Session schema

建议结构：

```json
{
  "session_id": "als-000001",
  "created_at": "...",
  "status": "open",
  "source_type": "audio_smoke_run",
  "source_id": "alsm-000001",
  "reviewer": {
    "name": "local reviewer",
    "role": "developer"
  },
  "playback_environment": {
    "device_type": "headphones",
    "notes": "",
    "volume_reference": "comfortable"
  },
  "queue": [],
  "summary": {
    "total": 0,
    "accepted": 0,
    "needs_fix": 0,
    "rejected": 0
  },
  "source_hash": "...",
  "integrity_hash": "..."
}
```

### 9.3 Review item schema

```json
{
  "item_id": "ali-000001",
  "track_ref": {
    "type": "smoke_item",
    "id": "smoke-001"
  },
  "audio_artifact": {
    "wav_hash": "...",
    "duration_seconds": 92.3,
    "audio_health_hash": "..."
  },
  "playback_confirmed": true,
  "review_mode": "manual",
  "rating": 4,
  "result": "accepted",
  "issue_categories": [],
  "notes": "",
  "markers": [],
  "reviewed_at": "..."
}
```

### 9.4 Manual guard

人工 review 必须满足：

- `review_mode=manual`
- `playback_confirmed=true`
- reviewer name / role 非空
- item 当前 WAV hash 与 review 绑定一致

不允许：

- synthetic review 被记为 manual。
- 没播放就 accepted。
- WAV 变化后旧 review 继续算 current。

### 9.5 CLI

新增：

```bash
python -m song_agent.cli audio-lab session create --from-smoke alsm-000001 --json
python -m song_agent.cli audio-lab session list --json
python -m song_agent.cli audio-lab session detail als-000001 --json

python -m song_agent.cli audio-lab session report als-000001 --json
```

## 14. Security / Integrity 要求

### 14.1 本机路径脱敏

所有 report / API summary / Studio public summary 都必须脱敏：

- Windows 盘符路径。
- UNC 路径。
- token。
- provider key。
- local SoundFont path。

### 14.2 Source hash

以下对象必须有 source hash：

- smoke-run report。
- listening session report。
- review item。
- marker。
- comparison report。

source hash 至少绑定：

- song-plan hash。
- MIDI hash。
- WAV hash。
- renderer profile fingerprint。
- audio profile fingerprint。
- audio health hash。

### 14.3 Stale guard

以下情况必须 stale：

- WAV 重新渲染。
- song-plan 变化。
- MIDI 变化。
- renderer profile 变化。
- audio profile 变化。
- audio health report 变化。

stale review 不允许作为 manual accepted evidence。

### 14.4 不引入新的公开包自证问题

v10.2 不需要新增公开 proof ZIP。如果确实实现本地 report verifier，也必须避免“report 自己证明自己”：

- verifier 读取当前 workspace artifacts。
- 或显式要求外部 artifact hashes。

不要在 v10.2 新增复杂外部证明链。

## 17. release-check

新增 smoke：

```text
v102.audio_lab_real_listening_smoke
```

纳入：

- `latest`
- `v10`
- `quick` 可只跑轻量路径

不建议纳入 v8/v9 profile。

### 17.1 Smoke 覆盖点

必须覆盖：

1. renderer 缺失时 `status=warning/skipped`，不伪装 passed。
2. fake runner 不能通过公开配置持久化。
3. smoke run 能生成 MIDI-only report。
4. fake runner 测试路径下能生成 WAV health report，但 runner kind 必须标记 test/fake，不得进入 release-ready。
5. manual review 必须 `playback_confirmed=true`。
6. synthetic review 不能满足 manual gate。
7. WAV hash 变化后旧 review stale。
8. marker 能创建 ReviewTask draft。
9. A/B review 能绑定左右 artifact hash。
10. report 脱敏本机路径。

## 23. 给开发的话

这版请不要继续优先做新的证明包。v10.2 的重点是让 MusicForge 回到音乐业务本身：开发在本机要能把歌生成出来、渲染成真实 WAV、打开 Studio 播放、写下人工听审意见、标注问题点，并把问题转成下一步修复入口。

你实现时按 package 分段推进，每完成一段就提交一次。不要等所有东西堆完才提交。测试里可以继续用 fake runner 做自动化覆盖，但对外状态必须明确 fake/test，不允许把它当真实 release-ready evidence。真实 SoundFont 和本机路径只保存在 `.musicforge/` 本地配置里，不要提交，不要写进文档，不要出现在公开 report。

最终交付时，请用一句话说清楚：这版是否已经在本机完成真实 WAV 播放和人工听审。如果没有，也必须诚实写明缺少什么条件。这个项目现在最需要的是可验证的音乐可用性，不是更多看起来很完整但没人真正听过的流程。

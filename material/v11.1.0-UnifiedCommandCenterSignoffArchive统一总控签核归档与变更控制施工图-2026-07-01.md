# v11.1.0 Unified Command Center Signoff / Archive 统一总控签核归档与变更控制施工图

## 0. 给开发的话

v11.0.0 已经把 MusicForge 从“很多强模块”推进到了“一个统一总控台”：

- Unified Command Center 能聚合 Audio Command Center、Trust Operations Hub、Public Trust Center、Release / Distribution / Submission / Operations、Maintenance、GA readiness、release-check。
- 它能生成 Evidence Graph、Evidence Inventory、Readiness Matrix、Gap Plan、Safe Runbook。
- 它有固定结构 ZIP 和离线 verifier。
- Release signoff 和 GA readiness 已经能要求 Unified Command Center evidence。
- reviewer 已经确认 `v11.0.0` 发布状态 OK。

但 v11.0.0 仍然只是“总览 + 编排 + 证据包”。它还缺一个真正产品级交付系统必须有的能力：

```text
统一总控台自己如何被正式签核？
签核后如何证明它没有被静默改写？
签核后底层证据变化怎么办？
如果必须重开，谁批准、为什么、重开了什么？
给外部 reviewer / 业务负责人 / 交付人员，应该交哪一个最终包？
```

所以 v11.1.0 不要继续新增一个孤立小功能。它应该在 v11.0.0 的基础上做一次“总控证据闭环”：

> 为 Unified Command Center 增加正式 Signoff、Change Request Reset、Immutable Archive、Final Handoff Pack、offline verifier 和 GA/Release gate 绑定，让 MusicForge 的最终准出从“ready report”升级成“可审计、可冻结、可重开、可移交”的完整交付凭证。

这版做完以后，业务上应该可以这样表达：

```text
这个 MusicForge release 已经通过统一总控台签核。
这是签核证书。
这是总控归档包。
这是离线验证命令。
这是变更历史。
如果后续任何底层证据或总控包被改过，验证会失败。
如果要重开，必须先创建并批准 Change Request。
```

## 2. 为什么 v11.1.0 要做签核归档

### 2.1 v11.0.0 的能力边界

v11.0.0 解决的是：

- 哪里缺证据。
- 哪里 stale。
- 哪里 runtime verifier failed。
- 哪些 safe action 可以跑。
- 统一 ZIP 是否能离线验证。
- GA / Release 是否可以 require UCC ready。

但它没有解决：

- UCC ready 之后，谁确认可以最终交付。
- UCC ZIP / report / readiness 在签核后是否被冻结。
- 签核后删除某些文件是否能绕过不可变状态。
- 签核后底层 Release / Distribution / Submission / Trust / Public / Maintenance evidence 变化，UCC signoff 是否会被挡住。
- 外部 reviewer 拿到的最终交付包是否包含 signoff history、change request、verification report、readiness matrix。
- 重开签核是否有 approved CR 绑定。

### 2.2 这不是“又加一个 ZIP”

v11.1.0 的核心不是为了多一个 ZIP 文件，而是建立最终不可变边界：

```text
底层证据 -> UCC runtime verifier -> UCC ZIP -> UCC verification report -> UCC signoff -> UCC archive -> final handoff
```

每一层都要绑定上一层的 hash / manifest / package_type / status，并能离线复验。

### 2.3 最终用户价值

完成 v11.1.0 后，用户不需要理解几十个模块，只需要看：

- Unified Command Center 是否 ready。
- Unified Command Center 是否 signed。
- Unified Command Center Archive 是否 passed。
- 是否有 open Change Request。
- 是否有 blocker / manual action。
- 是否有可交给外部的 Final Handoff Pack。

## 3. v11.1.0 目标

### 3.1 必须完成

1. 新增 Unified Command Center Signoff。
2. 新增 Signoff history hash chain。
3. 新增 Change Request / approved reset。
4. 签核后禁止 refresh / run-safe / export / zip 静默改写。
5. 新增 Unified Command Center Archive export / ZIP。
6. 新增 `verify-unified-command-center-archive-package`。
7. 新增 Final Handoff Pack。
8. 新增 `verify-unified-command-center-handoff-package`。
9. Release signoff / GA readiness 支持 require UCC signoff archive。
10. Studio 新增 Signoff / Archive / Handoff / Change Request 控件。
11. release-check 新增 `v111.unified_command_center_signoff_archive_smoke`。
12. README / CHANGELOG / version bump 到 `11.1.0`。

### 3.2 明确不做

v11.1.0 不做：

- 云端同步。
- 多用户权限系统。
- 第三方 CA / 公钥基础设施。
- 真正电子签名法意义上的签章。
- 自动 approve Change Request。
- 自动 signoff。
- 自动人工听审。
- 自动 submit / accept / publish。
- 替代底层 verifier。

### 3.3 关键设计原则

1. **签核只能基于当前通过的 UCC verification report。**
2. **签核后不可静默改写。**
3. **删除 signoff 文件不能绕过已签核状态。**
4. **reset 必须绑定 approved Change Request。**
5. **archive verifier 不能只信 archive 内部自证。**
6. **handoff pack 必须固定结构，不允许多余 entry。**
7. **所有人工文本必须脱敏。**
8. **所有外部 evidence 必须按 package_type 和 component_id 绑定。**

## 6. Store 行为

### 6.1 新增 Store 能力

建议在 `UnifiedCommandCenterStore` 增加：

```python
signoff(center_id, payload, *, release_check_report=None) -> dict
reset_signoff(center_id, change_request_id, payload=None) -> dict
create_change_request(center_id, payload) -> dict
approve_change_request(center_id, change_request_id, payload) -> dict
list_change_requests(center_id) -> list[dict]
get_change_request(center_id, change_request_id) -> dict
export_archive(center_id, *, release_check_report=None) -> dict
build_archive_zip(center_id, *, release_check_report=None) -> dict
verify_archive(center_id, *, strict=True) -> dict
export_handoff(center_id, *, archive_verification_report=None) -> dict
build_handoff_zip(center_id, *, archive_verification_report=None) -> dict
verify_handoff(center_id, *, strict=True) -> dict
```

### 6.2 已签核状态判断

不能只看 `signoff.json` 是否存在。

必须读取：

```text
signoff-history.jsonl
```

如果 latest valid event 是 `signoff_created`，状态就是 signed。

如果 latest valid event 是 `signoff_reset`，状态就是 unsigned / reset。

如果 history hash chain broken：

- `status = corrupted`
- refresh/export/zip/signoff/GA gate 全部失败
- 只能人工处理，不自动修复

### 6.3 签核前置条件

`signoff()` 必须检查：

1. UCC ZIP 存在。
2. UCC verification report 存在。
3. Runtime verifier 重新跑当前 UCC ZIP。
4. 外部 verification report 和 runtime verifier 绑定：
   - `zip_sha256`
   - `zip_size_bytes`
   - `manifest_hash`
   - `package_type`
   - `status == passed`
5. Readiness overall 是 `ready`。
6. `blocker_count == 0`。
7. 没有 unsupported safe action 被标成 completed。
8. release-check report 如果提供，hash 进入 signoff source。
9. 人工字段脱敏。

### 6.4 签核后禁止动作

签核后以下操作必须 409：

- `refresh`
- `run-safe`
- `export`
- `zip`
- 重新 `signoff`
- 改写 center metadata
- 删除 center

允许：

- `status`
- `report`
- `verify`
- `export_archive`
- `build_archive_zip`
- `verify_archive`
- `export_handoff`
- `build_handoff_zip`
- `verify_handoff`
- `create_change_request`
- `approve_change_request`
- `reset_signoff`

### 6.5 reset 规则

`reset_signoff()` 必须：

1. 要求 `change_request_id`。
2. Change Request 必须存在。
3. CR integrity OK。
4. CR status 是 `approved`。
5. CR 没有被 applied。
6. CR source 绑定当前 latest signoff。
7. reset 成功后：
   - 写 history event `signoff_reset`
   - 标记 CR `applied=true`
   - 记录 `applied_signoff_reset_hash`
   - 删除或保留 `signoff.json` 都可以，但状态必须由 history 决定

### 6.6 archive 构建规则

archive 必须在 signed 状态下构建。

构建前重新校验：

- `signoff.json` integrity。
- `signoff-history.jsonl` chain。
- latest history event 绑定当前 signoff。
- 当前 UCC ZIP 和 verification report 仍匹配 signoff source。
- 当前 UCC report/readiness/evidence graph hash 仍匹配 signoff source。
- 如果任何底层 evidence 已变化导致 runtime verifier 失败，archive 构建必须 409。

### 6.7 handoff 构建规则

handoff 是给外部 reviewer / 业务负责人看的“最终移交包”。

它必须基于：

- passed archive verification report。
- current archive ZIP。
- current signoff。
- current readiness summary。

handoff 不应包含所有底层大 ZIP，避免包无限膨胀。它应该包含：

- summary。
- verification instructions。
- fingerprints。
- package index。
- blockers/manual actions 摘要。
- archive verification report。

如要获取底层证据，按 package index 找原始包。

### 7.3 CLI 错误语义

- payload 缺字段：400 风格，CLI exit 1。
- signed immutable violation：409 风格，CLI exit 1。
- stale source：409 风格，CLI exit 1。
- verification failed：exit 1。
- unsafe ZIP：exit 1。

错误文本统一：

```text
error: Unified Command Center is signed. Create and approve a Change Request before modifying it.
error: Unified Command Center signoff source is stale. Reset signoff with an approved Change Request before rebuilding.
error: Unified Command Center archive verification failed.
```

## 10. Verifier 设计

### 10.1 Archive verifier 必查

`verify-unified-command-center-archive-package` 必须检查：

1. ZIP exists。
2. ZIP fixed allow-list。
3. duplicate entry。
4. raw backslash entry。
5. dangerous path。
6. `.musicforge/` case-insensitive 禁止。
7. nested ZIP 禁止，除非明确 allow-list；v11.1 建议禁止。
8. manifest package_type。
9. manifest files fixed allow-list。
10. file hash / size。
11. signoff package_type。
12. signoff integrity。
13. signoff history hash chain。
14. latest history event 是 signoff_created。
15. signoff source 与 UCC ZIP + verification report 匹配。
16. UCC verification report package_type。
17. UCC verification report status passed。
18. UCC verification report integrity。
19. readiness hash 匹配。
20. redaction scan。

### 10.2 Handoff verifier 必查

`verify-unified-command-center-handoff-package` 必须检查：

1. ZIP fixed allow-list。
2. duplicate / dangerous / backslash / `.musicforge/`。
3. manifest package_type。
4. handoff manifest integrity。
5. archive verification report package_type。
6. archive verification status passed。
7. handoff source 绑定 archive ZIP sha / manifest hash / archive verification hash。
8. package index 和 manifest files 一致。
9. executive summary 不含敏感信息。
10. reviewer instructions 不含本机 token 路径。
11. redaction scan。

### 10.3 不允许的自证路径

Archive verifier 不能只信：

- archive manifest 里写的 signoff hash。
- signoff 自己写的 readiness。
- UCC report 自己写的 status。
- verification report 里的 status 而不校验 ZIP。

Handoff verifier 不能只信：

- handoff manifest 自己写 archive passed。
- executive summary 自己写 signed。
- package index 自己写 hash。

必须从真实文件、真实 ZIP、真实 external verification report 反查。

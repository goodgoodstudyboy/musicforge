# v14.0.0 MusicForge 领域纵向迁移、兼容层清退与接口收敛施工图

日期：2026-07-15

当前稳定基线：v13.8.0

基线提交：`98a7b25cbe505dca9f2f3ab946951adf3ebd1b2a`

版本性质：架构主版本，不新增产品功能

目标版本：v14.0.0

## 1. 文档目的

v13.8.0 已经解决了 MusicForge 继续无边界增长的问题，但还没有完成全部历史代码的领域迁移。

v14.0.0 的任务不是继续增加新的 Board、Center、Archive、Verifier 或 Gate，而是把 v13 已建立的模块化单体架构落实到 creation、studio、quality、delivery、trust 和 program 六个真实领域，清除 active 生产路径对 compatibility 代码的依赖，并把接口层从机械拆文件改成按 use case 组织。

本施工图必须作为一个完整 Release Train 执行。开发可以按阶段提交，但不得在中间阶段声称兼容层已经退休，也不得在所有最终门禁通过前创建 v14.0.0 tag 或 GitHub Release。

## 2. Reviewer 结论与当前基线

v13.8.0 可以作为 v14 开发基线，当前没有架构阻断级 P1：

- active 生产依赖环为 0。

- 未批准 dependency exception 为 0。
- Program active -> compatibility 依赖为 0。
- Verification、Lifecycle、Persistence、Evidence Graph 和 Policy Engine 已成为共享平台能力。
- 架构、Capability、Interface、Evidence Policy 和 Kernel 定向测试通过。
- Windows/Linux CI、active/legacy test、security、nightly 和 final-SHA reviewer evidence 已建立。

## 3. v14.0.0 一句话目标

让每一条当前生产调用链都遵循：

```text
interfaces -> application -> domains -> platform
```

并使：

```text
active_to_compatibility_import_count == 0
```

历史兼容实现可以作为 archive-only 代码继续由 legacy/full/nightly 验证，但 current production、latest、ga、v14 和 security profile 不得再调用它们。

## 4. 版本边界

### 4.1 本版必须完成

- 六个 bounded context 都拥有真实业务实现，不再是空目录占位。
- active compatibility import edges 从 224 降为 0。
- `application/legacy_dependencies` 不再被 active 代码使用，并在确认零引用后删除。
- flat compatibility 模块不再承载 active implementation。
- CLI/API/Web 只调用 application command/query/service，不直接装配或修改 Store。
- active interface 中消除 `part_###.py`、`import *`、动态 symbol forwarding 和运行时 Store mutation。
- 将 GA、Release signoff 等超大 active orchestration 拆成命名明确的 use cases 和 policies。
- capability registry 覆盖全部 current evidence/gate capability。
- coverage、typing、module/function size 和 compatibility retirement 建立硬 ratchet。
- 保持所有公开 CLI/API/Web 行为兼容，除非本施工图明确列为 v14 breaking change。
- 保持 signed evidence、ZIP、history、binding 和 migration evidence 的字节与语义兼容。

### 4.2 本版禁止

- 新增第七个 bounded context。
- 新增新的全局 Board、Center、Hub、Vault 或 Command Center 产品层。
- 新增 package-internal self-attestation。
- 用移动文件、改目录名或增加 facade 冒充迁移完成。
- 为了指标删除安全测试、legacy tests 或 verifier blocker。
- 将 blocker 降级为 warning。
- 引入微服务、网络消息队列、分布式事务或远程数据库。
- 建立包含几十个 hook 的万能 BaseStore、BaseVerifier 或 BaseWorkflow。
- 在 route/CLI handler 中直接写私有 JSON、JSONL、SQLite 或 ZIP。
- 自动 approve、signoff、reset、publish、upload 或接受人工证据。

### 4.3 本版非目标

- 不新增音乐生成、编辑、发行或信任治理产品功能。
- 不重新设计 UI 视觉系统。
- 不改变 Provider 或 Renderer 协议。
- 不强制删除所有历史源文件；目标是 active 路径归零和历史代码隔离。
- 不重写已签核证据。

## 6. 依赖规则

### 6.1 生产依赖方向

```text
interfaces -> application -> domains -> platform
```

允许：

- interface 调用 application public command/query。
- application 编排一个或多个 domain public service。
- domain 使用 platform contract、verification、lifecycle、persistence 和 policy。
- composition root 创建 concrete repository/store，再注入 application service。

禁止：

- interface route/handler 直接获取具体 Store。
- interface property 在读取时修改 Store 依赖。
- domain 导入另一个 domain 的私有模块。
- domain/application 导入 CLI、Server、Web、release_check 或 compat。
- platform 导入 application/domain/interface。
- active code使用 `globals().update()` 转发公开 API。
- active interface 使用 `from ... import *`。
- active代码通过 `_resolve_symbol()` 隐藏依赖。

### 6.2 唯一 composition root

新增或明确一个受架构门禁保护的 composition root，例如：

```text
song_agent/application/bootstrap/container.py
```

职责仅限：

- 创建 repository、domain service、application service。
- 完成显式 constructor injection。
- 暴露 typed service registry。
- 管理进程级共享资源生命周期。

禁止：

- 在 property getter 中重新绑定依赖。
- 通过 service locator 字符串解析任意 implementation。
- 在 composition root 中写业务判断。

## 7. 迁移完成的定义

一个模块只有同时满足以下条件，才可以标记为 migrated：

1. 真实 implementation 位于对应 domain 或 application 目录。
2. current interface 调用 application public API。
3. implementation 不导入 flat compatibility facade。
4. capability/route/command/policy metadata 已更新。
5. 旧实现与新实现具有 differential contract tests。
6. ZIP/security/signoff/reset blocker 行为无降级。
7. active import edge 数量实际下降。
8. compatibility facade 只做显式、静态、无逻辑转发，或已删除。
9. legacy/full/nightly 仍可读取历史 evidence。
10. 该阶段 reviewer report 没有 P1/P2。

以下情况不算迁移：

- 新文件只 import 旧 Store 再导出。
- 将一个大文件机械切成 `part_001.py` 到 `part_020.py`。
- 用 `globals().update()`、`import *` 或动态字符串 resolver 复制旧 API。
- 修改 architecture baseline 将新违规列为允许。
- 仅让测试改为 import 新路径，但生产调用仍走旧实现。

## 9. Verification 与安全不变量

任何迁移后的 package verifier 必须继续覆盖：

- 固定 allow-list 或受限 pattern allow-list。
- duplicate ZIP entry。
- raw central-directory backslash entry。
- absolute、parent traversal、drive、UNC、control-character path。
- case-insensitive `.musicforge/` 禁止规则。
- symlink/non-regular entry。
- trailing bytes。
- nested ZIP allow-list、depth、size 和 extraction containment。
- manifest package type、integrity、file hash、size、entry count。
- public redaction。
- external verification report package type/integrity/current ZIP binding。
- external signoff/binding/history/checkpoint/receipt proof。
- runtime source verification。
- generation/current identity。

禁止 verifier 只验证 ZIP 内 JSON 自洽。

## 10. Lifecycle 不变量

所有 signoff/reset/archive workflow 必须继续满足：

- signoff history hash chain 可重建。
- signoff binding 在签核时独立落盘。
- 删除 signoff 文件不能降级成 unsigned。
- signed 后 refresh/mutation/export recompute 被阻断。
- archive 只复制 frozen snapshot。
- reset 需要 approved CR。
- CR action、target、source、request hash、approval hash 完整绑定。
- CR single-use。
- reset 后旧 generation 立即失效。
- successor signoff 只能建立在合法 reset 后。

## 11. Persistence 与迁移不变量

- SQLite 继续只保存 mutable index/workflow state。
- signed evidence、JSONL history、bindings、ZIP 继续是可离线验证的文件证据。
- verifier 不得依赖 SQLite 才能验证 package。
- 多文件写入继续使用 generation + atomic current pointer。
- cross-process 写入继续使用 WorkspaceLock。
- migration 先 verified backup，再 apply，再 verify，再 rollback rehearsal。
- 历史 signed evidence 不原地重写。
- rollback 必须 byte-identical。

## 14. Differential Test 要求

每个迁移 wave 至少包含：

1. v13 fixture 输入旧实现与新实现。
2. 比较公开 JSON/ZIP/CLI/API 输出。
3. 比较 blocker ids 和 status。
4. 比较 signed/history/binding hash 语义。
5. 比较 stale、tamper、full-resign、wrong package type、wrong identity。
6. 比较 Windows/POSIX path redaction。
7. 比较 migration 前后读取结果。

允许差异必须写入 versioned compatibility decision，不得用宽泛 normalize 隐藏。

## 15. 自动 Review 与提交协议

每个 Phase 必须执行以下流水线：

1. 实现当前 Phase，禁止夹带下一 Phase。
2. 运行定向 unit/contract/integration/security tests。
3. 运行 architecture、mypy、Ruff、marker manifest、coverage ratchet。
4. 运行对应 v14 smoke。
5. 生成 `runs/v14-review/phase-XX-review.json`。
6. 自动 reviewer 检查 diff、依赖边、security blocker、contract diff、测试遗漏。
7. P1/P2 必须修复并复跑；P3 必须记录 owner 和 deadline。
8. `git diff --check`。
9. 确认没有运行产物、secret、本机绝对路径。
10. 提交当前 Phase。
11. 提交后重跑架构与当前 profile。
12. 只有通过后才能进入下一 Phase。

禁止把十个 Phase 压成一个不可审查提交。

## 21. Stop Conditions

出现以下任一情况立即停止当前 Phase，不提交、不继续：

- public CLI/API contract 无计划变化。
- verifier blocker 减少或 stale/tamper 攻击通过。
- signed evidence 被原地重写。
- migration 无 verified backup 或 rollback 不一致。
- architecture edge 通过 baseline 放宽而不是代码迁移下降。
- current profile 引入 legacy callable。
- interface 为了迁移继续增加 Store wiring。
- coverage/typing 范围缩小。
- 测试通过依赖本机绝对路径、真实 token 或特定 GitHub IP。
- reviewer package 出现 secret、本机路径或 pending 状态。

## 22. 回滚方案

- v13.8.0 tag 是代码回滚基线。
- v14 mutable-state migration 必须先创建 verified backup。
- 每个 Phase 保持独立提交，可逐阶段 revert，但不得使用 destructive reset 覆盖用户数据。
- signed evidence 和历史 ZIP 不参与原地迁移。
- schema migration 必须 idempotent。
- rollback rehearsal 必须从实际非空 workspace 执行。
- rollback 后文件 hash、数据库关键索引和 current pointer 必须一致。

## 25. 给开发的话

这不是一次目录整理，也不是继续增加功能的版本。

请先完成 Phase 0 的可复算基线，再按 creation/studio、quality、delivery、trust、program 的依赖顺序迁移。每一阶段必须让 active compatibility edge 实际下降，并通过 differential/security tests；只增加 wrapper、part 文件或 baseline allow-list 不算完成。

接口层的目标是调用 application use case，而不是把旧 Store wiring 换一个文件名。领域迁移的目标是把行为所有权迁入 domain，而不是复制实现。兼容层的目标是 archive-only 和零 active caller，而不是隐藏统计。

每个 Phase 做完后自动测试、自动 review、修完 P1/P2、提交，再进入下一阶段。最终 v14.0.0 只有在 active compatibility edges 为 0、current profiles 无 legacy callable、迁移可回滚、final-SHA CI 和 reviewer package 全部通过时才允许发布。

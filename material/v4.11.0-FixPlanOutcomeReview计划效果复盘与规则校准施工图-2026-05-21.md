# v4.11.0 Fix Plan Outcome Review 计划效果复盘与规则校准施工图

日期：2026-05-21

当前稳定基线：v4.10.1

目标版本：v4.11.0

建议版本主题：Fix Plan Outcome Review / 计划效果复盘与规则校准

---

## 1. 背景

v4.7 到 v4.10 已经把 MusicForge 的验收修复闭环推进到比较完整的状态：

```text
Acceptance Suite
  -> Acceptance Analytics
  -> Acceptance Fix Sprint
  -> Recheck / Delta / Closeout
  -> Acceptance Knowledge Base
  -> Knowledge-assisted Fix Plan
  -> Fix Sprint from Plan
```

v4.10.1 之后，系统已经能基于 fresh analytics report 和 Acceptance KB 创建 Fix Plan，并且一个 Fix Plan 只能创建一个 Fix Sprint，避免了重复执行和 evidence 覆盖。

但现在还缺一个关键问题：

```text
这个 Fix Plan 到底有没有用？
```

现在能回答的是：

- 这个计划参考了哪些 KB。
- 计划创建了哪个 Fix Sprint。
- Sprint 最后有没有 close。
- KB 后续能沉淀修复经验。

还不能系统回答：

- 高分 planned item 是否真的带来了更好 delta。
- KB evidence 是否真的帮助了修复。
- 哪些 planned item 被执行后无效。
- 哪些 warning 最终变成真实风险。
- Planning Score 排序是否合理。
- Fix Plan 是否应该作为 Release Signoff 的强 evidence。
- 下一次计划评分规则应该怎么校准。

v4.11.0 要补的是这层“计划复盘”。

---

## 2. 一句话目标

> v4.11.0 要在 Fix Plan 创建并执行完 Fix Sprint 后，生成可审计的 Outcome Review Report，评估计划项命中率、KB 证据有效性、排序准确性和残留风险，并把这个复盘接入 Studio、Export、Release Signoff 和 release-check。

---

## 3. 版本定位

v4.11.0 不是新一轮自动修复，也不是 provider 评审。

它是一个质量治理层：

```text
Fix Plan
  -> Fix Sprint
  -> Delta / Closeout
  -> Outcome Review
  -> KB / Export / Signoff evidence
```

开发时要坚持三条边界：

1. 只复盘，不自动修改音乐。
2. 只给规则校准建议，不自动改 Planning Score 规则。
3. 只使用本地 deterministic 数据，不调用 provider，不用向量库，不引入外部服务。

---

## 4. 本版不做什么

明确不做：

- 不自动创建新的 ReviewTask。
- 不自动创建新的 Fix Plan。
- 不自动创建新的 Fix Sprint。
- 不自动修改 Acceptance KB entry。
- 不自动修改 Planning Score 规则。
- 不调用 provider judge。
- 不做自然语言 LLM 总结。
- 不把完整人工 review notes、provider raw response、本机路径、token 写入报告。
- 不把 hidden KB entry 的完整内容写进 export。
- 不把 synthetic review 当成人工复盘证据。

可以做：

- 计算 deterministic outcome score。
- 给出 calibration hints。
- 生成 follow-up 建议，但必须是手动触发。
- 在 Studio 里展示对比、证据和风险。
- 在 release signoff gate 中作为可选或必选 evidence。

---

## 5. 为什么 v4.11.0 现在该做

### 5.1 v4.10 已经进入“计划层”

v4.10 之前，系统更多是在做执行和记录：

```text
发现问题 -> 建 Sprint -> 修 -> 复验 -> 记知识
```

v4.10 开始，系统会根据历史知识主动生成计划：

```text
历史知识 + 当前分析 -> Fix Plan -> Sprint
```

一旦系统开始“建议怎么修”，就必须能回头检查“建议准不准”。

### 5.2 不复盘会导致 KB 越积越乱

KB entry 记录的是历史修复是否有效，但 Fix Plan 使用 KB 时会发生二次组合：

- 一个 planned item 可能命中多个 KB entry。
- 一个 Sprint 可能执行多个 planned item。
- 一次 delta improvement 可能来自部分 item，而不是整个 plan。

如果不做 Outcome Review，后续系统只能知道“有历史知识”，不知道“这个知识在计划里被用得好不好”。

### 5.3 v5 前必须把质量闭环做硬

后面如果进入真实音频、vocal、mixing，错误成本会更高。

真实音频能力上线前，必须先让系统具备：

- 能验收。
- 能发现问题。
- 能计划修复。
- 能执行修复。
- 能复盘计划是否有效。
- 能把复盘结果沉淀成下一次决策依据。

v4.11.0 就是 v5 前的最后一层质量治理。

## 6. 核心概念

### 6.1 Fix Plan Outcome Review

Fix Plan Outcome Review 是对一个 Fix Plan 执行结果的复盘报告。

它绑定：

- Fix Plan。
- 由该 Fix Plan 创建的 Fix Sprint。
- Fix Sprint items。
- Fix Sprint delta report。
- Fix Sprint closeout report。
- 相关 KB entries。
- 可选 post-KB report。

它回答：

- 计划是否执行完成。
- 计划排序是否合理。
- KB evidence 是否有帮助。
- 哪些 planned item 有效。
- 哪些 planned item 无效或证据不足。
- 哪些风险 warning 被验证。
- 下一次计划规则该注意什么。

### 6.2 Planned Item Outcome

每个 planned item 都要生成一个 item outcome。

字段包括：

- planned_item_id
- recommendation_id
- planning_score
- original_priority_rank
- fix_item_id
- fix_item_status
- linked_review_task_ids
- task_statuses
- knowledge_entry_ids
- knowledge_match_count
- expected_risk
- observed_outcome_status
- observed_effectiveness_score
- evidence_status
- delta_summary
- warnings

### 6.3 Evidence Status

每个 planned item 的 KB evidence 需要被归类：

```text
supported
mixed
unsupported
unknown
not_executed
```

建议判定：

- `supported`：item 关闭后 delta improved，相关 KB entry 也显示 effective 或 mixed positive。
- `mixed`：Sprint 有改善但 item 有 waiver、force close、synthetic review 或 issue delta 不明确。
- `unsupported`：item 执行后 delta regressed 或 item 未解决。
- `unknown`：缺 delta、缺 closeout、缺 recheck。
- `not_executed`：planned item 没有对应 active fix item 或没有执行证据。

### 6.4 Planning Calibration Hint

Calibration Hint 是 deterministic 的规则建议。

它不修改系统规则，只写报告。

示例：

```json
{
  "hint_id": "afpch-000001",
  "type": "score_adjustment_hint",
  "issue_type": "hook",
  "style": "rap beat",
  "current_signal": "history_mixed_effectiveness",
  "observed_outcome": "supported",
  "suggestion": "Mixed hook history for rap beat improved after targeted manual recheck. Keep medium risk but avoid over-penalizing if manual recheck is required.",
  "confidence": "medium",
  "manual_required": true
}
```

### 6.5 Plan Review Readiness

Outcome Review 有 readiness：

```text
ready
warning
blocked
stale
missing
```

含义：

- `ready`：Sprint closed，delta/closeout/source hash 都可验证。
- `warning`：可复盘，但存在 force close、waiver、synthetic review、KB 未刷新等问题。
- `blocked`：Sprint 未 close、缺 delta、缺 closeout、plan 未 used。
- `stale`：plan、sprint、delta、closeout 或 KB source 已变化。
- `missing`：没有 review。

新增模块建议：


```text

    source-summary.json
    item-outcomes.json

```

为什么不直接写到 `.musicforge/fix-plans/<plan-id>/`？

- Fix Plan 是计划本体。
- Outcome Review 是执行后复盘，生命周期不同。
- 未来可能允许同一个 plan 的只读 historical review 保留，不应污染 plan 原始 evidence。
- 列表和 export 更容易统一。

但 Fix Plan detail API 可以附带 latest outcome review summary。

## 11. Source Hash 规则

Outcome Review 必须有严格 source hash。

source hash 绑定：

- rules version。
- Fix Plan sanitized payload。
- Fix Plan source hash。
- Fix Sprint sanitized payload。
- Fix Sprint source payload。
- Fix items sanitized payload。
- delta report core payload。
- closeout report core payload。
- referenced KB entry summaries。

建议：

```python
source_payload = {
    "rules_version": ACCEPTANCE_FIX_PLAN_REVIEW_RULES_VERSION,
    "plan": fix_plan_summary_with_hash,
    "fix_sprint": fix_sprint_summary_with_hash,
    "items": item_payload_hashes,
    "delta": delta_source,
    "closeout": closeout_source,
    "kb_entry_hashes": kb_entry_hashes,
}
source_hash = stable_hash(source_payload)
```

### 11.1 Stale 条件

任一条件成立，report stale：

- Fix Plan 不存在。
- Fix Plan 本身 stale。
- Fix Plan source hash 改变。
- Fix Sprint 不存在。
- Fix Sprint 不是该 Fix Plan 创建的。
- Fix Sprint source 中 `fix_plan_source_hash` 与当前 plan 不一致。
- Fix Sprint items 改变。
- delta report 改变。
- closeout report 改变。
- referenced KB entry summary 改变。
- closeout 被 reset 或重写。

### 11.2 Pending 和 Blocked

以下情况不生成正式 `ready` review：

- plan.status 不是 `used`。
- plan.execution 没有 `created_fix_sprint_id`。
- Sprint 未 close。
- 缺 delta report。
- 缺 closeout report。

API 可以返回 409，错误文案要明确。

推荐文案：

```text
Acceptance Fix Plan Outcome Review requires a used plan with a closed Fix Sprint, delta report, and closeout report.
```

## 12. 评分规则

### 12.1 Plan Effectiveness Score

范围 0 到 100。

建议规则：

```text
base = 50

+20 if sprint delta improved
+10 if after_readiness is ready or releasable
+10 if resolved_item_count == planned_item_count
+8  if rating_delta >= 2
+5  if rating_delta >= 1
+8  if issue_count_delta <= -2
+5  if issue_count_delta == -1
+5  if accepted_delta > 0

-15 if sprint delta regressed
-12 if open_item_count > 0
-8  if waived_item_count > 0
-10 if closeout forced
-10 if synthetic_only
-8  if KB evidence missing for all items
-8  if high planning score item unsupported
```

最后 clamp 到 0 到 100。

### 12.2 Ranking Alignment Score

衡量计划排序是否合理。

简单 deterministic 做法：

1. 按 planning_score 得到 planned rank。
2. 按 observed_effectiveness_score 得到 observed rank。
3. 对每个 executed item 计算 rank distance。
4. 平均距离越小得分越高。

```text
alignment = 100 - average_rank_distance * 20
```

少于 2 个 item 时：

```text
ranking_alignment_score = null
```

### 12.3 KB Evidence Helpfulness

枚举：

```text
helpful
mixed_positive
neutral
misleading
insufficient
```

判定建议：

- `helpful`：有 KB match 的 item 大多 supported，且 no-kb item 没有更明显改善。
- `mixed_positive`：有 KB match 的 item 有改善，但存在 waiver 或部分 unknown。
- `neutral`：KB match 与 outcome 没有明显关系。
- `misleading`：KB match 高但 outcome unsupported 或 regressed。
- `insufficient`：KB match 太少。

## 13. Calibration Hints

Outcome Review 不改规则，只给提示。

### 13.1 Hint 类型

```text
score_adjustment_hint
risk_warning_hint
kb_match_quality_hint
manual_recheck_hint
waiver_policy_hint
synthetic_review_hint
issue_pattern_hint
style_pattern_hint
```

### 13.2 生成规则

示例：

- high score item unsupported：
  - `score_adjustment_hint`
  - 提醒该 issue/style 的 score 可能过高。

- no_kb_history item improved：
  - `kb_match_quality_hint`
  - 提醒没有历史时也可能有效，不要过度惩罚。

- mixed history item improved：
  - `risk_warning_hint`
  - 提醒 mixed risk 应保留，但不一定阻断。

- waiver-heavy item closeout passed：
  - `waiver_policy_hint`
  - 提醒 closeout 不能只看 passed，要看 waiver。

- synthetic-only recheck improved：
  - `synthetic_review_hint`
  - 提醒不能作为 release-ready 强证据。

### 13.3 Hint 不进入强门禁

Calibration Hint 不能直接阻断 Release Signoff。

它只能作为 warning evidence。

Release Signoff 如果设置：

```json
{
  "require_acceptance_fix_plan_review": true
}
```

只要求：

- review 存在。
- review 非 stale。
- readiness 不是 blocked。

不要求 score 必须大于某个阈值。

## 14. API 设计

### 14.1 Fix Plan 下的 Outcome Review

```text
GET  /api/acceptance/fix-plans/<plan-id>/outcome-review
POST /api/acceptance/fix-plans/<plan-id>/outcome-review/refresh
```

GET：

- 如果已有 review，返回 latest review。
- 如果没有，返回 summary status `missing`。
- 不自动创建。

POST refresh：

- 创建或刷新 review。
- 必须 plan used。
- 必须 sprint closed。
- 必须有 delta/closeout。
- 失败返回 409，不写半成品。

响应：

```json
{
  "ok": true,
  "outcome_review": {},
  "summary": {}
}
```

### 14.2 全局 Review 列表

```text
GET /api/acceptance/fix-plan-reviews
GET /api/acceptance/fix-plan-reviews/<review-id>
POST /api/acceptance/fix-plan-reviews/<review-id>/refresh
POST /api/acceptance/fix-plan-reviews/<review-id>/archive
```

支持 query：

```text
?release_id=rel-000001
?project_id=proj-000001
?status=ready
?include_archived=1
```

### 14.3 可选 Follow-up 建议预览

本版可以只做 preview，不创建实体：

```text
POST /api/acceptance/fix-plan-reviews/<review-id>/follow-up-preview
```

返回：

```json
{
  "manual_required": true,
  "suggested_next_steps": [
    {
      "type": "create_new_fix_plan",
      "reason": "Unsupported high-score hook item remains unresolved.",
      "target": {}

}
```

如果实现成本高，可以先不做这个 API，把建议放在 report 里。

```json
    "review_id": "afpr-000001",
    "status": "ready",
    "plan_effectiveness_score": 78

```

Sprint 的 source 是执行来源。

Outcome Review 是执行后证据。

## 18. Acceptance KB 集成

### 18.1 KB entry source 增强

如果 Fix Sprint 来源是 Fix Plan，KB entry 生成时建议把以下 summary 写进 source：

```json
{
  "fix_plan_id": "afp-000001",
  "planned_item_ids": ["afpi-000001"],
  "fix_plan_source_hash": "sha256..."
}
```

不要写完整 plan。

### 18.2 Outcome Review 查找 KB entries

Outcome Review 可以通过两种方式找 KB：

1. 读取 plan.planned_items[].knowledge.top_entry_ids，复盘“计划时参考的 KB”。
2. 搜索 KB entries 的 source.fix_sprint_id，复盘“执行后生成的新 KB”。

两者都要区分：

- planned KB evidence
- generated KB evidence

### 18.3 KB 未刷新后的 warning

如果 Sprint close 后还没有刷新 KB：

```text
kb_not_refreshed_after_closeout
```

这不阻断 Outcome Review，但会让 status 变成 `warning`。

- Release package 不需要完整过程明细。
- 完整报告留在本地 workspace。

## 20. Release Signoff Gate

Release Signoff payload 新增可选：

```json
{
  "require_acceptance_fix_plan_review": true,
  "acceptance_fix_plan_review_id": "afpr-000001"
}
```

### 20.1 Gate 规则

如果 `require_acceptance_fix_plan_review=true`：

- 必须找到 review。
- review 不能 stale。
- review.status 不能是 `blocked`、`archived`。
- review.readiness 不能是 `blocked`。
- review 必须绑定当前 release scope，或绑定该 release 内 project。

不要求：

- plan_effectiveness_score 大于 80。
- kb_evidence_helpfulness 必须 helpful。

这些只作为 warning。

### 20.2 Signoff Evidence

写入 release-signoff.json：

```json
{
  "acceptance_gate": {
    "acceptance_fix_plan_review": {
      "status": "passed",
      "review_id": "afpr-000001",
      "plan_id": "afp-000001",
      "plan_effectiveness_score": 78,
      "kb_evidence_helpfulness": "mixed_positive",
      "stale": false
    }
  }
}
```

## 21. 安全和脱敏

必须复用：

```python
sanitize_metadata()
sanitize_sensitive_text()
```

报告中禁止出现：

- `sk-...`
- GitHub token。
- Bearer token。
- Windows path。
- UNC path。
- provider raw response。
- full review notes。
- renderer source path。
- local audio path。

### 21.1 文本长度限制

建议：

- planning_reason 最多 500 字符。
- item outcome note summary 最多 300 字符。
- calibration hint suggestion 最多 400 字符。
- warnings 每条最多 180 字符。

### 21.2 Hidden KB

如果 plan 显式 include hidden KB：

- Outcome Review 可以显示 hidden entry id。
- 可以显示 hidden status。
- 可以显示脱敏 summary。
- 不能输出隐藏条目的完整 source/content。

## 22. 并发和原子写

Store 要有 root-level RLock。

写入顺序：

1. reserve review dir。
2. build report in memory。
3. write outcome-review.json。
4. write item-outcomes.json。
5. write source-summary.json。
6. append event。

如果中途失败：

- 未写 outcome-review.json 的占位目录可以清理。
- 已写完整 review 的目录不能删除。

读取时：

- 跳过损坏 JSON。
- list 不因单个坏 report 失败。
- detail 读到坏 JSON 返回明确错误。

## 28. 风险清单

### 28.1 Planned item 到 fix item 映射错误

风险：

- 一个 Fix Sprint item 缺 planned_item_id。
- planned_item_id 重复。
- item 顺序变化导致错配。

要求：

- 只按 id/hash 匹配。
- 不按数组下标匹配。
- hash 不一致就 stale。

### 28.2 把 Sprint 整体 delta 错算到每个 item

风险：

- Sprint improved，但某个 item 其实没有贡献。

处理：

- item outcome 可以使用 sprint delta，但必须标注 confidence。
- 如果缺 song/issue level delta，只能 `mixed` 或 `unknown`，不能强行 `supported`。

### 28.3 Force close 被当成成功

风险：

- forced close 的 Sprint 被算成高 effectiveness。

处理：

- force close 必须扣分。
- warning 必须进入 summary。
- signoff 只能 warning，不算强 evidence。

### 28.4 Synthetic review 被当成人工验收

风险：

- auto-review 结果进入 release evidence。

处理：

- synthetic-only 必须 warning。
- require gate 可通过或 warning由业务决定，但 report 不能写 manual confirmed。

### 28.5 KB entry 变化后 review 未 stale

风险：

- hidden/unhidden 或 refresh 改变 KB summary，review 仍被当作 valid。

处理：

- source hash 绑定 referenced KB entry summary。
- hidden 状态也参与 hash。

### 28.6 Export 泄露本机信息

风险：

- item outcomes 里带出本机路径或 review 原文。

处理：

- Export 只写 summary。
- report-out 也要 sanitize。
- release-check 注入 token/path 污染。

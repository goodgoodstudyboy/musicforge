# v9.9.0 Trust Operations Final Readiness Certificate 最终准出证书与交付移交包施工图

日期：2026-06-23

基线提交：92209025d1e64d247b718b8f1b12cffa5e701871  
执行角色：开发  
Reviewer 角色：规划、风险边界、验收审查

## 1. 版本定位

v9.0 到 v9.8 已经把 Trust Operations 的核心证据链做得很完整：

- v9.0 Trust Operations Hub
- v9.1 Delivery evidence / Runbook
- v9.2 Incident Response
- v9.3 Incident Knowledge / Regression Guards
- v9.4 Control Catalog / Assessment
- v9.5 Control Signoff
- v9.6 Continuous Assurance
- v9.7 Assurance Watch
- v9.8 Assurance Watch Signoff

这些能力已经能证明单个治理维度是否 ready，但还缺最后一层“给人看的最终准出证书”和“给接手方/审计方的交付移交包”。

v9.9.0 的目标：

> 把 Hub、Delivery、Incident、Knowledge、Control、Continuous Assurance、Assurance Watch、Watch Signoff 这些已经独立验证过的证据，汇总成一个 Final Readiness Certificate 和一个不可变 Handoff Pack，作为 v10.0 GA/LTS 前的最终收口证据。

这版不是再做一个局部 verifier，而是做 Trust Operations 的最终准出聚合层。

## 2. 为什么现在做这一版

目前系统已经很强，但使用者仍要打开很多独立包：

- Hub ZIP
- Hub verification report
- Delivery verification reports
- Incident ZIP / verification
- Incident Knowledge ZIP / verification
- Control assessment ZIP / verification
- Control Signoff Archive / verification
- Continuous Assurance ZIP / verification
- Assurance Watch ZIP / verification
- Assurance Watch Signoff Archive / verification

这对开发和 reviewer 是能接受的，但对最终移交和长期维护并不友好。

v9.9 要解决的问题：

- 一眼知道当前 Trust Operations 是否能准出。
- 一眼知道哪些证据是必需、哪些是 optional。
- 一眼知道每份证据的 package hash / manifest hash / verification hash。
- 离线 verifier 能独立复核最终证书是否绑定当前外部证据。
- 最终移交包不能靠内部 JSON 自证。
- 最终移交包签核后不能静默重建。

这会让 v10.0 可以聚焦“稳定版发布和文档收口”，而不是继续补证据链缺口。

## 3. 本版一句话

> v9.9.0 = Trust Operations Final Readiness Certificate + Handoff Pack + Handoff verifier + Hub final gate。

## 4. 本版不做什么

明确不做：

- 不新增音乐生成能力。
- 不新增 provider 调用。
- 不新增平台 API 对接。
- 不替代 v9.0-v9.8 的各自 verifier。
- 不把所有 nested package 原样塞进 Final Certificate。
- 不自动 signoff。
- 不自动 reset。
- 不自动 approve Change Request。
- 不做第三方公钥签名。
- 不做 Web 托管发布。
- 不做 v10.0 release。

v9.9 只做最终准出聚合证据和移交包。

报告是机器聚合结果，不能等同签核。

建议 schema：

```json
  "package_type": "musicforge_trust_operations_final_readiness_report",
  "report_id": "tofr-000001",
  "generated_at": "2026-06-23T00:00:00Z",
  "status": "ready",
  "source": {
    "hub_zip_sha256": "...",
    "hub_manifest_hash": "...",
    "hub_verification_report_hash": "...",
    "delivery_verification_set_hash": "...",
    "incident_verification_report_hash": "...",
    "incident_knowledge_verification_report_hash": "...",
    "control_verification_report_hash": "...",
    "control_signoff_verification_report_hash": "...",
    "continuous_assurance_verification_report_hash": "...",
    "assurance_watch_verification_report_hash": "...",
    "assurance_watch_signoff_verification_report_hash": "..."
  },
  "summary": {
    "required_evidence_count": 9,
    "passed_evidence_count": 9,
    "failed_evidence_count": 0,
    "missing_evidence_count": 0,
    "stale_evidence_count": 0,
    "manual_required_count": 0,
    "ready_for_signoff": true
  },
  "rows": [
    {
      "component_type": "hub",
      "component_id": "hub",
      "required": true,
      "status": "passed",
      "package_sha256": "...",
      "manifest_hash": "...",
      "verification_report_hash": "...",
      "blocker_count": 0
    }
  ],
  "blockers": [],
  "warnings": [],
  "integrity_hash": "..."

```

`integrity_hash` 覆盖：

- `status`
- `source`
- `summary`
- `rows`
- `blockers`
- `warnings`

不覆盖：

- `generated_at`
- `integrity_hash`

## 8. Final Readiness Certificate

证书是 public-safe / handoff-safe 的准出摘要。

建议 schema：

```json
{
  "schema_version": 1,
  "package_type": "musicforge_trust_operations_final_readiness_certificate",
  "certificate_id": "tofc-000001",
  "created_at": "2026-06-23T00:00:00Z",
  "status": "ready",
  "readiness_level": "final_ready",
  "source": {
    "report_hash": "...",
    "evidence_index_hash": "...",
    "hub_verification_report_hash": "...",
    "assurance_watch_signoff_verification_report_hash": "..."
  },
  "summary": {
    "ready": true,
    "required_evidence_count": 9,
    "passed_evidence_count": 9,
    "blocking_findings": 0
  },
  "public_summary": {
    "statement": "Trust Operations evidence is final-ready for handoff.",
    "generated_by": "MusicForge",
    "version": "9.9.0"
  },
  "integrity_hash": "..."
}
```

证书不应包含：

- 本机路径。
- token。
- raw provider output。
- reviewer 私密备注。
- `.musicforge` 内部绝对路径。

建议 schema：

```json
  "created_at": "2026-06-23T00:00:00Z",
  "items": [
    {
      "evidence_id": "hub",
      "component_type": "hub",
      "component_id": "hub",
      "required": true,
      "package_type": "musicforge_trust_operations_hub",
      "package_sha256": "...",
      "package_size_bytes": 123,
      "manifest_hash": "...",
      "verification_package_type": "musicforge_trust_operations_hub_verification",
      "verification_report_hash": "...",
      "verification_status": "passed"
    }
  ],
  "summary": {
    "item_count": 9,
    "required_count": 9,
```

- 所有 verification report hash 必须来自外部 report，不允许只靠 handoff ZIP 内部 summary 自证。
- index 里不写本机路径。

## 10. Verification Summaries

Handoff export 里要有：

```text

  delivery-verification-summary.json
  incident-verification-summary.json
  incident-knowledge-verification-summary.json

  control-signoff-verification-summary.json
  continuous-assurance-verification-summary.json
  assurance-watch-verification-summary.json
  assurance-watch-signoff-verification-summary.json
```

每个 summary 必须是从外部 verification report 生成的摘要，不是从 report.source 自己重新拼出来。

每个 summary 至少包括：

```json
{
  "component_type": "assurance_watch_signoff",
  "component_id": "toawq-000001",
  "package_type": "...",
  "status": "passed",
  "zip_sha256": "...",
  "zip_size_bytes": 123,
  "manifest_hash": "...",
  "verification_report_hash": "...",
  "source_hash": "...",
  "integrity_hash": "..."
}
```

Verifier 必须用这些 summary 反查 evidence index 与 final report。

## 12. Handoff History

`final-handoff-history.jsonl` 必须 hash chain。

事件类型：

```text
final_readiness_refreshed
final_certificate_created
final_handoff_signed
final_handoff_exported
final_handoff_zip_built
final_handoff_verified
change_request_created
change_request_approved
final_handoff_reset
```

每个事件：

```json
{
  "event_id": "tofh-000001",
  "event_type": "final_handoff_signed",
  "created_at": "2026-06-23T00:00:00Z",
  "payload": {},
  "payload_hash": "...",
  "previous_event_hash": "...",
  "event_hash": "..."
}
```

Verifier 必须：

- 重建 event chain。
- 校验 payload_hash。
- 校验 signoff event 与 `final-handoff-signoff.json` 字段一致。
- 校验 reset event 与 approved CR 因果绑定。

## 13. Change Request Reset

签核后 reset 必须走 approved CR。

建议 schema：

```json
{
  "schema_version": 1,
  "package_type": "musicforge_trust_operations_final_handoff_change_request",
  "change_request_id": "tofcr-000001",
  "status": "approved",
  "created_at": "...",
  "approved_at": "...",
  "created_by": "developer",
  "approved_by": "reviewer",
  "reason": "Rebuild final handoff after evidence changed.",
  "source": {
    "target_signoff_hash": "..."
  },
  "applied": {
    "applied_at": null,
    "applied_reset_hash": null
  },
  "integrity_hash": "..."
}
```

规则：

- 无 CR 不能 reset。
- draft CR 不能 reset。
- approved CR 只能用一次。
- CR target_signoff_hash 必须匹配当前 signoff。
- reset 后才能重新 refresh/report/export/zip。

### 15.1 verifier 必查

ZIP：

- open OK
- size limit
- uncompressed size limit
- entry count limit
- fixed allow-list
- no duplicate
- raw central directory path check
- no backslash
- no `.musicforge`
- no nested ZIP

Manifest：

- package_type 正确
- manifest integrity OK
- manifest.files 固定结构
- file hash/size 匹配

Final report：

- package_type 正确
- integrity OK
- status ready
- summary ready_for_signoff true
- blockers 为空

Certificate：

- package_type 正确
- integrity OK
- certificate source report hash 匹配 report
- certificate source evidence index hash 匹配 index

Evidence index：

- package_type 正确
- integrity OK
- 所有 required evidence present
- 每条 external verification report hash 匹配
- 多 delivery report 不允许丢第二条

Verification summaries：

- 每个 summary integrity OK
- summary 必须与 external verification report 匹配
- summary 必须与 evidence index row 匹配

Signoff：

- status signed
- payload_hash OK
- integrity OK
- source 绑定 report/certificate/index
- force false

History：

- event hash chain OK
- signed event 绑定当前 signoff
- reset event 绑定 approved CR

Redaction：

- 所有 JSON/TXT/JSONL 扫描
- 不允许敏感 key/value
- 不允许本机路径

### 15.2 关键 full-resign 防护

必须挡住：

- 改 final-readiness-report status 为 ready 并重签。
- 改 certificate status 为 ready 并重签。
- 删除 evidence index 中某条 failed row 并重签。
- 改 signoff signed_by 并重签。
- 改 history signed event 并重签。
- 用旧 Hub verification report 验当前 handoff。
- 用旧 Watch Signoff verification report 验当前 handoff。
- 多 delivery report 只提供第一条。
- ZIP 加 benign extra txt 并重签 manifest。


- archive-only。
- old verification report。
- old Hub report。

## 17. Store API

建议类：

```python
class TrustOperationsFinalReadinessStore:
    def refresh_report(...)
    def create_certificate(...)
    def sign(...)
    def create_change_request(...)
    def approve_change_request(...)
    def reset_signoff(...)
    def export_handoff(...)
    def build_handoff_zip(...)
    def verify_handoff_zip(...)
    def summary(...)
```

### 17.1 refresh_report()

输入外部 evidence 路径/report：

- Hub ZIP/report
- delivery reports
- Incident ZIP/report
- Knowledge ZIP/report
- Control ZIP/report
- Control Signoff archive/report
- Continuous Assurance ZIP/report
- Assurance Watch ZIP/report
- Assurance Watch Signoff archive/report

行为：

- 重新读取所有 external verification report。
- 计算 evidence index。
- 生成 final readiness report。
- 如果有 active signoff，返回 409。

### 17.2 create_certificate()

要求：

- report status ready。
- report integrity OK。
- evidence index integrity OK。
- active signoff 不存在。

### 17.3 sign()

要求：

- certificate ready。
- report ready。
- evidence index ready。
- no blockers。
- reason >= 8 chars。
- force false。

### 17.4 export_handoff()

规则：

- active signoff 存在。
- active signoff 当前。
- history 没有同 signoff 的 `final_handoff_exported`，否则 409。
- 删除 export 目录不能绕过。

### 17.5 build_handoff_zip()

规则：

- active signoff 存在。
- export 已存在且 manifest 绑定当前 signoff。
- history 没有同 signoff 的 `final_handoff_zip_built`，否则 409。
- 删除 ZIP 不能绕过。

## 22. 单元测试计划

### 22.1 Store

覆盖：

- evidence 完整 -> report ready。

## 23. 安全要求

## 30. 给开发的话

这版是 v9 的最后一次大收口，不要把它做成“又一个 summary 页面”。它要做的是最终准出证书和移交包：一个人接手这个项目时，可以只看 Final Readiness Certificate / Handoff Pack，就知道 Trust Operations 的所有关键证据是否已经 ready、是否经过签核、是否能离线复核。

实现顺序建议：

1. 先做 Store 和 evidence index。
2. 再做 Handoff ZIP verifier。
3. 再做 CLI 生命周期。
4. 再接 Server API。
5. 最后接 Studio。
6. release-check smoke 必须覆盖 full-resign 和 signed immutable，不要只覆盖 happy path。

核心原则还是这几个：

- 不信内部自证。
- 不信单个 summary。
- `--require-*` 必须有外部 verification report。
- 签核不可变必须基于 history。
- reset 必须 approved CR。
- 任何可移交 ZIP 必须 fixed allow-list。

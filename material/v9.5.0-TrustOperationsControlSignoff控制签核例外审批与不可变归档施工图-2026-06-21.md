## 1. 为什么需要 v9.5

v9.4 解决的是：

> 当前控制目录是否存在？控制评估是否通过？评估是否绑定外部 Hub / Incident / Knowledge 证据？

但正式交付前还缺几个关键动作：

1. 控制评估通过后，谁签核？
2. 如果某个非 critical 控制失败，是否允许例外？谁批准？理由是什么？
3. 签核后能不能删除 signoff 文件绕过不可变保护？
4. 签核后 Control Package / Assessment / Policy 改了，旧签核是否还能被错误复用？
5. 外部 reviewer 能否拿到一个独立 Control Signoff Archive 离线验收？
6. Hub gate 能否要求 Control Package 不只是 passed，而且已经签核归档？

v9.5 要补齐这些治理动作。

## 3. 范围

### 3.1 必须做

- Control Signoff 数据模型。
- Control Signoff history，作为不可变状态来源。
- Control Exception Request / Approval / Rejection / Applied。
- Control Signoff reset，必须绑定 approved Change Request。
- Control Signoff Archive export / ZIP / offline verifier。
- Hub verifier 新增 `--require-trust-control-signoff`。
- API / CLI / Studio 入口。
- release-check `v95.trust_operations_control_signoff_smoke`。
- README / CHANGELOG / version bump。

### 3.2 不做

- 不自动 approve exception。
- 不自动 reset signoff。
- 不自动修改 Control Policy。
- 不自动调用 provider。
- 不接真实电子签名/CA。
- 不做云端同步。
- 不支持 critical control waiver。

### 3.3 强约束

- 签核状态必须以 history 为准，不能只看 `signoff.json` 是否存在。
- 签核后即使删除 export 目录、ZIP 或 signoff 文件，也不能重新 export / ZIP。
- reset 必须有 approved Change Request，且 CR 只能用一次。
- Exception 只能覆盖 medium / warning / manual_required，不允许覆盖 critical / high required failed。
- Signoff Archive verifier 必须绑定当前 Control ZIP、Control verification report、Hub ZIP、Hub verification report、Incident verification report、Knowledge verification report。
- 任何同包全量重签都必须失败。

## 7. Signoff 规则

### 7.1 正常签核必须满足

- Control verification report status = passed。
- Control ZIP hash / size / manifest hash 与 verification report 匹配。
- Control verification report 绑定当前 Hub / Incident / Knowledge evidence。
- `required_failed_count == 0`。
- 没有 critical/high failed control。
- 没有 stale source。
- 没有 expired exception。
- 没有 redaction finding。

### 7.2 带 exception 签核

允许的情况：

- failed control severity 是 `medium` 或 `low`。
- control 是 non-required。
- exception status = approved。
- exception 没过期。
- exception source 绑定当前 assessment/control_result。
- signoff summary 明确记录 approved exception。

不允许：

- critical/high required failed。
- evidence_binding 类 failure。
- signed_immutability 类 failure。
- full_resign_semantic_guard failure。
- redaction failure。
- stale source。

### 7.3 force signoff

v9.5 不做 force signoff。
如果未来要做，也必须单独规划，不允许在 v9.5 偷偷加。

## 8. 不可变保护

签核后以下操作必须 409：

- create new exception。
- approve exception。
- export signoff archive。
- build archive ZIP。
- refresh signoff report。
- overwrite signoff。

但允许：

- read。
- verify。
- create change request。
- approve change request。
- reset signoff with approved CR。

重点：不可变状态必须读取 `signoff-history.jsonl` 的最后有效 signed 记录，而不是只看 `signoff.json`。

必须覆盖回归：

1. 签核后删除 `signoff.json`，export 仍 409。
2. 签核后删除 archive 目录和 ZIP，build 仍 409。
3. 签核后篡改 history，verifier failed。
4. reset 无 CR 409。
5. reset draft CR 409。
6. reset approved CR 成功。
7. 同一个 CR 第二次 reset 409。

### 10.1 Verifier 检查项

ZIP：

- open。
- size limit。
- uncompressed size limit。
- entry count limit。
- raw backslash entry failed。
- duplicate failed。
- path traversal failed。
- `.MusicForge` failed。
- nested zip failed。
- fixed allow-list。
- manifest.files 精确等于 allow-list。

Documents：

- package_type。
- integrity_hash。
- manifest source hash。
- signoff hash。
- history hash。
- exceptions hash。
- change_requests hash。
- report hash。
- source_verification_summary hash。

Signoff：

- status signed。
- signoff source matches Control verification report。
- signoff summary matches Control verification report summary。
- no forbidden approved exception。
- signed history contains current signoff hash。

Change Request：

- reset event 必须绑定 approved CR。
- CR 只能 applied 一次。
- current signoff reset history 与 CR applied hash 匹配。

External：

- Control ZIP sha / size / manifest hash。
- Control verification report hash。
- Hub ZIP / Hub verification。
- Incident ZIP / Incident verification。
- Knowledge ZIP / Knowledge verification。

Redaction：

- archive text 不得包含 token、本机绝对路径、UNC 路径、provider raw response。

### 10.2 必须阻断的攻击

1. 修改 signed_by 后重算 signoff / manifest。
2. 修改 source_verification_summary 后重算 manifest。
3. 把 signoff source 指向旧 Control ZIP。
4. 删除 history 里的 signed event。
5. 伪造 reset event，不绑定 approved CR。
6. approved exception 覆盖 critical control。
7. exception expired 仍被 signoff 接受。
8. 加 benign extra txt 并重算 manifest。
9. backslash entry。
10. `.MusicForge/internal.json`。

## 17. 安全复现必须覆盖

### 17.1 删除签核文件绕过

步骤：

1. sign。
2. 删除 `signoff.json`。
3. 调 `export_archive()` 或 `build_archive_zip()`。

预期：409。

### 17.2 旧 Control ZIP 复用

步骤：

1. sign archive。
2. 重新生成 Control Assessment / ZIP。
3. 用旧 signoff archive 跑 Hub gate。

预期：failed。

### 17.3 critical exception 伪造

步骤：

1. 让 critical control failed。
2. 手工伪造 approved exception。
3. 重算 signoff archive。

预期：verifier failed。

### 17.4 history tamper

步骤：

1. sign。
2. 修改 history event 的 signoff_hash。
3. 重算 archive manifest。

预期：verifier failed。

### 17.5 source verification summary full-resign

步骤：

1. 修改 source-verification-summary 指向旧 Control verification。
2. 重算 summary / manifest。

预期：verifier failed。

- Critical/high controls 不能豁免。
- Hub gate 可以要求 signed archive。

## 25. Reviewer 重点检查

Reviewer 审 v9.5 时优先看：

1. 签核不可变是否基于 history，而不是文件存在。
2. reset 是否必须 approved CR。
3. CR 是否只能用一次。
4. exception 是否不能覆盖 critical/high required failure。
5. signoff archive verifier 是否读取外部 Control ZIP / Control verification。
6. signoff archive verifier 是否继续绑定 Hub / Incident / Knowledge 外部证据。
7. Hub gate 是否不能只靠 signoff archive 自证。
8. full-resign 攻击是否覆盖 source summary、history、exception、signoff 四类。
9. release-check v9.5 是否在 v9/latest profile。
10. 所有敏感路径/token 是否仍被 redaction scan 挡住。

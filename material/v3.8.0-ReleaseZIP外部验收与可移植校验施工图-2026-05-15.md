# v3.8.0 Release ZIP 外部验收与可移植校验施工图

日期：2026-05-15

当前稳定基线：v3.7.1

目标版本：v3.8.0

定位：v3.7.1 已经完成 Release Workspace，可以把多个已签核 Project 组装成 Release Export 和 Release ZIP。v3.8.0 要继续往外走一步：让 Release ZIP 离开当前 `.musicforge/` 工作区之后，仍然可以在干净目录、另一台机器、或者只拿到 ZIP 文件的验收方那里被独立验证。核心目标是新增 `verify-release` 能力和可携带的验收报告。

---

## 1. 背景判断

v3.7.1 解决的是：

```text
多个 Project Final Export
  -> Release Workspace
  -> Release QA
  -> Release Export
  -> Release ZIP
  -> Release Signoff
```

这已经能回答：

```text
在当前 MusicForge 项目目录里，这个多曲目发行包是否可交付？
```

但正式交付还差一个很关键的问题：

```text
如果我只把 release-export.zip 发给别人，对方能不能不依赖我的本机状态，独立判断这个 ZIP 是否完整、安全、可信？
```

现在的 v3.7.1 验证仍然主要发生在本机 workspace：

- Release QA 会读 `.musicforge/releases/<release-id>/release.json`。
- Release QA 会回查 `.musicforge/projects/<project-id>/`。
- Release Signoff 会读当前 release-export manifest。
- release-check 也在当前 repo 内跑。

但真实交付时，验收方通常只拿到：

- 一个 ZIP。
- 也许还有一份 release id。
- 也许没有 `.musicforge/projects/`。
- 也许没有任何 Provider/Renderer 配置。
- 也许不信任发送方机器上的状态。

v3.8.0 要补的是“外部验收层”：只基于 ZIP 内容本身，重新检查 ZIP entry、manifest、hash、签核摘要、tracklist、每轨核心文件、脱敏、路径安全和格式完整性。

这一步很重要，因为它把 MusicForge 的交付链从“本机可信”提升到“交付物自证”。

---

## 2. 一句话目标

v3.8.0 要新增 Release ZIP Verifier：

```text
musicforge-release.zip
  -> unzip in memory / temp dir
  -> verify manifest / tracklist / files / hashes / signoff / redaction / paths
  -> produce release-verification-report.json
  -> CLI exit code
  -> Studio optional import-check
  -> release-check v3.8 smoke
```

最低成功标准：

```powershell
python -m song_agent.cli verify-release path\to\release-export.zip
```

可以在没有 `.musicforge/projects/` 的干净目录里运行，并且能明确返回：

- passed。
- warning。
- failed。

## 3. 版本边界

### 3.1 v3.8.0 必须做

- 新增 Release ZIP verifier 模块。
- 新增 `python -m song_agent.cli verify-release <zip>`。
- 支持输出 human summary。
- 支持输出 JSON report。
- 支持 exit code：
  - `0`：passed 或 warning，且没有 blocking failed。
  - `1`：failed、ZIP 不可读、manifest 不可信、redaction failed。
  - `2`：命令参数错误。
- 校验 ZIP entry path safety。
- 校验 ZIP 内 `manifest.json`。
- 校验 ZIP 内 `tracklist.json`。
- 校验 ZIP 内 `release.json`。
- 校验 ZIP 内 `release-qa.json`。
- 校验 ZIP 内 `release-signoff.json`。
- 校验每个 track 目录必需文件：
  - `manifest.json`
  - `README.txt`
  - `project-export.json`
  - `song-plan.json`
  - `song.mid`
- 校验 manifest.files 记录与 ZIP 实际 entry 对账。
- 校验 manifest 中每个文件的 sha256 与 ZIP entry 内容一致。
- 校验 ZIP 内 manifest 的 `source_hash`、`qa_source_hash` 基本存在。
- 校验 `release-signoff.json.export_manifest_hash` 与 ZIP 内 manifest 非 zip 部分 hash 一致。
- 校验 `release-signoff.json` 是 v3.7.1 合法 sidecar：它必须存在于 ZIP，但不要求出现在 `manifest.files[]`。
- 校验重复 ZIP entry：同名 entry 一律 failed。
- 校验 extra entry 时，允许列表只能来自 `manifest.files[].path` 加必需 sidecar entries，不能信 `manifest.zip.entries`。
- 校验敏感值：
  - Windows 盘符路径。
  - UNC 路径。
  - POSIX 用户路径。
  - provider key。
  - GitHub token。
  - Bearer token。
  - secret assignment。
- 生成 `release-verification-report.json`。
- release-check 新增 v3.8 smoke。
- README / CHANGELOG / version bump。
- 本施工图入库。

### 3.2 v3.8.0 可以做，但不强制

- Studio Release 页面上传/选择 ZIP 后验证。
- Studio 本地路径输入验证 ZIP。
- `POST /api/release-verifier/verify`。
- 生成 HTML verification report。
- verification report 打包进一个 sidecar ZIP。
- 支持验证解压后的 `release-export/` 目录。

如果时间紧，Studio/API 可以作为 v3.8.1 做；但 CLI 和核心 verifier 必须在 v3.8.0 完成。

### 3.3 v3.8.0 明确不做

- 不自动修复 ZIP。
- 不重新生成 Release Export。
- 不回写 `.musicforge/releases/`。
- 不修改 Project。
- 不调用 Provider。
- 不调用 Renderer。
- 不解码音频内容做听感判断。
- 不上传发行平台。
- 不做版权登记。
- 不信任 ZIP 内任何绝对路径。
- 不执行 ZIP 内任何脚本。

## 4. 核心原则

### 4.1 Verifier 只信 ZIP 内容，不信当前 workspace

Verifier 不能依赖：

- `.musicforge/projects/`
- `.musicforge/releases/`
- `runs/`
- provider config。
- renderer config。
- 当前 git 状态。

它可以依赖：

- Python 标准库。
- MusicForge 本地代码里的 schema / hash / redaction 逻辑。

### 4.2 Verifier 是只读验收器

Verifier 不写入被验证 ZIP。

默认只在 stdout 输出摘要。用户指定 `--report-out` 时，才写 verification report 到目标路径。

### 4.3 ZIP 不应被完整解压到工作区

默认应该用 `zipfile` 直接读 entry。

如果需要 temp dir：

- 用系统临时目录。
- 使用唯一目录。
- 验证后清理。
- 绝不按 ZIP entry 原样 extract 到用户目录。

### 4.4 Manifest 不是绝对信任源

Verifier 要读 manifest，但不能只信 manifest。

必须同时：

- 遍历 ZIP 实际 entries。
- 校验 entry path。
- 校验 manifest.files。
- 校验 hash。
- 校验缺失文件。
- 校验多余文件。

### 4.5 报告要可读也可机器读

CLI human summary 用于人看。

JSON report 用于后续流程：

- Studio 展示。
- 外部 CI。
- release-check。
- 交付存档。

## 6. Verification Report Schema

报告文件：

```text
release-verification-report.json
```

结构建议：

```json
{
  "schema_version": 1,
  "generated_at": "2026-05-15T00:00:00+00:00",
  "tool": {
    "name": "MusicForge Release Verifier",
    "version": "3.8.0"
  },
  "input": {
    "filename": "musicforge-release-000001-release-export.zip",
    "size_bytes": 123456,
    "sha256": "..."
  },
  "status": "passed",
  "strict": false,
  "summary": {
    "release_id": "release-000001",
    "release_name": "May Demo EP",
    "track_count": 2,
    "entry_count": 42,
    "checked_file_count": 40,
    "blocker_count": 0,
    "warning_count": 1
  },
  "checks": [],
  "track_checks": [],
  "files": [],
  "redaction_findings": [],
  "warnings": [],
  "blockers": []
}
```

### 6.1 status

- `passed`：无 blocker，无 warning。
- `warning`：无 blocker，有 warning。
- `failed`：有 blocker。

### 6.2 check 结构

```json
{
  "scope": "zip",
  "check_id": "zip_open",
  "status": "passed",
  "severity": "blocking",
  "message": "ZIP can be opened.",
  "count": 0
}
```

`scope` 可选：

- `zip`
- `manifest`
- `release`
- `tracklist`
- `track`
- `file`
- `redaction`

## 7. ZIP 层检查

### 7.1 zip_open

必须检查：

- ZIP 文件存在。
- 是文件。
- 不是目录。
- 不是 symlink。
- 可被 `zipfile.ZipFile` 打开。
- 没有 `BadZipFile`。

失败：blocking。

### 7.2 zip_size_limit

默认上限：

```text
512 MB
```

超过：

- strict=false：failed。
- 后续如需要可做配置。

### 7.3 zip_entry_count_limit

默认上限：

```text
5000 entries
```

超过：failed。

### 7.4 zip_uncompressed_size_limit

ZIP bomb 防护不能只看 ZIP 文件体积。Verifier 必须用 `ZipInfo.file_size` 汇总所有 entry 的未压缩体积。

默认上限：

```text
2048 MB
```

超过：failed。

要求：

- 不需要解压。
- 不读取 entry bytes。
- 只用 central directory 里的 `file_size` 先做第一层防护。
- 后续逐文件 hash 时仍要流式读取，不能一次性把大文件读入内存。

### 7.5 zip_entry_path_safe

每个 entry 必须：

- 是相对 POSIX path。
- 不以 `/` 开头。
- 不包含 `..`。
- 不包含 `.` path segment。
- 不包含 Windows drive prefix。
- 不包含 UNC 起始。
- 不包含 NUL。
- 不包含控制字符。
- 不以反斜杠逃逸。

失败：blocking。

### 7.6 zip_duplicate_entries

ZIP 格式允许出现同名 entry。不同解压工具对同名 entry 的处理可能不同，Python `ZipFile.read(name)` 也容易让实现误读最后一个或第一个。

Verifier 必须：

- 遍历 `archive.infolist()`。
- 以 normalized entry name 统计。
- 任意重复 entry 直接 failed。
- 即使重复 entry 的 hash 相同，也 failed。

这条是 P1 安全边界，不能降级成 warning。

### 7.7 zip_no_directory_traversal

即使不 extract，也要把 traversal 作为 blocking。

构造测试：

- `../evil.txt`
- `/absolute.txt`
- `C:/temp/evil.txt`
- `tracks/01/../../evil.txt`
- `\\server\share\evil.txt`

都必须 failed。

## 8. Manifest 层检查

必需 entry：

```text
manifest.json
release.json
tracklist.json
release-qa.json
release-signoff.json
README.txt
```

注意：v3.7.1 的合法 Release ZIP 有两个特殊 sidecar：

- `manifest.json`
- `release-signoff.json`

其中 `manifest.json` 是 ZIP 根 manifest，本身通常不适合用自引用 sha256 进入 `manifest.files[]`。

`release-signoff.json` 会在签核后写入 ZIP，用于让外部验收方看到最终签核摘要。v3.7.1 的真实口径是：它必须存在于 ZIP，但不要求出现在 `manifest.files[]`。Verifier 不能把它当成非法 extra entry。

### 8.1 manifest_exists

`manifest.json` 缺失：failed。

### 8.2 manifest_parse

必须是合法 UTF-8 JSON object。

失败：failed。

### 8.3 manifest_schema

检查：

- `schema_version` 存在。
- `release_id` 存在。
- `release_name` 存在。
- `source_hash` 存在。
- `qa_source_hash` 存在。
- 不要求 `signoff_hash` 存在。v3.7.1 已经不以 `manifest.signoff_hash` 作为签核绑定口径。
- `tracks` 是 list。
- `files` 是 list。
- `summary` 是 object。

缺少核心字段：failed。

### 8.4 manifest_files_shape

每个 file row 必须：

- `path` 非空。
- path 安全。
- `size_bytes` 是非负整数。
- `sha256` 是 64 位 hex。

不合格：failed。

### 8.5 manifest_file_hash_match

对每个 `manifest.files[]`：

- ZIP 里必须存在 entry。
- entry bytes 的 sha256 必须等于 manifest sha256。
- entry size 必须等于 manifest size。

缺失或 mismatch：failed。

### 8.6 manifest_extra_entries

ZIP 里有 manifest.files 没登记的 entry。

允许列表必须这样计算：

```text
allowed_entries = set(manifest.files[].path) + REQUIRED_SIDECAR_ENTRIES
```

`REQUIRED_SIDECAR_ENTRIES`：

```python
{
    "manifest.json",
    "release-signoff.json",
}
```

注意：

- `release.json`、`tracklist.json`、`release-qa.json`、`README.txt` 目前会进入 `manifest.files[]`，所以不需要在 sidecar 白名单里重复放行。
- `manifest.zip.entries` 只能作为一致性参考，不能作为允许列表。
- 攻击者可以追加 extra entry 后同步修改 `manifest.zip.entries`，而 `zip` 字段不参与 v3.7.1 的 signoff hash。
- 因此允许列表必须来自 `manifest.files[].path + REQUIRED_SIDECAR_ENTRIES`。

额外 entry 规则：

- strict=false：warning。
- strict=true：failed。
- dangerous entry / duplicate entry 不走 extra 规则，一律 failed。

注意：v3.7.1 的 ZIP 内 manifest 可能不记录 ZIP 自己的 sha256，这符合设计，不应该 failed。

## 9. Release / Tracklist 层检查

### 9.1 release_json

检查 `release.json`：

- UTF-8 JSON object。
- `release_id` 与 manifest 一致。
- `release_type` 存在。
- `track_count` 与 tracklist 一致。

不一致：failed。

### 9.2 tracklist_json

检查 `tracklist.json`：

- UTF-8 JSON object。
- `tracks` 是 list。
- 每个 track 有：
  - `track_id`
  - `disc_number`
  - `track_number`
  - `title`
  - `project_id`
  - `version_id`
  - `directory`
  - `file_count`

不合格：failed。

### 9.3 track_order

检查：

- `(disc_number, track_number)` 唯一。
- directory 唯一。
- track_id 唯一。
- track_number 从 1 开始。

不连续：

- strict=false：warning。
- strict=true：failed。

### 9.4 track_count_consistency

以下必须一致：

- manifest.summary.track_count。
- len(manifest.tracks)。
- len(tracklist.tracks)。
- release.track_count。

不一致：failed。

## 10. Track 文件检查

每个 track directory 必须存在。

必需文件：

```text
<track_dir>/manifest.json
<track_dir>/README.txt
<track_dir>/project-export.json
<track_dir>/song-plan.json
<track_dir>/song.mid
```

### 10.1 track_core_files

缺任一核心文件：failed。

### 10.2 track_song_plan_parse

`song-plan.json` 必须是 JSON object。

最小检查：

- title / tempo_bpm / key 可缺但 warning。
- sections 是 list。
- tracks 是 list。

解析失败：failed。

### 10.3 track_midi_header

`song.mid` 最低检查：

- bytes 以 `MThd` 开头。
- header length 合法。
- track count > 0。
- PPQ > 0。

失败：failed。

不需要完整 MIDI parser；v3.8.0 先做最小 header 验证。

### 10.4 track_optional_audio

如果 `--require-audio`：

- 每个 track 必须有 `song.wav`。
- WAV header 最低检查 `RIFF....WAVE`。

缺失或 header 失败：failed。

如果不 require：

- 缺 `song.wav` 不报错。

### 10.5 track_optional_stems

如果 `--require-stems`：

- 每个 track 必须有 `stems/manifest.json`。
- 每个 manifest 里声明的 stem MIDI 必须存在。

缺失：failed。

如果不 require：

- 缺 stems 不报错。

## 11. Signoff 检查

### 11.1 release_signoff_exists

`release-signoff.json` 缺失：failed。

### 11.2 release_signoff_parse

必须是 JSON object。

失败：failed。

### 11.3 signoff_status

允许：

- `signed`
- `force_signed`

其他状态：

- strict=false：warning 或 failed？建议 failed，因为 ZIP 用于交付验收。

### 11.4 signoff_manifest_hash

核心检查：

```python
stable_hash({key: value for key, value in manifest.items() if key != "zip"})
```

必须等于：

```text
release-signoff.json.export_manifest_hash
```

不一致：failed。

这就是 v3.7.1 修复点的外部验收版本。

不要检查 `manifest.signoff_hash`。v3.7.1 Release Export manifest 已经不写这个字段；要求它存在会误杀合法 ZIP。

### 11.5 signoff_qa_source

检查：

- `release-signoff.json.qa_source_hash` 存在。
- 与 manifest.qa_source_hash 或 release-qa summary source hash 对齐。

不一致：failed。

## 12. Redaction 检查

必须复用：

```text
song_agent/redaction.py
```

同时建议在 `release_verifier.py` 内保留 ZIP 验收专用扫描：

- token/key/path patterns。
- BLOCKED keys。

扫描范围：

- `manifest.json`
- `release.json`
- `tracklist.json`
- `release-qa.json`
- `release-signoff.json`
- 每个 track 的 `project-export.json`
- 每个 track 的 `song-plan.json`
- 每个 track 的 `manifest.json`
- README txt。

对二进制：

- `song.mid` 不做文本扫描。
- `song.wav` 不做文本扫描。
- stems MIDI/WAV 不做文本扫描。

### 12.1 blocked keys

出现以下 key：failed。

- `api_key`
- `access_token`
- `authorization`
- `password`
- `secret`
- `token`
- `raw_provider_response`
- `provider_snapshot`
- `local_path`
- `absolute_path`

### 12.2 sensitive values

出现以下 value：failed。

- provider key pattern。
- GitHub token pattern。
- Bearer token pattern。
- Windows drive path。
- UNC path。
- `/Users/<name>/...`
- `/home/<name>/...`

## 13. CLI 设计

新增命令：

```powershell
python -m song_agent.cli verify-release path\to\release-export.zip
```

参数：

```text
verify-release ZIP_PATH
  --json
  --report-out PATH
  --strict
  --require-audio
  --require-stems
  --max-zip-size-mb 512
  --max-entry-count 5000
```

### 13.1 默认输出

示例：

```text
MusicForge release verifier
input: musicforge-release-000001-release-export.zip
status: passed
release: release-000001 / May Demo EP
tracks: 2
entries: 42
checked files: 40
blockers: 0
warnings: 0
```

failed 示例：

```text
MusicForge release verifier
input: broken.zip
status: failed
blockers: 2

[failed] manifest_file_hash_match: tracks/01-song/song.mid hash does not match manifest.
[failed] redaction_scan: release.json contains local path.
```

### 13.2 JSON 输出

```powershell
python -m song_agent.cli verify-release release.zip --json
```

stdout 输出完整 report JSON。

### 13.3 report-out

```powershell
python -m song_agent.cli verify-release release.zip --report-out release-verification-report.json
```

写 report 文件。

如果 report-out 目标路径已存在：

- 默认覆盖可以接受。
- 但必须只写用户明确指定的文件。
- 不要自动写到 ZIP 旁边，避免污染交付目录。

### 13.4 exit code

- passed -> 0。
- warning -> 0。
- failed -> 1。
- 参数错误 -> 2。
- 未处理异常 -> 1，并输出 `error: ...`。

## 15. 安全测试矩阵

必须新增：

```text

```

可选：

### 15.1 正常 ZIP

用现有 Project/Release helpers 构造：

- 两个 Project。
- Final Export。
- Delivery QA。
- Delivery Signoff。
- Release Export。
- Release ZIP。
- Release Signoff。

断言：

- verifier status passed 或 warning。
- track_count == 2。
- manifest hash 与 signoff 一致。
- exit code 0。

### 15.2 ZIP 损坏

输入普通文本文件改名 zip。

断言：

- status failed。
- check `zip_open` failed。
- exit code 1。

### 15.3 dangerous entry

构造 ZIP 包含：

- `../evil.txt`
- `/absolute.txt`
- `C:/evil.txt`

断言：

- `zip_entry_path_safe` failed。

### 15.4 duplicate entry

构造 ZIP 包含两个同名 entry：

```text
tracklist.json
tracklist.json
```

或：

```text
tracks/01-song/song.mid
tracks/01-song/song.mid
```

断言：

- `zip_duplicate_entries` failed。
- strict=false 也 failed。

### 15.5 manifest missing

删除 ZIP 内 `manifest.json`。

断言 failed。

### 15.6 manifest hash mismatch

修改 ZIP 内某个 `song.mid` bytes，但不改 manifest sha。

断言：

- `manifest_file_hash_match` failed。

### 15.7 extra entry

加入 `extra.txt`。

断言：

- strict=false warning。
- strict=true failed。

并且要额外覆盖：

- 如果攻击者同步把 `extra.txt` 加进 `manifest.zip.entries`，但没有加入 `manifest.files[]`，仍然按 extra entry 处理。
- 这证明 Verifier 没有信任 `manifest.zip.entries` 作为允许列表。

### 15.8 legal sidecar entries

正常 v3.7.1 ZIP 中：

- `manifest.json` 可以不在 `manifest.files[]`。
- `release-signoff.json` 可以不在 `manifest.files[]`。

断言：

- strict=false 不报 extra。
- strict=true 也不报 extra。
- `release-signoff.json.export_manifest_hash` 仍必须校验。

### 15.9 redaction pollution

修改 ZIP 内 `release.json` 或 `tracklist.json`：

```json
{"notes": "<LOCAL_ABSOLUTE_PATH>", "api_key": "[REDACTED]"}
```

断言 redaction failed。

### 15.10 signoff hash mismatch

修改 `release-signoff.json.export_manifest_hash`。

断言 failed。

### 15.11 track core missing

删除某个 track 的 `song.mid`。

断言 failed。

### 15.12 require audio

正常 ZIP 没有 WAV 时：

- 默认 passed/warning。
- `--require-audio` failed。

### 15.13 require stems

正常 ZIP 没有 stems 时：

- 默认 passed/warning。
- `--require-stems` failed。

### 15.14 zip bomb guard

构造一个 ZIP，压缩后体积很小，但 `ZipInfo.file_size` 总和超过 `--max-uncompressed-size-mb`。

断言：

- `zip_uncompressed_size_limit` failed。
- 不需要真的解压到磁盘。

## 19. 风险清单

### P1：Verifier 信任 manifest.files

风险：

- manifest 被污染，隐藏恶意 entry。
- 攻击者把恶意 entry 加进 `manifest.zip.entries`，但不进 `manifest.files[]`，试图绕过 verifier。

要求：

- 既遍历 ZIP entries，也遍历 manifest.files。
- allowed entries 只能来自 `manifest.files[].path + REQUIRED_SIDECAR_ENTRIES`。
- `manifest.zip.entries` 只能做参考，不能作为允许列表。
- `manifest.json` 和 `release-signoff.json` 是合法 sidecar。
- extra entry 至少 warning，strict 下 failed。
- dangerous entry 一律 failed。

### P1：Verifier 漏掉重复 ZIP entry

风险：

- ZIP 内同名 entry 可能让不同工具读取不同内容。
- manifest hash 可能校验的是一个 entry，用户解压得到另一个 entry。

要求：

- 遍历 `ZipInfo` 原始列表。
- normalized path 重复直接 failed。
- strict=false 也 failed。

### P1：Verifier extract 到危险路径

风险：

- ZIP slip。

要求：

- 默认不 extract。
- 如果 temp extract，必须先验证 entry path。
- v3.8.0 建议完全不 extract。

### P1：signoff hash 计算口径不一致

风险：

- v3.7.1 用 `manifest without zip` 计算。
- verifier 如果用全 manifest，会误报或漏报。

要求：

- 复用同一 helper 或明确同一规则：

```python
stable_hash({key: value for key, value in manifest.items() if key != "zip"})
```

- 不要求 `manifest.signoff_hash`。
- 只检查 `release-signoff.json.export_manifest_hash`。

### P1：敏感信息扫描只扫 manifest

风险：

- token 藏在 release.json、tracklist、project-export 或 README。

要求：

- 扫所有 JSON/TXT。
- 二进制跳过。

### P2：大 ZIP 导致内存过大

风险：

- 一次性读入所有 entry。
- ZIP bomb：压缩体积小，未压缩总量极大。

要求：

- 对每个 entry 流式 hash。
- max size / max entry count。
- 用 `ZipInfo.file_size` 汇总未压缩大小并设置 `max_uncompressed_size_mb`。

### P2：CLI 输出太难读

风险：

- 用户不知道失败在哪里。

要求：

- human summary 必须列出前 N 个 blocker/warning。
- JSON report 保留完整 details。

## 21. 给开发的执行提醒

v3.8.0 不要被做成“解压 ZIP 看一眼”。它是交付可信链条的外部验证器。

开发时优先级：

1. `release_verifier.py` 核心纯函数。
2. 安全 ZIP entry 检查。
3. manifest/files/hash 对账。
4. signoff hash 对账。
5. redaction 全面扫描。
6. CLI exit code。
7. release-check 外部目录 smoke。
8. 可选 Studio/API。

不要在 verifier 里复用需要 ProjectStore 的逻辑。v3.8.0 的价值就在于：它可以离开 ProjectStore 独立工作。

最低交付闭环：

```text
v3.7.1 Release ZIP
  -> copy to temp external folder
  -> python -m song_agent.cli verify-release release.zip
  -> passed
  -> corrupt zip / polluted zip / hash mismatch zip
  -> failed
```

只要这个闭环稳定，MusicForge 的交付能力就从“我本机确认没问题”升级成“别人拿到包也能确认没问题”。

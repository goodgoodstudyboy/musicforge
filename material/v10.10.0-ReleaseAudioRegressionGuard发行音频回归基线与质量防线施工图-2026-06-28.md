# v10.10.0 Release Audio Regression Guard 发行音频回归基线与质量防线施工图

## 1. 给开发的交接说明

当前稳定基线是 v10.9.1。

v10.9.1 已经修住一个关键问题：Release Audio Timeline 必须绑定当前有效的 Release Audio Certification ZIP，污染底层 Certification ZIP 后，Timeline、Release signoff、GA readiness 都会失败。

下一版 v10.10.0 不要继续堆新的证明包层。它要把 v10.8 的 Certification 和 v10.9 的 Timeline 真正转化成质量回归防线：

> 当前 Release 的真实音频质量，和一个已签核基线相比，有没有变差？有没有新增 high / critical issue？有没有人工评分倒退？有没有修复成本上升？如果有，Release / GA 准出必须能挡住。

开发请先阅读本文，再按 Phase 1 到 Phase 6 分包实现。每个阶段完成后跑对应测试、提交、推 GitHub，不要一次性堆完。

## 3. 为什么 v10.10 做 Regression Guard

v10.2 到 v10.9 已经完成了真实音频验收主链路：

- v10.2 Audio Lab：能配置真实 renderer、渲染 WAV、人工试听、打 marker。
- v10.3 Audio Fix Sprint：能把音频问题修掉并人工复验。
- v10.4 Audio Campaign：能批量真实听审。
- v10.5 Campaign Governance：能把 Campaign 绑定 Release / GA。
- v10.6 Release-driven Campaign：能从 Release 自动创建正确绑定的 Campaign。
- v10.7 Remediation：能从 Campaign 问题编排修复与复验。
- v10.8 Audio Certification：能形成发行音频准出证书。
- v10.9 Audio Timeline：能保存音频证据时间线和长期趋势。

现在剩下的问题不是“有没有证据”，而是“证据显示这版音乐有没有退步”。

典型风险：

- 新版本全都 passed，但比上一版人工评分低。
- 新版本没有 critical blocker，但 high marker 数量明显增加。
- 同一首歌修复后又引入新的 mix_balance 问题。
- 平均 loudness / clipping / silence 指标变差。
- Remediation 数量上升，说明生成质量倒退。
- 开发只看当前 passed，不看历史基线，导致劣化进入发布。

v10.10 的目标就是把这些趋势变成 deterministic gate。

## 4. 目标

v10.10.0 要新增 Release Audio Regression Guard：

1. 选择一个已签核、已验证的 Release Audio Timeline / Certification 作为基线。
2. 读取当前 Release 的 Certification + Timeline。
3. 对比当前和基线的 track identity、人工评分、marker、issue taxonomy、remediation、audio health、certification summary。
4. 生成 Regression Report。
5. 生成 Regression Guard Decision：
   - passed
   - warning
   - failed
6. 支持签核前 gate：
   - Release signoff `require_release_audio_regression_guard=true`
   - GA readiness `ga.release_audio_regression_guard`
   - `verify-ga-readiness-report --require-release-audio-regression-guard`
7. 支持导出固定结构 ZIP 和 offline verifier。
8. release-check 增加 `v1010.release_audio_regression_guard_smoke`。

## 5. 不做什么

v10.10 不做：

- 不自动修改音乐。
- 不自动创建 Audio Fix Sprint。
- 不自动关闭 Campaign / Remediation / Certification / Timeline。
- 不自动签核 Release。
- 不自动选择基线。
- 不使用 provider / 外部 AI 来判断音乐好坏。
- 不把 synthetic / fake WAV 当作 release-ready 证据。
- 不用包内自证来证明基线或当前证据。

如果 report 提示 failed，只能生成 manual action 建议，不能自动修。

## 9. 数据结构：Baseline Binding

`baseline-binding.json` 必须来自外部 baseline Timeline / Certification verifier，不允许从当前 regression report 自证。

P1 规则：Baseline Timeline 也必须绑定 Baseline Certification。不能只验证 baseline Timeline 自身 passed，也不能只验证 baseline Certification 自身 passed。构建 baseline binding 时必须重新执行 Timeline verifier，并传入 baseline Certification ZIP + baseline Certification verification report，等价于：

```text
verify-release-audio-timeline-package baseline-timeline.zip
  --strict
  --require-passed
  --require-signed
  --require-current-certification
  --release-audio-certification baseline-certification.zip
  --release-audio-certification-verification-report baseline-certification-verification-report.json
```

如果 baseline Timeline verification report 是旧的、缺少 current certification binding、绑定的 Certification ZIP sha / manifest hash 与当前 baseline Certification ZIP 不一致，baseline binding 必须 failed，Release / GA gate 不能放行。

## 10. 数据结构：Current Binding

`current-binding.json` 和 baseline 结构一致，但必须绑定当前 Release：

- 当前 Release ID。
- 当前 Release tracks。
- 当前 Release Audio Certification ZIP。
- 当前 Release Audio Timeline ZIP。
- 当前 Certification ZIP 必须被 Timeline verifier 用 `require_current_certification=true` 校验。

如果当前 Certification ZIP 被污染，Regression refresh 必须 failed 或直接 409。

current binding 与 baseline binding 使用同一套 binding 规则：Timeline 必须通过当前 Certification ZIP + verification report 复验，不能只复用旧 Timeline verification report 的 passed 状态。

## 16. Baseline 选择规则

v10.10 先支持两种 baseline：

1. 显式 baseline：
   - 用户传 baseline Timeline ZIP + verification report。
   - 用户传 baseline Certification ZIP + verification report。
2. 同 Release previous signed baseline：
   - 读取本 Release 目录下已保存的 previous baseline config。
   - 只允许用于同一 Release 的 repeat certification 对比。

暂不做：

- 自动从所有历史 Release 中挑一个。
- 自动跨专辑聚类。
- provider 推荐 baseline。

基线选择必须是人工明确动作。

## 17. Track Identity 匹配规则

默认 identity mode 是 `release_track_lineage`，不能把 `final_export_hash` 当作默认相等条件。真实回归比较时，当前音频版本通常已经变化，final export hash 大概率不同；如果默认要求 hash 相等，会误杀正常的“同一首歌新版本 vs 基线版本”比较。

默认匹配优先级：

1. `project_id + release_track_lineage_id`
2. `project_id + source_track_slug`
3. `project_id + normalized_title`
4. `normalized_title + artist/context`，仅作为 warning match

`final_export_hash` 的用途：

- 作为 baseline/current 证据源 fingerprint。
- 用于检测同一侧 evidence 是否 current。
- 用于 `same_artifact_repeat_check` 模式下的严格相等检查。
- 不作为默认 track identity equality 条件。

配置项：

```json
{
  "identity_mode": "release_track_lineage"
}
```

支持模式：

- `release_track_lineage`：默认，用 track lineage / project / title 匹配同一首歌的不同音频版本。
- `same_artifact_repeat_check`：只用于重复验证同一 artifact，要求 baseline/current `final_export_hash` 相等。
- `manual_mapping`：用户显式提供 baseline track -> current track mapping，仍需 verifier 检查 mapping 指向的外部证据存在。

如果 `require_track_identity_match=true`：

- baseline track 缺失 -> failed。
- current track 缺失 -> failed。
- 默认模式下 final_export_hash 不一致不代表 identity failed，但必须记录到 evidence fingerprint delta。
- `same_artifact_repeat_check` 模式下 final_export_hash 不一致 -> failed。

如果匹配只能依赖 title，则进入 warning，除非用户提供 manual mapping。

## 18. Regression 判定规则

默认 P1 gate：

- 新增 critical issue > 0 -> failed。
- 新增 high issue > 0 -> failed。
- 任意 track manual rating drop > 0.5 -> failed。
- average manual rating drop > 0.25 -> failed。
- remediation count increase > 0 -> warning，若同时有 high issue -> failed。
- current audio health failed -> failed。
- current evidence synthetic/fake -> failed。
- current Timeline / Certification verification stale -> failed。

默认 warning：

- medium issue 增加。
- low issue 增加超过 3。
- accepted review count 下降。
- marker 数量明显增加但无 high/critical。
- baseline 缺少某些历史字段，只能部分比较。

## 19. Signoff 规则

Regression signoff 可选，但 Release / GA gate 可要求。

签核前必须：

- report status passed 或 warning。
- 不存在 blocking failed track。
- baseline binding current。
- current binding current。
- Timeline ZIP / Certification ZIP verification 都 passed。
- report integrity ok。

签核后：

- 不允许 refresh 覆盖 signed report。
- 不允许 export/zip 静默重建。
- 删除 signoff 文件不能绕过 history guard。
- export/zip 前必须逐项校验 signoff 绑定：
  - `regression_report_hash`
  - `track_matrix_hash`
  - `issue_index_hash`
  - `quality_delta_hash`
  - `blocker_register_hash`
  - `baseline_binding_hash`
  - `current_binding_hash`
- export/zip 前必须重建 history chain，并确认 latest signoff event 绑定当前 `regression-signoff.json`。

`regression-signoff-history.jsonl` 必须是 hash chain，不允许只是普通 append log。

每条 event 结构：

```json
{
  "schema_version": 1,
  "event_id": "ragevt-000001",
  "event_type": "regression_signoff_created",
  "created_at": "2026-06-28T00:00:00Z",
  "previous_event_hash": null,
  "payload": {
    "release_id": "rel-001",
    "signed_by": "audio-lead",
    "role": "audio-lead",
    "reason": "Regression guard passed.",
    "signoff_payload_hash": "...",
    "signoff_hash": "...",
    "report_hash": "...",
    "baseline_binding_hash": "...",
    "current_binding_hash": "...",
    "track_matrix_hash": "...",
    "issue_index_hash": "...",
    "quality_delta_hash": "..."
  },
  "payload_hash": "...",
  "event_hash": "..."
}
```

gate / verifier 必须重建 history chain，并校验当前 `regression-signoff.json` 与最新 valid signoff event payload 一致。删除 signoff 文件、重签 signoff JSON、或改 history 中的 `signed_by` / `report_hash` / binding hash，都必须 failed。

v10.10 不实现 signoff reset。已签核后如果需要刷新 baseline/current evidence，必须在后续版本单独设计 approved Change Request reset，并包含：

- approved Change Request id。
- Change Request hash。
- reset target signoff hash。
- previous signoff hash。
- reset reason hash。

在 v10.10 范围内，`reset_signoff()`、CLI reset action、`/audio-regression/signoff/reset` endpoint 都不是交付项，不能在文档、README 或 Studio 中宣称可用。

## 21. Offline Verifier

新增：

```powershell
python -m song_agent.cli verify-release-audio-regression-package <zip> `
  --strict `
  --require-passed `
  --require-current `
  --require-baseline-current `
  --baseline-timeline <zip> `
  --baseline-timeline-verification-report <json> `
  --baseline-certification <zip> `
  --baseline-certification-verification-report <json> `
  --current-timeline <zip> `
  --current-timeline-verification-report <json> `
  --current-certification <zip> `
  --current-certification-verification-report <json>
```

Verifier 不能只验证 regression ZIP 自洽。它必须反查外部证据：

- baseline Timeline ZIP 当前 sha / size / manifest hash。
- baseline Timeline verification report hash。
- baseline Certification ZIP 当前 sha / size / manifest hash。
- current Timeline ZIP 当前 sha / size / manifest hash。
- current Certification ZIP 当前 sha / size / manifest hash。
- baseline Timeline verification 必须启用 `require_current_certification=true`，并绑定 baseline Certification ZIP + verification report。
- current Timeline verification 必须启用 `require_current_certification=true`。

更重要的是：verifier 必须从外部 baseline/current Timeline ZIP + Certification ZIP 重新提取 normalized audio facts，再重算：

- expected track-regression-matrix。
- expected issue-regression-index。
- expected quality-delta-summary。
- expected blocker-register。
- expected regression report status / readiness / blockers。

然后用重算结果反查 regression ZIP 内的派生 JSON。不能只检查 matrix/report 自己的 `integrity_hash`，否则攻击者可以把 matrix、issue、quality、report 一起改成 passed 并重算所有内部 hash。

normalized audio facts 至少包括：

- track identity candidates。
- final export fingerprints。
- manual accepted / needs_fix / rejected review counts。
- manual rating。
- marker severity / category。
- remediation count / status。
- audio health status。
- certification track status。

`--require-current` 语义：

- current Timeline/Certification external evidence 必须存在。
- current Timeline 必须绑定 current Certification。
- current package sha / manifest / verification report hash 必须匹配当前文件。

`--require-baseline-current` 语义：

- baseline Timeline/Certification external evidence 必须存在。
- baseline Timeline 必须绑定 baseline Certification。
- baseline package sha / manifest / verification report hash 必须匹配当前文件。
- baseline evidence 被污染时，Regression verifier 必须 failed。

Gate 规则：

## 28. Release-check smoke

新增 check：

```text
v1010.release_audio_regression_guard_smoke
```

加入 profiles：

- full
- quick
- latest
- ga
- v10

Smoke 必须覆盖：

1. 构造 baseline Release：Certification passed + Timeline passed + signed。
2. 构造 current Release：Certification passed + Timeline passed。
3. current 无回归 -> Regression report passed。
4. Release signoff `require_release_audio_regression_guard=true` passed。
5. GA readiness require regression guard passed / warning allowed。
6. 当前 Certification ZIP 污染 -> regression refresh/gate failed。
7. 当前 Timeline ZIP 污染 -> regression verifier failed。
8. baseline Certification ZIP 污染 -> regression verifier failed。
9. 新增 high issue -> regression report failed，Release signoff 409。
10. rating drop 超阈值 -> regression report failed。
11. internal full-resign attack：把 matrix/report 改成 passed，重算 regression ZIP 内全部 hash，但不改外部 Timeline/Certification，verifier 必须 failed。
12. manifest-declared extra entry -> verifier failed。
13. redaction 污染 -> verifier failed。

Smoke detail 建议输出：

```text
baseline=passed, current=passed, regression=passed, release_gate=passed, ga=passed,
current_cert_tamper=failed, baseline_cert_tamper=failed, high_issue=failed/409,
rating_drop=failed, internal_full_resign=failed, declared_extra=failed, redaction=failed
```

## 38. 给开发的最后提醒

这版不要把 Regression Guard 做成“又一个 summary”。它的价值是把真实听审质量变成防退化门禁。

开发最容易犯的错误：

1. 只比较当前 report，不绑定 baseline/current 外部 verification。
2. 只看 track_count，不看 track identity。
3. 只看 report status，不看 high/critical issue delta。
4. 让 GA verifier 只信 GA report 自身。
5. 让 ZIP manifest 声明什么就放行什么。
6. signed 后仍允许 Studio refresh 覆盖 report。

这些都属于 reviewer 会打回的点。

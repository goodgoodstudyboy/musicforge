# v3.7.0 Release Workspace 多曲目发行工作台施工图

日期：2026-05-15

当前稳定基线：v3.6.1

目标版本：v3.7.0

定位：在 v3.6.1 已经把单曲 Project 的 Final Export、Delivery QA、Delivery Signoff 收紧之后，v3.7.0 不再继续只在单曲内加小功能，而是新增 Release Workspace。它把多个已经完成交付验收的 Project 组织成一个 EP / Album / Track Pack 级发行包，提供跨项目曲目管理、整包 QA、整包导出、整包 ZIP、整包签核和 Studio 操作面板。

---

## 1. 背景判断

MusicForge 到 v3.6.1 的能力已经非常长：

- 从 prompt / request 生成 SongPlan。
- 支持 local / provider / multinode 生成。
- 有 Project、Version、Variation、Edit、Visual Editor。
- 有 Asset、Reference、Context Pack。
- 有 Review Task、Review Candidate、Review Sprint。
- 有 Recommendation、Action Queue、Metrics、Provider Judge。
- 有 Sprint Closeout / Signoff。
- 有 Project Final Export。
- 有 Project Delivery QA / Delivery Signoff。
- 有 release-check 和大量安全回归。

现在它已经能回答一个问题：

```text
单首歌是否能交付？
```

v3.7.0 要开始回答下一个更大的问题：

```text
一组歌是否能作为一个正式发行包交付？
```

这里的“发行包”不是指直接上传到 Spotify、网易云、QQ 音乐或任何发行平台。v3.7.0 只做本地发行组装和验收：

- 哪些 Project 进入这次发行？
- 曲目顺序是什么？
- 每首歌使用哪个 final version？
- 每首歌是否已经通过 Delivery QA？
- 每首歌是否已经 Delivery Signoff？
- 整包的元数据是否完整？
- 整包是否存在跨曲目冲突？
- 整包导出的目录和 ZIP 是否完整、安全、可复核？
- 谁在什么时间签核了这次 release？

这一步的意义是：MusicForge 从“单曲生产工具”升级为“作品集交付系统”。

---

## 2. 一句话目标

v3.7.0 要新增 Release Workspace：

```text
Project Final Export + Delivery Signoff
  -> Release Workspace
  -> Tracklist / Metadata / Cross-project QA
  -> Release Export Bundle
  -> Release ZIP
  -> Release Signoff
  -> release-check v3.7 smoke
```

核心不是生成更多候选，而是把多个已完成的单曲 Project 变成一个可验收、可移交、可复核的多曲目交付包。

## 3. 版本边界

### 3.1 v3.7.0 必须做

- 新增 Release Store。
- 新增 `.musicforge/releases/<release-id>/` 本地持久化。
- 新增 ReleaseDocument / ReleaseTrack / ReleaseQAReport / ReleaseSignoff / ReleaseExportManifest。
- 新增 Release API：
  - 创建 release。
  - 列表 / 详情 / 隐藏 / 删除。
  - 添加 Project final track。
  - 移除 track。
  - 重排 track。
  - 刷新 track snapshot。
  - 刷新 Release QA。
  - 生成 Release Export。
  - 生成 Release ZIP。
  - 签核 / 强制签核 / reset signoff。
- Studio 新增 Releases 工作区。
- Project Final Export 页面增加 Add to Release 入口。
- Release QA 检查每个 track 的 Project Delivery QA / Delivery Signoff / Final Export / ZIP / redaction / hash。
- Release Export 生成整包目录。
- Release ZIP 生成整包 ZIP。
- Project Export / Final Export 不需要反向嵌入 release 全量数据，但 Release Export 要保留每个 Project 的安全摘要。
- `python -m song_agent.cli release-check` 新增 v3.7 smoke。
- README / CHANGELOG / version bump。
- 按既有节奏提交、推送、tag、GitHub Release。

### 3.2 v3.7.0 可以做，但不强制

- 从 Batch 自动创建 Release。
- Release metadata 模板。
- Release track bulk import。
- Release Export HTML summary。
- Release QA 单独下载 JSON。
- Studio 里更细的 drag-and-drop 排序。
- 曲目间音量 / loudness 分析。
- 曲目间风格一致性打分。

这些可以在 v3.7.1 或 v3.8.0 继续做。

### 3.3 v3.7.0 明确不做

- 不上传任何发行平台。
- 不做平台账号管理。
- 不做版权登记。
- 不做 ISRC 自动申请。
- 不做封面图生成。
- 不做音频母带处理。
- 不自动修改 Project。
- 不自动重建 Project Final Export。
- 不自动替换 Project final version。
- 不自动调用 provider。
- 不把原始 reference 文件复制进整包交付。
- 不绕过 Project Delivery QA。

## 4. 大版本原则

### 4.1 Release 是 Project 之上的编排层

Release 只能引用 Project 的交付结果，不能成为 Project 的另一个编辑入口。

允许：

- 读取 Project metadata。
- 读取 final version。
- 读取 final-export manifest。
- 读取 delivery-qa summary。
- 读取 delivery-signoff summary。
- 复制安全的 final-export 文件到 release-export。

不允许：

- 修改 SongPlan。
- 修改 Project version。
- 修改 Project final_version_id。
- 修改 Project selected_version_id。
- 修改 Review Sprint。
- 修改 Delivery QA。
- 修改 Delivery Signoff。
- 修改 Asset / Reference / Context Pack。

### 4.2 Release QA 是验收器，不是修复器

Release QA 只报告：

- pass。
- warning。
- failed。
- stale。

Release QA 不修复任何问题。遇到 Project 交付缺口时，开发必须让用户回到 Project 层修复。

### 4.3 Release Export 只能复制已验收产物

Release Export 只从每个 Project 的 `final-export/` 复制安全文件。

不能从以下位置直接复制：

- `runs/` 临时目录。
- `.musicforge/provider.json`。
- `.musicforge/renderer.json`。
- `.musicforge/references/` 原始文件。
- `.musicforge/assets/` 原始内部文件。
- Project 任意未验收 artifact。

### 4.4 Signoff 是审计事实

Release Signoff 是独立审计记录。它不能被普通 refresh 覆盖。

reset 必须：

- 写历史。
- 写 event。
- 保留旧 signoff 摘要。
- 不能静默删除。

### 4.5 所有导出都必须可迁移

Release Export 和 ZIP 里不能出现：

- 本机绝对路径。
- token。
- provider key。
- raw provider response。
- raw prompt。
- 原始 reference 文件。
- 任意 Windows / UNC / POSIX 本地路径。
- 指向当前机器 workspace 的路径。

## 6. 核心数据模型

### 6.1 ReleaseDocument

建议新增文件：

```text
song_agent/releases.py
```

核心结构：

```python
@dataclass
class ReleaseDocument:
    schema_version: int
    release_id: str
    name: str
    release_type: str
    status: str
    primary_artist: str
    label: str | None
    language: str | None
    notes: str | None
    created_at: str
    updated_at: str
    hidden: bool
    metadata: dict[str, Any]
    tracks: list[ReleaseTrack]
    latest_qa_summary: dict[str, Any]
    latest_export_summary: dict[str, Any]
    latest_signoff_summary: dict[str, Any]
```

字段约束：

- `release_type`：`single_pack` / `ep` / `album` / `demo_pack`。
- `status`：`draft` / `qa_failed` / `qa_warning` / `qa_passed` / `exported` / `signed` / `archived`。
- `name` 必填，最大 120 字符。
- `primary_artist` 可先允许空，但 QA 必须 warning 或 failed。
- `metadata` 只能存安全摘要，不存本机路径。

### 6.2 ReleaseTrack

```python
@dataclass
class ReleaseTrack:
    track_id: str
    track_number: int
    disc_number: int
    title: str
    artist: str | None
    project_id: str
    version_id: str
    final_export_hash: str | None
    delivery_qa_hash: str | None
    delivery_signoff_hash: str | None
    project_snapshot: dict[str, Any]
    export_snapshot: dict[str, Any]
    qa_snapshot: dict[str, Any]
    signoff_snapshot: dict[str, Any]
    stale: bool
    warnings: list[str]
    created_at: str
    updated_at: str
```

关键原则：

- `project_snapshot` 是快照，不是信任源。
- 每次 Release QA 必须重新读取 Project Store 和磁盘文件。
- `stale=true` 时不能签核 release。
- track 引用必须绑定 `project_id + version_id`。
- 默认添加 Project 时使用 Project 当前 `final_version_id`。
- 如果 Project 没有 final version，添加 track 返回 409。

### 6.3 ReleaseQAReport

```python
@dataclass
class ReleaseQAReport:
    schema_version: int
    release_id: str
    status: str
    generated_at: str
    source_hash: str
    checks: list[dict[str, Any]]
    track_checks: list[dict[str, Any]]
    blockers: list[dict[str, Any]]
    warnings: list[dict[str, Any]]
    summary: dict[str, Any]
```

`status`：

- `passed`
- `warning`
- `failed`
- `stale`

### 6.4 ReleaseSignoff

```python
@dataclass
class ReleaseSignoff:
    schema_version: int
    release_id: str
    status: str
    signed_at: str
    signed_by: str
    qa_source_hash: str
    release_source_hash: str
    export_manifest_hash: str | None
    forced: bool
    override_reason: str | None
    acknowledged_blockers: list[dict[str, Any]]
    acknowledged_warnings: list[dict[str, Any]]
    notes: str | None
```

`status`：

- `signed`
- `force_signed`
- `reset`

### 6.5 ReleaseExportManifest

```python
@dataclass
class ReleaseExportManifest:
    schema_version: int
    release_id: str
    release_name: str
    generated_at: str
    source_hash: str
    qa_source_hash: str
    signoff_hash: str | None
    tracks: list[dict[str, Any]]
    files: list[dict[str, Any]]
    zip: dict[str, Any]
    redaction_summary: dict[str, Any]
```

ZIP metadata 不允许写本地绝对路径，只允许：

- filename。
- size_bytes。
- sha256。
- entry_count。
- generated_at。

## 7. Release ID 和路径安全

### 7.1 ID 规则

建议：

```text
release-000001
release-000002
...
```

实现要求：

- 在 `ReleaseStore` 的锁内分配 ID。
- 用 `mkdir(..., exist_ok=False)` 原子占位。
- 并发创建 48 个 release 必须无冲突。
- 创建失败时只清理当前线程占位但未写入 `release.json` 的目录。

### 7.2 路径边界

所有 Release 文件操作必须保证：

- release dir resolve 后必须在 `.musicforge/releases/` 下。
- release-export dir resolve 后必须在当前 release dir 下。
- ZIP entry 不能以 `/` 开头。
- ZIP entry 不能包含 `..`。
- ZIP entry 不能包含盘符。
- ZIP entry 不能包含反斜杠路径逃逸。
- 复制 Project final-export 文件时，源路径 resolve 后必须在 Project 的 `final-export/` 下。

### 7.3 原子写

以下文件必须用同目录 temp + replace：

- `release.json`
- `release-qa.json`
- `release-signoff.json`
- `release-export/manifest.json`
- `release-export/tracklist.json`

事件文件可以 append，但必须在 Store lock 内完成。

## 9. Track Snapshot 规则

添加 track 时，必须读取：

- Project document。
- `final_version_id`。
- final version summary。
- `final-export/manifest.json`。
- `delivery-qa.json`。
- `delivery-signoff.json`。

然后写入安全摘要：

```json
{
  "track_id": "track-000001",
  "track_number": 1,
  "disc_number": 1,
  "title": "Song Title",
  "project_id": "project-000001",
  "version_id": "version-000003",
  "final_export_hash": "sha256...",
  "delivery_qa_hash": "sha256...",
  "delivery_signoff_hash": "sha256...",
  "project_snapshot": {
    "name": "Song Project",
    "final_version_id": "version-000003",
    "quality_score": 87,
    "tempo_bpm": 118,
    "key": "C",
    "duration_beats": 128
  },
  "qa_snapshot": {
    "status": "passed",
    "handoff_ready": true
  },
  "signoff_snapshot": {
    "status": "signed",
    "final_version_id": "version-000003"
  }
}
```

不允许写入：

- final export 绝对路径。
- zip 绝对路径。
- provider raw response。
- reference 原文。
- asset 原始内容。

## 10. Release Source Hash

Release QA 和 Signoff 都需要 source hash。

Release source hash 应包含：

- release schema version。
- release_id。
- release metadata。
- tracks 顺序。
- 每个 track 的 `project_id`。
- 每个 track 的 `version_id`。
- 每个 track 当前 Project final_export manifest hash。
- 每个 track 当前 Delivery QA source hash。
- 每个 track 当前 Delivery Signoff source hash。
- release export manifest hash，如果 signoff 绑定 export。

不能包含：

- updated_at。
- generated_at。
- non-semantic UI expanded/collapsed state。
- event log。

这样可以避免无意义 stale，也能挡住真实交付变更。

## 11. Release QA 检查矩阵

新增：

```text
song_agent/release_qa.py
```

### 11.1 总体检查

| check_id | 说明 | 失败级别 |
| --- | --- | --- |
| release_exists | release.json 可读 | failed |
| metadata_complete | name / type / primary_artist 基本完整 | warning 或 failed |
| track_count | track 数量满足 release_type | failed |
| track_order_unique | track_number + disc_number 唯一 | failed |
| no_hidden_tracks | 引用 Project 未 hidden 或允许 hidden | failed |
| no_duplicate_project_version | 同一 project/version 重复入包 | warning |
| source_hash_current | release source hash 与 QA 一致 | stale |
| redaction_scan | release 文档和导出摘要无敏感值 | failed |

### 11.2 Track 级检查

| check_id | 说明 | 失败级别 |
| --- | --- | --- |
| project_exists | Project 存在 | failed |
| version_exists | version_id 存在 | failed |
| version_is_final | version_id 等于 Project final_version_id | failed |
| final_export_exists | Project final-export 目录存在 | failed |
| final_export_manifest_exists | Project final-export manifest 存在 | failed |
| final_export_manifest_safe | manifest 无路径逃逸 | failed |
| final_export_core_files | Project 核心交付文件存在 | failed |
| delivery_qa_exists | delivery-qa.json 存在 | failed |
| delivery_qa_passed | Delivery QA passed 或 warning | failed 或 warning |
| delivery_qa_current | Delivery QA source hash 当前 | failed |
| delivery_signoff_exists | delivery-signoff.json 存在 | failed |
| delivery_signoff_final_version | Signoff final_version_id 匹配 track version | failed |
| delivery_signoff_current | Signoff 绑定当前 Delivery QA | failed |
| track_snapshot_current | track snapshot 未 stale | warning |
| zip_integrity | Project final-export.zip 与 manifest 一致 | warning 或 failed |

### 11.3 跨曲目检查

| check_id | 说明 | 失败级别 |
| --- | --- | --- |
| title_duplicates | 曲名重复 | warning |
| artist_consistency | artist 缺失或混乱 | warning |
| language_consistency | language 不一致 | warning |
| tempo_extreme_delta | tempo 差异极大 | warning |
| key_metadata_available | key 缺失 | warning |
| audio_availability | 要求 audio 时 WAV 缺失 | failed |
| stem_availability | 要求 stems 时 stem 缺失 | failed |

### 11.4 QA 状态规则

`failed`：

- 任意 blocking check failed。
- 任意 Project 不存在。
- 任意 final version 不匹配。
- 任意 final-export 核心文件缺失。
- 任意 Delivery QA failed/stale。
- 任意 Delivery Signoff 缺失或不匹配。
- release 文档或 export 摘要出现敏感值。

`warning`：

- 没有 failed，但存在 warning。

`passed`：

- 没有 failed。
- 没有 warning。

`stale`：

- QA report 的 source hash 与当前 release source hash 不一致。

## 12. Release Export

新增：

```text
song_agent/release_export.py
```

### 12.1 Export 前置条件

普通 export 必须满足：

- Release QA 存在。
- QA source hash 当前。
- QA status 为 `passed` 或 `warning`。
- 每个 track Project Delivery Signoff 有效。

如果 QA failed：

- 返回 409。
- 不生成 release-export。

如果 QA warning：

- 允许 export。
- manifest 记录 warnings。

### 12.2 Export 输出

Release Export 目录：

```text
release-export/
  manifest.json
  README.txt
  release.json
  tracklist.json
  release-qa.json

  tracks/
    01-track-title/
      manifest.json

      project-export.json
      song-plan.json
      song.mid
      song.wav
      quality-report.json
      validator-report.json
      stems/
        ...
```

### 12.3 Track 子目录命名

命名规则：

```text
<disc>-<track>-<slug>
```

单 disc 可以简化：

```text
01-song-title
02-another-song
```

要求：

- slug 只允许 `[a-z0-9-]`。
- 空 title 使用 track id。
- 重名自动加后缀。

### 12.4 Copy 白名单

从 Project final-export 复制的文件必须在白名单：

必需：

- `manifest.json`
- `README.txt`
- `project-export.json`
- `song-plan.json`
- `song.mid`

可选：

- `song.wav`
- `quality-report.json`
- `validator-report.json`
- `stems/**`
- `assets/*.json`
- `references-summary.json`
- `context-pack-summary.json`

禁止：

- provider raw response。
- provider snapshot 明文。
- 本机配置。
- 原始 references。
- 任意未在 Project Final Export manifest 中登记且不在内置核心清单中的文件。

## 13. Release ZIP

### 13.1 ZIP 入口

API：

```text
POST /api/releases/<release-id>/export/zip
GET  /api/releases/<release-id>/export.zip
```

### 13.2 ZIP 安全规则

构建 ZIP 时：

- 只打包 `release-export/` 下文件。
- entry path 必须是 POSIX 相对路径。
- entry path 不能包含 `..`。
- entry path 不能以 `/` 开头。
- entry path 不能包含盘符。
- entry path 不能包含控制字符。
- entry path 长度限制。
- 同名 entry 拒绝。

### 13.3 ZIP manifest 对账

Release QA 要检查：

- ZIP 存在。
- ZIP entry_count 匹配 manifest。
- ZIP entry hash 匹配 release-export 文件。
- ZIP 内 `manifest.json` 与磁盘 `manifest.json` 的核心 source hash 一致。
- ZIP 没有多余危险 entry。

## 14. Release Signoff

### 14.1 签核前置条件

普通 signoff 必须：

- Release QA 当前。
- QA status 为 `passed` 或 `warning`。
- Release Export 已生成。
- Export manifest source_hash 当前。
- 如果设置 `require_zip=true`，ZIP 必须存在且通过 QA。

如果 QA failed：

- 普通 signoff 返回 409。

### 14.2 强制签核

允许 force signoff，但必须：

- `override_reason` 非空。
- 记录当前 blockers。
- 记录当前 warnings。
- status 为 `force_signed`。
- Studio 明确展示。

强制签核不是推荐路径，只是为真实工作中“客户确认接受风险”的场景保留审计入口。

### 14.3 Reset

API：

```text
POST /api/releases/<release-id>/signoff/reset
```

要求：

- 如果没有 signoff，返回当前 not_signed。
- 如果已有 signoff，移动摘要到 history。
- 写 event。
- 删除或更新当前 `release-signoff.json` 为 not_signed，按现有 Delivery Signoff 风格选择一致实现。

## 17. 与现有能力的关系

### 17.1 与 Project Final Export

Release 不替代 Final Export。

Project Final Export 仍是单曲交付物。Release Export 只是组装多个 Project Final Export。

### 17.2 与 Delivery QA

Project Delivery QA 是 track 入包的基础。

Release QA 不重新做所有 Project 细节，但必须检查 Project Delivery QA 的当前性和 signoff 绑定。

### 17.3 与 Review Sprint

Release 层不直接读 Review Sprint 全量细节。

只通过 Project Final Export / Delivery QA 摘要获得：

- latest sprint readiness。
- closeout summary。
- signoff summary。
- metrics summary。

### 17.4 与 Asset / Reference

Release Export 不复制原始 Asset / Reference。

它只复制 Project Final Export 已经脱敏的摘要。

### 17.5 与 Provider

v3.7.0 不新增 provider 调用。

原因：

- Release Workspace 是交付编排层。
- Provider 生成和评审已经在 Project / Sprint 层。
- 发行层如果再调用 provider，容易引入不可审计的新内容。

## 18. 安全与脱敏

### 18.1 复用 redaction.py

Release QA、Release Export、Release Signoff 都必须复用：

```text
song_agent/redaction.py
```

检查范围：

- release.json。
- release-qa.json。
- release-export/manifest.json。
- release-export/release.json。
- release-export/tracklist.json。
- release-export/release-signoff.json。
- ZIP 内 JSON / TXT。

### 18.2 污染测试必须覆盖

构造污染字段：

```json
{
  "notes": "token=[REDACTED_TOKEN]",
  "metadata": {
    "local_path": "<LOCAL_ABSOLUTE_PATH>",
    "provider_response": "raw provider content should not export"
  }
}
```

要求：

- API summary 返回脱敏。
- Release Export 不写敏感值。
- Release QA raw scan 能检测未脱敏污染。
- ZIP 里无敏感值。

### 18.3 不信任 manifest

v3.6.1 已经修过 Delivery QA 不能只信 Project final-export manifest。v3.7.0 必须继承这个原则。

Release Export 不能只信 track snapshot 和 Project manifest。

必须：

- stat 实际文件。
- hash 实际文件。
- resolve 实际路径。
- 检查内置核心文件。
- 检查 ZIP entry。

## 19. 并发与状态机

### 19.1 ReleaseStore lock

ReleaseStore 需要 `RLock`。

以下操作必须在锁内完成：

- 创建 release。
- 删除 release。
- 添加 / 移除 / 重排 track。
- 写 release.json。
- 写 signoff。
- reset signoff。
- 写 event。

### 19.2 长任务

Release QA 和 Release Export 通常不需要后台 job，先同步执行即可。

如果测试发现 Release Export 很慢，先保留同步实现，不在 v3.7.0 引入新 job runner，避免范围失控。

### 19.3 状态转移

```text
draft
  -> qa_failed
  -> qa_warning
  -> qa_passed
  -> exported
  -> signed
  -> archived
```

规则：

- track 修改后，如果已签核，signoff 变 stale 或需要 reset。
- track 修改后，latest QA 变 stale。
- export 后如果 track 修改，export summary stale。
- signoff 后不能修改 track，除非先 reset signoff。建议修改接口对 signed release 返回 409。
- archive 后只读。

## 24. 风险清单

### P1：Release QA 信任 track snapshot

风险：

- track snapshot 可能过期。
- Project final version 可能变化。
- Project Delivery Signoff 可能 reset。

要求：

- QA 必须实时读取 Project Store。
- snapshot 只用于展示。
- source hash 必须覆盖当前 Project 交付状态。

### P1：Release Export 复制越界文件

风险：

- Project final-export manifest 被污染。
- track path 指向外部文件。

要求：

- 源路径 resolve 必须在 Project final-export 目录下。
- entry path 必须白名单。
- ZIP entry 必须安全。

### P1：已签核 Release 被修改

风险：

- 签核后 track 被替换，signoff 仍显示 signed。

要求：

- signed release 默认禁止 add/remove/reorder/update。
- 如必须修改，先 reset signoff。

### P1：整包 ZIP 泄露本机路径

风险：

- manifest 写入绝对路径。
- README 写入本机路径。

要求：

- ZIP metadata 不写 path。
- redaction raw scan 先于 sanitized output。
- release-check 固化污染场景。

### P2：Release Export 和 Project Final Export 生命周期混乱

风险：

- Project 重新 Final Export 后，Release Export 没有 stale。

要求：

- Release source hash 覆盖 Project final-export manifest hash。
- QA refresh 能标记 stale。
- Signoff 绑定当前 source hash。

### P2：Studio 过度复杂

风险：

- 一版做太多 UI 细节导致不稳。

要求：

- v3.7.0 UI 先以表格、按钮、详情面板为主。
- 不强求复杂拖拽。
- 先把流程跑通。

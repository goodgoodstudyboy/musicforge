# v4.4.0 Music Acceptance Lab 音乐成品自验与听审工作台施工图

创建日期：2026-05-18  
目标版本：v4.4.0  
当前稳定基线：v4.3.1  
角色定位：Reviewer 施工图 / 开发执行指南 / 自测验收规范

---

## 1. 背景

MusicForge 已经完成了从创作到发行提交前归档的本地闭环。

截至 v4.3.1，系统已经具备：

- 自动生成 SongPlan / MIDI。
- Project 多版本管理。
- 局部编辑、可视化编辑、片段插入、模板复用。
- Audition / Review / Candidate / Review Sprint。
- Final Export / Delivery QA / Release Workspace。
- Release Metadata / Distribution Package / Submission Package。
- 离线 verifier、签核、防篡改、路径安全、脱敏扫描。

但是现在还缺一个关键能力：

> 开发人员必须能自己证明“生成出来的音乐没有明显问题”。

过去的 release-check 更偏工程正确性：

- JSON 是否有效。
- MIDI 是否生成。
- ZIP 是否安全。
- Hash 是否对得上。
- 签核是否防篡改。

这些都很重要，但它们不能回答：

- 这首歌是不是空的？
- MIDI 有没有明显卡顿、超长音、重叠、全曲静音？
- 旋律是否异常机械？
- 鼓点是否缺失？
- 和弦/低音是否离谱？
- 歌曲结构是否像一首完整歌？
- 是否能渲染 WAV 并被听审？
- 开发人员是否真的听过并给出验收结论？

所以 v4.4.0 要做一个大跨步：建立 Music Acceptance Lab。

---

## 2. v4.4.0 定位

v4.4.0 做：

> Music Acceptance Lab：面向开发自测和业务验收的音乐成品体检、试听、听审、签核与报告系统。

它不是普通的单元测试。

它要让开发完成一个版本后，必须自己完成：

1. 生成多首代表性歌曲。
2. 渲染 MIDI。
3. 在可配置 renderer 存在时渲染 WAV。
4. 自动分析音乐结构、音符、轨道、动态、密度、重复、静音、异常音域。
5. 生成可听审 audition playlist。
6. 在 Studio 里逐首听审并打分。
7. 给出通过/需修复/拒绝结论。
8. 输出 `music-acceptance-report.json`。
9. release-check 至少跑一条 synthetic acceptance smoke。
10. 开发汇报时附带验收摘要。

---

## 3. 这一步为什么是大跨步

前面 v0.1 到 v4.3 的主线是“能生成、能编辑、能交付、能签核”。

v4.4 开始要回答“成品是否可用”。

这会把系统从工程流水线推进到产品验收体系：

```text
工程正确性
  -> 音乐结构正确性
  -> 音频可听性
  -> 人工听审确认
  -> 可审计验收报告
```

这个版本完成后，开发人员不能只说：

```text
pytest passed
```

还要说：

```text
acceptance suite 通过，生成 6 首，MIDI/WAV 可试听，自动体检无 blocking，人工听审 6/6 accepted。
```

---

## 4. 明确不做什么

v4.4.0 不做以下事项：

- 不做真正的 AI 音频主观美学判断。
- 不做人声合成。
- 不做母带处理。
- 不做自动混音评分。
- 不做在线播放平台上传。
- 不要求所有用户机器都配置 FluidSynth / SoundFont。
- 不强制真实 WAV 渲染通过，除非本机 renderer 已配置。
- 不用外部商业音频分析 API。
- 不使用真实版权素材。
- 不把人工听审伪装成自动判断。

v4.4.0 的原则：

- 自动体检负责发现明显错误。
- 人工听审负责确认音乐可接受。
- 系统负责把这两件事记录成可审计报告。

## 5. 核心概念

### 5.1 Acceptance Suite

一次音乐验收套件。

它包含多个 test case，每个 test case 会生成一首歌或一个版本。

示例：

```text
.musicforge/
  acceptance/
    suite-000001/
      suite.json
      cases/
        case-000001/
          request.json
          run/
          music-health.json
          listening-review.json
          acceptance-result.json
      music-acceptance-report.json
      acceptance-signoff.json
      events.jsonl
```

### 5.2 Acceptance Case

一首被验收的歌。

来源可以是：

- 新生成 job。
- Project version。
- Final Export。
- Release track。
- Submission target 引用的 Distribution package。

v4.4.0 最少实现：

- 从 request 生成。
- 从 Project version 验收。

### 5.3 Music Health Report

自动音乐体检报告。

它检查：

- SongPlan schema。
- MIDI 文件。
- track coverage。
- section coverage。
- note count。
- silence。
- note overlaps。
- note duration。
- pitch range。
- velocity range。
- density。
- repetition。
- quality score。
- hook presence。
- arrangement balance。
- audio render status。

### 5.4 Listening Review

人工听审记录。

字段包括：

- rating
- status
- notes
- issues
- accepted_by
- listened_at
- audio_mode
- playback_confirmed

### 5.5 Acceptance Signoff

整套验收签核。

只有当所有 blocking checks 通过，并且人工听审全部 accepted 或 waiver 后，才可签核。

## 9. 自动音乐体检维度

### 9.1 SongPlan 基础

Checks：

| check_id | blocking | 说明 |
| --- | --- | --- |
| song_plan_parse | yes | SongPlan 可解析 |
| title_present | no | title 非空 |
| tempo_range | yes | tempo 40-220 |
| meter_supported | yes | meter 合法 |
| sections_present | yes | 至少 3 个 section |
| tracks_present | yes | 至少 melody/chords/bass/drums 之一 |
| total_duration_reasonable | yes | 不能太短或极长 |

### 9.2 Section / Arrangement

Checks：

| check_id | blocking | 说明 |
| --- | --- | --- |
| section_timeline_contiguous | yes | section 时间线连续 |
| section_duration_positive | yes | 每段 bars > 0 |
| hook_or_chorus_present | warning | 有 hook 或 chorus |
| energy_shape_reasonable | warning | chorus/hook 能量不低于 verse |
| arrangement_density_not_flat | warning | 全曲密度不能完全平 |

### 9.3 Track Coverage

Checks：

| check_id | blocking | 说明 |
| --- | --- | --- |
| note_bearing_track_exists | yes | 至少一个有音符的 track |
| melody_or_lead_exists | warning | melody/lead 存在 |
| bass_or_low_support_exists | warning | bass 或低音乐器存在 |
| harmony_support_exists | warning | chord/pad/harmony 存在 |
| rhythm_support_exists | warning | drums/percussion 存在 |
| empty_tracks_limited | warning | 空轨不能太多 |

### 9.4 Notes

Checks：

| check_id | blocking | 说明 |
| --- | --- | --- |
| note_count_minimum | yes | 全曲 note 数至少阈值 |
| note_duration_positive | yes | 所有 note duration > 0 |
| note_within_song_bounds | yes | note 不越界 |
| pitch_range_valid | yes | MIDI pitch 0-127 |
| velocity_range_valid | yes | velocity 1-127 |
| no_extreme_overlaps | warning | 同轨重叠不能过多 |
| no_excessive_long_notes | warning | 超长音数量受限 |
| no_mechanical_grid_only | warning | 过度机械重复提示 |

### 9.5 Silence / Density

Checks：

| check_id | blocking | 说明 |
| --- | --- | --- |
| leading_silence_limited | warning | 开头空白不能过长 |
| trailing_silence_limited | warning | 结尾空白不能过长 |
| longest_internal_silence_limited | warning | 中间大段静音提示 |
| density_minimum | yes | 每 8 bars 至少有一定 note |
| density_peak_exists | warning | 有高潮密度峰值 |

### 9.6 MIDI

Checks：

| check_id | blocking | 说明 |
| --- | --- | --- |
| midi_exists | yes | MIDI 文件存在 |
| midi_header_valid | yes | MThd |
| midi_note_events_present | yes | note_on/off 存在 |
| midi_tracks_match_plan | warning | MIDI track 数和 plan 轨道可解释 |
| midi_eot_present | yes | EOT 存在 |

可以复用现有 MIDI 测试里的解析工具，或提取公共 parser。

### 9.7 WAV / Audio

Renderer 未配置时：

- 不 blocking。
- report 写 `audio_status=skipped_renderer_not_configured`。

Renderer 已配置时：

Checks：

| check_id | blocking | 说明 |
| --- | --- | --- |
| audio_rendered | yes | song.wav 存在 |
| wav_header_valid | yes | RIFF/WAVE |
| wav_duration_reasonable | warning | WAV 时长和 SongPlan 接近 |
| wav_nonzero_size | yes | 文件非空 |

不要在 v4.4.0 做 RMS / LUFS 复杂分析，除非实现成本很低。

## 10. Acceptance 判定规则

每个 case 最终状态：

```text
pending
generated
health_failed
needs_review
accepted
waived
rejected
```

自动体检：

- 有 blocking failed -> `health_failed`
- 无 blocking failed -> `needs_review`

人工听审：

- `accepted`：通过。
- `needs_fix`：需要修复。
- `rejected`：拒绝。
- `waived`：有问题但本次允许，需要 reason。

suite 通过条件：

- 所有 case 有 health report。
- 无 blocking failed，或有明确 waiver。
- 所有 case 有 listening review。
- 每个 review 必须 `playback_confirmed=true`。
- rating >= min_rating，默认 3。
- 所有 case status in `accepted|waived`。

## 11. 开发人员自验要求

开发 v4.4.0 完成后，不能只跑单测。

必须完成一套 developer acceptance suite。

### 11.1 最低 case 数

至少 6 首：

1. upbeat pop
2. ballad
3. electronic / synth
4. hip-hop / beat-driven
5. instrumental cinematic
6. acoustic / singer-songwriter

如果 provider 不配置，全部用 local deterministic generation。

### 11.2 每首必须有

- request.json
- song-plan.json
- song.mid
- validator-report.json
- quality.json 或 health report 中推断 quality
- music-health.json
- listening-review.json

如果 renderer 已配置：

- song.wav
- WAV 可播放

如果 renderer 未配置：

- 必须明确记录 audio skipped 原因。
- 不得伪造 WAV。

### 11.3 人工听审必须填写

每首：

```text
rating: 1-5
status: accepted / needs_fix / rejected / waived
playback_confirmed: true
notes: 至少 10 个字符
```

不能空 notes。

## 14. CLI

新增命令：

```powershell
python -m song_agent.cli acceptance-check
```

用途：

- 本地生成一套默认 developer suite。
- 运行自动体检。
- 如果 `--auto-review`，允许在 CI/smoke 中写 synthetic review，但必须标明 `review_mode=synthetic`，不能冒充人工听审。

参数建议：

```text
--out .musicforge/acceptance
--cases 6
--render-audio auto|always|never
--auto-review
--min-rating 3
--json
--report-out <path>
```

### 14.1 默认行为

`acceptance-check` 默认：

- 生成 6 个本地 deterministic case。
- 渲染 MIDI。
- 如果 renderer 配置有效，渲染 WAV。
- 运行 health。
- 不自动 accepted。
- 输出 `needs_review`。

用于 release-check 时：

```powershell
python -m song_agent.cli acceptance-check --cases 2 --auto-review --render-audio never
```

这只证明流程通，不代表真实人工听审。

开发最终汇报必须另跑 Studio 人工听审，或至少 CLI 生成后手动播放并写 review。

## 15. release-check 集成

新增 smoke：

```text
v4.4 music acceptance lab smoke
```

覆盖：

1. 创建 suite。
2. 添加 2 个 generated cases。
3. 生成 SongPlan/MIDI。
4. 运行 health。
5. 自动体检 passed/warning。
6. renderer 未配置时 audio skipped 合法。
7. 写 synthetic review。
8. build report。
9. signoff。
10. 尝试签核后改 review -> 409。
11. 污染 report 中本机路径/secret -> redaction failed。
12. 缺 MIDI -> health failed。

推荐输出：

```text
v4.4 music acceptance lab smoke: ok
  suite=suite-000001
  cases=2
  health=passed
  audio=skipped_renderer_not_configured
  review=synthetic
  sign=signed
  missing_midi=failed
  signed_guard=409
  redaction=failed
```

## 21. 质量阈值建议

默认阈值：

```text
min_sections = 3
min_total_notes = 64
min_note_tracks = 3
min_quality_overall = 75
max_blocking_failures = 0
max_warning_count = 8
min_rating = 3
min_accepted_cases = all
```

不同风格可以放宽：

- instrumental：不要求 lyric_fit。
- ambient：允许较低 note density，但不能全曲空。
- hip-hop：允许 melody 缺失，但 rhythm/bass 必须存在。
- acoustic：允许 drums 缺失，但 melody/chords/bass 需要足够。

v4.4.0 可以先把这些写成硬编码 profile，v4.5 再做可配置 acceptance profiles。

## 22. 安全要求

Acceptance 报告可能包含人工 notes，所以要继续做脱敏：

- `sk-*`
- GitHub token
- Bearer token
- Windows path
- UNC path
- `/Users/...`
- `/home/...`
- `api_key`
- `local_path`
- `source_path`
- `raw_provider_response`

人工 notes 写入前必须 `sanitize_sensitive_text()`。

report 和 signoff 都必须用 `sanitize_metadata()`。

## 23. 签核防篡改

Acceptance Signoff 参考 v3.8 / v4.3：

- report hash。
- signoff sidecar payload hash。
- 签核后禁止修改 suite/case/review/report。
- reset signoff 才能修改。

必须有回归：

- 篡改 `listened_by` -> verifier/report check failed。
- 篡改 report status -> failed。
- 签核后改 review -> 409。

## 28. Reviewer 必查点

Reviewer 检查 v4.4.0 时，不只看测试。

必须查：

1. `acceptance-check` 是否真的生成音乐 case。
2. health analyzer 是否能抓空曲、坏 MIDI、坏音符。
3. renderer 未配置是否清晰 skipped，而不是伪造通过。
4. renderer 配置时是否真的产生 WAV。
5. listening review 是否要求 playback_confirmed。
6. accepted review 是否要求 notes。
7. 签核后是否禁止改 review/case/report。
8. report 是否脱敏。
9. release-check 是否有 v4.4 smoke。
10. 开发汇报是否包含 6 首自验摘要。

这正好对应当前需求：开发人员完成这一步后，必须自己完成测试验收，自己确定生成出来的音乐没有明显问题。

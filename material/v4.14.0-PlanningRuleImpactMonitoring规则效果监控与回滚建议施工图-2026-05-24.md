# v4.14.0 Planning Rule Impact Monitoring 规则效果监控与回滚建议施工图

当前稳定基线：v4.13.1

目标版本：v4.14.0

建议版本主题：Planning Rule Impact Monitoring / 规则上线效果监控、漂移预警与回滚建议

编写时间：2026-05-24

适用对象：

- MusicForge 新开发人员
- reviewer
- 负责验收、规则治理、Release Signoff 的开发人员

---

## 1. 背景

v4.13.1 已经完成 Planning Rule Governance 的关键闭环：

```text
Planning Rule Set
  -> Planning Rule Simulation
  -> Promotion
  -> Approval
  -> Active Rule Version
  -> Fix Plan records active version
  -> Rollback
```

并且 v4.13.1 修掉了关键完整性问题：

- `ruleset-frozen.json` hash 会校验。
- `version.json` 里的 `promoted_from + approval` source hash 也会校验。
- 篡改 `promoted_from.recommendation` 或 `approval.approved_by` 后，Release Signoff 会返回 409。

现在系统已经能安全地“把一个规则版本上线”。

但上线后还缺一层：

```text
这个 active rule version 用在多少 Fix Plan？
它上线后 Outcome Review 有没有真的变好？
它有没有造成更多 stale、waiver、force close、synthetic-only 风险？
是否应该继续观察、要求更多人工复验，还是建议回滚？
```

这就是 v4.14.0 要做的事情。

---

## 2. 一句话目标

v4.14.0 要新增 Planning Rule Impact Monitoring：基于已上线的 Planning Rule Version、使用该规则生成的 Fix Plan、后续 Fix Sprint 和 Outcome Review，生成 deterministic impact report、adoption metrics、before/after trend、risk drift warning 和 rollback recommendation；报告可接入 Studio、CLI、Project/Release/Final Export 和 Release Signoff，但不得自动回滚、不得自动修改规则、不得自动创建 Fix Plan。

---

## 3. 为什么现在做 v4.14

v4.12 解决：

```text
候选规则在历史样本上看起来怎么样？
```

v4.13 解决：

```text
候选规则如何被人工批准并成为 active version？
```

v4.14 要解决：

```text
active version 上线后真实闭环效果怎么样？
```

没有 v4.14，会有几个风险：

- 规则上线后只知道“它上线了”，不知道“它效果如何”。
- Fix Plan 记录了 `planning_rule_version_id`，但没有聚合分析。
- Release Signoff 可以要求 Governance，但不知道当前 active rules 有没有负面漂移。
- Rollback 只能靠人主观判断，没有系统建议。
- 进入 v5 真实音频后，规则变化带来的问题会更难定位。

所以 v4.14 是进入 v5 前最后一层“观测与反馈治理”。

---

## 4. 核心原则

### 4.1 只监控，不自动回滚

即使 report 给出 `rollback_recommended`，系统也不能自动 rollback。

必须由人工去执行：

```text
planning-rule-governance rollback
```

### 4.2 报告必须 deterministic

同一份本地数据，多次 refresh 结果必须一致。

不能调用 provider。

不能依赖当前时间以外的随机因素。

### 4.3 只用本地证据

Impact report 只读取：

- Planning Rule Governance versions
- Acceptance Fix Plans
- Acceptance Fix Sprints
- Fix Plan Outcome Reviews
- Acceptance KB summary
- Acceptance Analytics summary

不读取外部网络。

### 4.4 明确人工与 synthetic 的区别

manual Outcome Review 权重高于 synthetic。

synthetic-only 数据只能作为 warning，不得作为强通过依据。

### 4.5 stale 数据不能进入通过结论

如果 source Fix Plan / Outcome Review / active version stale：

- impact report 可以生成，但 status 至少是 `warning`。
- Release Signoff require gate 必须 409。

### 4.6 不改历史 plan

v4.14 只能读历史 Fix Plan 的 `planning_rule_governance` source。

不能回写旧 plan。

---

## 5. v4.14 不做什么

明确不做：

- 不自动 rollback。
- 不自动 promote 新 ruleset。
- 不自动创建 simulation。
- 不自动创建 Fix Plan。
- 不自动创建 Fix Sprint。
- 不自动 apply edits。
- 不调用 provider judge。
- 不做跨机器多人协作锁。
- 不做长期数据库。
- 不做真实音频新能力。

## 6. 新增模块

新增文件：

```text
song_agent/planning_rule_impact.py
```

职责：

- 收集 active / historical Planning Rule Version 使用情况。
- 聚合 Fix Plan adoption metrics。
- 聚合 Outcome Review effectiveness。
- 计算 before/after trend。
- 生成 risk drift warning。
- 给出 deterministic recommendation。
- 提供 export/signoff summary。

不要把它塞进 `planning_rule_governance.py`：

- Governance 负责状态变更。
- Impact 负责观测分析。
- 两者分开后，reviewer 更容易确认 Impact 不会修改 active pointer。

## 9. 核心指标

### 9.1 Adoption Metrics

统计：

- active version 被多少 Fix Plan 使用。
- legacy_default plan 数量。
- superseded version plan 数量。
- active version adoption rate。

字段：

```json
{
  "adoption": {
    "active_plan_count": 4,
    "legacy_plan_count": 2,
    "superseded_plan_count": 1,
    "total_plan_count": 7,
    "active_adoption_rate": 57,
    "status": "partial"
  }
}
```

状态：

```text
missing
low
partial
healthy
dominant
```

建议口径：

- `missing`: total=0
- `low`: active rate < 25
- `partial`: 25 <= active rate < 70
- `healthy`: 70 <= active rate < 95
- `dominant`: >= 95

### 9.2 Outcome Effectiveness

从 Fix Plan Outcome Review 读取：

- plan_effectiveness_score
- ranking_alignment_score
- manual_recheck_confirmed
- synthetic_only
- item outcome observed_effectiveness_score
- kb_evidence_helpfulness

按 version 聚合：

```json
{
  "version_id": "prgv-000003",
  "plan_count": 4,
  "review_count": 3,
  "manual_review_count": 2,
  "synthetic_review_count": 1,
  "average_plan_effectiveness_score": 86,
  "average_ranking_alignment_score": 79,
  "average_observed_effectiveness_score": 82
}
```

### 9.3 Before / After

比较对象：

- active version samples
- previous version samples
- legacy_default samples

输出：

```json
{
  "before_after": {
    "baseline_group": "previous_or_legacy",
    "baseline_review_count": 3,
    "active_review_count": 4,
    "effectiveness_delta": 8,
    "ranking_alignment_delta": 4,
    "manual_only_delta": 1
  }
}
```

如果样本不足：

```text
insufficient_data
```

### 9.4 Risk Drift

必须统计：

- synthetic_only rate
- waived item rate
- force closed rate
- stale source rate
- no_kb_history rate
- hidden KB included count
- candidate_worse promoted count

输出：

```json
{
  "risk_drift": {
    "synthetic_only_rate": 50,
    "waiver_rate": 25,
    "force_close_rate": 0,
    "stale_source_count": 0,
    "warnings": ["synthetic_only_sample_high"]
  }
}
```

## 10. Recommendation 规则

建议枚举：

```text
insufficient_data
continue_monitoring
increase_manual_review
candidate_improving
rollback_watch
rollback_recommended
```

推荐逻辑建议：

### 10.1 insufficient_data

条件：

- observed_review_count < 2
- 或 active_plan_count < 2

### 10.2 candidate_improving

条件：

- manual_review_count >= 2
- effectiveness_delta >= 5
- ranking_alignment_delta >= 0
- force_close_rate_delta <= 0
- stale_source_count == 0

### 10.3 continue_monitoring

条件：

- 有改善，但样本仍少。
- 或 active adoption partial。

### 10.4 increase_manual_review

条件：

- synthetic_only_rate >= 50
- manual_review_count < synthetic_review_count

### 10.5 rollback_watch

条件：

- effectiveness_delta <= -5
- 或 waiver_rate_delta >= 20
- 或 force_close_rate_delta > 0

### 10.6 rollback_recommended

条件：

- manual_review_count >= 2
- effectiveness_delta <= -10
- ranking_alignment_delta < 0
- 或 force_close_rate_delta >= 20

重要：

```text
rollback_recommended 只是建议，不能自动执行 rollback。
```

## 11. Source Hash

Impact report source hash 必须覆盖：

- active governance summary
- active version source_hash
- version list summary
- included Fix Plan source summaries
- included Outcome Review source summaries
- scope
- options

不要覆盖：

- report_id
- created_at / updated_at
- export path
- UI filter state

stale 判断：

- active version 切换 => stale。
- included Fix Plan stale => stale。
- included Outcome Review stale => stale。
- governance active evidence stale => stale。
- governance integrity failed => stale。
- scope source changed => stale。

## 20. Release Signoff Gate

新增参数：

```json
{
  "require_planning_rule_impact": true,
  "planning_rule_impact_report_id": "prgir-000001",
  "allow_impact_warning": true
}
```

逻辑：

- require=true 但没有 report：409。
- report stale：409。
- report active_version_id != current active version：409。
- report recommendation == rollback_recommended：409，除非 force=true + override_reason。
- report recommendation == rollback_watch：409，除非 `allow_impact_warning=true` 或 force。
- report recommendation == increase_manual_review：如果 manual_review_count < min_manual_reviews，409。
- report status failed/blocked：409。

force 也不能绕过：

- stale report。
- active version mismatch。
- report integrity failed。

force 只能绕过：

- rollback_watch。
- rollback_recommended。
- insufficient manual reviews。

但必须写 override_reason。

Signoff evidence：

```json
{
  "planning_rule_impact": {
    "status": "passed",
    "report_id": "prgir-000001",
    "active_version_id": "prgv-000003",
    "recommendation": "continue_monitoring",
    "rollback_recommended": false,
    "stale": false
  }
}
```

## 23. release-check v4.14 smoke

新增：

```text
v4.14 planning rule impact smoke
```

建议流程：

1. 创建 project/release。
2. 创建 governance active version。
3. 创建 legacy Fix Plan，确认 legacy_default。
4. 创建 active rules 后的新 Fix Plan。
5. 创建 Fix Sprint / Outcome Review。
6. Refresh Impact Report。
7. 确认 report 记录 active adoption、manual/synthetic count、recommendation。
8. Project Export / Final Export / Release Export 都有 impact summary。
9. Release Signoff require impact passed。
10. 污染 Outcome Review 或切换 active version。
11. 旧 report stale。
12. signoff require impact 返回 409。
13. 构造 negative delta，确认 rollback_watch 或 rollback_recommended。
14. force + override 可以过 rollback recommendation，但 stale 不能 force。

输出示例：

```text
v4.14 planning rule impact smoke: ok report=prgir-000001 active=prgv-000001 plans=2 reviews=1 recommendation=continue_monitoring signoff=passed stale_guard=409 rollback_watch=409/200
```

```markdown
after promotion. It aggregates Fix Plan adoption, Outcome Review effectiveness,
manual vs synthetic review coverage, risk drift, and rollback recommendations.
It is evidence-only: it never rolls back rules, applies edits, creates Fix
Sprints, or signs releases automatically.
```

CLI 示例：

```powershell
python -m song_agent.cli planning-rule-impact refresh --release-id release-000001 --json
python -m song_agent.cli planning-rule-impact show prgir-000001 --json
```

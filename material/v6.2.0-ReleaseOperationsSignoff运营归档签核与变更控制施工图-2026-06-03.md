# v6.2.0 Release Operations Signoff 运营归档签核与变更控制施工图

日期：2026-06-03  
基线版本：v6.1.1  
目标版本：v6.2.0  
角色定位：Reviewer / Planner / Release Operations Governance Designer  
项目：MusicForge / song-agent

---

## 1. 背景

v6.0.0 做了 Release Operations Dashboard，让发行负责人能一眼看到 Release / Metadata / Audio / Rights / Format / Distribution / Submission / Submission Evidence / Verifier 的总状态。

v6.1.0 做了 Release Operations Runbook，把 Operations Report 的 next_actions 转成安全执行队列，只自动跑 refresh / export / zip / verify，signoff / reset / accepted / upload 等危险动作保持 manual_required。

v6.1.1 修掉了 Runbook 对已签核对象的静默改写风险，并补了 signed mutation 回归。

现在系统已经具备：

- 单模块签核：Release、Distribution、Submission、Submission Evidence。
- 证据汇总：Operations Report。
- 安全执行记录：Operations Runbook。
- 离线包验证：Operations ZIP、Runbook ZIP。

但还缺最后一层“运营归档签核”：

- 一个 Release 已经 accepted 后，谁确认它可以归档？
- Operations Report 是否和最新 Runbook / Submission Evidence / Package verifier 对齐？
- 后续如果要改元数据、重导出、重提交，是否必须创建 Change Request？
- Operations Dashboard 的 `archived` stage 目前是 pending，缺一个真实可达的归档动作。

所以 v6.2.0 应该做：

> Release Operations Signoff / Archive / Change Request：把 v6.0 的 Dashboard 和 v6.1 的 Runbook 执行结果收口成一个可审计、可离线验证、可阻断后续静默修改的运营归档签核层。

---

## 2. 先修补的底层风险

Reviewer 在 v6.1.1 后指出：

- Runbook 入口已经挡住 signed Release export/zip。
- 但 `build_release_export_bundle()` / `build_release_export_zip()` 底层函数本身仍可被其他内部调用绕过。

v6.2.0 开工前必须先收掉：

- `build_release_export_bundle(..., allow_signed=False)` 默认拒绝 signed / archived Release。
- `build_release_export_zip(..., allow_signed=False)` 默认拒绝 signed / archived Release。
- Release signoff 内部需要刷新 signoff sidecar / rebuild ZIP 时，显式传 `allow_signed=True`。
- 补底层单元测试：signed release 直接调用 helper 默认失败，ZIP 字节不变；`allow_signed=True` 仅用于签核内部通道。

这部分可以作为 v6.1.2 hotfix 提交，也可以作为 v6.2.0 第一提交。建议先单独提交，便于回滚和 review。

## 3. v6.2.0 总目标

新增 Release Operations Signoff。

一句话目标：

> 当 Release 已完成 accepted 证据、Operations Report 当前无 blocker、Runbook 安全动作已完成或只剩人工确认项、所有相关离线 verifier 通过时，允许创建 Operations Signoff，并可将 Release Operations stage 推进到 archived；签核后任何会改变发行证据链的动作都必须先创建并批准 Operations Change Request。

完成后，用户应该能：

- 在 Studio 的 Release Operations 面板看到 `Sign Operations`。
- 看到归档 gate：Operations Report、Runbook、Release ZIP、Distribution ZIP、Submission ZIP、Submission Evidence ZIP 是否全部 current / verified。
- 签核后生成 `operations-signoff.json`。
- 导出 Operations Archive Package，并用离线 verifier 验证。
- 如果签核后需要修改，创建 `Operations Change Request`，记录原因、影响范围、批准人、需要 reset 的签核项。
- Operations Report 的 `archived` stage 从 pending 变成可达。

---

## 4. 非目标

v6.2.0 不做：

- 不接真实 DSP API。
- 不自动上传或自动 accepted。
- 不自动 reset 任何签核。
- 不自动批准 Change Request。
- 不做多人权限系统。
- 不把平台账号、cookie、token、外部后台链接写入归档包。
- 不把所有下游大包复制进 Operations Archive。只写 summary、manifest hash、package sha、verifier summary。

## 6. Gate 规则

正常 Operations Signoff 必须满足：

- Operations Report current_stage 是 `accepted`。
- Operations Report integrity OK。
- Operations Report stale=false。
- blocker_count == 0。
- Runbook 不 stale。
- Runbook 没有 failed auto_safe item。
- Runbook 如果有 manual_required item，必须都是 signoff/accepted/upload 这类已由外部证据满足或 acknowledged。
- Release ZIP verifier passed/warning。
- Distribution package verifier 全部 passed/warning。
- Submission package verifier 全部 passed/warning。
- Submission Evidence package verifier 全部 passed/warning。
- Submission Evidence accepted_count 覆盖全部 submission item。
- redaction summary passed。

force signoff：

- 可以允许 warning。
- 可以允许某些非阻断 manual_required acknowledged。
- 不能绕过：
  - stale report。
  - integrity failed。
  - failed verifier。
  - accepted evidence missing。
  - redaction failed。
  - signed mutation evidence mismatch。

---

## 7. Archive Stage

v6.0 的 Operations stages 中 `archived` 一直是 pending。v6.2.0 要让它可达：

- 如果 Operations Signoff status in `signed|force_signed`，stage `archived` 为 passed。
- 如果没有 signoff，但 current_stage 已 accepted，archived 为 pending。
- 如果 signoff stale / integrity failed，archived 为 failed。

Operations Dashboard summary 增加：

```json
{
  "operations_signoff": {
    "status": "signed",
    "signed_at": "...",
    "signed_by": "local-user",
    "integrity_ok": true,
    "stale": false
  }
}
```

## 11. Export / Verifier

Operations Archive ZIP 只放摘要证据：

```text
operations-archive-manifest.json
operations-signoff.json
operations-report.json
latest-runbook-summary.json
verifier-summaries.json
package-ledger.json
change-request-summary.json
README.txt
```

Verifier 检查：

- ZIP safe path / raw backslash / duplicate / zip bomb。
- manifest.files hash/size。
- manifest.zip.entries 不扩权。
- operations-signoff payload_hash。
- operations-report integrity。
- runbook summary hash。
- package ledger hash。
- verifier summaries 全部 passed/warning。
- signoff source hash 与 operations report 对齐。
- `--require-signed` 时必须 signed/force_signed。
- redaction scan。

---

## 12. Change Request Guard

签核后，以下操作应提示需要 Operations Change Request：

- Release metadata 修改。
- Release export/zip rebuild。
- Distribution export/zip rebuild。
- Submission export/zip rebuild。
- Submission Evidence export/zip rebuild。
- Rights clearance report refresh。
- Format decision change。
- Audio/mastering/encoded audio evidence change。

v6.2.0 不一定要把所有旧 endpoint 都硬挡住，但至少：

- Operations Dashboard 必须显示 “signed but changed / change request required”。
- Release Operations Signoff gate 必须在 source hash 变化后 stale。
- 如果有 approved Change Request，reset Operations Signoff 时要记录 change_request_id。

## 15. Reviewer 验收重点

Reviewer 要重点看：

- Operations Signoff 是否能在 accepted 缺失时通过。若能，P1。
- force 是否能绕过 stale / integrity / redaction。若能，P1。
- Archive verifier 是否信任 `zip.entries` 扩权。若能，P1。
- 签核后 source 变化是否仍显示 archived passed。若是，P1。
- Change Request 是否能伪造 approval 绕过 integrity。若能，P1。
- Operations Archive 是否泄露本机路径/token/raw provider response。若有，P1。
- 底层 Release export/zip signed guard 是否保留。若被撤回，P1。

## 16. 后续方向

v6.3.0 可以做：

- Release Portfolio：多个 Release 的运营总览。
- Operations SLA：提交后反馈期限、accepted deadline、metadata deadline。
- Reminder / Calendar Export：本地 ICS/CSV，不接外部账号。
- Post-Release Retrospective：从 accepted evidence、change request、runbook 失败项生成复盘报告。

v6.2.0 先把单个 Release 的运营归档闭环做稳。

# v6.0.0 Release Operations Dashboard 发行运营总控台与准出编排施工图

日期：2026-06-03  
基线版本：v5.9.0  
目标版本：v6.0.0  
角色定位：Reviewer / Planner / Release Operations Designer  
项目：MusicForge / song-agent

---

## 1. 背景

MusicForge 到 v5.9.0 已经完成了一个很长的本地发行证据链：

- 生成层：SongPlan、MIDI、WAV、stems、mix、mastering、encoded audio。
- 创作层：Project、Version、Edit、Visual Editor、Clip、Template、Candidate、ReviewTask、ReviewSprint。
- 质量层：Quality、Acceptance、Human Review、Audio Review、Audio Revision、Mastering QA、Encoded Audio Acceptance。
- 发行层：Release、Release Export、Release ZIP、Release Metadata、Final Export、Distribution Package、Submission Package。
- 决策层：Format Decision、Planning Rules、Impact Monitoring、Rights Clearance。
- 提交后：Submission Evidence Archive，记录平台提交回执、反馈、重提、accepted/rejected evidence。
- 安全层：大量 source hash、integrity hash、stale guard、offline verifier、redaction scan、signed immutable guard。

这说明系统的“单项能力”已经足够多。现在的主要问题不是缺某一个 gate，而是：

- 操作入口分散在 Release、Project、Distribution、Submission、Acceptance、Rights、Audio、Evidence 等多个区域。
- 开发或业务想知道“这张 Release 到底还差什么才能发”，需要来回点很多 tab。
- 每个模块都有自己的 report / signoff / verifier，但缺少一个聚合的 Operations Readiness View。
- release-check 能证明系统内部链路，但真实使用时需要一个面板告诉开发下一步应该做什么。
- 多个 Distribution Target / Submission Batch / Evidence Package 的状态不能一眼看出。
- 一个 Release 是否已经从“可本地交付”推进到“可提交、已提交、已接受、可归档”，还没有统一状态机。

所以 v6.0.0 不建议继续堆一个新的专业 gate，而是做一次系统级收口：

> Release Operations Dashboard：把 Release 从创作、音频、元数据、权利、格式、交付包、提交包、提交后证据的所有状态，聚合成一个本地发行运营总控台，给出 readiness、blockers、warnings、next actions、evidence graph、portable operations report。

这是一个大版本，因为它把 v3-v5 的碎片化工作台整合为一个“发行负责人可以直接看”的总控视图。

## 2. v6.0.0 总目标

新增 Release Operations Dashboard / Operations Report。

一句话目标：

> 对任意 Release，系统能生成一个只读、可刷新、可导出、可离线验证摘要的 Operations Report，聚合 Release / Distribution / Submission / Evidence / Rights / Audio QA / Acceptance / Metadata / Format Decision / Export / Signoff 的当前状态，并给出清晰的 blocker、warning、next action 和 readiness stage。

v6.0.0 完成后，用户应该能在一个页面回答：

- 这张 Release 当前处于哪个运营阶段？
- 是否已经完成音频、元数据、权利、格式、交付包、提交包、提交后证据？
- 哪些 gate 是 failed / warning / missing / stale？
- 哪个 Distribution Target 还没签核？
- 哪个 Submission 还没提交或没 accepted？
- 哪条 Evidence 是 stale？
- 离线 verifier 是否都通过？
- 下一步应该按什么顺序执行？
- 这张 Release 是否可以进入“运营归档”？
- 如果不可以，具体 blockers 是什么？

## 3. 非目标

v6.0.0 不做以下事情：

- 不接真实 DSP / 发行商 API。
- 不自动上传 Distribution / Submission / Evidence ZIP。
- 不自动 signoff 任何 gate。
- 不自动 reset 任何 signoff。
- 不自动修改 Release Metadata / Rights / Audio Review / Submission Evidence。
- 不自动 apply ReviewTask / FixSprint。
- 不保存平台账号、cookie、token、OAuth、API key。
- 不替代各模块原有 verifier。
- 不把本机路径、token、provider raw response、平台后台敏感 URL 写进 Operations Export。
- 不实现完整生产项目管理系统、多人权限、云端协作。

v6.0 是本地运营总控与准出编排，不是平台自动化。

## 4. 核心原则

### 4.1 Dashboard 只读

Operations Dashboard 不能改变业务状态。

允许：

- refresh report。
- read all summaries。
- classify blockers/warnings。
- suggest next actions。
- export operations report。
- build operations ZIP。
- verify operations ZIP。

不允许：

- 自动 sign Release。
- 自动 sign Distribution。
- 自动 sign Submission。
- 自动 sign Evidence。
- 自动 reset。
- 自动 upload。
- 自动 accepted。

所有改变状态的动作仍然必须在原模块里显式执行。

### 4.2 不复刻所有模块逻辑

Dashboard 不能重新实现每个 gate 的细节。它应该调用或读取现有模块的 summary / gate / verifier 结果。

聚合层只负责：

- 统一状态模型。
- 统一 blocker/warning 分类。
- 统一 next action。
- 统一 readiness stage。
- 统一导出和脱敏。

### 4.3 Source Hash 必须绑定被聚合证据

Operations Report 必须有自己的 `source_hash` 和 `integrity_hash`。

source 必须包含：

- Release snapshot。
- Release signoff summary。
- Release export summary。
- Release ZIP verifier summary。
- Metadata QA summary。
- Acceptance summary。
- Audio / Mastering / Encoded Audio summaries。
- Rights Clearance summary。
- Format Decision summary。
- Distribution target summaries。
- Distribution verifier summaries。
- Submission batch summaries。
- Submission verifier summaries。
- Submission Evidence summaries。

如果这些源变了，旧 Operations Report 必须 stale。

### 4.4 Next action 必须可解释

不要只显示 “failed”。每个 blocker 要给出：

- scope
- entity id
- check id
- severity
- message
- recommended action
- action url / action hint
- blocking stage

例如：

```json
{
  "scope": "submission_evidence",
  "entity_id": "sub-000001",
  "check_id": "evidence_not_signed",
  "severity": "blocking",
  "message": "Submission Evidence Package is not signed.",
  "recommended_action": "Open Submission Evidence panel, refresh report, export ZIP, then sign evidence.",
  "action_hint": "submission.evidence.signoff"
}
```

### 4.5 Export 必须可离线审阅

Operations Export 不需要复制所有大文件。它应该导出：

- operations report
- operations manifest
- selected summaries
- verifier summaries
- evidence graph
- README

不应该复制：

- full Release ZIP
- Distribution ZIP
- Submission ZIP
- Submission Evidence ZIP
- audio files
- artwork files
- attachment binaries

但 manifest 可以记录这些外部包的 path hint、sha256、status。

## 6. Readiness Stage

新增统一状态机。

```text
draft
  -> project_ready
  -> release_ready
  -> audio_ready
  -> metadata_ready
  -> rights_ready
  -> format_ready
  -> distribution_ready
  -> submission_ready
  -> submitted
  -> accepted
  -> archived
```

### 6.1 stage 定义

`draft`：

- Release exists but no complete tracks/export.

`project_ready`：

- Release tracks point to valid Project final/export versions.

`release_ready`：

- Release QA / Export / ZIP / Signoff passed.

`audio_ready`：

- Required audio gates pass:
  - real audio baseline
  - per-track audio review
  - audio revision closeout if required
  - mastering if required
  - encoded audio if required
  - encoded audio review if required

`metadata_ready`：

- Release Metadata QA passed.
- platform metadata export exists.

`rights_ready`：

- Rights Clearance passed and signed if required.

`format_ready`：

- Format Decision selected and compatible with Distribution targets.

`distribution_ready`：

- Every active Distribution Target required by release has:
  - QA passed/warning according to profile policy
  - Export exists
  - ZIP exists
  - Signoff current
  - verifier passed

`submission_ready`：

- Every required Submission Batch has:
  - QA passed/warning
  - Export exists
  - ZIP exists
  - Signoff current
  - verifier passed

`submitted`：

- Every required Submission item has submitted-or-later evidence.

`accepted`：

- Every required Submission item has accepted evidence.
- Submission Evidence signoff current.

`archived`：

- Operations report exported and signed.
- Operations package verifier passed.

### 6.2 stage 输出

```json
{
  "current_stage": "submission_ready",
  "next_stage": "submitted",
  "stage_progress": {
    "completed": 8,
    "total": 11,
    "percent": 73
  },
  "stage_statuses": [
    {
      "stage": "release_ready",
      "status": "passed"
    },
    {
      "stage": "submitted",
      "status": "failed",
      "blocker_count": 1
    }
  ]
}
```

## 8. Source Hash 设计

### 8.1 Operations source

`source_hash` 应由一个稳定对象生成：

```json
{
  "release": {},
  "release_signoff": {},
  "release_export_summary": {},
  "release_zip_summary": {},
  "metadata_summary": {},
  "acceptance_summary": {},
  "audio_summary": {},
  "rights_summary": {},
  "format_decision_summary": {},
  "distribution_targets": [],
  "submission_batches": [],
  "submission_evidence": [],
  "verifier_summaries": []
}
```

禁止包含：

- 本机绝对路径
- export dir
- zip path
- generated_at
- temporary file name
- raw provider response
- token

### 8.2 Stale 规则

Operations Report stale 条件：

- Release changed。
- Release signoff reset or changed。
- Release Export changed。
- Release ZIP changed。
- Metadata QA changed。
- Rights report changed。
- Format Decision changed。
- Distribution target changed。
- Distribution signoff changed。
- Distribution verifier summary changed。
- Submission batch changed。
- Submission signoff changed。
- Submission Evidence report/signoff changed。
- any package verifier result changed。

## 9. API 设计

### 9.1 获取 Operations Overview

```http
GET /api/releases/<release-id>/operations
```

返回当前 report，如果没有 report，也返回 live summary：

```json
{
  "ok": true,
  "release_id": "release-000001",
  "summary": {},
  "report": {},
  "stale": false
}
```

### 9.2 刷新 Operations Report

```http
POST /api/releases/<release-id>/operations/refresh
```

行为：

- 读取所有模块 summary。
- 不改变任何模块状态。
- 不自动运行各模块 refresh，除非已有 summary 缺失时可输出 missing。
- 生成 `.musicforge/releases/<release-id>/operations/operations-report.json`。

### 9.3 Operations Export

```http
POST /api/releases/<release-id>/operations/export
```

输出：

```text
.musicforge/releases/<release-id>/operations/operations-export/
  operations-manifest.json
  operations-report.json
  evidence-graph.json
  readiness-summary.json
  verifier-summaries.json
  README.txt
```

### 9.4 Operations ZIP

```http
POST /api/releases/<release-id>/operations/export/zip
GET  /api/releases/<release-id>/operations/export.zip
```

### 9.5 Operations Verify

```http
POST /api/releases/<release-id>/operations/verify
```

调用 `verify-release-operations-package` 逻辑。

### 9.6 Operations Signoff

v6.0 是否需要 Operations Signoff？

建议 v6.0.0 **先不做签核**，只做 report/export/zip/verify。

原因：

- 现在已经有 Release / Distribution / Submission / Evidence signoff。
- 再加 Operations Signoff 容易形成“签核套签核”的复杂度。
- v6.0 先让 Dashboard 稳定，v6.1 再决定是否做 Operations Archive Signoff。

所以 v6.0 的 operations package 只可验证，不签核。

## 13. Offline Verifier

新增：

```text
song_agent/release_operations_verifier.py
```

校验：

- ZIP 可打开。
- ZIP entry path safe。
- raw central directory path safe。
- duplicate entry failed。
- required entries exist。
- manifest schema。
- manifest.files hash match。
- manifest.zip.entries 不能扩大允许 entry。
- operations-report integrity hash。
- readiness-summary hash。
- evidence-graph hash。
- verifier-summaries hash。
- redaction scan。
- blocker/warning shape。
- source_hash present。

Operations verifier 不需要深度验证 Release ZIP / Distribution ZIP / Submission ZIP，因为 Operations ZIP 不复制这些大包。它只验证 operations report 本身未被篡改。

如果用户需要深度验证，仍然用已有：

- `verify-release`
- `verify-distribution-package`
- `verify-submission-package`
- `verify-submission-evidence-package`

### 15.5 release-check smoke

新增：

```text
v6.0 release operations dashboard smoke
```

流程：

1. 创建 project / release。
2. 生成 Release Export / ZIP / Signoff。
3. 创建 Distribution target / export / zip / signoff。
4. 创建 Submission / export / zip / signoff。
5. 先 refresh operations，确认 current_stage 是 `submission_ready`，next action 指向 evidence receipt。
6. 记录 Submission Evidence receipt / feedback / acceptance / signoff。
7. refresh operations，确认 current_stage 是 `accepted`。

6. export 是否没有复制大包和敏感附件。
7. verifier 是否检查 raw central directory entry name。
8. duplicate entry 是否 failed。
9. manifest.zip.entries 是否不能扩大允许列表。
10. redaction 是否扫 raw manifest/report/README。
11. stage 是否因 optional gate 缺失而误 failed。
12. required gate 是否真的 failed。
13. release-check 是否覆盖从 submission_ready 到 accepted 的阶段变化。

## 19. 风险清单

### 19.1 聚合逻辑过大

Operations 容易变成巨型模块。

控制：

- domain collector 拆函数。
- 每个 collector 只读 summary。
- 不复刻 verifier 细节。
- 统一 output shape。

### 19.2 Stage 判断和 gate required 关系复杂

不同 Release 可能不要求 encoded / mastering / rights / submission evidence。

控制：

- domain 输出 `required`。
- optional missing 只能 warning / not_required。
- required missing 才 blocker。

### 19.3 Dashboard 误导用户以为已经上传平台

必须明确：

- Operations Dashboard 是本地视图。
- 不连接平台。
- 不上传。
- submitted / accepted 来自本地录入 evidence。

### 19.4 Export 泄露本机路径

控制：

- 所有 summary 走 sanitize_metadata。
- verifier redaction 扫 raw JSON。
- release-check 塞入通用本机路径占位和 token-like 占位字符串，确认 redaction failed。

### 19.5 老数据兼容

旧 Release 没有某些 summary。

控制：

- missing 输出 not_started / missing。
- 不崩溃。
- next action 指向相关模块。

## 21. 与 v5.9.0 的衔接

v5.9.0 解决的是：

- signed Submission Package 之后的外部过程证据。
- 提交回执、反馈、重提、接受确认。
- Evidence Package ZIP 和离线 verifier。

v6.0.0 解决的是：

- 把 Release 运营全链路聚合起来。
- 告诉用户当前在哪里、还差什么、下一步做什么。
- 把所有分散 gate 转成一个 operations readiness report。
- 让真实业务测试时不用在十几个 tab 之间猜状态。

两者关系：

```text
v5.9: 把提交后证据补完整
v6.0: 把所有发行证据汇总成运营总控台
```

## 22. 最终定义

v6.0.0 只有在下面这句话成立时才算完成：

> 一个 Release 的所有关键发行证据，都能在 Operations Dashboard 中被统一查看；系统能给出当前 stage、blockers、warnings、next actions，并能导出一个不含敏感信息、可离线验证的 Operations Package。

如果只是加几个前端卡片，不算完成。

如果 Dashboard 会改变业务状态，不算完成。

如果没有离线 verifier，不算完成。

如果不能覆盖 Submission Evidence，不算完成。

如果 next action 不可解释，不算完成。

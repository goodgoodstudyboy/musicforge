# v3.1.0 Review Sprint 智能排序与上下文推荐施工图

日期：2026-05-14

当前稳定基线：v3.0.0

目标版本：v3.1.0

定位：在 v3.0.0 已经完成 Review Sprint 多反馈组织、冲突检测和批量候选生成后，给 Sprint 增加可解释的“下一步推荐”：推荐先处理哪些 ReviewTask、哪些 task 适合批量生成、哪些 task 需要跳过，并为每个 task 推荐可复用的 Context Pack。v3.1.0 不自动执行推荐，不自动 apply，不自动 resolve，只把项目级决策依据整理清楚。

---

## 1. 背景

v3.0.0 已经把多条 ReviewTask 放进 Sprint：

```text
ReviewTask list
  -> ReviewSprint
  -> ordered task refs
  -> conflict report
  -> batch local/provider candidate generation
  -> single task apply
  -> sprint summary/export/final export
```

这个版本解决了“怎么组织一轮反馈”。

但它仍然偏人工管理：

- task 的顺序主要靠用户手动排。
- conflict report 只告诉你哪里冲突，不告诉你应该先修哪条。
- 用户不知道哪些 task 适合先生成 provider candidates。
- Context Pack 目前是通用 Library 推荐，和 ReviewTask/Sprint 的目标还没有深度结合。
- Sprint 关闭前缺少“下一步建议/未解决风险”的统一报告。

v3.1.0 要补的是“推荐层”，不是执行层。

---

## 2. 一句话目标

v3.1.0 要让 Review Sprint 从“多反馈列表”升级为“可解释的反馈推进计划”：

```text
ReviewSprint
  -> Analyze tasks and conflicts
  -> Recommend processing order
  -> Recommend candidate generation mode
  -> Recommend Context Packs per task
  -> Show Sprint Recommendation Report
  -> User chooses what to run
```

核心原则：

- 推荐只提供建议，不自动 apply。
- 推荐不自动生成候选，除非用户点击对应按钮。
- 推荐不自动保存 Context Pack，除非用户点击 Save。
- 推荐结果必须可解释。
- 推荐结果必须脱敏。
- 推荐结果必须能被 release-check 稳定验证。

---

## 3. 版本边界

### 3.1 v3.1.0 必须做

- 新增 Sprint Recommendation Report。
- 推荐 ReviewTask 处理顺序。
- 推荐每个 task 的 action：
  - generate_local
  - generate_provider
  - inspect_conflict
  - apply_ready_candidate
  - resolve
  - skip_stale
  - add_follow_up
- 推荐每个 task 的 reason 和 score breakdown。
- 接入 LibraryIndex，为 task 推荐 Context Pack preview。
- 支持从推荐 preview 保存 Context Pack。
- 支持把 Context Pack 用于 Sprint provider/local candidate generation payload。
- Studio Review Sprints 增加 Recommendations panel。
- Project Export / Final Export 加入 Sprint Recommendation summary。
- release-check 增加 v3.1 smoke。
- README / CHANGELOG / version bump。

### 3.2 v3.1.0 可以做，但不强制

- Sprint recommendation history。
- Recommendation diff：前后两次推荐变化。
- Provider 辅助解释排序。
- 一键把 recommended order 写回 sprint task order。
- 一键创建全部 recommended context packs。

### 3.3 v3.1.0 不做

- 不做 batch apply。
- 不做 auto resolve。
- 不做 auto close sprint。
- 不做自动执行推荐动作。
- 不做跨 project 推荐。
- 不做 provider 自动改排序。
- 不做音频理解、BPM/key 检测、音频转 MIDI。
- 不做复杂机器学习排序。

---

## 4. 核心判断

v3.1.0 的价值不是“更聪明地替用户决定”，而是把已有数据结构变成可解释建议：

已有输入：

- ReviewTask status / priority / target。
- ReviewCandidate rank / source / quality / risk。
- Decision Report。
- ReviewSprint conflict report。
- LibraryIndex search/recommend。
- ContextPackStore。

因此 v3.1.0 应该做 deterministic recommendation，不需要 provider。

Provider 可以后续 v3.1.1 或 v3.2 做“解释增强”，但核心推荐必须本地可复现。

## 5. 新增数据结构

### 5.1 存储文件

```text

### 5.2 SprintRecommendationReport

{
  "schema_version": 1,
  "project_id": "project-001",
  "sprint_id": "sprint-001",
  "created_at": "2026-05-14T...",
  "parent_version_id": "v001",
  "recommended_order": ["review-task-003", "review-task-001"],
  "recommended_actions": [
    {
      "task_id": "review-task-003",
      "rank": 1,
      "action": "generate_provider",
      "score": 88,
      "reason": "High priority task has local candidates but no provider candidates and no blocking conflicts.",
      "score_breakdown": {
        "priority": 25,
        "status": 20,
        "conflict": 15,
        "candidate_readiness": 10,
        "provider_gap": 10,
        "freshness": 8
      },
      "target": {
        "section_name": "chorus",
        "track_name": "bass",
        "role": "bass"
      },
      "context_pack_preview": {
        "asset_refs": [],
        "reference_refs": [],
        "query": {}
      },
      "warnings": []
    }
  ],
  "sprint_level_recommendation": {
    "next_action": "generate_provider_for_top_tasks",
    "reason": "Two high-priority tasks have local candidates but no provider alternatives.",
    "ready_to_close": false,
    "blocking_conflict_count": 0
  },
  "source_summary": {
    "task_count": 4,
    "conflict_count": 1,
    "context_recommendation_count": 3
  }
}
```

### 5.3 Action 枚举

```text
inspect_conflict
generate_local
generate_provider
refresh_decision_report
apply_ready_candidate
resolve
add_follow_up
skip_stale
skip_archived
no_action
```

含义：

- `inspect_conflict`：有 blocking 或强 warning，需要用户先看。
- `generate_local`：没有 ready candidates。
- `generate_provider`：已有 local candidates，但缺 provider candidates。
- `refresh_decision_report`：候选存在，但 report 缺失或过旧。
- `apply_ready_candidate`：已有推荐 candidate，且 task 未 applied。
- `resolve`：task 已 applied，建议用户确认是否 solved。
- `add_follow_up`：task needs_more_work，但 follow-up 不在 sprint。
- `skip_stale`：stale task，不能在 sprint 内继续。
- `skip_archived`：archived task。
- `no_action`：已 resolved 或无需处理。

## 6. 推荐排序算法

### 6.1 输入

对每个 Sprint task 收集：

- task status。
- task priority。
- task target section/track/role/global_marker_beat。
- candidate counts。
- provider candidate count。
- decision report recommended_candidate_id。
- conflict report 中关联该 task 的 conflicts。
-是否 stale。
- 是否有 follow_up_task_id。
- 是否 already applied/resolved。

### 6.2 Score

建议 0 到 100：

```text
score =
  priority_score
  + status_score
  + candidate_readiness_score
  + provider_gap_score
  + conflict_score
  + freshness_score
  + target_specificity_score
```

示例：

```python
priority_score = task.priority * 0.25

status_score:
  open -> 18
  candidate_ready -> 24
  applied -> 12
  resolved -> 0
  needs_more_work -> 10
  stale -> -30
  archived -> -50

candidate_readiness_score:
  no ready candidate -> 8
  ready candidate exists -> 18
  decision report exists -> 8

provider_gap_score:
  local exists and provider missing -> 10
  provider exists -> 4

conflict_score:
  no conflict -> 12
  warning conflict -> 4
  blocking conflict -> -30

freshness_score:
  current -> 8
  stale -> -40

target_specificity_score:
  section + track -> 8
  section only -> 4
```

Clamp 到 0..100。

### 6.3 Recommended action

按规则选择 action：

```text
if stale -> skip_stale
elif archived -> skip_archived
elif blocking conflict -> inspect_conflict
elif needs_more_work and follow_up missing -> add_follow_up
elif applied -> resolve
elif no ready candidates -> generate_local
elif local ready and no provider ready -> generate_provider
elif decision report missing -> refresh_decision_report
elif decision report has recommended candidate -> apply_ready_candidate
else -> no_action
```

不要让 provider_gap 比 blocking conflict 优先。

### 6.4 Recommended order

排序：

1. blocking/stale 放后面，除非 action 是 inspect_conflict。
2. score 高的在前。
3. priority 高的在前。
4. sprint ref order 小的在前。
5. task_id 稳定排序。

## 7. Context Pack 推荐

### 7.1 目标

给每个 task 推荐一个 context pack preview：

- 相关 asset。
- 相关 reference。
- 已有 hook/section/bass/drums 素材。
- 与 task target 和 review notes 匹配的素材。

### 7.2 输入 query

构建 request：

```json
{
  "source": "review_sprint_task",
  "goal": "review_task_candidate_generation",
  "project_id": "project-001",
  "sprint_id": "sprint-001",
  "task_id": "review-task-001",
  "review_task": {
    "title": "...",
    "summary": "...",
    "target": {},
    "priority": 80
  },
  "song_request": {
    "style": "...",
    "theme": "...",
    "tempo_bpm": 120,
    "key": "C"
  }
}
```

复用：

```python
recommend_library_context(index, request)
```

### 7.3 Preview 不自动保存

Recommendation report 可以包含 `context_pack_preview`，但不要自动创建 ContextPack。

新增 API 手动保存：

```http
POST /api/projects/<project-id>/review-sprints/<sprint-id>/recommendations/<task-id>/context-pack
```

Request：

```json
{
  "name": "Context for chorus bass fix",
  "selection": "recommended"
}
```

Response：

```json
{
  "ok": true,
  "context_pack": {}
}
```

保存时必须重新验证：

- asset/reference 未 hidden。
- source_hash 未 stale。
- pack refs 不超限。
- 文本脱敏。

### 7.4 用于 batch generation

Sprint batch provider/local generation 可以接收：

```json
{
  "use_recommended_context": true,
  "task_context_pack_ids": {
    "review-task-001": "pack-001"
  }
}
```

v3.1.0 第一版建议：

- 只支持用户手动选一个 `context_pack_id` 给整次 batch。
- 或者保存 pack 后，用户在 UI 里点击 Generate Provider With Context。

不要在 v3.1.0 自动为每个 task 应用不同 context pack，除非实现非常清楚。

## 9. API 设计

### 9.1 Recommendation report

```http
GET /api/projects/<project-id>/review-sprints/<sprint-id>/recommendations
POST /api/projects/<project-id>/review-sprints/<sprint-id>/recommendations/refresh
```

GET：

- 如果 report 存在，返回已保存 report。
- 如果不存在，可以即时生成并保存。

POST refresh：

- 重新读取 sprint/task/conflict/library。
- 重新生成 report。

Response：

```json
{
  "ok": true,
  "sprint": {},
  "recommendation_report": {},
  "summary": {},
  "conflict_report": {}
}
```

### 9.2 Save recommended Context Pack

```http
POST /api/projects/<project-id>/review-sprints/<sprint-id>/recommendations/<task-id>/context-pack
```

Request：

```json
{
  "name": "Chorus bass task context",
  "description": "Recommended from sprint task",
  "selection": "recommended"
}
```

Response：

```json
{
  "ok": true,
  "context_pack": {},
  "recommendation": {}
}
```

错误：

- task 不在 sprint：404。
- recommendation missing：409。
- no recommended refs：409。
- hidden/stale source：409。

### 9.3 Apply recommended order

可选：

```http
POST /api/projects/<project-id>/review-sprints/<sprint-id>/recommendations/apply-order
```

Request：

```json
{
  "task_ids": ["review-task-003", "review-task-001"]
}
```

如果做，必须只是重排 sprint refs，不执行任何 generation/apply。

如果时间紧，v3.1.0 不做这个 API。

## 12. 安全要求

### 12.1 不泄露敏感信息

Recommendation report 不能包含：

- API key。
- Authorization。
- raw provider prompt。
- raw provider response。
- 本机路径。
- 原始长 review notes。

所有文本字段：

- `sanitize_sensitive_text()`。
- `sanitize_metadata()`。

### 12.2 Context Pack stale guard

保存 recommended context pack 时必须重新校验：

- asset hidden -> reject。
- reference hidden -> reject。
- source hash mismatch -> reject。
- refs 超限 -> reject。

不能只信 report 里的 preview。

### 12.3 推荐不执行

任何 recommendation API 不允许：

- create candidate。
- apply candidate。
- resolve task。
- close sprint。

除了明确的 `apply-order`，也不能修改 sprint task_refs。

### 12.4 Deterministic

同样输入下 recommendation report 排序必须稳定。

排序 tie-break：

```text
score desc
priority desc
existing sprint order asc
task_id asc
```

## 16. Reviewer 检查重点

Reviewer 要重点看：

- Recommendation API 是否只生成 report，不执行 candidate/apply/resolve。
- 推荐排序是否 deterministic。
- blocking conflict 是否优先于 provider gap。
- stale task 是否不会被推荐 generate。
- Context Pack preview 是否重新校验后才保存。
- 保存 context pack 是否不信 recommendation report 缓存。
- report/export/final export 是否脱敏。
- Studio 是否明确展示“推荐不自动应用”。
- release-check 是否覆盖 context pack 保存和 provider generation with context。
- v3.0 Sprint 的 batch generation 和 apply guard 是否没有被改坏。

## 17. 完成标准

v3.1.0 完成必须满足：

- Sprint 可以生成 Recommendation Report。
- Report 有 recommended order。
- 每个 task 有 recommended action、reason、score breakdown。
- 至少能为 task 推荐 context pack preview。
- 用户可以手动保存 recommended context pack。

## 19. 最终判断

v3.1.0 应该做 Review Sprint 智能排序与上下文推荐。

原因：

- v3.0 已经能管理多个 ReviewTask。
- 下一步不是自动执行，而是告诉用户应该先看哪里、为什么。
- LibraryIndex 和 ContextPack 已经存在，应该和 ReviewTask/Sprint 结合起来。
- 这能提升多反馈推进效率，同时保持 MusicForge 的本地校验、人工 apply、安全脱敏原则。

做完 v3.1.0 后，工作流会从：

```text
我把多个反馈放进 Sprint，然后手动判断先做什么
```

升级为：

```text
系统给我一份可解释的 Sprint 推进建议和上下文推荐，我确认后再逐步生成候选、试听和应用
```

这是从“多反馈管理台”走向“创作决策辅助台”的关键一步。

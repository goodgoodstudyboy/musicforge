# v10.9.0 Release Audio Certification Timeline 音频准出证据时间线与长期质量趋势施工图

> 项目：MusicForge / song-agent
> 计划版本：v10.9.0
> 编写日期：2026-06-26
> 当前稳定基线：v10.8.0
> 角色定位：reviewer / planner
> 目标读者：开发执行人员、测试验收人员、后续 reviewer

---

## 1. 背景

v10.8.0 已经完成了 Release Audio Certification，总闸能力基本成型：

- Release tracks 绑定 `project_id + version_id + final_export_hash`。
- Final Export WAV、真实 renderer、人工 Audio Campaign review、Campaign Governance、Remediation evidence 被聚合到 Certification。
- Certification 支持 signoff、export、ZIP、offline verifier。
- Release signoff 和 GA readiness 可以要求当前 signed Certification。
- v10.8 smoke 已覆盖 manual review 缺失、fake/test WAV、Final Export stale、declared extra ZIP、GA 外部 evidence binding 等关键风险。

现在系统已经能回答：

> 当前 Release 能不能过音频准出总闸？

但还不能很好回答：

> 这个 Release 是如何一步步走到音频准出的？

具体缺口：

- 单首 track 经历了几轮听审？
- 哪些 marker / issue 出现过？
- 哪些 issue 被修复，哪些是重复问题？
- Campaign、Fix Sprint、Remediation、Certification 之间的因果链是否清楚？
- 当前 Certification 通过之前，是否曾经有 failed / needs_fix / rejected？
- 音频修复平均需要几轮？
- 某类 issue 是否在多个 Release 反复出现？
- reviewer / developer 能不能只看一个页面就判断音频质量演进？
- 后续 GA/LTS 维护时，能不能比较不同 Release 的音频风险趋势？

v10.8 是“总闸”。v10.9 应该做“证据时间线”和“长期质量趋势”。

---

## 2. 一句话目标

> v10.9.0 要新增 Release Audio Certification Timeline：把 Release 从 Final Export、Audio Lab、Campaign、Fix Sprint、Remediation、Certification 到 GA gate 的音频证据串成不可静默改写的事件时间线，并生成 track-level timeline、quality trend、issue taxonomy、risk register、export ZIP、offline verifier 和可选 Release/GA gate。

---

## 3. 本版定位

### 3.1 v10.9 不是再加一个按钮

这版不应该只是多一个报表。它应该把 v10.2 到 v10.8 的真实听审链路沉淀成可追溯账本：

```text
Release tracks
  -> Final Export snapshot
  -> Audio Lab real WAV item
  -> manual listening review
  -> markers / issues
  -> Audio Fix Sprint
  -> candidate A/B review
  -> selected candidate
  -> recheck session
  -> Audio Campaign
  -> Campaign signoff
  -> Campaign Governance archive
  -> Campaign Remediation closeout/signoff
  -> Release Audio Certification
  -> Certification signoff / verification
  -> GA readiness audio check
  -> Release Audio Timeline report
```

### 3.2 v10.9 要证明什么

完成后系统应能回答：

- 当前 Release 的每首歌音频证据链是否完整？
- 每首歌从首次真实听审到 Certification signoff 经过了多少阶段？
- 哪些 issue 曾经出现，最后是否被修复？
- 是否存在 open / unresolved / stale / fake / synthetic / missing evidence？
- Certification 是基于哪些具体 Campaign、Governance、Remediation、Final Export 证据形成的？
- 当前 timeline 是否绑定当前 Certification ZIP / verification report？
- 当前 timeline 是否能离线验证，且不能靠 ZIP 内部全量重签伪造？
- 是否可以把 timeline 作为 Release signoff / GA readiness 的额外审计 evidence？

### 3.3 为什么现在做

v10.8 已经有总闸，但总闸只给最终判定。后续开发和业务会需要：

- 对比多个 Release 的音频质量。
- 定位 recurring issue。
- 给人工听审人员一个复盘页面。
- 给开发一个“哪里最常出问题”的改进方向。
- 给发布验收一个“一眼看完证据链”的包。

如果不做 timeline，后续每次出问题都要从 Audio Lab、Campaign、Fix Sprint、Remediation、Certification 多个目录手工翻文件。

---

## 4. 明确不做

v10.9 不做以下事情：

- 不新增音乐生成算法。
- 不新增第三方音乐 API。
- 不自动替代人工听审。
- 不自动把 `needs_fix/rejected` 改成 accepted。
- 不自动 select candidate。
- 不自动 signoff Certification / Release / GA。
- 不做真实 loudness/mastering 算法。
- 不做公开 Public Trust Center 扩展。
- 不重写 v10.8 Certification，总闸仍由 v10.8 模块负责。

v10.9 是证据时间线和趋势层，不是生成层、渲染层或最终签核层。

## 6. 核心数据模型

### 6.1 Timeline Event

每条事件写入 `event-ledger.jsonl`。

```json
{
  "schema_version": 1,
  "event_id": "rate-evt-000001",
  "release_id": "rel-000001",
  "timeline_id": "ratl-000001",
  "track_identity": {
    "project_id": "proj-000001",
    "version_id": "ver-000003",
    "final_export_hash": "..."
  },
  "event_type": "audio_review_recorded",
  "status": "accepted",
  "severity": "info",
  "source_component": "audio_lab",
  "source_id": "als-000001:item-001",
  "source_hash": "...",
  "payload": {
    "review_result": "accepted",
    "review_mode": "manual",
    "playback_confirmed": true,
    "marker_count": 0
  },
  "evidence_refs": [
    {
      "kind": "audio_lab_session",
      "id": "als-000001",
      "hash": "..."
    }
  ],
  "recorded_at": "2026-06-26T00:00:00Z",
  "previous_event_hash": null,
  "payload_hash": "...",
  "event_hash": "..."
}
```

要求：

- `payload` 必须脱敏。
- 不允许写本机绝对路径。
- 不允许写 API key、token、provider raw response。
- `event_hash` 必须覆盖除自身外的核心字段。
- `previous_event_hash` 串成 hash chain。
- 同一个 timeline 内 event 顺序必须 deterministic。

## 7. Store 设计

新增 `ReleaseAudioTimelineStore`。

构造依赖：

```python
ReleaseAudioTimelineStore(
    release_store=...,
    project_store=...,
    audio_lab_store=...,
    audio_campaign_store=...,
    audio_campaign_planner_store=...,
    audio_campaign_governance_store=...,
    audio_campaign_remediation_store=...,
    release_audio_certification_store=...,
)
```

核心方法：

```python
refresh_timeline(release_id: str, *, force_new: bool = False) -> dict
list_timelines(release_id: str) -> dict
read_timeline(release_id: str, timeline_id: str | None = None) -> dict
read_events(release_id: str, timeline_id: str | None = None) -> dict
read_track_index(release_id: str, timeline_id: str | None = None) -> dict
read_quality_trend(release_id: str, timeline_id: str | None = None) -> dict
read_issue_taxonomy(release_id: str, timeline_id: str | None = None) -> dict
read_risk_register(release_id: str, timeline_id: str | None = None) -> dict
signoff_timeline(release_id: str, timeline_id: str, payload: dict) -> dict
export_timeline(release_id: str, timeline_id: str | None = None) -> dict
build_zip(release_id: str, timeline_id: str | None = None) -> dict
verify_zip(release_id: str, timeline_id: str | None = None, **options) -> dict
gate(release_id: str, *, required: bool, require_signed: bool = False, require_current_certification: bool = True) -> dict
```

### 7.1 refresh 行为

`refresh_timeline()` 应：

1. 读取 Release tracks。
2. 读取每个 track 的当前 Final Export manifest。
3. 读取 Release Audio Campaign plan/link/case index/report/signoff。
4. 读取 Audio Lab session items 和 manual reviews。
5. 读取 Audio Fix Sprint / Remediation 关联证据。
6. 读取 Campaign Governance archive verification。
7. 读取 Release Audio Certification report/signoff/verification。
8. 构造 deterministic event list。
9. 构造 track index / trend / taxonomy / risk / bindings。
10. 写入新的 timeline snapshot。

如果当前 latest timeline 已 signed：

- 不允许覆盖。
- 如果 source 未变，可返回 existing signed timeline。
- 如果 source 已变，创建 `timeline-000002` draft。

如果当前 latest timeline 未 signed：

- source 未变：可更新 draft，保持同一 timeline_id。
- source 变了：可重建 draft，但必须保留 events deterministic。

### 7.2 signoff 行为

`signoff_timeline()` 要求：

- timeline report status 为 `passed` 或 `warning`，不能是 `failed`。
- blocking risk count 为 0。
- evidence bindings 中 Certification status 为 passed。
- 如果存在 remediation needed，则 remediation status 为 passed。
- manual review coverage 为 100%。
- real audio coverage 为 100%。
- event chain integrity OK。

签核后：

- `timeline-signoff.json` 写入 timeline report hash、event ledger hash、track index hash、trend hash、taxonomy hash、risk hash、evidence binding hash。
- export/ZIP/verify 可以读取，但不允许静默重建已签核内容。
- 如果源 evidence 变化，必须生成新的 timeline snapshot。

## 8. Verifier 设计

新增 CLI：

```bash
python -m song_agent.cli verify-release-audio-timeline-package <zip>
```

基础参数：

```text
--json
--report-out <path>
--strict
--require-passed
--require-signed
--require-real-audio
--require-manual-review
--require-current-certification
--release-audio-certification <zip>
--release-audio-certification-verification-report <json>
```

### 8.1 固定 ZIP allow-list

Timeline ZIP 固定 entry：

```text
manifest.json
audio-timeline-report.json
track-timeline-index.json
event-ledger.jsonl
quality-trend.json
issue-taxonomy.json
risk-register.json
evidence-bindings.json
README.txt
```

如果 signed：

```text
timeline-signoff.json
```

不允许：

- 额外 entry。
- `../`
- 绝对路径。
- 反斜杠路径。
- `.musicforge/` 或大小写变体。
- nested ZIP。
- duplicate entry。
- manifest.files 声明额外文件。

### 8.2 Event chain 校验

Verifier 必须检查：

- event id deterministic 且唯一。
- `previous_event_hash` 链连续。
- `payload_hash` 正确。
- `event_hash` 正确。
- ledger 最终 hash 与 manifest/report/signoff 绑定。
- event 中没有本机路径、token、raw provider。

### 8.3 派生文档校验

Verifier 不能只检查 integrity hash，还要从 `event-ledger.jsonl` 反推：

- track timeline summary。
- issue taxonomy occurrence。
- risk register blocker/warning 数。
- quality trend basic counters。

例如攻击者全量重签 `quality-trend.json`，把 `open_blocker_count` 从 1 改成 0，但 event-ledger 中仍有 open blocker，verifier 必须 failed。

### 8.4 外部 Certification 绑定

启用 `--require-current-certification` 时，必须传：

```bash
--release-audio-certification <zip>
--release-audio-certification-verification-report <json>
```

Verifier 要求：

- 外部 Certification ZIP 当前可验证。
- verification report 绑定当前 Certification ZIP sha、size、manifest hash。
- `evidence-bindings.json.release_audio_certification` 与外部 report 一致。
- timeline report 里的 certification summary 与外部 report 一致。
- 如果外部 Certification verification failed，则 timeline verifier failed。

这点必须收紧，避免 timeline ZIP 自己写一个 passed certification summary 就通过。

### 8.5 签核校验

`--require-signed` 时：

- `timeline-signoff.json` 必须存在。
- signoff status 必须 `signed`。
- signoff integrity OK。
- signoff 绑定 report/index/ledger/trend/taxonomy/risk/evidence hash。
- signoff 绑定 source_hash。
- signed timeline 不能被重新 export 覆盖。

## 11. Release / GA Gate 接入

### 11.1 Release signoff

新增可选参数：

```json
{
  "require_release_audio_timeline": true,
  "require_release_audio_timeline_signed": true,
  "require_release_audio_timeline_current_certification": true
}
```

Gate 规则：

- `require_release_audio_timeline=true` 时，timeline report status 不能 failed。
- `require_release_audio_timeline_signed=true` 时，必须 signed。
- `require_release_audio_timeline_current_certification=true` 时，timeline 必须绑定当前 passed Certification evidence。
- hard block 不允许 force 绕过。

### 11.2 GA readiness

新增 GA check：

```text
ga.release_audio_timeline
```

`ga-check` 新增参数：

```bash
--require-release-audio-timeline
--release-audio-timeline <zip>
--release-audio-timeline-verification-report <json>
--release-audio-certification <zip>
--release-audio-certification-verification-report <json>
```

`verify-ga-readiness-report` 必须要求外部 timeline ZIP + timeline verification report。不能只信 GA report 内部的 summary。

## 19. 给开发的话

这版不要把它做成“又一个 summary JSON”。v10.9 的价值是把音频准出的因果链保存下来：哪首歌、哪次听审、哪个 marker、哪个修复、哪个 recheck、哪个 Certification，最后如何进入 GA gate。

实现时请坚持三条原则：

1. Timeline 只能记录证据，不能替代证据。需要强门禁时必须绑定外部 Certification ZIP + verification report。
2. 已签核 snapshot 不允许静默改写。源 evidence 变化就生成新 timeline 或直接 409。
3. verifier 不能只信 integrity_hash。trend、taxonomy、risk 必须能从 event-ledger 反推，防止全量重签伪造。

每完成一个阶段就本地测试、提交、推送。不要攒到最后一次性提交。尤其是 verifier 和 release-check，要尽早跑通，后面 UI 才有稳定基础。

# v5.3.0 Audio Revision Workbench 音频修复工作台与混音复听闭环施工图

日期：2026-05-27

角色定位：reviewer / planner

当前稳定基线：v5.2.1

目标版本：v5.3.0

---

## 1. 背景

v5.0.0 到 v5.2.1 已经把 MusicForge 从“能生成 MIDI”推进到了“能交付真实音频并有人工听审证据”的阶段：

- v5.0.0：Renderer Profile、WAV Audio Health、Audio Artifact Manifest、Release Audio QA。
- v5.1.0：逐曲人工音频听审证据、marker、Release Signoff 人工听审 gate。
- v5.2.0：Mix State、Mix Patch、Mix Preview、Stem Health、Mix Board。
- v5.2.1：修复当前 mix evidence 可信度，Release Signoff 和 `verify-release` 都会校验 `mix-state.json` 是否匹配包内当前 `song-plan.json` / `song.mid`。

现在系统已经能回答：

> 这首歌有没有真实 WAV？有没有人听过？当前包里的 mix-state 是否真的对应当前 SongPlan / MIDI？

但它还不能很好地回答：

> 听审发现问题以后，如何系统化地产生多个修复候选、A/B 复听、选择最佳候选、应用到 Release Track，并重新进入验收？

v5.3.0 的核心就是补这个闭环：**Audio Revision Workbench，音频修复工作台**。

这不是再做一个孤立按钮，而是把 v5.1 的听审 marker、v5.2 的 Mix Patch、Stem Health、Release Signoff 串起来，形成可追踪、可回滚、可复验的“听审问题修复流程”。

---

## 2. 版本定位

v5.3.0 要做的是 Release 级音频修复闭环：

1. 从 Release Audio Review 中归集问题 marker。
2. 为每个 track / marker 建立 Audio Revision Issue。
3. 基于当前 Mix State 生成多个 deterministic Mix Candidate。
4. 每个 candidate 可渲染 MIDI / WAV，并做 audio health / stem health。
5. 支持 before / after A/B 试听和人工 candidate review。
6. 只允许人工选择一个 candidate apply。
7. Apply 后创建新的 Project Version，并显式更新 Release Track 指向该版本。
8. Apply 后旧 audio review 自动变 stale，需要重新听审。
9. Release Signoff 可要求所有 Audio Revision Session 已 close 且无未解决 high / critical issue。
10. Release Export / ZIP / verifier 可携带并校验 audio revision evidence。

一句话：

> v5.2 让人能调混音，v5.3 要让“听审发现问题以后如何修、如何复听、如何进入交付”变成完整流程。

---

## 3. 明确不做

v5.3.0 不做以下内容：

- 不做 LUFS / True Peak / streaming loudness 标准化。
- 不做 EQ、压缩、混响、延迟、母带插件链。
- 不做实时 DAW 波形编辑。
- 不做 MP3 / AAC / FLAC 多格式发行包，这应放到后续 v5.4 或 v5.5。
- 不做自动替人判断“音乐好不好”。
- 不做自动 apply / 自动签核。
- 不做 provider 自动混音替代人工，provider 最多后续作为建议来源，v5.3 主线必须 deterministic local。
- 不做音频扒谱、音频分轨、人声处理。

v5.3 只做一个工程化闭环：**问题归集 -> 修复候选 -> 复听决策 -> 应用 -> 重新验收**。

---

## 4. 为什么现在做这个

当前 v5.2 已经有 Mix Patch，但它偏底层：

- 用户或系统能创建 patch。
- patch 能 preview。
- patch 能 apply 成 child version。
- release signoff 能要求 mix evidence 当前有效。

但真实使用时，用户不会直接说“把 track-003 velocity_scale 设成 0.87”。用户会说：

- 00:38 鼓太冲。
- 副歌旋律被和弦盖住。
- bass 抢了主旋律。
- bridge 太空。
- ending 能量掉得太快。
- 某首歌整体比其他歌小。

这些反馈已经能存在 Release Audio Review marker 里，但从 marker 到 patch 之间缺一个工作台：

- 哪些 marker 还没处理？
- 这个问题生成了哪些候选？
- 哪个候选听起来最好？
- 这个候选是否真的基于当前 WAV？
- apply 后 Release Track 是否明确指向新版本？
- 旧听审是否已经被判 stale？
- 重新听审是否通过？

v5.3 就是补这个中间层。

---

## 5. 总体目标

v5.3.0 完成后，系统应该支持：

1. Release 下创建 Audio Revision Session。
2. Session 自动扫描当前 Release Audio Review markers，生成 Issue Index。
3. Issue 可以按 track、marker category、severity、section、status 筛选。
4. Issue 可以生成 2 到 5 个 local deterministic Mix Candidate。
5. Candidate 记录完整 patch、source hash、preview MIDI/WAV、audio health、stem health。
6. Candidate 支持人工 review：accepted、rejected、needs_tweak、favorite、notes、markers。
7. Candidate apply 后创建新的 Project Version，variant_type 建议为 `audio_revision_mix_edit`。
8. Apply 后 Release Track 必须显式切换到新 version，不能静默刷新。
9. Apply 后原 track 的旧 accepted audio review 因 WAV hash 变化自动 stale。
10. Session close 前必须确认：
    - selected candidate 已 apply，或 issue 已 waived。
    - high / critical issue 不能静默忽略。
    - applied track 已重新生成 Final Export / Release Export evidence。
11. Release Signoff 可启用 `require_audio_revision_closeout=true`。
12. `verify-release` 可离线检查 audio revision evidence 的 integrity / source hash / selected candidate / applied version。
13. Studio 提供 Audio Revision Workbench，而不是只在 Mix Board 里散落按钮。

## 6. 核心概念

### 6.1 AudioRevisionSession

Release 级修复会话。

建议落盘：

`.musicforge/releases/<release-id>/audio-revisions/<session-id>/session.json`

字段建议：

```json
{
  "schema_version": 1,
  "session_id": "ars-000001",
  "release_id": "release-000001",
  "status": "open",
  "title": "Audio revision pass 1",
  "created_at": "...",
  "updated_at": "...",
  "source": {
    "release_hash": "...",
    "track_snapshots": [],
    "audio_review_summary_hash": "...",
    "release_audio_qa_hash": "...",
    "mix_gate_summary_hash": "..."
  },
  "source_hash": "...",
  "issue_count": 0,
  "open_issue_count": 0,
  "selected_candidate_count": 0,
  "applied_candidate_count": 0,
  "warnings": [],
  "integrity_hash": "..."
}
```

状态：

- `open`
- `candidate_generation`
- `reviewing_candidates`
- `partially_applied`
- `closed`
- `archived`

禁止状态：

- 已 `closed` 的 session 不能再生成 candidate。
- 已 `archived` 的 session 不能 apply。
- source stale 后不能 apply、close，只能 refresh 或新建 session。

`.musicforge/releases/<release-id>/audio-revisions/<session-id>/issues/<issue-id>.json`

字段建议：

```json
{
  "schema_version": 1,
  "issue_id": "ari-000001",
  "session_id": "ars-000001",
  "release_id": "release-000001",
  "track_id": "track-000001",
  "project_id": "project-000001",
  "version_id": "v000003",
  "source_review_id": "arv-000001",
  "source_marker_id": "marker-000001",
  "category": "mix_balance",
  "severity": "high",
  "section_id": "section-003",
  "start_beat": 32.0,
  "end_beat": 48.0,
  "summary": "drums too loud in chorus",
  "status": "open",
  "candidate_group_id": null,
  "selected_candidate_id": null,
  "applied_version_id": null,
  "waiver": null,
  "source_hash": "...",
  "integrity_hash": "..."
}
```

状态：

- `open`
- `candidates_ready`
- `candidate_selected`
- `applied`
- `needs_recheck`
- `rechecked`
- `waived`
- `stale`

Issue 不应该直接修改 SongPlan。它只组织证据和决策。

对某个 issue 的一个修复候选，本质是 Mix Patch + Preview + Health + Review。

候选状态：

- `draft`
- `rendered`
- `ready_for_review`
- `reviewed`

### 6.4 AudioRevisionCloseout

Session closeout 报告。

建议落盘：

`.musicforge/releases/<release-id>/audio-revisions/<session-id>/closeout.json`

字段：

- issue 总数。
- open / waived / applied / rechecked 数量。
- high / critical issue 是否全部处理。
- selected candidate 是否都 apply。
- apply 后 Release Track 是否指向新 version。
- 重新 audio review 是否仍缺失。
- stale / integrity / redaction 检查。
- closeout status：`passed` / `warning` / `failed`。
- force close reason，v5.3 建议不允许 force stale close。


所有 download endpoint 必须校验：

- candidate 当前不 stale。
- candidate integrity ok。
- artifact path 在 candidate 目录下。

### 8.4 Release Track 显式更新

v5.3 需要新增或收紧一个明确动作：

```text
POST /api/releases/<release_id>/tracks/<track_id>/replace-version
```

payload：

```json
{
  "project_id": "project-000001",
  "version_id": "v000004",
  "reason": "Applied audio revision candidate arc-000001",
  "source": {
    "audio_revision_session_id": "ars-000001",
    "issue_id": "ari-000001",
    "candidate_id": "arc-000001"
  }
}
```

要求：

- Release 已签核时返回 409，必须 reset signoff。
- `project_id` 必须和原 track 相同，除非显式 `allow_project_change=true`，v5.3 建议先不支持换 project。
- version 必须存在。
- version 必须有 Final Export 或可生成 Final Export。
- 替换后 track snapshot 更新，旧 audio review 自动 stale。

不要让 apply candidate 静默修改 Release Track。建议 apply candidate 可返回 `applied_version_id`，然后由同一个 API 内部显式执行 replace，并把这个动作写入 event。

## 9. Candidate 生成策略

v5.3 主线必须 deterministic local，不依赖外部 API。

建议内置策略：

### 9.1 mix_balance

如果 marker category 是 `mix_balance`：

- `reduce_drums`
  - drums velocity_scale 0.85 到 0.92
  - section automation 优先限制在 marker section
- `lift_melody`
  - melody volume +1.0 到 +2.0 dB
  - melody velocity_scale 1.05 到 1.12
- `reduce_bass`
  - bass volume -1.0 到 -2.5 dB
  - bass velocity_scale 0.88 到 0.95
- `balance_section`
  - 问题 section 内降低 accompaniment，略抬 melody

### 9.2 sound_quality

如果 marker category 是 `sound_quality`：

- `reduce_clipping_risk`
  - 全局或问题 section velocity_scale 0.88 到 0.95
- `de_muddy_low_end`
  - bass / chords 轻微降低，melody 保持
- `thin_dense_section`
  - dense tracks section automation velocity_scale 降低

### 9.3 arrangement

如果 marker category 是 `arrangement`：

- `section_energy_lift`
  - hook / melody / drums 在 section 内轻微提升
- `section_energy_reduce`
  - 非主旋律轨道降低
- `focus_hook`
  - melody +1 dB，chords -1 dB，drums 轻微降低

### 9.4 severity 映射

- `low`：调整幅度 0.5 到 1.0 dB，velocity 0.95 到 1.05。
- `medium`：调整幅度 1.0 到 2.0 dB，velocity 0.90 到 1.10。
- `high`：调整幅度 2.0 到 3.0 dB，velocity 0.85 到 1.15。
- `critical`：仍然只能生成候选，不允许自动 apply；closeout 必须人工确认。

所有策略都要受 v5.2 Mix Patch validator 限制，不能突破 volume / pan / velocity 的范围。

## 10. Candidate Scoring

v5.3 的 score 不是“音乐审美最终判断”，只是排序辅助。

建议 score 组成：

```text
deterministic_score =
  source_current_score
  + health_score
  + issue_match_score
  + minimal_change_score
  + stem_health_score
  - risk_penalty
```

维度：

- `source_current_score`
  - source hash 当前有效才给满分。
- `health_score`
  - WAV health passed 给高分，warning 降分，failed 不可 ready。
- `issue_match_score`
  - 策略是否匹配 marker category / severity。
- `minimal_change_score`
  - patch 操作越少、影响范围越小，分数越高。
- `stem_health_score`
  - stem health passed 加分。
- `risk_penalty`
  - critical issue、过大 volume delta、全局变更、mute/solo 长期残留都扣分。

不允许因为 score 高就自动 apply。

## 11. A/B 复听要求

候选 review 必须绑定候选 WAV hash。

字段建议：

```json
{
  "review_status": "accepted",
  "review_mode": "manual",
  "reviewer": "developer",
  "rating": 4,
  "playback_confirmed": true,
  "listened_at": "...",
  "candidate_wav_sha256": "...",
  "parent_wav_sha256": "...",
  "notes": "candidate B fixed drum balance without hurting hook",
  "markers": []
}
```

规则：

- `review_mode=synthetic` 不能 select。
- `playback_confirmed=false` 不能 select。
- candidate WAV 变更后 review stale。
- parent WAV 变更后 review stale。
- review notes / markers 走 redaction。

Studio 必须清楚显示：

- Parent audio player。
- Candidate audio player。
- Candidate patch summary。
- Audio health status。
- Stem health status。
- Manual review form。

## 12. Apply 规则

Apply candidate 必须非常保守：

1. 重新读取当前 Project Version 的 SongPlan / MIDI / Mix State。
2. 重新校验 candidate source hash。
3. 重新从 candidate patch 计算结果。
4. 重新渲染 MIDI / WAV。
5. 写入 child Project Version。
6. 写入 `edit-metadata.json`：

```json
{
  "edit_source": "audio_revision",
  "edit_type": "audio_revision_mix_edit",
  "audio_revision": {
    "release_id": "release-000001",
    "session_id": "ars-000001",
    "issue_id": "ari-000001",
    "candidate_id": "arc-000001",
    "source_review_id": "arv-000001",
    "source_marker_id": "marker-000001"
  }
}
```

7. 写入 child version 的 `mix-state.json` / `mix-patch.json`。
8. 显式更新 Release Track 指向新 version。
9. 标记 issue status 为 `needs_recheck`。
10. 标记 session status 为 `partially_applied`。

禁止：

- 直接信任 candidate preview 目录中的 SongPlan / MIDI / WAV。
- apply stale candidate。
- apply 未 manual accepted 的 candidate。
- 同一 issue apply 多个 candidate，除非先 reopen 并产生新 issue / new round。
- 已签核 Release 里 apply candidate。

---

## 13. Recheck 闭环

Apply 以后不能直接认为问题解决。

必须进入 recheck：

1. Release Track 已指向新 Project Version。
2. Track Final Export 已刷新。
3. Release Audio QA 已刷新。
4. 旧 audio review 因 WAV hash 变化 stale。
5. 用户必须新增当前 WAV 的 manual accepted audio review。
6. issue 才能从 `needs_recheck` 变为 `rechecked`。

如果 recheck review 仍然 `needs_fix`：

- issue 进入 `open` 或创建 follow-up issue。
- 原 candidate 保持 applied，但不能 close session。
- 可以生成第二轮 candidates。

---

## 14. Closeout Gate

Session close 时生成 closeout report。

Closeout passed 条件：

- session source 当前有效。
- 所有 high / critical issue：
  - 已 `rechecked`，或
  - 已 `waived` 且有 waiver reason 和 reviewer。
- 所有 selected candidate：
  - 已 apply，或明确取消选择。
- 所有 applied candidate：
  - 对应 Release Track 当前指向 applied version。
  - 当前 track audio review 已 manual accepted。
- 无 integrity failed。
- 无 redaction failed。

Closeout warning 条件：

- low / medium issue waived。
- 有 candidate health warning，但人工接受。
- 有未选择候选。

Closeout failed 条件：

- stale source。
- high / critical issue open。
- selected candidate 未 apply。
- applied candidate 未 recheck。
- current Release Track 不匹配 applied version。
- evidence tampered。

建议 v5.3 不允许 `force=true` 绕过 stale / tampered。可以允许 force close warning，但必须写 reason。

## 15. Release Signoff 接入

Release Signoff 新增选项：

```json
{
  "require_audio_revision_closeout": true
}
```

Gate 逻辑：

- 如果 Release 有 audio review marker 且 category 属于 `mix_balance` / `sound_quality` / `arrangement`，但没有任何 Audio Revision Session，返回 warning 或 failed。建议 require=true 时 failed。
- 所有非 archived session 必须 closeout passed 或 acceptable warning。
- stale session 直接 failed。
- tampered closeout 直接 failed。
- high / critical open issue 直接 failed。
- applied candidate 后未 recheck 直接 failed。

Signoff evidence 写入：

```json
{
  "audio_revision_gate": {
```

## 19. 安全和一致性要求

### 19.1 路径安全

所有 candidate artifact path 必须解析在：

`.musicforge/releases/<release-id>/audio-revisions/<session-id>/candidates/<candidate-id>/`

下载时必须二次校验。

禁止：

- 绝对路径。
- `..`
- 反斜杠绕过。
- UNC 路径。
- candidate metadata 指向其他 candidate 目录。

### 19.2 Source Hash

Candidate source hash 至少绑定：

- release_id
- track_id
- project_id
- version_id
- parent SongPlan hash
- parent MIDI hash
- parent WAV hash
- current Mix State hash
- source review id / marker id
- issue payload hash
- renderer profile id / profile hash

只要这些变化，candidate stale。

### 19.3 Integrity Hash

以下对象都要 integrity hash：

- session
- issue
- candidate
- candidate review
- closeout
- exported summary

篡改后 API GET 应显示 `integrity_ok=false`，危险动作返回 409。

### 19.4 Redaction

以下字段必须走 `sanitize_sensitive_text` / `sanitize_metadata`：

- issue summary
- review notes
- candidate notes
- waiver reason
- closeout notes
- strategy labels
- export summaries

release-check 要污染：

- `C:\Users\...`
- `D:\Music\...`
- `\\server\share\...`
- `sk-...`
- GitHub token 样式
- Bearer token

### 19.5 Signed Release Guard

Release 已签核后：

- 不能创建 session。
- 不能 generate candidates。
- 不能 review candidate。
- 不能 apply candidate。
- 不能 replace Release Track version。
- 不能 close / archive session。

必须先 reset signoff。

## 24. 风险清单

### 风险 1：apply candidate 信任 preview cache

必须禁止。

Apply 时必须从当前父版本 SongPlan + 当前 Mix State + candidate patch 重算，不能读取 preview 里的结果当真。

### 风险 2：Release Track 没有显式切版本

如果 apply 只是创建 child version，但 Release Track 仍指向旧 version，用户会误以为修复进入发行包。

必须有显式 replace track version，并写 event。

### 风险 3：旧 audio review 没 stale

Apply 后 WAV hash 变了，旧 review 必须 stale。否则签核可能复用旧听审证据。

### 风险 4：candidate 下载路径污染

candidate metadata 可能被篡改指向其他文件。下载前必须 path guard + hash guard。

### 风险 5：closeout 被 force 绕过

stale / tampered 不允许 force。warning 可以 force，但必须写 reason。

### 风险 6：候选太多导致 Studio 难用

v5.3 每个 issue 默认 3 个候选即可，最多 5 个。

### 风险 7：score 被误解为音乐质量结论

score 只是排序辅助，最终必须 manual review。

## 25. 给开发的执行准则

开发时按下面顺序推进：

1. 先做 Store 和测试，不碰 UI。
2. 再做 API，不急着加 Studio。
3. Candidate apply 一定要先写回归测试。
4. Signoff / verifier 一定要覆盖篡改场景。
5. Studio 最后接。
6. 每完成一个可独立验收的 Phase，就提交一次。
7. 每次提交前至少跑定向测试。
8. v5.3.0 发布前必须跑完整 release-check。

每个阶段完成后建议推 GitHub，避免本地长期堆大改。

## 26. 建议版本节奏

如果 v5.3.0 一次性太大，可以拆成：

- v5.3.0：Session / Issue / Candidate / Apply / Closeout 主闭环。
- v5.3.1：修 stale / path / signoff 细节。
- v5.4.0：Audio Revision Review Pack，把候选 A/B 包导出给外部听审。
- v5.5.0：Loudness / multi-format delivery。

但 v5.3.0 的最低可发布标准必须包含：

- marker -> issue
- issue -> candidate
- candidate -> manual review
- accepted candidate -> apply
- apply -> release track update
- recheck -> closeout
- release signoff gate
- verifier

少任何一个，这版都不算闭环。

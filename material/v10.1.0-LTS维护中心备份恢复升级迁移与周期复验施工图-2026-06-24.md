## 1. 版本定位

v10.0.0 已经把 MusicForge 收到 GA/LTS：安装文档、GA readiness、Studio System Health、人工验收 runbook、Final Handoff 绑定都已经完成。  
v10.0.1 又修掉了 GA report 自证问题：强门禁必须绑定外部 Manual Acceptance report、Final Handoff ZIP 和 Final Handoff verification report。

下一步不应该继续堆一个更上层公开证明包。  
v10.1.0 应该解决 GA 之后真实维护中会马上遇到的问题：

- 我现在的 `.musicforge/` 里积累了大量 Project、Release、Acceptance、Trust、Publication、Hub、GA 证据，怎么备份？
- 新版本升级前，如何确认我不会把本地证据链、人工听审、Final Handoff、Public Trust Center 结果弄坏？
- 如果开发换人或电脑换机器，如何把工作区恢复到可运行状态？
- 现在 release-check 已经很大，日常维护到底跑哪些检查？
- 如果本地 provider/renderer 配置、ignored 文件、runs 历史目录、GitHub tag 状态漂移，谁提醒我？
- v10 进入 LTS 后，每周、每次发布、每次升级前应该留下什么维护记录？

所以 v10.1.0 的定位是：

> v10.1.0 = LTS Maintenance Center：本地维护工作台 + 安全备份包 + 恢复预案 + 升级前检查 + schema migration 框架 + 周期复验报告。

这版是 GA 之后的“长期维护底座”，不是创作功能扩张。

## 2. 为什么 v10.1 要做这个

MusicForge 现在功能已经非常完整，但长期使用的最大风险已经变成运维风险：

- 本地 `.musicforge/` 是真正的状态中心，GitHub 只保护代码，不能保护用户本地项目、验收、Release、Submission、Trust 证据。
- `.musicforge/provider.json`、`.musicforge/renderer.json` 不能提交，但它们的配置状态又会影响生成、音频渲染和验收。
- `runs/` 被忽略，不应该作为长期证据唯一来源；但很多 export / verification / package 会落在 runs 或 workspace 内。
- 旧机器迁移到新机器时，新开发可能直接复制整个目录，容易把 token、临时缓存、历史产物、路径污染一起带走。
- 以后 v10.2、v10.3 继续做功能时，需要一个正式 migration / upgrade preflight 框架，避免每次 schema 改动都靠开发临时判断。
- 现在 full pytest 很慢，日常维护不能每次都跑完整测试；需要明确 daily / weekly / release / emergency profiles。
- 业务方真正关心的是“我的音乐、验收证据、交付包、公开信任中心，能不能长期复验和恢复”。

v10.1 要把这些问题产品化。

## 3. 本版一句话

> 做一个 LTS Maintenance Center，让开发和业务能一键查看维护状态、创建安全备份、验证备份、生成恢复预案、做升级前检查、执行周期复验，并在 Studio 里看到清晰结果。

## 4. 本版不做什么

明确不做：

- 不做云端备份。
- 不做远程同步。
- 不做账号体系。
- 不做第三方 CA、公证处、时间戳服务。
- 不自动上传 GitHub。
- 不把 provider key、GitHub token、SoundFont 本机绝对路径打进备份。
- 不默认备份 `runs/` 全量历史目录。
- 不做 destructive restore 的默认执行。
- 不把 backup package 当成公开证明包。
- 不做数据库迁移到 SQLite/Postgres。
- 不重写现有 Store。
- 不引入重型依赖。

这版是本地 LTS 运维，不是云运维平台。

## 5. 成功标准

v10.1.0 完成后，应满足：

1. Studio 有 Maintenance / LTS 面板，能看到当前代码版本、Git 状态、GA 状态、最近备份、最近维护检查、最近 upgrade preflight。
2. CLI 有 `maintenance` 总入口，能创建、列出、验证、导出备份，能生成 restore plan。
3. 备份包不会包含明文 API key、GitHub token、本机 token 文件路径、provider/renderer 原始配置明文。
4. 备份 verifier 能发现 ZIP path traversal、反斜杠路径、重复 entry、manifest spoof、hash mismatch、redaction 污染、超大 ZIP bomb。
5. restore 默认只生成 plan，不覆盖当前工作区；真正 restore 必须显式 `--confirm`，并且目标目录必须通过路径安全检查。
6. upgrade preflight 能告诉开发：当前版本、目标版本、工作区是否干净、是否已有可验证备份、ignored config 是否安全、GA 是否可用。
7. migration registry 能记录已执行 migration，并保证 migration 幂等。
8. maintenance check 支持至少 `daily`、`weekly`、`release` 三个 profile。
9. release-check 增加 v10.1 smoke，覆盖 backup、verify、restore-plan、upgrade-preflight、migration idempotency、redaction。
10. README / docs 增加 LTS 维护和备份恢复说明。
11. 发布前本地 `doctor`、`release-check --profile ga --skip-tests --json`、`release-check --profile latest --skip-tests --json` 通过。
12. v10.1.0 tag / GitHub Release / origin/master 对齐。

## 6. 术语

### 6.1 Maintenance Center

本地维护中心。包含：

- 维护状态 summary。
- 备份列表。
- 备份验证报告。
- 恢复预案。
- 升级前检查。
- migration 状态。
- 周期复验历史。

### 6.2 Maintenance Backup

本地备份包。它不是公开证明包，不面向外部接收方。  
它的目标是安全恢复 `.musicforge/` 中的业务状态和关键验收证据。

### 6.3 Restore Plan

恢复预案。默认只读备份包，列出将恢复哪些目录、哪些文件会被覆盖、哪些本机配置需要人工重新配置。  
不执行写入。

### 6.4 Upgrade Preflight

升级前检查。用于 `git pull`、切 tag、升级版本、运行 migration 前。

### 6.5 Migration Registry

本地 schema / store migration 记录。  
未来 v10.x 如果修改本地数据结构，需要在这里登记 migration id、执行结果、source hash 和 rollback note。

## 10. Phase B：Maintenance Backup

### 10.1 目标

创建可验证的本地备份包。  
它要能保存核心业务状态，但不能泄漏 secrets。

### 10.2 Backup 模式

支持三种模式：

```text
metadata
workspace
workspace_with_artifacts
```

#### metadata

只备份：

- projects metadata
- releases metadata
- acceptance reports
- trust operation reports
- public trust center / hub reports
- maintenance state

不备份大文件、不备份原始 references/audio。

#### workspace

默认推荐模式。备份 `.musicforge/` 的大部分业务状态，但排除 secrets 和本机路径配置。

必须排除：

```text
.musicforge/provider.json
.musicforge/renderer.json
.musicforge/local-*.json
.musicforge/*token*
.musicforge/*key*
.musicforge/**/provider-snapshot.json
```

注意：如果现有 store 里有 provider snapshot，它必须走 redaction 后的公开/摘要版本，不能原样备份。

#### workspace_with_artifacts

可选模式。允许带上 selected final exports / release zips / distribution packages / trust packages。  
不默认启用，因为可能很大。

### 10.3 Backup ZIP 固定结构

```text
musicforge-maintenance-backup.zip
  manifest.json
  README.txt
  workspace-index.json
  redaction-report.json
  git-summary.json
  ga-summary.json
  maintenance-summary.json
  data/
    musicforge/
      ...
```

manifest 示例：

```json
{
  "schema_version": 1,
  "package_type": "musicforge_lts_maintenance_backup",
  "backup_id": "mb-000001",
  "created_at": "...",
  "app_version": "10.1.0",
  "mode": "workspace",
  "source": {
    "git_head": "...",
    "git_status": "clean",
    "workspace_root": "."
  },
  "files": [
    {
      "path": "data/musicforge/projects/project-001/project.json",
      "size_bytes": 1234,
      "sha256": "..."
    }
  ],
  "excluded": [
    {
      "path": ".musicforge/provider.json",
      "reason": "secret_or_local_config"
    }
  ],
  "redaction": {
    "status": "passed",
    "finding_count": 0
  },
  "integrity_hash": "..."
}
```

### 10.4 必须排除和脱敏

必须识别：

- `sk-...`
- `ghp_...`
- `github_pat_...`
- `Bearer ...`
- Windows 用户路径，如 `C:\Users\...`
- 任意盘符路径，如 `D:\Music\...`
- UNC 路径，如 `\\server\share\...`
- `githubkey.txt`
- provider api key
- remote URL token

备份 verifier 要在 raw ZIP content 层扫描，不只扫描 manifest。

### 10.5 CLI

```powershell
python -m song_agent.cli maintenance backup create --mode workspace --json
python -m song_agent.cli maintenance backup list --json
python -m song_agent.cli maintenance backup verify --backup-id mb-000001 --json
python -m song_agent.cli verify-maintenance-backup .musicforge\maintenance\backups\mb-000001\musicforge-maintenance-backup.zip --json
```

### 10.6 API

```text
GET  /api/maintenance/backups
POST /api/maintenance/backups
GET  /api/maintenance/backups/<backup-id>
POST /api/maintenance/backups/<backup-id>/verify
GET  /api/maintenance/backups/<backup-id>/download
```

### 10.7 Verifier 检查

必须覆盖：

- ZIP 可读。
- `package_type == musicforge_lts_maintenance_backup`
- ZIP entry path safe。
- raw entry name 不允许反斜杠。
- 不允许 duplicate entry。
- 不允许 absolute path。
- 不允许 `..`。
- 不允许 `.git/`。
- 不允许 `.musicforge/provider.json`、`.musicforge/renderer.json` 原样进入。
- manifest.files 与 ZIP entries 对齐。
- file hash 对齐。
- total uncompressed size 限制。
- entry count 限制。
- redaction scan passed。
- manifest spoof 失败。
- declared extra file 失败。
- hidden extra file 失败。

### 10.8 测试

- create workspace backup。
- verify passed。
- tamper one JSON -> failed。
- add extra entry -> failed。
- duplicate entry -> failed。
- backslash entry -> failed。
- path traversal -> failed。
- inject token -> failed。
- provider.json should not be inside ZIP。
- renderer.json should not be inside ZIP。

## 11. Phase C：Restore Plan 与安全恢复

### 11.1 目标

先做 restore plan，再做可选 restore。  
默认不能直接覆盖当前 `.musicforge/`。

### 11.2 Restore Plan

命令：

```powershell
python -m song_agent.cli maintenance backup restore-plan --backup-id mb-000001 --target C:\tmp\musicforge-restore --json
python -m song_agent.cli maintenance backup restore-plan --zip path\to\musicforge-maintenance-backup.zip --target C:\tmp\musicforge-restore --json
```

输出：

```json
{
  "status": "ready",
  "backup_id": "mb-000001",
  "target": "C:\\tmp\\musicforge-restore",
  "actions": [
    {"action": "create_dir", "path": ".musicforge/projects"},
    {"action": "write_file", "path": ".musicforge/projects/project-001/project.json"}
  ],
  "warnings": [
    "Provider config is not restored. Recreate .musicforge/provider.json manually if needed."
  ],
  "blockers": []
}
```

### 11.3 Restore 执行

命令：

```powershell
python -m song_agent.cli maintenance backup restore --backup-id mb-000001 --target C:\tmp\musicforge-restore --confirm --json
```

规则：

- 没有 `--confirm` 只能输出 plan。
- target 必须是明确目录。
- target 不允许是 repo root，除非额外传 `--allow-current-workspace`。
- 如果 target 已存在且非空，默认 blocked。
- 如果要覆盖，必须传 `--overwrite`，并且先自动生成 target-before-restore backup。
- restore 后自动跑：
  - `doctor`
  - `maintenance status`
  - `ga-check --json`

### 11.4 不恢复的内容

Restore 不自动恢复：

- provider key。
- renderer soundfont path。
- GitHub token。
- remote URL credential。
- local absolute paths。
- browser/session tokens。

Restore plan 必须告诉开发这些需要人工重新配置。

### 11.5 测试

- restore-plan 对 clean target ready。
- restore without confirm 不写文件。
- restore with confirm 写入。
- target traversal blocked。
- non-empty target blocked。
- current repo root blocked。
- unsafe ZIP blocked。
- restore 后 doctor 可运行。

## 12. Phase D：Upgrade Preflight

### 12.1 目标

升级前检查当前 workspace 是否适合升级。

### 12.2 CLI

```powershell
python -m song_agent.cli maintenance upgrade preflight --target-version 10.1.0 --json
python -m song_agent.cli maintenance upgrade preflight --target-version 10.2.0 --require-verified-backup --json
```

### 12.3 检查项

至少包含：

- 当前 app version。
- 当前 git HEAD。
- 当前 branch status。
- origin/master 是否可读。
- 当前 tag 是否存在。
- 工作区是否干净。
- 是否存在 verified backup。
- 最新 backup 是否覆盖当前 git head。
- `.musicforge/provider.json` 是否被 Git 跟踪。
- `.musicforge/renderer.json` 是否被 Git 跟踪。
- `doctor` 是否通过。
- `ga-check` 是否可运行。
- release-check latest 是否可运行。
- migration state 是否健康。

### 12.4 状态

```text
ready
warning
blocked
```

阻断项：

- dirty worktree 且未允许。
- tracked secret config。
- no verified backup when `--require-verified-backup`。
- migration state corrupted。
- current version newer than target version。

### 12.6 测试

## 13. Phase E：Migration Registry

### 13.1 目标

v10.1 建 migration 框架，哪怕本版只有一个 no-op / state 初始化 migration。  
以后 v10.2+ 改 store schema 时必须走这个框架。

### 13.2 migration-state.json

```json
{
  "schema_version": 1,
  "app_version": "10.1.0",
  "applied": [
    {
      "migration_id": "2026-06-24-v10.1-maintenance-state",
      "status": "applied",
      "applied_at": "...",
      "source_hash": "...",
      "result_hash": "...",
      "notes": "Initialized maintenance state."
    }
  ]
}
```

### 13.3 CLI

```powershell
python -m song_agent.cli maintenance migration status --json
python -m song_agent.cli maintenance migration plan --json
python -m song_agent.cli maintenance migration run --json
```

### 13.4 规则

- migration 必须幂等。
- migration 前如果没有 verified backup，要 warning；如果 `--require-backup` 则 blocked。
- migration 不能删除用户数据。
- migration 不能修改 provider/renderer config。
- migration 失败要留下 event。
- migration success 要写 `events.jsonl`。

### 13.5 测试

- status empty。
- plan includes v10.1 init migration。
- run applies once。
- rerun no-op。
- corrupted state failed。
- run with require-backup and no backup blocked。

## 18. 安全边界

### 18.1 Secret 泄漏

最高优先级。  
任何 backup / restore plan / check report / API response / Studio payload 都不能泄漏：

- provider api key。
- GitHub token。
- 本机 token file path。
- SoundFont 绝对路径。
- Windows 用户目录。
- raw provider response。

必须有污染测试。

### 18.2 ZIP 安全

Backup verifier 必须和现有 verifier 保持同等标准：

- raw central directory entry name 检查。
- Windows 反斜杠检查。
- duplicate entry 检查。
- path traversal 检查。
- absolute path 检查。
- case-insensitive `.musicforge` 特殊目录策略。
- ZIP bomb 上限。

### 18.3 Restore 安全

Restore 是本版最大风险。  
默认永远不写文件，只生成 plan。

写入要求：

- `--confirm`
- target path safe
- target empty
- backup verified
- backup package type correct
- manifest hash passed

### 18.4 Backup 不是公开证明

不要给 backup 做 public attestation / registry / transparency / acceptance board。  
backup 是本地恢复工具，不是对外信任链。

### 18.5 Migration 不做破坏性变更

v10.1 migration 只初始化 maintenance state，不做历史 store 改写。  
如果必须改历史数据，只允许写新 sidecar，不允许覆盖原始用户数据。

## 21. Reviewer 验收口径

Reviewer 通过标准：

- Backup 不包含 secrets。
- Backup verifier 能挡住 ZIP 攻击和 redaction 污染。
- Restore 默认只生成 plan，不写文件。
- Restore 写入必须显式 confirm。
- Upgrade preflight 能阻断无备份升级。
- Migration 幂等。
- Maintenance profiles 不为空且失败能传递。
- Studio Maintenance 面板存在且可用。
- release-check v10.1 smoke 通过。
- `ga` / `latest` profile 通过。
- 工作区干净。
- origin/master、tag、GitHub Release 对齐。

Reviewer 不接受：

- 把 `.musicforge/provider.json` 或 `.musicforge/renderer.json` 原样打进 backup。
- 把 SoundFont 本机路径写进 backup。
- restore 默认覆盖当前工作区。
- backup verifier 只信 manifest，不读 ZIP entries。
- empty maintenance profile 返回 passed。
- full pytest 超时却写成 passed。
- remote URL 写 token。
- 文档出现本机 token 路径。

## 22. 风险清单

### P1：备份泄漏 secrets

处理：

- 默认排除 provider/renderer config。
- raw ZIP redaction scan。
- release-check 污染测试。

### P1：restore 路径穿越

处理：

- raw entry name 检查。
- target resolved path 必须在 target root 内。
- restore-plan 与 restore 都做同样检查。

### P1：备份包自证绕过

本版 backup 是本地恢复工具，不做公开证据。  
但 verifier 仍必须防 manifest spoof、extra entry、duplicate、hash mismatch。

### P1：误删用户数据

处理：

- restore 默认 dry-run。
- 非空 target blocked。
- overwrite 前必须自动生成 before-restore backup。

### P2：备份包过大

处理：

- 默认 workspace 不含 `runs/`。
- workspace_with_artifacts 必须显式启用。
- manifest 写 size summary。

### P2：release-check 时间继续变长

处理：

- v10.1 smoke 必须小而完整。
- full pytest 不作为日常维护要求。
- maintenance profiles 分 daily/weekly/release。

### P2：migration 框架过度设计

处理：

- v10.1 只做最小 registry。
- 不做复杂 migration DSL。
- 不做数据库。

1. 先做只读 Maintenance Status。

5. 再接 Studio 面板。

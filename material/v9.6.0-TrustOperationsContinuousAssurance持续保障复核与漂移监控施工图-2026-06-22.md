> 当前稳定基线：v9.5.0<br>

> 核心目标：在 v9.5 Control Signoff 之上，新增持续保障复核层，把一次性签核后的证据漂移、过期、事故、回归防线状态纳入周期性 Assurance Run，并让 Hub 准出可以要求“当前仍然受控”。

## 0. 给开发的话

v9.5 已经完成：

- Trust Operations Hub。
- Delivery evidence gate。
- Incident Response。
- Incident Knowledge / Regression Guards。
- Control Catalog / Policy / Assessment。
- Control Signoff / Exception / Change Request reset。
- Control Signoff Archive / offline verifier。
- Hub gate `--require-trust-control-signoff`。

v9.6 不要重做这些模块。v9.6 要解决的是另一个问题：

> 签核通过只能证明“某一个时间点”满足要求。
> 但系统会继续变化：Hub 可能重新导出，delivery verification 可能更新，incident 可能重开，control exception 可能过期，regression guard 可能长期没跑。
> v9.6 要让系统能周期性回答：当前证据链是否仍然有效？有没有漂移？是否需要人工复核？

建议你把 v9.6 理解成：

```text
v9.5 signed Control Signoff
  + current Hub verification
  + current delivery verification evidence
  + current incident / knowledge / control evidence
  -> Continuous Assurance Run
  -> Assurance Archive ZIP
  -> Offline verifier
  -> Hub gate: require_continuous_assurance
```

```powershell

python -m song_agent.cli release-check --profile v9 --skip-tests --json
```

预期：

- `HEAD = origin/master = v9.5.0^{}`。
- `git status` 只有 `## master...origin/master`。
- v9 profile 6/6 passed。
- latest profile 25/25 passed。

如果基线不对，先停下来，不要在错误分支上开发。

## 1. 为什么需要 v9.6

v9.5 解决的是：

1. Control Assessment 通过后能不能正式签核。
2. 例外能不能审批。
3. 签核后能不能不可变归档。
4. 外部 verifier 能不能离线验收 Control Signoff Archive。
5. Hub gate 能不能要求 Control Signoff。

但 v9.5 仍然是一次性签核模型。它没有解决：

1. 签核后 Hub 证据是否变化。
2. 签核后 delivery verification 是否变化。
3. 签核后 Control Signoff 是否仍匹配当前 Hub / Incident / Knowledge。
4. 低风险例外是否已经过期。
5. Regression Guards 是否长期未运行。
6. Incident Board 是否出现新的 open critical/high incident。
7. Release / Distribution / Submission evidence 是否从 ready 退化。
8. 外部 reviewer 能否拿到一份“持续复核结果”离线验收。

v9.6 要补的是持续保障层：

```text
Signed evidence is not enough.
Current evidence must still match the signed state.
Assurance must detect drift before the next public or delivery gate.
```

## 2. 一句话目标

新增 Trust Operations Continuous Assurance：

```text
Trust Hub + Control Signoff + Delivery Verification + Incident / Knowledge / Control Evidence
  -> Assurance Policy
  -> Assurance Run
  -> Drift / Freshness / Exception / Incident / Guard checks
  -> Assurance Archive ZIP
  -> Offline verifier
  -> Hub gate: require_continuous_assurance
```

v9.6 完成后，系统应该能回答：

- 当前 Hub 是否仍匹配已验证证据。
- 当前 Control Signoff 是否仍匹配当前 Hub / Control / Incident / Knowledge。
- 当前 delivery evidence 是否仍满足 ready。
- 当前 incident 状态是否阻断。
- 当前 exception 是否过期。
- 当前 regression guard 是否缺失或过期。
- 是否可以把持续复核结果打包给外部 reviewer 离线验证。
- Hub 准出是否可以强制要求当前 Continuous Assurance passed。

## 3. 本版边界

### 3.1 v9.6 要做

- Assurance Policy。
- Assurance Run。
- Assurance Report。
- Drift / freshness / exception / incident / guard checks。
- Assurance Archive export / ZIP。
- Offline verifier。
- Hub verifier 新增 `--require-continuous-assurance`。
- CLI / API / Studio 接入。
- release-check matrix 新增 v9.6 smoke。
- README / CHANGELOG / version bump。

### 3.2 v9.6 不做

- 不做真实后台定时任务。
- 不做 OS scheduler / Windows Task Scheduler。
- 不做邮件、Webhook、Slack、飞书通知。
- 不做 provider 或 LLM 自动判断。
- 不自动 reset signoff。
- 不自动 approve Change Request。
- 不自动关闭 incident。
- 不自动重新签核 Control Signoff。
- 不做远程网络探测。
- 不把 Assurance Run 当成法律签名。

### 3.3 为什么不做定时任务

本项目目前是本地优先、可复验优先。真实 scheduler 会带来：

- 长驻进程生命周期。
- 后台任务并发。
- 用户本机环境差异。
- 时间漂移和时区问题。

v9.6 先做“可手动触发、可离线验证、可进入 Hub gate”的 Assurance Run。后续如果要做 scheduler，可以在这个稳定模型上追加。

## 5. 核心原则

### 5.1 不允许自证

Assurance Archive 不能只靠自己内部 JSON 说自己 passed。

Verifier 必须反查外部证据：

- Hub ZIP hash。
- Hub manifest hash。
- Hub verification report hash。
- Control Signoff Archive hash。
- Control Signoff verification report hash。
- Control assessment verification hash。
- Incident Board verification hash。
- Incident Knowledge verification hash。
- Delivery verification report hash list。

如果只改 Assurance Archive 里的 `status: passed` 并重算 manifest，必须 failed。

### 5.2 Drift 必须来源于当前外部证据

Assurance Run 可以保存 source snapshot，但 verifier 不能只信 snapshot。

需要重新读取外部 verification report 并比较：

- `zip_sha256`
- `zip_size_bytes`
- `manifest_hash`
- `verification_report_hash`
- `package_type`
- `status`

### 5.3 时间策略必须可测试

不要直接在核心逻辑里散落 `datetime.now()`。

建议：

- Store 层方法允许传 `now: Optional[str]` 或内部集中用一个 `utc_now_iso()` helper。
- 测试可以构造固定时间。
- Policy 使用天数阈值，但判定函数接受固定当前时间。

### 5.4 签核不可变模型沿用 v9.5

v9.6 不新增 Assurance Signoff。

如果未来要对 Assurance Run 签核，必须单独规划。v9.6 只做：

- Assurance Run。
- Assurance Archive。
- Offline verification。
- Hub gate。

### 5.5 所有 ZIP 都必须固定结构

Assurance ZIP 必须 fixed allow-list：

```text
README.txt
trust-operations-assurance-manifest.json
assurance-run.json
assurance-report.json
assurance-policy.json
evidence-index.json
external-verification-summary.json
assurance-history.jsonl
```

不允许 extra entry。
不允许 declared extra。
不允许 duplicate entry。
不允许 backslash entry。
不允许 `.musicforge/`。
不允许 nested ZIP。

## 7. Store 设计

新增类：

```python
class TrustOperationsContinuousAssuranceStore:
    def __init__(self, root: Path): ...

    def ensure_default_policy(self) -> dict: ...
    def get_policy(self, policy_id: str = "toap-default") -> dict: ...
    def update_policy(self, payload: dict) -> dict: ...

    def refresh_run(self, hub_id: str, payload: dict) -> dict: ...
    def list_runs(self, hub_id: str | None = None) -> list[dict]: ...
    def get_run(self, run_id: str) -> dict: ...
    def export_archive(self, run_id: str) -> dict: ...
    def build_archive_zip(self, run_id: str) -> dict: ...
    def verify_archive_zip(self, run_id: str, payload: dict) -> dict: ...
```

### 7.1 ID 分配

使用现有项目风格：

```text
toa-000001
toa-000002
```

并发创建必须：

- 使用 lock。
- 在 lock 内分配 ID。
- 用 `mkdir(..., exist_ok=False)` 原子占位。

### 7.2 原子写

所有 JSON 写入继续使用项目已有原子写 helper。

不要直接 `write_text` 写核心 JSON，除非该模块现有 helper 已明确允许。

### 7.3 Stale 判定

`get_run()` 应该能返回 stale 状态。

Stale 来源：

- policy hash 变化。
- Hub verification report hash 变化。
- Control Signoff verification report hash 变化。
- Control assessment verification report hash 变化。
- Incident Board verification report hash 变化。
- Incident Knowledge verification report hash 变化。
- Delivery verification report hash 集合变化。

不要让旧 Assurance Run 在外部证据变化后继续被 Hub gate 接受。

### 7.4 Export / ZIP 阻断

如果 run stale：

- `export_archive()` 返回 409。
- `build_archive_zip()` 返回 409。

如果 run failed：

- 允许 export/zip，用于审计失败证据。
- 但 verifier status 应是 failed。
- Hub gate 不接受 failed。

这样外部 reviewer 可以看到失败报告，但准出不会误通过。

## 8. 检查规则

### 8.1 Hub current

必须检查：

- Hub verification report status == passed。
- Hub ZIP sha256 匹配。
- Hub ZIP size 匹配。
- Hub manifest hash 匹配。
- Hub report hash 与 Assurance source 匹配。

失败：

```text
check_id = hub_verification_current
status = failed
severity = blocking
```

### 8.2 Delivery ready

如果 policy `require_delivery_ready=true`：

- Release / Distribution / Submission / Submission Evidence / Release Operations 的 verification report 都必须 passed。
- 如果有多个同类 component，必须按 `component_type + component_id` 一一匹配。
- 缺 report 不能默认为 not_configured passed。

失败：

```text
delivery_verification_missing
delivery_verification_failed
delivery_component_not_ready
```

### 8.3 Control Signoff current

必须检查：

- Control Signoff verification report status == passed。
- Control Signoff Archive ZIP sha256 / size / manifest hash 与 report 匹配。
- Control Signoff verification report 中绑定的 Hub verification hash 与当前 Hub verification hash 匹配。
- Control Signoff verification report 中绑定的 Incident / Knowledge evidence 与当前外部 evidence 匹配。

失败：

```text
control_signoff_verification_missing
control_signoff_verification_failed
control_signoff_source_drift
```

### 8.4 Exception expiry

如果 Control Signoff Archive 或 verification report 暴露 exception summary：

- expired approved exception -> failed。
- critical/high approved exception -> failed。
- required control exception -> failed。
- medium/low active exception -> warning 或 passed，按 policy。

如果现有 Control Signoff verification 已经覆盖 critical/high/required exception，则 Assurance 仍要把结果摘要入 report，便于 Dashboard 看到。

### 8.5 Incident open blocker

如果 Incident Board verification report 可用：

- open critical -> failed。
- open high -> failed，除非 policy 显式降为 warning；默认 failed。
- open medium -> warning。
- resolved/closed -> passed。

需要从 Incident Board external report 或 package summary 读取，不允许从 Assurance report 自证。

### 8.6 Regression Guard freshness

如果 Incident Knowledge / Regression Guards 有 evidence：

- missing required guard -> failed。
- guard stale -> warning 或 failed，默认 warning。
- guard failed -> failed。
- synthetic-only guard -> warning。

如果现有 Knowledge package 没有足够字段，v9.6 先做：

- `missing_guard_evidence` warning。
- 不要强行解析不存在的字段。

### 8.7 Freshness

基于 policy 天数阈值。

判断字段来源：

- verification report `generated_at`。
- package manifest `created_at`。
- signoff `signed_at`。
- fallback 到文件里已有 created_at。

如果字段缺失：

- required evidence 缺 timestamp -> warning。
- 如果 policy `strict_timestamps=true` -> failed。

默认先 warning，避免破坏旧 v9.5 evidence。

### 8.8 Redaction scan

Assurance Archive verifier 必须扫描：

- `sk-...`
- GitHub token。
- Bearer token。
- Windows drive path。
- UNC path。
- `.musicforge` 内部路径。
- `githubkey.txt`。
- provider raw response。

复用 `song_agent/redaction.py`。

```powershell
  --hub-package <hub.zip> `
  --hub-verification-report <hub-verification-report.json> `

  --delivery-verification-report <distribution-verification-report.json> `
  --require-current `
```

### 10.1 Verifier 必须检查

- ZIP 可打开。
- raw central directory entry 安全。
- no duplicate entry。
- fixed allow-list。
- manifest files exactly match fixed allow-list。
- file sha256 / size match。
- manifest integrity。
- report integrity。
- policy integrity。
- evidence-index integrity。
- external-verification-summary integrity。
- source hash match。
- external Hub binding。
- external Control Signoff binding。
- external Control Assessment binding。
- external Incident Board binding。
- external Incident Knowledge binding。
- delivery verification binding。
- redaction scan。
- package_type。
- status。

### 10.2 Full resign 攻击必须失败

测试场景：

1. 生成 passed Assurance ZIP。
2. 修改 `assurance-report.json`：
   - status 改 passed。
   - readiness 改 ready。
   - 删除 blocker。
3. 重算 report integrity。
4. 重算 manifest。
5. ZIP 重新打包。
6. 外部 evidence 不变。
7. verifier 必须 failed。

失败点应类似：

```text
toa_external_summary_match
toa_source_hash_match
toa_hub_verification_binding
```

### 10.3 旧 verification report 必须失败

测试场景：

1. 生成 Assurance ZIP A。
2. verify 得到 report A。
3. 重建 ZIP B 或修改 manifest。
4. Hub gate 使用 ZIP B + report A。
5. 必须 failed。

## 19. 安全边界

### 19.1 不接受 source_path 上传

所有外部 evidence 应来源于：

- 现有 store artifact。
- verifier report。
- base64 upload。
- JSON body。

不要开放：

```json
{
  "source_path": "C:\\Users\\..."
}
```

### 19.2 不泄露本机路径

Archive / report / verifier output 不能包含：

- `C:\Users\...`
- `D:\...`
- UNC path。
- `.musicforge` 内部路径。
- token 文件路径。

### 19.3 不允许 nested package 偷渡

Assurance ZIP 不需要包含外部 Hub ZIP / Control ZIP。

只存摘要和 hash。

### 19.4 不允许旧 report 绑定新 ZIP

所有 verification report 必须包含：

- `zip_sha256`
- `zip_size_bytes`
- `manifest_hash`
- `source_hash`

Hub gate 必须校验这些字段。

## 29. 给开发的最后提醒

v9.6 的关键词不是“再加一个报表”，而是“当前仍然可信”。

你实现时要一直问三个问题：

1. 这个 Assurance passed 是从当前外部 evidence 反推出来的吗？
2. 如果有人改了 Assurance ZIP 并重算所有内部 hash，verifier 能不能挡住？
3. 如果 Hub / Control / Incident / Delivery 在 Assurance 之后变化，旧 Assurance 会不会被拒绝？

只要这三个问题都能稳定回答，v9.6 就是有效的。

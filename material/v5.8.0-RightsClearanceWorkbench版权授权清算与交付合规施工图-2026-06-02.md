# v5.8.0 Rights Clearance Workbench 版权授权清算与交付合规施工图

日期：2026-06-02  
基线版本：v5.7.1  
目标版本：v5.8.0  
角色定位：Reviewer / Planner / Release Gate Designer  
项目：MusicForge / song-agent

---

## 1. 背景

MusicForge 已经从本地确定性作曲 MVP，逐步推进到 Release / Distribution / Submission 级别的交付系统。

截至 v5.7.1，系统已经具备：

- SongPlan / MIDI / WAV / stem / mix / mastering / encoded audio 的生成、审计和验收。
- Acceptance / Human Review / Audio Review / Audio Revision / Mastering / Encoded Audio Acceptance 的人工证据链。
- Release Export / Distribution Export / Submission Package / offline verifier。
- Format Decision Workbench，能解释为什么选择 MP3、FLAC、AAC 等交付格式。
- Release / Distribution signoff gates，能阻止 stale、fake、tampered、synthetic-only、role-incompatible evidence。

现在主要缺口不是“音频文件能不能交付”，而是“这些内容有没有权利可以交付”。

发行级音乐系统必须回答这些问题：

- 这首歌的词曲作者是谁？
- 每个作者的贡献比例是多少？
- 是否用了外部参考音频、MIDI、歌词、风格文本、素材、候选片段？
- 这些引用是否可用于商业发行？
- 是否包含第三方素材、样本、未授权片段、平台禁止内容？
- metadata 里的 credits 是否和实际项目证据一致？
- Distribution / Submission package 里是否有 rights clearance 证据？
- 离线 verifier 能否在脱离 `.musicforge/` 的情况下校验权利证据未被篡改？

所以 v5.8.0 建议做一个大的跨步：Rights Clearance Workbench。

这不是法律意见系统，也不是自动判定真实版权归属。它是一个本地、可审计、可签核的发行合规证据层，用来把“谁贡献了什么、用了什么来源、是否已清算、谁确认过”固化进 Release / Distribution / Submission 的交付链路。

---

## 2. v5.8.0 总目标

新增 Rights Clearance Workbench，覆盖 Release 级版权、授权、素材来源、署名一致性、人工确认、导出证据、离线校验和 signoff gate。

一句话目标：

> 在 Release 进入 Distribution / Submission 前，必须能证明每首 track 的作者、授权、引用素材、credits、lyrics、asset/reference/context pack provenance 都已被人工清算，并且该证据可导出、可离线验证、可防篡改、可阻断签核。

---

## 3. 非目标

v5.8.0 不做以下事情：

- 不自动提供法律结论。
- 不接入真实版权库、PRO、ISRC/UPC 机构、DSP API。
- 不自动识别采样音频里的版权曲目。
- 不做音频指纹匹配。
- 不做合同 PDF OCR。
- 不要求开发准备真实商业合同或真实身份证明。
- 不把用户本机路径、合同原文、token、provider raw response 打进 export ZIP。
- 不自动替换 metadata credits，只做校验和显式同步建议。

---

## 4. 核心原则

### 4.1 手工确认优先

Rights Clearance 可以给 deterministic risk hint，但最终 clearance 必须是人工确认。

所有 release-ready gate 必须要求：

- `review_mode == "manual"`
- `confirmed_by` 非空
- `confirmed_at` 非空
- `attestation` / `reason` / `clearance_note` 非空
- source hash 当前
- integrity hash 通过

### 4.2 本地证据，不外泄敏感信息

系统可以存储本地 evidence，但 export / ZIP 只能写 sanitized summary。

需要脱敏的内容：

- 本机绝对路径。
- GitHub token / API key / Bearer token。
- 合同文件路径。
- 原始 provider response。
- reference source path。
- reviewer private notes 中的敏感值。
- email / phone 等个人信息，除非显式作为 public credit name。

### 4.3 Gate 不信 UI，不信 manifest 摘要

所有 signoff gate 必须重新从 Store 读取当前 rights report，并校验：

- report source hash。
- report integrity hash。
- track coverage。
- release metadata hash。
- referenced asset/reference/context pack/current source hash。
- manually accepted clearance reviews。

### 4.4 Export / verifier 双重校验

Release Export / Distribution Export / Submission Export 要写 rights evidence。

Verifier 必须离线校验：

- summary hash。
- per-track report hash。
- release metadata credits match。
- required files exist。
- JSON integrity。
- redaction scan。
- no dangerous ZIP entry。
- no duplicate entry。

### 6.1 RightsParty

```json

  "created_at": "2026-06-02T00:00:00Z",
  "updated_at": "2026-06-02T00:00:00Z"

```

要求：

- `display_name` / `public_credit_name` 要脱敏。
- `contact` 默认不进入 export。
- `party_type=ai_assisted` 只能表示“使用 AI 辅助创作”，不能表示法律主体。

```json
{
  "party_id": "party-000001",
  "role": "composer",
  "share_percent": 100.0,
  "source": "manual",
  "confirmed": true,
  "notes": "sanitized"
}
```

role 建议枚举：

- `composer`
- `lyricist`
- `arranger`
- `producer`
- `performer`
- `vocalist`
- `engineer`
- `mastering_engineer`
- `publisher`
- `rights_admin`

v5.8.0 必须至少校验：

- composer share total = 100 或明确 waiver。
- lyricist share total = 100，如果 track 有 lyrics 且不是 instrumental。
- producer/arranger 不强制 100，但要能记录。

## 7. Source Hash 口径

Rights source hash 必须覆盖：

- Release tracklist。
- Project final version ids。
- Release metadata track credits。
- Track title / ISRC / lyrics/instrumental flags。
- Asset refs from project versions / edits / candidates / context packs。
- Reference refs from project versions / edits / candidates / context packs。
- Editor clip inserts / template inserts metadata summary。
- Provider usage summary only as sanitized hash, not raw provider response。
- Existing rights parties / contributor splits / manual clearances。

不应该覆盖：

- `updated_at` 这类纯时间字段。
- review import history 中不影响当前 clearance 的旧记录。
- export ZIP path。
- 本机绝对路径。

## 8. 自动检查项

### 8.1 Track Coverage

每个 Release track 必须有 TrackRightsRecord。

失败条件：

- missing track rights record。
- record track_id 不在当前 release tracklist。
- duplicate track rights record。
- hidden/stale project version。

### 8.2 Contributor Split

检查：

- composer split total = 100。
- lyricist split total = 100，如果有歌词且非 instrumental。
- share_percent 在 0 到 100。
- contributor party exists。
- public_credit_name 非空。

状态：

- `failed`：缺 composer / share 不等于 100 / party 不存在。
- `warning`：producer/arranger 缺失。
- `passed`：满足要求。

### 8.3 Metadata Credits Consistency

检查 Release Metadata 的 credits 和 rights contributor 是否一致。

失败条件：

- metadata composer 不在 rights composer。
- rights composer 不在 metadata composer。
- lyrics track 缺 lyricist。
- ISRC 缺失时，如果当前 Distribution/Submission gate 要求 metadata，则 failed。

允许：

- `waived`，但必须有 manual waiver reason。

### 8.4 Source Usage Risk

检查所有来源：

- Asset。
- Reference。
- Context Pack。
- Editor Clip。
- Template insert。
- Candidate apply。
- Provider edit/candidate/review outputs。

风险规则：

- `source_type=reference` 且 `reference_type=audio_wav`：默认 high，需要 manual cleared。
- `source_type=reference` 且 `reference_type=midi`：默认 medium，需要 manual cleared 或 transformation note。
- `source_type=reference` 且 `reference_type=lyrics_text`：默认 high，需要 manual cleared。
- `source_type=style_note`：默认 low，但仍需记录。
- `source_type=asset`：如果 asset 来源是 generated/local project，可以 low；如果来源是 external reference，则继承 reference risk。
- `sample`：critical，默认阻断，除非 manual clearance accepted。

### 8.5 Sensitive / Redaction Scan

任何 rights report / export summary 不允许包含：

- `sk-...`
- `ghp_...`
- `github_pat_...`
- `Bearer ...`
- Windows path：`C:\...`、`D:\...`
- UNC path：`\\server\share\...`
- provider raw response。
- local source_path。
- email / phone 进入 public export，除非显式白名单。

## 12. Release Signoff Gate

Release signoff 新增参数：

```json
{
  "require_rights_clearance": true
}
```

Gate 规则：

必须通过：

- rights report exists。
- report current。
- integrity passed。
- all release tracks covered。
- every track manual clearance accepted 或 explicitly waived。
- composer split passed。
- lyricist split passed for lyrics tracks。
- metadata credits consistency passed 或 waived。
- no blocked / critical unresolved source usage。
- no stale/hidden referenced source。
- redaction scan passed。
- Release Export contains current rights evidence。

失败返回：

```json
{
  "error": "Rights clearance gate failed.",
  "rights_clearance": {
    "status": "failed",
    "failures": [
      "track-000001:composer_share_total",
      "track-000002:high_risk_reference_uncleared"
    ]
  }
}
```

force 策略：

- `critical` / `blocked` / `stale` / `integrity failed` 不允许 force。
- `warning` 可以 force，但必须 override reason。
- `missing manual clearance` 不允许 force。

## 16. 安全边界

### 16.1 Path Safety

所有 export path 必须为固定相对路径。

不允许：

- `../`
- leading slash。
- Windows drive。
- backslash ZIP entry。
- duplicate ZIP entry。

### 16.2 Report Integrity

每个 JSON report 必须有：

- `source_hash`
- `integrity_hash`
- `schema_version`

读取时必须重新计算。

### 16.3 Signed Release Mutability

Release signed 后：

- 不能修改 rights parties。
- 不能修改 rights contributors。
- 不能修改 source clearance。
- 不能 refresh rights report。
- 必须先 reset Release signoff。

### 16.4 Export Stale Guard

如果 rights report 变化后没有重建 Release Export：

- Release signoff `require_rights_clearance=true` 必须 409。
- Distribution signoff `require_rights_clearance=true` 必须 409。
- Submission signoff `require_rights_clearance=true` 必须 409。

## 20. Reviewer 重点检查清单

开发完成后，reviewer 必须重点查：

1. `require_rights_clearance=true` 是否真的阻断 missing/manual/stale/tampered evidence。
2. signed Release 后 rights 相关写操作是否 409。
3. Release Export 是否写 current rights evidence。
4. Export 后修改 rights report，signoff 是否 409。
5. Verifier 是否不信 manifest summary，是否打开 sidecar 重算 hash。
6. Distribution / Submission verifier 是否能抓缺失和篡改。
7. redaction 是否覆盖 Windows path / UNC / token / raw provider response。
8. hidden/stale Reference / Asset 是否阻断。
9. composer / lyricist split 是否按 track 逐条校验。
10. UI 是否只是调用 API，没有前端绕过逻辑。
11. release-check 是否覆盖正向、篡改、stale、redaction、missing contributor。

## 21. 风险清单

### 风险 1：把 rights clearance 做成法律结论

规避：

- 所有文案使用 `clearance evidence` / `manual attestation`。
- 不使用 `legal approved` 这类绝对词。

### 风险 2：导出敏感合同信息

规避：

- Export 只写 summary。
- 原始合同路径/文本不进入 ZIP。
- redaction scan 阻断。

### 风险 3：metadata credits 和 rights contributors 分叉

规避：

- Gate 强制 consistency check。
- 提供 UI 差异提示。
- 不自动覆盖 metadata，除非用户明确操作。

### 风险 4：source usage 漏掉 editor/template/candidate provenance

规避：

- 从 Project Export / Compare / Final Export 已有 metadata 反向聚合。
- release-check 构造至少一个 asset/reference/context pack source。

### 风险 5：签核后仍可改 rights

规避：

- 复用 Release signed mutable guard。
- 所有 POST/refresh/review/party update 都先检查 signoff。

## 22. 与 v5.7 的衔接

v5.7 解决的是：

> 为什么交付 MP3 / FLAC / AAC，且格式证据是否当前、人工验收、角色兼容。

v5.8 解决的是：

> 这些要交付的 track 是否具备可发行的权利、署名、授权和来源清算证据。

二者关系：

- Format Decision 决定“交付什么格式”。
- Rights Clearance 决定“这些内容能不能交付”。
- 两者都应该成为 Release / Distribution / Submission 的可选强 gate。
- 发行级 smoke 应逐步打开两者。

## 24. 最终定义

v5.8.0 完成后，MusicForge 的发行链路应达到：

1. 音频健康可验收。
2. 人工听审可追溯。
3. 编码格式可解释。
4. Distribution / Submission package 可离线验证。
5. 权利、署名、来源、授权清算可审计。
6. 签核后任何会影响交付可信度的内容都不能静默变化。

这一步完成后，后续 v5.9 / v6.0 才适合继续推进：

- v5.9：Platform Submission History / DSP feedback reconciliation。
- v6.0：真实生产项目的 end-to-end release rehearsal。

# MusicForge v1.3.1 到 v1.4.0 施工图：Provider 编辑收紧与多候选生成

> 基准版本：v1.3.0  
> 规划日期：2026-05-07  
> 执行原则：先用 v1.3.1 修掉 Provider preview/apply 的边界，再用 v1.4.0 做多候选 Provider Edit 和自动评分排序。  
> 核心判断：v1.3.0 已经把自然语言 Provider 编辑接进来了，下一步要从“单个 preview”升级成“多个候选方案可比较、可选择、可追踪”。

当前已知观察点：

- Preview apply 还需要更明确地定义“是否允许重复 apply”。
- Preview 应绑定 parent SongPlan source hash，防止父版本变化后误 apply 旧 preview。

## 2. 总路线

推荐路线：

1. **v1.3.1：Provider Edit 收紧版**
   - 不加多候选大功能。
   - 专门修 preview/apply、usage、路由和 stale。
   - 让 v1.3 Provider edit 更稳。

2. **v1.4.0：多候选 Provider Edit**
   - 一次自然语言指令生成多个候选 patch/preview。
   - 本地验证、质量评分、critic 排序。
   - Studio 展示 A/B/C 候选，用户选择一个 apply。
   - 候选组进入 Project 审计和 usage 汇总。

一句话：

> v1.3.1 负责“单候选链路可靠”，v1.4.0 负责“多候选创作决策”。

## 5. v1.3.1 Package B：Preview source hash 与 stale apply 防护

### 5.1 问题

Provider edit preview 生成后，会写入：

```text
.musicforge/projects/<project-id>/edit-previews/<preview-id>/
  preview.json
  patch.json
  candidate-song-plan.json
```

但 preview 当前应明确绑定生成时的 parent `song-plan.json`。否则未来如果 parent version 的 plan 被 force 重跑、修复或异常覆盖，旧 preview 可能被 apply 到不再一致的 parent。

### 5.2 目标行为

创建 preview 时：

- 计算 parent `song-plan.json` 的 sha256。
- 写入 `preview.json`：

```json
{
  "source": {
    "parent_version_id": "v001",
    "parent_job_id": "job-001",
    "song_plan_sha256": "..."
  }
}
```

Apply preview 时：

- 重新计算当前 parent `song-plan.json` sha256。
- 如果 hash 不一致，返回 409：

```text
Provider edit preview is stale because the parent song-plan.json has changed.
```

### 5.3 文件建议

修改：

- `song_agent/provider_edits.py`
- `song_agent/server.py`
- `tests/test_provider_edits.py`
- `tests/test_server_edits.py`

### 5.4 安全规则

- hash 只基于 parent `song-plan.json` 内容。
- 不在 preview metadata 中保存本地绝对路径。
- apply 时不信任 candidate 文件；继续基于 patch + 当前 parent 本地重算最终结果。

### 5.5 测试

新增：

- preview.json 包含 source hash。
- parent plan 不变时 apply 成功。
- parent plan 内容变化后 apply 返回 409。
- stale preview 不创建新 project version。
- stale preview 不创建 edit job。

## 6. v1.3.1 Package C：Preview apply 幂等规则

### 6.1 问题

Preview apply 后会把 preview 标记为 `applied`。需要明确同一个 preview 是否可以再次 apply。

推荐规则：

> 默认不允许重复 apply。同一个 preview 只能生成一个正式 child version。

理由：

- 避免用户连点按钮生成多个重复版本。
- 避免 provider usage 和 project versions 重复。
- 如果确实想再生成一次，应重新生成 preview 或用 child version 创建 variation/edit。

### 6.2 API 行为

如果 preview status 是 `applied`：

```text
POST /api/projects/<project-id>/versions/<version-id>/edit-preview/<preview-id>/apply
```

返回：

```http
409 Conflict
```

body：

```json
{
  "error": "Provider edit preview has already been applied."
}
```

### 6.3 Studio 行为

- Apply 成功后禁用 Apply Preview 按钮。
- 如果再次点击，展示 409 错误，不刷新成空状态。
- Preview result 展示 applied version/job。

### 6.4 测试

新增：

- 同 preview 第一次 apply 成功。
- 第二次 apply 返回 409。
- 第二次 apply 不新增版本。
- Studio HTML/JS 有 applied 状态处理。

## 7. v1.3.1 Package D：Provider usage 接真实 token 字段

### 7.1 问题

v1.3.0 的 provider usage 结构已经存在：

```json
{
  "prompt_tokens": 0,
  "completion_tokens": 0,
  "total_tokens": 0,
  "estimated_cost": null
}
```

但 OpenAI-compatible client 如果返回：

```json
{
  "usage": {
    "prompt_tokens": 100,
    "completion_tokens": 50,
    "total_tokens": 150
  }
}
```

系统应该把这些字段写入 provider usage。

### 7.2 推荐实现

Provider client 返回 patch 时，不只返回 JSON content，还要能带 usage metadata。

可选方案：

#### 方案 A：扩展 client 返回结构

新增：

```python
@dataclass
class ProviderCallResult:
    data: dict[str, Any]
    usage: dict[str, Any] = field(default_factory=dict)
    request_id: str | None = None
```

`generate_edit_patch_json()` 可以继续兼容旧返回 dict，但新 client 可返回 `ProviderCallResult`。

#### 方案 B：在 OpenAICompatibleClient 内保存 last_usage

不推荐。状态型 client 容易并发混乱。

推荐方案 A。

### 7.3 usage 字段映射

写入：

- `prompt_tokens`
- `completion_tokens`
- `total_tokens`
- `request_id`，如果 response header 或 body 有
- `latency_ms`，用本地时间差计算

暂不做真实 cost 估算，`estimated_cost` 仍可为 null。成本估算放 v1.5.0。

### 7.4 测试

新增：

- fake opener 返回 usage，provider edit preview/apply 后 usage 文件包含 token。
- provider usage API 返回 token 汇总。
- token usage 不含 API key。
- mock provider 仍兼容。

## 9. v1.4.0 总目标

v1.4.0 的主题：

> Multi-candidate Provider Edit：一次自然语言指令生成多个候选编辑方案，本地验证和评分排序后，让用户选择一个应用成正式版本。

用户要能说：

- “给我 3 个副歌更燃的版本。”
- “给我 4 个 hook 文案方案，但不要改旋律。”
- “给我 3 个不同和弦走向，保持节奏和歌词。”
- “生成 3 个更适合短视频的版本，我挑一个。”

系统要做到：

1. 生成 N 个候选 patch。
2. 每个候选都能本地 apply 成 preview。
3. 每个候选都跑 validator/quality。
4. 每个候选都有 critic score。
5. Studio 展示候选列表和排序。
6. 用户选择一个 apply。
7. 未选择的候选不进入正式 Project versions。

## 10. v1.4.0 核心概念：Candidate Group

### 10.1 为什么需要 Candidate Group

单个 preview 解决的是“一条指令 -> 一个方案”。多候选要管理的是：

```text
一条指令 -> 多个候选 -> 评分排序 -> 选择一个 apply
```

所以需要一个组级对象，避免把多个 preview 散落在目录里不好管理。

### 10.2 存储建议

```text
.musicforge/projects/<project-id>/candidate-groups/<group-id>/
  group.json
  candidates/
    cand-001/
      preview.json
      patch.json
      candidate-song-plan.json
      validator-report.json
      quality.json
      critic.json
      provider-usage.json
    cand-002/
      ...
```

### 10.3 group.json

```json
{
  "group_id": "cg-001",
  "project_id": "project-demo",
  "parent_version_id": "v001",
  "parent_job_id": "job-001",
  "instruction": "Give me 3 stronger chorus options.",
  "candidate_count": 3,
  "status": "ready",
  "created_at": "...",
  "source": {
    "song_plan_sha256": "..."
  },
  "ranking": [
    {"candidate_id": "cand-002", "score": 91},
    {"candidate_id": "cand-001", "score": 88},
    {"candidate_id": "cand-003", "score": 84}
  ],
  "selected_candidate_id": null,
  "applied_version_id": null
}
```

### 10.4 candidate preview

每个 candidate 复用 v1.3 的 ProviderEditPreview，但需要增加：

```json
{
  "candidate_id": "cand-001",
  "group_id": "cg-001",
  "rank": 2,
  "scores": {
    "quality_overall": 88,
    "critic": 84,
    "novelty": 62,
    "combined": 81
  }
}
```

## 12. v1.4.0 Package B：Multi-candidate Provider Patch Generation

### 12.1 目标

让 Provider 一次或多次生成多个 patch。

### 12.2 两种生成策略

#### 策略 A：单次请求返回多个 candidates

Provider 返回：

```json
{
  "schema_version": 1,
  "candidates": [
    {"summary": "...", "operations": [], "confidence": 0.8},
    {"summary": "...", "operations": [], "confidence": 0.7}
  ]
}
```

优点：

- 省请求次数。
- 候选更容易互相区分。

缺点：

- 单次输出 JSON 更长，更容易坏。

#### 策略 B：多次请求，每次一个 patch

循环调用现有 provider edit patch。

优点：

- 复用 v1.3。
- 更容易重试单个失败。

缺点：

- 请求次数和成本更高。
- 候选之间可能重复。

### 12.3 推荐

v1.4.0 采用混合策略：

- 默认使用策略 A。
- 如果策略 A 返回 invalid，可 fallback 到策略 B。
- mock provider 同时支持两种模式。

### 12.4 新 schema

新增：

```python
class ProviderEditCandidateSet:
    schema_version: int
    candidates: list[ProviderEditPatch]
```

限制：

- `candidate_count` 最小 2，最大 5。
- 每个 patch 仍沿用 v1.3 `ProviderEditPatch` 校验。
- 整体 JSON 最大 128KB。

### 12.5 Prompt Template

新增 built-in template：

- `provider-edit-candidates`

模板必须要求：

- 返回 JSON only。
- 返回候选数组。
- 每个候选必须解释差异。
- 不要包含路径、URL、secret、代码。

### 12.6 测试

- mock provider 返回 3 个候选。
- invalid candidate 被跳过或导致整体失败，规则要明确。
- 超过最大候选数被截断或拒绝。
- fallback 多次请求可用。
- secret/path 被拒。

## 13. v1.4.0 Package C：Candidate Validation、Scoring 和 Ranking

### 13.1 目标

每个候选都不能只是 provider patch。它必须经过本地验证并评分排序。

### 13.2 评分维度

建议先做 deterministic score：

| 维度 | 权重 | 说明 |
| --- | --- | --- |
| quality_overall | 50% | `music_quality` overall |
| validator | 20% | validator passed 得满分，否则失败 |
| patch_confidence | 10% | provider confidence |
| novelty | 10% | 与 parent 差异适中，不是完全没变化 |
| instruction_fit | 10% | critic 对 instruction 匹配度 |

v1.4.0 如果 critic 还比较轻，可以先 deterministic：

- quality_overall 直接来自 quality。
- validator failed 的候选直接排除。
- novelty 用 section/track diff 粗算。
- instruction_fit 先由 provider confidence 或 mock critic 给出。

### 13.3 新模块

新增：

- `song_agent/candidate_scoring.py`
- `tests/test_candidate_scoring.py`

### 13.4 candidate critic

可以新增 prompt：

- `provider-edit-candidate-critic`

但 v1.4.0 不强依赖真实 provider critic。mock/deterministic critic 要能跑 release-check。

### 13.5 失败规则

候选生成后：

- schema invalid：candidate failed。
- apply patch failed：candidate failed。
- validator failed：candidate failed。
- quality 缺失：candidate warning，不一定 failed。

Group 状态：

- 至少 1 个候选 ready：group ready。
- 全部 failed：group failed。
- 部分 failed：group partial_ready。

### 13.6 测试

- 3 个候选能排序。
- validator failed 的候选不排第一。
- quality 更高的候选排名更高。
- novelty 过低会降分。
- group partial_ready 正确。

## 14. v1.4.0 Package D：Candidate Group API

### 14.1 API

新增：

```text
POST /api/projects/<project-id>/versions/<version-id>/edit-candidates
GET  /api/projects/<project-id>/candidate-groups
GET  /api/projects/<project-id>/candidate-groups/<group-id>
POST /api/projects/<project-id>/candidate-groups/<group-id>/apply
POST /api/projects/<project-id>/candidate-groups/<group-id>/delete
```

### 14.2 创建候选组 payload

```json
{
  "instruction": "Give me 3 stronger chorus options.",
  "candidate_count": 3,
  "template_id": "provider-edit-candidates",
  "strategy": "auto"
}
```

### 14.3 apply payload

```json
{
  "candidate_id": "cand-002",
  "name": "Chosen stronger chorus",
  "note": "Selected from candidate group cg-001"
}
```

### 14.4 行为规则

创建：

- 不新增正式 Project version。
- 写 candidate group。
- 每个 ready candidate 有 preview/candidate plan/quality/critic。

Apply：

- 只能 apply ready candidate。
- 检查 source hash。
- group 已 applied 时默认拒绝重复 apply。
- 创建正式 provider_edit project version。
- version metadata 记录 group_id 和 candidate_id。

Delete：

- 只能删 group 文件，不删已经 apply 出来的正式 version。
- 如果 group 已 applied，删除 group 前要保留 version metadata 中的 group/candidate ref。

### 14.5 测试

- 创建 3 候选 group。
- list/detail 返回 ranking。
- apply 排名第一候选成功。
- apply 不存在 candidate 返回 404。
- apply failed candidate 返回 409。
- 重复 apply group 返回 409。
- delete group 不删 version。
- auth 覆盖所有 API。

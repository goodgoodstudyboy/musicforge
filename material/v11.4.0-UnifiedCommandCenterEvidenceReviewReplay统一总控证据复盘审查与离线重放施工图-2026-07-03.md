# v11.4.0 Unified Command Center Evidence Review / Replay 统一总控证据复盘、外部审查与离线重放施工图

> 基线版本：v11.3.1
> 目标版本：v11.4.0
> 日期：2026-07-03
> 施工目标：把 v11.0-v11.3 已经形成的 Unified Command Center、签核、持续复核、漂移响应证据链，整理成一个可交给外部 reviewer 离线复盘、按步骤重放验证、定位缺口和输出审查结论的 Review / Replay 包。

---

## 0. 给开发的话

v11.3.1 已经把 Drift Response 的关键 P1 修住：

- closed Drift Response verifier 不再信 ZIP 内部 `change-request-bindings.json` 自证。
- 新增外部 `change-request-binding-report.json`。
- verifier 会绑定 manual action、source drift、approved CR payload hash、action queue hash、CR binding hash。
- Release signoff / GA readiness 同步要求这份外部 CR proof。
- `missing_cr_proof`、`forged_cr`、`wrong_item_cr`、`reused_cr` 都已进入 v11.3 smoke。

当前稳定基线：

- v11.3.1
- Commit：`7d8eb1431ec1fc002664110693e6f879f3efa926`
- Release：https://github.com/goodgoodstudyboy/musicforge/releases/tag/v11.3.1
- `release-check --profile v11 --skip-tests --json`：`4/4 passed`
- `release-check --profile ga --skip-tests --json`：`29/29 passed`

这说明现在 UCC 链路已经具备：

```text
统一总控 ready
统一总控签核
统一总控归档
最终移交包
签核后持续复核
漂移响应与 CR proof
Release / GA gate 绑定
```

但项目继续往前，如果还只是继续加一个局部小模块，会越来越碎。

v11.4.0 要做的不是再发明一个新的 gate，而是把已有证据链整理成一个 reviewer 真正能用的包：

```text
我拿到这个包，不需要打开 .musicforge workspace。
我能知道这个 release 为什么被认为 ready。
我能看到每条证据来自哪里。
我能按固定顺序重放 verifier。
我能知道哪些证据是 current，哪些是 stale。
我能看到 Drift Response 如何从 failed review 走到 clear recheck。
我能验证 CR proof 不是 ZIP 内部自证。
我能输出审查结论：accepted / needs_changes / rejected。
```

所以 v11.4.0 的定位是：

> 建立 Unified Command Center Evidence Review / Replay Pack，把 UCC、Archive、Handoff、Continuous Review、Drift Response、CR proof、GA readiness、release-check、外部 delivery/trust/maintenance evidence 汇总成一个固定结构、可离线重放、可审查回执、可接入 GA/Release gate 的证据复盘包。

一句话：

```text
v11.3 证明“漂移可以被受控处理”。
v11.4 证明“整条 UCC 证据链可以被外部 reviewer 独立复盘”。
```

## 1. 当前状态

当前 v11 系列能力：

1. v11.0：Unified Command Center
   - evidence graph
   - evidence inventory
   - readiness matrix
   - gap plan
   - safe runbook
   - fixed ZIP
   - offline verifier

2. v11.1：UCC Signoff / Archive / Handoff
   - signoff hash chain
   - signoff binding summary
   - immutable archive
   - final handoff pack
   - approved CR reset

3. v11.2：UCC Continuous Review
   - signed evidence post-signoff review
   - drift report
   - incident board
   - recovery drill
   - external evidence failure becomes blocking drift

4. v11.3：UCC Drift Response
   - failed review -> response case
   - safe action queue
   - manual Change Request binding
   - clear recheck
   - response closeout
   - external CR binding proof

现在的系统已经很强，但 reviewer / 新开发 / 业务验收仍然有一个实际痛点：

> 证据很多，模块很多，命令很多，包也很多。系统能验证，但人不容易复盘。

具体表现：

1. reviewer 要分别找 UCC ZIP、UCC verification、Archive ZIP、Archive verification、Handoff ZIP、Continuous Review ZIP、Drift Response ZIP、CR proof、GA report、release-check report。
2. 每个 verifier 的参数不同，容易漏传外部 proof。
3. 即使所有包都通过，也缺一个“审查叙事”：为什么通过，关键证据是什么，哪些项必须人工确认。
4. 如果 reviewer 发现问题，目前只能散落地创建 CR / drift response，缺一个 review response 入口。
5. 新开发接手时，很难快速理解 v11 证据链的因果顺序。

v11.4.0 要解决这个“可复盘性”和“可审查性”问题。

## 2. v11.4.0 目标

建议模块名：

**Unified Command Center Evidence Review / Replay**

中文名：

**统一总控证据复盘、外部审查与离线重放**

核心目标：

1. 生成 Evidence Review Pack。
2. 将所有 v11 关键证据的 ZIP、verification report、external proof 摘要纳入固定结构。
3. 提供 Replay Plan，明确外部 reviewer 应该按什么顺序运行 verifier。
4. 提供 Replay Result，由系统本地或外部 verifier 逐步重放。
5. 提供 Evidence Narrative，解释从 readiness 到 signoff 到 drift response 的因果链。
6. 支持 External Review Response 导入。
7. accepted response 可生成 Review Acceptance Evidence。
8. needs_changes / rejected response 只能生成 Change Request draft，不自动 reset / signoff / closeout。
9. Release signoff / GA readiness 可选要求 Evidence Review Pack accepted。
10. release-check 增加 v11.4 smoke。

14. 接入 release-check matrix。
15. 更新 README / CHANGELOG / version。

### 3.2 明确不做

v11.4.0 不做这些：

1. 不自动 approve reviewer response。
2. 不自动 reset UCC signoff。
3. 不自动 reset Drift Response。
4. 不自动 close Continuous Review incident。
5. 不自动修改 Release / Distribution / Submission / Trust / Maintenance 证据。
6. 不做远程发布或云端审查服务。
7. 不做账号权限系统。
8. 不做 provider 调用。
9. 不把原始敏感 workspace 路径打进 Review Pack。
10. 不在 Review Pack 内嵌套所有底层 ZIP 的完整内容，除非固定 allow-list 明确允许。

边界原则：

```text
Review Pack 用于复盘和审查，不用于静默修复。
Reviewer response 用于表达结论，不用于直接改系统状态。
任何改变签核、重建归档、接受风险的动作，仍然必须走对应模块的 approved Change Request。
```

## 4. 用户流程

### 4.1 正常复盘流程

1. 用户已有 signed UCC。
2. 用户已有 UCC Archive / Handoff。
3. 用户已有最新 Continuous Review。
4. 如果有 drift，用户已有 closed Drift Response。
5. 用户创建 Evidence Review Pack。
6. 系统生成 Replay Plan。
7. 系统运行 Replay。
8. Replay 全部通过。
9. 系统导出 Review Pack ZIP。
10. 外部 reviewer 离线运行 verifier。
11. reviewer 填写 accepted response。
12. 用户导入 response。
13. 系统生成 Review Acceptance Evidence。
14. Release / GA gate 可要求该 accepted evidence。

### 4.2 发现问题流程

1. reviewer 运行 replay 后发现某一步 failed。
2. reviewer response = `needs_changes` 或 `rejected`。
3. 用户导入 response。
4. 系统只创建 Change Request draft。
5. 不自动修改任何 signed evidence。
6. 用户按具体模块处理问题：
   - Continuous Review failed：走 v11.3 Drift Response。
   - UCC signoff 需要重开：走 v11.1 approved CR reset。
   - 底层 evidence stale：回到底层模块重建并验证。
7. 完成后重新生成 Review Pack。

### 4.3 交接流程

1. 项目负责人导出 Review Pack。
2. 同步给开发 / reviewer / 业务。
3. 对方只需要：

```powershell
python -m song_agent.cli verify-unified-command-center-evidence-review-package review-pack.zip --strict --require-replay-passed
```

4. 如果需要复核 accepted response：

```powershell
python -m song_agent.cli verify-unified-command-center-evidence-review-acceptance-package review-acceptance.zip --review-pack review-pack.zip --review-pack-verification review-pack-verification-report.json
```

`evidence-narrative.json` 和 `reviewer-guide.md` 用于人读。

必须解释：

1. 当前 UCC 是否 ready。
2. 是否 signed。
3. Archive / Handoff 是否 current。
4. Continuous Review 是否 clear。
5. 如果出现过 drift，Drift Response 如何关闭。
6. CR proof 覆盖哪些 manual items。
7. GA readiness 结论。
8. release-check 结论。
9. reviewer 需要人工确认什么。

Markdown 不得包含：

1. 本机绝对路径。
2. token / API key。
3. provider raw response。
4. 未脱敏 source note。

### 6.3 状态机

Review status：

```text
draft
replay_pending
replay_passed
replay_failed
exported
verified
accepted
needs_changes
rejected
stale
archived
```

允许流转：

```text
draft -> replay_pending -> replay_passed -> exported -> verified
draft -> replay_pending -> replay_failed
verified -> accepted
verified -> needs_changes
verified -> rejected
accepted -> archived
```

禁止：

1. `accepted` 后静默 refresh。
2. `accepted` 后重建 ZIP 覆盖旧证据。
3. `needs_changes` 自动改底层证据。
4. `rejected` 自动关闭 Drift Response。

### 6.4 stale 判定

以下任一变化，Review Pack stale：

1. UCC ZIP hash 变化。
2. UCC verification report hash 变化。
3. UCC Archive ZIP / manifest / verification 变化。
4. Handoff ZIP / manifest / verification 变化。
5. Continuous Review ZIP / verification 变化。
6. Drift Response ZIP / verification / CR proof 变化。
7. GA report 变化。
8. release-check report 变化。
9. delivery/trust/public/maintenance 外部 evidence 变化。
10. signoff binding summary 变化。

stale 后：

1. `export_review` 返回 409。
2. `build_zip` 返回 409。
3. `create_acceptance_evidence` 返回 409。
4. Release / GA gate 返回 failed。

## 9. Review Response

### 9.1 Response JSON

外部 reviewer response：

```json
{
  "schema_version": 1,
  "package_type": "musicforge_unified_command_center_evidence_review_response",
  "review_pack_id": "uccer-000001",
  "review_pack_zip_sha256": "...",
  "review_pack_manifest_hash": "...",
  "review_pack_source_hash": "...",
  "replay_result_hash": "...",
  "reviewer": {
    "name": "Reviewer",
    "organization": "External QA",
    "role": "lead_reviewer"
  },
  "result": "accepted|needs_changes|rejected",
  "findings": [
    {
      "severity": "low|medium|high|critical",
      "component": "drift_response",
      "message": "..."
    }
  ],
  "signed_at": "..."
}
```

### 9.2 import 规则

必须：

1. 只接受 JSON/base64 或 ZIP/base64。
2. 拒绝 `source_path` / `local_path` / `file_path`。
3. 必须显式包含：
   - `review_pack_id`
   - `review_pack_zip_sha256`
   - `review_pack_manifest_hash`
   - `review_pack_source_hash`
   - `replay_result_hash`
4. 导入端不得自动补 binding 字段。
5. binding 不匹配则 response status = `stale` 或直接 400。
6. 文本字段全部脱敏。

### 9.3 needs_changes / rejected

如果 response 是 `needs_changes` 或 `rejected`：

1. 生成 Change Request draft。
2. draft 指向对应 finding。
3. 不自动 approve。
4. 不自动 reset。
5. 不自动创建 Drift Response。
6. 不自动修改 UCC。

### 9.4 accepted evidence

accepted response 可以生成：

```text
accepted-evidence/<evidence-id>/evidence-acceptance.zip
```

固定 entries：

```text
manifest.json
acceptance-report.json
original-response-public.json
response-verification-summary.json
original-response-binding-summary.json
README.txt
```

verifier 必须防：

1. reviewer name / organization 全量重签伪造。
2. response binding 改写。
3. accepted 改成 needs_changes 或反过来。
4. Review Pack hash mismatch。
5. duplicate / extra / path / backslash / `.MusicForge` / nested ZIP。
6. redaction scan。

## 17. 风险清单

### P1：Review Pack 变成内部自证

风险：

- `replay-result.json` 自称 passed。
- `verification-summaries` 自称 external reports passed。

要求：

- verifier 必须重新读取外部 ZIP / report。
- 缺外部参数时 required mode failed。

### P1：accepted response 被全量重签伪造

风险：

- 攻击者把 reviewer 改成另一个人。
- 重算 evidence report / manifest。

要求：

- accepted evidence ZIP 必须包含原始 response verification summary。
- verifier 必须反查 raw response hash / payload hash / binding summary。

### P1：CR proof 漏传但 Drift Response 仍通过

风险：

- v11.3.1 修过的点在 v11.4 汇总时退化。

要求：

- Review Pack verifier 必须要求外部 CR proof。
- release-check 必须覆盖 `missing_cr_proof=failed`。

### P1：stale UCC 仍能复盘通过

风险：

- UCC ZIP 被重建，Review Pack 仍使用旧 source。

要求：

- export / zip / acceptance evidence / gate 前都要 runtime stale check。

### P2：包太大或命令太复杂

风险：

- reviewer 不愿意用。

要求：

- `reviewer-guide.md` 必须给一条主命令。
- Replay Plan 让系统帮 reviewer 排序。

### P2：release-check 超时

风险：

- full pytest 太重。

要求：

- v11.4 smoke 必须定向。
- 不强制完整 pytest。
- 但必须跑 v11/latest/ga profiles。

## 21. 给开发的执行提醒

这版不要把目标做偏。

v11.4 不是为了再加一个漂亮 dashboard，也不是为了把所有 ZIP 都复制进一个巨大的包。核心是三件事：

1. **复盘顺序固定**：reviewer 不用猜先验哪个包。
2. **外部证据绑定**：任何 summary 都不能自证通过。
3. **审查结论闭环**：accepted 可以沉淀 evidence；needs_changes / rejected 只能产生 CR draft。

实现时优先保证 verifier 严格性。UI 可以简单，但 verifier 不能松。宁可第一版界面朴素，也不要出现“包内全量重签还能通过”的问题。

如果遇到取舍，按这个优先级：

```text
security verifier > stale guard > release/GA gate > CLI/API > Studio polish
```

每完成一个包，都先补失败复现，再补 happy path。不要最后才补安全测试。

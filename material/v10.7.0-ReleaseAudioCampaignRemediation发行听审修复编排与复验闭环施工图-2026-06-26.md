# v10.7.0 Release Audio Campaign Remediation 发行听审修复编排与复验闭环施工图

> 项目：MusicForge / song-agent
> 计划版本：v10.7.0
> 编写日期：2026-06-26
> 当前稳定基线：v10.6.1
> 角色定位：reviewer / planner
> 目标读者：开发执行人员、测试验收人员、后续 reviewer

---

## 1. 背景

v10.6.1 已经把 Release 级真实听审战役的创建路径收紧到一个可用基线：

- Release track 会记录 `project_id + version_id + final_export_hash`。
- Release-driven Audio Campaign planner 可以从 Release tracks 自动创建 Audio Lab session 和 Audio Campaign。
- Audio Lab session 会复制 WAV 到 session 内，不持久化本机绝对路径。
- Campaign case index 会带 Release track identity。
- Release signoff 的 `require_audio_campaign=true` 会校验 Campaign cases 覆盖当前 Release tracks。
- v10.6.1 修复了 `final_export_hash` stale 问题：当前 `final-export/manifest.json` hash 不匹配 Release track 记录时，planner preflight 会失败，Release signoff 即使 `force=true` 也会 409。

现在主流程已经是：

```text
Release tracks
  -> Release Audio Campaign Plan
  -> Audio Lab Session
  -> Audio Campaign
  -> manual listening review
  -> Campaign signoff/archive/verify
  -> Release signoff / GA readiness
```

这个流程的创建端已经顺了，但失败后的修复端还不够顺。

当前如果听审出现问题，开发仍需要手工串联：

1. 找出 Campaign 里哪些 case 是 `needs_fix` / `rejected`。
2. 找出具体 Audio Lab session item 和 marker。
3. 手动创建 Audio Fix Sprint。
4. 手动创建 draft。
5. 手动生成 candidate。
6. 手动做 A/B review。
7. 手动选择 candidate。
8. 手动创建 recheck session。
9. 手动复听 recheck item。
10. 手动 close Audio Fix Sprint。
11. 再手动 refresh Campaign report。
12. 再手动 signoff / archive / verify。
13. 再手动回到 Release signoff。

也就是说，v10.6 解决了“从 Release 正确创建听审战役”，但还没有解决“听审失败后如何系统化修复并回到 Release 准出”。

v10.7.0 要补上这个缺口。

---

## 2. 一句话目标

> v10.7.0 要新增 Release Audio Campaign Remediation Orchestrator：从 Release-bound Audio Campaign 的失败 case 自动生成修复计划、Fix Sprint、候选、复验任务和 closeout 证据，把“听出问题 -> 修复 -> A/B -> 复验 -> 回到 Campaign/Release 准出”变成一个可追踪、可复跑、可门禁的标准流程。

## 3. 业务定位

### 3.1 v10.2 到 v10.7 的关系

| 版本 | 已解决问题 | 粒度 |
|---|---|---|
| v10.2 | 能不能真实渲染、播放、人工听、打 marker | Audio Lab session |
| v10.3 | 单个或多个 marker 能不能变成修复冲刺 | Audio Fix Sprint |
| v10.4 | 一批歌能不能批量真实听审并形成 Campaign | Audio Campaign |
| v10.5 | Campaign 能不能变成 Governance evidence | Campaign Archive / GA gate |
| v10.6 | 能不能从 Release 自动创建绑定正确的 Campaign | Release-driven Campaign Plan |
| v10.7 | Campaign 失败后能不能自动编排修复和复验闭环 | Release Campaign Remediation |

v10.7 不替代 v10.3 的 Audio Fix Sprint，而是把多个 Fix Sprint 编排成 Release/Campaign 级闭环。

### 3.2 这一版要证明什么

v10.7 完成后，系统应能回答：

- 当前 Release-bound Campaign 有哪些失败 case？
- 每个失败 case 是否已经生成修复冲刺？
- 是否有重复 Fix Sprint？
- 每个 Fix Sprint 是否已经有 candidate？
- candidate 是否经过人工 A/B review？
- 是否已选择 candidate？
- 是否已创建 recheck session？
- recheck 是否使用 release-ready real audio？
- recheck 是否全部 manual accepted？
- Fix Sprint closeout 是否 passed？
- Campaign report 是否已经重新刷新并 passed？
- Campaign signoff/archive/verify 是否可以继续执行？
- Release signoff 是否还能绑定当前 Campaign evidence？

### 3.3 这一版不做什么

明确不做：

- 不自动替代人工听审。
- 不自动把 `needs_fix` 判成 `accepted`。
- 不自动 select candidate。
- 不自动 signoff Campaign。
- 不自动 Release signoff。
- 不接外部音乐生成 API。
- 不引入 provider 自动修复。
- 不做 DAW 级音频编辑。
- 不把 fake/test WAV 当 release-ready。
- 不修改 v8/v9 Public Trust Center 或 Trust Operations Hub 主链。

### 8.1 Refresh Plan 规则

输入：

- `release_id`
- 可选 `campaign_id`

如果 `campaign_id` 缺失：

1. 读取 Release Audio Campaign Plan link。
2. 如果 link 缺失，返回 409：

```text
Release Audio Campaign link is missing. Create or link a campaign first.
```

3. 如果 link coverage 不 passed，返回 409。

Plan 必须读取：

- Release tracks。
- Audio Campaign。
- Campaign report。
- Campaign case index。
- Audio Lab sessions / cases。
- 已有关联 Audio Fix Sprint。
- 每个 sprint closeout。

Plan 必须做 stale 判断：

- Release track identity 变化。
- Release track current final export hash 不匹配。
- Campaign source hash 变化。
- Campaign report hash 变化。
- Case index hash 变化。
- Audio Lab session item source hash 变化。
- Fix Sprint source hash stale。

### 8.2 Issue 收集规则

从 Campaign cases 收集问题：

- case review status 是 `needs_fix`。
- case review status 是 `rejected`。
- case 有 high marker。
- case 有 critical marker。
- case 关联 Audio Fix Sprint 但 sprint 未 closed。
- case 关联 Fix Sprint closeout failed。
- case recheck 仍 needs_fix / rejected。
- case recheck audio 是 fake/test。

去重 key：

```python
stable_hash({
  "campaign_id": campaign_id,
  "case_id": case_id,
  "session_id": session_id,
  "item_id": item_id,
  "marker_id": marker_id or "review",
  "marker_source_hash": marker_source_hash,
  "release_track_identity": identity_key,
})
```

同一 issue 重复 refresh 不应产生新 issue id。

## 9. Safe Action Queue

### 9.1 run-safe 的原则

`run_safe_actions()` 只能做不会替代人工判断的事情。

允许：

- 刷新 plan。
- 创建缺失 Fix Sprint。
- 创建 drafts。
- 生成 local candidates。
- 刷新 closeout report。
- 刷新 campaign report。
- 导出 remediation evidence。

禁止：

- 自动写入人工 review。
- 自动 select candidate。
- 自动 close sprint。
- 自动 campaign signoff。
- 自动 release signoff。
- 自动 reset signoff。
- 自动 force override。

### 9.2 Action 状态

动作状态：

```text
pending
running
completed
manual_required
blocked
skipped
failed
stale
```

如果遇到人工步骤，状态必须是 `manual_required`，不能用 `completed` 伪装。

### 9.3 Idempotency

重复运行 `run-safe`：

- 不重复创建同 source key 的 Fix Sprint。
- 不重复创建同 item/draft type 的 draft。
- 不重复生成已有且未 stale 的 candidate，除非 payload 明确 `regenerate=true`。
- 不重复 export ZIP，除非 source hash 变化且未签核。

## 10. 与 Audio Fix Sprint 的集成

### 10.1 创建 Fix Sprint

优先复用现有：

```python
AudioFixSprintStore.create_sprint({
  "session_ids": [session_id],
  "name": f"Release {release_id} campaign {campaign_id} fix {session_id}",
  "include_test_audio": False
})
```

需要补充：

- sprint `source` 里记录 `release_id`、`campaign_id`、`case_ids`。
- issue -> sprint 映射写入 remediation plan。
- 如果已有 open sprint 匹配相同 source key，复用而不是报错。

### 10.2 Draft

默认 draft type：

```text
mix_patch
```

可选：

```text
review_task
audio_revision
mix_patch
```

默认策略：

- `mix_balance` -> `mix_patch`
- `mastering` -> `audio_revision`
- `timing` -> `review_task` 或 `mix_patch`
- `arrangement` -> `review_task`
- `noise` -> `audio_revision`
- `performance` -> `review_task`
- `other` -> `review_task`

### 10.3 Candidate

候选生成仍然只允许 local deterministic。

如果现有 AudioFixSprintStore 只能生成本地候选，v10.7 不要扩展 provider。

### 10.4 A/B Review

必须人工：

- `review_mode=manual`
- `playback_confirmed=true`
- reviewer name/role 必填并脱敏
- preferred 不能自动默认

### 10.5 Recheck

recheck session 必须：

- 绑定 selected candidate。
- 使用 release-ready audio。
- 不允许 fake/test WAV。
- 每个 recheck item 必须 manual accepted。

### 10.6 Close Sprint

只有满足：

- selected candidate 存在。
- A/B manual review 存在。
- recheck session 存在。
- recheck item manual accepted。
- release-ready audio count 覆盖全部 selected items。
- no needs_fix / rejected recheck。

才能 close。

## 11. 与 Audio Campaign 的回链

Remediation closeout passed 后，要做：

1. `AudioCampaignStore.refresh_report(campaign_id)`。
2. Campaign report 应从 needs_fix 变 passed。
3. Campaign signoff 才允许继续。
4. Campaign archive/verify 继续沿用 v10.5 的治理链。

如果 Campaign 已经 signed：

- 不允许 remediation 修改 Campaign。
- 返回：

```text
Signed Audio Campaign cannot be remediated. Reset campaign signoff with an approved Change Request first.
```

## 12. Release / GA Gate 接入

### 12.1 Release signoff 新参数

建议新增可选参数：

```json
{
  "require_audio_campaign_remediation": true,
  "audio_campaign_remediation_zip_path": "...",
  "audio_campaign_remediation_verification_report_path": "..."
}
```

如果 `require_audio_campaign_remediation=true`：

- 必须有 remediation closeout passed。
- 必须绑定当前 Release id。
- 必须绑定当前 Campaign id。
- 必须绑定当前 Campaign report hash。
- 必须绑定当前 Release track final_export_hash。
- 必须无 stale。
- 如果当前 Campaign 从未出现 issue，可以允许 remediation summary `issue_count=0`，但仍要生成 closeout evidence。

### 12.2 GA readiness

`ga-check` 可选接入：

```text
--require-audio-campaign-remediation
--audio-campaign-remediation-zip
--audio-campaign-remediation-verification-report
```

如果没有要求，不阻断 GA。

### 12.3 不要破坏已有 require_audio_campaign

`require_audio_campaign=true` 仍然只要求 Campaign Archive。

`require_audio_campaign_remediation=true` 是额外门禁，不要隐式打开，避免影响现有用户。

## 16. 安全和不可变规则

### 16.1 Stale Guard

以下变化必须使 remediation plan stale：

- Release tracks 改变。
- Release track final_export_hash 与当前 manifest hash 不一致。
- Audio Campaign source hash 改变。
- Campaign report hash 改变。
- Case index hash 改变。
- Audio Lab session source hash 改变。
- Fix Sprint source hash 改变。
- Candidate artifact hash 改变。
- Recheck session source hash 改变。

stale 后：

- `run-safe` 返回 409。
- `closeout` 返回 failed。
- `signoff` 返回 409。
- `export/zip` 返回 409，除非仅导出 stale diagnostic report，默认不做。

### 16.2 Manual Guard

不能自动写：

- manual A/B review
- manual recheck review
- selected candidate
- close sprint
- campaign signoff
- release signoff

### 16.3 Fake/Test Audio Guard

以下不能作为 passed closeout：

- `test_fake_count > 0`
- `release_ready_audio_count < selected item count`
- renderer runner_kind 不是 real
- audio health failed
- WAV missing 或 hash mismatch

### 16.4 Redaction

所有人工输入必须走：

```python
sanitize_sensitive_text()
sanitize_metadata()
```

覆盖字段：

- sprint name
- action notes
- reviewer name
- reviewer role
- candidate review notes
- recheck notes
- selected_by
- signed_by
- override reason
- closeout notes

禁止落盘：

- `sk-...`
- `ghp_...`
- `api_key=...`
- `Authorization: Bearer ...`
- `C:\Users\...`
- `D:\...`
- UNC path
- `provider-snapshot.json`
- raw provider response

## 18. release-check

新增：

```text
v107.release_audio_campaign_remediation_smoke
```

加入 profiles：

- `v10`
- `ga`
- `latest`
- `quick`
- `full`

Smoke 必须覆盖：

1. 创建 Release。
2. 添加带真实 WAV 的 Project final export track。
3. 用 v10.6 planner 创建 Release-bound Campaign。
4. 写入一个 `needs_fix` review 和 high marker。
5. Campaign report 状态应为 needs_fix / failed。
6. Refresh remediation plan。
7. Plan issue_count = 1。
8. `run-safe` 创建 Fix Sprint。
9. `run-safe` 创建 draft。
10. `run-safe` 生成 local candidate。
11. candidate 未 manual A/B 时，closeout failed。
12. 写入 manual A/B review。
13. select candidate。
14. create recheck session。
15. recheck 未 manual accepted 时，closeout failed。
16. 写入 manual accepted recheck。
17. close Fix Sprint passed。
18. remediation closeout passed。
19. refresh Campaign report passed。
20. Campaign signoff/archive/verify passed。
21. Release signoff with `require_audio_campaign=true` passed。
22. Release signoff with `require_audio_campaign_remediation=true` passed，如果本版接入此 gate。
23. 修改 final export manifest 后，remediation run-safe 409。
24. 修改 campaign report/hash 后，remediation signoff 409。
25. duplicate run-safe 不重复创建 Fix Sprint。
26. redaction 注入后 export 不含敏感原文。
27. ZIP tamper failed。

Smoke detail 建议输出：

```text
plan=needs_action, issues=1, sprint=afs-000001, candidate=afc-000001,
manual_ab=passed, recheck=accepted, closeout=passed, campaign=passed,
```

## 24. Reviewer 验收重点

Reviewer 应重点复现：

### 24.1 正常闭环

```text
Release -> Campaign -> needs_fix -> remediation plan -> Fix Sprint -> candidate
-> manual A/B -> selected -> recheck -> manual accepted -> closeout -> campaign passed
```

### 24.2 stale final export

1. Release 添加 track。
2. 创建 Campaign。
3. 修改 project final-export manifest。
4. remediation run-safe 必须 409。
5. Release signoff with force 仍必须 409。

### 24.3 duplicate sprint

重复 run-safe 不得重复创建 sprint。

### 24.4 manual guard

无 manual A/B 或 manual recheck，closeout 必须 failed。

### 24.5 fake/test guard

使用测试 WAV 或 fake runner，closeout 必须 failed。

### 24.6 signed campaign guard

Campaign signed 后，不允许 remediation 静默改 Campaign。

### 24.7 redaction

人工字段注入：

```text
sk-secret-value
api_key=secret
C:\Users\liuhuanji\...
```

导出和 ZIP 不得保留原文。

## 25. 给开发的话

这版不要急着做 UI，先把 Store 和 release-check 跑通。核心不是“多几个按钮”，而是要让失败听审的状态机可靠：每个 issue 从哪里来、生成了哪个 Fix Sprint、候选是否人工 A/B、复验是否真实音频、closeout 是否能反查当前 Campaign 和 Release，这些都必须有 hash 绑定和 stale guard。

实现时优先复用现有 `AudioCampaignStore.create_fix_sprints()` 和 `AudioFixSprintStore`，不要复制一套修复系统。v10.7 的价值是编排和门禁，不是重写修复引擎。每完成一个阶段就提交并推 GitHub；不要攒到最后一次性提交，方便 reviewer 在中途发现状态机问题。

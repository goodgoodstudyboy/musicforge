# v4.3.0 Submission Workspace 多平台提交批次工作台施工图

创建日期：2026-05-18  
目标版本：v4.3.0  
当前稳定基线：v4.2.1  
角色定位：Reviewer 施工图 / 开发执行指南

---

## 1. 背景

MusicForge 现在已经走到了一个新的阶段。

从 v3.7 到 v4.2，系统已经具备：

- Release Workspace：把多个 Project Final Export 组织成一个 Release。
- Release Metadata：发行资料、平台元数据、歌词、credits。
- Distribution Prep：针对不同平台或用途生成 Distribution Target。
- Platform Template Packs：模板规则、平台字段映射、提交清单。
- Distribution Package Layout Contract：把 audio / artwork / lyrics 的包内路径变成可预览、可校验、可离线验收的契约。
- verify-distribution-package：脱离 `.musicforge/` 后仍能验证交付包完整性、安全性、签核追溯。

v4.2.1 已经收紧了两个关键交付风险：

- 真实源文件扩展名和模板渲染扩展名必须一致，不能把 MIDI fallback 包装成假 WAV。
- verifier 遇到恶意或损坏的 `template-pack.json` 必须输出 failed report，不能异常崩溃。

所以 v4.3.0 不应该继续在单个 Distribution Target 里小修小补。

下一步要解决的是：

> 一个 Release 往往不是只交给一个平台，也不是只有一个 ZIP。用户需要把多个 Distribution Target 组织成一次“提交批次”，记录每个平台包的准备状态、提交时间、提交人、外部平台回执、补件请求、最终通过情况。

这就是 v4.3.0 的核心：Submission Workspace。

---

## 2. v4.3.0 定位

v4.3.0 做：

> Release Submission Workspace：把一个 Release 下多个已签核 Distribution Target 组织成可审计、可验收、可导出的本地提交批次。

它是“提交前最后一道本地工作台”，不是平台 API 自动上传器。

它要解决：

- 多平台 target 一次性组织。
- 每个平台包的状态对齐。
- 提交前总 QA。
- 提交批次签核。
- 提交记录、外部回执、补件记录。
- 可导出 submission bundle。
- 离线 verify submission bundle。
- Studio 顶层操作面板。

---

## 3. 明确不做什么

v4.3.0 不做以下事项：

- 不接入 Spotify / Apple Music / YouTube / DistroKid / TuneCore / CD Baby 等真实平台 API。
- 不做 OAuth 登录。
- 不自动上传音频、封面或 metadata 到外部平台。
- 不爬取平台状态。
- 不做 royalty / split accounting。
- 不做版权合同管理。
- 不做 ISRC / UPC 自动申请。
- 不做外部邮件发送。
- 不做云同步。
- 不改变 v4.2 Distribution Package ZIP 格式的核心口径。

这些可以放到 v4.4+ 或 v5.x。

v4.3.0 只做本地提交批次管理和可验证导出。

---

## 4. 当前能力缺口

现在用户已经能对一个 Distribution Target 做：

- QA
- Export
- ZIP
- Signoff
- Verify

但是缺少这些关键能力：

1. 无法把多个 target 组织成“一次提交”。
2. 无法知道一个 Release 目前哪些平台包已签核、哪些还没签核。
3. 无法记录“这个 ZIP 已经在 2026-05-18 提交给某平台”。
4. 无法保存平台回执编号、外部链接、审核状态。
5. 无法记录平台要求补件时，补件原因和重新提交历史。
6. 无法导出一份“提交批次包”，给团队或自己归档。
7. 无法离线验证 submission bundle 是否被篡改。
8. Studio 没有一个统一视图看所有平台交付进度。

v4.3.0 要补这些。

## 5. 核心概念

### 5.1 Distribution Target

已有概念。

一个 target 是面向某个平台或用途的一份 Distribution Package。

例如：

- Generic DSP
- Demo Pitch
- Internal Archive
- Apple Music Template
- YouTube Content ID Template

target 的职责仍然是生成单个平台包。

### 5.2 Submission Batch

v4.3.0 新增概念。

一个 Submission Batch 是一次提交批次。

它属于一个 Release，包含多个 Distribution Target 的提交记录。

例如：

```text
release-000001
  submissions/
    sub-000001/
      submission.json
      qa.json
      submission-export/
      submission-package.zip
      submission-signoff.json
      events.jsonl
```

一个 batch 可以包含：

- target-000001：Generic DSP
- target-000002：Internal Archive
- target-000003：Demo Pitch

它记录这些 target 当前打包文件的 hash、签核状态、外部提交状态。

### 5.3 Submission Item

Submission Batch 内的单个平台条目。

一个 item 绑定一个 target。

它记录：

- target_id
- package_id
- distribution_zip_sha256
- verifier summary
- submission status
- external reference
- submitted_at
- submitted_by
- platform_status
- resubmission_count
- latest_feedback

### 5.4 Submission QA

整个 batch 的总 QA。

它不替代 Distribution QA，而是汇总并增加跨 target 检查。

### 5.5 Submission Signoff

提交批次签核。

只有 batch QA 通过或 warning 时才允许签核。

签核后禁止静默改写 batch export / zip / items。

## 10. Submission Store API

### 10.1 create_submission()

输入：

```json
{
  "name": "DSP submission round 1",
  "target_ids": ["target-000001", "target-000002"],
  "notes": "First submission batch"
}
```

行为：

- 验证 release 存在。
- 验证 target 存在。
- item 初始从 target 快照生成。
- 如果 target 已 signed，则 item `submission_status=ready`。
- 如果 target 未 signed，则 item `submission_status=pending` 且 warning。
- 写 `submission.json`。
- 写 event。

### 10.2 add_target()

行为：

- 签核后的 submission 禁止 add。
- archived submission 禁止 add。
- 同一个 target 不允许重复添加。
- 添加后 QA/export/signoff summary 标 stale。

### 10.3 remove_target()

行为：

- 签核后的 submission 禁止 remove。
- 如果 item 已 submitted / accepted，默认禁止删除。
- 可支持 `withdraw=true`，但不删除审计，只把 item 标 `withdrawn`。

### 10.4 refresh_items()

行为：

- 重新读取 target 的 latest package / signoff / verifier 状态。
- 如果 target package hash 变化，item 标 stale。
- 如果 target signoff reset，item 标 stale。

### 10.5 record_submission()

记录某 item 已经提交到外部平台。

输入：

```json
{
  "submitted_by": "LHJ",
  "external_reference": "APPLE-123456",
  "external_url": "https://example.invalid/submission/123",
  "submitted_at": "2026-05-18T10:00:00+08:00",
  "note": "Uploaded manually"
}
```

要求：

- item 必须 ready。
- submission batch 必须 signed，或者允许 reviewer 明确决定是否允许未签核记录提交。
- 建议 v4.3.0 规定：必须 signed 后才能 record submitted。
- `external_url` 只允许 http/https，输出时脱敏。
- 不允许本机路径。
- 记录 event。

### 10.6 record_feedback()

记录平台反馈。

输入：

```json
{
  "status": "needs_changes",
  "message": "Cover art text too close to edge",
  "fields": ["artwork"],
  "received_at": "2026-05-18T11:00:00+08:00"
}
```

要求：

- 文本值脱敏。
- 可产生 follow-up note。
- 如果 status=needs_changes，则 item/submission 标 needs_changes。

### 10.7 mark_accepted()

记录平台通过。

输入：

```json
{
  "external_reference": "APPLE-123456",
  "accepted_at": "2026-05-18T12:00:00+08:00",
  "note": "Approved by platform"
}
```

## 11. Submission QA

新增 `build_submission_qa_report()`。

### 11.1 source state

source state 至少包含：

- release_id
- release status
- release latest signoff summary
- release latest export summary
- submission items
- each target snapshot
- target package id
- target package zip sha256
- target distribution manifest hash
- target signoff hash
- target verifier summary
- target template hash
- target layout hash

source_hash 必须基于脱敏后的 source state。

### 11.2 checks

必须有：

| check_id | severity | 说明 |
| --- | --- | --- |
| release_exists | blocking | Release 必须存在 |
| release_not_archived | blocking | archived release 不可提交 |
| release_signed | blocking | Release 必须已签核 |
| submission_has_items | blocking | 至少一个 item |
| target_exists | blocking | 每个 item 的 target 必须存在 |
| target_signed | blocking | 每个 target 必须已签核 |
| target_zip_exists | blocking | 每个 target 必须有 package ZIP |
| target_zip_hash_match | blocking | item 记录的 ZIP hash 必须和当前一致 |
| target_verify_passed | blocking | 每个 target verifier 必须 passed 或 warning |
| target_not_stale | blocking | target QA/export/signoff 不得 stale |
| duplicate_profile | warning | 同 profile 多个 target 给 warning |
| duplicate_template | warning | 同 template 多个 target 给 warning |
| submission_feedback_open | warning | 存在未处理 needs_changes |
| external_reference_safe | blocking | 外部回执字段不得含本机路径/secret |
| redaction_scan | blocking | raw submission 不得含敏感值 |

### 11.3 QA 状态

```text
failed：存在 blocking failed
warning：无 blocking failed，但有 warning
passed：全部通过
stale：source_hash 不一致
```

## 13. Submission ZIP

新增 `build_submission_package_zip()`。

输出：

```text
submission-package.zip
```

ZIP 必须包含：

```text
submission-manifest.json
submission-signoff.json
README.txt
submission-report.json
submission-targets.csv
submission-events.jsonl
targets/target-000001/distribution-package.zip
targets/target-000001/distribution-manifest.json
targets/target-000001/distribution-verify-report.json
```

必须检查：

- entry name 不能绝对路径。
- entry name 不能包含 `..`。
- entry name 不能包含反斜杠。
- 不能有 duplicate entry。
- entry count 上限。
- 总解压大小上限。
- 单文件大小上限。

不要信 manifest.zip.entries 作为放行来源。

允许列表必须来自：

- manifest.files[].path
- 必需 sidecars：
  - `submission-manifest.json`
  - `submission-signoff.json`

## 14. Submission Signoff

新增：

```python
sign_submission_package()
reset_submission_signoff()
submission_signoff_summary()
```

### 14.1 签核前置条件

必须满足：

- QA status in `passed|warning`
- export exists
- ZIP exists
- source_hash 一致
- submission-manifest hash 一致
- 每个 target ZIP hash 一致
- 每个 target verify report 仍 passed/warning

### 14.2 签核记录

```json
{
  "schema_version": 1,
  "submission_id": "sub-000001",
  "status": "signed",
  "signed_by": "LHJ",
  "signed_at": "...",
  "force": false,
  "reason": "",
  "export_manifest_hash": "...",
  "sidecar_payload_hash": "..."
}
```

参考 v3.8.1：

- `export_manifest_hash` 校验 manifest without zip。
- `sidecar_payload_hash` 覆盖 `submission-signoff.json` 除 hash 字段以外的展示字段。
- 篡改 signed_by / signed_at 必须被 verifier 抓住。

### 14.3 签核后写保护

签核后禁止：

- add target
- remove target
- refresh items
- export
- zip
- update notes
- update item submitted metadata

是否允许 record external submission？

建议允许，因为签核后才应该记录真实提交。

但要做成“状态事件追加”，不能改写已签核 export/zip。

也就是说：

- signed submission package 不变。
- post-signoff submission status events 记录在 `events.jsonl` 和 `submission.json`。
- 如果要把提交状态重新打包归档，必须 reset signoff 再 export/zip/signoff。

## 15. 离线校验 CLI

新增命令：

```powershell
python -m song_agent.cli verify-submission-package path\to\submission-package.zip
```

参数：

```text
--json
--report-out <path>
--strict
--require-submitted
--require-accepted
```

### 15.1 verify checks

必须检查：

| check_id | 说明 |
| --- | --- |
| zip_open | ZIP 可打开 |
| zip_entry_path_safe | entry path 安全 |
| zip_duplicate_entries | 不允许重复 entry |
| zip_entry_count_limit | entry 数量上限 |
| zip_total_uncompressed_limit | 总解压大小上限 |
| submission_manifest_exists | manifest 存在 |
| submission_signoff_exists | signoff 存在 |
| submission_manifest_schema | schema 合法 |
| submission_manifest_file_hash_match | files hash 对账 |
| submission_signoff_hash_match | signoff hash 对账 |
| submission_signoff_sidecar_payload_hash | signoff 展示字段防篡改 |
| target_distribution_zip_exists | 每个 target ZIP 存在 |
| target_distribution_zip_hash_match | 每个 target ZIP hash 一致 |
| target_distribution_manifest_exists | target manifest 摘要存在 |
| target_verify_report_exists | target verify report 存在 |
| target_verify_status_allowed | target verify passed/warning |
| csv_formula_safe | CSV 安全 |
| redaction_scan | 无 secret / 本机路径 |

### 15.2 嵌套 Distribution ZIP 校验

v4.3.0 不建议完全解压并深度校验每个嵌套 ZIP 的全部内容，因为已有 `verify-distribution-package` 能做这件事。

但必须至少：

- hash 对账。
- 可选深度校验。

建议参数：

```text
--deep
```

`--deep` 时：

- 从 submission ZIP 读取嵌套 distribution-package.zip 到临时目录。
- 调用 `verify_distribution_package()`。
- 汇总每个 target 的 verifier report。

release-check 必须覆盖 `--deep`。

- 错误返回 `error: ...`。
- 状态冲突返回 409。
- 输入校验失败返回 400。
- 不存在返回 404。
- 导出 ZIP 下载必须使用安全 Content-Disposition。
- 不允许 GET 执行有副作用操作。

## 18. 安全与脱敏

v4.3.0 要继承前面所有安全纪律。

### 18.1 敏感值

必须脱敏：

- api_key
- token
- authorization
- password
- secret
- Bearer token
- GitHub token
- sk-*
- Windows drive path
- UNC path
- macOS /Users path
- Linux /home path

### 18.2 外部 URL

允许 http/https。

但：

- 不允许 `file://`
- 不允许本机路径伪装
- 不允许换行
- 不允许控制字符
- 不允许超长 URL

### 18.3 ZIP 安全

同 v3.8 / v4.0 / v4.2：

- raw central directory entry name 检查。
- 反斜杠失败。
- `..` 失败。
- 绝对路径失败。
- duplicate entry 失败。
- zip bomb 防护。

### 18.4 不信任缓存

Submission export 不得信任 `submission.json` 里的旧 target hash。

导出时必须重新读取：

- target JSON
- target latest package summary
- target ZIP 文件
- distribution manifest
- verifier report

## 19. Stale Guard

这些情况必须让 submission QA/export 变 stale 或 failed：

- Release track 变化。
- Release metadata 变化。
- Release signoff reset。
- Distribution target QA 变化。
- Distribution target export/zip 变化。
- Distribution target signoff reset。
- Template Pack 更新导致 target summary stale。
- Layout hash 变化。
- Target ZIP hash 变化。
- Submission item 绑定的 package_id 不再是 latest。

签核后如果发现 stale：

- 不允许静默刷新 signed export。
- `verify` 应该返回 warning/failed。
- UI 提示 reset signoff 后重新打包。

## 28. 高风险点

### 28.1 嵌套 ZIP 校验

Submission ZIP 内包含 Distribution ZIP。

风险：

- 只校验文件存在，不校验 hash。
- deep verify 临时文件清理不完整。
- nested ZIP bomb。

要求：

- 默认至少 hash 对账。
- `--deep` 时调用 distribution verifier。
- 临时目录使用 `TemporaryDirectory`。

### 28.2 签核后状态记录

如果签核后允许 record submitted，容易误改 signed manifest。

要求：

- signed export/zip 不变。
- 状态记录写 `submission.json` / events。
- 如果用户需要重新导出含最新状态的包，必须 reset signoff。

### 28.3 target stale

Distribution target reset signoff 后，submission item 不能继续显示 ready。

要求：

- refresh / QA / export 都必须重读 target。
- stale 必须 blocking。

### 28.4 外部回执污染

用户可能粘贴：

```text
C:\Users\...
sk-...
Bearer ...
=HYPERLINK(...)
```

要求：

- JSON 输出脱敏。
- CSV formula guard。
- verifier raw scan。

## 33. 结论

v4.3.0 应该迈大一步，从“单个 Distribution Package 的可信布局”推进到“多个 Distribution Package 的提交批次管理”。

这一步完成后，MusicForge 的发行链路会变成：

```text
Project Final Export
  -> Release Workspace
  -> Release Metadata
  -> Distribution Target
  -> Distribution Package
  -> Submission Batch
  -> Submission Package
  -> External Platform Manual Submission
```

这仍然坚持本项目一直以来的原则：

- 先本地化验证。
- 先可审计。
- 先可恢复。
- 先不碰不可控的外部平台 API。

v4.3.0 完成后，MusicForge 才真正具备“从创作到发行提交前归档”的完整本地闭环。

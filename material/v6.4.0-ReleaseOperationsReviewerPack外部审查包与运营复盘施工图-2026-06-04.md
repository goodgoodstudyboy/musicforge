# v6.4.0 Release Operations Reviewer Pack 外部审查包与运营复盘施工图

日期：2026-06-04  
基线版本：v6.3.1  
目标版本：v6.4.0  
角色定位：Reviewer / Planner / Release Governance Product Architect  
项目：MusicForge / song-agent

---

## 1. 背景

v6.3.1 已经把 Release Operations 的核心证据链串成了 hash-chained Audit Ledger，并修掉了两个关键问题：

- `require_archive` 必须同时有 Operations Archive Export 和 Operations Archive Verification。
- reset 后 re-sign 的历史 reset 也必须绑定 applied Change Request，不能只校验当前 `operations-signoff.json`。

这意味着单个 Release 的机器证据链已经基本站住：

- Dashboard 说明状态。
- Runbook 说明怎么安全执行。
- Signoff / Archive 说明怎么归档。
- Change Request 说明签核后如何重置。
- Audit Ledger 说明证据顺序和因果。
- Audit Package 可以离线验证。

但是现在的证据仍然偏“机器可验证”，不是“人容易审查”。

真实业务里会有几类人：

- 项目负责人：想知道这首歌为什么可以交付。
- 开发负责人：想知道哪些步骤最容易卡住，下一版要优化什么。
- 外部 reviewer：不想看 `.musicforge` 内部结构，只想拿一个只读包判断是否可信。
- 业务人员：想看一份简明结论，不想翻 800 行 JSONL。
- 未来开发：想从历史 Release 学到流程问题。

v6.3 Audit ZIP 能验证，但还不能很好回答：

- 这次 Release 从 draft 到 archived 的关键路径是什么？
- 哪些阶段耗时最长？
- 哪些 blocker / warning 被 force 或 override？
- 哪些 Change Request 改过证据链？
- 哪些 verifier 是 passed，哪些只是 warning / missing？
- 哪些人工动作是必须的？
- 外部 reviewer 应该重点看哪些文件？
- 这次 Release 有什么复盘结论？
- 和上一个 Release 相比，风险有没有下降？

所以 v6.4.0 应该做：

> Release Operations Reviewer Pack / Retrospective：基于 v6.3 Audit Ledger 生成一份只读、脱敏、可离线验证、适合人审查的审查包和运营复盘报告。

---

## 2. v6.4.0 总目标

一句话目标：

> 把 v6.3.1 的机器审计账本转成外部 reviewer 能直接阅读和验证的 Release Reviewer Pack，同时生成内部可复盘的 Operations Retrospective，帮助团队理解交付质量、流程瓶颈和风险趋势。

完成后用户应该能：

- 在 Studio 的 Release Operations 页面生成 Reviewer Pack。
- 下载 `operations-reviewer-pack.zip`。
- 在外部干净目录验证：

```powershell
python -m song_agent.cli verify-release-operations-reviewer-pack path\to\operations-reviewer-pack.zip --json --strict --require-audit --require-signed --require-archive
```

- 打开包内 `REVIEWER_GUIDE.md`，不用懂 MusicForge 内部结构也能看懂：
  - Release 是什么。
  - 当前状态是什么。
  - 为什么可以 archived。
  - 哪些证据支持。
  - 哪些 warning / override 存在。
  - 哪些 Change Request 发生过。
  - 如何验证包。
- 查看 `RETROSPECTIVE.md`：
  - 阶段耗时。
  - 风险热点。
  - 人工动作清单。
  - verifier 结果。
  - 改进建议。
- Reviewer Pack 自身被篡改、加危险 entry、复制本机路径、污染 token、伪造 manifest 时，离线 verifier 必须 failed。

---

## 3. 非目标

v6.4.0 不做：

- 不接真实 DSP API。
- 不做云端审查门户。
- 不做在线多人评论系统。
- 不自动签核、reset、approve Change Request。
- 不改变 Release / Distribution / Submission 的业务状态。
- 不复制音频大文件、artwork 大文件、提交 ZIP、分发 ZIP。
- 不替代 v6.3 Audit Package；Reviewer Pack 是面向人的只读摘要包，Audit Package 仍是机器底层证据。
- 不做跨 Release Portfolio Audit。跨 Release 可以在 v6.5 之后做。

## 6. 数据来源

Reviewer Pack 只读读取：

- Release document。
- Release events。
- Operations Report。
- Operations Audit Report。
- Operations Audit Ledger。
- Operations Audit Package verification report。
- Operations Signoff summary。
- Operations Archive verification report。
- Latest Runbook summary。
- Change Request ledger。
- Package verifier ledger。

不要重新计算业务状态，不要修改下游 evidence。

如果 Audit Ledger 不存在，Reviewer Pack 可以生成 `failed` report，但不能生成 `passed` pack。

如果 Audit Ledger stale / failed，Reviewer Pack 必须 failed。

---

## 7. Reviewer Report 规则

### 7.1 必须 passed 的条件

Reviewer Report `status=passed` 需要：

- Audit Report 存在。
- Audit Report integrity OK。
- Audit Report `status` 不是 `failed`。
- Audit Ledger hash chain OK。
- Operations Signoff summary 是 `signed` 或 `force_signed`。
- Operations Archive verified。
- Change Request reset causality passed。
- redaction scan passed。

### 7.2 Blockers

以下是 blocker：

- Audit Report missing。
- Audit Report integrity failed。
- Audit Ledger chain failed。
- Operations Signoff missing。
- Operations Archive verification missing / failed。
- Change Request reset causality failed。
- Reviewer Report redaction failed。
- Reviewer Pack export manifest integrity failed。

### 7.3 Warnings

以下是 warning：

- Operations Signoff 是 `force_signed`。
- Audit Report status 是 `warning`。
- Verifier summary 有 warning。
- 有 applied Change Request。
- 有 override reason。
- 有 manual_required action 未纳入自动流程。
- 有旧版本 compatibility warning。

warning 不阻止生成包，但必须在 `REVIEWER_GUIDE.md` 和 `risk-summary.json` 中清楚列出。

---

## 8. Retrospective 规则

Retrospective 面向内部开发和业务复盘，不作为准出 gate。

### 8.1 Timeline

从 Audit Ledger 提取：

- release created。
- operations report refresh。
- runbook created。
- runbook safe actions completed。
- operations signoff。
- archive export。
- archive verify。
- change request created / approved / applied。
- audit refresh。
- reviewer pack export。

### 8.2 Stage durations

根据 `occurred_at` 计算阶段耗时：

- release_to_operations_report。
- operations_report_to_runbook。
- runbook_to_signoff。
- signoff_to_archive。
- archive_to_audit。
- total_release_operations_duration。

如果时间缺失：

- 不猜测。
- 输出 `duration_status=unknown`。
- 加 warning。

### 8.3 Risk hotspots

按事件和 warning 聚合：

- force signoff。
- applied Change Request。
- verifier warning。
- missing optional evidence。
- manual_required items。
- stale refresh。
- package rebuild after signoff blocked。

### 8.4 Recommendations

只给本地 deterministic 建议，不调用 provider：

- 如果 manual_required 多：建议补 Runbook safe action 或流程说明。
- 如果 verifier warning 多：建议下一版收紧 verifier 或修证据源。
- 如果 Change Request 多：建议检查签核前检查项是否不足。
- 如果 durations unknown：建议补事件 timestamp。
- 如果 Operations Archive verify 在 Audit 前才补：建议把 verify 加入 Runbook safe action。

### 9.1 REVIEWER_GUIDE.md

必须包含：

- Release 基本信息。

- Risk hotspots。

## 12. Verifier 设计

新增：

```text
song_agent/release_operations_reviewer_pack_verifier.py
```

必须校验：

- ZIP open。
- ZIP size limit。
- total uncompressed size limit。
- entry count limit。
- raw central directory entry path。
- unsafe path。
- duplicate entry。
- required entries。
- manifest integrity hash。
- manifest.files shape。
- manifest.files hash 对账。
- strict extra entry failed。
- `manifest.zip.entries` 不能扩权。
- reviewer-report integrity hash。
- retrospective-report integrity hash。
- audit summary hash / ledger hash 引用。
- REVIEWER_GUIDE.md 和 RETROSPECTIVE.md redaction scan。
- JSON blocked key scan。
- require_audit：Audit status 必须不是 failed，ledger hash 必须存在。
- require_signed：Operations Signoff 必须 signed / force_signed。
- require_archive：Operations Archive verified 必须 true。

篡改场景必须 failed：

- 改 `reviewer-report.json` summary。
- 改 `retrospective-report.json` recommendation。
- 删除 `REVIEWER_GUIDE.md`。
- 加 `../evil.txt`。
- raw entry 写 `extra\file.txt`。
- duplicate `README.txt`。
- 往 manifest.zip.entries 加 extra 并写入 extra 文件。
- README 注入 `sk-secret-value` 或 `C:\Users\...`。

## 14. Export 接入

### 14.1 Operations Report

Operations Report 可以加入只读 summary：

```json
"reviewer_pack": {
  "status": "passed",
  "source_hash": "...",
  "integrity_hash": "...",
  "zip_sha256": "..."
}
```

注意避免 source hash 循环：

- Reviewer Pack 可以引用 Operations Report / Audit Report。
- Operations Report 只能引用 Reviewer Pack summary。
- Reviewer Pack source hash 不能纳入 Operations Report 中的 reviewer_pack summary。

### 14.2 Operations Archive

不要把 Reviewer Pack ZIP 塞进 Operations Archive，避免循环。

可以在 Archive manifest 中只写 reviewer summary。

## 15. 安全边界

必须满足：

- Reviewer Pack 是只读摘要包。
- 不复制音频、artwork、分发 ZIP、提交 ZIP、evidence ZIP。
- 不复制 raw provider response。
- 不复制本机路径。
- 不复制 token。
- 不复制平台账号信息。
- 不暴露 `.musicforge` 真实绝对路径。
- 不允许 source_path / local_path / file_path 进入导出 JSON。
- Markdown 文本也要 redaction scan。
- Verifier 扫 JSON / JSONL / TXT / MD / CSV。

## 20. Reviewer 验收重点

Reviewer 要重点看：

- Reviewer Pack 是否只读，不改变业务状态。

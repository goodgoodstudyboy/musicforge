# v12.6.0 Unified Release Program Continuity Distribution Kit 项目级连续性交付套件与外部灾备验收包施工图

> 建议下一版：v12.6.0  
> 预期稳定基线：v12.5.0 发布完成后  
> 当前注意事项：当前工作区仍有 v12.5 改动未提交；本文按 v12.5.0 已提交、已通过干净 GA、已发布为稳定基线后的下一版设计。  
> 核心目标：把 v12.5 的 Continuity / Recovery Drill 从“本地可证明恢复”升级成“可交给外部审计、法务、长期存储方的一包式连续性交付套件”。v12.6 要把 Continuity Archive、Vault Operations Archive、source Vault 证据、外部 verification reports、signoff bindings、restore guide、handoff receipt 和离线 verifier 组织成固定结构 Distribution Kit，并确保它在离开原工作区后仍可深度复验。

---

## 1. 背景

v12.0 到 v12.5 已经完成 Program 级证据链的关键阶段：

- v12.0 Program Board：多个 Release Train Handoff 聚合成 Program 准出。
- v12.1 Program Operations：Program CR、safe runbook、continuous review、lifecycle audit。
- v12.2 Program Handoff：外部 review、accepted evidence、decision board、handoff signoff。
- v12.3 Evidence Vault：把 Program / Operations / Handoff / accepted evidence 封存为可 deep verify 的 Vault。
- v12.4 Vault Operations：Vault Registry、custody policy、runtime custody review、transfer pack、长期托管 signoff。
- v12.5 Continuity / Recovery Drill：证明 Vault Operations Archive 能在隔离目录恢复、重放和复验。

v12.5 能回答：

> “我能不能在隔离环境里，从当前 Vault Operations 证据恢复并复验 Program 证据链？”

但真实外部交接还缺一层：

1. 审计方不一定有原工作区路径。
2. 法务/长期存储方需要一包式交付材料，而不是一串 CLI 参数。
3. v12.5 Continuity Archive 本身不嵌套 source ZIP，这是正确的；但外部交付需要一个安全 allow-list 下的 bundle。
4. 接收方需要知道哪些 ZIP 是核心、哪些 report 是证明、哪些 binding 是外部锚点。
5. 如果交付包里混入额外文件、旧 report、错 package_type、伪造 anchor，必须被 verifier 抓住。
6. 如果交付包内所有 JSON 被整体重签，但底层 source package 不匹配，也必须失败。
7. 需要一个 receiver receipt / handoff receipt，但不能让 receiver response 反过来改写已签核证据。

所以 v12.6 建议进入：

**Unified Release Program Continuity Distribution Kit**

中文名：

**项目级连续性交付套件与外部灾备验收包**

---

## 2. 版本定位

### 2.1 一句话

v12.6 是 Program 级连续性证据的外部分发层：它把 v12.5 Continuity Archive 与它依赖的 v12.4 Vault Operations Archive、v12.3 Vault ZIP / anchor、所有 verification reports 和 signoff bindings 组成固定结构 Distribution Kit，并提供离线 verifier、接收方 guide、handoff receipt 和 Release / GA gate。

### 2.2 和 v12.5 的关系

v12.5：

- 运行本地 recovery drill。
- 生成 Continuity Archive。
- 证明恢复演练 passed。
- 签核 continuity evidence。

v12.6：

- 不改变 v12.5 archive。
- 不重新计算 v12.5 drill。
- 将 v12.5 archive 与外部依赖证据打成 Distribution Kit。
- 提供 kit-level verifier。
- 支持外部 receiver receipt。
- 支持 Release / GA gate 要求 Distribution Kit passed。

### 2.3 本版必须解决的问题

1. 新增 Continuity Distribution Kit Store。
2. Kit 输入必须来自当前已签核 v12.5 Continuity Archive。
3. Kit 必须收集并绑定：
   - Continuity Archive ZIP。
   - Continuity verification report。
   - Continuity signoff binding。
   - Vault Operations Archive ZIP。
   - Vault Operations verification report。
   - Vault Operations signoff binding。
   - Evidence Vault ZIP。
   - Vault verification report。
   - Vault anchor。
4. Kit 必须生成：
   - package manifest。
   - package index。
   - verification index。
   - source binding summary。
   - receiver guide。
   - restore command guide。
   - custody checklist。
   - optional receiver receipt template。
5. Kit verifier 必须支持：
   - fixed allow-list。
   - nested ZIP allow-list。
   - 每个 nested ZIP runtime verification。
   - external report / binding / anchor 交叉校验。
   - full-resign 防护。
   - trailing bytes。
   - raw backslash entry。
   - `.MusicForge/` 大小写变体。
   - redaction。
6. Receiver receipt 必须是后验文件：
   - 可以记录接收方已收到。
   - 不能参与修改 signed continuity / vault operations。
   - 不能让 failed kit 变 passed。
7. Release signoff / GA readiness 可要求：
   - `require_unified_release_program_continuity_distribution_kit=true`
   - Kit ZIP passed。
   - Kit verification report passed。
   - 可选 receiver receipt accepted。
8. release-check 新增 v12.6 smoke。

### 2.4 本版不做什么

v12.6 不做：

- 不做真实云上传。
- 不做远程 registry。
- 不做第三方 CA / PKI。
- 不做时间戳服务。
- 不做跨 Program portfolio。
- 不修改 v12.3 / v12.4 / v12.5 包格式。
- 不自动 approve CR。
- 不自动 reset Program / Vault Operations / Continuity。
- 不自动导入 reviewer decision。
- 不把 receiver receipt 当成准出核心证据。

如果要做远程发布 / 外部透明度登记 / 多接收方 quorum，应放到 v12.7+。

## 3. 核心原则

### 3.1 Kit 是分发层，不是签核层

Kit 不能重新签核 Program。

Kit 只能证明：

- 当前 signed Continuity Archive 存在。
- 它依赖的 source Vault Operations / Vault 证据完整。
- 所有外部 reports / bindings / anchors 与 source package 匹配。
- 接收方拿到一包后能离线复验。

### 3.2 Fixed allow-list 是硬边界

Distribution Kit 是少数允许嵌套 ZIP 的包。正因为它允许嵌套 ZIP，所以必须固定 allow-list。

禁止：

- 任意 `manifest.files[]` 扩展。
- 任意 `package-index.json` 扩展。
- 任意 `nested/*.zip` 扩展。
- 任意 `docs/*.txt` 扩展。

新增文件必须改 verifier allow-list 和测试。

### 3.3 Nested ZIP 必须逐个 runtime verify

Kit verifier 不能只比对 SHA。

每个 nested package 必须调用自己的 verifier：

- Continuity Archive -> `verify_unified_release_program_continuity_package`
- Vault Operations Archive -> `verify_unified_release_program_vault_operations_package`
- Evidence Vault ZIP -> `verify_unified_release_program_vault_package`

并交叉比对：

- zip sha。
- zip size。
- manifest hash。
- verification report hash。
- package_type。
- signoff binding / anchor hash。

### 3.4 Receiver receipt 是后验，不是核心信任锚

Receiver receipt 只能证明：

- 某人 / 某组织声称收到 kit。
- 收到的 kit hash 是什么。
- 验证结果是什么。
- 是否接受或提出问题。

它不能：

- 修改 kit source hash。
- 修改 continuity signoff。
- 让 failed kit 变 passed。
- 替代 verifier。

### 3.5 不允许包内自证

Verifier 不能只信：

- kit manifest。
- kit package-index。
- kit verification-index。
- continuity report summary。
- vault operations registry summary。
- receiver receipt。

必须从 nested ZIP + external sidecar 反推 source binding。

## 7. Verifier 必查项

### 7.1 Kit ZIP 基础安全

必须检查：

- ZIP exists。
- ZIP readable。
- no duplicate entry。
- no trailing data。
- raw central directory no backslash。
- path safe。
- no absolute path。
- no `..`。
- no `.musicforge/` 或大小写变体。
- fixed allow-list exact match。
- manifest.files exact match。
- package-index exact match。
- verification-index exact match。
- file hash match。
- uncompressed size limit。

### 7.2 Nested ZIP allow-list

唯一允许的 nested ZIP：

```text
packages/continuity-archive.zip
packages/vault-operations-archive.zip
packages/evidence-vault.zip
```

任何其他 `.zip` 必须 failed。

### 7.3 Nested runtime verification

当 `--deep` 时：

1. 先做 Kit ZIP preflight。
2. 若 Kit preflight 有 blocking failure，不得解压 nested ZIP。
3. 对 `continuity-archive.zip` 调用 v12.5 verifier：
   - strict。
   - deep_restore。
   - require_signed。
   - require_current_vault_operations。
   - 使用 Kit 内 bindings 和 verification reports。
4. 对 `vault-operations-archive.zip` 调用 v12.4 verifier：
   - strict。
   - deep。
   - require_signed。
   - require_current_vault。
5. 对 `evidence-vault.zip` 调用 v12.3 verifier：
   - strict。
   - deep。
   - require_anchor。
6. 对每个 runtime report 与 Kit index 交叉校验。

### 7.4 Full-resign 防护

必须挡住：

1. 修改 package-index，把 continuity archive hash 指向伪造 ZIP。
2. 重算 package-index / manifest / source-binding。
3. 不替换 nested ZIP。
4. verifier 必须 failed。

也必须挡住：

1. 修改 nested continuity archive 的 signoff。
2. 重算 nested continuity archive manifest。
3. 重算 Kit manifest / package-index。
4. 但不具备匹配外部 continuity signoff binding。
5. verifier 必须 failed。

### 7.5 Receiver receipt 校验

当 `--require-receiver-receipt`：

- receipt 必须存在。
- package_type 正确。
- integrity OK。
- kit_sha256 匹配当前 Kit ZIP。
- kit_manifest_hash 匹配当前 Kit manifest。
- verification_report_hash 匹配当前 Kit verification report。
- decision 必须 `accepted`。
- receipt 不能包含 source_path/local_path/file_path。
- receipt 不能让 failed Kit 变 passed。

## 19. 给开发的话

v12.6 的核心不是“把几个 ZIP 塞进一个 ZIP”这么简单。它是第一个允许 nested ZIP 的 Program 级外部分发包，所以 verifier 必须比前几版更严格：

1. 先写 verifier，再写 Store。
2. nested ZIP 只允许三份，路径固定，名字固定。
3. 每个 nested ZIP 必须 runtime verify，不能只比 hash。
4. package-index / verification-index 只能作为索引，不能作为可信事实。
5. receiver receipt 是后验记录，不是信任锚，不能让 failed Kit 变 passed。
6. release-check smoke 必须把 forged package-index、extra nested ZIP、nested continuity tamper、receipt wrong hash 都打进去。

这版做稳后，v12 系列会从“本地可恢复”推进到“外部可交付、可验收、可长期存储”。这是 Program 级证据链真正离开开发机的关键一步。

# v10.11.0 Release Audio Baseline Governance 音频基线治理与回归响应闭环施工图

## 1. 给开发的交接说明

当前待发布基线是 v10.10.0。v10.10.0 已经新增 Release Audio Regression Guard，可以把当前 Release 的 Certification / Timeline 和一个外部基线做 deterministic 对比，并在 Release signoff / GA readiness 上挡住音频质量倒退。

v10.11.0 不要再只做一个新的证明 ZIP。它要补上 v10.10 之后真正缺的业务闭环：

1. 基线不能靠开发临时手选。必须有可审计的 Baseline Registry，明确哪一个 Release Audio Certification / Timeline 被批准为黄金基线。
2. 回归失败不能只显示 failed。必须生成 Regression Response Plan，把每个退化点映射成可执行动作、人工修复入口、复验要求和关闭条件。
3. Release / GA 准出不能只看当前 regression passed。必须确认基线是 approved/current，回归响应已经 closed，且所有证据仍然绑定当前 Release audio evidence。

开发请先完成 v10.10.0 的提交、推送、tag 和 Release。v10.10 发布干净后，再按本文开工 v10.11.0。不要在 v10.10 未提交状态下继续叠 v10.11。

## 2. 开工前基线确认

开工前必须确认：

```powershell
git status --short --branch
git rev-parse HEAD
git show-ref --tags -d v10.10.0
python -m song_agent.cli doctor
python -m song_agent.cli release-check --profile v10 --skip-tests --json
python -m song_agent.cli release-check --profile ga --skip-tests --json
python -m song_agent.cli release-check --profile latest --skip-tests --json
```

预期：

- 工作区干净。
- HEAD / origin/master / v10.10.0^{} 指向同一个 commit。
- `song_agent.__version__` 和 `pyproject.toml` 是 `10.10.0`。
- v10 / ga / latest release-check 通过。

如果 `ga` 仍因为 `git.status` failed，说明 v10.10 还没提交或没推送，不要开工。

## 3. 为什么 v10.11 做 Baseline Governance + Regression Response

v10.10 解决的是“能否发现音频回归”。但生产上还会出现三类问题：

1. **基线选择不受控**
   - 开发可能选错 baseline release。
   - baseline 可能来自未签核或过期的 Certification / Timeline。
   - baseline 和当前 Release track set 不兼容。
   - baseline 被替换后，旧 regression report 仍被沿用。

2. **回归失败后没有闭环**
   - report 知道 rating_drop / new_high_issue / health_degrade，但没有生成修复计划。
   - 修复动作可能散落到 Audio Fix Sprint、Campaign Remediation、人工复听，没有统一 closeout。
   - 回归问题被标记 waived 后，Release 仍可能误签。

3. **GA 准出证据仍缺少治理层**
   - GA 需要证明：当前使用的 baseline 是 approved/current。
   - GA 需要证明：曾经 failed/warning 的 regression 已经被处理或明确阻断。
   - GA 需要证明：response closeout 之后，Certification / Timeline / Regression 没有再次变化。

v10.11 要把 v10.10 的 guard 变成可运营的质量治理系统。

## 4. v10.11 总目标

新增两个核心能力：

1. **Release Audio Baseline Governance**
   - 从已签核 Release Audio Certification + Timeline 创建 baseline candidate。
   - 支持 approve / activate / supersede / revoke。
   - 支持 baseline scope 和 track-set compatibility 校验。
   - 已 approved / active baseline 不允许静默改写。
   - 导出 Baseline Registry ZIP，并支持离线 verifier。

2. **Release Audio Regression Response**
   - 从 v10.10 Regression Report 自动生成 Response Plan。
   - 将 regression blockers / warnings 映射成 action items。
   - 支持 safe actions 创建 Audio Fix Sprint / Release Audio Campaign Remediation 草稿。
   - 支持人工 waive 低风险 warning，但 high / critical regression 不能被普通 waive 放行。
   - closeout 必须绑定新的 current Certification / Timeline / Regression 证据。
   - 导出 Regression Response ZIP，并支持离线 verifier。

最终接入：

- Release signoff gate：
  - `require_release_audio_baseline_governance=true`
  - `require_release_audio_regression_response=true`
- GA readiness：
  - `ga.release_audio_baseline_governance`
  - `ga.release_audio_regression_response`
- `verify-ga-readiness-report` 外部证据门禁。
- Studio Release 页面新增 Baseline Governance / Regression Response 控件。
- release-check 新增 `v1011.release_audio_baseline_response_smoke`。

## 5. 明确不做什么

v10.11 不做：

- 不自动修改音乐。
- 不自动 apply mix / edit / mastering。
- 不自动签核 Release。
- 不自动把 failed regression 降级为 warning。
- 不允许 provider / LLM 决定是否通过音频回归。
- 不把 synthetic / fake WAV 当 release-ready 证据。
- 不从包内自证推断 baseline/current 是否可信。
- 不做跨 portfolio 的长期质量策略，那是后续 v10.12+。

v10.11 可以创建草稿和 action queue，但所有会改变音乐、改变签核、改变最终交付的动作必须保持 manual_required 或走已有人工链路。

- `revoked`: 不可再用于 signoff / GA。

## 9. Baseline scope 规则

Baseline 必须有 scope。v10.11 至少支持：

1. `release_line`
   - 用于同一 album / EP / batch 的后续 RC 对比。
2. `project`
   - 用于单项目多版本对比。
3. `track_set`
   - 用于固定 track set 的严格对比。

兼容性规则：

- 当前 Release 的 `track_identity_set_hash` 必须和 baseline 一致，除非 explicit compatibility mode 是 `allow_added_tracks`。
- 默认不允许少 track。
- 默认不允许 project_id/version_id 混淆。
- `final_export_hash` 变化时，必须重新生成 current Certification / Timeline / Regression。
- baseline 的 Certification / Timeline verification report 必须 current/passed/signed。

如果不兼容，Baseline Governance gate 必须 failed。

## 12. Baseline Registry verifier

新增 `verify_release_audio_baseline_registry_package()`。

必须校验：

- ZIP exists / readable。
- fixed allow-list。
- duplicate entry failed。
- path traversal / backslash / drive path / `.musicforge` case variants failed。
- `manifest.package_type == "release_audio_baseline_registry"`。
- `manifest.files[]` 必须等于固定结构。
- registry integrity hash。
- each baseline integrity hash。
- approved/active baseline approval history hash-chain。
- active baseline 不能 revoked / superseded。
- baseline evidence 必须绑定外部 Certification / Timeline verification fingerprints。
- redaction scan。

注意：Baseline Registry ZIP 本身不能证明 Certification / Timeline 当前有效。需要在 gate 或 verify 命令中传外部证据路径，或者从本地 Release store 重新读取当前 verification report。

## 14. Regression Response action mapping

Regression kinds:

- `new_critical_issue`
- `new_high_issue`
- `manual_rating_drop`
- `accepted_to_needs_fix`
- `audio_health_degrade`
- `remediation_count_increase`
- `marker_recurrence`
- `track_missing_from_current`
- `baseline_incompatible`

Action mapping:

| regression kind | default action | safe auto? |
|---|---|---|
| new_critical_issue | manual_required + create remediation draft | no |
| new_high_issue | create Audio Fix Sprint draft | yes, draft only |
| manual_rating_drop | create Audio Lab review session draft | yes, draft only |
| accepted_to_needs_fix | create Release Audio Campaign Remediation draft | yes, draft only |
| audio_health_degrade | create Audio Fix Sprint draft | yes, draft only |
| remediation_count_increase | manual review | no |
| marker_recurrence | create Regression recurrence note | yes |
| track_missing_from_current | block | no |
| baseline_incompatible | block | no |

Safe action 的定义：

- 可以创建草稿。
- 可以刷新 report / export / zip / verify。
- 不能 apply 音乐修改。
- 不能关闭 sprint。
- 不能签核 Release。
- 不能把 failed 降级成 passed。

```text
POST /api/releases/<release-id>/audio-regression-response/verify
GET  /api/releases/<release-id>/audio-regression-response/download
```

Waiver 规则：

- `critical` 不允许 waive。
- `high` 默认不允许 waive；如果后续业务明确要允许，必须另做 approved Change Request。
- `warning` 可 waive，但必须写 reason、reviewer、role。
- waiver 内容必须 `sanitize_sensitive_text()`。
- waiver 会进入 history hash-chain。

Closeout 规则：

- response source 不能 stale。
- regression source 不能 stale。
- baseline 必须仍 approved/active 且未 revoked。
- 所有 action item 必须 completed 或 allowed waiver。
- 如果原 regression 是 failed，closeout 必须绑定一个新的 current Regression Guard，且 status 必须 passed。
- closeout 后 export/zip 不允许静默重建；如果 source 变化，必须 failed。

## 18. Release signoff gate

Release signoff payload 新增：

```json
{
  "require_release_audio_baseline_governance": true,
  "require_release_audio_regression_response": true
}
```

Gate 行为：

1. `require_release_audio_baseline_governance=true`
   - 当前 Release 必须选择 approved/active baseline。
   - baseline 必须 compatible。
   - baseline source evidence 必须 current。
   - revoked/superseded baseline 失败。
   - force=true 不能绕过。

2. `require_release_audio_regression_response=true`
   - 如果 Regression Guard status 是 passed 且没有 blocker，可允许 response not_required。
   - 如果 Regression Guard status 是 warning/failed，必须有 closed response。
   - closed response 必须绑定当前 Regression Guard。
   - failed regression 不允许靠 waiver 直接通过。
   - force=true 不能绕过 stale/invalid source。

## 21. release-check

新增：

```text
v1011.release_audio_baseline_response_smoke
```

加入 profiles：

- `v10`
- `latest`
- `ga`
- `full`
- `quick` 可选，如果耗时可不加。

Smoke 必须覆盖：

1. 从已签核 baseline release 创建 baseline candidate。
2. approve + activate baseline。
3. 当前 Release 使用 active baseline 生成 Regression Guard。
4. Regression passed 时 response not_required，Release/GA gate passed。
5. 人为制造 current quality degrade，Regression failed。
6. 创建 response plan，生成 action items。
7. high/critical waiver 被拒绝。
8. safe action 只创建 draft，不 apply。
9. recheck 后 Regression passed，response closeout passed。
10. Release signoff + GA readiness passed。
11. baseline revoked 后 gate failed。
12. baseline registry ZIP full resign failed。
13. response ZIP full resign failed。
14. response closeout 后篡改 action-items/export 409。
15. declared extra ZIP entry failed。
16. redaction failed。

Smoke detail 示例：

```text
baseline=active, regression=failed->passed, response=closed, high_waive=409, safe_actions=draft_only, signoff=passed, ga=passed, revoked=failed, baseline_full_resign=failed, response_full_resign=failed, signed_tamper=409
```

## 24. 关键风险和必须防住的回归

### P1：Baseline Registry 自证

风险：攻击者篡改 baseline source，然后重算 registry integrity。

必须防：

- verifier / gate 必须反查外部 Certification / Timeline verification fingerprints。
- active baseline 必须有 approval history chain。
- revoked baseline 不能通过 gate。

### P1：Response Plan 删除 high issue 后重签

风险：从 action-items 删除 high issue，然后重算 plan/report hash。

必须防：

- verifier 必须从外部 Regression ZIP 重新推导 expected action items。
- action item count、severity、issue ids、track ids 必须匹配。

### P1：旧 Response closeout 复用

风险：current Certification / Timeline 更新后，旧 response closeout 仍被 Release signoff 使用。

必须防：

- closeout source hash 必须包含 current Certification / Timeline / Regression verification fingerprints。
- Release gate 每次重新读取当前证据。

### P1：Baseline scope 错配

风险：用另一个 Release 的 baseline 放行当前 Release。

必须防：

- track_identity_set_hash 必须匹配。
- project_id + version_id + final_export_hash 必须逐 track 校验。
- 不兼容只能 failed，force=true 不能绕过。

### P1：Signed export 静默改写

风险：signed baseline / response 被篡改后，export/zip 重建出新包。

必须防：

- export/zip 前校验 signoff/approval 绑定的每个 sidecar hash。
- 删除 signoff 文件也不能绕过，必须读取 history hash-chain。

## 25. 验收标准

v10.11.0 完成必须满足：

- 新模块、API、CLI、Studio 控件都存在。
- Baseline Governance 可以从 signed Certification / Timeline 创建 approved active baseline。
- Regression Response 可以从 failed Regression Guard 创建 action plan。
- high/critical regression 不能被普通 waiver 放行。
- Response closeout 必须绑定新 passed regression。
- Release signoff gate 接入并 hard block stale/invalid evidence。
- GA readiness 和 verifier 接入外部 evidence。
- ZIP verifier 固定 allow-list，能挡 full-resign、declared extra、duplicate、path/backslash、redaction。
- release-check v10/latest/ga 通过。
- 工作区干净。
- README / CHANGELOG / version 完整。

## 26. 给开发的话

这版的重点不是多做几个按钮，而是把 v10.10 的“发现回归”变成真正可运营的“基线批准、回归响应、复验关闭、准出绑定”。

实现时请记住三条硬规则：

1. **所有 gate 都要反查外部证据**，不能只信当前 ZIP 里的 report/source/integrity 自证。
2. **所有 signed / approved / closed 状态都要有 history hash-chain**，删除当前 JSON 文件不能绕过不可变状态。
3. **safe action 只能创建草稿和报告**，不能自动改音乐、不能自动签核、不能自动把 failed 改成 passed。

每完成一个 Phase 就提交并推 GitHub。不要攒一个巨大提交。每次提交前至少跑该 Phase 的定向测试；最终发布前跑 v10 / latest / ga release-check。

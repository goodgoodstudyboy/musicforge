日期：2026-05-05

## 0. 当前状态

v0.2.0 已完成并发布，当前稳定基线是：

- 本地 Studio 面板。
- local / provider 两种生成模式。
- ProviderConfig 与 `.musicforge/provider.json`。
- Mock provider。
- OpenAI-compatible `/chat/completions` client。
- provider-backed `SongPlan` pipeline。
- masked provider snapshot。
- `doctor` CLI。
- 测试基线：`90 passed`。

当前工作区已经出现一个合理的 v0.2.1 前置修复：

- `song_agent/providers/openai_compatible.py`
- `tests/test_provider_client.py`

内容是 provider error 脱敏，防止 HTTP error body 或 OSError 文本里回显 key/token。这个修复应该先单独验收、提交、推送，作为 v0.2.1 的第一个小包。

## 1. 下一步应该做什么

建议下一步做 `v0.2.1`，主题是：

```text
Job control + retry + watchdog + provider error hardening
```

原因：

- v0.2.0 已经能调用 provider，外部模型调用会带来网络失败、超时、模型输出错误、任务卡住等问题。
- 如果现在直接进入多 agent，失败点会成倍增加，当前 job runner 还不够稳。
- 先把单 job 的取消、重试、超时、heartbeat、watchdog、错误脱敏做好，后面的多 agent 和 batch 才不会返工。

## 2. v0.2.1 完成定义

v0.2.1 完成后必须满足：

- provider error 文本统一脱敏。
- queued job 可以 cancel，且不会执行。
- running job 可以请求 cancel，并在阶段边界停下。
- failed job 可以 retry。
- retry 会增加 `attempt_count`。
- retry 不覆盖原始输入。
- retry 不泄露 provider key。
- job 有 `heartbeat_at`。
- long-running/stalled job 可以被 watchdog 标记。
- startup recovery 对 running/queued/paused/waiting_retry 仍然可靠。
- 面板有 cancel/retry 状态反馈。
- 测试覆盖 cancel、retry、watchdog、脱敏。
- local mode 和 provider mode 都继续可用。
- README、CHANGELOG、版本号更新到 `0.2.1`。
- 每完成一个小包都要 commit + push GitHub。

## 3. v0.2.1 不做什么

明确不做：

- 不做 batch。
- 不做多 agent。
- 不做局部重生成。
- 不做 audio render。
- 不做复杂队列系统。
- 不引入 Celery、Redis、数据库。
- 不做远程鉴权。
- 不改变公开 SongPlan schema。

如果开发发现必须引入这些内容，先停下来汇报。

## 5. JobState 设计

v0.2.1 建议扩展 job state。

当前已有：

```text
job_id
title
output_dir
status
created_at
updated_at
step
message
summary
error
attempt_count
cancel_requested
pause_requested
hidden
input_payload
provider_snapshot
artifacts
deleted
interrupted
last_seen_at
started_at
finished_at
```

建议新增：

```text
heartbeat_at
retry_requested
retry_count
max_retries
next_retry_at
last_error
stalled
stall_timeout_seconds
```

字段含义：

- `heartbeat_at`：runner 最近一次活跃时间。
- `retry_requested`：用户是否请求 retry。
- `retry_count`：实际 retry 次数。
- `max_retries`：当前 job 允许自动 retry 次数，第一版可以默认 0。
- `next_retry_at`：后续自动 backoff 用，v0.2.1 可先预留。
- `last_error`：最近一次失败错误。
- `stalled`：watchdog 判定任务卡住。
- `stall_timeout_seconds`：判定 stalled 的阈值。

状态枚举建议：

```text
queued
running
completed
failed
cancelled
interrupted
stalled
waiting_retry
```

注意：

- `hidden` 仍然不是 status。
- `stalled` 可以是 status，也可以是 bool。第一版建议直接 status=`stalled`，同时 `stalled=true`。
- `retry_count` 和 `attempt_count` 不完全相同：attempt 是实际运行次数，retry_count 是失败后重新发起的次数。

## 6. Job 控制 API

v0.2.1 应稳定这些 API。

### 6.1 POST /api/jobs/<id>/cancel

当前已有基础版，v0.2.1 要加强阶段边界检查。

行为：

- queued：立即 `cancelled`。
- running：设置 `cancel_requested=true`，runner 在阶段边界停止。
- completed：409。
- failed：409。
- cancelled：200 幂等。
- interrupted/stalled：409 或 200 视具体语义，建议 409。

响应：

```json
{
  "ok": true,
  "job": {
    "job_id": "demo",
    "status": "cancelled",
    "cancel_requested": true
  }
}
```

### 6.2 POST /api/jobs/<id>/retry

新增。

行为：

- failed：允许 retry。
- stalled：允许 retry。
- interrupted：允许 retry。
- completed：409。
- running：409。
- queued：409。
- cancelled：可选，建议 409，避免用户误触。

retry 规则：

- 使用原始 `input_payload`。
- 使用当前有效 provider config 还是旧 snapshot，需要明确。建议 v0.2.1 使用当前有效 provider config，并在新 attempt 写新的 provider snapshot。
- 不删除旧日志，append 新 attempt 事件。
- 不覆盖 request。
- 可以覆盖 `song-plan.json` 和 `song.mid`，但要记录 attempt。
- `attempt_count += 1`。
- `retry_count += 1`。
- 清空 `error` 或将旧 error 移到 `last_error`。

响应：

```json
{
  "ok": true,
  "job": {
    "job_id": "demo",
    "status": "queued",
    "retry_count": 1,
    "attempt_count": 1
  }
}
```

### 6.3 POST /api/jobs/<id>/pause / resume

v0.2.1 可以选择不做完整 pause/resume。如果要做，必须只在阶段边界生效。

建议：

- v0.2.1 优先做 cancel/retry/watchdog。
- pause/resume 放 v0.2.2 或 v0.3.0 前置，除非开发成本很低。

## 7. Pipeline 阶段边界

当前 pipeline 阶段大致是：

```text
normalize_request
deterministic_compose / provider_compose
validate_song_plan
render_midi
```

v0.2.1 要在阶段边界加入控制检查：

```python
before_step:
  heartbeat
  if cancel_requested: stop as cancelled

after_step:
  heartbeat
  if cancel_requested: stop as cancelled
```

注意：

- 如果 provider request 正在阻塞，cancel 不能立即中断 socket。第一版只保证请求返回后的阶段边界停止。
- `timeout_seconds` 是 provider 请求最长阻塞保护。
- 后续可考虑把 provider 请求做成可中断或更短超时。

## 8. Watchdog 设计

目标：server 不要永远显示 running。

### 8.1 Watchdog 触发

启动 server 时启动一个后台 watchdog thread。

周期：

```text
每 5 秒扫描一次
```

默认 stall timeout：

```text
300 秒
```

可先写死，后续再配置。

### 8.2 判定规则

如果 job 满足：

- `status == "running"`
- `heartbeat_at` 存在
- 当前时间 - `heartbeat_at` > `stall_timeout_seconds`

则：

```json
{
  "status": "stalled",
  "stalled": true,
  "step": "stalled",
  "message": "Job stalled because no heartbeat was observed.",
  "error": "No heartbeat within stall timeout."
}
```

如果 running job 没有 `heartbeat_at`：

- 用 `updated_at` 作为 fallback。

### 8.3 API

可以暂时不新增 watchdog API。

但 `/api/jobs/<id>` 应返回：

- `heartbeat_at`
- `stalled`
- `stall_timeout_seconds`

### 8.4 测试

- 构造 running job，heartbeat 很旧，调用 watchdog tick，变 stalled。
- 构造 running job，heartbeat 新，不变。
- completed job 不受 watchdog 影响。
- stalled job 可以 retry。

为了测试，不要真的 sleep 300 秒。实现一个可直接调用的方法：

```python
def run_watchdog_tick(now: datetime | None = None) -> int:
    ...
```

## 9. Retry 设计

### 9.1 手动 retry

v0.2.1 先做手动 retry。

API：

```text
POST /api/jobs/<id>/retry
```

允许状态：

```text
failed
stalled
interrupted
```

retry 后状态：

```text
queued -> running -> completed/failed
```

### 9.2 自动 retry

v0.2.1 可以先不做自动 retry。如果要预留字段：

- `max_retries`
- `next_retry_at`
- `waiting_retry`

但不要默认启用自动 retry，避免外部 provider 出错时不断消耗额度。

### 9.3 日志和产物

retry 建议写事件：

```json
{"event": "retry_requested", "retry_count": 1}
{"event": "attempt_started", "attempt_count": 2}
```

产物策略：

- `request.json` 保持一致。
- `provider-snapshot.json` 可更新为新 attempt 的 snapshot。
- `song-plan.json` 可被新 attempt 覆盖。
- `song.mid` 可被新 attempt 覆盖。
- `events.jsonl` append，不清空。
- `run-summary.json` 更新到最新 attempt。

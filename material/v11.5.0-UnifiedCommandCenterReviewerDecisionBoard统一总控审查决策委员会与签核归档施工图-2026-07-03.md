# v11.5.0 Unified Command Center Reviewer Decision Board 统一总控审查决策委员会、仲裁签核与不可变归档施工图

> 基线版本：v11.4.1  
> 目标版本：v11.5.0  
> 日期：2026-07-03  
> 施工目标：在 v11.4 Evidence Review / Replay 的基础上，建立多 reviewer 决策委员会，把外部复盘响应、accepted evidence、needs_changes findings、quorum、角色要求、最终 decision signoff 和不可变 archive 串成可离线验证、可接入 Release / GA gate 的正式审查决策闭环。

v11.4.1 已经把 v11.4.0 的关键 P1 修住：

- Evidence Review accepted gate 不再只读旧 verification report。
- `require_accepted=True` 时会 runtime 验证当前 accepted evidence ZIP。
- Release signoff payload 已透传 `unified_command_center_evidence_review_acceptance_response_verification_report`。
- `missing_acceptance_zip=failed` 已进入 v11.4 smoke。

当前稳定基线：

- v11.4.1
- Commit：`52b4584461e777b6e975b7b8930e2b9c7464dce1`
- Release：https://github.com/goodgoodstudyboy/musicforge/releases/tag/v11.4.1
- `release-check --profile v11 --skip-tests --json`：`5/5 passed`
- `release-check --profile ga --skip-tests --json`：`30/30 passed`
- `release-check --profile latest --skip-tests --json`：`50/50 passed`

这说明：

```text
v11.4 已能生成可复盘 Review Pack。
Replay 能绑定外部 UCC / Archive / Handoff / Continuous Review / Drift Response / CR proof。
accepted response 能生成 accepted evidence。
Release / GA gate 已能要求 Evidence Review evidence。
```

但 v11.4 仍然只解决“一个 reviewer 的复盘证据可以被验证”。

真实交付里，外部审查通常不是一个人说了算：

1. 技术 reviewer 看证据链是否完整。
2. 交付负责人看是否可以准出。
3. 安全 reviewer 看签核、CR、敏感信息和外部 proof。
4. 业务 owner 看 findings 是否可接受。
5. 有些 finding 需要仲裁。
6. 有些 reviewer accepted，但另一个 reviewer needs_changes。
7. 最终结论必须有 quorum、有角色覆盖、有决策签核、有不可变归档。

所以 v11.5.0 的定位是：

> 建立 Unified Command Center Reviewer Decision Board，把多个 v11.4 Review Response / Accepted Evidence 汇总成正式审查委员会决策。它支持 quorum、required roles、finding 合并、冲突仲裁、decision report、decision signoff、不可变 archive、离线 verifier，并接入 Release / GA gate。

一句话：

```text
v11.4 证明“证据链可外部复盘”。
v11.5 证明“外部复盘结论经过正式多人决策并可审计签核”。
```

### 1.1 当前已有能力

1. v11.0 Unified Command Center

   - Review Pack
   - Replay Plan / Result
   - External Proof Index
   - external reviewer response
   - accepted evidence
   - Evidence Review Release / GA gate

### 1.2 当前缺口

v11.4 完成后仍有这些问题：

1. 只有单个 accepted evidence，无法表达多 reviewer quorum。
2. 多个 reviewer 的 findings 无统一归并。
3. needs_changes / rejected response 只能生成 CR draft，但没有 decision board 统一跟踪。
4. 多 reviewer 冲突无法审计：
   - A accepted
   - B needs_changes
   - C rejected
5. 没有 required roles：
   - security reviewer
   - release owner
   - delivery owner
   - technical reviewer
6. 没有 board-level signoff。
7. 没有 board archive。
8. Release / GA gate 只能要求 Evidence Review accepted，不能要求“多人审查委员会已签核”。

v11.5 要补这个缺口。

```text
Board 不能静默改变被审查证据。
```

## 4. 用户流程

### 4.1 happy path

1. 用户已有 v11.4 Evidence Review Pack。
2. 用户已有 Review Pack verification report。
3. 多个 reviewer 各自提交 response。
4. accepted response 生成 accepted evidence。
5. 用户创建 Decision Board。
6. 用户配置 quorum policy：
   - min accepted count
   - min organizations
   - required roles
7. 用户 attach accepted evidence。
8. 系统生成 response index。
9. 系统生成 finding ledger。
10. 系统生成 quorum report。
11. 系统生成 decision matrix。
12. 如果 quorum passed 且无 blocking finding，board status = `ready_for_signoff`。
13. 用户 signoff board。
14. 系统生成 immutable archive。
15. Release / GA gate 要求 Decision Board Archive + verifier passed。

### 4.2 needs_changes path

1. reviewer 提交 `needs_changes`。
2. Board 记录 finding。
3. 如果 finding severity 是 high / critical，board status = `blocked`。
4. Board 生成 Change Request draft。
5. 不自动 approve。
6. 用户按 v11.3 / v11.4 或底层模块修复。
7. 重新生成 Evidence Review Pack。
8. 重新创建或 refresh Board。
9. 新 response / accepted evidence 覆盖旧问题。

### 4.3 reviewer 冲突 path

例如：

```text
technical reviewer: accepted
security reviewer: needs_changes
release owner: accepted
```

Decision Board 必须：

1. 标记 conflict。
2. 记录冲突来源。
3. 阻断 signoff，除非：
   - high/critical finding 已关闭，或
   - 有 explicit waiver policy，且本版如果实现 waiver，必须要求 approved CR。

建议 v11.5 第一版不做复杂 waiver，只允许：

```text
medium/low finding 可手工 acknowledge。
high/critical finding 必须修复或 rejected。
```

### 4.4 rejected path

1. 任一 required role reviewer 提交 `rejected`。
2. Board status = `rejected`。
3. signoff 不允许通过。
4. 只能生成 CR draft。
5. 不自动重开任何签核。

### 6.3 状态机

Board status：

```text
draft
collecting
ready_for_closeout
blocked
ready_for_signoff
signed
archived
stale
rejected
reset
```

允许流转：

```text
draft -> collecting
collecting -> ready_for_closeout
collecting -> blocked
ready_for_closeout -> ready_for_signoff
ready_for_signoff -> signed
signed -> archived
signed -> reset
reset -> collecting
```

禁止：

1. `signed` 后 attach response。
2. `signed` 后 refresh。
3. `signed` 后 export 覆盖旧 archive。
4. `signed` 后 zip 覆盖旧 archive。
5. `signed` 后没有 approved CR 的 reset。

## 9. Quorum Policy

### 9.1 默认 policy

默认建议：

```json
{
  "min_accepted_count": 2,
  "min_organization_count": 1,
  "required_roles": ["technical_reviewer", "release_owner"],
  "block_on_required_rejection": true,
  "block_on_any_rejection": false,
  "block_on_high_findings": true,
  "block_on_critical_findings": true
}
```

### 9.2 policy 校验

1. `min_accepted_count >= 1`
2. `min_organization_count >= 1`
3. `required_roles` 必须在白名单内。
4. 如果 `required_roles` 为空，至少要求 `min_accepted_count >= 2`。
5. policy 写入 source hash，policy 改变后旧 board stale。

### 9.3 readiness 判定

Board ready 条件：

1. Review Pack external verification passed。
2. 所有 required accepted evidence current。
3. accepted count 满足 policy。
4. organization count 满足 policy。
5. required roles 全部有 accepted。
6. 没有 required reviewer rejected。
7. 没有 open high finding。
8. 没有 open critical finding。
9. conflict report status clear 或 non-blocking。

## 10. Signoff / Reset

### 10.1 Signoff

Signoff 只能在 `ready_for_signoff` 时执行。

必须校验：

1. decision report integrity。
2. quorum report passed。
3. conflict report clear。
4. finding ledger 无 blocking findings。
5. evidence review runtime verification passed。
6. accepted evidence runtime verification passed。
7. board history chain valid。

### 10.2 Signed immutable guard

签核后禁止：

1. attach response。
2. attach accepted evidence。
3. refresh board。
4. closeout。
5. export archive overwrite。
6. build archive ZIP overwrite。
7. change policy。

即使删除：

1. `decision-signoff.json`
2. `export/`
3. `decision-board-archive.zip`

也不能绕过，因为 signed state 必须从 `board-history.jsonl` 判断。

### 10.3 Reset

Reset 必须：

1. 创建 Change Request。
2. CR 绑定当前 signoff hash。
3. CR approved。
4. CR integrity OK。
5. CR 未被 applied。
6. reset 成功后 CR 标记 applied。

不允许：

1. 无 CR reset。
2. 重复使用 CR。
3. 使用不匹配当前 signoff 的 CR。

## 17. 安全风险与 reviewer 重点

### P1：Board ZIP 内部自证

风险：

- `accepted-evidence-index.json` 被改成 passed。
- `quorum-report.json` 被改成 passed。
- `decision-report.json` 被改成 ready。

要求：

- verifier 必须重新读取外部 Review Pack / accepted evidence / response verification。

### P1：角色伪造

风险：

- 攻击者把 reviewer role 从 observer 改成 security_reviewer。

要求：

- role 必须由外部 accepted evidence / response verification 反查。
- Board 内 role 不得自证。

### P1：accepted evidence 复用

风险：

- 同一份 accepted evidence 被复制成两个 reviewer，伪造 quorum。

要求：

- evidence_id / response_id / response_payload_hash 不能重复计数。
- organization / role count 必须基于唯一 reviewer / response。

### P1：签核后删除 signoff 绕过

要求：

- signed state 从 history chain 读。
- 删除 signoff 后任何 mutation 仍 409。

### P1：high finding 被静默忽略

要求：

- open high / critical finding 阻断 signoff。
- release-check 必须覆盖。

### P2：Board 复杂导致难用

要求：

- CLI happy path 尽量短。
- Studio 默认 policy 足够可用。
- reviewer-guide.md 说明最少步骤。

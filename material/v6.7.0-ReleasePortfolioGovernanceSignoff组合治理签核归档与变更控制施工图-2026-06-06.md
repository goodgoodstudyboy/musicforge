# v6.7.0 Release Portfolio Governance Signoff 组合治理签核归档与变更控制施工图

日期：2026-06-06

当前稳定基线：v6.6.1

目标版本：v6.7.0

角色定位：reviewer / planner 交给开发执行

---

## 1. 背景

v6.5.0 已经把系统从单个 Release 的运营审计，推进到跨 Release 的 Portfolio Audit：

- 能对多个 Release 做 readiness ranking。
- 能生成 trend report。
- 能生成 risk register。
- 能生成 deterministic recommendations。
- 能导出 Portfolio Audit ZIP。
- 能在外部目录离线验证 Portfolio Audit ZIP。

v6.6.0 / v6.6.1 继续把 Portfolio Audit 的风险和建议推进为 Portfolio Governance Action Queue：

- 能从 Portfolio Audit 生成治理动作队列。
- 能区分 safe action 和 manual_required action。
- 能运行安全动作，例如 refresh / export / zip / verify。
- 能导出 Governance Queue package。
- 能离线验证 Governance Queue package。
- 能阻断 stale queue source。
- v6.6.1 已修复 stale queue 仍可 export / zip 的风险：`run-safe`、`export`、`zip` 都会被同一条 stale 语义阻断；只有 run-safe 自己造成的 `post_portfolio_refresh_required` 执行证据允许导出。

所以现在系统已经能做到：

1. 发现组合风险。
2. 生成组合治理动作。
3. 执行安全动作。
4. 产出可验证的治理队列证据。

但还缺最后一层治理闭环：

> 谁确认这一轮组合治理已经完成？
> 谁确认剩余 manual actions 是可接受的？
> 谁确认 queue package 已被外部验证？
> 签核后如果要重开，需要什么变更理由和审批证据？
> 最终交付给 reviewer 的组合治理归档包是什么？

v6.7.0 要补的就是这层。

---

## 2. 一句话目标

v6.7.0 要实现：

> 为 Release Portfolio Governance Queue 增加正式 Signoff / Archive / Change Request 流程，把一轮组合治理动作从“可执行队列”提升为“已签核、可归档、可离线验证、可追责”的组合治理闭环。

这版不是做更多自动修复，而是做治理收口。

---

## 3. 当前缺口

v6.6.1 已经能回答：

- 风险队列是什么？
- 哪些动作执行了？
- 哪些动作需要人工？
- 队列是否 stale？
- 队列导出 ZIP 是否可离线验证？

但还不能可靠回答：

- 这轮治理是否正式结束？
- 结束时底层 Portfolio Audit 是否已经刷新到执行后的状态？
- manual_required 项是否有人明确承接、豁免或转入后续工作？
- queue export / zip verifier 是否是当前证据，不是旧包？
- 签核后是否还能被静默重新 export / zip？
- 签核被 reset 时，是否有 approved Change Request？
- 外部 reviewer 拿到的最终治理归档包是否包含完整因果链？

这些缺口如果不补，会导致 v6.6 的队列变成“动作日志”，但还不是“治理结论”。

---

## 4. v6.7.0 核心交付

### 4.1 Portfolio Governance Signoff

新增 queue 级签核：

- 正常签核：所有硬性 gate 通过后签核。
- 强制签核：只允许绕过非硬性 blocker，必须写 `override_reason`。
- 签核后 queue 进入只读状态。
- 签核证据必须带 source hash、queue hash、action plan hash、execution report hash、manual list hash、queue verifier hash。
- 签核不允许绕过 stale / integrity failed / unsafe path / verifier failed。

### 4.2 Portfolio Governance Archive

新增组合治理归档包：

- 归档包绑定已签核 queue。
- 归档包包含 queue、action plan、execution report、manual list、queue verification report、signoff、change requests、before/after portfolio summary。
- 归档包支持 ZIP。
- 归档包支持离线 verifier。
- verifier 不依赖 `.musicforge/` 当前 workspace。

### 4.3 Portfolio Governance Change Request

新增变更控制：

- 签核后不能静默 reset。
- reset signoff 必须提供 approved Change Request。
- Change Request 必须有 payload hash / integrity hash。
- 一个 Change Request 只能 apply 一次。
- reset 后记录因果链：哪个 CR 导致哪个 signoff reset。

### 4.4 Studio / API / CLI 接入

在 Portfolio Audit workspace 的 Governance Queue 区块增加：

- Signoff
- Force Signoff
- Reset Signoff
- Change Request
- Export Archive
- Build Archive ZIP
- Verify Archive ZIP
- Download Archive ZIP

新增 CLI：

- 创建/查看/签核/重置治理签核。
- 创建/审批/查看 Change Request。
- 导出/打包/验证 Governance Archive。

### 4.5 Export / Release Check 接入

- Portfolio Audit export 应包含 latest governance signoff / archive summary。
- Governance Queue detail 应返回 signoff / archive / change request 摘要。
- `release-check` 增加 v6.7 smoke。

## 5. 非目标

v6.7.0 明确不做这些：

- 不自动执行 manual_required 动作。
- 不自动 signoff Release。
- 不自动 reset Release / Operations / Distribution / Submission 的任何签核。
- 不上传平台。
- 不调用 provider。
- 不做跨 portfolio 的治理调度。
- 不把 force signoff 作为正常成功路径。
- 不允许 signed queue 继续被 run-safe / export / zip 静默改写。

## 11. Signoff Gate 规则

### 11.1 正常签核必须通过

正常 signoff 必须满足：

- queue 不存在 stale。
- queue integrity OK。
- action plan integrity OK。
- execution report integrity OK。
- manual action list integrity OK。
- queue export manifest 存在且 hash 对得上。
- queue ZIP 存在且 sha256 对得上。
- queue verification report 存在且 status 是 `passed` 或允许的 `warning`。
- safe action 没有 failed。
- blocked action 没有 unresolved blocker。
- manual_required action 已被 acknowledgement 覆盖，或者明确写入 follow-up / waiver。
- 如果 execution 记录 `post_portfolio_refresh_required=true`，必须满足：
  - post source hash 与当前 portfolio source hash 一致。
  - post portfolio report hash 与当前 report hash 一致。
  - execution report integrity OK。
  - queue.latest_execution_report_hash 与 execution.integrity_hash 一致。

### 11.2 强制签核允许绕过

force signoff 只能绕过：

- manual_required 未全部处理。
- warning 类 blocker。
- 组合风险仍偏高但已经人工接受。

force signoff 必须写：

- `override_reason`
- `signed_by`
- `manual_acknowledgements` 或 `override_scope`

### 11.3 强制签核也不能绕过

force signoff 绝不能绕过：

- stale source。
- integrity failed。
- queue verifier failed。
- unsafe path。
- duplicate ZIP entry。
- redaction failed。
- queue source hash 与当前 source hash 不一致且不是 run-safe 记录的 documented drift。
- execution report hash 被篡改。
- queue export manifest hash 不匹配。
- queue ZIP sha256 不匹配。

这条要写进测试。

---

## 12. 签核后不可变规则

一旦 `signoff.status in ["signed", "force_signed"]`：

以下操作必须 409：

- `run_safe_actions`
- `export_queue`
- `build_zip`
- 修改 action plan
- 修改 manual action list
- archive 之外的 queue mutation

允许：

- 读取 queue。
- 读取 signoff。
- 创建 Change Request。
- 导出 Governance Archive。
- 构建 Governance Archive ZIP。
- 验证 Governance Archive ZIP。

reset signoff 后才能重新 run/export/zip。

reset 必须提供 approved CR。

### 13.4 错误码约定

- 400：payload 不合法。

- 500：只用于不可预期内部错误。

## 16. 离线 Verifier 规则

新增模块：

```text
song_agent/release_portfolio_governance_archive_verifier.py
```

必须检查：

- ZIP 文件存在。
- ZIP entry name 原始值安全，不能只信 `zipfile` 归一化结果。
- 禁止反斜杠 entry。
- 禁止绝对路径。
- 禁止 `..`。
- 禁止 duplicate entry。
- entry 数量上限。
- 总解压大小上限。
- `manifest.json` 存在。
- manifest package type 正确。
- manifest.files 与 ZIP entries 一致。
- manifest.files sha256 与实际 entry 一致。
- queue / action plan / execution report / manual list integrity OK。
- signoff integrity OK。
- queue verification report status 可接受。
- signoff.evidence 中记录的 hashes 与 sidecar payload 对得上。
- change requests integrity OK。
- redaction scan 通过。
- Markdown / JSON / TXT 均做敏感值扫描。

strict 模式还应检查：

- 不允许 extra entry。
- 不允许 missing sidecar。
- 不允许 force signoff，除非未传 `--require-no-force`。
- 不允许 manual_required 未 acknowledgement。

## 19. 安全与脱敏

必须沿用统一 redaction：

```text
song_agent/redaction.py
```

重点扫描：

- signoff reason
- override reason
- manual acknowledgement note
- CR reason
- CR approval note
- Markdown 文件
- archive manifest
- portfolio summaries

必须脱敏：

- API key
- GitHub token
- Bearer token
- Windows 盘符路径
- UNC 路径
- source_path / local_path / file_path
- raw provider response

API 不接受任何本机路径上传。

Archive ZIP verifier 必须扫描 raw manifest，再输出脱敏报告。

## 25. 风险清单

### 风险 1：签核后仍可静默改写 queue export

必须通过 signed immutable guard 防住。

### 风险 2：force signoff 被滥用

force 不能绕过 stale / integrity / verifier / unsafe path。

### 风险 3：archive manifest 与 signoff 形成循环 hash

不要让 signoff hash 覆盖 archive zip metadata。Archive manifest 记录 signoff hash；signoff 记录 queue evidence。

### 风险 4：run-safe 后 source hash 改变导致误判 stale

v6.6.1 已允许 documented run drift 导出。v6.7 signoff 也必须支持这类情况，但要严格校验：

- execution integrity OK
- pre_source_hash == queue.source_hash
- post_source_hash == current source hash
- post_portfolio_report_hash == 当前 portfolio report hash

### 风险 5：Change Request 可以重复 reset

CR apply 后必须变成 `applied`，二次使用 409。

### 风险 6：外部 verifier 只信 manifest

Verifier 不能只信 manifest.files 或 manifest.zip.entries。必须从真实 ZIP central directory 读取 entry，检查 duplicate、raw backslash、危险路径、hash。

### 风险 7：manual acknowledgement 泄露本机路径或 token

所有 note/reason/approval_note 都必须 redaction。

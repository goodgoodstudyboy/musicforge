# v5.7.0 Release Format Decision Workbench 发行格式对比决策工作台施工图

日期：2026-06-01

角色定位：reviewer / planner

当前稳定基线：v5.6.1

目标版本：v5.7.0

---

## 1. 背景

v5.5.1 和 v5.6.1 已经把发行音频格式链路打到了一个比较可信的阶段：

- v5.5.1：MP3 / FLAC / AAC / WAV 多格式编码、manifest、hash/header、Release/Distribution package 验证。
- v5.5.1 hotfix：fake runner 不能进入公开配置，fake evidence 会被 gate / verifier 拒绝。
- v5.5.1 hotfix：Distribution layout 按 `audio_format_profiles` 打包，不再误回落 WAV。
- v5.6.0：Encoded Audio Acceptance，逐 profile / track 的 health + manual review。
- v5.6.1 hotfix：Release Export 可以保留全量 encoded acceptance evidence，Release Signoff 可以只要求其中一个 profile 子集。

所以现在系统能回答：

> MP3/FLAC/AAC 是否真实生成？是否来自当前母带？是否通过自动 health？是否有人实际听过？Distribution 包里的文件和 evidence 是否能离线验证？

但还不能回答一个更业务化的问题：

> 这次 Release 到底应该交付哪些格式？为什么选择 MP3 320 而不是 MP3 V0？为什么给客户试听包用 MP3 而平台包用 FLAC/WAV？这些选择是否有 A/B 听审和证据支撑？

当前 v5.6 的问题不是“缺少校验”，而是“缺少决策层”：

- 多个 encoded profile 都可能通过验收，但没有格式间比较。
- Distribution target 可以要求格式，但没有“格式选择理由”。
- Release Signoff 可以要求某个 profile，但没有证明“为什么这个 profile 是被选中的交付格式”。
- 人工听审是逐格式逐曲的，但没有 profile-level ranking / recommendation。
- 如果同一首歌 MP3 320 通过、AAC 有 artifact、FLAC 完美，系统不能生成一个交付建议。
- 如果某个平台模板要求 MP3，但 release team 决定用 FLAC 做 archive，也没有统一决策报告。

v5.7.0 要补的就是这一层：**Release Format Decision Workbench，发行格式对比决策工作台**。

---

## 2. 版本定位

v5.7.0 不是新的编码器，也不是外部平台上传。

它要做的是：

> 在已经生成并验收的 encoded audio profiles 之上，建立 profile 级 A/B 对比、格式推荐、交付格式选择、决策报告和签核 evidence。

一句话：

> v5.6 证明“每个格式可以交付”，v5.7 证明“为什么选择这些格式交付”。

---

## 3. 明确不做

v5.7.0 不做以下内容：

- 不做云端 ABX 测试平台。
- 不做自动替代人工审美判断。
- 不上传 Spotify / Apple / YouTube / SoundCloud。
- 不做平台官方合规认证。
- 不做真实 LUFS / true peak 标准测量，除非已有本地工具支持。
- 不做完整 psychoacoustic 音质评分。
- 不做自动选择后静默修改 Distribution Target；所有选择必须人工确认。
- 不把 synthetic review 当成 release-ready 决策证据。
- 不允许 fake encoder / fixture runner 结果进入正式 decision report。

v5.7 可以有 deterministic recommendation，但最终 `selected_profiles` 必须由人工确认或明确 override。

---

## 4. 为什么现在做

如果在 v5.5 之前做格式决策，基础格式 evidence 不可信。

如果在 v5.6 之前做格式决策，人工听审证据不完整。

现在 v5.6.1 已经具备：

- encoded manifest
- encoded health
- encoded review
- Release Export sidecar
- Distribution Export sidecar
- offline verifier
- profile subset signoff

所以 v5.7 可以在这些证据之上做决策层，不需要重新发明编码链路。

---

## 5. 核心目标

v5.7.0 完成后，系统必须支持：

1. 创建 Release Format Decision Session。
2. 从现有 encoded profiles 中生成可比较的 profile matrix。
3. 对每个 profile 计算 deterministic score。
4. 聚合 health、manual review、file size、format、distribution target requirement。
5. 支持 profile-level A/B review summary。
6. 生成 recommendation：selected / fallback / archive / rejected。
7. 由人工确认 selected delivery profiles。
8. 生成 Format Decision Report。
9. Release Signoff 可以要求 current decision report。
10. Distribution Target 可以绑定 decision profile 或 decision recommendation。
11. Release Export / Distribution Export / ZIP 写入 decision evidence。
12. `verify-release` / `verify-distribution-package` 可以离线验证 decision evidence。
13. Studio 有 Format Decision Workbench。
14. release-check 覆盖多 profile、选择、stale、tamper、fake、subset、Distribution target 映射。

## 10. Source Hash 设计

Format decision source hash 必须绑定：

- release id / track ids / project ids / version ids
- encoded audio manifest hashes
- encoded audio acceptance summary hash
- accepted review ids and hashes
- distribution targets options hash
- template pack ids / hashes if used
- selected profile ids
- manual decision reason

不能绑定：

- generated_at
- display-only fields
- event log

如果以下内容变化，decision report 必须 stale：

- Release tracks 变化
- encoded manifest 变化
- encoded health 变化
- encoded review 变化
- Distribution target required formats 变化
- selected profile 变化
- template pack bound to target 变化

---

## 11. Scoring 规则

v5.7 不需要复杂 ML，deterministic score 即可。

建议初始分：

```text
base = 50
```

加分：

```text
health passed: +20
all required manual reviews accepted: +20
average rating >= 4.5: +10
lossless archive role: +8
distribution target requires profile: +15
file size efficient for delivery role: +5
```

扣分：

```text
health warning: -10
any needs_fix/rejected: -30
missing manual review: -40
synthetic-only: -40
stale evidence: -50
fake evidence: hard fail
too large for delivery role: -5 to -15
not required by any target and not archive: -5
```

硬失败：

```text
fake_evidence
manifest_stale
acceptance_stale
review_tampered
manual_review_missing when release_ready=true
```

输出 score breakdown：

```json
{
  "score": 91,
  "breakdown": [
    {"rule": "health_passed", "delta": 20},
    {"rule": "manual_reviews_accepted", "delta": 20},
    {"rule": "distribution_required", "delta": 15}
  ]
}
```

## 12. Recommendation 规则

默认 role 推断：

- `wav_master`: fallback 或 master source，不默认 delivery，除非 target 要 WAV。
- `flac_lossless`: archive 或 lossless delivery。
- `mp3_320`: delivery / pitch / generic client share。
- `mp3_v0`: size-sensitive delivery / optional fallback。
- `aac_256`: mobile / podcast / platform-specific delivery。

如果 Distribution Target 指定：

```json
"audio_format_profiles": ["mp3_320"]
```

则 `mp3_320` 必须进入 `selected_defaults`，除非 evidence failed。

如果 target 要多个 profile：

```json
["mp3_320", "flac_lossless"]
```

两个都必须进入 selected 或 archive，且 report coverage 要写明。

```http
POST /api/releases/<release-id>/format-decisions/<session-id>/matrix
```


POST 行为：

- 重新读取当前 encoded / acceptance / distribution target evidence。
- 写 `matrix.json`。
- 如果 source stale，不静默覆盖旧 selected decision，必须标记 stale。

### 13.3 Recommendation

```http
POST /api/releases/<release-id>/format-decisions/<session-id>/recommend
GET  /api/releases/<release-id>/format-decisions/<session-id>/recommendation
```

### 13.4 Select

```http
POST /api/releases/<release-id>/format-decisions/<session-id>/select
```

Payload：

```json
{
  "selected_profiles": ["mp3_320"],
  "archive_profiles": ["flac_lossless"],
  "fallback_profiles": ["wav_master"],
  "rejected_profiles": ["aac_256"],
  "decided_by": "developer",
  "reason": "MP3 320 is required for demo pitch; FLAC is retained for archive."
}
```

Rules：

- `selected_profiles` 必须全部在 candidate profiles 中。
- selected profile 必须 health passed/warning 且 manual review accepted。
- fake/stale/tampered profile 不允许 selected。
- required distribution profile 不允许被 rejected，除非 target 已解除绑定或 reason + force，但 release-ready 默认不允许 force。
- `reason` 必填。

### 13.5 Report

```http
POST /api/releases/<release-id>/format-decisions/<session-id>/report
GET  /api/releases/<release-id>/format-decisions/<session-id>/report
POST /api/releases/<release-id>/format-decisions/<session-id>/activate
```

`activate` 将 session 写入：

```text
active-session.json
```

Release Signoff 使用 active session。

## 16. Release Signoff Gate

Release Signoff payload 新增：

```json
{
  "require_format_decision": true,
  "format_decision_session_id": "fds-000001"
}
```

规则：

1. 必须有 active session 或 payload 指定 session。
2. Decision report 必须 current。
3. Decision report integrity 必须 passed。
4. `selected_profiles` 必须覆盖 signoff 所需 `required_audio_format_profiles`。
5. 如果 `require_encoded_audio_review=true`，selected profiles 必须全部通过 encoded acceptance。
6. 如果 Distribution targets 已绑定 Release，target required profiles 必须被 selected/archive 覆盖。
7. fake/stale/tampered evidence 不可 force。
8. warning 可 force，但必须 `override_reason`。

Signoff evidence 写入：

```json
"format_decision": {
  "session_id": "fds-000001",
  "report_hash": "...",
  "selected_profiles": ["mp3_320"],
  "archive_profiles": ["flac_lossless"],
  "status": "passed"
}
```

## 20. Redaction 与安全

Manual decision reason、review notes、recommendation reasons 都要脱敏：

- API keys
- GitHub token
- Bearer token
- Windows path
- UNC path
- provider raw response
- local absolute path

Decision report 不允许写：

- 本机 ffmpeg 完整路径
- provider API key
- raw local source path
- user home path

所有 file paths 必须是 package relative path。

---

## 21. Integrity 与 Stale

必须有：

```text
format_decision_session_hash
format_matrix_hash
format_recommendation_hash
format_decision_report_hash
```

Stale 场景：

1. 新增/删除 Release track。
2. encoded audio re-render。
3. encoded health refresh 后 hash 变化。
4. encoded review 更新。
5. Distribution target required profiles 变化。
6. template pack 变化。
7. selected profiles 更新但 report 未刷新。
8. report JSON 被手工篡改。

Stale 后：

- GET report 要显示 `stale=true`。
- Release Signoff 409。
- Distribution Signoff 409。
- verifier failed。

### 22.6 Release Check

`python -m song_agent.cli release-check` 新增 v5.7 smoke：

流程：

1. 创建 Release。
2. 生成 selected mastered WAV。
3. encoded render `mp3_320,flac_lossless,aac_256`。
4. health refresh。
5. manual review：
   - mp3 accepted
   - flac accepted
   - aac needs_fix 或 rejected
6. create format decision session。
7. matrix / recommendation。
8. select mp3 as delivery，flac as archive，aac rejected。
9. report / activate。
10. Release Signoff `require_format_decision=true` passed。
11. verify-release `--require-format-decision --require-encoded-audio-review --require-audio-formats mp3_320` passed。
12. Distribution target mp3 -> signoff/package verify passed。
13. Tamper decision report -> verifier failed。
14. Change Distribution target to require aac -> signoff 409。

Smoke 输出示例：


## 26. 风险点

### 26.1 不要自动替用户做交付选择

Recommendation 可以给建议，但 selected profiles 必须人工确认。

### 26.2 不要让全量导出和子集签核再出现 v5.6.0 的问题

Release Export 可以包含全量 format decision evidence。

Signoff 可以只要求某个 profile 子集。

Gate 应判断覆盖关系，不应要求全量 hash 等于子集 hash。

### 26.3 不要让 rejected profile 阻断无关 target

如果 target 只要求 MP3，AAC rejected 不应阻断 target。

但如果 target 后续改成要求 AAC，必须 stale / 409。

### 26.4 不要让 Distribution target 静默改变 selected profiles

Target 变化只能让 decision stale，不能自动改 decision。

### 26.5 不要让 warning 被当作 passed

Health warning / review warning 可以进入 report，但 signoff 是否允许必须明确，并要求 override reason。

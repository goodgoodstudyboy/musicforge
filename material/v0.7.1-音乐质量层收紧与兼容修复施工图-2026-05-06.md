# MusicForge v0.7.1 施工图：音乐质量层收紧与兼容修复

日期：2026-05-06  
角色：reviewer / planner  
目标版本：v0.7.1  
前置版本：v0.7.0

## 1. 为什么要先做 v0.7.1

v0.7.0 已经完成音乐质量层第一版：

- SongPlan quality metadata
- `song_agent/music_quality.py`
- deterministic / multinode quality-aware generation
- critic dimension scores
- repair 低风险 quality 修复
- provider prompt / mock provider quality 字段
- `/api/jobs/<id>/quality`
- Studio Quality tab
- Timeline energy / tension / density / hook

这一步方向是对的，但 v0.7.0 是质量层第一版，最容易出现的问题不是“缺大功能”，而是：

- 旧数据没有 quality 时，Studio 各视图表现不一致。
- `/quality` 等 runtime API 在 job 未完成时错误码不够清晰。
- validator view 和 quality view 没有完全打通。
- quality analyzer 的规则还比较粗，容易误报或漏报。
- repair 只补 metadata，但不一定重新计算修复后的 quality。
- provider 输出 quality 字段虽然可用，但 schema 兼容和异常测试还不够紧。

所以 v0.7.1 不建议开始 v0.8.0 stem。应该先收紧 v0.7.0 的质量层，让它稳定、可解释、兼容旧产物，再进入多轨导出。

## 2. v0.7.1 总目标

v0.7.1 的目标是“质量层稳定化”。

要交付：

1. 旧 SongPlan 兼容更一致
   - 没有 `quality` 的旧 `song-plan.json` 在 Summary、Timeline、Validator、Quality tab 中都能得到一致的推断质量信息。
   - 不要求旧 JSON 被改写，但视图层要能推断并展示。

2. Runtime API 错误更清晰
   - job 未完成、`song-plan.json` 不存在时，`/quality` 应返回 `409 Conflict`，而不是被外层捕获成 `400` 或 `500`。
   - `/validator` 如果有 plan，要合并 quality warnings；如果没有 plan，则清晰说明。

3. Quality analyzer 收紧
   - 修正明显误报。
   - 增加边界测试。
   - 让评分更稳定，不因为缺少 metadata 就出现不一致。

4. Critic / repair 收紧
   - critic 的 `dimension_scores` 和 quality view 对齐。
   - repair 后的 quality metadata 必须反映修复后的最终 plan。
   - node retry 后 quality 仍保持一致。

5. Studio 展示收紧
   - Timeline 对旧 plan 也显示推断的 energy/tension/density。
   - Quality tab 对 missing plan / running job 给友好错误。
   - Validator tab 能显示 quality warnings。

## 3. 本阶段不做什么

v0.7.1 不做：

- 不做 stem / 分轨 WAV，这放 v0.8.0。
- 不做钢琴卷帘编辑。
- 不做真实 provider 深度调参。
- 不做复杂乐理依赖。
- 不做评分模型训练。
- 不做多版本 A/B 评分。
- 不改 MIDI renderer 的核心协议。

这是一个修复和收紧版本，不是功能扩张版本。

## 4. 必修问题清单

### P1：旧 plan 的 Timeline 不能推断 quality intent

当前 `build_timeline_view()` 主要从 `plan["quality"]["section_intents"]` 读取：

```python
intents = _section_intents_by_name(plan_data)
```

如果旧 `song-plan.json` 没有 `quality`，Timeline 里的：

- `energy`
- `tension`
- `density`
- `role`
- `hook`

会全部是默认空值或 0。

但 `/quality` 会用 `analyze_song_quality(song_plan)` 推断质量，所以旧 plan 在 Quality tab 和 Timeline tab 中会表现不一致。

修复要求：

- `build_timeline_view()` 应在缺少 quality intent 时调用 quality analyzer 推断。
- 不要改写磁盘上的旧 `song-plan.json`。
- Timeline view 应返回推断值。

验收：

- 给一个没有 `quality` 的旧 plan，Timeline 仍能显示：
  - intro energy 2
  - verse energy 4
  - chorus energy 7
  - chorus hook true
- Quality tab 和 Timeline tab 的 section intent 一致。

建议测试：

- `tests/test_runtime_views.py::test_timeline_infers_quality_for_legacy_plan`

### P1：/quality 在 job 未完成时应返回 409

当前 `_send_runtime_view()` 对 `timeline/tracks` 做了 plan_path 检查：

```python
if view_name in {"timeline", "tracks"} and not plan_path.exists():
    409
```

但 `quality` 分支会直接：

```python
plan = read_json(plan_path)
```

如果 job 正在运行、排队、失败且没有 `song-plan.json`，这个错误会被外层捕获成不够清晰的错误。

修复要求：

- `view_name in {"timeline", "tracks", "quality"}` 时都检查 `song-plan.json`。
- 错误码：`409 Conflict`
- 错误文案：

```text
song-plan.json is not available for this job yet.
```

验收：

- 创建 queued job，不等完成直接请求 `/api/jobs/<id>/quality`。
- 返回 409。
- body 是 JSON error。
- auth 模式下仍先鉴权，未授权仍 401。

建议测试：

- `tests/test_server.py::test_quality_endpoint_requires_song_plan`
- `tests/test_server_auth.py` 保持现有保护测试。

### P1：Validator view 没有合并 quality warnings

`build_validator_view(report, plan=None)` 已支持传 plan 后合并 quality warnings。

但 server 当前调用：

```python
build_validator_view(report)
```

这意味着 `/api/jobs/<id>/validator` 不能显示 quality warnings。

修复要求：

- 如果 `song-plan.json` 存在，读取 plan 并传给 `build_validator_view(report, plan)`。
- 如果 plan 不存在，仍返回 validator 当前结果。
- 如果 validator-report 不存在但 plan 存在，也应返回 missing validator + quality warnings。

验收：

- 构造一个有 quality warning 的 plan。
- `/validator` 返回 warnings 包含 quality warning。
- 没有 validator-report 时，仍能返回 `status: missing`，并包含 quality warning。

建议测试：

- `tests/test_server.py::test_validator_endpoint_includes_quality_warnings`
- `tests/test_runtime_views.py::test_validator_view_merges_quality_warnings`

## 5. Quality analyzer 收紧项

### P2：Instrumental 判断不应依赖 warnings 字符串

当前 `_is_instrumental()`：

```python
if plan.quality and any("instrumental" in warning.lower() for warning in plan.quality.warnings):
    return True
return all(not section.lyrics for section in plan.sections)
```

这个判断太间接。SongPlan 本身没有 vocal_mode，所以短期不能完美判断，但不能依赖 warning 文本。

v0.7.1 建议：

- 保留 `all(not section.lyrics for section in plan.sections)` 作为默认 instrumental 推断。
- 如果未来要精确判断，可以把 `vocal_mode` 加进 quality summary 或 SongPlan metadata，但 v0.7.1 不强加大改动。
- 移除或弱化基于 warnings 文本的判断。

验收：

- 没有 lyrics 的 plan，`lyric_fit=0`。
- 有 lyrics 的 plan，`lyric_fit` 参与评分。
- warnings 里出现 instrumental 字样不应单独决定 instrumental。

建议测试：

- `tests/test_music_quality.py::test_instrumental_detection_does_not_depend_on_warning_text`

### P2：Bass root mismatch 规则过粗

当前 `_bass_root_mismatches()` 只看每个 section 的第一颗 bass note 和第一颗 chord：

```python
expected = _bass_root(section.chords[0])
notes = _notes_in_section(bass.notes, section)
if notes and abs(notes[0].pitch - expected) > 12:
    mismatch
```

这会误判一些合理的 passing note 或 octave 写法，也会漏掉 section 后半段错位。

v0.7.1 建议低成本收紧：

- 每个 section 至少检查每小节第一拍或每个 chord 对应小节附近的 bass note。
- 允许 octave 等价：使用 pitch class 或 root class 判断，而不是绝对音高差。
- 如果没有 bass note，不在 harmony 里报 mismatch，交给 arrangement 的 empty/missing 检查。

验收：

- C chord 下 C2/C3/C4 都不报 mismatch。
- C chord 下 F# 或 B 连续出现才报 warning。
- passing note 不应单独触发 mismatch。

建议测试：

- `tests/test_music_quality.py::test_bass_root_accepts_octaves`
- `tests/test_music_quality.py::test_bass_root_ignores_passing_note`
- `tests/test_music_quality.py::test_bass_root_mismatch_requires_repeated_problem`

### P2：Mechanical repetition 检查需要避免误报 hook repetition

当前 repetition 规则：

```python
if len(set(windows)) <= 1 and len(windows) > 2:
    warning
```

Hook 的合理重复可能被误报。

v0.7.1 建议：

- 如果重复只集中在 hook/chorus，可以降低为 info 或不报。
- 如果全曲所有 section 都同一四音窗口，才 warning。
- 检查 rhythm + pitch 两维，不只看 pitch。

验收：

- chorus hook 重复不 warning。
- verse/chorus/outro 全部相同机械重复 warning。

建议测试：

- `tests/test_music_quality.py::test_hook_repetition_is_allowed`
- `tests/test_music_quality.py::test_global_mechanical_repetition_warns`

### P2：Quality summary 应避免过度依赖 title

当前：

```python
return f"{plan.title} scores {scores.overall}/100 with {hook_text}."
```

可用，但不够业务化。v0.7.1 可以轻量改为：

- 包含整体质量。
- 包含 hook 状态。
- 包含主要 warning 数。

示例：

```text
Overall 87/100. Hook: chorus. Warnings: static harmony, bass root mismatch.
```

验收：

- summary 不为空。
- 包含 overall score。
- 包含 hook section。
- 有 warning 时包含 warning 数或关键 code。

## 6. Critic / repair 收紧项

### P1：Repair 后应重新计算最终 quality

当前 repair 流程会调用 `repair_quality_metadata()`，但需要明确保证：

- 如果修复了 melody pitch、velocity、duration，最终 quality 基于修复后的 tracks。
- 如果修复了 chorus melody，最终 scores 应反映修复后的 melody。
- `RepairPlan.actions` 里能看到 quality 修复动作。

验收：

- 构造 melody range too narrow 的 plan。
- repair 后 chorus melody 被抬高。
- repair 后 quality score 不低于 repair 前。
- repair actions 包含 `lift_chorus_melody`。

建议测试：

- `tests/test_multinode_pipeline.py::test_repair_recomputes_quality_after_track_fix`
- `tests/test_music_quality.py::test_repair_quality_metadata_improves_score`

### P2：Critic dimension_scores 应和 Quality view 对齐

现在 critic 有 `dimension_scores`，Quality view 也有 scores。v0.7.1 要明确：

- Critic 的 `dimension_scores` 不含 `overall` 可以，但 Quality view 里的 `critic.dimension_scores` 和 `scores` 的同名维度应一致。
- 如果没有 critic node，比如 single pipeline，Quality view 仍可正常返回，不应显示 critic 假数据。

验收：

- multinode job 的 `/quality` 返回 `scores.structure == critic.dimension_scores.structure`。
- single job 的 `/quality` 没有 critic 或 critic 为空，但页面不报错。

建议测试：

- `tests/test_server.py::test_quality_endpoint_critic_scores_match_quality_scores`
- `tests/test_runtime_views.py::test_quality_view_without_critic_is_valid`

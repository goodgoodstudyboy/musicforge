# v4.8.0 Acceptance-driven Fix Sprint 验收驱动修复冲刺施工图

日期：2026-05-20

当前稳定基线：v4.7.1

目标版本：v4.8.0

建议版本主题：Acceptance-driven Fix Sprint / 验收问题驱动修复冲刺

---

## 1. 背景

v4.7.1 已经把 Acceptance Suite、Regression Songbook、Human Review Pack、人工听审结果、ReviewTask 和 Release Signoff 串成了 Acceptance Analytics。

现在系统已经能回答：

- 哪些 song_id 经常失败。
- 哪些风格弱。
- 哪些 issue type 高频出现。
- 哪些 analytics report 是 stale。
- 哪些 recommendation 可以显式创建 ReviewTask。
- Release Signoff 能看到 analytics evidence，并能挡住 blocked readiness。

但是 v4.7 仍然停在“分析和建议”层。

下一步不应该继续堆更多 dashboard，而应该让验收结果真正驱动修复工作流：

```text
Acceptance Analytics
  -> Recommendations
  -> Fix Sprint
  -> ReviewTasks
  -> candidate / edit / manual work
  -> Re-run Acceptance Suite
  -> Compare before/after
  -> Decide close / continue
```

v4.8.0 的目标就是补上这条链路。

---

## 2. 版本定位

一句话定位：

> v4.8.0 把 Acceptance Analytics 的 recommendations 组织成一个可执行、可追踪、可复验、可计算质量 delta 的 Acceptance Fix Sprint。

它不是替代 v3.x 的 Review Sprint，而是基于验收结果自动组织“修复冲刺”的上层入口。

v3.x Review Sprint 的任务来源主要是创作评审、候选决策、Judge、Closeout。

v4.8 Acceptance Fix Sprint 的任务来源是：

- Acceptance Analytics recommendation
- Songbook heatmap weakness
- Issue taxonomy 高频问题
- Human Review Pack needs_fix / rejected
- Release Signoff blocked analytics evidence

---

## 3. v4.8.0 明确不做什么

本版不做：

- 不自动 apply candidate。
- 不自动修改 Project final version。
- 不自动关闭 Release。
- 不调用 provider 自动修歌，除非后续用户显式走已有 provider candidate API。
- 不做真实音频模型、vocal、mixing、mastering。
- 不把 synthetic review 当成人工验收。
- 不让 stale analytics recommendation 创建修复任务。
- 不把 Fix Sprint 的结果直接作为 Release Signoff 通过依据。
- 不删除原始 Acceptance Suite、ReviewTask 或 Project Version。

本版允许：

- 从 fresh Acceptance Analytics report 显式创建 Fix Sprint。
- 从 recommendations 批量创建或绑定 ReviewTask。
- 组织修复优先级、issue group、songbook group。
- 触发复验 suite 创建。
- 复验后计算 before/after delta。
- 在 Studio 里展示 Fix Sprint 状态和修复效果。
- 将 Fix Sprint summary 写入 Release Export / Final Export / Signoff evidence。

## 4. 核心用户故事

### 4.1 开发人员

开发人员希望：

- 不用手动翻 analytics report，系统能把高优先级问题整理成一个 sprint。
- 一键把 recommendation 变成 ReviewTask。
- 清楚知道每个 song_id 该修什么。
- 修完后能重新跑验收。
- 能看到修复前后 rating、status、issue count 有没有改善。

### 4.2 Reviewer

Reviewer 希望：

- 能看到某个 Release 的 blocked analytics 有没有被真正处理。
- 能看到 Fix Sprint 是否完成。
- 能看到哪些问题被 waiver，哪些还 open。
- 能看到复验 suite 是否比原 suite 更好。

### 4.3 业务方

业务方希望：

- 知道“这次验收没过”之后开发怎么修。
- 知道修复是否有效。
- 知道还有哪些风格或歌曲不稳定。

## 5. 新增概念

### 5.1 Acceptance Fix Sprint

验收修复冲刺。

它是一个围绕某个 analytics report 或 release analytics evidence 创建的修复工作单元。

一个 Fix Sprint 包含：

- source analytics report
- source hash
- selected recommendations
- fix items
- linked ReviewTasks
- optional linked Review Sprint
- recheck Acceptance Suite
- delta report
- closeout report

### 5.2 Fix Item

Fix Sprint 内的一个具体修复项。

来源可以是：

- recommendation
- songbook heatmap row
- issue taxonomy row
- human review rejected case
- manually added issue

### 5.3 Recheck Suite

修复后重新创建或绑定的 Acceptance Suite。

Recheck Suite 必须明确：

- 对应哪个 Fix Sprint。
- 复验哪些 song_id。
- 使用哪个 profile。
- 是否要求人工听审。
- 是否使用 Human Review Pack。

### 5.4 Delta Report

修复前后对比报告。

对比维度：

- readiness_status
- accepted / needs_fix / rejected count
- average rating
- manual coverage
- issue taxonomy count
- weakness score
- per-song status
- per-style status
- ReviewTask close rate

## 7. Source Hash 与 Stale Guard

这是 v4.8 的 P1 核心。

Fix Sprint 创建时必须记录：

- analytics report_id
- analytics source_hash
- recommendation_id 列表
- selected recommendation payload hash

后续任何执行动作前必须检查：

- source analytics report 是否存在。
- report 是否 stale。
- current_source_hash 是否等于创建时 source_hash。
- recommendation_id 是否仍存在。
- recommendation payload 是否未改变。

如果不满足：

```text
409 Fix Sprint source analytics is stale. Refresh analytics and create a new Fix Sprint.
```

允许读旧 Fix Sprint，但不允许继续生成新任务、recheck、closeout。

## 8. API 设计

### 8.1 Fix Sprint CRUD

```text
GET  /api/acceptance/fix-sprints
POST /api/acceptance/fix-sprints
GET  /api/acceptance/fix-sprints/<fix-sprint-id>
POST /api/acceptance/fix-sprints/<fix-sprint-id>/archive
POST /api/acceptance/fix-sprints/<fix-sprint-id>/refresh-status
```

创建 payload：

```json
{
  "name": "Release analytics fixes",
  "analytics_report_id": "analytics-...",
  "recommendation_ids": ["rec-001", "rec-002"],
  "scope": {
    "type": "release",
    "release_id": "release-000001"
  },
  "profile_id": "developer_manual",
  "require_manual_recheck": true
}
```

行为：

- analytics report 必须 fresh。
- recommendation_ids 为空时可默认选择高优先级 create_review_task recommendations。
- 如果 report readiness 是 ready/watch，允许创建但提示 low_priority。
- 创建后 status=draft 或 planned。

### 8.2 Fix Items

```text
GET  /api/acceptance/fix-sprints/<id>/items
POST /api/acceptance/fix-sprints/<id>/items
POST /api/acceptance/fix-sprints/<id>/items/<item-id>/waive
POST /api/acceptance/fix-sprints/<id>/items/<item-id>/reopen
```

手动新增 item 时必须显式填写：

- title
- target.song_id 或 issue_types
- reason

### 8.3 创建 / 绑定 ReviewTask

```text
POST /api/acceptance/fix-sprints/<id>/create-review-tasks
POST /api/acceptance/fix-sprints/<id>/items/<item-id>/create-review-task
POST /api/acceptance/fix-sprints/<id>/items/<item-id>/link-review-task
```

约束：

- 只能从 fresh Fix Sprint 创建。
- 不重复创建相同 song_id + issue_types 的 open ReviewTask。
- 如果已有 open task，返回 existing 并绑定。
- 如果 item 没有 project_id，返回 409，需要用户手动指定 project_id。
- 创建的 ReviewTask source.source_type 应为 `acceptance_fix_sprint`。
- ReviewTask source 应包含 fix_sprint_id、item_id、analytics_report_id、recommendation_id、source_hash。

### 8.4 Recheck Suite

```text
POST /api/acceptance/fix-sprints/<id>/create-recheck-suite
POST /api/acceptance/fix-sprints/<id>/link-recheck-suite
GET  /api/acceptance/fix-sprints/<id>/recheck
```

create-recheck-suite payload：

```json
{
  "profile_id": "developer_manual",
  "song_ids": ["rap_beat_001", "cn_pop_ballad_001"],
  "require_manual_review": true,
  "copy_requests_from_source": true
}
```

行为：

- 默认复验所有 Fix Item 涉及的 song_id。
- 如果 item 关联 project/version，复验 case 应使用 project_version source。
- 如果没有 project/version，只能创建 generated_request case，并记录 warning。
- release-ready profile 不允许 synthetic 通过。

### 8.5 Delta Report

```text
GET  /api/acceptance/fix-sprints/<id>/delta
POST /api/acceptance/fix-sprints/<id>/delta/refresh
```

Delta 计算：

- source analytics report vs recheck analytics report。
- source suite/case vs recheck suite/case。
- item 状态变化。
- ReviewTask 完成率。

### 8.6 Closeout

```text
GET  /api/acceptance/fix-sprints/<id>/closeout
POST /api/acceptance/fix-sprints/<id>/close
```

close gate：

- source 不能 stale。
- 所有 non-waived items 必须 fixed 或 closed。
- recheck suite 必须存在。
- recheck report 必须不是 stale。
- recheck analytics readiness 不能是 blocked。
- release-ready recheck 必须人工覆盖完整。
- 如果有 waived item，必须有 waiver reason。
- force close 必须 override_reason。

## 12. ReviewTask 关系

v4.8 不需要重造候选系统。

它应该复用现有 ReviewTask / Review Sprint / candidate 工作流。

创建 ReviewTask 时：

- source_type = acceptance_fix_sprint
- priority 继承 item priority
- title 继承 item title
- summary 继承 analytics evidence
- target 指向 project/song/version
- review_snapshot 带 recommendation 摘要

不要在 ReviewTask 里复制完整 analytics report。

## 14. 安全与脱敏

所有新增 report、event、export 都必须走 sanitize。

重点字段：

- item title
- item summary
- waiver reason
- override reason
- manual notes
- recommendation reason
- reviewer name
- project/release names

禁止导出：

- 本机绝对路径
- source_path
- provider raw response
- token/api_key/secret
- 完整 Human Review Pack 原始 response

## 17. P1 风险清单

开发必须重点防：

- stale analytics report 还能创建 Fix Sprint。
- stale Fix Sprint 还能创建 ReviewTask。
- stale Fix Sprint 还能创建 recheck suite。
- recommendation payload 改变但旧 sprint 继续执行。
- duplicate ReviewTask 重复创建。
- item 没有 project_id 却静默创建无效 ReviewTask。
- recheck suite 用 synthetic review 冒充 manual release-ready。
- delta report 把不同 song_id 错配。
- closeout 在 open item 存在时放行。
- waiver 没有 reason。
- export 泄露本机路径或人工听审原文。

---

## 18. Reviewer 检查重点

Reviewer 验收时至少检查：

1. fresh analytics report 能创建 Fix Sprint。
2. stale analytics report 创建 Fix Sprint 返回 409。
3. Fix Sprint source 变 stale 后，create-review-tasks / create-recheck-suite / close 都返回 409。
4. duplicate open ReviewTask 不重复创建。
5. Recheck Suite 明确绑定 fix_sprint_id。
6. Delta Report before/after 口径正确。
7. Release Export 中只有 summary，没有完整 notes 和本机路径。
8. release-check v4.8 smoke 覆盖主链路。
9. 全量测试、doctor、release-check、git diff --check 全过。

# v5.0.0 Real Audio Baseline 真实音频基线与人工听审准出施工图

日期：2026-05-25

角色定位：reviewer / planner

当前稳定基线：v4.14.1

目标版本：v5.0.0

---

## 1. 背景

MusicForge 到 v4.14.1 已经完成了从生成、编辑、候选、评审、冲刺、发行、分发、人工验收、知识库、规划规则治理、规则效果监控到回滚建议的一整套工程闭环。

现在系统的问题不再是“流程有没有”，而是更接近业务本质：

- 生成出来的音乐是否真的可听？
- MIDI 是否能稳定转成 WAV？
- WAV 是否完整、非静音、非削波、时长合理？
- 人工听审证据是否能绑定到 Release Signoff？
- 交付包里的音频是否能离开本机后被独立验证？

v4.4 到 v4.6 已经做了 Acceptance Suite 和 Human Review Pack，但那一层仍然可以是 MIDI-only，也允许 synthetic review 明确标注为非人工听审。v5.0 应该把系统推进到“真实音频基线”：

1. 开发环境必须能配置和验证真实音频渲染能力。
2. 核心验收不再只看 SongPlan / MIDI，而要引入 WAV 健康检查。
3. Release Signoff 可以要求真实 WAV + 人工听审证据。
4. 离线 verifier 可以验证音频 artifact 的完整性、格式和 hash。

这不是做 Suno/Udio 这类外部音乐生成，也不是做 AI 演唱。v5.0 的目标是把现有 MIDI 生成链路变成可被稳定试听、验收、交付的本地音频链路。

---

## 2. 版本目标

v5.0.0 要完成一个可落地的 Real Audio Baseline：

- Renderer Profile：明确本地渲染配置，不再只有单一 renderer.json。
- Audio Health：对 WAV 做自动体检。
- Audio Artifact Manifest：所有重要 WAV 产物都有来源 hash、renderer profile hash、文件 hash。
- Acceptance Audio Gate：acceptance suite 支持强制真实音频和人工听审。
- Release Audio Gate：Release Signoff 支持要求真实音频健康报告和 Human Review Pack evidence。
- Studio Audio Lab：面板里可以看到音频渲染、体检、问题、人工听审入口。
- Offline Verification：Release / Distribution verifier 能识别并验证真实 WAV artifact。

---

## 3. 明确不做

v5.0 不做以下内容，避免范围失控：

- 不接入 Suno、Udio、Stable Audio 等外部音乐生成平台。
- 不做歌词演唱、人声合成、AI vocal、歌手音色克隆。
- 不做自动母带、自动响度标准化、LUFS 精准分析。
- 不做 DAW 工程导出，比如 Ableton、FL Studio、Logic 工程。
- 不做 MP3/AAC/FLAC 多格式转码矩阵。
- 不做平台自动上传。
- 不允许 synthetic review 冒充人工听审。
- 不允许签核后静默改写音频包。

可以预留接口，但不能在 v5.0 半成品接入。

---

## 4. 当前基线需要继承的原则

v5.0 必须保持前面版本已经形成的工程准则：

- 本地优先，先本地验证。
- 所有核心 artifact 都有 hash / source hash / stale guard。
- 所有导出内容必须脱敏，不能暴露本机路径、token、provider 原始响应。
- 所有涉及文件路径的接口必须做 workspace 边界保护。
- 所有 ZIP verifier 必须检查重复 entry、反斜杠 entry、危险路径、hash mismatch、redaction。
- 签核后禁止静默修改，必须 reset / revoke 后才能重建。
- Provider、synthetic、manual 必须明确区分。
- release-check 必须覆盖新增主线 smoke。
- 每完成一段可验收功能就提交并推 GitHub。

## 5. v5.0 核心用户故事

### 5.1 开发者配置真实渲染环境

开发者可以在 Studio 或 CLI 配置一个 Renderer Profile，例如：

- profile name：Local FluidSynth GM
- engine：fluidsynth
- soundfont：本机 sf2/sf3 文件
- sample rate：44100
- channels：2
- output bit depth：16
- timeout seconds：60

系统可以测试该 profile：

- FluidSynth 可执行文件是否存在。
- SoundFont 文件是否存在。
- 能否用极短 MIDI 渲染出有效 WAV。
- 输出 WAV 是否能被 Audio Health 解析。

注意：导出报告中不能写本机 soundfont 绝对路径，只能写脱敏 label、engine、soundfont hash、profile hash。

### 5.2 生成歌曲后稳定渲染 WAV

用户在 Job / Project Version / Candidate / Release 里可以选择 Renderer Profile 生成 WAV。

系统必须记录：

- source song-plan hash
- source midi hash
- renderer profile hash
- renderer engine
- soundfont hash
- wav file hash
- render started_at / finished_at
- render status / error

如果 song-plan、MIDI、renderer profile、soundfont 任意一个变化，旧 WAV 必须 stale。

### 5.3 WAV 自动体检

系统对 WAV 做基础健康检查：

- 文件是否存在。
- 文件是否在 workspace 内。
- WAV header 是否有效。
- sample rate 是否符合要求。
- channels 是否符合要求。
- bit depth / sample width 是否符合要求。
- duration 是否合理。
- 是否全静音或接近全静音。
- 是否严重削波。
- peak amplitude 是否异常。
- RMS 是否过低。
- 开头/结尾是否存在长静音。
- MIDI 时长和 WAV 时长是否明显不一致。

v5.0 不要求专业 LUFS，但需要有 deterministic 的基础指标和明确 warning/fail。

### 5.4 人工听审必须绑定真实音频

Human Review Pack 在 audio-required 模式下必须包含 WAV 或可试听音频入口。

人工 response 必须记录：

- reviewer name
- listened_at
- review_mode=manual
- audio_artifact_hash
- audio_health_report_id / hash
- rating
- accepted / needs_fix / rejected
- notes
- markers

如果 WAV 被重新渲染，旧 response 必须 stale，不能继续作为 release-ready 证据。

### 5.5 Release Signoff 可以要求真实音频准出

Release Signoff 新增 gate：

- require_audio_health=true
- require_human_audio_review=true
- require_audio_artifact_current=true

这些 gate 要求：

- Release 内所有 selected/final project version 都有当前 WAV。
- 所有 WAV 都通过 Audio Health。
- 所有要求人工听审的 suite 都是 manual accepted。
- Human Review Pack source hash 当前。
- Acceptance Report source hash 当前。
- Release Export / ZIP 内音频 hash 与 report 一致。

## 6. 推荐模块设计

### 6.1 `song_agent/audio_profiles.py`

职责：

- 管理 Renderer Profile。
- 兼容现有 `.musicforge/renderer.json`。
- 提供 profile hash。
- 提供 profile test。
- 对外输出脱敏 profile summary。

建议数据目录：

```text
.musicforge/
  audio-profiles/
    profiles.json
    events.jsonl
```

RendererProfile 建议字段：

```json
{
  "profile_id": "arp-000001",
  "name": "Local FluidSynth GM",
  "engine": "fluidsynth",
  "enabled": true,
  "is_default": true,
  "engine_path": "C:\\tools\\fluidsynth\\fluidsynth.exe",
  "soundfont_path": "D:\\soundfonts\\GeneralUser.sf2",
  "sample_rate": 44100,
  "channels": 2,
  "bit_depth": 16,
  "timeout_seconds": 60,
  "created_at": "...",
  "updated_at": "..."
}
```

对外脱敏 summary：

```json
{
  "profile_id": "arp-000001",
  "name": "Local FluidSynth GM",
  "engine": "fluidsynth",
  "enabled": true,
  "is_default": true,
  "sample_rate": 44100,
  "channels": 2,
  "bit_depth": 16,
  "soundfont_sha256": "...",
  "profile_hash": "...",
  "paths_redacted": true
}
```

注意：

- 本机路径只能留在本地配置，不进入 Project Export / Release Export / Final Export / ZIP。
- 如果 soundfont 文件不存在，profile test 必须 failed。
- profile 更新后，依赖该 profile 的 WAV artifact 必须 stale。

### 6.2 `song_agent/audio_health.py`

职责：

- 只用标准库解析 WAV。
- 输出 deterministic audio health report。
- 不依赖外部音频库。

建议支持：

- PCM WAV 16-bit / 24-bit / 32-bit 基础解析。
- mono / stereo。
- duration 计算。
- sample count。
- peak。
- rms。
- clipping ratio。
- near silence ratio。
- leading silence seconds。
- trailing silence seconds。
- basic DC offset。

AudioHealthReport 建议字段：

```json
{
  "report_id": "ahr-000001",
  "status": "passed",
  "wav_sha256": "...",
  "source": {
    "job_id": "...",
    "project_id": "...",
    "version_id": "...",
    "audio_artifact_id": "..."
  },
  "format": {
    "sample_rate": 44100,
    "channels": 2,
    "sample_width_bytes": 2,
    "duration_seconds": 92.4,
    "frame_count": 4074840
  },
  "metrics": {
    "peak": 0.82,
    "rms": 0.16,
    "clipping_ratio": 0.0,
    "near_silence_ratio": 0.04,
    "leading_silence_seconds": 0.12,
    "trailing_silence_seconds": 0.3,
    "dc_offset": 0.001
  },
  "checks": [
    {
      "id": "wav_header",
      "status": "passed",
      "message": "Valid PCM WAV."
    }
  ],
  "warnings": [],
  "failures": [],
  "source_hash": "...",
  "integrity_hash": "..."
}
```

建议阈值：

- duration_seconds < 8：failed，太短。
- duration_seconds > 600：warning 或 failed，按 profile 设置。
- peak <= 0.001：failed，基本静音。
- rms <= 0.005：failed，过低。
- clipping_ratio > 0.01：failed。
- clipping_ratio > 0.001：warning。
- leading silence > 5s：warning。
- trailing silence > 8s：warning。
- MIDI duration 与 WAV duration 差距 > 10%：warning；> 25% failed。

这些阈值放到 profile 或 constants，测试要稳定。

### 6.3 `song_agent/audio_artifacts.py`

职责：

- 管理 WAV artifact manifest。
- 对 Job / Project Version / Candidate / Audition / Release 统一记录 audio artifact。
- 做 source hash 和 stale 判断。

建议 AudioArtifactManifest：

```json
{
  "artifact_id": "aud-000001",
  "kind": "project_version_audio",
  "status": "ready",
  "wav_path": "audio/song.wav",
  "wav_sha256": "...",
  "source_song_plan_hash": "...",
  "source_midi_hash": "...",
  "renderer_profile_hash": "...",
  "soundfont_sha256": "...",
  "health_report_id": "ahr-000001",
  "health_report_hash": "...",
  "created_at": "...",
  "updated_at": "..."
}
```

安全要求：

- `wav_path` 必须解析到对应 run/project/release 的安全目录下。
- 下载 WAV 前必须校验 manifest current。
- stale artifact 不能下载、不能进入 Release Signoff、不能进入 Distribution Package。
- manifest 里的路径不能被篡改成其他本机文件。

### 6.4 扩展现有 renderer

现有 renderer 已支持 FluidSynth MIDI -> WAV，但 v5.0 要把它收紧：

- 支持 profile_id。
- 使用 list argv，`shell=False`。
- timeout。
- capture stderr/stdout。
- render 后必须立刻跑 Audio Health。
- renderer error 必须脱敏。
- 不允许把 soundfont 绝对路径写入导出。

## 11. Acceptance Profile 调整

现有 profile：

- midi_smoke
- developer_manual
- release_candidate
- audio_required

v5.0 建议明确语义：

### 11.1 midi_smoke

- 不要求 WAV。
- 允许 synthetic。
- 只做开发快速检查。
- 不能作为 release-ready gate。

### 11.2 developer_manual

- 推荐 WAV。
- 允许部分 skipped，但必须显示 warning。
- 可用于日常开发试听。

### 11.3 release_candidate

- 必须覆盖 12 首 Regression Songbook。
- 必须 manual accepted。
- 如果 renderer profile 可用，必须有 WAV。
- 如果 Release Signoff 开启 `require_audio_health=true`，必须全部 WAV health passed。

### 11.4 audio_required

- 必须真实 WAV。
- renderer 不可用直接 failed。
- synthetic review 不可作为通过证据。
- 每首歌必须有 manual review response。

## 12. Regression Songbook 音频要求

12 首内置 Regression Songbook 必须覆盖：

- 不同 style。
- 不同 tempo。
- 不同 duration。
- instrumental / lyric rewrite 场景。
- dense arrangement。
- sparse arrangement。
- hook repetition。
- bass / drums / chords / melody 的基础覆盖。

v5.0 不要求每首都好听到商业级，但必须：

- MIDI 能生成。
- WAV 能渲染。
- WAV 非静音。
- 时长合理。
- 没有明显削波。
- 人工 review 明确给出 accepted / needs_fix / rejected。

## 13. 安全与完整性要求

### 13.1 路径安全

所有路径必须满足：

- 解析到 workspace 内部。
- 下载接口不可越界。
- manifest 路径不可指向任意本机文件。
- ZIP entry 不允许 `..`、绝对路径、反斜杠、重复 entry。

### 13.2 脱敏

必须扫描：

- profile summary
- audio-health report
- renderer stderr/stdout
- Project Export
- Final Export
- Release Export
- ZIP
- Human Review Pack

敏感信息包括：

- Windows drive path
- UNC path
- token / api key
- bearer token
- provider raw response
- soundfont_path
- engine_path

### 13.3 stale guard

以下变化必须让 audio artifact stale：

- song-plan.json 变化。
- song.mid 变化。
- renderer profile 变化。
- soundfont file hash 变化。
- audio-health report 被篡改。
- human review response 绑定的 audio artifact hash 不匹配。

### 13.4 签核后只读

Release / Distribution / Submission 已签核后：

- 不允许重新 render audio 覆盖旧包。
- 不允许重新 export audio summary。
- 不允许改 Human Review Pack。
- 必须 reset signoff 后才能重建。

### 14.5 Release-check v5.0 smoke

## 16. 最小验收标准

v5.0.0 不能只做到 UI 或字段。必须满足以下最低标准：

- 至少一个 fake renderer / deterministic WAV fixture 能完整跑通音频链路。
- Audio Health 能准确识别 valid / silence / clipped / malformed WAV。
- Project Version 能生成 WAV artifact manifest。
- WAV artifact stale 后不能下载、不能 signoff。
- Human Review Pack 的 manual response 绑定 audio artifact hash。
- Release Signoff 能用 `require_audio_health=true` 阻断缺失或失败音频。
- Release Signoff 能用 `require_human_audio_review=true` 阻断 synthetic-only。
- Release ZIP 离开 workspace 后 `verify-release --require-audio` 能独立验证。
- release-check 包含 v5.0 smoke。
- 全量测试通过。

## 17. Reviewer 重点检查清单

### P1 必查

- 是否仍允许 synthetic review 通过 release-ready audio gate。
- 是否有任何导出文件泄露 soundfont_path / engine_path / 本机 WAV 绝对路径。
- 是否能通过篡改 manifest path 下载任意本机文件。
- 是否能通过修改 song.mid 后继续复用旧 WAV。
- 是否能通过修改 renderer profile 后继续复用旧 WAV。
- 是否能通过篡改 audio-health.json 继续 signoff。
- 是否 verify-release 只相信 manifest.zip.entries。
- 是否签核后还能重新 export / render / zip。

### P2 必查

- malformed WAV 是否返回 failed report，而不是 CLI traceback。
- renderer 不可用时 audio_required 是否 failed。
- release_candidate 是否明确区分 manual 和 synthetic。
- Studio 是否清晰显示 skipped / failed / warning / passed。
- Windows 路径、UNC 路径是否被 redaction。

### P3 可优化

- health metric 阈值是否太苛刻。
- Audio Lab UI 是否拥挤。
- fake renderer 是否足够稳定。
- CLI 输出是否便于开发定位。

## 20. 结论

v5.0 应该是 MusicForge 从“自动化作曲工程系统”迈向“能被真实试听和验收的音乐生产系统”的分界点。

这版不追求商业级混音，也不追求 AI 演唱。它只解决一个硬问题：

生成出来的东西必须能稳定变成真实音频，并且真实音频必须经过自动体检和人工听审后，才能作为 Release 证据继续向后走。

如果这一步做扎实，后面的音频反馈、混音控制、外部 provider、平台交付都会有可靠地基。

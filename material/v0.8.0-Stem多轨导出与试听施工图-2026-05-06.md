## 1. 为什么 v0.8.0 要做 Stem

现在 MusicForge 已经具备这些能力：

- 单曲生成：SongRequest -> SongPlan -> MIDI。
- Studio 操作面板：创建任务、查看 Timeline / Tracks / Validator / Quality / Nodes。
- Provider 配置：local / provider 两种生成模式。
- 多节点编排：planner / critic / repair / builder。
- 批量生产：CSV 导入、batch launch、失败重试、导出。
- 音频渲染：整首 MIDI -> WAV，并可在 Studio 播放。
- 安全保护：access token、路径边界保护、发布检查。
- 音乐质量层：结构、hook、density、energy、tension 等质量 metadata。

下一步不要急着继续堆更复杂的 Agent 智能。当前最缺的是“产物形态”。

用户真正拿到一首歌以后，会自然需要：

- 单独下载 melody / chords / bass / drums。
- 单独试听某一轨。
- 把 MIDI stem 或 WAV stem 拿去 DAW 继续加工。
- 在批量生产时，一次性导出每首歌的 stems。
- 对比不同版本时，不只听整首，还能听到每个声部是否合理。

所以 v0.8.0 的核心目标是：把 MusicForge 从“整首歌生成器”推进到“可交付多轨工程素材的音乐生产工具”。

## 2. v0.8.0 目标

必须完成：

- 从现有 SongPlan 的 tracks 生成 per-track MIDI stems。
- 每个 stem 都有独立、可下载的 `.mid` 文件。
- 复用现有 FluidSynth 链路，把 stem MIDI 渲染为 per-track `.wav`。
- Job detail 增加 Stems 视图。
- Studio 可以查看 stem 状态、下载 MIDI、渲染 WAV、试听 WAV。
- Batch 可以批量生成 stems，并在 export.json 中带出 stem 状态。
- 所有 stem 文件访问都必须经过路径边界保护，不能让请求参数变成任意文件读取。
- 所有新接口都必须走现有 auth 保护。
- 完成 README / CHANGELOG / 版本号更新，并发布 v0.8.0。

建议完成：

- Studio 支持简单的 Solo / Mute 试听体验。
- Stem manifest 记录每轨 note_count、duration、role、instrument、MIDI/WAV 状态。
- Batch 支持只重试失败 stem 渲染。

暂不做：

- 不做 DAW 工程文件，比如 Ableton / Logic / FL Studio project。
- 不做 MP3 / FLAC / OGG，继续只支持 WAV。
- 不做真实混音台、音量自动化、pan、EQ、压缩器。
- 不做音频源分离，这里的 stem 是从 SongPlan track 渲染出来的，不是把一段混音 WAV 拆开。
- 不做交互式 MIDI 编辑器。
- 不做复杂 waveform editor。

## 4. 文件与数据结构设计

推荐新增模块：

- `song_agent/stems.py`

推荐新增测试：

- `tests/test_stems.py`
- `tests/test_server_stems.py`
- `tests/test_batch_stems.py`

推荐产物目录：

```text
runs/<job-id>/
  stems/
    manifest.json
    midi/
      melody.mid
      chords.mid
      bass.mid
      drums.mid
    audio/
      melody.wav
      chords.wav
      bass.wav
      drums.wav
```

不要把 stem 文件混在 `renders/` 根目录下。`renders/song.mid` 和 `renders/song.wav` 继续代表整首歌；`stems/` 专门代表多轨素材。

Manifest 建议结构：

```json
{
  "version": 1,
  "job_id": "demo-song",
  "source_song_plan": "data/song-plan.json",
  "created_at": "2026-05-06T00:00:00Z",
  "updated_at": "2026-05-06T00:00:00Z",
  "stems": [
    {
      "stem_id": "melody",
      "track_name": "melody",
      "role": "melody",
      "instrument": "lead",
      "midi_path": "stems/midi/melody.mid",
      "midi_exists": true,
      "audio_path": "stems/audio/melody.wav",
      "audio_exists": true,
      "audio_status": "completed",
      "audio_error": null,
      "note_count": 64,
      "duration_beats": 64.0,
      "channel": 0,
      "program": 81,
      "updated_at": "2026-05-06T00:00:00Z"
    }
  ]
}
```

Stem status 建议：

- `not_started`
- `queued`
- `running`
- `completed`
- `failed`
- `skipped`

Stem ID 规则：

- 只能由系统从 track name / role 派生，不能直接信任用户请求。
- 必须 slug 化，例如 `lead melody` -> `lead-melody`。
- 同名 track 要自动追加后缀，例如 `melody`、`melody-2`。
- API 读取 stem 文件时，只能从 manifest 中匹配 stem_id，再拼接固定目录。
- 禁止把 `../`、绝对路径、反斜杠路径当作 stem_id。

## 5. MIDI Stem 生成规则

新增能力：

- `build_stem_manifest(plan, run_dir, job_id) -> StemManifest`
- `render_stem_midis(plan, run_dir, job_id) -> StemManifest`
- `read_stem_manifest(run_dir) -> StemManifest | None`
- `render_stem_audio(run_dir, stem_ids=None, force=False) -> StemManifest`

每个 stem MIDI 应该是合法 Type-1 MIDI：

- 包含 header chunk。
- 包含 meta track。
- 包含一个 music track。
- PPQ 继续使用 `480`。
- tempo meta 与整首 song.mid 一致。
- time signature meta 与整首 song.mid 一致。
- drums 继续使用 channel 9。
- melody/chords/bass 继续使用当前 role channel 和 program。
- 每个 note 必须有 note_on / note_off 配对。
- 每个 track 必须有 EOT。

空 track 处理：

- 如果 SongPlan 正常 validate，理论上不应该有空 track。
- 但为了兼容 provider 异常输出，stem 层不要直接崩整个任务。
- 对空 track 建议标记 `skipped`，manifest 中记录 `note_count=0` 和 `audio_status=skipped`。

## 6. Job API 设计

新增 API：

### `GET /api/jobs/<job_id>/stems`

用途：读取 stem manifest。

行为：

- job 不存在：`404`
- song-plan 不存在：`409`
- manifest 不存在：返回一个 derived preview，或返回 `{"stems": [], "status": "not_started"}`。
- 推荐：如果 song-plan 存在但 manifest 不存在，可以只根据 song-plan 构造 preview，不写磁盘。

### `POST /api/jobs/<job_id>/render-stems`

用途：生成 per-track MIDI stems。

行为：

- job 不存在：`404`
- song-plan 不存在：`409`
- song-plan schema 错误：`409` 或 `400`，错误信息要清楚。
- 成功：`200`，返回 manifest。
- 重复调用：默认幂等，不重复生成不同文件名。
- 支持 body：`{"force": true}`，用于覆盖已有 stems。

### `POST /api/jobs/<job_id>/render-stem-audio`

用途：把 stem MIDI 渲染为 stem WAV。

请求 body：

```json
{
  "stem_ids": ["melody", "bass"],
  "force": false
}
```

行为：

- 如果没有 body，默认渲染所有未完成 stem。
- 如果 manifest 不存在但 song-plan 存在，可以先自动生成 stem MIDI。
- renderer 未配置：`400`
- 指定 stem_id 不存在：`404`
- 单个 stem 渲染失败：manifest 中标记该 stem `failed`，接口返回可以是 `207` 不建议使用；为保持项目当前简单风格，建议返回 `200` 并在 manifest 里体现 partial failure。
- 不要把 stem audio 失败标记为整个 job failed。

### `GET /api/jobs/<job_id>/stems/<stem_id>/midi`

用途：下载单个 stem MIDI。

行为：

- job 不存在：`404`
- stem 不存在：`404`
- MIDI 文件不存在：`404`
- content-type 使用 `audio/midi` 或 `application/octet-stream`，保持浏览器可下载。

### `GET /api/jobs/<job_id>/stems/<stem_id>/audio`

用途：下载或播放单个 stem WAV。

行为：

- job 不存在：`404`
- stem 不存在：`404`
- WAV 文件不存在：`404`
- content-type 使用 `audio/wav`。

## 7. Studio 设计

Job detail 新增 `Stems` tab。

Stems tab 必须包含：

- 顶部操作：
  - Render Stems
  - Render Stem Audio
  - Refresh
- Stem table：
  - Stem
  - Role
  - Instrument
  - Notes
  - Duration
  - MIDI
  - WAV
  - Error
  - Actions
- 每行 actions：
  - Download MIDI
  - Render Audio
  - Download WAV
  - Play / Pause
  - Solo
  - Mute

试听体验要求：

- v0.8.0 不要求实现专业混音台。
- 最低要求：每个 stem 有独立 `<audio controls>`。
- 推荐要求：
  - 点击 Solo 时暂停其它 stem，只播放当前 stem。
  - 点击 Mute 时暂停当前 stem，并把该行显示为 muted。
  - 不做多轨同步播放精度承诺，避免把浏览器播放器伪装成 DAW。

页面状态：

- 无 song-plan：显示 `SongPlan is not available yet.`
- 未生成 stems：显示 `Stems have not been rendered yet.`
- renderer 未配置：Render Stem Audio 按钮可点，但后端返回清晰错误；前端显示 renderer missing。
- 部分失败：行级展示错误，不要只在顶部显示一个笼统失败。

## 8. Batch 设计

Batch 不应该一开始就做得太复杂，但 v0.8.0 至少要能让批量任务导出 stem 状态。

BatchItem 建议新增字段：

- `stem_status`
- `stem_manifest_path`
- `stem_count`
- `stem_audio_completed_count`
- `stem_error`

状态建议：

- `not_started`
- `queued`
- `running`
- `completed`
- `partial_failed`
- `failed`
- `skipped`

新增 Batch API：

### `POST /api/batches/<batch_id>/render-stems`

用途：对 batch 中已完成且有 song-plan 的 item 生成 stems。

行为：

- batch 不存在：`404`
- batch generation running：`409`
- 没有可处理 item：`409`
- 每个 item 单独更新 stem 状态。
- 默认包含 MIDI stems 和 WAV stems 两步，还是只做 MIDI stems？
  - 建议 v0.8.0 拆开：`render-stems` 只做 MIDI，`render-stem-audio` 做 WAV。

### `POST /api/batches/<batch_id>/render-stem-audio`

用途：对 batch 中已有 stem MIDI 的 item 渲染 WAV。

行为：

- renderer 未配置：`400`
- 每个 item 单独记录成功、失败、partial_failed。
- 复用现有 batch audio runner 的并发控制，不要新开无限线程。

### `POST /api/batches/<batch_id>/render-failed-stems`

用途：只重试失败的 stem render。

### `POST /api/batches/<batch_id>/render-failed-stem-audio`

用途：只重试失败的 stem audio render。

Batch export.json 新增字段：

```json
{
  "stem_status": "completed",
  "stem_manifest": "runs/demo/stems/manifest.json",
  "stem_count": 4,
  "stem_audio_completed_count": 4,
  "stem_error": null
}
```

Studio Batch 区域新增列：

- Stem
- Stem Audio
- Stem Error

Studio Batch 操作按钮新增：

- Render Stems
- Render Stem Audio

## 9. 安全与边界

必须遵守：

- 新增 API 全部走现有 auth。
- 任何下载 API 都不能直接用请求参数拼文件路径。
- stem_id 必须从 manifest 查找后再定位文件。
- 所有文件必须位于对应 `runs/<job-id>/stems/` 下。
- 删除 job 时，stems 跟随 run_dir 一起删除。
- FluidSynth 调用继续使用 list argv 和 `shell=False`。
- manifest 不写入 provider key、token、本机敏感路径以外的无关信息。
- 错误信息不要暴露 access token、provider key。
- README 示例不要写本机私有路径。

路径安全检查建议：

- 新增 `_ensure_stem_path_is_safe(run_dir, path)`。
- `target.resolve().relative_to((run_dir / "stems").resolve())` 必须成功。
- 下载前必须确认文件存在且是文件。

## 13. 风险点

Stem ID 冲突：

- 同名 track 必须自动加后缀。
- 不能让后一个 track 覆盖前一个文件。

Provider 输出异常：

- provider 可能返回奇怪 track 名、空 notes、未知 role。
- stem 层要尽量降级处理，不能因为一个空 track 让整首 job 无法查看。

音频渲染耗时：

- stem WAV 渲染会比整首 WAV 更耗时。
- 不要无限并发调用 FluidSynth。
- 默认顺序渲染，batch 内继续遵守 max_concurrency。

浏览器多轨同步：

- `<audio>` 标签无法保证专业级多轨同步。
- v0.8.0 只承诺单轨试听和简单 Solo / Mute。
- 真正同步播放和混音台应放到后续版本。

路径安全：

- 这是本版本最容易出现 P1 的地方。
- 所有下载 API 必须以 manifest 为索引，不能直接拼用户输入。

Batch 恢复：

- 服务重启时，queued/running stem 状态必须恢复为 failed/interrupted。
- 不要让 Batch 永远挂在 running。

## 15. v0.9.0 初步方向

# v9.3.0 Trust Operations Hub 事故知识库与回归防线施工图

> 当前稳定基线：v9.2.1  
> v9.2.1 已修复 Incident closeout 可被伪造 `status: passed` evidence 放行的问题。  
> v9.3.0 的目标，是把 v9.2 的事故关闭闭环继续推进：关闭不是终点，关闭后的经验必须沉淀成知识、规则、回归检查和复发预警。

---

## 0. 给开发的话

v9.2.1 已经能做到：

```text
Hub blocker -> Incident -> Triage -> Plan -> Evidence -> Verify Fix -> Closeout -> Incident ZIP -> Hub gate
```

这解决了“问题能不能安全关闭”的问题。  
但还有一个更大的运营缺口：

```text
同类问题下次会不会再次发生？
这个事故修复经验是否能复用？
它是否应该变成 release-check 回归？
它影响了哪些链路？
它是不是过去几版反复出现？
Hub signoff 能不能要求高危事故已有回归防线？
```

所以 v9.3.0 要做：

```text
Trust Operations Incident Knowledge Base + Regression Guard
```

这版的核心不是再多一个 package，而是建立“事故复盘 -> 知识条目 -> 回归防线 -> 复发检测 -> Signoff gate”的闭环。

你要坚持几条红线：

- 只从已关闭、非 stale、closeout passed、证据绑定有效的 Incident 生成知识条目。
- 不能从伪造/失败/过期 evidence 生成知识。
- 回归检查不能自动修改业务状态，只能报告 pass/fail/manual_required。
- Hub signoff gate 可以要求 critical/high incident 有 regression guard。
- Knowledge / Regression Guard ZIP 必须固定结构、可离线验、可防 full-resign。
- 所有自由文本继续 redaction。

## 2. 为什么需要 v9.3.0

v9.2.1 解决的是单次事故闭环：

```text
这次事故是否已修？
这次 closeout 是否可信？
这次 Hub gate 是否能绑定 incident closeout？
```

但真实项目继续推进时，会遇到这些问题：

1. 同类错误复发
   - 多 target verifier 又只检查第一条。
   - closeout 又信了 summary 自证。
   - ZIP allow-list 又漏了 extra entry。

2. 事故复盘无法复用
   - 关闭时的原因、证据、修复方式只留在 Incident 里。
   - 下一次开发不知道这个坑已经踩过。

3. release-check 不能自动吸收事故经验
   - 如果 reviewer 手动发现 P1，但没有转成 smoke，后续可能回归。

4. Hub signoff 没法要求“事故已形成防线”
   - 事故可以关闭，但未必有 regression guard。
   - critical/high 事故关闭后应当要求防复发。

v9.3.0 要建立：

```text
Closed Incident
  -> Knowledge Entry
  -> Regression Guard
  -> Guard Run Report
  -> Recurrence Detection
  -> Hub Signoff Evidence
```

## 4. 非目标

v9.3.0 不做这些：

- 不接外部知识库。
- 不接 Jira / GitHub Issues。
- 不调用 LLM / provider 总结事故。
- 不自动生成任意 Python 测试代码并执行。
- 不自动修改 `release_check_matrix.py` 后提交。
- 不做真实后台定时任务。
- 不自动 approve / signoff / reset。
- 不自动关闭新 incident。
- 不把本地 deterministic regression guard 冒充第三方审计。
- 不引入数据库。
- 不引入外部依赖。

允许做：

- 本地 Knowledge Base。
- 本地 Regression Guard Spec。
- Deterministic guard runner。
- 手动将 guard 提升为 release-check smoke 的建议。
- 导出/ZIP/离线 verifier。
- Studio 面板。

## 8. Knowledge Entry 生成规则

只允许从这些 Incident 生成 entry：

- `status == closed`
- `stale == false`
- closeout report `status == passed`
- Incident verification report `status == passed`
- Incident evidence binding integrity passed
- Hub verification binding current

拒绝：

- open / triaged / in_progress / waiting_verification / verified 但未 closed。
- archived 但 verification 不 current。
- closeout 缺 evidence。
- evidence 是 forged / package_type mismatch / component mismatch。
- incident ZIP verifier failed。
- incident source stale。

生成 classification：

| Incident category / check_id | root_cause | failure_mode |
| --- | --- | --- |
| `delivery_verification_missing` | `missing_external_verification_report` | `external_report_coverage` |
| `hub_verification_blocker` + `component_coverage` | `incomplete_component_coverage` | `same_type_multi_component_coverage` |
| ZIP path safety failed | `unsafe_zip_entry` | `zip_safety_regression` |
| redaction failed | `sensitive_payload_leak` | `redaction_regression` |
| stale evidence | `stale_external_evidence` | `stale_guard_regression` |
| signed mutation blocked | `immutable_state_mutation_attempt` | `immutability_guard` |

如果无法分类：

```text
root_cause = unknown
failure_mode = manual_required
```

`manual_required` 也可以生成 knowledge entry，但不能自动生成 guard，只能生成 recommendation。

## 9. Regression Guard 类型

第一版只做 deterministic guard，不跑动态代码。

支持 guard_type：

```text
external_report_coverage
external_report_binding
zip_safety_regression
redaction_regression
stale_evidence_guard
immutability_guard
incident_closeout_guard
manual_required
```

### 9.1 external_report_coverage

检查：

- Hub delivery evidence rows。
- external verification reports。
- component_type + component_id 覆盖。
- missing / duplicate / extra / mismatch。

这是 v9.1.1 / v9.2.1 的核心经验。

### 9.2 external_report_binding

检查：

- evidence package_type。
- status。
- zip_sha256。
- zip_size_bytes。
- manifest_hash。
- source_hash。
- verification report hash。

用于防止 v9.2.0 的 forged evidence 问题。

### 9.3 zip_safety_regression

检查：

- duplicate entry。
- backslash entry。
- dangerous path。
- `.MusicForge` 大小写变体。
- nested zip。
- manifest spoof。
- extra entry。

### 9.4 redaction_regression

检查：

- token。
- `sk-...`
- GitHub token。
- Bearer token。
- Windows drive path。
- UNC path。
- local username path。

### 9.5 stale_evidence_guard

检查：

- verification report 的 zip/hash 是否仍匹配当前 package。
- Hub report source 是否变化。
- Incident Board source 是否变化。

### 9.6 immutability_guard

检查：

- signed state 不允许 refresh/export/zip。
- 删除 signoff 文件不能解锁。
- history/event log 仍能判定 signed。

### 9.7 incident_closeout_guard

检查：

- blocking/high/critical incident 关闭必须有 valid evidence。
- evidence 必须绑定当前 Hub verification。
- closeout 必须有 event log 支撑。

Full-resign 回归：

- 把 entry severity 从 high 改 low，重签全部，仍失败。
- 删除 guard，重签 summary，仍失败。
- 把 failed guard run 改 passed，重签全部，仍失败。
- 把 recurrence open 改 closed，重签全部，仍失败。
- 替换 source summary，重签全部，但外部 Incident verification 不匹配，失败。
- 插入 benign extra txt，失败。
- manifest zip entries spoof，失败。

## 15. Recurrence Detection

第一版做 deterministic matching：

匹配条件：

- `classification.failure_mode` 相同。
- 当前 open incident 的 `category` 相同。
- 当前 open incident 的 `component_type` 相同。
- 当前 Hub blocker check_id 与 entry source check_id 相同或同类。

输出：

```json
{
  "matches": [
    {
      "entry_id": "tok-000001",
      "incident_id": "inc-000009",
      "match_type": "same_failure_mode",
      "severity": "high",
      "blocking": true,
      "status": "open"
    }
  ]
}
```

如果 matched open blocking incident > 0：

- recurrence report `status=failed`。
- Knowledge verifier `--require-no-open-recurrence` failed。

## 23. 关键风险

### 风险 1：Knowledge 从不可信 incident 生成

必须要求 Incident verification passed，且 evidence binding valid。  
不要从 raw incident summary 直接生成。

### 风险 2：Guard run 只看 knowledge 自己的 summary

Guard run 必须重新读取当前 Hub / Incident / delivery evidence，不能只看知识包自证。

### 风险 3：full-resign 把 failed guard run 改成 passed

Verifier 必须从 guard spec + source 重新推断 run 是否合理。

### 风险 4：隐藏 entry 被 refresh 恢复

参考 v4.9.1 的经验：hidden 状态必须保留。

### 风险 5：Hub gate 只信 Knowledge report

Hub gate 必须同时需要 Knowledge ZIP + Knowledge verification report，并绑定 Incident verification + Hub verification。

### 风险 6：回归防线变成自动改代码

v9.3 不自动修改 release-check 源码。  
只输出 suggested release-check candidate。

## 25. 给开发的最后提醒

v9.3 的核心价值是“防复发”。

如果 v9.2 是：

```text
事故已经修完了吗？
```

那么 v9.3 是：

```text
这个事故还会不会再犯？
如果再犯，系统能不能立刻发现？
```

不要为了“看起来自动化”去生成不可控代码。  
先做稳定、确定性、可解释、可离线验证的 regression guard。  
只要这条线做扎实，后面 v9.4 才能继续做事故趋势、SLO、运营周报或自动创建修复计划。

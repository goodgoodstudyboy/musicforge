# MusicForge 后端能力逐步推进计划

日期：2026-05-05

## 0. 当前判断

MusicForge 现在已经有了本地操作面板和最小后端，但它还不是完整的音乐生产系统。

当前版本完成的是“浏览器面板能调用现有 deterministic MIDI MVP”的闭环。它证明了本地 web 工作台路线可行，也给后续功能提供了统一入口。但 provider、批量任务、多 agent 编排、音频渲染、暂停恢复、重试保护等后端能力还没有真正完成。

所以后续开发不能误以为“面板搭好了，后端就完成了”。正确理解应该是：

- v0.1.1：面板壳 + 最小 job 后端 + MIDI MVP。
- v0.1.2：补齐 job 管理、预览视图和恢复能力。
- v0.2.0：接入 provider 配置和模型调用。
- v0.3.0：进入多 agent 音乐生成后端。
- v0.4.0：批量生产。
- v0.5.0：音频渲染和播放器。
- v0.6.0：运行保护、权限、安全发布。

## 3. 总体开发原则

后续开发必须遵守：

1. 每个阶段都能本地运行和本地测试。
2. 不破坏当前 CLI。
3. 不破坏当前面板的基本 job 创建流程。
4. 所有 job 输入、状态、日志、产物都要落盘。
5. 所有外部 provider 能力必须可关闭。
6. 默认模式仍然是无网络 deterministic。
7. 所有模型输出必须走 schema 校验。
8. 所有预期错误要返回 JSON error 或 CLI `error: ...`，不能让用户看到 traceback。
9. 运行产物不能提交 Git。
10. provider key、token、本机私有路径不能进入仓库。
11. 每个阶段做小提交，不要一次性塞完所有能力。

### 3.1 GitHub 推送准则

后续开发必须采用“小功能完成就提交并推送”的节奏。不要等一个大版本全部写完才推远端。原因很简单：这个项目正在快速变复杂，远端 GitHub 是最重要的备份点和回滚点。

“合适的功能单元”定义：

- 一个 API 能完整工作，并且有测试。
- 一个后端模块能独立通过测试。
- 一个 UI 面板能力能从浏览器完成闭环。
- 一个 bug 被复现、修复、测试覆盖。
- 一个阶段的文档、README、CHANGELOG 更新完成。

不算合适功能单元的情况：

- 只写了一半接口，前端还调用不了。
- 测试失败。
- 产物目录、临时文件、密钥文件还在工作区。
- 只是临时 debug print。
- schema 改了一半，旧 CLI 已经坏了。
- 面板按钮已经出现，但后端 API 没有实现。

每完成一个合适功能单元，开发必须按下面流程执行：

```powershell
git status --short --branch
python -m pytest -q
git diff --check
git diff --stat
```

如果这个功能涉及 CLI，额外运行：

```powershell
python -m song_agent.cli examples\song_request.json --out runs\local-check --force
```

如果这个功能涉及面板，额外运行：

```powershell
python -m song_agent.cli serve --host 127.0.0.1 --port 8787
```

然后浏览器手工验证相关功能。验证通过后提交：

```powershell
git add <changed-files>
git commit -m "feat: describe the completed capability"
git push origin master
git status --short --branch
```

如果是 bug fix：

```powershell
git commit -m "fix: describe the fixed behavior"
git push origin master
```

如果只是测试：

```powershell
git commit -m "test: cover the behavior"
git push origin master
```

如果只是文档：

```powershell
git commit -m "docs: describe the workflow"
git push origin master
```

推送后必须确认：

```powershell
git status --short --branch
git log --oneline -3
```

期望结果：

- `git status` 不再显示 `ahead`。
- 工作区干净。
- 最新提交在本地日志顶部。

如果 `git push origin master` 失败：

- 不要说已经备份。
- 不要把 token 拼到 remote URL。
- 不要把 token 写入 README、material、commit message。
- 先检查网络和远端地址。
- 如果确实是 GitHub 连接问题，明确报告“本地已提交，远端未推送”。

### 3.2 Tag 和 Release 准则

普通功能单元：提交并推送即可，不需要打 tag。

阶段完成：打版本 tag，例如：

```powershell
git tag v0.1.2
git push origin v0.1.2
```

适合打 tag 的节点：

- `v0.1.1`：本地面板 MVP。
- `v0.1.2`：job 管理和预览。
- `v0.2.0`：provider 配置和模型接入。
- `v0.2.1`：pause/resume/cancel/retry。
- `v0.3.0`：多 agent 后端。
- `v0.4.0`：batch。
- `v0.5.0`：音频渲染。
- `v0.6.0`：安全和鉴权。

每次打 tag 前必须：

```powershell
python -m pytest -q
git status --short --branch
```

并更新：

- `CHANGELOG.md`
- `README.md`，如果命令、面板、API 或运行方式有变化。

### 3.3 Secret 和本机信息检查

每次推送前都要做基础扫描：

```powershell
rg -n "C:\\\\Users|token|ghp_|github_pat_|sk-|api_key|access_token" README.md CHANGELOG.md material song_agent tests pyproject.toml
```

允许出现的情况：

- 文档里讲 token 安全准则。
- 代码里出现字段名 `api_key`、`access_token`。

不允许出现的情况：

- 真实 token。
- 本机私有 token 文件路径。
- 带 token 的 remote URL。
- 个人账号写进公开发布文档。

## 6. v0.2.1：真实 pause/resume/cancel 和 retry

- `pause_requested`
- `cancel_requested`
- `retry_count`
- `next_retry_at`
- `last_error`
- `started_at`
- `finished_at`
- `heartbeat_at`

API：

- [ ] `POST /api/jobs/<job_id>/pause`
- [ ] `POST /api/jobs/<job_id>/resume`
- [ ] `POST /api/jobs/<job_id>/cancel`
- [ ] `POST /api/jobs/<job_id>/retry`

- pause 在阶段边界生效。
- failed job 可以 retry。
- retry 不能覆盖原始输入。

- [ ] 长时间无 heartbeat 标记为 stalled。

- [ ] provider 网络错误可以进入 waiting_retry。

### 16.4 Timeline view 输出结构

输入来自 `song-plan.json`：

```json
{
  "title": "Rainy Convenience Store",
  "tempo_bpm": 92,
  "meter": "4/4",
  "sections": [
    {
      "name": "intro",
      "start_bar": 1,
      "bars": 4,
      "chords": ["Cmaj7", "Am7", "Dm7", "G7"]
    }
  ]
}
```

输出建议：

```json
{
  "title": "Rainy Convenience Store",
  "tempo_bpm": 92,
  "meter": "4/4",
  "total_bars": 32,
  "estimated_seconds": 83.48,
  "sections": [
    {
      "index": 0,
      "name": "intro",
      "start_bar": 1,
      "end_bar": 4,
      "bars": 4,
      "start_beat": 0,
      "end_beat": 16,
      "estimated_start_seconds": 0.0,
      "estimated_end_seconds": 10.43,
      "chords": ["Cmaj7", "Am7", "Dm7", "G7"]
    }
  ]
}
```

计算规则：

- 第一版只支持 `4/4` 精确计算。
- `beats_per_bar` 从 meter 前半部分解析，例如 `4/4` -> 4。
- `seconds_per_beat = 60 / tempo_bpm`。
- `start_beat = (start_bar - 1) * beats_per_bar`。
- `end_beat = start_beat + bars * beats_per_bar`。
- `estimated_start_seconds = start_beat * seconds_per_beat`。
- `estimated_end_seconds = end_beat * seconds_per_beat`。
- `total_bars = max(section.start_bar + section.bars - 1)`。

边界：

- `tempo_bpm` 缺失或非法时返回 JSON error，不要 traceback。
- `sections` 为空时返回空 sections 和 `total_bars=0`。
- meter 非标准时先按 `4/4` fallback，并在 view 中给 `warnings`。

可选 warnings：

```json
{
  "warnings": ["Unsupported meter 7/8; timeline estimated with 4 beats per bar."]
}
```

### 16.5 Tracks view 输出结构

输入来自 `song-plan.json`：

```json
{
  "tracks": [
    {
      "name": "Melody",
      "instrument": "lead synth",
      "notes": [
        {"pitch": 64, "start_beat": 0, "duration_beats": 1, "velocity": 90}
      ]
    }
  ]
}
```

输出建议：

```json
{
  "track_count": 4,
  "note_count": 256,
  "tracks": [
    {
      "index": 0,
      "name": "Melody",
      "instrument": "lead synth",
      "note_count": 64,
      "pitch_min": 60,
      "pitch_max": 76,
      "start_beat_min": 0,
      "end_beat_max": 128,
      "average_velocity": 88.4,
      "density_notes_per_bar": 2.0
    }
  ]
}
```

计算规则：

- `note_count` 是 notes 数量。
- `pitch_min/max` 只统计有 pitch 的 note。
- `end_beat = start_beat + duration_beats`。
- `average_velocity` 缺省 velocity 按 90。
- `density_notes_per_bar = note_count / total_bars`，没有 total_bars 时返回 null。

边界：

- 空 tracks 返回 `track_count=0`、`note_count=0`。
- 某个 track notes 为空，pitch 字段为 null。
- 非法 note 不在 view 层吞掉 schema 错误；如果 plan 已经通过 schema，则 view 可假设字段存在。

### 16.10 delete 行为和安全边界

API：

```text
POST /api/jobs/<job_id>/delete
```

建议第一版 delete 的语义：

- 只允许删除非 running job。
- running job 返回 409，提示先 cancel。
- 删除 job 的 run directory。
- 从内存 `self.jobs` 移除。
- 删除前验证路径必须在 `runs/` 目录内。

安全规则：

- 必须使用 `Path.resolve()`。
- `run_dir.resolve()` 必须位于 `runs_dir.resolve()` 内。
- 不能删除 `runs_dir` 本身。
- 不能删除空路径。
- 不能跟随用户传入的任意路径。
- Windows 上使用 PowerShell 删除时不能字符串拼接；代码里用 Python `shutil.rmtree` 也要先做路径边界校验。

伪代码：

```python
def _ensure_run_dir_is_safe(self, run_dir: Path) -> Path:
    base = self.runs_dir.resolve()
    target = run_dir.resolve()
    if target == base:
        raise ValueError("Refusing to delete runs directory.")
    if base not in target.parents:
        raise ValueError("Refusing to delete outside runs directory.")
    return target
```

响应：

```json
{
  "ok": true,
  "deleted": true,
  "job_id": "demo"
}
```

测试：

- completed job 可以 delete。
- delete 后 `GET /api/jobs/<id>` 返回 404。
- delete 后目录不存在。
- running job delete 返回 409。
- 构造 output_dir 指向 runs 外时 delete 返回错误，不删除外部目录。

### 16.11 cancel 行为

API：

```text
POST /api/jobs/<job_id>/cancel
```

第一版行为：

- queued job：立即变成 `cancelled`。
- completed job：返回 409，不允许 cancel。
- failed job：返回 409，不允许 cancel。
- cancelled job：幂等返回 ok。
- running job：设置 `cancel_requested=true`，message 说明会在阶段边界停止。

当前 deterministic pipeline 很短，running cancel 可能来不及生效。v0.1.2 可以先接受这个现实，但状态字段要正确。

响应示例：

```json
{
  "ok": true,
  "job": {
    "job_id": "demo",
    "status": "cancelled",
    "cancel_requested": true
  }
}
```

测试：

- queued job cancel 后不执行。
- completed job cancel 返回 409。
- unknown job 返回 404。

如果当前架构一创建 job 就马上启动线程，测试 queued cancel 比较难。可以先实现：

- `JobStore.create_job(payload, start_immediately=True)`。
- 测试里传 `start_immediately=False` 创建 queued job。

但不要把这个测试 helper 暴露给前端。

### 16.12 startup recovery 状态转换表

server 启动时扫描 `runs/*/data/job-state.json`。

状态转换建议：

| 旧状态 | 新状态 | 原因 |
| --- | --- | --- |
| completed | completed | 已完成，正常恢复 |
| failed | failed | 已失败，正常恢复 |
| cancelled | cancelled | 已取消，正常恢复 |
| interrupted | interrupted | 已中断，正常恢复 |
| queued | interrupted | 上一个 server 已退出，不会自动继续 |
| running | interrupted | 上一个 server 已退出，不能继续显示 running |
| waiting_retry | interrupted | v0.1.2 暂不恢复 retry |
| paused | interrupted | v0.1.2 暂不恢复 paused |

interrupted job 字段：

```json
{
  "status": "interrupted",
  "step": "interrupted",
  "message": "This job was interrupted by a previous server shutdown.",
  "error": "Job was running when the server stopped."
}
```

要求：

- 转换后写回 `job-state.json`。
- 不删除已有产物。
- 如果已经有 `song-plan.json` 或 `song.mid`，artifacts 仍可发现。

测试：

- 手工写一个 running job-state。
- 启动 server。
- `/api/jobs` 返回 interrupted。
- 文件中的 job-state 也被更新为 interrupted。

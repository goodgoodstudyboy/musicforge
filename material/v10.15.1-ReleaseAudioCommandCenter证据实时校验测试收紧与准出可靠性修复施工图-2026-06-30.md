# v10.15.1 Release Audio Command Center 证据实时校验、测试收紧与准出可靠性修复施工图

## 0. 给开发的话

v10.15.0 已经把音频准出链路整合成 Release Audio Command Center，这是方向正确的一大步。但 reviewer 复核时发现一个需要继续收紧的点：当前核心安全边界主要在 offline verifier / Release gate / GA gate 中闭合，而 Command Center 的 `refresh` / `inventory` 阶段对外部 evidence 的判断偏轻，更多依赖已有 verification report。

这不构成 v10.15.0 的发布阻断，因为真正准出路径会重新跑 verifier。但从产品体验和长期可靠性看，Command Center 作为“总控台”，它的页面状态也应该尽量接近真实准出结果，不能让用户先看到 ready，等到导出或签核时才发现底层 evidence 已 stale 或 verification report 是旧的。

v10.15.1 的目标是：**把 Command Center 从“证据汇总器”收紧成“实时可信的证据总控台”。**

这版不要做新业务功能，不要新增签核，不要新增音乐处理。只做硬化、测试和可靠性修复。

## 2. Reviewer 发现的问题与判断

### 2.1 P1 候选：Command Center refresh 阶段没有充分实时反查底层 evidence

当前代码路径大致是：

- `ReleaseAudioCommandCenterStore.refresh()`
- `_build_documents()`
- `_component_row()`

`_component_row()` 现在主要检查：

- ZIP 路径存在
- verification report 路径存在
- verification report status 是 `passed`
- verification report 的 `zip_sha256` 等于当前 ZIP hash

真正严格的 runtime verification 在：

- `verify_release_audio_command_center_package()`
- Release signoff gate
- GA readiness verifier

这意味着：

- 页面 inventory 可能短暂显示 ready。
- 但导出验证或签核时失败。

这不是安全绕过，因为 gate 仍会挡住；但作为总控台，体验和语义不够严谨。

v10.15.1 应该把这点补上。

### 2.2 P2：缺少独立 Store / verifier / CLI / Server 单测文件

当前 v10.15 的核心覆盖在：

- `tests/test_release_check.py::test_v1015_release_audio_command_center_smoke`
- `tests/test_release_check_matrix.py`
- `tests/test_webui.py`

这能覆盖整体链路，但不利于后续维护。

施工图 v10.15.0 要求过独立文件：

- `tests/test_release_audio_command_center.py`
- `tests/test_server_release_audio_command_center.py`
- `tests/test_cli_release_audio_command_center.py`

实际未补齐。v10.15.1 应该补上，尤其是 verifier 攻击面和 runbook 边界。

### 2.3 P3：Readiness 状态维度偏粗

当前 readiness 更接近：

- ready
- blocked

但总控台需要更清晰地区分：

- `missing`
- `stale`
- `verification_failed`
- `runtime_failed`
- `blocked`
- `manual_required`
- `ready`

这对 UI 和 gap plan 都很关键。

## 5. 具体改动一：实时 evidence runtime verification

### 5.1 新增内部函数

在 `song_agent/release_audio_command_center.py` 中新增或重构：

```python
def _component_runtime_status(
    key: str,
    zip_path: Path | str | None,
    verification_report_path: Path | str | None,
    evidence: dict[str, Any],
) -> dict[str, Any]:
    ...
```

输出建议：

```json
{
  "component_key": "timeline",
  "zip_present": true,
  "verification_report_present": true,
  "verification_report_integrity": "passed",
  "verification_report_status": "passed",
  "zip_binding": "passed",
  "runtime_verification_status": "passed",
  "runtime_manifest_hash": "...",
  "runtime_blockers": [],
  "status": "ready",
  "readiness": "ready",
  "message": "Evidence is current and runtime verification passed."
}
```

### 5.2 调用底层 verifier

Command Center refresh 阶段应复用 `release_audio_command_center_verifier.py` 里的 `_runtime_verify()` 逻辑，或抽一个 public helper，避免复制验证参数。

建议新增：

```python
from song_agent.release_audio_command_center_verifier import verify_command_center_component
```

或者将 `_runtime_verify()` 改成非私有：

```python
def verify_release_audio_command_center_component(...)
```

注意：如果只是为了 store 内部使用，仍可以保留私有，但要避免在两个文件复制逻辑。

### 5.3 状态判定规则

组件状态：

| 条件 | status | readiness |
|---|---|---|
| ZIP 缺失 | missing | missing |
| verification report 缺失 | missing | missing |
| verification report integrity failed | blocked | verification_failed |
| verification report zip hash 不匹配 | stale | stale |
| runtime verifier failed | blocked | runtime_failed |
| runtime manifest hash 与 report manifest hash 不匹配 | stale | stale |
| report passed + runtime passed + fingerprint match | ready | ready |

### 5.4 不要吞掉底层错误

当前 `_component_row()` 把异常变成 blocked message 是合理的，但需要保留：

- `runtime_blockers`
- `runtime_failed_count`
- `verification_report_hash`
- `zip_sha256`
- `manifest_hash`

不要只写一句异常字符串。

### 6.1 Backward compatibility

旧 v10.15.0 Command Center ZIP 的 verifier 可以不兼容，因为 v10.15 还不是长期归档标准；但如果实现成本不高，verifier 可允许缺 `runtime` 时 warning。

建议 v10.15.1 的 verifier 对 v10.15.1 新 ZIP 严格要求 runtime 字段。

## 7. 具体改动三：Readiness Matrix 细化

当前 readiness row 建议扩展：

```json
{
  "component_key": "timeline",
  "required": true,
  "readiness": "runtime_failed",
  "severity": "blocking",
  "message": "Timeline runtime verification failed.",
  "verification_status": "passed",
  "runtime_status": "failed",
  "next_action": {
    "action_type": "safe_rebuild_or_manual",
    "label": "Rebuild Timeline package and verification report.",
    "source_module": "release_audio_timeline"
  }
}
```

状态建议：

- `ready`
- `missing`
- `stale`
- `verification_failed`
- `runtime_failed`
- `manual_required`
- `not_required`

### 7.1 Gap Plan 排序

Gap Plan 应按以下优先级排序：

1. `runtime_failed`
2. `stale`
3. `verification_failed`
4. `missing`
5. `manual_required`
6. warning

这样用户看到的是最需要处理的证据问题。

## 8. 具体改动四：Runbook 收紧

当前 runbook safe actions 包括：

- refresh command center
- export command center
- build zip
- verify zip

v10.15.1 要补两个保护：

### 8.1 Runtime failed 时 export / zip 是否允许

建议：

- blocked report 仍允许 export / zip，因为它有诊断价值。
- 但 ZIP manifest 必须标明 `readiness=blocked`。
- `verify --require-ready` 必须 failed。
- `verify` 不带 `require-ready` 可以 passed，但 summary status 是 blocked。

### 8.2 run-safe 结果必须保留 blocked context

`runbook-results.json` 里每个 action 应记录：

- action status
- command center readiness before
- command center readiness after
- blocked components

避免只看到 `completed`，却不知道 completed 后仍 blocked。

## 9. 具体改动五：Offline verifier 收紧

`release_audio_command_center_verifier.py` 要补：

1. runtime 字段完整性检查。
2. fingerprint.runtime_status 绑定检查。
3. verification summary runtime_status 绑定检查。
4. readiness matrix 与 inventory runtime status 一致性。
5. gap plan 与 readiness matrix 一致性。
6. runbook manual actions 与 gap plan 一致性。

新增 checks：

```text
release_audio_command_center_runtime_status_present
release_audio_command_center_runtime_status_binding
release_audio_command_center_readiness_runtime_binding
release_audio_command_center_gap_plan_runtime_binding
release_audio_command_center_runbook_gap_binding
```

### 9.1 full-resign 攻击回归

新增攻击：

- 篡改某个 component 的 runtime_status 为 passed。
- 同步重算 inventory、readiness、gap plan、report、manifest。
- 不改外部底层 evidence。
- verifier 必须 failed。

现有 full-resign 是改 action queue fingerprint；这次要补 runtime status 语义攻击。

## 10. 具体改动六：Release / GA gate 明确 current evidence

当前 Release gate 已通过 `verify_release_audio_command_center_package(... require_ready=True, **evidence)` 反查外部 evidence。

v10.15.1 要补测试确认：

- 传旧 Command Center ZIP + 新底层 evidence -> 409。
- 传新 Command Center ZIP + 旧 verification report -> 409。
- 传伪造 GA report + 重算 integrity -> verifier failed。

如果代码已有，不必大改，只补测试。

## 18. 验收标准

v10.15.1 完成必须满足：

1. Command Center refresh 能发现 stale verification report。
2. Command Center refresh 能发现 runtime verifier failed。
3. Studio readiness 不再把 stale/runtime failed evidence 显示为 ready。
4. Gap Plan 能给出明确下一步。
5. run-safe 不执行 manual/signoff/reset/provider/music edit。
6. offline verifier 能挡 runtime status full-resign 攻击。
7. Release signoff gate 能挡旧 Command Center ZIP。
8. GA readiness verifier 能挡 forged Command Center / forged GA report。
9. 独立 Store / CLI / Server 测试文件已补。
10. v10/latest/ga release-check 全绿。
11. 工作区干净，版本一致。

## 19. Reviewer 复查重点

开发完成后，reviewer 重点看：

- `_component_row()` 是否还只看 verification report status。
- Command Center refresh 是否真的调用底层 runtime verifier。
- runtime_failed 是否能进入 inventory / readiness / gap plan。
- `verify-release-audio-command-center-package --require-ready` 是否挡住 stale/runtime failed。
- Release gate 是否要求当前外部 evidence。
- GA verifier 是否要求当前外部 evidence。
- 是否补了独立测试文件，而不是只改 release-check smoke。
- ZIP allow-list 是否仍固定。
- redaction 是否仍覆盖新增 runtime message。

## 20. 一句话总结

v10.15.0 做了“整合入口”，v10.15.1 要做“可信入口”。这版的价值不是新功能，而是让 Command Center 页面、CLI、offline verifier、Release gate、GA gate 对同一套证据给出一致结论。

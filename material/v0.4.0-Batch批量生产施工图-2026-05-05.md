# MusicForge v0.4.0 施工图：Batch 批量生产与批次控制台

当前稳定版本是 `v0.3.2`。它已经补齐了 node retry 的关键问题：

- `harmony_planner` retry 会正确影响 `arrangement_planner -> critic -> repair -> song_plan_builder`。
- node retry API 已改为后台线程，返回 `202 Accepted`。
- 单 job 的生成、节点查看、节点重试、恢复和 provider 脱敏已经足够支撑批量生产。

因此 `v0.4.0` 可以进入 Batch 批量生产阶段。

## 1. v0.4.0 一句话目标

让用户在 MusicForge Studio 里导入 CSV，一次生成多首歌，支持并发控制、暂停、继续、失败重试、导出报告，并且每个 batch item 都能关联到现有 job 详情。

```text
CSV -> Batch -> Batch Items -> Jobs -> SongPlan/MIDI/Nodes -> Export
```

## 2. 为什么现在做 batch

以前不能做 batch 的原因：

- 单 job 状态机还不完整。
- provider 配置和脱敏还没完成。
- multinode 没有可观察节点。
- node retry 只是 501 占位。
- retry harmony 时会出现 chord track 不一致。

现在这些已经解决。继续做 batch 是合理的，因为 batch 复用现有 job runner，不需要重写音乐生成主链路。

## 3. v0.4.0 不做什么

不要扩大范围。

本版本不做：

- 不做 WAV/MP3 音频渲染。
- 不做专辑级母带。
- 不做自动发布到外部平台。
- 不做复杂任务队列服务。
- 不引入 Celery、Redis、数据库。
- 不做多用户权限。
- 不做云端同步。
- 不做任意 DAG batch。

继续坚持本地化优先，标准库优先，可测试优先。

## 4. 最终用户体验

Studio 增加一个 `Batch` tab。

用户流程：

1. 打开 Studio。
2. 进入 Batch tab。
3. 粘贴 CSV 或上传 CSV。
4. 设置 batch name、generation mode、pipeline mode、max concurrency。
5. 点击 Import。
6. 页面显示批次和 item 预览。
7. 点击 Launch。
8. 面板显示 item 状态变化。
9. 某个 item 失败后，可点击 Retry Failed。
10. 完成后点击 Export，得到 batch 报告。
11. 每个 item 可以跳转到对应 job detail 查看 nodes、timeline、tracks、validator、MIDI。

## 6. 持久化目录

Batch 元数据放在：

```text
.musicforge/batches/<batch_id>/
  batch.json
  items.json
  export.json
  events.jsonl
```

说明：

- `.musicforge/` 已经被忽略，不会提交到 GitHub。
- `runs/` 继续只放单 job 产物。
- batch item 只保存 `job_id` 和 `output_dir` 引用，不复制 job 产物。

### 6.1 为什么不放 runs/

`runs/` 的职责是单个生成任务的产物目录。batch 是组织层、调度层、索引层。如果混在 `runs/` 里，后面删除 batch、导出 batch、恢复 batch 都会和 job 产物混在一起。

推荐边界：

```text
.musicforge/batches/   批次状态、批次 item、批次 export
runs/                  每首歌的实际生成产物
```

## 8. 状态机

### 8.1 Batch status

允许状态：

```text
draft
queued
running
paused
completed
completed_with_errors
cancelled
failed
```

建议规则：

- `draft`：已导入，未 launch。
- `queued`：准备启动。
- `running`：至少有一个 item queued/running。
- `paused`：暂停启动新的 item，已 running 的 job 不强杀。
- `completed`：全部 completed。
- `completed_with_errors`：没有 running/queued，但存在 failed/cancelled。
- `cancelled`：用户取消整个 batch。
- `failed`：batch 调度本身失败，不是 item 失败。

### 8.2 Item status

允许状态：

```text
queued
running
completed
failed
cancelled
skipped
```

建议规则：

- `queued`：等待调度。
- `running`：已创建 job，job 未结束。
- `completed`：job completed。
- `failed`：job failed/stalled/interrupted。
- `cancelled`：job cancelled 或 batch cancel。
- `skipped`：后续保留，v0.4.0 可以不用。

## 9. CSV 规范

### 9.1 支持字段

第一版支持：

```csv
title,language,style,theme,duration_seconds,tempo_bpm,key,vocal_mode,lyrics,generation_mode,pipeline_mode
```

必填：

```text
title
language
style
theme
```

可选：

```text
duration_seconds
tempo_bpm
key
vocal_mode
lyrics
generation_mode
pipeline_mode
```

默认值：

```text
duration_seconds=180
vocal_mode=guide_melody
generation_mode=local
pipeline_mode=multinode
```

### 9.2 输入格式

`POST /api/batches/import-csv` 推荐支持 JSON body：

```json
{
  "name": "May demo batch",
  "csv_text": "title,language,style,theme\nSong A,en,pop,rain\nSong B,en,rock,city",
  "generation_mode": "local",
  "pipeline_mode": "multinode",
  "max_concurrency": 1
}
```

说明：

- 先支持 `csv_text`，不要一开始做 multipart upload。
- 文件上传可以在 Studio 里用 JS 读成本地文本，再 POST `csv_text`。
- 每行可以覆盖 `generation_mode` 和 `pipeline_mode`。
- 如果行内没有 mode，则使用 batch 默认 mode。

### 9.3 CSV 校验

必须校验：

- CSV 不能为空。
- 必填列存在。
- 每行必填值非空。
- `duration_seconds` 在 30 到 600。
- `tempo_bpm` 为空或 40 到 240。
- `generation_mode` 只能是 `local/provider`。
- `pipeline_mode` 只能是 `single/multinode`。
- `max_concurrency` 只能是 1 到 4。

错误返回 400，信息要能让用户定位哪一行。

示例：

```text
CSV row 3 is missing required field: theme.
```

## 12. 调度设计

### 12.1 第一版调度策略

不要引入外部队列。使用标准库线程。

建议：

- `BatchStore` 管数据。
- `JobStore` 继续负责单 job。
- `BatchRunner` 或 `JobStore` 内部 helper 负责把 batch item 转成 job。

可以新增：

```python
class BatchRunner:
    def __init__(self, batch_store: BatchStore, job_store: JobStore) -> None:
        ...

    def launch(batch_id: str) -> None:
        ...

    def tick(batch_id: str) -> None:
        ...
```

但不要为了抽象过度拆。第一版也可以放在 `server.py`，只要测试清楚。

### 12.2 max concurrency

调度循环：

```text
while batch running:
  sync running item statuses from jobs
  available = max_concurrency - running_count
  start up to available queued items
  if no queued/running left: finish batch
  sleep short interval
```

建议 sleep：

```text
0.1 到 0.5 秒
```

测试里不要依赖太长 sleep。

### 12.3 item 启动

每个 item 启动时：

1. 从 item.request 构造 payload。
2. 注入 `generation_mode` / `pipeline_mode`。
3. 调用现有 `JobStore.create_job(payload, start_immediately=True)`。
4. 保存 item.job_id / output_dir / status=running / attempt_count+1。

注意：不要绕过 `JobStore` 直接调用 `generate_request()`。batch 必须复用已有 job 状态机，否则面板 job detail、provider snapshot、node retry 都会断。

### 12.4 pause

`pause` 的语义：

- 不再启动新的 queued item。
- 已经 running 的 job 继续跑。
- batch status 变为 `paused`。

不要第一版就强行 cancel running jobs。

### 12.5 resume

`resume` 的语义：

- batch 从 `paused` 回到 `running`。
- 继续启动 queued item。

### 12.6 retry-failed

`retry-failed` 的语义：

- 只把 failed / cancelled / interrupted / stalled 对应 item 重新置为 queued。
- 不影响 completed item。
- item.attempt_count 递增由启动时处理。
- 如果原 job 失败保留，retry 新建 job 更简单、更干净。

建议第一版 retry failed 创建新 job，不复用旧 job 的 `POST /api/jobs/<id>/retry`。原因：

- batch item 的一次尝试对应一个 job 更清晰。
- export 可以记录最新 job。
- 旧 job 仍在 runs 里可查。

后续如果要保留 attempt history，可扩展：

```text
attempts: [{job_id, output_dir, status, error}]
```

v0.4.0 可以先不做 attempts 列表。

## 13. Provider batch 规则

provider batch 第一版必须可用，但要保守。

规则：

- batch 默认可以选择 `generation_mode=provider`。
- provider config 缺失时，launch 返回 400，不能启动半个批次。
- provider snapshot 仍由每个 job 自己写。
- batch.json / items.json 不能保存明文 key。
- export 不能包含明文 key。
- max_concurrency 对 provider 默认建议 1。

Studio 里可以提示：provider batch 建议并发 1。

## 19. Reviewer 核验重点

reviewer 检查 `v0.4.0` 时重点看：

- CSV required columns 是否严格校验。
- 行级错误是否能定位 row number。
- batch id 是否并发安全。
- max concurrency 是否真实生效。
- pause 是否只停止新 item，不误杀 running job。
- resume 是否继续 queued item。
- retry failed 是否不影响 completed item。
- batch item 是否复用 `JobStore.create_job()`。
- provider batch 是否要求 provider config。
- batch export 是否不泄露 key。
- delete batch 是否不会删除 runs。
- open-folder 是否只允许 POST。
- `.musicforge/batches/` 是否未提交。
- 旧 CLI 和旧 Studio job 功能是否不回归。

## 21. v0.4.0 后下一步

`v0.4.0` 完成后，不要马上加更多 batch 复杂度。下一步建议是：

```text
v0.5.0：音频渲染和浏览器试听
```

原因：

- batch 可以批量生成 MIDI。
- 但用户最终要听结果。
- `v0.5.0` 应把 `song.mid` 转成 `song.wav`，并在 Studio 里播放。

如果 `v0.4.0` 后发现 batch 调度仍不稳，可以先做 `v0.4.1` 修复调度和恢复，再进 `v0.5.0`。

# v10.15.0 Release Audio Command Center 音频准出总控台、统一证据编排与一键准出施工图

## 0. 给开发的话

这版不要再做成“又多一个孤立模块”。v10.2 到 v10.14 已经把真实音频环境、人工试听、Fix Sprint、Campaign、Certification、Timeline、Regression、Baseline、Observatory、Action Queue、Action Queue Signoff 全部做出来了，但现在的问题是：**链路太长、入口太散、证据太多、用户不知道下一步该点哪里。**

v10.15.0 的目标是做一个真正能指导业务和开发使用的 **Release Audio Command Center**：

- 它是音频准出的总控台。
- 它聚合当前 Release 的所有音频证据。
- 它明确告诉用户：哪些已经 ready，哪些缺证据，哪些 stale，下一步要做什么。
- 它能生成一个 deterministic 的 execution plan。
- 它能安全执行只读或可重建的 safe action。
- 它能导出一个统一的 Audio Command Center ZIP，供 Release signoff、GA readiness、外部归档和 reviewer 离线验证。
- 它不替代人工听审、不自动签核、不自动修音乐、不自动 approve waiver。

开发时请先完整读完本施工图，再动代码。不要把 v10.15 做成“把各模块按钮搬到一个页面”。它必须有自己的 source model、readiness matrix、gap plan、runbook、offline verifier 和 release-check smoke。

## 2. 为什么 v10.15 要“整合”

### 2.1 现有音频准出链路已经过长

从 v10.2 到 v10.14，音频链路大致是：

1. Audio Lab：真实音频环境、单曲试听、marker、A/B。
2. Audio Fix Sprint：从 marker 进入修复 sprint。
3. Audio Campaign：发行候选批量真实听审。
4. Audio Campaign Governance：campaign 归档、趋势、门禁。
5. Release-driven Audio Campaign：从 Release tracks 自动创建 campaign。
6. Campaign Remediation：听审失败后的修复编排。
7. Release Audio Certification：音频准出证书。
8. Certification Timeline：音频证据时间线。
9. Regression Guard：和 baseline 比较，挡回归。
10. Baseline Governance：baseline 创建、批准、激活。
11. Regression Response：回归响应和 waiver guard。
12. Quality Observatory：跨发行趋势、风险和建议。
13. Quality Action Queue：把风险建议转成行动队列。
14. Quality Action Queue Signoff：手工处置、closeout、signoff、archive。

这些能力都重要，但使用者不应该记住 14 个入口和几十个 ZIP / verification report 参数。

### 2.2 当前痛点

现状对开发和业务都偏繁琐：

- 不知道某个 Release 当前卡在哪一环。
- 不知道要先 rebuild 哪个 evidence。
- 不知道哪个 ZIP / verification report 是 stale。
- Release signoff / GA readiness 的参数越来越多。
- Studio 页面存在大量分散控件，用户需要跨区跳转。
- release-check 能验证，但不能直接给业务一个“下一步动作清单”。
- 证据链虽然强，但缺一个总览包。

### 2.3 v10.15 的定位

v10.15 是音频准出链路的“整合层”和“操作层”：

- 向下读取 v10.2-v10.14 的证据。
- 横向生成统一 readiness / blockers / evidence matrix。
- 向上提供 Release signoff / GA readiness / reviewer 的单一入口。

一句话：**把零散的音频治理能力变成一个可执行、可审计、可离线验收的 Release Audio Command Center。**

## 5. 设计原则

### 5.1 只聚合，不自证

Command Center 可以生成 summary，但 verifier 不能只相信自己的 summary。

必须反查底层证据：

- Certification ZIP + verification report
- Timeline ZIP + verification report
- Regression Guard ZIP + verification report
- Baseline Registry ZIP + verification report
- Regression Response ZIP + verification report
- Observatory ZIP + verification report
- Action Queue ZIP + verification report
- Action Queue Signoff Archive ZIP + verification report

### 5.2 显式区分 ready / warning / blocked / missing / stale

不要用一个 `passed` 混掉所有状态。

建议状态：

- `ready`
- `warning`
- `blocked`
- `missing`
- `stale`
- `manual_required`
- `not_configured`

### 5.3 一切可执行动作必须分类

Action 类型：

- `safe_auto`
- `safe_rebuild`
- `manual_required`
- `blocked`
- `not_supported`

`safe_auto` 只能做读取、刷新 report、export、verify、生成 plan。

`safe_rebuild` 可以重建未签核、可变证据；如果目标证据已签核或 archived，必须 blocked。

`manual_required` 包括人工听审、签核、reset、waiver、provider、上传、改音乐。

### 5.4 签核后不可变

Command Center 自己也要支持 signoff 吗？

v10.15 建议先不做 Command Center 自身 signoff，而是做：

- Report / Export / ZIP
- offline verifier
- Release / GA gate

Command Center signoff 可以留到 v10.16。如果 v10.15 同时做 signoff，会范围过大。

### 5.5 不降低原有门禁

Release signoff 如果要求 Command Center，只代表新增一个“总控证据包”门禁；不能绕过原有：

- `require_release_audio_certification`
- `require_release_audio_timeline`
- `require_release_audio_regression`
- `require_release_audio_baseline_governance`
- `require_release_audio_regression_response`
- `require_release_audio_quality_observatory`
- `require_release_audio_quality_action_queue`
- `require_release_audio_quality_action_queue_signoff`

Command Center gate 通过，只能说明“整合视角也认为证据齐全且绑定当前 Release”。

    def __init__(self, workspace_root: Path): ...

    def refresh_report(

    def build_evidence_inventory(self, release_id: str, evidence_paths: dict | None = None) -> dict: ...

    def build_readiness_matrix(self, release_id: str, evidence_paths: dict | None = None) -> dict: ...

    def build_gap_plan(self, release_id: str, evidence_paths: dict | None = None) -> dict: ...

    def create_runbook(self, release_id: str, *, include_safe_rebuild: bool = False) -> dict: ...

    def run_safe(self, release_id: str, runbook_id: str) -> dict: ...

### 9.1 refresh_report()

职责：

- 读取 Release 当前 tracks。
- 读取各底层 evidence 的 package / verification report。
- 生成 inventory / readiness / gap plan。
- 写入 `command-center-report.json`。

要求：

- 如果 evidence 缺失，报告可以生成，但状态必须是 `blocked` 或 `missing`。
- 如果 evidence stale，状态必须是 `stale`。
- 不因为某个 evidence 缺失直接抛异常，除非 Release 本身不存在。

### 9.2 run_safe()

只允许：

- refresh command center report
- export command center package
- build command center zip
- verify command center package
- refresh missing non-signed summary if underlying store already supports safe refresh and target is not signed

不允许：

- signoff
- reset
- approve
- waive
- create manual review
- edit music
- run provider
- rebuild signed archive
- mutate any signed evidence

遇到不允许动作：

```json
{
  "status": "manual_required",
  "message": "This action requires human approval."
}
```

### 9.3 export_package()

固定导出结构，不允许随意多文件。

导出前必须：

- 重新读取当前 report。
- 校验 report integrity。
- 如果 report stale，返回 409。
- 如果 readiness 已经 blocked，也允许 export，但 manifest 必须写 `readiness_status=blocked`。

理由：blocked 的 Command Center 包对 reviewer 也有价值，它能说明缺口。

### 9.4 build_zip()

ZIP 固定 allow-list。

不允许：

- extra entry
- duplicate entry
- path traversal
- backslash path
- `.musicforge/` 或大小写变体
- nested ZIP
- 本机绝对路径
- token / key / provider response 原文

### 10.1 verifier 必查项

ZIP 层：

- zip exists
- zip readable
- no duplicate entries
- no unsafe path
- no backslash path
- no `.musicforge/` case variants
- no nested zip
- exact allow-list
- manifest files exact match
- file hash match
- redaction scan

Document 层：

- manifest integrity
- command center report integrity
- inventory integrity
- readiness matrix integrity
- gap plan integrity
- runbook integrity
- runbook result integrity

External evidence 层：

- 每个 required component 必须有外部 ZIP 和 verification report。
- 外部 verification report 必须 integrity OK。
- 外部 verification report 必须绑定当前 ZIP sha / size / manifest hash。
- runtime verify 必须重新跑底层 verifier，不只读旧 report。
- Command Center 中记录的 fingerprint 必须等于外部 evidence runtime fingerprint。

Readiness 层：

- `--require-ready` 下，任何 required component missing / stale / blocked 都 failed。
- 不传 `--require-ready` 时，blocked 包可以通过结构校验，但 summary status 是 blocked。

## 18. 安全要求

### 18.1 禁止 source_path 导入

Command Center 不需要上传文件，不应接受：

- `source_path`
- `local_path`
- `file_path`

### 18.2 路径安全

ZIP entry 必须：

- 使用 `/`
- 相对路径
- 不含 `..`
- 不含盘符
- 不含 UNC
- 不含反斜杠
- 不含控制字符
- 不以 `/` 开头
- 不进入 `.musicforge` 任意大小写变体

### 18.3 脱敏

所有输出 JSON / TXT / HTML 需要走现有 redaction：

- API key
- bearer token
- GitHub token
- Windows path
- UNC path
- provider raw response
- local workspace path

### 18.4 不复制底层包

Command Center ZIP 不嵌套底层 ZIP。原因：

- 避免包过大。
- 避免 nested ZIP 安全问题。
- 保持外部 evidence binding 明确。

## 26. Reviewer 重点检查清单

开发完成后，reviewer 要重点看：

- 是否又新增了一个孤立模块，而不是整合入口。
- verifier 是否只信 Command Center 自己的 JSON。
- run-safe 是否误执行 manual/signoff/reset/provider/action。
- signed evidence 是否会被 Command Center 重建。
- missing evidence 是否被当 warning 放行。
- stale evidence 是否被 force 绕过。
- Release signoff gate 是否绑定当前 Command Center ZIP 和 verification report。
- GA verifier 是否能挡 forged report。
- ZIP 是否固定 allow-list。
- redaction 是否覆盖所有 summary / report / README。
- release-check 是否覆盖 full-resign 攻击。

## 28. 对开发的直接要求

这版是“整合复杂度”的版本，不是“增加复杂度”的版本。

你实现时要不断问自己：

- 用户能不能一眼看懂 Release 现在能不能准出？
- 用户能不能知道下一步该做什么？
- reviewer 能不能离线验证这个结论？
- 攻击者全量重签 Command Center 自己的 JSON 后，能不能骗过 verifier？
- Command Center 有没有偷偷替用户做人工签核或音乐修改？

如果答案不清楚，就不要继续堆代码，先补数据模型和测试。

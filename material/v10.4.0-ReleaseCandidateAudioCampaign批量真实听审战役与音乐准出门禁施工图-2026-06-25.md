# v10.4.0 Release Candidate Audio Campaign 批量真实听审战役与音乐准出门禁施工图

> 目标读者：MusicForge 开发执行人员  
> 当前稳定基线：v10.3.1  
> 规划角色：Reviewer / Planner  
> 计划版本：v10.4.0  
> 文档日期：2026-06-25

---

## 1. 背景

v10.2 已经把真实音频环境、Audio Lab、人工试听 session、marker、A/B comparison 做出来。

v10.3 已经把单个或多个 Audio Lab session 里的 `needs_fix` / `rejected` marker 推进成 Audio Fix Sprint，可以生成候选、人工 A/B、选择 candidate、创建 recheck session，并用 closeout gate 阻断测试 WAV、未复验、stale source、仍有问题的修复结果。

v10.3.1 又补齐了人工文本入口脱敏，避免 sprint name、review notes、selected_by、closed_by 把 token 或本机路径落盘。

现在系统已经具备“听一首、发现问题、修一轮、复验一轮”的能力。但真正做 release candidate 时，开发需要面对的不是一首歌，而是一批歌：

- 12 首内置 Regression Songbook。
- 一个 Release 里的多首 track。
- 一个 Project 的多个候选版本。
- 一批自动生成的风格覆盖样本。
- 一批经过 Audio Fix Sprint 修复后的 recheck 样本。

如果继续靠开发手工打开多个 Audio Lab session 和多个 Audio Fix Sprint，流程会变得分散：

- 哪些歌已经真实渲染 WAV？
- 哪些歌只是 test fake WAV？
- 哪些歌已经人工听审？
- 哪些歌有 high / critical marker？
- 哪些问题已经创建 Fix Sprint？
- 哪些 Fix Sprint 已经关闭？
- 哪些 recheck 仍然不是 release-ready audio？
- 哪些歌曲可以作为 release candidate？
- 最终凭什么说“这批生成音乐没问题”？

v10.4.0 要解决这个问题：把单曲 Audio Lab 和单个 Audio Fix Sprint 提升为批量级 Release Candidate Audio Campaign。

---

## 2. 一句话目标

> v10.4.0 建立 Audio Campaign 工作台，让开发能够对一批歌曲执行真实音频回归、人工听审、问题修复、复验、签核和离线验收，形成“这批生成音乐已人工确认可用”的工程证据。

它不是新的音乐生成模型，也不是自动审美裁判。它是本地批量 QA / release candidate 听审战役。

---

## 3. 业务定位

### 3.1 v10.2 / v10.3 / v10.4 的边界

| 版本 | 已解决问题 | 粒度 |
|---|---|---|
| v10.2 | 能不能真实渲染、播放、人工听、打 marker | 单个 Audio Lab session |
| v10.3 | 听出问题后能不能修复、A/B、复验、关闭 | 单个 Audio Fix Sprint |
| v10.4 | 一批 release candidate 能不能批量听审、批量修复、批量准出 | Campaign / Release Candidate |

v10.4 不是替代 v10.2 / v10.3，而是调度和汇总它们。

### 3.2 与 acceptance-check 的关系

`acceptance-check` 偏向结构化验收和 songbook 覆盖。它可以证明：

- 生成链路能跑。
- SongPlan / MIDI / validator 没坏。
- regression songbook 覆盖完整。
- synthetic 或 manual acceptance 状态满足规则。

Audio Campaign 偏向真实音频和人工听感验收。它要证明：

- 每首候选歌都有真实 renderer 产出的 WAV。
- 每首歌被开发实际播放和人工评价。
- 每个问题 marker 都有处理结论。
- 每个 high / critical 问题都不能被忽略。
- 每个修复都必须通过重新听审。
- test fake WAV 不能进入 release-ready。

二者可以互相引用，但不能互相替代。

### 3.3 与 Human Review Pack 的关系

Human Review Pack 更适合外部审查或离线听审响应导入。

Audio Campaign 是内部开发/制作团队的批量准出战役。它可以导出 review pack，但 v10.4 重点不是外部 reviewer，而是本地开发自验。

---

## 4. 不做什么

v10.4.0 明确不做：

- 不接 Suno / Udio / 其他外部音乐生成 API。
- 不让 provider 自动判断音乐是否 release-ready。
- 不把 synthetic review 当成人工听审。
- 不自动 apply 修复 candidate。
- 不自动 close 有 high / critical 未处理问题的 campaign。
- 不要求提交真实 SoundFont、真实 WAV、真实 `.musicforge/renderer.json`。
- 不把 Audio Campaign 直接塞进 Public Trust Center 或 v8/v9 的公开证明链。
- 不做多人账号权限系统。
- 不做云端播放、云端存储、云端协作。
- 不做 DAW 级混音编辑器。
- 不做音频版权指纹检测。

## 8. 核心工作流

### 8.1 创建 Campaign

支持来源：

1. `songbook`
   - 默认读取内置 Regression Songbook。
   - release_candidate profile 必须覆盖完整 songbook。

2. `release`
   - 从 Release 的 track / final export / selected version 创建 case。
   - 用于真实发行前批量听审。

3. `project`
   - 从 Project selected/final version 创建 case。
   - 用于单项目 release candidate。

4. `batch`
   - 从 Batch item 创建 case。
   - 用于批量生成结果听审。

5. `manual`
   - 允许传 request JSON / job id / project version id 列表。

创建时必须写 `source_hash`。

### 8.2 生成 / 渲染

Campaign 应该支持安全的分步执行：

```text
draft -> generate -> render -> review_pending
```

规则：

- 如果 case 已有 job / project version，可复用，不强制重生成。
- 如果没有 WAV，尝试按 renderer profile 渲染。
- `release_candidate` / `audio_required` profile 必须要求真实 renderer。
- `test_fake` WAV 只能用于 smoke，不允许进入 release-ready。
- 渲染后写 `audio_health.json` 和 case source hash。

### 8.3 创建 Listening Session

Campaign 可以批量创建 Audio Lab session：

- 一个 campaign 可以对应一个或多个 listening session。
- 每个 case 至少绑定一个 current review item。
- review item 必须明确：
  - `review_mode=manual`
  - `playback_confirmed=true`
  - reviewer name / role
  - rating
  - accepted / needs_fix / rejected

### 8.4 问题聚合

Campaign report 必须汇总：

- needs_fix case
- rejected case
- high / critical marker
- audio health failed
- stale artifact
- missing manual review
- synthetic-only review
- test fake audio

这些问题不应该只写到文本里，应成为可机器检查的 blockers。

### 8.5 批量创建 Audio Fix Sprint

Campaign 应该提供：

```text
create-fix-sprints
```

行为：

- 从 campaign 的 needs_fix / rejected / high marker case 创建 Audio Fix Sprint。
- 优先复用已有 open sprint，避免重复创建。
- 每个 case 记录 linked fix sprint。
- 不自动 generate candidate。
- 不自动 select candidate。
- 不自动 close sprint。

### 8.6 Recheck 汇总

Campaign 不直接替代 Audio Fix Sprint recheck，但必须读取它：

- 关联 fix sprint closeout。
- 关联 recheck session。
- 确认 recheck manual accepted。
- 确认 recheck WAV 是 release-ready audio。
- 确认 selected candidate 没有 stale。

### 8.7 Closeout / Signoff

Campaign closeout gate：

必须全部满足：

- 所有 case 已生成或已绑定合法 source。
- 所有 case 有 WAV。
- 所有 release-ready case 是 real renderer audio。
- 所有 case audio health passed 或允许 warning。
- 所有 case 有 manual review。
- 所有 case review status 是 accepted 或 recheck_accepted。
- 没有 open high / critical marker。
- 没有 open needs_fix / rejected case。
- 所有相关 Audio Fix Sprint 已 closed。
- 所有 fix sprint closeout passed。
- 所有 recheck session release-ready。
- 没有 stale source。
- 没有未脱敏敏感文本。

签核后：

- `campaign.json` 状态变 `signed`。
- 写 `signoff.json`。
- 写 `history.jsonl`。
- 阻断 generate / render / create-fix-sprints / refresh destructive operation。

## 12. Verifier 规划

新增：

```text
song_agent/audio_campaign_verifier.py
python -m song_agent.cli verify-audio-campaign-package <zip>
```

验证内容：

### 12.1 ZIP 安全

- 禁止 duplicate entries。
- 禁止 absolute path。
- 禁止 `..` traversal。
- 禁止反斜杠 entry。
- 禁止 `.musicforge/` 内部敏感目录。
- 禁止 nested ZIP，除非明确 allow-list；v10.4 默认不允许 nested ZIP。
- 限制 entry count。
- 限制总解压大小。

### 12.2 Manifest 对账

- `manifest.json` package_type 必须是 `audio_campaign`.
- `manifest.files[]` 与实际 entries 一致。
- 每个 entry 的 size / sha256 必须匹配。
- `campaign-report.json` hash 必须匹配 manifest。
- `campaign-signoff.json` 如存在，必须绑定 report hash。

### 12.3 Evidence 对账

- 每个 case report 必须绑定 case source hash。
- audio health summary 必须绑定 WAV hash。
- listening summary 必须绑定 session item hash。
- fix sprint summary 必须绑定 fix sprint closeout hash。
- recheck summary 必须绑定 recheck session hash。

### 12.4 Gate flags

支持：

```text
--strict
--require-real-audio
--require-manual-review
--require-fix-sprints-closed
--require-signed
--require-no-open-high
--require-no-open-critical
```

这些 flag 不能只信 ZIP 内自证。对仍在本地 workspace 的 verify API，可以传外部 store 路径做更强校验；CLI 离线模式至少要验证包内 sidecar 的完整性和一致性。

## 13. GA / Release Check 接入

### 13.1 release-check

新增：

```text
v104.audio_campaign_smoke
```

纳入：

- `profile v10`
- `profile latest`
- `profile ga`
- `profile full`

Smoke 必须覆盖：

1. 创建 campaign。
2. 生成或绑定至少 2 个 case。
3. 一个 fake/test WAV case 被 closeout blocker 阻断。
4. 一个 real-marked WAV case 可 manual accepted。
5. 一个 needs_fix case 创建 Audio Fix Sprint。
6. Fix Sprint 未 closed 时 campaign failed。
7. Fix Sprint closed + recheck accepted 后 campaign passed。
8. 注入 fake secret marker / `api_key=...` / `C:\Users\...` 后 report/export 不保留原文。
9. ZIP verifier passed。
10. 篡改 report / manifest / case report 后 verifier failed。
11. stale source 后 refresh/report/signoff 409 或 failed。

## 15. 状态机

Campaign 状态：

```text
draft
  -> running
  -> reviewing
  -> needs_fix
  -> rechecking
  -> ready
  -> signed
  -> archived

任何阶段:
  -> stale
  -> blocked
```

状态转换规则：

- `draft -> running`：开始 generate/render。
- `running -> reviewing`：所有 case 至少有可播放 artifact。
- `reviewing -> needs_fix`：任一 case needs_fix/rejected/high marker。
- `needs_fix -> rechecking`：已创建 fix sprint 并开始 recheck。
- `rechecking -> ready`：所有 blockers 清除。
- `ready -> signed`：人工签核。
- `signed -> archived`：后续版本可做 archive；v10.4 可只保留 signed。
- 任何 source 改变：`stale`。

## 23. 给开发的话

你接 v10.4 时，不要把它理解成“再加一个面板”。这版的核心是让业务真正能回答：

> 这一批自动生成的歌，开发到底有没有真实听过？有没有发现问题？发现的问题有没有修？修完有没有重新听？最后有没有证据证明它们可以进入 release candidate？

因此优先级是：

1. 数据结构和 gate 要稳。
2. fake/test audio 必须被挡住。
3. manual review 必须是真的 manual。
4. Audio Fix Sprint 必须闭环后才能 close campaign。
5. 所有人工文本必须脱敏。
6. 所有 artifact 必须 hash/source 绑定。
7. ZIP verifier 必须能抓篡改。

只要这些后端规则稳，Studio 面板可以朴素一点；反过来，如果面板好看但 gate 不严，这版就是失败的。

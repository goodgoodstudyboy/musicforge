## 2. 先理解项目现在是什么

MusicForge 是本地优先的自动化音乐生成与编辑工作台。

核心原则：

- 本地 deterministic pipeline 必须可跑，不依赖 provider。
- Provider 是增强，不是主链路前提。
- 所有重要工作都要先本地验证。
- 每次完成一个合适功能包，都要 commit，并在通过验证后 push 到 GitHub。
- Project Version 是正式版本；preview、audition、candidate 都是缓存或工作台产物，不是正式版本。
- Apply 类操作不能信任缓存产物，必须从 parent + patch/intents 重新计算。
- Export / Final Export 不允许泄露本地路径、token、provider key、raw prompt、原始长 notes。


### 2.2 重点理解当前能力

到 v2.7.1，已经完成：

- Project 工作区和版本管理。
- Visual Editor、Preview、Apply。
- Audition：从 parent/preview 创建试听片段。
- Review Board：给 audition 打 rating/status/favorite/notes/tags/markers。
- Review Edit：从 audition review 创建一次本地 edit 或 provider preview。
- v2.7.1 已修复 marker beat 坐标：audition 内 marker beat 是局部 beat，映射父版本时必须加上 audition range 的 `start_beat`。

v2.8.0 要做的是：

```text
Audition Review
  -> ReviewTask
  -> 多个 ReviewCandidate
  -> ranking / MIDI / 可选 WAV
  -> 用户 apply 一个 candidate
  -> 生成正式 child Project Version
  -> resolved 或 needs_more_work
```

关键收紧：

- 一个 ReviewTask 只允许 apply 一个 candidate。
- `needs_more_work` 不在旧 task 内二次 apply，而是创建 linked follow-up ReviewTask。
- `keep/hook` marker 是 preserve signal，不能抢占 `fix/issue/drop` marker 的目标。
- candidate MIDI/WAV 下载只能来自当前 candidate 的 `renders/song.mid` / `renders/song.wav`。
- Provider review candidates 是 Package G，可放到 v2.8.1。

## 5. v2.8.0 分包执行顺序

每完成一个 package，先本地测试，再 commit。不要攒到最后一次性提交。

### Package A：ReviewTask 基础层

目标：

- 新增 `song_agent/review_tasks.py`。
- 实现 `ReviewTask` 数据模型。
- 实现 `ReviewTaskStore`。
- 从 audition review 创建 task。
- 实现 target section / target track 推断。
- 实现 local marker beat -> global marker beat。
- 实现 priority。
- 实现 stale 检测。
- 实现 follow-up task 数据结构。

硬规则：

- `custom` / `changed_sections` / `section` range 有 `start_beat` 时，marker global beat = `start_beat + marker.beat`。
- `fix/issue/drop` marker 优先于 `keep/hook` marker。
- `keep/hook` marker 默认只作为 preserve signal。
- `needs_more_work` 之后的新一轮必须是 linked follow-up task。

测试：


## 9. 开发者最容易踩的坑

1. 把 marker beat 当成全局 beat。

   必须先加 audition range `start_beat`。

2. keep/hook marker 抢占 fix target。

   fix/issue/drop 优先，keep/hook 是 preserve。

3. apply 复制 candidate 缓存 SongPlan。

   Apply 必须 parent + intents/patch 重新计算。

4. needs_more_work 在旧 task 内二次 apply。

   旧 task 只能 apply 一次；下一轮用 follow-up task。

5. candidate path 只检查 review-tasks root。

   必须检查当前 candidate renders 目录和固定文件名。

6. provider scope 过早膨胀。

   A-F 是 v2.8.0 主线，Package G 可以 v2.8.1。

7. 改坏 v2.7 review edit。

   v2.7 的 `/review-edit-preview` 和 `/review-edit` 必须继续通过。

## 10. 给开发者的最终执行口径

先不要急着写 UI。

正确顺序：

```text
读 README/CHANGELOG/material
  -> 跑基线测试
  -> Package A ReviewTask
  -> Package B Local Candidates
  -> Package C API
  -> Package D Studio
  -> Package E Export
  -> Package F release-check/docs/version
  -> 全量验收
  -> push/tag/release
```

v2.8.0 的验收核心不是“页面上多几个按钮”，而是形成一条可信的反馈闭环：

```text
一条 audition review
  -> 一个 ReviewTask
  -> 多个候选
  -> 用户试听和选择
  -> 只 apply 一次
  -> 生成正式版本
  -> resolved 或 linked follow-up
  -> 全链路可追踪、可导出、可回归测试
```

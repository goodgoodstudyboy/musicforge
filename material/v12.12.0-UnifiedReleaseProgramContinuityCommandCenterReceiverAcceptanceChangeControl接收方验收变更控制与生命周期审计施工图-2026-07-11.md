# v12.12.0 Unified Release Program Continuity Command Center Receiver Acceptance Change Control 施工图

日期：2026-07-11

目标版本：v12.12.0

当前稳定基线：v12.11.0

主题：接收方验收签核后的受控变更、继任签核、生命周期审计和 Release / GA 准出绑定。

---

## 1. 背景

v12.9 到 v12.11 已经把项目级连续性链路推进到接收方接管层：

- v12.9：Continuity Command Center，聚合连续性恢复、Vault Operations、Distribution Kit、Acceptance Board 等证据，并做运行时复验。
- v12.10：Continuity Command Center Signoff / Archive / Final Handoff，完成总控签核、不可变归档和最终移交包。
- v12.11：Continuity Command Center Receiver Acceptance，接收方基于当前 Final Handoff 做 review、response、accepted evidence、Decision Board、signoff、archive。

v12.11 解决的是“接收方是否基于当前交付包完成验收并签核”。但签核以后还缺一层长期运营能力：

- 接收方签核后发现接收范围、角色、组织、response evidence 或 handoff evidence 需要调整时，目前只能重新开一套流程。
- v12.11 明确不做 reset，因此无法表达“旧签核被受控撤销，继任签核成为 current”的因果链。
- Release / GA 只能看到当前 Receiver Acceptance Archive，无法判断历史上是否发生过 reset、reset 是否由 approved CR 驱动、当前签核是第几代。
- 离线审计需要证明历史签核未被删除覆盖，reset proof 未被全量重签伪造，successor signoff 确实发生在合法 reset 之后。

v12.12 要补的是 Receiver Acceptance 的变更治理层：把 v12.11 的单次接收方验收，升级为可 reset、可继任、可审计、可长期运营的接管证明。

---

## 2. 版本目标

v12.12 新增 **Continuity Command Center Receiver Acceptance Change Control / Lifecycle Audit**。

核心目标：

1. 为已签核的 Receiver Acceptance 提供 approved single-use Change Request reset。
2. reset 后旧 Receiver Acceptance 不再作为 current release-ready evidence，但历史 Archive 必须保留。
3. reset 必须绑定 approved CR、allowed action、source/target identity、previous signoff、previous archive、previous verification、previous binding。
4. reset 后必须重新导入 / 复验 response、重新生成 accepted evidence、重新 refresh board、重新 signoff、重新 archive、重新 verify。
5. 新增 Receiver Acceptance Lifecycle Audit，把多 generation 的 signoff、archive、reset proof、successor signoff 串成可离线验证的生命周期报告。
6. Release signoff / GA readiness 可要求 current Receiver Acceptance + Change Control / Lifecycle Audit 同时通过。

一句话：v12.12 不是再加一个验收面板，而是把 v12.11 的接收方验收变成可变更、可追责、可长期审计的治理闭环。

---

## 3. 非目标

v12.12 不做：

- 不重新设计 v12.11 Receiver Response / Accepted Evidence / Board quorum 规则。
- 不自动生成接收方 response。
- 不自动批准 Change Request。
- 不自动把 rejected / needs_changes 变成 accepted。
- 不修改 v12.10 Command Center Signoff / Final Handoff。
- 不修改 v12.9 Command Center source。
- 不删除历史 Receiver Acceptance Archive。
- 不提供第三方 CA、公钥基础设施或链上登记。
- 不做外部公开门户发布。
- 不做复杂 Studio UX，只接入最小状态和操作入口。

- previous signoff hash。

- previous verification report hash。

### 6.5 Reset Binding Summary

`reset-000001-binding-summary.json`

必须由 reset 操作当场落盘，不允许 archive/verifier 时现算。

绑定：

- CR binding report hash。
- previous acceptance fingerprints。
- v12.11 signoff history latest event hash。
- lifecycle event hash。
- generation before / after。
- single-use consumed marker。

- `change_request_approved`

## 7. Store API

### 7.1 create_change_request()

输入：

```python
create_change_request(program_id: str, payload: dict) -> dict
```

要求：

- 当前 v12.11 Receiver Acceptance 必须 signed。
- 当前 v12.11 archive ZIP 必须 runtime verify passed。
- 当前 v12.11 verification report 必须绑定当前 ZIP。
- 当前 v12.11 signoff binding 必须存在且 integrity OK。
- `change_type` 必须是 `reset_receiver_acceptance_signoff`。
- `allowed_actions` 必须包含且只能包含本版允许的 action。
- payload 中的 path/source_path/local_path/file_path 直接拒绝。
- 文本字段必须 sanitize。

输出：

- CR JSON。
- CR binding source snapshot。
- lifecycle event `change_request_created`。

### 7.2 approve_change_request()

输入：

```python
approve_change_request(program_id: str, change_request_id: str, payload: dict) -> dict
```

要求：

- CR 存在。
- CR integrity OK。
- CR status 是 open。
- approval target/source 必须完全匹配 CR。
- approval allowed_actions 必须完全匹配 CR。
- 不能 approval 一个 already applied / superseded / revoked CR。
- approval 不能改变 target/source。

输出：

- approval JSON。
- CR status -> approved。
- `cr-*-binding-report.json`。
- lifecycle event `change_request_approved`。

### 7.3 reset_receiver_acceptance_signoff()

输入：

```python
reset_receiver_acceptance_signoff(program_id: str, change_request_id: str, payload: dict) -> dict
```

要求：

- CR 存在、approved、integrity OK。
- approval integrity OK。
- CR binding report integrity OK。
- CR `change_type == reset_receiver_acceptance_signoff`。
- CR `allowed_actions` 包含 `reset_receiver_acceptance_signoff`。
- CR target/source 与当前 v12.11 signed evidence 一致。
- 当前 v12.11 signoff history hash-chain 完整。
- 当前 v12.11 archive ZIP runtime verify passed。
- 当前 v12.11 verification report 绑定当前 ZIP。
- 当前 v12.11 signoff binding 是外部独立 proof，不能只信 ZIP 内副本。
- CR 未被使用过。

效果：

- 生成 reset proof。
- 生成 reset binding summary。
- CR status -> applied。
- 记录 applied reset hash。
- 当前 generation + 1。
- v12.11 current signed 状态变为 `reset_pending`。
- Release / GA gate 必须 failed，直到 successor signoff + archive + verify 完成。

禁止：

- force 绕过。
- 删除 signoff 文件绕过。
- 重复使用 CR。
- 用 wrong action CR reset。
- 用别的 program 的 CR reset。
- 用篡改 approval / binding report reset。

### 7.4 refresh_lifecycle_report()

输入：

```python
refresh_lifecycle_report(program_id: str, payload: dict | None = None) -> dict
```

要求：

- 读取所有 CR / approval / reset proof / generation。
- 读取当前 v12.11 Receiver Acceptance 状态。
- runtime verify 当前 v12.11 archive。
- 如果 reset pending，则 report status 必须 `blocked`。
- 如果 successor signed 且 verified，则 report status 可 `passed`。

输出：

- lifecycle report。
- generation index。
- reset proof index。
- risk register。
- current readiness。

### 7.5 export_archive()

输入：

```python
export_archive(program_id: str, payload: dict | None = None) -> dict
```

要求：

- lifecycle report status passed。
- 当前 generation signed。
- 当前 v12.11 Receiver Acceptance archive runtime verify passed。
- reset proof 语义验证 passed。
- lifecycle event hash-chain passed。
- 不允许在 reset pending 时 export。
- 如果 export 目录已存在，必须先重新校验文件与 report/source/signoff 绑定。

输出固定 archive 目录。

### 7.6 build_archive_zip()

输入：

```python
build_archive_zip(program_id: str, payload: dict | None = None) -> dict
```

要求：

- export archive 通过。
- ZIP 已存在时必须 runtime verify 当前 ZIP。
- 禁止 trailing data。
- 固定 allow-list。
- manifest.files 必须等于 allow-list。
- file-index 必须等于 allow-list。

## 8. v12.11 Store 需要配合的改动

v12.12 需要给 v12.11 Store 加一个受控 reset hook。

建议方法：

```python
mark_reset_pending(program_id: str, reset_proof: dict) -> dict
```

要求：

- 只能由 v12.12 Change Store 调用。
- 必须传入 reset proof 和 reset binding。
- 必须验证 reset proof package type。
- 必须把当前 signed state 标记为 reset_pending。
- 不能删除历史 signoff / history / archive。
- 后续 `signoff()` 允许 successor signoff，但必须检测 reset_pending 且 reset proof valid。
- successor signoff 必须写入 history event，绑定 reset proof hash。

继任签核时必须满足：

- v12.11 board 重新 refresh。
- response / accepted evidence 重新 current。
- rejected / needs_changes 仍会阻断。
- signoff history chain 从旧 generation 延续，不能断链。
- successor signoff binding summary 绑定 reset proof hash。

### 9.1 固定 allow-list

Change Archive ZIP 只允许：

```text
README.md
manifest.json
file-index.json
lifecycle-report.json
lifecycle-event-log.jsonl
current-generation.json
generation-index.json
change-request-index.json
reset-proof-index.json
external-evidence-manifest.json
integrity-summary.json
redaction-report.json
change-requests/*.json
approvals/*.json
reset-proofs/*.json
reset-bindings/*.json
generation-fingerprints/*.json
```

不允许：

- 任意 nested ZIP。
- `.musicforge/` 或大小写变体。
- 反斜杠 entry。
- `..`。
- 绝对路径。
- duplicate entry。
- manifest spoof。
- trailing bytes。
- 未声明文件。
- 声明但不存在文件。

### 9.2 Reset Proof 语义验证

不能只验证 reset proof integrity。

必须从以下外部证据反推：

- CR。
- approval。
- CR binding report。
- previous acceptance archive fingerprint。
- previous acceptance verification report。
- previous signoff binding。
- previous signoff history event。
- lifecycle reset event。
- current successor signoff。

必须检查：

- `generation_after == generation_before + 1`。
- reset proof 的 previous signoff hash 等于 previous signoff binding。
- reset proof 的 previous archive hash 等于 previous archive ZIP。
- reset proof 的 verification report hash 等于 previous verification report。
- CR target 指向 previous acceptance。
- approval target/source 等于 CR target/source。
- CR allowed_actions 包含 reset action。
- CR single-use，不能重复出现在 reset-proof-index。
- current generation 指向 successor acceptance。

### 9.3 Lifecycle Event Hash Chain

必须从 `lifecycle-event-log.jsonl` 重建：

- event hash。
- previous event hash。
- generation transitions。
- reset event 与 reset proof hash。
- successor signoff event 与 successor signoff hash。
- archive verification event 与 verification report hash。

篡改 reset_count、current generation、event order、event payload 后必须 failed。

### 9.4 Current Gate

`--require-current` 时必须同时满足：

- lifecycle report status passed。
- current generation signed。
- current receiver acceptance archive verify passed。
- current signoff binding 外部 proof passed。
- no reset pending。
- no unapplied approved reset CR targeting current signoff。
- no failed / stale current receiver acceptance runtime verification。

## 10. Release Signoff Gate

Release signoff 新增参数：

```json
{
  "require_unified_release_program_continuity_command_center_acceptance_change_control": true,
  "unified_release_program_continuity_command_center_acceptance_change_archive": "...zip",
  "unified_release_program_continuity_command_center_acceptance_change_verification_report": "...json",
  "unified_release_program_continuity_command_center_acceptance_archive": "...zip",
  "unified_release_program_continuity_command_center_acceptance_verification_report": "...json",
  "unified_release_program_continuity_command_center_acceptance_signoff_binding": "...json"
}
```

Gate 行为：

- require=false：不阻断，但 summary 可显示 missing / warning。
- require=true：缺任一外部 evidence 直接 409。
- reset pending 直接 409。
- stale previous/current archive 直接 409。
- failed lifecycle verification 直接 409。
- force=true 不能绕过。

Release signoff evidence 写入：

- change archive ZIP hash。
- change archive manifest hash。
- change verification report hash。
- current receiver acceptance archive hash。
- current receiver acceptance signoff hash。
- current generation。
- reset count。
- lifecycle status。

## 16. P1 风险与防线

### P1-1 reset proof 包内自证

风险：

攻击者同步篡改 reset proof、binding summary、manifest、lifecycle report，使 ZIP 内部自洽。

解决：

- verifier 必须从外部 previous receiver acceptance archive、verification report、signoff binding 反推 reset proof。
- reset binding summary 必须 reset 时落盘，不允许 archive 时现算。
- Change Archive verifier 必须要求外部 current Receiver Acceptance evidence。

### P1-2 approval 全量重签

风险：

把 approval target/source 改成攻击者想要的对象，再重算 integrity。

解决：

- approval 必须反查原始 CR target/source。
- CR binding report 必须绑定 CR hash 和 approval hash。
- reset proof 必须绑定 CR binding report hash。

### P1-3 删除 signoff/history 绕过

风险：

删除 v12.11 signoff 或 history，让 Store 误判为未签核，从而重新签核。

解决：

- v12.11 Store 已有 history 缺失保护；v12.12 reset 前还必须复验。
- 如果 history 缺失但 archive/signoff/binding 存在，必须 409。
- successor signoff 只允许在 valid reset pending 状态发生。

### P1-4 reset 后仍 release-ready

风险：

reset 成功后旧 Receiver Acceptance 仍被 Release / GA 当作 ready。

解决：

- reset 后 v12.11 gate 必须 failed。
- v12.12 lifecycle status 必须 reset_pending。
- Release / GA require change control 时必须 rejected。
- successor signed + archive verified 后才恢复 ready。

### P1-5 generation 混淆

风险：

用 gen-1 archive 搭配 gen-2 report，或用别的 program 的 evidence。

解决：

- 所有 evidence identity 必须绑定 `component_type + program_id + generation + source_hash`。
- verifier 按 generation index 逐项校验。
- current-generation.json 不能作为唯一信源，必须由 lifecycle events 重建。

## 21. 给开发的话

这版不要把重点放在“再做一个新面板”。v12.11 已经有接收方验收面板，v12.12 的价值是签核后的治理：reset 必须有 approved CR，CR 必须 single-use，reset proof 必须能被外部证据反推，successor signoff 必须发生在合法 reset 之后。

优先做 Store + verifier + P1 回归，再接 API/CLI。最容易被 reviewer 打回的点有三个：

1. reset proof / lifecycle report 只在包内自洽。
2. approval 只看 status approved，不反查 CR target/source。
3. reset 后旧 Receiver Acceptance 仍能被 Release / GA 当作 ready。

把这三个点先写死，后面的 UI 和文档都只是收口工作。

# MusicForge v0.9.0 施工图：Project 工作区与版本管理

日期：2026-05-06

基线版本：v0.8.1

## 0. 前置结论

v0.8.1 已经把 v0.8.0 的 Stem 生命周期问题收紧，可以作为 v0.9.0 的稳定基线。

当前系统已经具备：

- local / provider 两种生成模式。
- single / multinode 两种 pipeline。
- Job 创建、取消、重试、隐藏、删除。
- Node 级 retry。
- Timeline / Tracks / Quality / Validator / Nodes runtime views。
- MIDI、整首 WAV、Stem MIDI、Stem WAV。
- Batch CSV 批量生产。
- Batch audio / stem render。
- Studio 本地操作面板。
- Access token 鉴权。
- release-check 发布保护。

现在最缺的不是继续增加单点渲染能力，而是补一个上层业务对象：Project。

一句话目标：

> v0.9.0 要把零散的 jobs/runs/batches 组织成“同一首歌的创作项目”，支持多版本生成、版本对比、定稿、导出和 Studio 工作区管理。

## 1. 为什么要做 Project

目前 MusicForge 的核心对象是 Job：

- 创建一次请求就是一个 job。
- 每个 job 有独立 runs/<job-id>/。
- job 可以重试、node retry、渲染 audio/stems。
- Batch item 也只是关联到一个 job。

这对 MVP 是够的，但对真实写歌流程不够。

真实创作流程通常是：

1. 输入一个歌曲想法。
2. 生成第一版。
3. 不满意，换风格、换 tempo、换歌词或让某个 node retry。
4. 生成第二版、第三版。
5. 对比不同版本的结构、质量分数、MIDI、WAV、Stem。
6. 选一个版本作为 keeper / selected / final。
7. 导出最终素材。
8. 以后再回来继续改。

如果没有 Project 层，用户只能在一堆 jobs 里面找，越用越乱。

所以 v0.9.0 的业务重点是：

- 一个 Project 代表“一首歌/一个创作任务”。
- 一个 Project 下可以挂多个 Versions。
- 每个 Version 关联一个 Job。
- Studio 先选 Project，再看它下面的版本。
- 用户可以把某个版本标记为 selected/final。
- 后续 v1.0 前的局部编辑、版本对比、导出打包，都基于 Project 做。

## 2. v0.9.0 目标

必须完成：

- 新增 Project 数据模型与本地持久化。
- 新增 Project API。
- Studio 新增 Projects 工作区。
- 支持从 Project 创建新版本 job。
- 支持把现有 job 关联/导入到 Project。
- 支持 version list、selected version、final version。
- 支持 Project 级 summary：版本数量、最新版本、最佳 quality、是否有 audio/stems。
- 支持 Project 级导出 manifest。
- 支持 Project hide/unhide/delete。
- 兼容已有 jobs/batches，不破坏旧 workflow。
- README / CHANGELOG / version bump 到 `0.9.0`。
- 发布 GitHub Release。

建议完成：

- Project version diff：对比两个版本的 tempo/key/sections/tracks/quality/audio/stem 状态。
- Project clone-from-version：基于某个版本的请求创建新版本。
- Studio 中从 job detail 一键 `Add to Project`。
- Batch 导入时可选择创建 Project，或按 title 自动归档到 Project。

暂不做：

- 不做可视化 MIDI 编辑器。
- 不做 section 局部编辑。
- 不做多人协作。
- 不做数据库，继续本地文件持久化。
- 不做云同步。
- 不做复杂权限系统，继续复用现有 access token。
- 不做 DAW 工程文件。

## 3. 命名说明

本施工图里使用：

- Project：一首歌或一个创作主题的上层工作区。
- Version：Project 下的一次生成结果。
- Job：已有运行任务对象。
- Run：Job 的文件目录 `runs/<job-id>/`。
- Selected version：当前选中的推荐版本。
- Final version：用户明确定稿的版本。

Version 不直接复制 job 产物，先只保存 job 引用和快照摘要。

## 4. 数据目录设计

推荐新增本地目录：

```text
.musicforge/
  projects/
    <project-id>/
      project.json
      versions.json
      events.jsonl
      export.json
```

不建议把 Project 放进 `runs/`：

- `runs/` 是运行产物。
- `.musicforge/projects/` 是 Studio 业务索引。
- 删除 Project 不应默认删除 runs。
- 删除 Job 也不应直接破坏 Project 元数据，要把 Version 标记为 missing_job。

`.musicforge/` 已经被 `.gitignore` 忽略，这符合本地工作区定位。

建议新增模块：

- `song_agent/projects.py`

### ProjectState

建议字段：

```python
@dataclass
class ProjectState:
    project_id: str
    name: str
    description: str = ""
    status: str = "active"
    created_at: str = ...
    updated_at: str = ...
    hidden: bool = False
```

Project status：

- `active`
- `archived`
- `finalized`

先不要支持复杂状态流转。hide/unhide 仍然用 hidden 字段。

### ProjectVersion

建议字段：

```python
@dataclass
class ProjectVersion:
```


必须复用现有安全习惯：

- project_id 必须 slug 化。
- project_dir 必须在 `.musicforge/projects/` 下面。
- delete_project 只能删除 project metadata，不删 `runs/`。
- 使用 `write_json()` 写入，保持原子写 JSON 的项目风格。
- events.jsonl 追加 Project 事件。

Project ID 规则：

- 基于 name slug。
- 同名自动追加后缀：`my-song`、`my-song-2`。
- 不允许超过合理长度，建议 80 字符以内。

Version ID 规则：

- `v001`、`v002`、`v003`。
- 不使用 Git hash。
- index 从 1 递增。
- 版本显示名默认：`Version 1`、`Version 2`。

## 7. Project 与 Job 的关系

Project 不替代 Job。

Job 仍然负责：

- 生成。
- retry。
- node retry。
- audio render。
- stem render。
- runtime views。

Project 负责：

- 把多个 job 组织起来。
- 保存版本索引。
- 提供版本对比和定稿。
- 提供 Project 级导出。

### 创建 Project 后生成第一版

推荐 API 逻辑：

1. `POST /api/projects`
2. 创建 Project。
3. 可选 `request` 字段存在时，自动创建 job。
4. job 创建后添加为 `v001`。

### 从 Project 创建新版本

推荐：

`POST /api/projects/<project-id>/versions`

Body：

```json
{
  "request": {
    "title": "My Song",
    "language": "Chinese",
    "style": "pop",
    "theme": "late night city",
    "tempo_bpm": 96
  },
  "generation_mode": "local",
  "pipeline_mode": "multinode",
  "name": "Slower chorus version",
  "note": "Try lower tempo and warmer arrangement."
}
```

行为：

- 创建新 job。
- 添加 ProjectVersion。
- 返回 project + version + job。

### 从已有 job 添加到 Project

推荐：

`POST /api/projects/<project-id>/versions/from-job`

Body：

```json
{
  "job_id": "my-song",
  "name": "Imported version",
  "note": "Generated before Project workspace existed."
}
```

行为：

- job 不存在：404。
- job 已经在该 project 中：409。
- job 可属于多个 project 吗？
  - 建议 v0.9.0 不禁止，但 Studio 要提示。
  - 后续如果混乱，再加反向索引。

返回完整 document：


获取时应同步版本状态：

### POST /api/projects/<project-id>/selected

Body：

```json
{
  "version_id": "v002"
}
```

行为：

- version 不存在：404。
- 设置 `selected_version_id`。
- append event。

### POST /api/projects/<project-id>/final

Body：

```json
{
  "version_id": "v002"
}
```

行为：

- version 不存在：404。
- 建议只允许 completed version 设为 final。
- 设置 `final_version_id` 和 project.status=`finalized`。
- append event。

### GET /api/projects/<project-id>/diff

Query：

- `left=v001`
- `right=v002`

返回建议：

```json
{
  "left": {"version_id": "v001", "job_id": "..."},
  "right": {"version_id": "v002", "job_id": "..."},
  "changed": {
    "request": {...},
    "summary": {...},
    "quality": {...},
    "artifacts": {...}
  }
}
```

v0.9.0 的 diff 不需要复杂：

- title / style / theme / tempo / key / duration / lyrics 是否变化。
- sections 数量、track 数量、note 数量。
- quality overall 和 dimension 分数。
- midi/audio/stem 是否存在。

### GET /api/projects/<project-id>/export

生成 `.musicforge/projects/<project-id>/export.json`。

包含：

- project state。
- versions。
- selected version。
- final version。
- 每个 version 的 job/run paths。
- 每个 version 的 song_plan/midi/audio/stem manifest 路径。
- quality summary。

不要复制大文件到 Project 目录。v0.9.0 只做 manifest export。

## 11. 数据同步策略

Project version 是 job 的索引快照，不是独立事实源。

每次读取 Project detail 时：

- 调 `ProjectStore.sync_project(document, job_store)`。
- 对每个 version：
  - job 存在：刷新 status、summary、quality_score、artifact flags。
  - job 不存在：标记 missing_job。
- 重新计算：
  - version_count。
  - latest_version_id。
  - best_quality_version_id。
  - best_quality_score。
- 保存更新后的 project。

Artifact flags：

- `has_midi`：job artifacts 有 midi 或 `renders/song.mid` 存在。
- `has_audio`：job artifacts 有 audio 或 `renders/song.wav` 存在。
- `has_stems`：`stems/manifest.json` 存在且未 stale。
- `has_stem_audio`：manifest 中任意 stem audio_exists。

Quality score：

- 优先从 `song-plan.json` 的 `quality.scores.overall` 读取。
- 没有 quality 时，可以用现有 quality analyzer 推断，但不要重写 job artifact。
- 读取失败则 None。

## 12. 安全与边界

必须遵守：

- 所有 Project API 走现有 Bearer auth。
- project_id 必须 slug 验证。
- version_id 必须匹配 `v\d{3,}` 或从 versions.json 查找。
- delete_project 只能删除 `.musicforge/projects/<id>`。
- 不允许通过 Project API 任意删除 runs。
- export 只写 `.musicforge/projects/<id>/export.json`。
- Project 里不要保存 provider key、access token。
- Project event 不写敏感配置。
- README 不写本机私有路径。

路径边界：

```python
root = Path(".musicforge/projects").resolve()
target = project_dir.resolve()
target.relative_to(root)
```

## 17. 风险点

### 范围过大

Project workspace 容易把功能做成另一个大系统。v0.9.0 必须控制边界：

- 只做项目索引和版本管理。
- 不做编辑器。
- 不复制产物。
- 不重构 JobStore。

### 状态同步

ProjectVersion 是快照，但 job 是事实源。读取 Project 时必须同步，否则 Studio 会显示旧状态。

### 删除语义

Project delete 只能删除 `.musicforge/projects/<id>`，不能删除 `runs/`。

如果用户要删除 runs，继续走 Job delete。

### Batch 自动归档重复

Batch retry 可能产生新 job，也可能复用 item 状态。必须避免同一个 job 被重复添加到同一个 Project。

### UI 复杂度

Studio 已经有 Jobs、Batch、Provider、Renderer。Projects 加进去以后不要把页面变成不可扫读。

建议：

- Projects 放在 Jobs 上方或独立 section。
- Project detail 用 tabs。
- 保持表格密度，不做大卡片。

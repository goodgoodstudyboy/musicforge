# v10.6.0 Release-Driven Audio Campaign 发行驱动真实听审战役自动编排施工图

> 项目：MusicForge / song-agent
> 计划版本：v10.6.0
> 编写日期：2026-06-26
> 基线版本：v10.5.1
> 角色定位：reviewer / planner
> 目标读者：开发执行人员、测试验收人员、后续 reviewer

---

## 1. 背景

v10.4.0 做出了 Release Candidate Audio Campaign：

- 可以把多个 Audio Lab Listening Session 聚合成批量真实听审战役。
- 可以识别 fake/test WAV。
- 可以要求 manual review。
- 可以接入 Audio Fix Sprint。
- 可以 signoff / export / ZIP / verify。

v10.5.0 又把 Audio Campaign 提升为 Governance evidence：

- Audio Campaign Governance report。
- Analytics summary。
- Signed archive ZIP。
- Offline archive verifier。
- GA readiness gate。
- Release signoff gate。

v10.5.1 修掉了关键 P1：

- Release signoff 不再只看 Audio Campaign case 数量。
- 现在必须用 `project_id + version_id + final_export_hash` 覆盖当前 Release tracks。
- unrelated Campaign 不能再给当前 Release 签核。

这说明证据链已经比较牢，但实际工作流还不够顺。

当前开发/业务要完成一次真实音乐验收，仍然需要手动串很多步骤：

1. 先知道 Release 有哪些 tracks。
2. 手动创建 Audio Lab smoke/listening session。
3. 手动把 session item 补齐 `project_id`、`version_id`、`final_export_hash`。
4. 手动 review。
5. 手动创建 Audio Campaign。
6. 手动 signoff。
7. 手动 archive / verify。
8. 手动把 campaign id / archive path / verification path 填进 Release signoff 或 GA check。

v10.5.1 可以挡住错绑，但没有让正确流程变简单。

v10.6.0 要解决的是：**从 Release 出发，一键创建绑定正确的真实听审战役骨架，让开发只需要负责真实渲染和人工听审，不再手动补绑定字段。**

---

## 2. 一句话目标

> v10.6.0 要新增 Release-driven Audio Campaign Orchestrator：从一个 Release 自动生成带 track identity 的 Audio Lab listening sessions 和 Audio Campaign，自动完成预检、缺口提示、archive/verify/signoff 建议，让“这张 Release 的每首歌都被真实听审”成为顺手完成的标准流程。

### 3.1 已有模块

已存在：

```text

song_agent/release_checks.py
song_agent/release_check_matrix.py
```

### 3.2 v10.5.1 的关键规则

Release signoff 的 Audio Campaign gate 已经要求：

```text
release track identity:
  project_id
  version_id
  final_export_hash

audio campaign case identity:
  project_id
  version_id
  final_export_hash
```

匹配算法必须是：

```text
stable_hash({
  "project_id": project_id,
  "version_id": version_id,
  "final_export_hash": final_export_hash
})
```

任何字段缺失或不一致都不能通过 coverage gate。

### 3.3 当前痛点

v10.5.1 的机制安全，但操作路径不自然：

- Studio 里创建 Campaign 仍然从 session id 出发，不是从 Release 出发。
- 开发必须知道哪些字段要写入 Audio Lab item。
- release track 的 final_export_hash 对普通使用者不可见。
- 多 track release 的听审进度没有集中面板。
- 真实 renderer 缺失时，系统会失败，但没有 release-level 的准备清单。
- campaign signoff 后，业务仍要自己记住 archive / verify / Release signoff 的顺序。

## 4. v10.6.0 总目标

v10.6.0 完成后，应支持：

1. 从 Release 直接创建 Audio Campaign Plan。
2. 每个 Release track 自动生成一个 Audio Lab listening item。
3. 每个 item 自动写入：
   - `release_id`
   - `track_id`
   - `track_number`
   - `project_id`
   - `version_id`
   - `final_export_hash`
   - `title`
   - `expected_audio_artifact_hash`
4. 自动检查每个 track 是否具备 release-ready WAV。
5. 自动创建 Audio Lab Listening Session。
6. 自动创建 Audio Campaign，并绑定这些 session。
7. 自动生成 Release Audio Campaign Plan report。
8. Studio Release 页面新增 “Create Audio Campaign From Release”。
9. CLI/API 支持同样流程。
10. release-check 新增 v10.6 smoke，覆盖 correct flow 和 mismatch guard。
11. 不改变 v10.5.1 的门禁安全口径。

## 5. 明确不做什么

v10.6.0 不做：

- 不做自动人工听审。
- 不伪造 manual review。
- 不把 test_fake WAV 当 release-ready。
- 不自动 signoff Release。
- 不自动 approve Change Request。
- 不自动 reset Audio Campaign signoff。
- 不自动调用外部音乐生成 API。
- 不新增云端发布。
- 不接第三方分发平台。
- 不修改 v10.5.1 的 identity key 规则。

v10.6.0 只做“从 Release 到真实听审战役的自动编排”和“缺口提示”。

## 8. Release Track Identity

必须复用 v10.5.1 规则。

```python
stable_hash({
    "project_id": track.project_id,
    "version_id": track.version_id,
    "final_export_hash": track.final_export_hash,
})
```

### 8.1 不允许降级匹配

不能只用：

- title
- track number
- project_id only
- version_id only
- audio file name
- wav hash only

原因：

- title 可变。
- track number 可变。
- project final export hash 才代表当前交付版本。
- wav hash 可以被重新渲染，但 final export hash 才是 release track 的包级证据。

### 8.2 title 只用于展示

`title` 可以出现在 UI 和 report 中，但不能作为 gate 的主匹配键。

## 9. Audio Artifact 读取策略

Planner 需要给每个 Release track 找到 release-ready WAV。

优先级：

1. Project Final Export 中的 `song.wav`。
2. Release Export 中的 track `song.wav`。
3. Mastering selected candidate WAV。
4. Encoded audio 不作为 primary WAV，只用于后续 distribution 检查。

如果没有 WAV：

- preflight failed。
- 不创建 session，除非 payload 明确 `allow_missing_audio=true`。
- 即使允许创建，也不能进入 signoff-ready。

建议 v10.6 默认不允许 missing audio。

## 11. 从 Release 创建 Campaign

新增：

```python
AudioCampaignPlannerStore.create_campaign_from_release(release_id, payload)
```

默认流程：

1. `refresh_plan(release_id)`
2. `preflight(release_id)`
3. 如果 preflight failed，返回 failed，不创建 session/campaign。
4. 创建 Audio Lab session。
5. 创建 Audio Campaign，payload：

```json
{
  "from_session": "als-000001",
  "name": "Release Audio Campaign: <release name>",
  "profile": "release_candidate",
  "release_id": "release-000001",
  "settings": {
    "require_real_renderer": true,
    "allow_test_fake_audio": false,
    "allow_synthetic_review": false,
    "block_high_or_critical_markers": true,
    "minimum_rating": 4
  }
}
```

6. 写 `campaign-link.json`。
7. 返回 session/campaign/plan/preflight。

### 11.1 不自动 signoff

创建 campaign 后，状态应该是：

```text
campaign.status = needs_review 或 reviewing
```

用户必须人工 review 每个 item，然后再 signoff。

### 11.2 已有 campaign 处理

如果当前 Release 已经有 active campaign link：

- 如果 campaign 未 signed：允许继续使用。
- 如果 campaign signed 且 coverage passed：返回现有 campaign。
- 如果 campaign signed 但 source stale：阻断，需要创建新的 plan。
- 如果 campaign reset 后 `needs_fix`：允许 refresh/link new session。

不允许静默覆盖旧 campaign-link。

## 12. Preflight 检查清单

每个 track 必须检查：

### 12.1 final export 存在

```text
release_track_final_export_present
```

失败原因：

- track.final_export_hash missing。
- Project final-export/manifest.json missing。
- Release track snapshot stale。

### 12.2 WAV 存在

```text
release_track_wav_present
```

失败原因：

- final export 缺 song.wav。
- Release export 缺 track song.wav。
- WAV header invalid。

### 12.3 WAV health passed

```text
release_track_audio_health_passed
```

至少检查：

- wav header
- duration
- non-silent
- not clipped
- sample rate / bit depth if available

可复用 v5+ 的 audio health。

### 12.4 renderer real

```text
release_track_real_renderer
```

不能接受：

- runner_kind = test_fake
- missing renderer
- skipped renderer

### 12.5 identity complete

```text
release_track_identity_complete
```

必须有：

- project_id
- version_id
- final_export_hash

### 12.6 duplicate identity

```text
release_track_identity_unique
```

同一 Release 内两个 track 如果 identity 相同，应 warning 或 failed？

建议：

- 如果是同一首歌重复收录，允许，但需要 `allow_duplicate_track_identity=true`。
- 默认 failed，避免误把一首歌覆盖两首歌。

## 17. 关键安全约束

### 17.1 不信用户传入的 final_export_hash

API payload 里如果带 `final_export_hash`，只能用于 debug，不可作为 source of truth。

source of truth 必须来自：

- Release track snapshot。
- Project final export manifest。

### 17.2 不信本机绝对路径

Audio Lab item 可以保存相对路径或 artifact hash。

不要把：

- 本机绝对路径
- renderer local path
- SoundFont path
- provider key

写入公开 report。

### 17.3 创建后 source 变化要 stale

如果 Release tracks 变化：

- plan stale。
- campaign-link stale。
- status 显示 stale。
- 不允许 `Use For Release Signoff`。

### 17.4 signed campaign 不自动刷新

复用 v10.4.1 规则：

- signed campaign 不可 refresh。
- signed campaign 不可 silent mutate。
- 需要 approved Change Request reset。

### 17.5 Archive 不自动重建

复用 v10.5 规则：

- 已为 signoff 构建 archive 后，不可 silent rebuild。

## 18. Release Signoff 改动

v10.6 不改变 gate 核心规则，但可以增强 payload 便利性。

当前用户需要传：

```json
{
  "require_audio_campaign": true,
  "audio_campaign_id": "acmp-000001",
  "audio_campaign_archive_zip_path": "...",
  "audio_campaign_archive_verification_report_path": "..."
}
```

v10.6 可允许只传：

```json
{
  "require_audio_campaign": true,
  "audio_campaign_plan": true
}
```

系统从 Release 的 `campaign-link.json` 找到：

- campaign_id
- archive_zip_path
- archive_verification_report_path

但必须：

- link integrity OK。
- campaign coverage passed。
- archive verification passed。
- archive verification report 绑定当前 archive ZIP。

如果 link 不存在，返回：

```text
Audio Campaign plan is missing. Create a Release Audio Campaign first.
```

### 18.1 不要隐式创建

Release signoff 不应自动创建 campaign。

signoff 只能使用已存在且 verified 的证据。

## 20. Release Check

新增：

```text
v106.release_driven_audio_campaign_smoke
```

Profile：

- `v10`
- `ga`
- `latest`
- `quick`
- `full`

## 29. 给开发的话

这版不要再扩新的大证据链，重点是把 v10.4 到 v10.5 已经做好的真实听审能力变成“正常人会用”的 Release 工作流。

你要记住两点：

1. **正确性来自 Release track identity，不来自用户手填。**
   `project_id + version_id + final_export_hash` 必须从 Release / Project Final Export 读取，不能信 API payload。

2. **系统可以自动编排，但不能自动听审。**
   可以自动创建 session、campaign、plan、preflight，但 manual review 必须由人完成，test_fake 永远不能变成 release-ready。

做完后，业务侧应该能这样理解：

> 我打开 Release，点一下 Create Audio Campaign From Release，系统把每首歌准备成听审项；我逐首真实试听并打分；全部通过后 signoff campaign；系统自动知道这批听审证据属于这张 Release。

这才是 v10.6 要交付的价值。

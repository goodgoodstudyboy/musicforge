# v12.13.0 Release Check Acceleration and Heavy Smoke Refactor 施工图

日期：2026-07-12

目标版本：v12.13.0

主题：发布检查加速、重型 smoke 拆分、性能预算与安全覆盖保持

当前稳定基线：v12.12.0 本地提交候选

## 1. 背景

v12.12 之后，项目级连续性链路已经覆盖到：

- Unified Release Program Board
- Program Operations
- Program Final Handoff
- Evidence Vault
- Vault Operations
- Continuity Recovery
- Continuity Distribution Kit
- Continuity Acceptance Board
- Continuity Acceptance Change Control
- Continuity Command Center
- Continuity Command Center Signoff
- Receiver Acceptance
- Receiver Acceptance Change Control

功能链路已经足够完整，但 release-check 的验证成本开始明显偏高。最近一次 reviewer 复核时观测到：

- `v1212.unified_release_program_continuity_command_center_receiver_acceptance_change_control_smoke` 单项约 408 秒。
- `v1211.unified_release_program_continuity_command_center_receiver_acceptance_smoke` 单项约 243 秒。
- `v129.unified_release_program_continuity_command_center_smoke` 单项约 110 秒。
- `v1210.unified_release_program_continuity_command_center_signoff_smoke` 单项约 76 秒。
- `release-check --profile v12 --skip-tests` 约 17 分钟。
- `release-check --profile latest --skip-tests` 约 18 分钟。
- `release-check --profile ga --skip-tests` 在未提交状态下功能项全过，但整体仍要约 17 分钟才到 `git.status` 失败。

这说明当前主要问题不是测试失败，而是“单个 smoke 里串行重建完整世界、重复生成 ZIP、重复跑深度 verifier、重复 GA 构造”。如果继续按这个模式往 v12.13、v12.14 叠功能，发布前验证会越来越难跑，也会降低 hotfix 周转速度。

v12.13 因此不建议继续新增业务面，而应该专门做 release-check 性能治理。

## 2. 总目标

v12.13 的目标不是减少安全覆盖，而是在保持现有 P1/P2 防护场景的前提下，把重型 smoke 拆分成更小、更可复用、更可诊断的检查。

必须达成：

- v12 profile skip-tests 目标耗时从约 17 分钟降到 6 分钟以内。
- latest profile skip-tests 目标耗时从约 18 分钟降到 8 分钟以内。
- 单个 smoke 默认预算不超过 90 秒。
- v12.12 现有安全信号必须保留：
  - wrong action reset 409
  - approval target mismatch 409
  - reused CR 409
  - old evidence blocked
  - successor signoff
  - lifecycle passed
  - archive passed
  - gate passed
  - GA gate passed
  - reset proof full-resign failed
  - missing previous root failed
  - event order full-resign failed
  - declared extra failed
  - duplicate failed
  - dangerous path failed
  - nested ZIP failed
  - redaction failed
  - `.MusicForge` failed
  - raw backslash failed
  - trailing bytes failed
  - signed reset proof export/zip 409
  - signed reset proof gate failed
- release-check JSON 报告必须能清楚告诉 reviewer：
  - 哪些检查最慢。
  - 哪些检查超出性能预算。
  - 哪些重型检查被拆分后对应哪些旧 smoke 信号。

## 3. 非目标

v12.13 不做：

- 不新增新的 Program / Continuity / Acceptance 业务对象。
- 不移除任何现有安全攻击场景。
- 不把 P1 防护降级成 warning。
- 不靠简单调大 timeout 掩盖慢问题。
- 不要求完整 `pytest -q` 作为日常 release-check 默认路径。
- 不把测试 fixture 的可信 proof 伪造逻辑放到生产 verifier 里。

## 4. 当前慢点拆解

### 4.1 v12.12 smoke 慢的主要原因

当前 `_v1212_unified_release_program_continuity_command_center_receiver_acceptance_change_control_smoke()` 做了太多事情：

- 创建完整 Program / Acceptance / Change Control 世界。
- 创建 CR、approval、reset proof。
- 篡改 approval 并恢复。
- reset 后重建 successor evidence。
- successor signoff。
- Acceptance archive build / verify。
- Change Control lifecycle refresh。
- Change Control archive build / verify。
- Change Control gate。
- GA readiness build / verify。
- 多个 ZIP 篡改攻击：
  - reset proof full-resign
  - event order full-resign
  - declared extra
  - duplicate
  - dangerous path
  - nested ZIP
  - redaction
  - `.MusicForge`
  - raw backslash
  - trailing bytes
- 本地签核后 reset proof 源污染，分别验证 export/zip/gate。

这些场景都重要，但不需要每个场景都重新使用同一个超大端到端流程串行跑完。v12.13 要把它拆成多个独立检查，并复用同一个 prepared evidence snapshot。

### 4.2 v12.11 / v12.10 / v12.9 的重复成本

v12.11、v12.10、v12.9 都在构建相邻的完整 continuity command center 场景。它们之间有大量重复：

- Program evidence 构造。
- Continuity Distribution Kit 构造。
- Acceptance Board 构造。
- Command Center report / ZIP / verification。
- GA repo stub 构造。
- ZIP 安全攻击样本生成。

v12.13 应该抽出共享 fixture builder，让每个 smoke 只做自己的增量断言。

## 5. 设计原则

### 5.1 分层，而不是删覆盖

每个重型 smoke 拆成三类：

- `semantic`：直接调用 Store / verifier，覆盖业务语义和状态机。
- `zip-security`：只针对已生成的 archive ZIP 做固定结构、路径、duplicate、redaction、trailing data 等攻击。
- `gate-integration`：只跑 Release / GA / profile 集成，数量要少。

### 5.2 一次构造，多次复用

同一个 profile 运行中，v12.9-v12.12 的基础 continuity evidence 可以复用。

建议新增 release-check scoped fixture 缓存：

- 缓存只在单次 release-check 进程内有效。
- 缓存目录必须在 temp root 下。
- 缓存 key 至少包含：
  - fixture schema version
  - check id group
  - song_agent version
  - relevant source helper hash
  - Python major/minor
- 缓存内容不能跨 release-check 进程复用，避免 stale 状态污染。

### 5.3 生产 verifier 不为测试让步

可以新增测试/fixture helper，但不能让生产 verifier 接受测试专用的捷径。

允许：

- 在 `song_agent/release_check_fixtures.py` 或测试 helper 中集中构造 evidence。
- 在 release-check 进程里复用 temp fixture。
- 在 smoke 中读取 fixture 产物做攻击样本。

禁止：

- verifier 因测试性能绕过 runtime verification。
- gate 因测试性能只信旧 verification report。
- production Store 增加 test-only bypass。

### 5.4 慢检查必须可见

release-check 已有 timing 输出，但 v12.13 要把性能预算变成一等信息：

- check definition 支持 `duration_budget_seconds`。
- JSON summary 增加：
  - `slow_checks`
  - `checks_over_budget`
  - `duration_budget_status`
  - `profile_duration_budget_seconds`
- report-out / timing-out 都写入这些字段。

## 7. 具体实施步骤

### Step 1：建立性能基线采集

实现内容：

- 在 release-check report 中固定输出：
  - per-check duration
  - slowest top N
  - over-budget checks
  - profile total duration
- 给 `ReleaseCheckDefinition` 增加可选字段：
  - `duration_budget_seconds`
  - `budget_enforced_profiles`
  - `budget_warning_only`

建议默认：

- v12.12 重型旧 smoke 初期预算 120 秒，目标压到 90 秒。
- v12.11 预算 90 秒。
- v12.9 / v12.10 预算 60 秒。
- v12 profile 总预算 360 秒。
- latest profile skip-tests 总预算 480 秒。

验收：

- `release-check --profile v12 --skip-tests --json` 输出 `duration_budget_status`。
- 当前未优化前也能明确列出 v12.12 为 over-budget。

### Step 2：抽出 v12 continuity prepared fixture

实现内容：

新增 `release_check_fixtures.py`，提供类似：

- `ReleaseCheckFixtureCache`
- `prepare_v12_command_center_world(base, *, include_acceptance=True, include_change_control=True)`
- `prepare_v12_receiver_acceptance_signed(base)`
- `prepare_v12_receiver_acceptance_change_reset(base)`

产物必须包含：

- program store root
- program_id
- acceptance store paths
- change control store paths
- current acceptance archive ZIP
- acceptance verification report
- signoff binding
- previous generation root
- change control archive ZIP
- change control verification report
- GA kwargs builder 所需路径

要求：

- 所有路径在 temp root 内。
- fixture 不落到 repo。
- fixture 不复用到下一次 release-check 进程。
- fixture 不能隐藏 runtime verifier failure。

验收：

- 新增单测确认重复调用同一 fixture key 时不重复构造完整世界。
- 缓存命中时仍能复制隔离目录，避免一个攻击测试污染另一个测试。

### Step 3：拆 v12.12 smoke

把当前 v12.12 单个大 smoke 拆成至少四个 checks：

1. `v1212.receiver_acceptance_change_control_semantics`
   - wrong action reset 409
   - approval target mismatch 409
   - reset applied
   - reset gate failed
   - reused CR 409
   - old evidence board blocked
   - policy override 409
   - successor signoff signed
   - lifecycle passed
   - gate passed

2. `v1212.receiver_acceptance_change_control_zip_security`
   - declared extra failed
   - duplicate failed
   - dangerous path failed
   - nested ZIP failed
   - redaction failed
   - `.MusicForge` failed
   - raw backslash failed
   - trailing bytes failed

3. `v1212.receiver_acceptance_change_control_external_binding`
   - internal full-resign passed when no external proof is required
   - reset proof full-resign failed when previous root is required
   - missing previous root failed
   - event order full-resign failed

4. `v1212.receiver_acceptance_change_control_signed_mutation`
   - signed reset proof export 409
   - signed reset proof zip 409
   - signed reset proof gate failed

5. Thin compatibility smoke:
   - Keep old check id if compatibility is needed, but make it call the split checks or assert a minimal happy path.
   - Preferred: update matrix to use split checks and keep old function only for targeted pytest compatibility.

验收：

- 每个拆分 check 单项小于 90 秒。
- 四个拆分 checks 的 detail 合并后覆盖旧 v12.12 全部信号。
- `tests/test_release_check.py::test_v1212...` 更新为验证拆分后的 detail 或保留薄 smoke。

### Step 4：拆 v12.11 / v12.10 / v12.9

v12.11：

- 分成 receiver acceptance semantics、ZIP security、GA gate 三组。
- 避免每个攻击样本都重新创建 full response/evidence。

v12.10：

- 分成 signoff semantics、archive verifier、reset guard 三组。
- full-resign signed_by 场景只需要一个 signed archive fixture。

v12.9：

- 分成 runtime inventory、external binding、GA gate 三组。
- 底层 ZIP 污染和旧 report 场景复用同一 prepared command center world。

验收：

- v12.9-v12.12 加总耗时不超过 240 秒。
- v12 profile 总耗时不超过 360 秒。
- latest skip-tests 不超过 480 秒。

### Step 5：新增 v12.13 acceleration smoke

新增 check：

- `v1213.release_check_acceleration_smoke`

覆盖：

- fixture cache 命中。
- split check 选择正确。
- performance summary 有 slow/over-budget 字段。
- `--profile v12 --skip-tests --json` 不出现空检查集。
- `--only` split check 可单独运行。
- `--group command-center --since 12.9` 能选择 v12.9-v12.13。
- over-budget warning 不会掩盖 failed check。

建议 detail 输出：

- `fixture_cache=hit`
- `split_checks=present`
- `budget_summary=present`
- `v12_budget=passed`
- `latest_budget=passed`

### Step 6：profile 策略调整

当前 `V12_PROFILES = ("full", "quick", "latest", "ga", "v12")` 导致所有 v12 历史 smoke 都进入 latest/ga。

v12.13 建议引入更清楚的分层：

- `v12`：v12 全量 smoke，但使用拆分后轻量 checks。
- `latest`：只跑最新 v12.13 + 最近关键链路薄集成 + 基础 git/meta/security。
- `ga`：跑所有 GA gate 必需的功能 checks，但重型 ZIP attack matrix 应由 split security checks 控制预算。
- `full`：保留所有历史 checks 和 pytest.full。

注意：

- 不建议直接从 `ga` 移除关键安全 checks。
- 可以把重型攻击矩阵拆出去，但必须保留至少一个 GA gate 集成 check。
- 若某些深度攻击只适合 full，可以在 release-check report 中标明 `coverage_level=full_only`，但 v12.13 不建议第一版就大幅降级 GA。

### Step 7：防回退测试

必须补测试：

- matrix 包含 v12.13。
- v12 profile 包含拆分 checks。
- release-check JSON 包含 performance summary。
- budget overrun 会被记录。
- split checks 的 expected detail 覆盖旧 v12.12 信号。
- fixture cache 不跨进程复用。
- fixture cache 污染隔离：一个 tamper case 不影响后续 case。
- `git.status` 失败时，performance summary 仍输出。

## 9. 风险与防护

### 风险 1：拆分后安全覆盖被隐性减少

防护：

- 旧 v12.12 detail 信号列成硬断言。
- v12.13 smoke 必须检查 split checks 的 detail 合并集。
- reviewer 不接受“耗时下降但信号缺失”。

### 风险 2：fixture cache 污染测试

防护：

- 每个 tamper case 使用 fixture clone。
- 原始 prepared fixture 只读。
- cache hit 返回 copy，不返回原路径。

### 风险 3：性能预算变成 flaky

防护：

- 第一版可采用 warning + report，只有明显退化才 failed。
- 对关键目标使用宽松阈值：单项 90 秒、v12 360 秒、latest 480 秒。
- report 记录机器/平台/Python 版本。

### 风险 4：生产代码被测试 helper 污染

防护：

- fixture module 明确命名为 release-check 专用。
- 不被 Server/API/Store/verifier 生产路径调用。
- 不允许新增 `test_mode` 到生产 verifier。

## 10. 开发顺序建议

1. 先加 performance summary，不改现有 smoke。
2. 加 fixture cache 和 v12 prepared world helper。
3. 拆 v12.12。
4. 跑 v12 profile，确认耗时变化。
5. 拆 v12.11 / v12.10 / v12.9。
6. 加 v12.13 acceleration smoke。
7. 更新 README / CHANGELOG / version。
8. 跑 v12/latest/ga。
9. 提交。

## 11. 给开发的话

v12.13 不要继续叠新业务。现在最重要的是把 release-check 从“一个 smoke 串完整世界”改成“共享准备态 + 拆分语义/ZIP/GA 集成”。核心要求是：耗时降下来，但 v12.12 reviewer 已经认可的攻击面一个都不能少。

实现时先别急着改 profile 范围，先把 performance summary 和 v12.12 split 做出来。只要能证明 v12 profile 从约 17 分钟降到 6 分钟以内，同时旧 detail 信号全部还在，这版就有价值。任何为了快而跳过 runtime verifier、跳过 external binding、或者让 GA 只信旧 report 的改动，都不要做。

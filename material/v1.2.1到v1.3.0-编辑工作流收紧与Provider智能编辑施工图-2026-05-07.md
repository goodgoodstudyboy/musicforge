# MusicForge v1.2.1 到 v1.3.0 施工图：编辑工作流收紧与 Provider 智能编辑

> 基准版本：v1.2.0  
> 规划日期：2026-05-07  
> 执行原则：先用 v1.2.1 收紧 v1.2.0 的边界，再进入 v1.3.0 的 Provider-backed Edit 主线。  
> 核心判断：v1.2.0 已经形成“预设编辑 -> 版本对比 -> ZIP 交付”闭环，下一步不能盲目堆 UI，要把安全边界和智能编辑能力一起规划清楚。

---

## 1. 当前状态

v1.2.0 已完成并验证：

- Edit Preset Library：内置预设、本地用户预设、API、Studio Apply/Save。
- Project Compare：A/B 版本对比，包含质量、门禁、edit metadata、section、track、MIDI/WAV 状态。
- Final Export ZIP：基于现有 final-export 目录构建安全 ZIP，manifest 记录 size、sha256、entry_count。
- Project 搜索筛选：Studio 项目列表支持搜索、状态、variant 过滤。
- release-check 已覆盖 v1.2 workflow smoke。

本地核验结果：

```text
python -m pytest -q
368 passed

python -m song_agent.cli release-check
通过

python -m song_agent.cli doctor
通过
```

v1.2.0 当前不是“不能用”，而是“可用但需要收紧”。如果直接进入 v1.3.0 的 Provider 智能编辑，会把已有边界风险放大。

---

## 2. 总路线

推荐路线：

1. **v1.2.1：编辑工作流收紧版**
   - 不做大功能。
   - 专门修复 v1.2.0 的边界、兼容、可观测和 UI 小风险。
   - 发布一个小版本，确保后续 Provider edit 有稳定地基。

2. **v1.3.0：Provider 智能编辑版**
   - 让用户用自然语言改歌。
   - Provider 只产出受控 edit patch / SongPlan 候选。
   - 所有输出必须经过本地 schema、validator、quality、MIDI render、diff preview。
   - Studio 支持预览、确认、落盘成非破坏式项目版本。

一句话：

> v1.2.1 负责“守住边界”，v1.3.0 负责“把自然语言编辑接进来”。

## 4. v1.2.1 Package A：Final Export ZIP stale 收紧

### 4.1 问题

v1.2.0 已经能生成 ZIP，但要明确处理这些情况：

- final-export 目录重新生成后，旧 `final-export.zip` 可能还在。
- manifest 里的 zip 信息可能对应旧目录内容。
- Studio 可能显示 ZIP 可下载，但它已经不是当前 final-export 的 ZIP。

### 4.2 目标行为

推荐策略：

1. 每次 `build_final_export_bundle()` 重新生成 final-export 目录前，删除旧 `final-export.zip`。
2. manifest 里 `zip` 字段只代表当前 final-export 目录构建出来的 ZIP。
3. `GET /api/projects/<id>/final-export.zip` 如果 ZIP 不存在，返回 404。
4. Studio 如果 manifest 无 zip，显示 `ZIP not built`。
5. release-check 检查 final-export 重建后旧 zip 被清理。

### 4.3 推荐改动

修改：

- `song_agent/final_export.py`
- `song_agent/server.py`
- `tests/test_final_export.py`
- `tests/test_server_projects.py`

可新增 helper：

```python
def clear_final_export_zip(project_dir: Path) -> None:
    zip_path = final_export_zip_path(project_dir)
    if zip_path.exists():
        if zip_path.is_symlink():
            raise FinalExportError("Refusing to remove a symlinked final export ZIP.")
        zip_path.unlink()
```

在 `build_final_export_bundle()` 或 `_prepare_export_dir()` 前后清理旧 zip。推荐在确认 `project_dir` 边界后、替换 final-export 目录前清理。

### 4.4 测试

必须覆盖：

- 生成 final-export -> build zip -> 再生成 final-export，旧 zip 被删除。
- 旧 manifest zip 字段不会被新 manifest 保留。
- GET zip 在未 build 时返回 404。
- symlink zip 不被盲删。

### 4.5 验收命令


## 5. v1.2.1 Package B：Preset payload 和 merge 边界收紧

### 5.1 问题

v1.2.0 已做 preset 基础校验，但 Provider edit 前必须进一步保证：

- preset 默认 payload 和显式 intent merge 后，仍然必须经过完整 EditIntent 校验。
- 用户自定义 preset 不能靠深层字段绕过路径、token、文件字段限制。
- target_defaults 解析不到目标时，要有清晰错误或 Studio 提示，不能静默生成错误编辑。

### 5.2 目标行为

1. `merge_preset_intent()` 后的结果必须创建 `EditIntent` 并调用 `validate_edit_intent()`。
2. user preset 的 `payload`、`target_defaults`、嵌套 list/dict 都要检查敏感字段。
3. 对 `payload` 的 size 做限制，避免巨大 JSON 卡住 Studio。
4. `target_defaults` 如果解析不到必要目标，API 应返回清晰错误。
5. edit metadata 中保留 preset ref，但不保存完整 user preset payload。

### 5.3 推荐限制

建议新增常量：

```python
MAX_PRESET_JSON_BYTES = 16_384
MAX_PRESET_TEXT_FIELD = 240
MAX_PRESET_PAYLOAD_DEPTH = 6
```

敏感字段规则继续覆盖：

- `path`
- `file`
- `absolute_path`
- `local_path`
- `token`
- `api_key`
- 任意以 `_path` 结尾的 key
- 建议新增：`secret`、`password`、`credential`

### 5.4 测试

新增：

- 深层 payload 里含 `api_key` 被拒绝。
- payload JSON 过大被拒绝。
- target_defaults 指向不存在 section/track 时，API 返回 400 或明确错误。
- preset merge 后显式 intent 覆盖仍然有效。
- edit metadata 不包含完整 preset payload。

### 5.5 验收命令


## 6. v1.2.1 Package C：Compare API 和 Studio 布局收紧

### 6.1 问题

Compare 是创作决策核心，必须保证旧项目和异常输入不会崩。

重点场景：

- `left` 或 `right` 为空。
- left/right 是同一个版本。
- version 存在但 job output_dir 丢失。
- song-plan.json 缺失或旧 schema。
- edit-metadata.json 损坏。
- quality 缺失。
- 版本名、歌词、instruction 太长导致 Studio 撑破布局。

### 6.2 API 目标

`GET /api/projects/<id>/compare`：

- 缺 left/right：400，提示 `left and right version ids are required.`
- 版本不存在：404。
- 同版本对比：允许，summary recommendation 可以是 `tie`。
- 缺 plan：200，sections/tracks 空，quality fallback 到 ProjectVersion。
- 损坏 metadata：忽略 metadata，不 500。

### 6.3 Studio 目标

Compare tab：

- 长文本截断或换行。
- 表格在小屏横向滚动或分块显示。
- audio controls 不挤压 diff 表格。
- 缺 WAV 时显示 `WAV not rendered`，不要显示坏链接。

### 6.4 测试

新增：

- compare 缺 left/right 返回 400。
- compare 同版本返回 200。
- compare 缺 run_dir / song-plan 仍返回 200。
- 损坏 edit-metadata 不 500。
- webui 中 Compare 区域包含小屏布局 class 或 CSS。

## 8. v1.3.0 总目标

v1.3.0 的主题：

> Provider-backed Edit：让用户用自然语言对项目版本做受控修改，并通过本地验证层落成新的非破坏式版本。

用户要能说：

- “让最后一段副歌更燃一点，但不要改歌词。”
- “把第一段主歌变克制，鼓少一点，bass 简单一点。”
- “副歌换成更明亮的和弦，但旋律不要大改。”
- “给我 3 个 hook 文案变体，然后我对比选一个。”

系统要保证：

- Provider 不能直接写文件。
- Provider 不能绕过本地 schema。
- Provider 不能产出任意路径。
- Provider 输出必须变成受控 edit patch 或 SongPlan candidate。
- 最终仍然走本地 validator、quality、MIDI render、Project version、Compare。

---

## 9. v1.3.0 架构原则

### 9.1 Provider 只做建议，不做落盘

Provider 的职责：

- 理解自然语言编辑意图。
- 产出结构化 edit patch。
- 或产出完整 SongPlan candidate。

本地系统的职责：

- 校验 patch。
- 应用 patch。
- 校验 SongPlan。
- 修复低风险问题。
- 渲染 MIDI。
- 写 job/project/version。
- 记录 usage。

### 9.2 优先 patch，谨慎 whole-plan

推荐 v1.3.0 首选：

```text
自然语言 instruction -> Provider edit patch -> 本地 apply patch -> SongPlan candidate
```

不要一开始就让 provider 返回完整 SongPlan 作为唯一模式。完整 SongPlan 输出大、易错、token 高、调试困难。

可以支持两种模式：

| 模式 | 名称 | v1.3.0 建议 |
| --- | --- | --- |
| `patch` | Provider 返回 edit patch | 必做 |
| `song_plan` | Provider 返回完整 SongPlan | 可选，默认关闭 |

### 9.3 所有 Provider 输出都要本地复核

必须经过：

1. JSON parse。
2. schema 校验。
3. path/secret 字段扫描。
4. EditIntent / patch 校验。
5. SongPlan.from_dict。
6. validator。
7. quality analyze。
8. MIDI render smoke。
9. Project version 非破坏式落盘。

## 11. v1.3.0 Package B：Provider Edit Patch Schema

### 11.1 目标

定义 Provider 可以返回什么，不能让模型随便产出任意 SongPlan。

新增一个受控 patch schema：

```json
{
  "schema_version": 1,
  "summary": "Lift final chorus energy",
  "operations": [
    {
      "op": "set_section_energy",
      "section_name": "chorus",
      "energy": 0.9,
      "preserve": ["lyrics", "harmony"]
    }
  ],
  "warnings": [],
  "confidence": 0.82
}
```

### 11.2 支持的 operations

v1.3.0 先支持少量高价值操作：

| op | 说明 |
| --- | --- |
| `set_section_energy` | 修改 section energy / density 相关特征 |
| `set_section_chords` | 修改 section chords，必须使用支持和弦白名单 |
| `set_track_density` | 修改指定 track 在 section 的密度 |
| `rewrite_section_lyrics` | 修改指定 section 歌词 |
| `melody_variation` | 指定 section 的轻量旋律变化 |
| `arrangement_variation` | 轻量编配变化 |

不要开放：

- 任意 Python 代码。
- 任意文件路径。
- 任意 MIDI event raw bytes。
- 任意外部 URL。

### 11.3 文件建议

新增：

- `song_agent/provider_edits.py`
- `tests/test_provider_edits.py`

### 11.4 数据结构

```python
@dataclass
class ProviderEditPatch:
    schema_version: int
    summary: str
    operations: list[ProviderEditOperation]
    warnings: list[str]
    confidence: float
```

每个 operation 都要：

- 限制 op 名称。
- 限制字段。
- 校验目标存在。
- 校验数值范围。
- 校验 chords 白名单。
- 校验文本长度。

### 11.5 Patch 应用

推荐复用 v1.1.x 的 local edit engine：

- Provider patch -> 转成一组 `EditIntent`
- 对 parent SongPlan 顺序 apply
- 每一步 validate
- 最终 analyze quality

如果某个 op 无法映射到现有 EditIntent，再新增最小能力，不要绕过 edit engine。

### 11.6 测试

- 合法 patch 能应用。
- 非法 op 被拒绝。
- 非法 chord 被拒绝。
- 不存在 section/track 被拒绝。
- patch 里出现 path/token 被拒绝。
- 多 operation 顺序应用后 parent plan 不变。

## 12. v1.3.0 Package C：Provider-backed Edit Pipeline

### 12.1 目标

在 Project Edit 的基础上支持 `provider_mode=provider`。

当前 v1.1.x/v1.2.x 的 local edit 是：

```text
parent version -> EditIntent -> local edit engine -> child job/version
```

v1.3.0 增加：

```text
parent version -> natural instruction -> provider patch -> local apply -> validator/quality/render -> child job/version
```

### 12.2 Job 类型

可以复用 edit job，但 metadata 要区分：

```json
{
  "edit_type": "provider_patch",
  "provider_mode": "provider",
  "instruction": "...",
  "provider": {
    "provider_type": "openai-compatible",
    "model": "xxx",
    "usage_id": "..."
  },
  "patch": {
    "operation_count": 2,
    "summary": "..."
  }
}
```

不要在 metadata 里保存明文 key。

### 12.3 API

扩展现有：

```text
POST /api/projects/<project-id>/versions/<version-id>/edit
```

新增 payload：

```json
{
  "provider_mode": "provider",
  "instruction": "Make the final chorus more energetic but keep lyrics.",
  "template_id": "provider-edit-intent",
  "preview": false,
  "start_immediately": true
}
```

如果 `preview=true`，不直接创建最终 child version，只创建 preview 或返回 patch。

也可以新增专门 endpoint：

```text
POST /api/projects/<project-id>/versions/<version-id>/edit-preview
POST /api/projects/<project-id>/versions/<version-id>/edit-apply
```

推荐 v1.3.0 做 preview/apply 分离，Studio 体验更清晰。

### 12.4 Pipeline 步骤

Provider edit job 建议事件：

1. `provider_edit_started`
2. `prompt_template_loaded`
3. `provider_request_started`
4. `provider_response_received`
5. `provider_patch_validated`
6. `provider_patch_applied`
7. `song_plan_validated`
8. `quality_analyzed`
9. `midi_rendered`
10. `project_version_created`
11. `provider_edit_completed`

### 12.5 错误处理

- Provider 未配置：400，提示先配置 Provider。
- Provider timeout：job failed，保留错误脱敏信息。
- Provider 返回非 JSON：job failed，保存 sanitized raw excerpt，不超过 500 字符。
- Patch 校验失败：job failed，记录 validation errors。
- SongPlan validator 失败：尝试 repair；repair 失败则 failed。
- 失败不创建 completed child version，或创建 failed version 时必须明确 status。

### 12.6 测试

- mock provider 成功返回 patch。
- fake opener 覆盖 OpenAI-compatible response。
- 非 JSON response 失败且脱敏。
- patch invalid 失败且 parent 不变。
- provider key 不进入 job-state、metadata、logs、API。
- provider edit 成功后可 compare。

## 17. v1.3.0 Reviewer 核心检查点

### 17.1 Provider 输出安全

必须检查：

- Provider 输出不能直接落盘。
- Provider 输出不能包含路径字段并被执行。
- 非 JSON / schema 错误不会 500。
- provider key 不出现在：
  - job-state.json
  - edit-metadata.json
  - provider-usage.json
  - events.jsonl
  - API response
  - release-check output

### 17.2 Parent version 不变

所有 provider edit 必须非破坏式：

- parent `song-plan.json` 不变。
- parent MIDI 不变。
- parent project version 不被覆盖。
- child version 有明确 lineage。

### 17.3 Preview 不污染正式版本

Preview 阶段：

- 不增加正式 project version。
- 不改 selected/final。
- 不覆盖 parent artifacts。

Apply 阶段：

- 才创建正式 job/version。
- 重新本地验证。

### 17.4 Prompt Template 安全

- user template 不被提交。
- prompt 长度有限制。
- template override 可 reset。
- built-in template 不可删除。

### 17.5 Usage 可观测

- usage 能看到 model、latency、tokens。
- 失败调用也有记录。
- 不泄露 key。

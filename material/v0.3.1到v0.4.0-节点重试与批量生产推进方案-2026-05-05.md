# MusicForge v0.3.1 到 v0.4.0 推进方案：节点重试、下游失效与批量生产

当前版本是 `v0.3.0`。它已经把 MusicForge 从单 composer 升级成了可观察的 multinode pipeline：

- 每个 agent node 都有结构化 schema。
- 每个 node 都能落盘到 `data/nodes/`。
- Studio 有 Nodes tab。
- provider-backed planning nodes 已接入。
- critic / repair / song_plan_builder 已跑通。
- `pipeline_mode=single|multinode` 已进入 CLI 和 Studio。

这说明“多 Agent 音乐生成后端”已经成型。下一步不要立刻堆更多模型能力，也不要马上上音频渲染。现在最该补的是：

```text
v0.3.1：节点级重试 + 下游失效 + 节点结果复用保护
v0.4.0：批量生产 batch console
```

原因很直接：批量生产会一次性跑很多首歌。如果单首歌内部的 node 失败后只能整首重跑，后面 batch 的失败恢复成本会很高，面板体验也会很粗。先把 node-level retry 做扎实，再做 batch，后续返工最少。

## 1. 总体判断

### 1.1 现在已经具备的能力

`v0.3.0` 已经满足：

- 单首歌本地生成。
- 单首歌 provider 生成。
- 多节点编排。
- 节点落盘和查看。
- 整个 job retry。
- job cancel / delete / hide。
- runtime views。
- provider key 脱敏。

### 1.2 现在缺的能力

最关键缺口：

- 节点 retry 现在只是 `501` 占位。
- 重跑某个 node 后，下游节点没有失效机制。
- 节点之间依赖关系还没有显式持久化。
- provider node 失败后不能从失败节点继续。
- Studio 不能对某个 node 单独执行 retry。
- batch 还没有数据模型、导入、并发、导出和失败恢复。

### 1.3 推荐顺序

必须按这个顺序：

1. `v0.3.1`：node-level retry。
2. `v0.3.2`：可选，局部 regenerate，比如只改歌词、只改和声、只改配器。
3. `v0.4.0`：batch 批量生产。
4. `v0.5.0`：音频渲染和浏览器试听。
5. `v0.6.0`：安全、鉴权、发布保护。

如果开发资源有限，`v0.3.2` 可以跳过，直接从 `v0.3.1` 进入 `v0.4.0`。

## 2. v0.3.1 目标

`v0.3.1` 的目标不是新增更复杂的音乐能力，而是让 multinode pipeline 变成真正可运维、可恢复、可局部重跑的系统。

一句话目标：

```text
用户能在 Studio 里选择某个失败或不满意的 node，点击 Retry，只重跑必要节点，并自动失效下游产物，最终重新生成 song-plan 和 MIDI。
```

## 3. v0.3.1 不做什么

明确不做：

- 不做 batch。
- 不做 WAV/MP3 音频渲染。
- 不做复杂图编辑器。
- 不做任意 DAG 拖拽。
- 不做真实多模型路由。
- 不做人工编辑 node JSON 后继续运行。
- 不做完整局部音乐编辑器。

这些可以以后做，但 `v0.3.1` 要保持范围清楚。

### 4.1 节点依赖图

建议位置：

```text

```

推荐定义：

```python
NODE_DEPENDENCIES = {
    "brief_planner": [],
    "style_planner": ["brief_planner"],
    "structure_planner": ["brief_planner", "style_planner"],
    "lyric_planner": ["brief_planner", "structure_planner"],
    "harmony_planner": ["brief_planner", "structure_planner"],
    "melody_planner": ["style_planner", "structure_planner"],
    "arrangement_planner": ["style_planner", "structure_planner", "melody_planner"],
    "critic": ["arrangement_planner", "harmony_planner", "lyric_planner"],
    "repair": ["critic"],
    "song_plan_builder": ["repair"],
}
```

同时提供：

```python
def downstream_nodes(node_name: str) -> list[str]:
    ...

def upstream_nodes(node_name: str) -> list[str]:
    ...

def affected_nodes_for_retry(node_name: str) -> list[str]:
    ...
```

### 4.2 节点状态

当前 node record 已有：

- `node`
- `status`
- `started_at`
- `finished_at`
- `attempt_count`
- `provider_snapshot`
- `input_summary`
- `output_summary`
- `output`
- `error`

`v0.3.1` 建议增加：

```text
invalidated_at
invalidated_by
retry_count
last_error
depends_on
```

节点状态建议统一成：

```text
pending
running
completed
failed
skipped
repaired
invalidated
```

注意：`invalidated` 不代表节点失败，它代表上游被重跑后，这个节点旧结果不能再信。

### 4.3 失效规则

当 retry 某个节点：

1. 校验 node name。
2. 找到下游 affected nodes。
3. 把目标节点和所有下游节点标记为 `invalidated`。
4. 删除或保留旧 output 要统一。
5. 从目标节点开始重新执行 pipeline。
6. 成功后写新的节点 record。
7. 重写：
   - `data/song-plan.json`
   - `renders/song.mid`
   - `data/validator-report.json`
   - `data/run-summary.json`
   - `data/job-state.json`

建议保留旧 output，但 summary 上明确标记 invalidated。这样 reviewer 能追踪历史。

### 4.4 retry 起点

第一版不要支持从任意中间缓存恢复太复杂。建议实现：

```text
重跑目标 node + 全部下游 node
上游 node 从既有 record.output 读取
```

例如 retry `lyric_planner`：

- 读取旧的 `brief_planner`
- 读取旧的 `style_planner`
- 读取旧的 `structure_planner`
- 重跑 `lyric_planner`
- 重跑 `critic`
- 重跑 `repair`
- 重跑 `song_plan_builder`
- 重写 final song-plan 和 MIDI

例如 retry `brief_planner`：

- 所有节点都要重跑，因为它是最上游。

例如 retry `critic`：

- 重跑 `critic`
- 重跑 `repair`
- 重跑 `song_plan_builder`
- 重写 final song-plan 和 MIDI

### 4.5 provider 配置

provider node retry 必须遵守：

- 仍然使用当前 `.musicforge/provider.json` 或 env config。
- 写新的 masked provider snapshot。
- node record 和 job state 不能泄露明文 key。
- provider 配置缺失时，返回 400，不破坏旧产物。

### 4.6 cancel 与 retry

node retry 本质上是一次 job 运行。建议：

- 只有 `completed` / `failed` / `stalled` / `interrupted` job 可以 node retry。
- `running` job 不允许 node retry，返回 409。
- node retry 期间 job status 变成 `running`。
- cancel 请求仍然能在节点边界停止。

## 5. v0.3.1 API 设计

### 5.1 重试节点

当前已有占位：

```text
POST /api/jobs/<job_id>/nodes/<node_name>/retry
```

`v0.3.1` 需要把它从 501 变成真实实现。

成功返回：

```json
{
  "ok": true,
  "job": {},
  "retry": {
    "node": "lyric_planner",
    "affected_nodes": ["lyric_planner", "critic", "repair", "song_plan_builder"]
  }
}
```

错误情况：

- job 不存在：404
- node 不存在：404
- node name 非法：400
- job running：409
- job pipeline_mode 不是 multinode：409
- provider 配置缺失：400

### 5.2 查看依赖

建议新增：

```text
GET /api/jobs/<job_id>/nodes/<node_name>/dependencies
```

返回：

```json
{
  "job_id": "demo",
  "node": "lyric_planner",
  "upstream": ["brief_planner", "structure_planner"],
  "downstream": ["critic", "repair", "song_plan_builder"]
}
```

如果时间紧，这个 API 可以不做，但 Studio retry 确认弹窗需要 affected nodes 信息。

### 5.3 list nodes 增强

`GET /api/jobs/<job_id>/nodes` 里每个 node summary 增加：

```json
{
  "depends_on": [],
  "retry_count": 0,
  "invalidated_at": null,
  "invalidated_by": null,
  "can_retry": true
}
```

```python

    request: SongRequest,
    node_name: str,

    provider_config: ProviderConfig | None,
    provider_snapshot: dict | None,
    node_store: NodeStore,
    control: ControlFn | None = None,
) -> SongPlan:
    ...
```

策略：

- 对上游 completed node，读取 `record.output` 并转换为对应 schema。
- 对目标和下游 node，重新运行。
- 最终返回新的 `SongPlan`。

第一版可以只支持固定 pipeline，不做任意 DAG。

## 14. v0.4.0 调度策略

第一版不要引入复杂队列库。继续用标准库线程即可。

要求：

- batch launch 时，根据 `max_concurrency` 启动 item。
- 每个 item 复用现有 `JobStore.create_job()`。
- item 状态由 job 状态同步。
- batch 状态由 item 聚合。
- server 重启后能从 `.musicforge/batches/` 和 `runs/` 恢复。
- `retry-failed` 只重试 failed / stalled / interrupted items。

第一版建议限制：

```text
max_concurrency: 1 到 4
```

本地工具没有必要一开始无限并发，尤其 provider 模式容易打爆 API。

## 19. 给开发的最终执行原则

开发必须遵守：

- 每个功能包完成后都要测试、commit、push。
- 不要把多个大功能攒成一个提交。
- 不要把 `.musicforge/provider.json`、真实 key、个人路径提交。
- 不要破坏旧 CLI：
  - `python -m song_agent.cli examples\song_request.json --out runs\demo --force`
  - `python -m song_agent.cli generate examples\song_request.json --out runs\demo --force`
- 不要让 provider 成为默认依赖，本地 deterministic 必须永远可跑。
- 新增 API 必须有测试。
- 新增 UI 行为至少有静态测试或 API smoke。

## 20. Reviewer 核验重点

`v0.3.1` reviewer 重点：

- node retry 是否真的不再返回 501。
- retry 上游 node 时，下游是否 invalidated 并重跑。
- retry 中游 node 时，上游是否复用，不被误重跑。
- failed provider node 是否可重试。
- provider 明文 key 是否不泄露。
- running job 是否禁止 node retry。
- single pipeline job 是否禁止 node retry。
- retry 后 `song-plan.json`、`song.mid`、validator report 是否更新。
- 测试是否覆盖路径穿越和非法 node name。

`v0.4.0` reviewer 重点：

- CSV 导入是否校验 required columns。
- batch item 是否复用单 job 状态机。
- max concurrency 是否真的生效。
- pause 是否停止启动新 item。
- retry failed 是否只重试失败项。
- export 是否包含每首歌状态、job_id、output_dir、error。
- 删除 batch 是否不会误删 runs 产物。
- provider batch 是否不泄露 key。

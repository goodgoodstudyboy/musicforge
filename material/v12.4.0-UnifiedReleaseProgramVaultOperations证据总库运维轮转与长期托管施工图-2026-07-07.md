# v12.4.0 Unified Release Program Vault Operations 证据总库运维轮转与长期托管施工图

> 建议下一版：v12.4.0  
> 当前稳定基线：v12.3.0  
> 核心目标：把 v12.3 的 Unified Release Program Evidence Vault 从“一次性封存包”升级成“可长期托管、可周期复验、可轮转、可交接、可撤销/替换、可离线审计”的 Program 级证据生命周期系统。v12.4 不再继续堆新的 Program gate，而是围绕 Vault 建立运维层：Vault Registry、Custody Policy、Review Run、Rotation Plan、Transfer Pack、Custody Signoff、固定结构 Archive ZIP 和离线 verifier。

---

## 1. 背景

v12.0 到 v12.3 已经完成了 Program 级主线：

- v12.0 Unified Release Program Board：聚合多个 Release Train Handoff，形成 Program 级准出。
- v12.1 Program Operations Center：支持 Program CR、safe runbook、continuous review、lifecycle audit。
- v12.2 Program Final Handoff Board：支持外部验收、accepted evidence、decision board、handoff signoff。
- v12.3 Program Evidence Vault：把 Program / Operations / Handoff / accepted evidence 封装进 Vault，支持外部 anchor 和 deep offline verification。

v12.3.0 已经修过关键 P1：

- Vault package 固定 allow-list。
- deep preflight 阻断危险结构。
- temp root containment。
- raw backslash ZIP entry 检测。
- forged package-index + forged anchor 回归。

因此 v12.3 已经可以回答：

> “这个 Program 的全部准出证据是否被封存在一个可离线深度复验的 Vault 里？”

但真实长期交付还缺下一层：

1. Vault 不是生成一次就结束，它需要周期复验。
2. Vault anchor 是外部证明，必须记录当前 anchor 是否仍被认可。
3. 如果底层 Program / Operations / Handoff 有后续 reset 或 supersede，旧 Vault 不能继续被误认为 current。
4. 如果需要把 Vault 交给外部审计方、法务、长期存储方，需要 transfer pack 和 custody receipt。
5. 如果 Vault ZIP、anchor、verification report 任一发生漂移，需要明确是 stale、tampered、superseded、revoked 还是 storage_lost。
6. 如果要重新封存 Vault，必须生成新 Vault generation，不能静默覆盖旧 Vault。
7. Release / GA gate 现在可以要求 Vault passed，但不能证明 Vault 已被长期托管策略接管。

所以 v12.4 建议进入：

**Unified Release Program Vault Operations**

中文名：

**项目级证据总库运维轮转与长期托管**

---

## 2. 版本定位

### 2.1 一句话

v12.4 是 Program Evidence Vault 的生命周期运维层：它记录每一代 Vault 的 current / superseded / revoked 状态，周期性 deep verify，生成轮转计划和托管交接包，并用独立签核和离线 verifier 证明 Vault 已进入可长期保存的受控状态。

### 2.2 和 v12.3 的关系

v12.3：

- 生成单个 Evidence Vault。
- 生成 `vault-anchor.json`。
- 生成 Vault verification report。
- 支持 deep verifier。
- 支持 Release / GA gate 要求 Vault passed。

v12.4：

- 不替代 v12.3 Vault。
- 不改变 v12.3 Vault ZIP 格式。
- 在 v12.3 之上建立 Vault Registry 和 Custody Operations。
- 负责判断哪个 Vault generation 是 current。
- 负责记录周期复验、轮转、撤销、交接和签核。
- 负责输出 Vault Operations Archive ZIP。

### 2.3 本版必须解决的问题

1. 建立 Vault Registry，记录一个 Program 下所有 Vault generations。
2. 每个 generation 绑定：
   - Vault ZIP hash / size。
   - Vault manifest hash。
   - Vault source hash。
   - Vault anchor hash。
   - Vault verification report hash。
   - deep verification status。
   - state：`current` / `superseded` / `revoked` / `archived` / `lost`。
3. 建立 Custody Policy：
   - review interval。
   - required deep verification。
   - required accepted evidence。
   - required anchor。
   - required replicas。
   - allowed custodian roles。
   - retention class。
4. 支持 Custody Review Run：
   - 重新运行 v12.3 deep verifier。
   - 校验 Vault ZIP、anchor、verification report 是否仍匹配。
   - 输出 review report。
   - 标记 stale / tampered / missing / current / superseded。
5. 支持 Rotation Plan：
   - 当当前 Vault stale、底层 Program/Handoff/Operations 发生更新、policy 变化、anchor 变化、或 custodian 要求重封存时，生成明确计划。
   - 计划只描述动作，不自动改底层 Program。
6. 支持 Vault Supersede / Revoke：
   - Supersede 必须指向新的 passed Vault generation。
   - Revoke 必须写明原因。
   - Revoked Vault 不可作为 Release / GA gate evidence。
7. 支持 Custody Transfer Pack：
   - 面向外部审计/法务/长期存储方。
   - 包含 registry summary、current Vault fingerprint、anchor summary、review run summary、replica checklist、recipient guide。
   - 不泄漏本机路径和密钥。
8. 支持 Custody Signoff：
   - 对当前 registry + policy + latest review + transfer pack 做签核。
   - 签核时独立落盘 `vault-operations-signoff-binding-summary.json`。
   - 签核后 refresh / review / supersede / revoke / export / zip 的可变写操作必须受限。
9. 支持 Vault Operations Archive ZIP：
   - 固定结构。
   - 包含 current Vault ZIP 或其固定路径副本。
   - 包含外部 anchor、verification report、registry、policy、review run、transfer pack、signoff binding。
   - 离线 verifier 可深度复验。
10. 接入 Release signoff 和 GA readiness：
    - `require_unified_release_program_vault_operations=true`。
    - 必须绑定当前 Vault Operations Archive ZIP、verification report、signoff binding。
11. release-check 增加 v12.4 smoke。

### 2.4 本版不做什么

v12.4 不做：

- 不修改 v12.3 Vault ZIP 内部结构。
- 不自动重建 Program / Operations / Handoff。
- 不自动 approve CR。
- 不自动 reset Program。
- 不自动导入新的外部 reviewer response。
- 不引入真实 PKI / 第三方 CA。
- 不做公网发布或 Transparency Feed。
- 不做跨多个 Program 的 portfolio 排名。
- 不做分布式存储同步。

如需真正外部签名、时间戳服务、远程 registry，应该放到 v12.5+。

## 3. 核心设计原则

### 3.1 Vault Operations 是生命周期层，不是证据生成层

它不能替代 v12.3 的 Vault verifier。

所有“这个 Vault 是否真实有效”的判断必须调用：

```bash
python -m song_agent.cli verify-unified-release-program-vault-package ... --deep --require-anchor
```

v12.4 只负责记录：

- 哪个 Vault 当前有效。
- 何时复验过。
- 是否需要轮转。
- 是否已交接给 custodian。
- 是否已被签核进入长期托管。

### 3.2 Registry 不能只信自身 JSON

Vault Registry 的每条 generation 必须能反查外部证据：

- Vault ZIP。
- Vault anchor。
- Vault verification report。

Verifier 不能只看 registry 里的 hash。它必须运行或验证 runtime report：

- `zip_sha256`。
- `zip_size_bytes`。
- `manifest_hash`。
- `source_hash`。
- `verification_report_hash`。
- `anchor_hash`。

### 3.3 Supersede / revoke 是显式事件

不能因为新 Vault 生成就自动把旧 Vault 标成 superseded，除非调用显式动作：

- `supersede_vault(old_generation_id, new_generation_id, reason)`
- `revoke_vault(generation_id, reason)`

每个事件写入 hash-chain history。

### 3.4 签核后不可静默变更

一旦 Vault Operations signoff：

- `refresh_registry` -> 409。
- `run_review` -> 409。
- `create_rotation_plan` -> 409。
- `supersede` -> 409。
- `revoke` -> 409。
- `export_archive` -> 409，除非 archive 尚未创建且只复制签核时 frozen snapshot。
- `build_zip` -> 409，除非 ZIP 尚未创建且只打包 frozen export。

v12.4 建议采用和 v11.6 / v12.2 一致的策略：

- signoff 时冻结 docs + binding。
- signoff 后允许一次 immutable archive build。
- archive/verifier 只能复制 frozen snapshot，不能重新计算 source docs。

### 3.5 Binding sidecar 必须签核时落盘

`vault-operations-signoff-binding-summary.json` 必须在 signoff 创建时生成。

禁止 archive/export 时从 `vault-operations-signoff.json` 现读现算。

Verifier 必须用外部 binding proof 反查：

- signer。
- role。
- reason。
- signed_at。
- signoff hash。
- history latest event hash。
- registry hash。
- policy hash。
- latest review hash。
- current Vault generation fingerprint。
- archive manifest hash。

### 3.6 Archive ZIP 必须固定结构

不能允许 manifest 自己声明额外文件通过。

Verifier 必须有固定 allow-list：

- 固定 core docs。
- 固定 current Vault package/proofs。
- 可按 generation_id 允许的历史 review reports，但路径必须由 registry 派生。

任何 extra entry、duplicate entry、反斜杠、`.MusicForge/`、`../`、nested 未授权 ZIP 都失败。

## 9. Offline Verifier 设计

### 9.1 固定结构

Archive ZIP 必须只允许：

```text
manifest.json
vault-operations-report.json
registry.json
policy.json
latest-review-report.json
rotation-plan-summary.json
transfer-report.json
vault-operations-signoff.json
vault-operations-signoff-binding-summary.json
vault-operations-history.jsonl
packages/current-vault.zip
proofs/current-vault-anchor.json
proofs/current-vault-verification-report.json
docs/recipient-guide.md
docs/replica-checklist.json
README.txt
```

如果允许历史 review reports，则路径必须由 registry/review index 派生：

```text
reviews/<run-id>/review-report.json
reviews/<run-id>/runtime-vault-verification-report.json
```

`run-id` 必须通过 safe identifier 校验。

### 9.2 必须检查

Verifier checks：

- ZIP 存在。
- 无 duplicate entries。
- entry count 限制。
- uncompressed size 限制。
- path 安全：
  - no absolute。
  - no `..`。
  - no backslash。
  - no `.musicforge/`，大小写不敏感。
- raw central directory backslash scan。
- package_type。
- schema_version。
- manifest integrity。
- manifest.files 精确匹配固定 allow-list。
- manifest file hash。
- registry integrity。
- policy integrity。
- latest review integrity。
- transfer report integrity。
- signoff integrity。
- signoff binding integrity。
- history hash-chain。
- binding sidecar 和 signoff/history/registry/policy/review/transfer 的交叉校验。
- current Vault ZIP hash。

- current Vault verification report hash。
- runtime deep Vault verification。
- redaction scan。

### 9.3 不可信内容

Verifier 不得信任：

- manifest.zip.entries 作为 allow-list 来源。
- registry.current_generation_id 自证。
- review-report.status 自证。
- transfer-report.status 自证。
- signoff.signed_by 自证。
- package-index 自行声明的额外 nested ZIP。

所有关键判断必须由：

- fixed allow-list。
- external signoff binding。
- runtime v12.3 Vault verifier。
- history hash-chain。
- current generation fingerprint。

共同决定。

## 18. 给开发的话

v12.4 不要做成“又一个 summary 报表”。这版的核心是让 v12.3 Vault 进入受控生命周期：

- Registry 要能回答“哪个 Vault 是当前有效版本”。
- Custody Review 要能回答“当前 Vault 今天重新深度复验是否仍然通过”。
- Rotation Plan 要能回答“为什么需要重封存，下一步手工做什么”。
- Transfer Pack 要能回答“交给外部 custodian 时对方该拿什么、怎么验”。
- Signoff / Archive 要能回答“这个托管状态已经被冻结，不能被静默改写”。

实现优先级：

1. Store + verifier + P1 回归先做。
2. Release / GA gate 第二。
3. CLI / Server 第三。
4. Studio 最后接按钮。

不要先做 UI。只要 verifier 和 signed immutability 有洞，UI 做得再完整也会被打回。

# v10.3.0 Audio Fix Sprint 音频问题修复冲刺与人工复验闭环施工图

> 目标读者：MusicForge 开发执行人员  
> 当前稳定基线：v10.2.1  
> 规划角色：Reviewer / Planner  
> 计划版本：v10.3.0  
> 文档日期：2026-06-24

---

## 1. 背景

v10.2.1 已经把 Audio Lab 的基础闭环做出来了：可以检查真实音频环境，可以跑 MIDI/WAV smoke，可以创建人工试听 session，可以记录 marker，可以做 A/B comparison，并且修掉了 `needs_fix` close 语义和测试 WAV 被误读为 release-ready 的问题。

现在的问题不再是“能不能听”，而是“听出问题后如何系统化修掉”。如果每个 marker 都只生成一个孤立 draft，开发仍然需要人工到处找问题、排优先级、生成候选、A/B 对比、复验、关闭问题。这个过程如果不产品化，就会回到手工混乱状态。

v10.3.0 应该把 v10.2 的 Audio Lab marker 推进成 Audio Fix Sprint：

- 聚合一个或多个 Listening Session 中的 `needs_fix` / `rejected` / high severity marker。
- 自动分类、去重、排序。
- 给每个问题生成明确 fix item。
- 允许批量创建 ReviewTask / AudioRevision draft / MixPatch draft。
- 为每个 fix item 生成可听候选，但不自动 apply。
- 用 A/B review 选择候选。
- 修复后跑 recheck session。
- 最后生成 closeout report，明确哪些问题已解决、哪些仍需人工处理。

这一版仍然不做外部音乐 API，也不允许系统替代人工判断。它的核心是让“听审发现问题 -> 修复 -> 再听 -> 关闭”成为可追踪的工程流程。

---

## 2. 总目标

v10.3.0 的目标：

> 建立 Audio Fix Sprint，把 Audio Lab 的人工听审问题转成有优先级、有候选、有 A/B、有复验、有关闭报告的本地修复冲刺。

开发完成后应能做到：

1. 从一个或多个 Audio Lab Listening Session 创建 Fix Sprint。
2. 自动收集 `needs_fix` / `rejected` item 和 marker。
3. 对 marker 做分类、去重、排序。
4. 为每个 fix item 创建修复草稿。
5. 批量生成本地候选。
6. 对候选做 A/B 人工 review。
7. 选择候选并创建非破坏式 Project Version 或 draft evidence。
8. 重新渲染 WAV。
9. 创建 recheck listening session。
10. 关闭 sprint 并生成 closeout report。

---

## 3. 不做什么

本版明确不做：

- 不自动 apply 任何候选。
- 不允许 provider 自动修复并直接进入 release-ready。
- 不把 synthetic review 当人工复验。
- 不新增公开信任包。
- 不要求真实 SoundFont 提交仓库。
- 不做复杂 DAW 级音频编辑。
- 不做多用户权限系统。
- 不接外部 ticket 系统。
- 不把 Audio Fix Sprint 立即变成 GA 强制门禁。

## 8. Sprint 创建

### 8.1 创建来源

支持：

- 单个 Audio Lab Listening Session。
- 多个 Audio Lab Listening Session。
- Audio Lab session report。

不建议 v10.3 支持 release audio review 直接创建，避免与已有 Audio Revision Workbench 范围重叠。可以保留扩展点。

### 8.2 收集规则

收集：

- review result 为 `needs_fix` 的 item。
- review result 为 `rejected` 的 item。
- severity 为 high / critical 的 marker。
- category 属于音频修复范围的 marker。

排除：

- stale item。
- MIDI-only item。
- test_fake 且未明确允许 `include_test_audio=true` 的 item。
- 已经被同一个 open sprint 引用过的 marker。

### 8.3 Duplicate guard

同一个 `session_id + item_id + marker_id + marker_source_hash` 不允许进入两个 open sprint。

如果用户重复创建，应返回：

```text
409 Audio Lab marker is already assigned to an open Audio Fix Sprint.
```

### 8.4 CLI

```bash
python -m song_agent.cli audio-fix-sprint create --from-session als-000001 --name "Fix first smoke pass" --json
python -m song_agent.cli audio-fix-sprint list --json
python -m song_agent.cli audio-fix-sprint detail afs-000001 --json
python -m song_agent.cli audio-fix-sprint refresh afs-000001 --json
```

## 9. Issue Ranking

### 9.1 排序目标

开发打开 sprint 后，应该先知道哪些问题最重要。

### 9.2 Priority score

建议 deterministic scoring：

```text
priority =
  severity_weight
  + review_result_weight
  + audio_health_weight
  + repeated_category_weight
  + release_ready_risk_weight
```

权重建议：

```text
critical marker: +50
high marker: +35
medium marker: +20
rejected item: +40
needs_fix item: +25
audio health failed: +30
audio health warning: +15
category repeated across sessions: +10
test fake source: -20
```

### 9.3 输出

`issue-index.json`：

```json
{
  "summary": {
    "issue_count": 3,
    "critical_count": 0,
    "high_count": 2,
    "top_category": "mix_balance"
  },
  "items": [
    {
      "fix_item_id": "afi-000001",
      "priority": 75,
      "category": "mix_balance",
      "reason": ["high severity", "needs_fix review"]
    }
  ]
}
```

## 11. Candidate 生成

### 11.1 v10.3 首选候选类型

首选支持本地 deterministic candidate：

- `mix_patch_candidate`
- `audio_revision_candidate`

如果现有 Audio Revision Workbench 需要 Release 上下文才能工作，v10.3 可以先把候选定义为 draft candidate，不强制生成真实 Project Version。

### 11.2 候选生成规则

```bash
python -m song_agent.cli audio-fix-sprint generate-candidates afs-000001 --local --json
```

API：

```text
POST /api/audio-fix-sprints/<id>/generate-candidates
```

payload：

```json
{
  "mode": "local",
  "fix_item_ids": ["afi-000001"],
  "render_audio": "auto"
}
```

### 11.3 必须保持手动 apply

即使候选生成成功，也只能：

- 预览。
- 下载 MIDI/WAV。
- 创建 A/B comparison。
- 人工选择。

不能自动 apply。

### 11.4 Renderer 语义

如果使用测试 WAV writer：

- candidate 可以生成。
- candidate report 必须标记 `runner_kind=test_fake`。
- `release_ready=false`。
- closeout 不能把它当真实音频修复证据。

## 12. A/B Review 集成

### 12.1 每个候选都应能创建 A/B

候选生成后可以自动创建 comparison：

- left = 原始 WAV。
- right = candidate WAV。

### 12.2 Review gate

候选 selected 前必须有人工 A/B review：

- `review_mode=manual`
- `playback_confirmed=true`
- `preferred in {right, same}`
- rating 不低于原始问题设定阈值

如果 `preferred=left`，候选不能被 selected。

### 12.3 API

```text
POST /api/audio-fix-sprints/<id>/items/<fix-item-id>/candidates/<candidate-id>/ab-review
POST /api/audio-fix-sprints/<id>/items/<fix-item-id>/candidates/<candidate-id>/select
```

## 13. Recheck Session

### 13.1 目标

Fix Sprint 的关闭不能只看候选被选择，必须重新听。

### 13.2 Recheck 创建

```bash
python -m song_agent.cli audio-fix-sprint create-recheck-session afs-000001 --json
```

API：

```text
POST /api/audio-fix-sprints/<id>/recheck-session
```

Recheck session 应复用 Audio Lab Listening Session。

### 13.3 Recheck 规则

closeout 要求：

- 每个 selected candidate 对应 recheck item。
- recheck item 必须 manual reviewed。
- critical / high 原问题不能仍是 needs_fix / rejected。
- stale recheck 不能 close。

### 14.1 CLI

### 14.2 API

### 14.3 Closeout report

```json
{
  "closeout_id": "afco-000001",
  "fix_sprint_id": "afs-000001",
  "status": "passed",
  "summary": {
    "fix_item_count": 3,
    "resolved_count": 2,
    "unresolved_count": 1,
    "manual_recheck_count": 3,
    "test_fake_count": 0,
    "release_ready_audio_count": 3
  },
  "blockers": [],
  "warnings": [],
  "source_hash": "...",
  "integrity_hash": "..."
}
```

### 14.4 Close gate

正常 close 必须满足：

- sprint source 不是 stale。
- fix item 没有 critical unresolved。
- selected candidate 不是 stale。
- recheck session 已完成。
- manual review 全覆盖。
- 测试 WAV 不能作为 release-ready 修复证据。

允许 `force_close` 吗？

v10.3 建议先不支持 force close。等真实使用后再决定。

## 15. Stale Guard

以下变化必须导致 sprint 或 item stale：

- 原 Listening Session report 变化。
- 原 WAV 变化。
- marker source hash 变化。
- candidate artifact 变化。
- A/B comparison artifact 变化。
- recheck session 变化。

stale sprint：

- 不能 generate candidates。
- 不能 select candidate。
- 不能 close。
- 可以 refresh，生成新的 issue index。

---

## 16. Redaction

所有 report / API summary / export summary 必须脱敏：

- Windows 路径。
- UNC 路径。
- SoundFont path。
- provider key。
- GitHub token。
- raw local artifact absolute path。

Candidate 内部可以保存相对路径。不要在公开 summary 中展示绝对路径。

### 20.1 Smoke 必须覆盖

1. 从 Audio Lab needs_fix session 创建 sprint。

11. accepted-only recheck 可以 close passed。

如果 GitHub HTTPS 继续不稳定，可以使用一次性 `http.curloptResolve` 或 GitHub API。不得修改 remote 为 token URL，不得把 token 写进日志、文档、代码。

## 26. 给开发的话

v10.3 不要做成“又多几个按钮”。这版真正要解决的是：听出来的问题，能不能稳定地进入修复、候选、A/B、复验、关闭。

你实现时要特别注意三条线：

1. **不自动 apply。** 系统可以帮忙生成候选，但选择和应用必须由人确认。
2. **不把测试 WAV 当真实准出。** fake/test runner 只能服务自动测试，不能成为 release-ready 证据。
3. **不让 needs_fix 被关闭成正常完成。** 只有复验通过的问题才能 close；未解决的问题要明确留在 closeout blocker 里。

交付时请给 reviewer 一段可复现说明：从 Audio Lab needs_fix session 创建 sprint，生成候选，做 A/B，创建 recheck，最后 closeout。这个流程跑通，v10.3 才算真正完成。

# v6.8.0 Release Portfolio Governance Audit Ledger 组合治理审计账本与跨发行证据链施工图

日期：2026-06-06

当前稳定基线：v6.7.1

目标版本：v6.8.0

角色定位：reviewer / planner 交给开发执行

---

## 1. 背景

当前系统已经走到了组合治理闭环：

- v6.5.0：Release Portfolio Audit，跨多个 Release 发现 readiness / risk / trend / recommendation。
- v6.6.0：Release Portfolio Governance Queue，把 portfolio risk / recommendation 变成 safe / manual action queue。
- v6.6.1：修复 stale queue 仍可 export / zip 的问题，stale 后 `run-safe`、`export`、`zip` 都阻断。
- v6.7.0：Release Portfolio Governance Signoff / Archive / Change Request，治理队列可以正式签核、归档、重开必须走 approved CR。
- v6.7.1：修复 queue verifier report 与当前 queue ZIP / export manifest 未绑定的问题，签核不再接受旧 verifier report。

现在系统能回答：

- Portfolio 层风险是什么？
- 治理动作队列是什么？
- 哪些 safe action 执行了？
- 哪些 manual action 被承接或豁免？
- queue 是否被签核？
- queue archive 是否能离线验证？
- reset signoff 是否有 approved Change Request？

但它还不能很好回答一个更高层的问题：

> 从 Portfolio Audit 创建开始，到 Governance Queue 执行、签核、归档、变更重开、重新签核，这条跨 Release 组合治理链条是否完整、可排序、不可篡改、可外部审计？

v6.8.0 要做的是：

> 给组合治理层补一条 `Portfolio Governance Audit Ledger`，把 Portfolio Audit、Governance Queue、Signoff、Archive、Change Request、Verifier、Reset 因果关系串成 hash-chained ledger，并导出一个外部 reviewer 可验证的组合治理审计包。

这不是再加一个动作队列，而是给已经完成的组合治理闭环加“审计账本”。

---

## 2. 一句话目标

v6.8.0 要实现：

> Release Portfolio Governance Audit Ledger：为每个 Portfolio Audit 聚合所有相关 Governance Queue 的创建、执行、验证、签核、归档、变更、重签证据，生成 hash-chained audit ledger、audit report、export ZIP 和离线 verifier，让外部 reviewer 能独立确认组合治理流程没有断链、篡改或旧证据复用。

---

## 3. 为什么下一版应该做 Ledger

v6.7.1 已经把单条 queue 收口了，但 portfolio 级治理经常不是一条 queue：

- 一个 Portfolio Audit 可能产生多个 Governance Queue。
- 同一个 Queue 可能因为 CR reset 后重新 signoff。
- Safe actions 可能触发 `post_portfolio_refresh_required`，之后又要刷新 Portfolio Audit。
- 有些 manual actions 被 acknowledgement，有些被 force signoff 接受。
- Archive ZIP 可以独立验证，但 reviewer 想看的是“所有 queue 和 portfolio 是否整体闭环”。

如果没有 ledger，只能逐个文件查：

- `portfolio-audit.json`
- `queue.json`
- `execution-report.json`
- `queue-verification-report.json`
- `signoff.json`
- `signoff-history.jsonl`
- `change-requests/*.json`
- `governance-archive-verification-report.json`

这会导致 reviewer 成本高，也容易漏掉：

- reset 没有 CR。
- CR applied 但 signoff history 没记录。
- signoff 指向 verifier A，但 archive 里用了 verifier B。
- queue 被签核后又出现了新的 queue export。
- portfolio refresh 后旧 queue archive 仍被当作当前证据。

v6.8.0 的 ledger 要把这些关系统一显式化。

## 4. 核心交付

### 4.1 Portfolio Governance Audit Ledger

新增 ledger：

- 文件：`portfolio-governance-audit-ledger.jsonl`
- 每行一个不可变事件。
- 每个事件有 `entry_hash`。
- 每个事件有 `previous_entry_hash`。
- ledger 最后形成 `ledger_head_hash`。

事件类型覆盖：

- portfolio audit created / refreshed / exported / zipped / verified
- governance queue created / run-safe / exported / zipped / verified
- governance signoff signed / force_signed / reset
- governance change request created / approved / rejected / applied
- governance archive exported / zipped / verified
- stale detected
- integrity failed detected

### 4.2 Portfolio Governance Audit Report

新增 report：

- 文件：`portfolio-governance-audit-report.json`
- 总结 ledger 状态。
- 计算 closed governance coverage。
- 计算 unsigned / stale / failed / force signed / reset count。
- 检查 CR reset 因果链。
- 检查 archive verification coverage。
- 检查 queue verification 与 signoff evidence 绑定。

### 4.3 Portfolio Governance Audit Export / ZIP

新增 portable package：

```text
portfolio-governance-audit/
  manifest.json
  portfolio-governance-audit-report.json
  portfolio-governance-audit-ledger.jsonl
  portfolio-summary.json
  queue-summaries.json
  signoff-summaries.json
  archive-verification-summaries.json
  change-request-ledger.json
  README.txt
  GOVERNANCE_AUDIT.md
portfolio-governance-audit.zip
```

### 4.4 Offline verifier

新增离线 verifier：

```powershell
python -m song_agent.cli verify-release-portfolio-governance-audit-package path\to\portfolio-governance-audit.zip --strict --require-signed --require-archives --json
```

必须可以在外部干净目录验证，不依赖 `.musicforge/`。

### 4.5 API / CLI / Studio

接入：

- API：Portfolio Audit detail 下增加 audit ledger endpoints。
- CLI：`release-portfolio-governance-audit`
- Studio：Portfolio Audit workspace 增加 `Governance Audit Ledger` 面板。

### 4.6 Signoff / Portfolio Export Evidence

接入：

- Portfolio Audit export 增加 governance audit summary。
- Governance Signoff 可选要求 `require_governance_audit=true`。
- Portfolio Governance Archive manifest 增加 latest audit summary 是可选，不反向造成循环依赖。

## 5. 非目标

v6.8.0 不做：

- 不新增自动治理动作。
- 不自动创建新的 Governance Queue。
- 不自动 signoff。
- 不自动 reset。
- 不自动 approve Change Request。
- 不修改单个 Release 的证据。
- 不替代 v6.7 Governance Archive verifier。
- 不把 ledger 作为唯一事实源；ledger 是可验证审计视图，底层 sidecar 仍是事实源。

## 8. Ledger Entry Schema

`portfolio-governance-audit-ledger.jsonl` 每行建议：

```json
{
  "schema_version": 1,
  "entry_id": "pgal-000001",
  "portfolio_id": "pfa-000001",
  "queue_id": "pgq-000001",
  "event_type": "governance_signoff_signed",
  "event_at": "2026-06-06T00:00:00Z",
  "source": {
    "kind": "governance_signoff",
    "path": "portfolio-governance-queues/pgq-000001/signoff.json",
    "payload_hash": "..."
  },
  "links": {
    "portfolio_report_hash": "...",
    "queue_hash": "...",
    "action_plan_hash": "...",
    "execution_report_hash": "...",
    "queue_verification_report_hash": "...",
    "signoff_hash": "...",
    "archive_manifest_hash": "",
    "change_request_id": ""
  },
  "summary": {
    "status": "signed",
    "safe_completed": 3,
    "manual_required": 2,
    "force": false
  },
  "previous_entry_hash": "",
  "entry_hash": "..."
}
```

Hash 规则：

- `entry_hash = stable_hash(entry without entry_hash)`
- `previous_entry_hash` 指向上一条 ledger entry 的 `entry_hash`
- 第一条 `previous_entry_hash = ""`

排序规则：

1. `event_at`
2. `event_type`
3. `queue_id`
4. `source.kind`
5. `payload_hash`

必须 deterministic，测试要固定。

## 11. Report 检查项

必须检查：

### 11.1 Ledger chain

- entry_id 连续。
- previous_entry_hash 正确。
- entry_hash 正确。
- ledger_head_hash 正确。

### 11.2 Queue coverage

- 每个 portfolio 下相关 queue 都进入 ledger。
- 每个 signed queue 都有 signoff entry。
- 每个 signed queue 都有 queue verification entry。
- 每个 signed queue 的 verifier zip hash 与 signoff evidence 一致。
- 每个 archive verified queue 都有 archive verification entry。

### 11.3 Signoff / reset causality

- reset signoff 必须有 applied CR。
- applied CR 必须只对应一个 reset。
- reset history 里的 reset hash 必须能在 signoff reset record 或 queue event 中找到。
- force signoff 必须有 override reason。

### 11.4 Stale guard

- 如果 Portfolio Audit source 变化，旧 audit report 要标 stale。
- stale audit report 不能 export / zip。
- stale audit report 不能作为 Governance Signoff evidence。

### 11.5 Archive verifier coverage

- archive manifest exists。
- archive ZIP exists。
- archive verification report status passed 或 warning。
- archive verification report 与 archive ZIP sha256 绑定。

### 11.6 Redaction

- report、ledger、markdown、summary 都不能出现 token / local path / raw provider response。

## 15. Offline Verifier 规则

新增：

```text
song_agent/release_portfolio_governance_audit_verifier.py
```

必须校验：

- ZIP 存在且普通文件。
- ZIP entry path safe。
- raw central directory entry name safe。
- duplicate entry failed。
- total uncompressed size limit。
- entry count limit。
- manifest exists。
- manifest package_type 正确。
- manifest integrity hash。
- manifest.files 与实际 ZIP entries 一致。
- file sha256 / size 一致。
- ledger JSONL 每行可解析。
- ledger chain hash 正确。
- report integrity hash 正确。
- report.ledger.ledger_head_hash 与 ledger 最后一条 entry hash 一致。
- queue summary / signoff summary / CR ledger sidecar payload hash 对得上。
- required signed gate。
- required archives gate。
- no-force gate。
- reset CR causality gate。
- redaction scan。
- manifest.zip.entries 不能扩大 allowed entries。

strict 模式：

- extra entry failed。
- missing sidecar failed。
- warning 变 failed 由参数控制，不默认。

## 18. 与 v6.7 Signoff 的关系

v6.8 不应该让 signoff 强依赖 audit ledger，否则会形成循环：

1. signoff 需要 ledger。
2. ledger 又需要 signoff。

正确关系：

- v6.7 queue signoff 是 queue closeout 的事实。
- v6.8 ledger 是 portfolio 层审计视图。
- ledger 可以作为 Portfolio Audit external review 的 evidence。
- 后续 v6.9 可以考虑 Portfolio-level Signoff，届时再要求 Governance Audit Ledger。

但 v6.8 可以在 queue signoff summary 中显示 latest audit status，不能反向阻断 queue signoff。

## 20. Stale 策略

Audit report 绑定 source：

```json
{
  "portfolio_source_hash": "...",
  "queue_source_hashes": {
    "pgq-000001": "..."
  },
  "signoff_hashes": {},
  "archive_verification_hashes": {}
}
```

以下变化应使 report stale：

- Portfolio report/trend/risk 变化。
- 新 queue 创建。
- queue source hash 变化。
- execution report 变化。
- signoff reset / re-sign。
- archive verification report 变化。
- CR 状态变化。

stale 后：

- `export_audit()` 409。
- `build_zip()` 409。
- verifier 不负责判断 workspace stale，只判断包内一致性。

## 26. 风险清单

### 风险 1：Ledger 成为新的事实源

Ledger 只能是审计视图。底层 sidecar 仍是事实源。Verifier 校验包内一致性，不反向修改 workspace。

### 风险 2：Ledger 与 Signoff 形成循环

v6.8 不要求 queue signoff 依赖 ledger。以后如果做 portfolio-level signoff，再要求 ledger。

### 风险 3：Reset 因果链不完整

必须校验 reset -> applied CR -> signoff history -> queue event 的因果绑定。

### 风险 4：只校验 manifest 不校验真实 ZIP

Verifier 必须读 central directory raw entry names，检查 duplicate / backslash / dangerous path。

### 风险 5：Stale report 被导出

report source hash 变化后 export/zip 必须 409。

### 风险 6：大量历史事件导致文件过大

v6.8 先不做分页导出，但 API 可只返回 ledger tail。完整 ledger 在 ZIP 里。

# v9.2.0 Trust Operations Hub 事故响应与修复闭环施工图

> 当前稳定基线：v9.1.1  
> v9.1.1 已修复 Trust Operations Hub 在同类型多条 delivery verification report 下只校验第一条的问题。  
> v9.2.0 的目标，是把 v9.1 的 Hub readiness / blocker / manual action / safe runbook，推进成可追踪、可修复、可复验、可关闭的 Trust Operations Incident Response 闭环。

---

## 0. 给开发的话

你接手 v9.2.0 时，不要把它理解成“再加一个导出 ZIP”。

v9.0 到 v9.1 已经完成了这几步：

```text
v9.0: 统一 Trust Operations Hub，总览公开证明、发布通道、监控状态
v9.1: 扩展到 Release / Distribution / Submission / Operations 全链路 delivery evidence
v9.1.1: 修复多 Distribution Target / 多同类型外部 verification report 的绑定问题
```

现在缺的不是“看见问题”，而是：

```text
看见问题以后，怎么进入修复闭环？
谁确认它是问题？
用什么动作修？
哪些动作可以自动安全执行？
哪些动作必须人工？
修完以后靠什么证据复验？
关单以后能不能被篡改？
Hub 签核能不能要求所有高危事故已关闭？
```

所以 v9.2.0 要做的是：

```text
Trust Operations Incident Response / Remediation Closure
```

核心交付：

- 从 Hub blocker / delivery blocker / monitoring critical incident / runbook blocked action 生成 Incident。
- Incident 有稳定生命周期、严重级别、来源绑定、事件链、修复计划和复验证据。
- 可以创建 Remediation Plan，但只能自动执行安全动作。
- 不能自动 signoff、reset、submit、accept、provider、manual review。
- Incident Closeout 必须绑定当前 Hub / delivery / external verification evidence。
- Hub signoff / Hub verifier 可选启用 `require_incident_closeout`，要求高危/阻断事故全部关闭。
- Incident package 可导出、可 ZIP、可离线验证。
- release-check 增加 v9.2 smoke，覆盖 stale、full-resign、路径安全、缺外部证据、误关单等回归。

这版的重点不是 UI 好看，而是状态机和证据链正确。

## 2. v9.1.1 还缺什么

v9.1.1 现在已经能回答：

```text
Hub 当前 ready / blocked / stale 的原因是什么？
哪些 delivery evidence 已绑定？
哪些外部 verification report 缺失或不匹配？
哪些 safe runbook action 可以执行？
```

但它还不能完整回答：

```text
这些 blocker 是否已经进入问题跟踪？
哪些 blocker 属于同一个根因？
哪些 blocker 是 critical / high？
谁 triage 过？
修复计划是什么？
修复动作执行到哪一步？
修完后用哪个新 verification report 证明？
问题关闭以后是否仍绑定当前 Hub source？
Hub 签核时是否能阻断“还有未关闭高危事故”？
```

现在的 blocker / action 还是一次性报告字段。  
v9.2.0 要把它们升级成持久化运营对象。

## 3. v9.2.0 一句话目标

新增 Trust Operations Incident Response：

```text
Hub Report / Delivery Matrix / Monitoring / Runbook Result
  -> Incident Board
  -> Incident Records
  -> Remediation Plans
  -> Safe Action Drafts
  -> Manual Evidence
  -> Fix Verification
  -> Incident Closeout
  -> Incident Package / ZIP / Verifier
  -> Hub Signoff require_incident_closeout gate
```

业务上要能回答：

> 当前 Trust Operations Hub 发现的问题，是否已经完成分级、修复、复验和关闭？是否还有高危事故阻断对外交付？

## 4. 非目标

v9.2.0 不做这些：

- 不接 Jira / Linear / GitHub Issues。
- 不发邮件、Slack、Webhook。
- 不做多用户权限。
- 不做真实后台定时任务。
- 不自动 submit / accepted。
- 不自动 signoff / reset。
- 不自动 approve Change Request。
- 不自动跑 provider。
- 不自动上传任何本地文件路径。
- 不自动修改 Release / Distribution / Submission 的业务状态。
- 不把本地 deterministic proof 冒充第三方 CA 签名。
- 不引入数据库。
- 不引入外部依赖。

允许做：

- 本地 Incident store。
- 本地 action plan。
- 本地 safe runbook draft。
- base64 manual evidence 导入。
- 外部 verification report 绑定。
- 离线 verifier。
- Studio 控件。

### 7.3 Severity

固定枚举：

```text
critical
high
medium
low
info
```

默认映射建议：

| 来源 | 默认 severity | blocking |
| --- | --- | --- |
| open critical publication monitoring incident | critical | true |
| missing external verification report under require_delivery_ready | high | true |
| stale external verification report | high | true |
| failed package verifier | high | true |
| signed mutation blocked | medium | true |
| runbook safe action blocked | medium | true |
| manual action pending | medium | false |
| warning-only delivery readiness | low | false |

注意：

- severity 可以人工调整，但必须记录事件。
- `critical/high` 的 closeout 不允许 force 跳过 current verification。
- `blocking=true` 的 incident 会影响 Hub signoff gate。

## 8. Incident 生成规则

### 8.1 从 Hub blockers 生成

来源：

- `blocker-register.json`
- `delivery-blocker-register.json`
- `manual-action-queue.json`
- `delivery-manual-action-queue.json`
- `hub-report.json`
- `delivery-readiness-matrix.json`
- `verification_summary_index`

生成逻辑：

- 同一 `source_type + check_id + component_type + component_id` 应映射到同一个 open incident。
- 如果已有 open incident，不重复创建，更新 `last_seen_at`。
- 如果 blocker 消失，不自动关闭 incident，只标记 `source_resolved=true`，等待 closeout。
- 如果 source hash 改变，旧 incident 标 `stale=true`，需要 refresh/reconcile。

### 8.2 从 Runbook blocked 生成

来源：

- `trust-operations-hub-runbook.zip`
- `execution-report.json`
- `runbook-result.json`

规则：

- blocked safe action 生成 `runbook_action_blocked` incident。
- manual_required action 不默认生成 incident，除非它阻断 Hub ready。
- runbook stale 生成 `runbook_stale` incident，severity medium。

### 8.3 从 Publication Monitoring 生成

如果 Hub 已绑定 publication monitoring verification：

- open critical incident -> critical incident。
- open high incident -> high incident。
- stale monitoring package -> high incident。

不要信 monitoring summary 自证；必须走现有 external monitoring verification report。

### 8.4 从 Delivery Evidence 生成

规则必须沿用 v9.1.1：

- 多条同类型 delivery evidence 必须按 `component_type + component_id`。
- 缺任意一条 external report -> incident。
- duplicate report id -> incident。
- unknown external report -> incident。
- external report hash mismatch -> incident。
- verifier failed -> incident。

## 9. State Machine

### 9.1 Incident lifecycle

```text
open
  -> triaged
  -> in_progress
  -> waiting_verification
  -> verified
  -> closed
  -> archived
```

允许简化路径：

```text
open -> triaged -> closed
```

但只允许在：

- severity 是 low/info。
- blocking 是 false。
- closeout reason 非空。
- source 已经 resolved。

禁止：

- `critical/high` 直接 close。
- stale incident close。
- 缺 closeout report close。
- close 后继续修改 remediation plan。
- archived 后任何 mutation。

### 9.2 Board lifecycle

```text
open
ready_for_closeout
closed
archived
```

第一版不做 Board signoff，只做 Hub signoff gate。  
Board export / ZIP 是证据包，不是业务签核。

```json

  "hub_report_id": "optional",

```

Response:

```json
{
  "incident_board": {},
  "created_count": 2,
  "updated_count": 1,
  "stale_count": 0
}
```

### 10.2 Triage

Request:

```json
{
  "severity": "high",
  "owner": "local-user",
  "notes": "Distribution target needs rebuild.",
  "blocking": true
}
```

Rules:

- severity 必须合法。
- owner / notes 需要 redaction。
- 修改 severity / blocking 必须写 event。

### 10.3 Plan

Request:

```json
{
  "strategy": "default",
  "steps": [
    {
      "action_type": "manual_required",
      "title": "Rebuild target package"
    },
    {
      "action_type": "verify_distribution_package",
      "component_type": "distribution",
      "component_id": "target-002"
    }
  ]
}
```

Rules:

- 禁止危险 action。
- safe action 只能生成计划，不应该直接执行，除非显式 `run_safe=true`。
- 如果执行 safe action，必须写 remediation result。

### 10.4 Evidence import

Request:

```json
{
  "kind": "external_verification_report",
  "component_type": "distribution",
  "component_id": "target-002",
  "content_base64": "..."
}
```

Rules:

- 禁止 source_path。
- JSON decode 前限制 body size。
- 验证 report 必须和 component 匹配。
- 若 verification report 本身 failed，则 evidence 可记录，但不能用于 closeout passed。

### 10.5 Close

Request:

```json
{
  "closed_by": "local-user",
  "reason": "Verification now passes.",
  "force": false
}
```

Rules:

- critical/high 不允许 force 绕过 current verification。
- stale incident 不允许 close。
- blocking incident 必须有 passed closeout checks。
- close 后写 event。

## 12. Hub Verifier 扩展

`verify-trust-operations-hub-package` 新增：

```text
--require-incident-closeout
--incident-board-package path\to\trust-operations-incident-board.zip
--incident-board-verification-report path\to\trust-operations-incident-verification-report.json
```

规则：

- 如果 `--require-incident-closeout`：
  - 必须提供 Incident ZIP。
  - 必须提供 Incident verification report。
  - verification report 必须绑定当前 Incident ZIP。
  - Incident package source 必须绑定当前 Hub report / Hub verification。
  - open critical/high/blocking incident 必须为 0。
  - stale incident 必须为 0。
  - failed closeout 必须为 0。
- 不能只信 Hub ZIP 内部 incident summary。
- 如果 Hub ZIP 和 Incident ZIP 指向不同 `hub_report_hash`，失败。

## 22. 关键风险

### 风险 1：Incident closeout 只信自己 ZIP 自证

必须用外部 Hub verification / delivery verification 反查。  
不要只信 `incident-board-report.json`。

### 风险 2：critical incident 被全量重签成 closed

必须用 event log 重建状态。  
不能只读 final summary。

### 风险 3：source 变化后旧 closeout 仍被接受

必须比较：

- Incident closeout source hash。
- 当前 Hub report hash。
- 当前 Hub verification report hash。
- 当前 delivery external report hash。

### 风险 4：safe action 越权

Incident remediation plan 不能自动执行：

- signoff
- reset
- submit
- accepted
- provider
- upload
- manual review

### 风险 5：多 component 再次只校验第一条

沿用 v9.1.1 教训：  
凡是 delivery / external report，都要按 `component_type + component_id` 建索引。

### 风险 6：evidence 泄露本机路径或 token

所有 evidence payload 和导出内容都必须 redaction。  
遇到 raw `C:\Users\...`、`D:\...`、`\\server\share`、`sk-...`、GitHub token、Bearer token，应 failed 或脱敏。

## 25. 给开发的最后提醒

这版最容易写错的地方，是把 Incident 当成普通 checklist。

它不是 checklist。它是对 Hub blocker 的运营化闭环：

```text
发现 -> 分级 -> 计划 -> 证据 -> 复验 -> 关闭 -> 可离线验证
```

每一步都要能解释：

- 来源是什么。
- 当前是否 stale。
- 证据是否来自外部 verifier。
- 是否能防 full-resign。
- 是否会绕过人工决策。

如果你不确定某个动作能不能自动执行，默认当成 `manual_required`。  
v9.2 的价值不是自动化所有东西，而是让所有阻断项可追踪、可证明、可安全关闭。

# v9.8.0 Trust Operations Assurance Watch Signoff 持续保障队列签核归档与准出绑定施工图

日期：2026-06-22
当前稳定基线：v9.7.0
基线提交：e139e33d287525a6a8f4ee881f4ad9fbe2345079
执行角色：开发

## 1. 版本定位

v9.7.0 已经完成 Trust Operations Assurance Watch：

- Schedule
- Watch Queue
- Drift Action Pack
- Watch ZIP
- 离线 verifier
- Hub gate：`--require-assurance-watch-clear`

这说明系统已经能持续检查 Trust Operations Hub、Continuous Assurance、delivery evidence、incident/knowledge/control 证据是否漂移，并能用 Watch package 证明“当前 watch 是 clear 的”。

v9.8.0 要补上的不是新的监控项，而是“谁确认了这次持续保障检查可以作为准出证据”。也就是说，要把 v9.7 的 Watch clear 结果提升为正式、可追溯、不可变、可离线验收、可绑定 Hub gate 的签核证据。

一句话目标：

> v9.8.0 做 Trust Operations Assurance Watch Signoff / Closeout / Archive，让“持续保障队列已经清空且被人工确认”成为 Trust Operations Hub 的正式准出门禁。

## 2. 为什么要做这一版

当前 v9.7 的能力是：

- 系统可以生成 Watch Queue。
- 系统可以运行 Watch Queue。
- 系统可以判断 queue 是否 clear。
- 系统可以导出 Watch ZIP。
- Hub verifier 可以要求 Watch clear。

但 v9.7 仍有一个治理缺口：

- 没有正式的 signoff 对象。
- 没有 closeout 报告。
- 没有 signoff history。
- 没有签核后不可变保护。
- 没有 approved Change Request reset。
- 没有独立的 Watch Signoff Archive ZIP。
- Hub gate 只能要求“watch clear”，不能要求“watch clear 已经被签核并归档”。

这会导致一个实际问题：

> v9.7 能证明机器检查结果是 clear，但不能证明这个结果经过了人工准出确认，也不能证明签核后的证据没有被静默重建。

v9.8 要把这个缺口补齐。

## 3. 本版不做什么

为了避免范围失控，v9.8.0 明确不做以下内容：

- 不新增 provider 调用。
- 不新增音乐生成能力。
- 不新增发行平台对接。
- 不做第三方 CA / 公钥基础设施。
- 不做自动 approve / 自动 signoff。
- 不允许 runbook 自动执行 signoff。
- 不允许 force signoff 绕过 blocking drift。
- 不做 Web 托管发布。
- 不做多用户权限体系。
- 不重构 v9.7 Watch Queue 的核心模型，除非为签核绑定必要字段。

## 4. 总体设计

新增一个独立层：

```text
Trust Operations Hub
  -> Continuous Assurance
  -> Assurance Watch Queue
  -> Assurance Watch Signoff
  -> Assurance Watch Signoff Archive
  -> Hub verifier gate
```
v9.8 新增对象：

- Watch Closeout Report
- Watch Signoff
- Watch Signoff History
- Watch Signoff Change Request
- Watch Signoff Archive Export
- Watch Signoff Archive ZIP
- Watch Signoff Archive verifier report

签核前必须满足：

- Watch Queue 当前不是 stale。
- Watch Queue 已运行完成。
- Watch Queue 没有 blocking drift。
- Watch Queue 没有 overdue blocking action。
- Watch ZIP verifier passed。
- Hub verification report passed。
- Continuous Assurance verification report passed。
- 显式传入的外部 evidence report 与当前包匹配。

签核后必须保证：

- 不能静默 refresh closeout。
- 不能静默重新 export archive。
- 不能静默重新 build archive ZIP。
- 删除 export 目录或 ZIP 文件不能绕过不可变保护。
- reset 必须走 approved Change Request。
- Change Request 只能使用一次。

## 7. 核心 schema

### 7.1 WatchCloseout

建议字段：

```json
{
  "schema_version": 1,
  "closeout_id": "awco-000001",
  "queue_id": "awq-000001",
  "created_at": "2026-06-22T00:00:00Z",
  "updated_at": "2026-06-22T00:00:00Z",
  "status": "passed",
  "source": {
    "queue_id": "awq-000001",
    "queue_source_hash": "...",
    "queue_report_hash": "...",
    "watch_zip_sha256": "...",
    "watch_zip_size_bytes": 123,
    "watch_manifest_hash": "...",
    "watch_verification_report_hash": "...",
    "hub_zip_sha256": "...",
    "hub_manifest_hash": "...",
    "hub_verification_report_hash": "...",
    "continuous_assurance_report_hash": "..."
  },
  "summary": {
    "total_watch_items": 0,
    "passed_watch_items": 0,
    "failed_watch_items": 0,
    "manual_required_items": 0,
    "overdue_items": 0,
    "blocking_drift_count": 0,
    "watch_clear": true,
    "ready_for_signoff": true
  },
  "blockers": [],
  "warnings": [],
  "manual_actions": [],
  "integrity_hash": "..."
}
```

`integrity_hash` 必须覆盖：

- `status`
- `source`
- `summary`
- `blockers`
- `warnings`
- `manual_actions`

不应覆盖自身字段 `integrity_hash`。

### 7.2 WatchSignoff

建议字段：

```json
{
  "schema_version": 1,
  "signoff_id": "awsg-000001",
  "queue_id": "awq-000001",
  "closeout_id": "awco-000001",
  "status": "signed",
  "signed_at": "2026-06-22T00:00:00Z",
  "signed_by": "reviewer",
  "role": "owner",
  "reason": "Watch queue clear and external verification passed.",
  "source": {
    "closeout_integrity_hash": "...",
    "queue_source_hash": "...",
    "watch_zip_sha256": "...",
    "watch_manifest_hash": "...",
    "watch_verification_report_hash": "...",
    "hub_verification_report_hash": "...",
    "continuous_assurance_report_hash": "..."
  },
  "decision": {
    "approved": true,
    "force": false,
    "exceptions": []
  },
  "payload_hash": "...",
  "integrity_hash": "..."
}
```

要求：

- `force` 在 v9.8 中固定为 false。
- 如果未来要做 exception board，放 v9.9 或之后。
- `signed_by` / `role` / `reason` 要做 redaction。
- `reason` 不允许空。
- 签核只允许在 closeout status 为 passed 时执行。

### 7.3 WatchSignoffHistory

`watch-signoff-history.jsonl` 每行一个事件。

事件类型建议：

```text
closeout_refreshed
signoff_created
change_request_created
change_request_approved
signoff_reset
archive_exported
archive_zip_built
archive_verified
```

每个事件建议字段：

```json
{
  "schema_version": 1,
  "event_id": "awhe-000001",
  "event_type": "signoff_created",
  "created_at": "2026-06-22T00:00:00Z",
  "queue_id": "awq-000001",
  "payload_hash": "...",
  "previous_event_hash": "...",
  "event_hash": "..."
}
```

事件链要求：

- `previous_event_hash` 必须形成链。
- verifier 必须重建链。
- 删除中间事件、重排事件、改事件 payload 都必须 failed。

### 7.4 Change Request

签核后 reset 必须使用 approved CR。

建议字段：

```json
{
  "schema_version": 1,
  "change_request_id": "awcr-000001",
  "queue_id": "awq-000001",
  "status": "approved",
  "created_at": "2026-06-22T00:00:00Z",
  "approved_at": "2026-06-22T00:00:00Z",
  "created_by": "developer",
  "approved_by": "reviewer",
  "reason": "Need to rerun watch after external evidence changed.",
  "target_signoff_hash": "...",
  "used": false,
  "applied_at": null,
  "applied_reset_hash": null,
  "integrity_hash": "..."
}
```

reset 规则：

- CR 必须存在。
- CR integrity 必须 OK。
- CR status 必须 approved。
- CR target_signoff_hash 必须匹配当前 signoff。
- CR used 必须 false。
- reset 成功后：
  - `used=true`
  - 写 `applied_at`
  - 写 `applied_reset_hash`
  - history 写 `signoff_reset`
- 同一 CR 不允许重复 reset。

## 8. Store API 设计

建议类：

```python
class TrustOperationsAssuranceWatchSignoffStore:
    def refresh_closeout(...)
    def get_closeout(...)
    def sign(...)
    def get_signoff(...)
    def create_change_request(...)
    def approve_change_request(...)
    def reset_signoff(...)
    def export_archive(...)
    def build_archive_zip(...)
    def verify_archive_zip(...)
```

### 8.1 refresh_closeout()

输入：

- `queue_id`
- watch queue report / package info
- watch verification report
- hub verification report
- continuous assurance verification report

行为：

- 重新读取当前 Watch Queue。
- 重新读取当前 Watch report。
- 校验 Watch Queue source 未 stale。
- 校验 Watch verification report 与当前 Watch ZIP / manifest 匹配。
- 校验 Hub verification report passed。
- 校验 Continuous Assurance verification report passed。
- 生成 closeout。

如果已有 signoff 且未 reset：

- 返回 409。
- 不允许刷新 closeout。

### 8.2 sign()

输入：

- `queue_id`
- `signed_by`
- `role`
- `reason`

行为：

- 读取 closeout。
- closeout 必须 passed。
- closeout integrity 必须 OK。
- history 当前不能已有 active signoff。
- 生成 watch-signoff.json。
- 写 history。

不允许：

- closeout failed 时签核。
- closeout stale 时签核。
- reason 为空。
- force 签核。

### 8.3 export_archive()

行为：

- 如果已有 active signoff，允许首次 export。
- 如果已经 export 过，且 active signoff 存在，允许 idempotent 重读，但不允许静默重建不一致内容。
- 如果 export 目录被删除，但 history 表明 active signoff 已存在，应允许重新导出吗？

这里建议采用更严格规则：

> 签核后 archive export 一旦完成，删除 export 目录不能绕过不可变保护。若需要重建，必须 approved CR reset 后重新签核。

因此：

- active signoff 存在且 history 已有 `archive_exported`，再次 export 返回 409。
- active signoff 存在但还没有 `archive_exported`，允许 export。
- 删除 export 目录后重复 export 也返回 409。

这个口径和 v7/v8/v9 多个 archive hotfix 保持一致。

### 8.4 build_archive_zip()

同 export 规则：

- active signoff 存在且 history 已有 `archive_zip_built`，再次 build ZIP 返回 409。
- active signoff 存在但没有 `archive_zip_built`，允许 build。
- 删除 ZIP 后重复 build 返回 409。

### 8.5 reset_signoff()

输入：

- `queue_id`
- `change_request_id`

行为：

- 校验 CR。
- 清除 active signoff 状态。
- 不删除历史。
- 标记 CR used。
- 写 reset event。

reset 后才允许重新 refresh closeout / sign / export / zip。

```

### 10.1 verifier 必查项

ZIP 安全：

- raw central directory entry name 检查。
- duplicate entry failed。
- backslash entry failed。
- dangerous path failed。
- `.MusicForge/` 这类大小写变体 failed。
- nested ZIP failed。
- extra entry failed。
- missing fixed entry failed。

manifest：

- package_type 必须等于 `trust_operations_assurance_watch_signoff_archive`。
- manifest.files 必须等于固定 allow-list。
- manifest file hash / size 必须匹配。
- manifest_hash 必须匹配。

closeout：

- closeout integrity OK。
- closeout status passed。
- closeout source 与 manifest.source 一致。

signoff：

- signoff integrity OK。
- signoff status signed。
- signoff source closeout hash 匹配。
- signoff payload_hash 匹配。

history：

- event chain OK。
- 必须存在 signoff_created。
- 如果有 signoff_reset，则必须绑定 approved CR。
- active signoff 必须能从 history 推导出来。

Change Request：

- CR integrity OK。
- used CR 只能对应一个 reset event。
- reset event hash 必须匹配 CR applied_reset_hash。

外部 evidence 绑定：

- `--watch-package` 的 sha256/size/manifest hash 必须匹配 closeout source。
- `--watch-verification-report` 必须 passed，且绑定当前 watch package。
- `--hub-verification-report` 必须 passed，且 hash 匹配 closeout source。
- `--continuous-assurance-report` 必须 passed，且 hash 匹配 closeout source。

redaction：

- 扫描所有 JSON/TXT/JSONL。
- 不允许 token、Bearer、GitHub PAT、OpenAI key、本机绝对路径、UNC 路径。
- 不允许 `C:\Users\...`、`D:\...`、`\\server\share`。

### 10.2 关键防伪用例

verifier 必须挡住：

- 改 `watch-signoff.json.signed_by` 后重算 manifest。
- 改 `watch-closeout.summary.watch_clear=true` 后重算 manifest。
- 删除 failed blocker 后重算 closeout integrity。
- 重签 history 中间事件。
- 删除 reset event。
- 伪造 Change Request 为 approved。
- 替换 Watch ZIP 但沿用旧 verification report。
- 替换 Hub report 但不更新 closeout source。
- ZIP 里增加 benign `notes.txt` 并重签 manifest。

```

如果项目已有 Trust Operations API prefix，请优先沿用现有命名。

API 状态码：

- 200：读取成功。
- 201：创建成功。
- 202：如走异步任务，表示已接受。
- 400：参数错误。
- 404：queue/signoff/CR 不存在。
- 409：stale、已签核不可变、CR 无效、证据不匹配。

所有错误响应：

```json
{
  "error": "..."
}
```

不得返回 traceback。

## 25. 给开发的话

你接这版时，不要把它理解成“再加一个报告页面”。v9.7 已经能证明 Watch Queue clear，v9.8 要证明的是：这个 clear 结果已经被正式确认、签核、归档，并且签核后的归档不能被静默重建。

实现时先做后端 store 和 verifier，再接 CLI/API/Studio。不要先做 UI。安全边界优先级高于页面功能：签核不可变、approved Change Request reset、外部 evidence 绑定、ZIP allow-list、full-resign 防伪，这几个点缺一个都不能发版。

如果你发现某个证据只能靠同一个 ZIP 里的 JSON 自证，就停下来重新设计 sidecar 或外部 verification binding。这个项目一路走到 v9，核心原则已经很明确：可交付证据必须能被外部 verifier 独立复核，不能靠内部字段自说自话。

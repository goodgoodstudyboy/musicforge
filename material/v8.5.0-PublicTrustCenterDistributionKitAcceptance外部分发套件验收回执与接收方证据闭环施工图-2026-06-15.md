# v8.5.0 Public Trust Center Distribution Kit Acceptance 外部分发套件验收回执与接收方证据闭环施工图

> 本文是给开发执行的 v8.5.0 施工图。当前稳定基线是 v8.4.1。
>
> v8.4.1 已经把 Public Trust Center Distribution Kit 做成了固定结构、可离线深度验收的一体化交付包，并修掉了“额外文件写进 manifest/files/file-index 后整体重签仍通过”的 P1。
>
> v8.5.0 的目标，是补上 Distribution Kit 发出去之后的“接收方验收回执”和“验收证据闭环”：外部方拿到 Kit 后，如何证明自己验证过、验证的是哪一个 Kit、结论是 accepted / needs_changes / rejected，以及这份回执如何被本地系统安全导入、审计、导出和离线复验。

---

## 1. 背景

v8.0 到 v8.4 已经完成了公开信任中心的主信任链：

1. `public-trust-center.zip`
   - 公开信任中心主包。
   - 包含 public-safe HTML / data / manifest。
   - 支持 delivery readiness、delivery anchor、Registry、Transparency、checkpoint 验证。

2. `public-trust-center.delivery-anchor.json`
   - PTC ZIP 外部锚点。
   - 绑定 PTC ZIP hash、manifest hash、source hash、delivery fingerprint sidecar。

3. `public-trust-center-anchor-registry.zip`
   - Anchor Registry。
   - 管理 current / published / revoked / superseded anchor。

4. `public-trust-center-anchor-transparency.zip`
   - Anchor Transparency。
   - 记录 Anchor Registry 状态的 append-only ledger。
   - 绑定当前 checkpoint。

5. `ptc-anchor-checkpoint-current.json`
   - 外部留存 checkpoint。
   - 用来发现 PTC / anchor / registry / transparency 整体替换。

6. `public-trust-center-distribution-kit.zip`
   - v8.4 新增的一体化外部分发套件。
   - 内含 PTC ZIP、delivery anchor、Anchor Registry ZIP、Anchor Transparency ZIP、checkpoint、三份 verification report。
   - 支持一条命令 `verify-public-trust-center-distribution-kit-package` 深度离线验收。
   - v8.4.1 已经强制固定 ZIP entry allow-list、`manifest.files[]` allow-list、`file-index.json.files[]` allow-list。

现在剩下的问题是：

> 我们能证明“自己生成了一个可验证的 Kit”，但还不能证明“外部接收方已经拿到某一个具体 Kit、独立验证过它，并给出了可审计的结论”。

这会影响真实交付场景：

- 对接发行方、合作方、客户、审计方时，对方可能说“我验收通过了”，但我们系统里没有结构化证据。
- 对方可能反馈 `needs_changes`，但反馈没有绑定到具体 Kit hash，后续无法判断反馈是否对应当前包。
- 对方可能只看过旧 Kit，后来我们重新生成了 Kit，但旧回执仍被误当成当前证据。
- 对方可能给了一个裸 JSON，我们导入端如果自动补 hash，会降低证据可信度。
- accepted 结论需要能生成 public-safe evidence，供之后公开门户或二次交付引用。

v8.5.0 就是补这个闭环。

---

## 2. v8.5.0 定位

一句话：

> v8.5.0 要在 Public Trust Center Distribution Kit 之上新增接收方验收回执工作流：生成 response template、导入外部 response、校验 response 与当前 Kit 的绑定、生成 accepted evidence、处理 needs_changes / rejected，并提供独立离线 verifier。

它不是替代 Distribution Kit verifier，而是补充在它之后：

```text
生成 PTC / Anchor / Registry / Transparency
  -> 生成 Distribution Kit
  -> 外部方离线 verify Distribution Kit
  -> 外部方填写 acceptance response
  -> 本地导入 response
  -> 本地生成 public-safe accepted evidence 或 needs_changes draft
  -> accepted evidence 可离线 verify
```

---

## 3. 本版不做什么

为了避免 v8.5 失控，本版明确不做：

1. 不接入真实 CA / PGP / X.509。
2. 不做在线公证平台。
3. 不自动把 accepted evidence 发布到 GitHub Release assets。
4. 不自动 revoke / supersede Anchor Registry。
5. 不自动修改 Public Trust Center、Anchor Registry、Transparency。
6. 不自动把 needs_changes 变成 signed Change Request。
7. 不允许导入端给外部 response 自动补 `distribution_kit_zip_sha256`、`manifest_hash`、`source_hash` 等绑定字段。
8. 不接受 API 传入 `source_path` / `local_path` / `file_path` 去读取本地文件。
9. 不把 `.musicforge/` 内部路径、token、provider 原始响应、本机路径写进 evidence ZIP。
10. 不把 synthetic review 当成人工外部验收。

## 7. Acceptance Response Template

### 7.1 生成入口

新增 Store 方法：

```python
PublicTrustCenterDistributionKitAcceptanceStore.create_response_template(
    center_id: str = "ptc-default",
    payload: dict | None = None,
    *,
    now: str | None = None,
) -> dict
```

前置条件：

- 当前 Distribution Kit ZIP 必须存在。
- 当前 Distribution Kit verification report 必须存在。
- verification report 必须是 `passed`。
- verification report 必须绑定当前 Distribution Kit ZIP 和 manifest。
- 如果当前 Kit stale，不能生成 template。

### 7.2 Template 内容

建议结构：

```json
{
  "schema_version": 1,
  "template_type": "musicforge_public_trust_center_distribution_kit_acceptance_template",
  "center_id": "ptc-default",
  "template_id": "ptcdka-template-000001",
  "created_at": "2026-06-15T00:00:00+00:00",
  "kit_binding": {
    "distribution_kit_zip_sha256": "...",
    "distribution_kit_zip_size_bytes": 123,
    "distribution_kit_manifest_hash": "...",
    "distribution_kit_report_hash": "...",
    "distribution_kit_source_hash": "...",
    "distribution_kit_verification_report_hash": "...",
    "ptc_zip_sha256": "...",
    "anchor_registry_zip_sha256": "...",
    "anchor_transparency_zip_sha256": "...",
    "checkpoint_hash": "..."
  },
  "required_verification": {
    "strict": true,
    "deep": true,
    "require_current": true,
    "require_anchor_registry_current": true,
    "require_anchor_published": true,
    "require_anchor_not_revoked": true,
    "require_anchor_transparency_current": true,
    "require_anchor_checkpoint": true
  },
  "response_template": {
    "response_type": "musicforge_public_trust_center_distribution_kit_acceptance_response",
    "response_id": "",
    "result": "accepted",
    "review_mode": "external_manual",
    "reviewer": {
      "name": "",
      "organization": "",
      "role": ""
    },
    "reviewed_at": "",
    "verification": {
      "status": "",
      "tool": "",
      "tool_version": "",
      "command": "",
      "report_hash": "",
      "summary": {}
    },
    "kit_binding": {},
    "findings": [],
    "comments": ""
  }
}
```

### 7.3 关键规则

- `kit_binding` 必须来自当前 Kit 和当前 verification report。
- 模板可以帮助外部方复制 binding 字段，但导入端不得自动为裸 response 补字段。
- `review_mode` 必须是 `external_manual`。
- `result` 只能是：
  - `accepted`
  - `needs_changes`
  - `rejected`
- `reviewed_at` 必须是 ISO 时间。
- `reviewer.name` / `reviewer.organization` 必须做敏感值脱敏。

## 8. Acceptance Response Import

### 8.1 Store 方法

```python
PublicTrustCenterDistributionKitAcceptanceStore.import_response(
    center_id: str = "ptc-default",
    payload: dict | None = None,
    *,
    now: str | None = None,
) -> dict
```

支持输入：

```json
{
  "content_base64": "...",
  "format": "json"
}
```

也可以支持：

```json
{
  "response": { "...": "..." }
}
```

明确拒绝：

```json
{"source_path": "C:\\Users\\..."}
{"local_path": "D:\\..."}
{"file_path": "\\\\server\\share\\..."}
```

### 8.2 Import 校验

导入时必须校验：

1. `response_type == "musicforge_public_trust_center_distribution_kit_acceptance_response"`。
2. `response_id` 非空，且只能包含安全字符。
3. `result` 在允许枚举内。
4. `review_mode == "external_manual"`。
5. `kit_binding` 完整存在。
6. `kit_binding.distribution_kit_zip_sha256` 等于当前 Kit ZIP hash。
7. `kit_binding.distribution_kit_manifest_hash` 等于当前 manifest hash。
8. `kit_binding.distribution_kit_report_hash` 等于当前 report hash。
9. `kit_binding.distribution_kit_source_hash` 等于当前 report source hash。
10. `kit_binding.distribution_kit_verification_report_hash` 等于当前 verification report hash。
11. `verification.status == "passed"` 才允许 `result == "accepted"`。
12. `needs_changes` / `rejected` 可以导入，但不能生成 accepted evidence。
13. 外部 response 中缺少 binding 字段时必须失败，不能由导入端补齐。
14. response 中出现 token、本机路径、`sk-`、GitHub token、Bearer token 等必须脱敏；严重污染可直接拒绝。
15. response body 大小要有限制，建议默认 512 KB。

### 8.3 落盘内容

每个 response 落盘：

```text
responses/<response-id>/
  original-response.json
  response-verification-report.json
  response-binding-summary.json
  response-state.json
  events.jsonl
```

`response-state.json` 建议：

```json
{
  "schema_version": 1,
  "response_id": "external-accept-001",
  "center_id": "ptc-default",
  "result": "accepted",
  "status": "accepted_current",
  "imported_at": "...",
  "reviewed_at": "...",
  "review_mode": "external_manual",
  "source_hash": "...",
  "response_payload_hash": "...",
  "raw_response_sha256": "...",
  "kit_binding_status": "current",
  "verification_status": "passed",
  "accepted_evidence_id": null,
  "warnings": []
}
```

状态枚举：

- `accepted_current`
- `accepted_stale`
- `needs_changes_current`
- `needs_changes_stale`
- `rejected_current`
- `rejected_stale`
- `invalid`

## 9. Response Verify

### 9.1 Store 方法

```python
PublicTrustCenterDistributionKitAcceptanceStore.verify_response(
    center_id: str,
    response_id: str,
    *,
    now: str | None = None,
) -> dict
```

校验项：

- response JSON parse。
- response schema。
- response payload hash。
- binding 对当前 Kit 是否 current。
- 当前 Kit verification report 是否仍 current。
- result / verification.status 语义是否匹配。
- findings 是否结构化。
- redaction scan。

### 9.2 Stale 规则

如果发生以下任一情况，response 必须 stale：

- Distribution Kit ZIP 被重建，hash 变化。
- manifest hash 变化。
- report source hash 变化。
- verification report hash 变化。
- Anchor Registry / Transparency / checkpoint 改变导致 Kit source 改变。

stale response 仍保留，但：

- 不能生成 accepted evidence。
- 不能作为 current accepted evidence。
- 不能被 Public Trust Center 后续聚合为当前接受证据。

## 10. Accepted Evidence

### 10.1 生成条件

只有满足以下条件才能生成 accepted evidence：

1. response result 是 `accepted`。
2. response review_mode 是 `external_manual`。
3. response verification.status 是 `passed`。
4. response binding 当前。
5. 当前 Kit verification report 是 `passed`。
6. 当前 Kit 未 stale。
7. response redaction scan 通过。

### 10.5 Public-safe 原则

`original-response-public.json` 不应该完整暴露敏感内容。建议：

- 保留 reviewer name / organization / role，但必须脱敏。
- comments 可以保留 public excerpt，长度限制 500 字符。
- findings 保留 severity / code / public_message。
- 不保留 email、phone、本机路径、token、原始命令行中的本机绝对路径。
- 如果外部 response 有敏感字段，public projection 必须用 `[REDACTED]`。

## 11. Accepted Evidence Offline Verifier

新增 CLI：

```powershell
python -m song_agent.cli verify-public-trust-center-distribution-kit-accepted-evidence-package path\to\accepted-evidence.zip --json --strict --require-current --distribution-kit path\to\public-trust-center-distribution-kit.zip --report-out accepted-evidence-verification-report.json
```

新增 verifier：

```python
verify_public_trust_center_distribution_kit_accepted_evidence_package(
    zip_path: Path,
    *,
    strict: bool = False,
    require_current: bool = False,
    distribution_kit_path: Path | None = None,
    max_zip_size_bytes: int = ...,
    max_uncompressed_size_bytes: int = ...,
    max_entry_count: int = ...,
) -> dict
```

### 11.1 Evidence ZIP 固定结构

必须固定 allow-list：

```text
evidence-manifest.json
evidence-report.json
original-response-public.json
original-response-binding-summary.json
response-verification-summary.json
distribution-kit-verification-summary.json
README.txt
VERIFY.txt
```

不允许：

- 任意 nested ZIP。
- `.musicforge/` 或大小写变体。
- 反斜杠 entry。
- `../`。
- 绝对路径。
- 重复 entry。
- manifest.files 自行声明额外文件。

### 11.2 Verifier checks

至少包含：

- `ptcdkae_zip_entry_path_safe`
- `ptcdkae_zip_duplicate_entries`
- `ptcdkae_zip_allowed_entries`
- `ptcdkae_manifest_integrity`
- `ptcdkae_manifest_allowed_files`
- `ptcdkae_manifest_file_hashes`
- `ptcdkae_report_integrity`
- `ptcdkae_report_source_hash`
- `ptcdkae_response_public_projection_match`
- `ptcdkae_original_response_binding_match`
- `ptcdkae_response_verification_summary_match`
- `ptcdkae_distribution_kit_verification_summary_match`
- `ptcdkae_external_distribution_kit_hash_match`
- `ptcdkae_redaction_scan`

### 11.3 外部 Kit 参数

如果传入：

```powershell
--distribution-kit path\to\public-trust-center-distribution-kit.zip
```

则 verifier 必须校验：

- 该 ZIP 的 sha256 等于 evidence report 中的 `distribution_kit_zip_sha256`。
- 该 ZIP 的 manifest hash 等于 evidence report 中的 `distribution_kit_manifest_hash`。
- 如果可行，调用 Distribution Kit verifier 做深度校验。

如果没有传入外部 Kit：

- verifier 可以验证 evidence 包内部一致性。
- 但 `require_current` 应该返回 warning 或 failed，具体建议：
  - 默认：warning `distribution_kit_not_supplied`。
  - `--require-current`：failed。

## 12. needs_changes / rejected 回流

外部 response 如果是：

- `needs_changes`
- `rejected`

系统必须能记录，但不能自动改信任链。

### 12.1 Store 行为

导入后：

```json
{
  "status": "needs_changes_current",
  "change_request_draft": {
    "draft_id": "ptcdkcr-000001",
    "source_response_id": "external-review-001",
    "severity": "high",
    "summary": "External reviewer requested changes.",
    "findings": []
  }
}
```

### 12.2 不能自动做的事

严禁自动：

- revoke anchor。
- supersede anchor。
- reset Public Trust Center signoff。
- rebuild Distribution Kit。
- mark response accepted。

### 12.3 后续交给哪个模块

本版只生成 draft。后续如果要正式执行，应交给：

- Anchor Registry Change Request。
- Public Trust Center refresh。
- Distribution Kit regenerate。
- Reviewer 手工确认。

## 17. 安全边界

### 17.1 禁止自证

Accepted Evidence verifier 不能只相信 `evidence-report.source`。

必须至少交叉校验：

1. evidence report。
2. original response public projection。
3. original response binding summary。
4. response verification summary。
5. distribution kit verification summary。
6. 可选外部 Distribution Kit ZIP。

### 17.2 防整体重签

release-check 必须覆盖：

- 攻击者修改 reviewer name / organization。
- 同步重算 evidence report / manifest / public response / binding summary。
- 但无法提供与原始 response payload 一致的 binding。
- verifier 必须 failed。

如果因为本版没有真实第三方签名，无法彻底防止“攻击者同时伪造 response 和 evidence”，必须在 README 里写清楚边界：

> v8.5 accepted evidence 是本地导入的外部回执证据，不是第三方 CA 签名。它能证明该 evidence 包与被导入的 response、Kit 指纹和 verification report 一致；不能在没有独立外部签名或外部留存 response 的情况下证明 reviewer 身份不可抵赖。

### 17.3 API 文件输入

API 禁止：

- `source_path`
- `local_path`
- `file_path`

CLI 可以支持 file path，但 CLI 输出和 README 要清楚说明这是本机操作者命令，不是远程 API 能力。

### 17.4 Redaction

扫描范围：

- response。
- evidence report。
- original response public projection。
- binding summary。
- verification summary。
- README / VERIFY。
- manifest。

必须识别：

- `sk-...`
- GitHub token。
- Bearer token。
- Windows 盘符路径。
- UNC path。
- `.musicforge` 内部路径。
- `githubkey.txt`。

## 23. 风险清单

### R1：导入端自动补 binding

风险：

- 外部 response 没绑定具体 Kit，却被系统自动补齐，证据可信度下降。

要求：

- 缺字段必须 400 / failed。
- release-check 必须覆盖 `missing_binding=failed`。

### R2：accepted evidence 自证

风险：

- 只改 evidence report / manifest / summary 并整体重签，verifier 仍 passed。

要求：

- verifier 必须交叉校验 public response、binding summary、response verification summary、distribution kit verification summary。
- release-check 必须覆盖 full resign tamper。

### R3：stale response 被当成 current

风险：

- 外部验的是旧 Kit，新 Kit 生成后旧 response 仍被当成当前 accepted evidence。

要求：

- Kit hash / manifest hash / report hash / verification report hash 任一变化，response stale。
- stale response 不能生成 evidence。

### R4：needs_changes 自动改链

风险：

- 外部反馈 needs_changes 后系统自动 revoke / supersede / reset，造成不可控变更。

要求：

- 只生成 draft。
- 任何链路变更仍需要人工批准。

### R5：public projection 泄漏隐私

风险：

- reviewer comments 中带邮箱、token、本机路径，被写进 public evidence。

要求：

- public projection 强制 redaction。
- verifier redaction scan 覆盖所有文本 JSON。

### R6：API 本地文件读取

风险：

- 远程 API 通过 source_path 读取服务器本机文件。

要求：

- API 拒绝 source_path/local_path/file_path。
- 测试覆盖。

## 25. 给开发的话

这版不要把重点放在“再生成一个更大的 ZIP”。v8.4.1 已经把 Distribution Kit 做好了，v8.5.0 的核心是“别人验收后的证据怎么进系统”。

你实现时要抓住三个原则：

1. 外部 response 必须自己显式声明它验的是哪个 Kit，导入端不能替它补。
2. accepted evidence 只能从 current、manual、passed 的 response 生成。
3. needs_changes / rejected 只能生成 draft，不能自动修改 Anchor、PTC、Registry、Transparency。

优先把 Store 和 verifier 做硬，再接 API / CLI / Studio。每完成一块就本地跑对应测试，确认通过后提交并推 GitHub。不要等所有 UI 都做完才提交。

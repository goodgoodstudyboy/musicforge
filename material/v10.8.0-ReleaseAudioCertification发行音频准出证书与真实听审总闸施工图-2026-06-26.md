# v10.8.0 Release Audio Certification 发行音频准出证书与真实听审总闸施工图

> 项目：MusicForge / song-agent
> 计划版本：v10.8.0
> 编写日期：2026-06-26
> 当前稳定基线：v10.7.1
> 角色定位：reviewer / planner
> 目标读者：开发执行人员、测试验收人员、后续 reviewer

---

## 1. 背景

v10.2 到 v10.7 已经把“真实音频听审”从单点能力推进成一条较完整的链：

| 版本 | 已落地能力 | 粒度 |
|---|---|---|
| v10.2 | Audio Lab：真实 renderer 环境检查、WAV smoke、人工试听 session、marker、A/B | 单个 listening session |
| v10.3 | Audio Fix Sprint：marker -> draft/candidate -> A/B -> recheck -> closeout | 修复冲刺 |
| v10.4 | Release Candidate Audio Campaign：批量真实听审、campaign report、signoff/export/ZIP/verifier | 听审战役 |
| v10.5 | Audio Campaign Governance：campaign archive、analytics、GA/Release gate | 治理归档 |
| v10.6 | Release-driven Audio Campaign：从 Release tracks 自动创建绑定正确的真实听审战役 | Release -> Campaign |
| v10.7 | Release Audio Campaign Remediation：Campaign 失败后自动编排 Fix Sprint、候选、复验和 closeout | Campaign 修复闭环 |

v10.7.1 进一步收紧了两个关键证据风险：

- 已签核 remediation 在 `gate/export/zip/verify` 前会重新校验当前 Release track Final Export source。
- Remediation ZIP verifier 使用固定 allow-list，拒绝 manifest 声明的额外文件。

现在的问题不是缺少某一个底层功能，而是缺少一个“最终音频准出总闸”：

- Release 是否真的有当前 Final Export？
- 每首歌是否有真实 renderer 产出的 WAV？
- 每首歌是否完成逐曲人工听审？
- Release-bound Audio Campaign 是否覆盖当前 Release tracks？
- Campaign 是否 signed、archived、verified？
- 如果 Campaign 出现 `needs_fix/rejected/high/critical marker`，是否有 remediation closeout？
- Remediation 是否 signed、verified，且绑定当前 Release track Final Export？
- Audio Fix Sprint 的 recheck 是否是真实 release-ready WAV，而不是 test/fake WAV？
- GA readiness 是否绑定的是当前所有音频证据，而不是旧报告？

这些检查目前分散在 Audio Lab、Audio Campaign、Campaign Governance、Release signoff、GA readiness、Remediation、Final Export 等多个模块里。v10.8 要把它们聚合成一个可离线验证、可导出、可签核、可作为 GA/Release 总门禁的 Release Audio Certification。

---

## 2. 一句话目标

> v10.8.0 要新增 Release Audio Certification：把 Release 的真实音频产物、逐曲人工听审、Audio Campaign、Remediation、Campaign Governance、Final Export、GA readiness 证据汇总成一个“发行音频准出证书”，并提供 export/ZIP/offline verifier/signoff gate，作为音乐是否真的可以交付的总闸。

---

## 3. 本版定位

### 3.1 v10.8 不再是一个修补点

v10.8 应该迈大一点，做“证书层”和“总闸层”：

```text
Release
  -> Final Export evidence
  -> Track WAV / audio health
  -> Per-track manual audio review
  -> Release-driven Audio Campaign
  -> Campaign Governance archive verification
  -> Campaign Remediation closeout/signoff/verification
  -> GA readiness audio checks
  -> Release Audio Certification report
  -> Certification signoff
  -> Certification ZIP
  -> offline verifier
  -> Release signoff / GA readiness gate
```

### 3.2 这一版要证明什么

v10.8 完成后，系统应能给出一个明确答案：

> 当前 Release 的音频是否已经经过真实渲染、真实人工听审、问题修复、复验、归档和离线验证，是否可以进入最终发行或交付？

它要能回答：

- 当前 Release 有多少 tracks？
- 每个 track 绑定的 `project_id + version_id + final_export_hash` 是否仍是当前？
- 每个 track 的 `song.wav` 是否存在、hash 是否匹配、audio health 是否允许 release？
- 每个 track 是否有当前 WAV hash 的 manual accepted audio review？
- Release Audio Campaign 是否覆盖全部当前 tracks？
- Campaign 是否 signed？
- Campaign Archive ZIP 是否存在且 verification passed？
- Campaign Archive verification 是否绑定当前 ZIP/manifest？
- 是否存在 needs_fix/rejected/open high-critical marker？
- 若存在问题，Remediation closeout 是否 passed？
- 若要求签核，Remediation 是否 signed 且当前？
- Remediation ZIP verification 是否 passed？
- Audio Fix Sprint recheck 是否全部 real/release-ready/manual accepted？
- 是否存在 fake/test WAV 被算进 release-ready？
- GA readiness report 是否引用当前 Certification evidence？
- Certification 本身是否可导出、可离线验证、可签核、不可静默改写？

---

## 4. 明确不做

v10.8 不做以下事情：

- 不自动生成音乐。
- 不自动替代人工听审。
- 不自动把 `needs_fix/rejected` 改成 accepted。
- 不自动 select candidate。
- 不自动 signoff Campaign / Remediation / Release。
- 不接第三方音乐 API。
- 不做 DAW 级音频编辑。
- 不做 loudness/mastering 新算法。
- 不新增外部分发平台适配。
- 不替代 v8/v9 Trust / Public Trust Center 链路。

v10.8 是音频准出证据聚合层，不是音乐生成层，也不是公开信任门户层。

## 7. Store 设计

新增类：

```python
class ReleaseAudioCertificationStore:
    def refresh_report(self, release_id: str, payload: dict | None = None) -> dict: ...
    def read_report(self, release_id: str, *, default: dict | None = None) -> dict: ...
    def build_track_matrix(self, release_id: str) -> dict: ...
    def build_evidence_index(self, release_id: str) -> dict: ...
    def build_blocker_register(self, release_id: str) -> dict: ...
    def signoff(self, release_id: str, payload: dict | None = None) -> dict: ...
    def reset_signoff(self, release_id: str, payload: dict | None = None) -> dict: ...
    def export_package(self, release_id: str) -> dict: ...
    def build_zip(self, release_id: str) -> dict: ...
    def verify_zip(self, release_id: str, **kwargs) -> dict: ...
    def gate(self, release_id: str, *, required: bool, require_signed: bool = False) -> dict: ...
```

### 7.1 `refresh_report()`

`refresh_report()` 应读取并刷新当前证据：

- Release tracks。
- 每个 track 的 Final Export manifest。
- 每个 track 的 WAV/audio health。
- per-track manual audio review。
- Release-driven Audio Campaign link。
- Audio Campaign report/case-index/signoff。
- Audio Campaign Governance archive verification。
- Audio Campaign Remediation closeout/signoff/verification。
- GA readiness report。

注意：

- 若 certification 已签核，默认禁止 refresh，返回/抛出 409。
- 后续如需 reset，必须走 approved Change Request。v10.8 可以先不做复杂 CR，但至少要防止签核后静默重写。

### 7.2 `gate()`

Release signoff 和 GA readiness 应调用 gate：

```python
gate(release_id, required=True, require_signed=True)
```

必须满足：

- certification report `status == passed`
- report integrity OK
- source current
- track matrix 当前
- evidence index 当前
- blocker register 当前
- 若 `require_signed=True`，必须有 signed certification signoff，且 signoff 绑定当前 report hash/source hash。

任何 stale / missing / failed 都是 hard_block，`force=true` 不能绕过。

## 8. Certification 检查规则

### 8.1 Release Track / Final Export

每条 Release track 必须：

- 有 `project_id`
- 有 `version_id`
- 有 `final_export_hash`
- 当前 `final-export/manifest.json` 存在
- 当前 manifest sha256 等于 Release track 记录的 `final_export_hash`

失败 check：

```text
release_track_final_export_missing
release_track_final_export_stale
release_track_identity_missing
release_track_duplicate_identity
```

### 8.2 WAV / Audio Health

每条 track 必须：

- `song.wav` 存在，或者 Release Export 中有当前 mastered/selected WAV。
- WAV header 合法。
- audio health `status in {"passed", "warning"}`，但不能有 hard blockers。
- 不能是 test/fake WAV。
- renderer runner kind 必须是 `real` 或等价 release-ready 标识。

失败 check：

```text
track_wav_missing
track_wav_hash_mismatch
track_audio_health_failed
track_audio_fake_or_test
track_audio_not_release_ready
```

### 8.3 Per-track Manual Review

每条 track 必须：

- 有 manual accepted review。
- review 绑定当前 WAV hash。
- `playback_confirmed == true`
- reviewer name/role 已脱敏。
- synthetic review 不能作为 release-ready 证据。

失败 check：

```text
track_manual_review_missing
track_manual_review_not_accepted
track_manual_review_stale_wav
track_synthetic_review_not_allowed
```

### 8.4 Audio Campaign

必须：

- 有 Release-driven campaign link。
- coverage status passed。
- campaign cases 覆盖当前 Release tracks by `project_id + version_id + final_export_hash`。
- campaign report status passed。
- campaign signed。

失败 check：

```text
audio_campaign_missing
audio_campaign_coverage_failed
audio_campaign_case_index_stale
audio_campaign_report_failed
audio_campaign_signoff_missing
```

### 8.5 Audio Campaign Governance

必须：

- Archive ZIP 存在。
- Archive verification report exists。
- verification report status passed。
- verification report 绑定当前 archive ZIP sha256/size/manifest hash。
- Archive evidence 与当前 campaign signoff/report/case-index 一致。

失败 check：

```text
audio_campaign_archive_missing
audio_campaign_archive_verification_missing
audio_campaign_archive_verification_failed
audio_campaign_archive_verification_stale
```

### 8.6 Audio Campaign Remediation

如果 campaign 没有 failed case/open high-critical marker，则 Remediation 可以是 `not_required`。

如果存在 `needs_fix` / `rejected` / high / critical marker，则必须：

- remediation plan exists。
- closeout report passed。
- all linked Audio Fix Sprints closed。
- all candidate A/B reviews manual。
- all recheck sessions manual accepted。
- recheck WAV 是 real release-ready。
- remediation signoff exists when `require_signed=True`。
- remediation ZIP verification passed。
- remediation evidence current source。

失败 check：

```text
audio_campaign_remediation_required_missing
audio_campaign_remediation_closeout_failed
audio_campaign_remediation_signoff_missing
audio_campaign_remediation_verification_failed
audio_campaign_remediation_stale_source
audio_fix_sprint_recheck_missing
audio_fix_sprint_recheck_fake_audio
audio_fix_sprint_manual_ab_missing
```

### 8.7 GA Readiness

Certification 应能成为 GA readiness 的一个外部证据：

```text
ga.release_audio_certification
```

GA verifier 要求时不能只信 GA report 自证，必须传入 Certification ZIP + verification report。

失败 check：

```text
ga_audio_certification_missing
ga_audio_certification_verification_failed
ga_audio_certification_stale
```

## 9. Export / ZIP

### 9.1 固定 allow-list

ZIP entry 固定：

```text
manifest.json
certification-report.json
track-audio-matrix.json
evidence-index.json
blocker-register.json
README.txt
```

可选：

```text
certification-signoff.json
```

Verifier 必须拒绝：

- 任何额外 entry。
- manifest.files[] 声明的额外文件。
- duplicate entry。
- 反斜杠路径。
- `.musicforge/` 或大小写变体。
- nested ZIP。
- path traversal。
- 绝对路径。
- 本机路径/token/API key 泄漏。

### 9.2 manifest

```json
{
  "package_type": "release_audio_certification",
  "schema_version": 1,
  "release_id": "rel-000001",
  "generated_at": "...",
  "source_hash": "...",
  "report_hash": "...",
  "track_matrix_hash": "...",
  "evidence_index_hash": "...",
  "blocker_register_hash": "...",
  "signoff_hash": null,
  "files": [],
  "zip": {},
  "integrity_hash": "..."
}
```

`integrity_hash` 不包含 `zip` 字段，或者明确使用已有项目同类 verifier 的稳定口径。

## 13. Release Signoff 接入

Release signoff payload 新增：

```json
{
  "require_release_audio_certification": true,
  "require_release_audio_certification_signed": true
}
```

规则：

- `require_release_audio_certification=true` 时 certification report 必须 passed。
- `require_release_audio_certification_signed=true` 时 certification signoff 必须 signed 且 current。
- 任何 stale / missing / failed 是 hard_block。
- `force=true` 不能绕过 stale/current/source/hash 问题。
- `force=true` 也不能绕过 missing real audio / missing manual review / unresolved remediation。

Release signoff sidecar 中写入：

```json
"release_audio_certification": {
  "status": "passed",
  "report_hash": "...",
  "signoff_hash": "...",
  "zip_sha256": "...",
  "verification_report_hash": "..."
}
```

## 18. 安全与证据边界

必须坚持这些规则：

- 不信 ZIP 内部自证。
- 不信 manifest.zip.entries 扩大允许文件集。
- 不允许额外 entry。
- 不允许 source_path/local_path/file_path 进入可导出证据。
- 不允许本机路径进入 report/export/ZIP。
- 不允许 fake/test WAV 被算作 release-ready。
- 不允许 synthetic review 被算作 manual release-ready。
- 不允许 `force=true` 绕过 source stale。
- 不允许签核后 refresh/export/zip 静默改写。
- verification report 必须绑定当前 ZIP sha256、size、manifest hash。
- Release signoff / GA readiness 使用 Certification evidence 时，必须绑定外部 Certification ZIP + verification report。

## 22. 给开发的话

这版不要再做散点按钮。v10.8 的核心是“音频准出总闸”：把 v10.2 到 v10.7 已经有的真实听审、修复、复验、Campaign、Remediation、Governance 证据统一成 Release Audio Certification。

开发时请按阶段推进，每完成一个阶段就本地测试、提交、推 GitHub。不要等到最后堆成一个大提交。尤其注意两条红线：

1. 签核后不能静默改写证据。任何 refresh/export/zip 如果会改变已签核证据，都必须 409。
2. 离线 verifier 不能信包内自证。ZIP entry、manifest.files、report、signoff、verification report 都要互相绑定，并且对额外文件、重签伪造、stale source 做失败回归。

- 哪些 negative smoke 已覆盖。
- 是否跑过完整 pytest；如果没跑，说明原因，不要虚报。

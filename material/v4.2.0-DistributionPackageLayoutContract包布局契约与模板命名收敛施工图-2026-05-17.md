# v4.2.0 Distribution Package Layout Contract 包布局契约与模板命名收敛施工图

日期：2026-05-17

目标版本：v4.2.0

当前稳定基线：v4.1.2

负责人角色：开发执行

Reviewer 角色：继续按安全、可审计、可本地验证、可离线验收的标准卡口

---

## 1. 背景

v4.0.0 到 v4.0.1 已经完成 Distribution Prep：本地 Distribution Target、artwork、QA、export、ZIP、signoff、verify-distribution-package。

v4.1.0 到 v4.1.2 完成 Platform Template Packs 和 Submission Checklist，并连续修掉两个关键边界：

- v4.1.1：已签核 target 绑定的全局 template pack 不允许 update/delete。
- v4.1.2：任何 target 仍引用 template pack 时，不允许 delete，避免悬空 `template_pack_id` 绕过 rules/checklist。

现在稳定基线已经具备“模板驱动 QA 和 checklist”的能力，但 reviewer 在 v4.1.0 审查时留下一个 P2：`file_naming` 在导出时没有完整落地。

当前问题不是一个简单 bug，而是 Distribution Package 的“包布局契约”还不够明确：

- Template Pack 允许定义 `file_naming.artwork/audio/lyrics`。
- Export 只有 audio/artwork 部分使用模板命名。
- lyrics 没有走模板命名。
- audio 当前会丢弃模板里的目录，只保留文件名。
- artwork 只替换 `{ext}`，不支持已允许的其他变量。
- manifest 中 `artwork.package_path` 仍固定写成 `artwork/cover.ext`，可能和真实文件路径不一致。
- Studio 不能预览最终包布局，用户要等导出后才知道文件会怎么命名。
- verifier 只验证 ZIP 文件安全和 hash，没有验证“模板声明的布局规则是否被真实执行”。

v4.2.0 要把这个环节收紧：Template Pack 的命名规则必须变成可预览、可校验、可导出、可离线验收的契约。

---

## 2. 版本定位

v4.2.0 的定位是：

> Distribution Package Layout Contract：把 template `file_naming` 从“配置字段”升级为“可验证的包布局契约”。

做完后，用户应该能在 Studio 中选择 Distribution Target 后，提前看到：

- audio 文件最终路径。
- artwork 文件最终路径。
- lyrics 文件最终路径。
- platform metadata CSV 路径。
- checklist/docs 路径。
- 是否有重名冲突。
- 是否有不安全路径。
- 哪些文件来自 template naming，哪些是固定 sidecar。

导出后，manifest 和 verifier 应该能证明：

- 真实 ZIP entries 和 layout preview 一致。
- `manifest.layout` 中记录了模板命名规则、渲染结果和 hash。
- `artwork.package_path` 与实际 entry 一致。
- audio、lyrics、artwork 都不会越界、不会反斜杠、不会绝对路径、不会重复 entry。
- 篡改 template naming 或 ZIP entry 后，verify-distribution-package 能失败。

---

## 3. 不做什么

v4.2.0 不做以下事项：

- 不接发行平台 API。
- 不上传文件到任何平台。
- 不保存平台账号、cookie、token。
- 不做真实平台官方规范同步。
- 不做多平台批量提交。
- 不做 GUI 拖拽式文件树编辑器。
- 不做用户自定义脚本、Jinja、表达式执行。
- 不允许模板读取本机路径。
- 不允许模板从 URL 下载内容。
- 不把 `file_naming` 扩展成自由代码。

## 4. 当前实现问题清单

### 4.1 audio 命名丢目录

当前 `song_agent/distribution_export.py` 中 `_copy_audio_files()` 使用：

```python
base = render_file_pattern(naming["audio"], track=track, ext="wav").split("/")[-1]
target = export_dir / "audio" / name
```

这意味着模板如果写：

```json
{
  "file_naming": {
    "audio": "tracks/disc-{disc_number}/{track_number:02d}-{slug_title}.wav"
  }
}
```

实际导出会丢掉 `tracks/disc-1/`，变成 `audio/01-title.wav`。

### 4.2 artwork 命名只替换 `{ext}`

当前 `_copy_artwork()` 使用：

```python
rel = naming.get("artwork", "cover.{ext}").replace("{ext}", suffix.lstrip("."))
```

但模板校验允许 `{slug_title}`、`{track_number}` 等变量。若用户写：

```json
{
  "file_naming": {
    "artwork": "covers/{slug_title}.{ext}"
  }
}
```

导出可能得到字面量 `{slug_title}`，并且 manifest 的 `package_path` 仍写成 `artwork/cover.png`。

### 4.3 lyrics 没走模板命名

当前 Distribution Export 直接：

```python
_copy_tree_prefix(release_export_dir, export_dir, "lyrics", copied_files)
```

这会保留 Release Export 原始 lyrics 路径，不使用 template `file_naming.lyrics`。

### 4.4 manifest 缺少 layout contract

当前 manifest 有：

- `template`
- `checklist`
- `files`
- `artwork`

但没有一个明确的 `layout` 段描述：

- template naming pattern。
- 每个 track/audio/lyrics/artwork 的渲染结果。
- 冲突解决结果。
- 哪些 entry 是 fixed sidecar，哪些 entry 是 rendered。

### 4.5 Studio 无法预览布局

用户在 Studio 里选 template 后，看不到最终文件树。

### 4.6 verifier 不知道模板布局是否真实执行

目前 verifier 能发现 hash tamper、dangerous entry、duplicate entry，但不能判断：

- template 里声明 audio 应该在 `tracks/...`，实际 ZIP 却在 `audio/...`。
- artwork package_path 和真实 entry 不一致。
- lyrics 没按 template 命名。

## 5. 总体目标

v4.2.0 必须完成以下目标：

1. 新增 Distribution Layout 计算层。
2. Template file naming 按类型收敛，不再使用一套变量随便套所有文件。
3. Export 统一使用 layout 计算结果复制 audio/artwork/lyrics。
4. Manifest 写入 layout summary 和 layout hash。
5. Verifier 校验 layout hash、layout entries、template naming 与真实 ZIP entries。
6. Studio 支持 Layout Preview。
7. release-check 覆盖自定义目录、重名、tamper、path unsafe、manifest mismatch。
8. README / CHANGELOG / version 更新。

## 6. 设计原则

### 6.1 模板是数据，不是程序

`file_naming` 只允许 `{variable}` 变量替换，不允许：

- 函数调用。
- 表达式。
- 条件。
- 循环。
- 环境变量。
- 文件系统路径读取。
- URL。

### 6.2 按文件类型限定变量

不同文件类型允许不同变量：

audio/lyrics 是 track-scoped，可以使用 track 变量。

artwork 是 release-scoped，不能使用 track-only 变量，除非后续支持 per-track artwork。v4.2.0 不做 per-track artwork。

### 6.3 先 layout，再 export

导出不能边复制边临时拼路径。必须先生成 layout plan：

```text
target + release manifest + metadata + template + artwork
  -> DistributionLayoutPlan
  -> validate layout
  -> export files exactly as planned
  -> manifest.layout = summary(plan)
```

### 6.4 manifest 是验收契约

manifest 不只列文件 hash，还要写：

- layout schema version。
- layout source hash。
- rendered entries。
- naming patterns。
- collision strategy。

### 6.5 verifier 只信 ZIP 内内容

离线 verifier 不依赖 `.musicforge/` 工作区。它只读取 ZIP 内：

- distribution-manifest.json
- template-pack.json
- template-summary.json
- docs/checklist.json
- package/release/tracklist/metadata 文件
- ZIP entries

然后重算 layout 相关 hash。

### 8.1 DistributionLayoutPlan

建议使用 dict，不强制 dataclass，保持项目现有风格。

```json
{
  "schema_version": 1,
  "release_id": "release-000001",
  "target_id": "target-000001",
  "template_pack_id": "tpl-000001",
  "template_hash": "...",
  "source_hash": "...",
  "collision_strategy": "append-index",
  "entries": [
    {
      "entry_id": "audio:track-001",
      "kind": "audio",
      "track_id": "track-001",
      "source_rel": "tracks/track-001/song.wav",
      "path": "audio/01-song-title.wav",
      "pattern": "audio/{track_number:02d}-{slug_title}.{ext}",
      "ext": "wav",
      "required": false,
      "exists": true,
      "status": "planned"
    },
    {
      "entry_id": "lyrics:track-001",
      "kind": "lyrics",
      "track_id": "track-001",
      "source_rel": "lyrics/01-song-title.txt",
      "path": "lyrics/01-song-title.txt",
      "pattern": "lyrics/{track_number:02d}-{slug_title}.txt",
      "ext": "txt",
      "required": false,
      "exists": true,
      "status": "planned"
    },
    {
      "entry_id": "artwork:cover",
      "kind": "artwork",
      "track_id": null,
      "source_rel": ".musicforge/releases/.../distribution/artwork/artwork-001.png",
      "path": "artwork/cover.png",
      "pattern": "artwork/cover.{ext}",
      "ext": "png",
      "required": true,
      "exists": true,
      "status": "planned"
    }
  ],
  "warnings": [],
  "errors": [],
  "summary": {
    "status": "passed",
    "entry_count": 3,
    "audio_count": 1,
    "lyrics_count": 1,
    "artwork_count": 1,
    "collision_count": 0
  },
  "layout_hash": "..."
}
```

注意：

- `source_rel` 只能是用于诊断的相对描述，不能泄露本机绝对路径。
- artwork 的实际本机路径不能进 manifest。
- `layout_hash` 不包含 volatile 时间。

### 8.2 Manifest layout 段

Distribution manifest 增加：

```json
{
  "layout": {
    "schema_version": 1,
    "layout_hash": "...",
    "source_hash": "...",
    "template_pack_id": "tpl-000001",
    "template_hash": "...",
    "collision_strategy": "append-index",
    "entries": [
      {
        "entry_id": "audio:track-001",
        "kind": "audio",
        "track_id": "track-001",
        "path": "audio/01-song-title.wav",
        "sha256": "...",
        "size_bytes": 12345
      }
    ],
    "summary": {
      "status": "passed",
      "entry_count": 3
    }
  }
}
```

manifest `files[]` 仍是全量文件列表。`layout.entries[]` 是 template-controlled entries 的子集。

### 8.3 Exported layout sidecar

Distribution Export 增加：

```text
layout/manifest-layout.json
layout/file-tree.txt
```

`manifest-layout.json` 写入 manifest `layout` 的完整可读版本。

`file-tree.txt` 是人类可读文件树，例如：

```text
Distribution Package Layout

audio/
  01-song-title.wav
artwork/
  cover.png
lyrics/
  01-song-title.txt
docs/
  checklist.md
  submission-notes.md
```

## 9. File Naming 规则收敛

### 9.1 默认命名

没有 template 时，保持现有兼容行为：

```json
{
  "audio": "audio/{track_number:02d}-{slug_title}.wav",
  "lyrics": "lyrics/{track_number:02d}-{slug_title}.txt",
  "artwork": "artwork/cover.{ext}"
}
```

注意：默认 audio 仍可以输出到 `audio/`，但要通过 layout 统一计算，而不是散落在 export 内部。

### 9.2 audio 允许变量

audio 是 track-scoped：

- `{track_number}`
- `{track_number:02d}`
- `{disc_number}`
- `{slug_title}`
- `{track_id}`
- `{isrc}`
- `{ext}`

允许目录：

```text
audio/{track_number:02d}-{slug_title}.{ext}
tracks/disc-{disc_number}/{track_number:02d}-{slug_title}.{ext}
```

不允许：

```text
../x.wav
C:\x.wav
\\server\share\x.wav
http://example.com/x.wav
audio/{unknown}.wav
audio/{title.upper()}.wav
```

### 9.3 lyrics 允许变量

lyrics 是 track-scoped：

- `{track_number}`
- `{track_number:02d}`
- `{disc_number}`
- `{slug_title}`
- `{track_id}`
- `{isrc}`
- `{language}`
- `{ext}`

默认 ext 为 `txt`。

### 9.4 artwork 允许变量

artwork 是 release-scoped：

- `{release_slug}`
- `{release_id}`
- `{upc}`
- `{profile_id}`
- `{target_id}`
- `{ext}`

不允许 `{track_number}`、`{slug_title}`、`{track_id}` 这类 track-only 变量。

如果 v4.1 已经允许用户创建了 artwork pattern 含 track 变量，v4.2.0 要在 validate 中报错，并且在 target QA 中显示 `template_file_naming_invalid`。

### 9.5 platform CSV 命名

v4.2.0 可以保留固定：

```text
template-platform-metadata.csv
```

暂不允许 template 自定义 CSV 文件名。多 CSV 模板放 v4.3+。

## 10. 冲突处理

### 10.1 同路径冲突

如果两个 layout entries 渲染到同一个 path：

- 默认策略：`append-index`
- 示例：

```text
audio/song.wav
audio/song-2.wav
audio/song-3.wav
```

但必须记录 collision：

```json
{
  "entry_id": "audio:track-002",
  "original_path": "audio/song.wav",
  "path": "audio/song-2.wav",
  "collision": true,
  "collision_index": 2
}
```

### 10.2 与 fixed sidecar 冲突

模板路径不能覆盖 fixed sidecar：

- distribution-manifest.json
- distribution-signoff.json
- package.json
- release.json
- tracklist.json
- README.txt
- template-pack.json
- template-summary.json
- docs/checklist.json
- docs/checklist.md
- docs/submission-notes.md
- release-metadata.json
- platform-metadata.csv
- credits.csv
- layout/manifest-layout.json
- layout/file-tree.txt

如果 template 渲染出这些路径，QA 必须 failed，Export 必须拒绝。

### 10.3 与普通 copied files 冲突

如果 lyrics/audio/artwork 和已有 metadata 文件冲突，也必须 failed。

## 11. Distribution QA 接入

`song_agent/distribution_qa.py` 增加 layout 相关 checks：

| check_id | 条件 | severity |
|---|---|---|
| layout_plan_valid | layout plan 无 errors | blocking |
| template_file_naming_valid | file_naming 变量和路径合法 | blocking |
| layout_no_reserved_collision | 未覆盖 fixed sidecar | blocking |
| layout_no_unsafe_paths | 无绝对路径、反斜杠、`..` | blocking |
| layout_collision_resolved | 同类冲突已 append-index | warning |
| layout_required_artwork_present | require_artwork 时 artwork entry exists | blocking |
| layout_required_audio_present | require_audio 时每轨 audio exists | blocking |

注意：

- QA 不能只在 Export 时失败，必须提前暴露给 Studio。
- QA source hash 必须包含 layout plan hash。
- template update 后未签核 target stale 的逻辑继续保留。

## 12. Distribution Export 改造

### 12.1 Export 改为使用 LayoutPlan

`build_distribution_export_package()` 流程改为：

```text
read release export manifest
resolve target template
reconcile checklist
build_distribution_layout_plan(...)
validate layout
copy fixed files
copy layout planned files
write docs/checklist
write template files
write layout sidecars
write distribution-manifest.json
```

### 12.2 删除散落复制逻辑

逐步替换：

- `_copy_audio_files()`
- `_copy_artwork()`
- `_copy_tree_prefix(..., "lyrics")`

可以保留 helper，但它们必须接受 layout entry，而不是自己计算 path。

### 12.3 artwork.package_path 修正

manifest `artwork.package_path` 必须等于 layout artwork entry 的 `path`。

如果无 artwork，保持 `{}`。

### 12.4 records 只从真实文件生成

`files[]` 的 `sha256/size_bytes` 必须从真实写入后的文件生成。

layout `entries[]` 的 `sha256/size_bytes` 也要来自真实文件，而不是计划值。

## 13. Verifier 改造

`song_agent/distribution_verifier.py` 增加 layout 验证：

### 13.1 新增 checks

| check_id | 说明 |
|---|---|
| distribution_layout_exists | v4.2+ package 必须有 manifest.layout |
| distribution_layout_sidecar_exists | `layout/manifest-layout.json` 存在 |
| distribution_layout_hash_match | manifest.layout 和 sidecar hash 一致 |
| distribution_layout_entries_declared | layout entries 都在 manifest.files 中 |
| distribution_layout_entries_exist | layout entries 都在 ZIP 中 |
| distribution_layout_file_hash_match | layout entry hash/size 与 ZIP 一致 |
| distribution_layout_reserved_collision | layout entries 没有覆盖 fixed sidecar |
| distribution_layout_template_patterns_match | layout 记录的 pattern 与 template-pack file_naming 一致 |
| distribution_artwork_package_path_match | manifest.artwork.package_path 指向真实 artwork entry |

### 13.2 兼容旧包

如果 ZIP 是 v4.1 或更早，没有 `layout`：

- verify-distribution-package 不应该直接 failed。
- 给 warning：

```text
distribution_layout_legacy_missing: warning
```

如果 manifest schema 或 package generated version >= 4.2.0，则 layout 缺失必须 failed。

### 13.3 严格模式

`verify-distribution-package --strict` 下：

- v4.1 legacy missing layout 可以 failed。
- extra entries 仍按现有规则 failed。

## 16. 安全要求

### 16.1 路径安全

所有 rendered path 必须：

- POSIX relative path。
- 不含反斜杠。
- 不以 `/` 开头。
- 不以 `//` 开头。
- 不含 `..` 或 `.` path segment。
- first segment 不含 `:`。
- 不为空。
- 不以 `/` 结尾。

### 16.2 CSV 安全保持

Platform CSV 仍必须 escape formula：

- `=`
- `+`
- `-`
- `@`
- tab
- CR/LF

### 16.3 Redaction

Layout sidecar 和 manifest layout 不能包含：

- 本机绝对路径。
- API key。
- token。
- bearer。
- URL。

### 16.4 ZIP 安全

现有 verifier 规则继续保留：

- duplicate entry failed。
- unsafe entry failed。
- ZIP bomb guard。
- manifest files hash。
- signoff sidecar payload hash。

## 21. 风险清单

### 风险 1：文件树改动影响旧测试

解决：

- 默认命名尽量保持现有输出路径。
- 新 layout 先覆盖 template-controlled entries。
- release-check 要检查 legacy 兼容。

### 风险 2：lyrics 文件路径来源不稳定

Release Export 里的 lyrics 可能不是每首歌都有。

解决：

- layout entry `exists=false` 可作为 warning 或 passed，取决于 template/profile `require_lyrics`。
- v4.2.0 不把 lyrics 默认设为 blocking，除非 template rules 有 `require_lyrics=True`。

### 风险 3：artwork 是 release-scoped，但模板作者用了 track variable

解决：

- validate failed。
- QA failed。
- Studio 明确显示不支持。

### 风险 4：collision 自动改名影响平台预期

解决：

- collision 记录 warning。
- manifest layout 记录 original_path 和 final path。
- Studio Layout Preview 显示 collision。

### 风险 5：Verifier 和 Export 使用不同逻辑

解决：

- layout hash 只基于 ZIP 内 manifest/template/entries 重算，不依赖工作区。
- 核心路径安全函数尽量复用，但 verifier 必须只读 ZIP。

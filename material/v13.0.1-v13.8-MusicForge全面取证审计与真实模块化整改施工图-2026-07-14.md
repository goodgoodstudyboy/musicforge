# v13.0.1-v13.8 MusicForge 全面取证审计与真实模块化整改施工图

日期：2026-07-14
审查对象：v12.14.0 到 v13.0.0
当前 HEAD：03e5ca021b5e7cac4615595b05e2739993116035
结论等级：v13.0.0 发布链路通过，但不能作为“真实 LTS 架构收口”验收。

## 1. 总结结论

v13.0.0 的发布工程状态是好的：tag、Release、GitHub Actions quality、active pytest、GA、v13、latest、security profile 都有通过记录，工作区干净。它可以作为一个“发布过的过渡基线”。

但 v12.14-v13.0 这条重构线没有真正完成施工图承诺的架构目标。核心问题不是某一个 smoke 没过，而是很多验收条件本身过弱：

- 架构无环是通过把 245 个旧模块重新归类为 `compatibility` 后排除得到的，不是实际迁移完成。
- Verification / Lifecycle / Persistence kernel 已经存在，但大量生产路径仍在用各自的旧实现。
- Evidence Graph / Policy Engine 有入口，但 GA 和 Release signoff 主路径仍是 `require_*` 参数树。
- CLI/API/Web 分层有外壳，但 API/Web 和多个 CLI command 仍是巨型接口模块。
- release-check 拆分有目录结构，但 current profile 仍大量通过 legacy wrapper 或 monolith 执行。
- CI quality 通过的是 active suite，不等于施工图要求的 full/legacy/nightly LTS 验收。

因此，后续开发不要继续叠功能。下一阶段必须先把“安全内核 + 架构门禁 + 真实迁移 + 测试治理”收紧，否则 v13 之后继续加功能会把复杂度重新推高。

## 2. 审计方法

### 2.4 独立攻击面复核

复核了几个不依赖 release-check 自身的共享内核缺口：

- Evidence Graph 可以信任 manifest 里的 `component_id/generation/current`，没有从 runtime evidence 反推真实身份。

这些是 P1，因为它们位于“统一内核”层。只要后续能力开始大量复用这些内核，缺口会放大。

## 3. 分版本验收结论

已完成：

- 有 architecture guardrails。
- 有 baseline、module ownership、mega file、cycle、compat import 统计。

## 4. P1 问题清单

### P1-1 Evidence Graph 身份和 generation 可被 manifest 伪造

位置：

- `song_agent/platform/evidence_graph/builder.py:156`
- `song_agent/platform/evidence_graph/builder.py:185`
- `song_agent/platform/evidence_graph/builder.py:188`
- `song_agent/platform/evidence_graph/builder.py:190`

问题：

Evidence Graph 使用 manifest row 提供的 `component_id/generation/current` 构造 EvidenceRef，而不是从 runtime verification summary 或 package source 反推真实身份。攻击者可以把真实 Program package 的 manifest item 改成另一个 component_id/generation，并让 graph 输出伪造 identity。

影响：

- Policy Engine 的节点身份不可信。
- require policy 未来一旦成为主闸，会把错误 evidence 计入正确组件。

必须修复：

- CapabilitySpec 必须声明 identity extractor。
- runtime verifier 必须输出 canonical identity：component_type、component_id、generation、current_generation、package_type、source_hash。
- Evidence Graph 必须比较 manifest identity、runtime identity、external report identity，三者不一致即 failed。

### P1-2 Verification Kernel ZIP entry 类型检查不足

位置：

- `song_agent/platform/verification/engine.py:21`
- `song_agent/platform/verification/engine.py:23`
- `song_agent/platform/verification/engine.py:68`
- `song_agent/platform/verification/manifest.py:39`

问题：

- `strict` 被丢弃。
- 没有拒绝目录 entry。
- 没有统一拒绝非普通文件 entry。
- manifest 只校验 hash，不校验 size。

影响：

- Shared kernel 不能作为所有 verifier 的安全基础。
- 后续迁移越多，风险越集中。

必须修复：

- `strict=False` 只能减少非安全类 warning，不能关闭 path/duplicate/directory/trailing/redaction/package-type/hash/size。
- 对 `ZipInfo.is_dir()`、外部属性中的 symlink/特殊文件、空名、raw backslash、absolute path、parent traversal 全部 hard fail。
- manifest row 必须要求 `path/sha256/size_bytes`。

### P1-3 ArchiveBuilder duplicate ZIP 可绕过

位置：

- `song_agent/platform/lifecycle/archive.py:51`
- `song_agent/platform/lifecycle/archive.py:52`

问题：

已有 ZIP 校验用 `set(archive.namelist())`，duplicate entry 会被 set 去重。若追加一个 duplicate entry，`archive.read(name)` 读取最后一个匹配内容时可能仍等于 expected，导致污染 ZIP 被当作 frozen snapshot。

必须修复：

- 所有 archive 校验必须使用 `infolist()`。
- entry count、entry order、duplicate、CRC、size、raw central directory 都要校验。
- ArchiveBuilder 应直接复用 Verification Kernel 的 ZIP envelope checks。

### P1-4 ChangeRequestService fail-open

位置：

- `song_agent/platform/lifecycle/change_control.py:32`
- `song_agent/platform/lifecycle/change_control.py:35`
- `song_agent/platform/lifecycle/change_control.py:36`
- `song_agent/unified_release_program_operations.py:153`
- `song_agent/unified_release_program_operations.py:190`

问题：

通用 ChangeRequestService 只有在 approval 带 `approved_actions` 时才校验 action；只有 approval 和 request 都有 hash 时才比较 request hash。平台服务作为统一内核时应该安全默认，而不是由每个 store 自己补救。

必须修复：

- approval 必须含 `approved_actions`，且 expected action 必须在内。
- approval 必须含 `request_hash`，且等于 request submitted hash。
- request 必须含 immutable `submitted_request_hash`。
- approval target/source 必须等于 request target/source，也必须等于 expected target/source。
- 旧 approval 格式需要 migration 或 compatibility gate，不能继续 fail-open。

### P1-5 Persistence/UoW/SQLite authority 没有生产落地

问题：

v12.17 的 FileUnitOfWork、WorkflowRepository、SQLite index 基本不是生产写入主路径。Program 系列 store 仍直接读写 JSON，SQLite 只是派生索引。

影响：

- 崩溃恢复、并发事务、rollback 仍依赖各 store 自己小心实现。
- 容易出现 JSON 已写、索引未同步、on_commit 失败的半状态。

必须修复：

- 选一个 active vertical slice，把 repository + UoW 作为唯一写入入口。
- SQLite current generation / event ledger 作为 authority，JSON export 作为 projection。
- 禁止新 store 直接使用 `write_json()` 写状态文件，除 migration/export 外。

### P1-6 Lifecycle Kernel 没有成为生产基础

问题：

ArchiveBuilder、SignoffService、ResetService、GenerationService adoption 太低。每个业务 store 仍保留自己的 signoff/archive/reset 算法。

影响：

- 以前每个版本反复修的 full-resign、delete-signoff、signed mutation、CR reuse 问题还会在新 store 重复出现。

必须修复：

- 所有 active Program/Continuity/UCC signoff/archive/reset 改为统一 lifecycle service。
- 旧 custom code 只允许作为 adapter，不允许保留独立安全算法。
- lifecycle service 自带攻击回归矩阵。

### P1-7 Interface modularization 只是外壳

位置：

- `song_agent/interfaces/api/router.py:84`
- `song_agent/interfaces/api/router.py:130`
- `song_agent/interfaces/api/server.py:20`
- `song_agent/interfaces/api/routes/studio.py:8`

问题：

API route registry 不是实际 dispatch。它扫描旧 `_handle_request` 源码生成 inventory，schema 是 `legacy-compatible`。多个 CLI/API 文件仍是数千行。

必须修复：

- API registry 必须成为真实 dispatch。
- 每个 route handler 只做 parse、调用 application service、serialize。
- 新 API route 不允许直接 import compatibility store。
- Web panel 必须真正拆分加载，不再把巨型 `app.js` 当唯一实现。

### P1-8 Policy Engine 不是主闸

位置：

- `song_agent/ga_readiness.py:59`
- `song_agent/ga_readiness_verifier.py:74`

问题：

GA build/verify 仍是上百个参数和大量 `require_*` 分支。Policy Engine 只在有 evidence_manifest 时作为补充。

必须修复：

- GA/Release gate 以 Evidence Manifest + Policy Profile 为主入口。
- 旧 `require_*` 参数只能转换成 policy profile，不能独立决定 readiness。
- 每个 capability 必须完整声明 CLI/API/Web/release-check/gate policy metadata。

### P1-9 release-check 没有真正脱离 legacy monolith

位置：

- `song_agent/release_check/checks/registry.py:30`
- `song_agent/release_check/checks/legacy/monolith.py`

问题：

registry 找不到 callable 时回落 monolith。latest/GA/v12/v13/security 仍有大量 legacy wrapper 或 monolith callable。v13 的 `test_current_profiles_exclude_historical_monolith` 不能证明 current profiles 完全脱离 monolith。

必须修复：

- latest、ga、v13、security profile 不允许任何 callable 来自 legacy wrapper 或 monolith。
- legacy monolith 只能属于 `legacy` profile。
- release-check governance 必须输出 per-profile legacy count，并对 current profile hard fail。

### P1-10 v13 LTS reviewer package 证据不完整

问题：

- final quality workflow excludes slow/legacy。
- 没有 final SHA nightly 通过。
- reviewer final package 没有 full release-check profile。
- migration plan file_count 为 0，不能证明真实 workspace migration。

必须修复：

- LTS reviewer package 必须包含 final SHA 的 quality、nightly、full release-check、active suite、legacy suite、migration rehearsal。
- migration fixture 必须包含至少一个代表性 v12.13 workspace，不能是空 plan。

## 5. P2/P3 问题清单

### P2-1 架构 ratchet 可被当前 baseline 自证

`architecture-baseline.json` 与当前代码同提交更新时，门禁只说明“没有超过当前基线”，不能证明相比上一 release 变好。

修复：architecture ratchet 必须读取上一 release tag 的 baseline，并生成不可修改的 delta report。

### P2-2 interfaces 未纳入硬大小门禁

当前最大臃肿点在 interfaces，但结构化限制重点没有让接口层 hard fail。

修复：所有 interface module 进入 max file lines、max function lines、max direct domain import、max compatibility import 门禁。

### P2-3 docs 继续臃肿

README、CHANGELOG、material 都很大，docs/changelog 只有 placeholder。

修复：README 保留用户入口，详细历史迁入 docs/changelog；material 只保留当前 LTS/施工图索引，历史计划归档。

### P2-4 mypy/Ruff 覆盖不足

Ruff workflow 排除了部分接口路径，mypy 只覆盖很小文件集合并 skip imports。

修复：新增 strict subset，至少覆盖 platform/application/domains/interfaces 新模块；旧 compatibility 可逐步豁免。

### P2-5 测试分类依赖路径和名字

slow/legacy 标记依赖自动规则，容易让核心风险被排除。

修复：新测试必须显式 marker；CI 对未标 marker 的测试 fail。

## 6. 后续版本施工路线

从现在起，所有版本都必须遵守：

- 每版只修一个主目标。
- 每版必须有 reviewer checklist。
- 每版先跑定向，再跑 current profiles，再跑 GA。
- 每版必须在干净工作区复跑 GA 后才能 commit/tag/release。
- reviewer 未明确 PASS，不进入下一版。
- 不允许新增功能入口绕过 platform/application/domain 边界。

## 7. v13.0.1 安全内核 hotfix

目标：先修共享内核的 P1。这个版本必须优先，不要再加功能。

范围：

- Evidence Graph identity binding。
- Verification Kernel ZIP entry safety。
- ArchiveBuilder duplicate/trailing/path safety。
- ChangeRequestService fail-closed。

不做：

- 不做大迁移。
- 不拆 Web。
- 不改业务 UI。

实现任务：

1. 在 `RuntimeVerificationSpec` 或 `CapabilitySpec` 增加 `identity_fields` / `identity_extractor` 契约。
2. 所有 capability runtime verifier 返回 canonical identity：
   - component_type
   - component_id
   - generation
   - current_generation
   - package_type
   - source_hash
3. Evidence Graph build 时比较：
   - manifest item identity
   - runtime summary identity
   - external verification report identity
4. 修 `verify_package_envelope()`：
   - `strict` 不得被丢弃。
   - directory entry hard fail。
   - symlink/特殊文件 hard fail。
   - manifest size_bytes 必须校验。
5. 修 ArchiveBuilder：
   - 用 `infolist()`。
   - duplicate hard fail。
   - existing ZIP 与 frozen snapshot 比较必须包括 entry count、entry order、raw names、size、hash。
6. 修 ChangeRequestService：
   - approval 缺 `approved_actions` 直接 fail。
   - approval 缺 `request_hash` 直接 fail。
   - request 缺 `submitted_request_hash` 直接 fail。
   - target/source/action/hash 必须全匹配 expected。
7. 给已有 Program Operations/Receiver Acceptance/Command Center reset 路径补 migration 或 compatibility normalization。

必须新增测试：

- Evidence Graph forged `component_id` fails。
- Evidence Graph forged `generation/current` fails。
- Verification Kernel directory entry fails。
- Verification Kernel symlink or special file fails。
- Verification Kernel manifest wrong size fails。
- ArchiveBuilder duplicate existing ZIP fails。
- ChangeRequest approval missing actions fails。
- ChangeRequest approval missing request_hash fails。
- Existing v12/v13 smoke 全部通过。

```powershell
python -m song_agent.cli doctor
git diff --check
```

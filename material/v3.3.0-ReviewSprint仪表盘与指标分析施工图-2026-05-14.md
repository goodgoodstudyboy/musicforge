# v3.3.0 Review Sprint 仪表盘与指标分析施工图

日期：2026-05-14

当前稳定基线：v3.2.1

目标版本：v3.3.0

定位：在 v3.2.1 已经完成 Review Sprint Recommendation Report 和 Action Queue 的基础上，新增 Review Sprint Dashboard / Metrics 层，把一轮反馈推进过程中的任务状态、候选质量、Action Queue 执行结果、provider 成本、人工采纳、质量变化、导出状态，汇总成可解释、可复盘、可本地验证的项目管理视图。v3.3.0 只做分析和展示，不新增自动 apply，不新增自动 resolve，不新增 provider judge。

---

## 1. 背景

当前系统已经完成了一条很长的创作闭环：

```text
Project
  -> Version
  -> Visual Editor Preview
  -> Audition
  -> Review Board
  -> ReviewTask
  -> ReviewCandidate
  -> Decision Report
  -> ReviewSprint
  -> Recommendation Report
  -> Action Queue
  -> Manual Apply
  -> Compare / Export / Final Export
```

v3.0.0 解决的是“把多条反馈放进一个 Sprint 管理”。

v3.1.0 解决的是“告诉用户下一步建议做什么”。

v3.2.0 / v3.2.1 解决的是“把建议变成可选择、可审计、可安全执行的 Action Queue”。

现在的问题不是缺少执行按钮，而是缺少管理视图：

- 一轮 Sprint 到底推进得怎么样？
- 哪些 task 已经解决，哪些还卡着？
- local/provider 候选分别产出了多少？
- provider 花了多少 token，是否值得？
- Action Queue 执行成功率是多少？
- 多少建议被采纳，多少被跳过？
- 人工 apply 的候选是否来自系统推荐？
- Sprint 是否真的让作品质量变好了？
- 当前 Project 是否已经接近 final-ready？
- 下一轮应该继续修，还是可以收尾？

v3.3.0 要补的是“复盘与管理层”。

---

## 2. 一句话目标

v3.3.0 要让 Review Sprint 从“可执行队列”升级为“可度量的创作迭代工作台”：

```text
Review Sprint data
  -> Metrics snapshot
  -> Dashboard report
  -> Trend / funnel / cost / quality views
  -> Project-level summary
  -> Export / Final Export summary
```

核心不是替用户做决定，而是让用户清楚看到：

- 这轮反馈修了什么。
- 系统做了什么。
- 人工选择了什么。
- 花了多少成本。
- 质量有没有变化。
- 还剩哪些风险。

## 4. 核心原则

### 4.1 Metrics 是派生数据

Metrics 不应该成为业务真相来源。

真实状态仍来自：

- Project document。
- Project versions。
- ReviewTask。
- ReviewCandidate。
- Decision Report。
- ReviewSprint。
- Recommendation Report。
- Action Queue。
- Provider usage。
- Quality report。
- Compare / Final Export。

Metrics 只是把这些状态汇总成可读报告。

因此 metrics 可以删除后重建。

### 4.2 Dashboard 不能改变业务状态

刷新 metrics 只允许：

- 读取现有状态。
- 写 metrics snapshot/report。
- 写 dashboard refreshed event。

不能：

- 创建 candidate。
- 执行 action queue。
- apply candidate。
- resolve task。
- archive task。
- final project。

### 4.3 指标必须可解释

每个核心指标都要能追溯来源：

```json
{
  "metric": "provider_candidate_count",
  "value": 6,
  "source": {
    "task_ids": ["review-task-001", "review-task-002"],
    "candidate_ids": ["revcand-002", "revcand-003"]
  }
}
```

不要只给一个神秘分数。

### 4.4 指标必须本地 deterministic

同一份 `.musicforge/projects/<project-id>/...` 输入，刷新 metrics 应该得到同样结果，除 `created_at/refreshed_at` 外。

不要把 provider 参与 metrics 计算。

Provider usage 可以读取并汇总，但不要调用 provider。

### 4.5 缺数据时要优雅降级

历史项目可能没有：

- recommendation-report.json
- action-queues
- decision-report.json
- quality metadata
- provider usage
- final export

Dashboard 不能报错。缺失时用：

```json
{
  "status": "not_available",
  "reason": "No action queues found."
}
```

## 5. 指标体系

### 5.1 Sprint Overview

用于回答：这轮 Sprint 现在处于什么状态？

字段建议：

```json
{
  "sprint_id": "sprint-001",
  "sprint_name": "Chorus Bass Fix",
  "status": "in_progress",
  "task_count": 5,
  "open_task_count": 2,
  "resolved_task_count": 2,
  "applied_task_count": 1,
  "blocked_task_count": 1,
  "stale_task_count": 0,
  "archived_task_count": 0,
  "ready_candidate_task_count": 3,
  "needs_more_work_count": 1,
  "completion_rate": 0.4
}
```

计算：

```text
completion_rate = resolved_task_count / active_task_count
```

active task 不包含 archived。

### 5.2 Task Throughput

用于回答：task 的推进速度和状态流转如何？

字段建议：

```json
{
  "created_task_count": 5,
  "candidate_ready_task_count": 3,
  "applied_task_count": 1,
  "resolved_task_count": 2,
  "follow_up_task_count": 1,
  "average_candidate_count_per_task": 2.4,
  "task_status_counts": {
    "open": 1,
    "candidate_ready": 2,
    "applied": 1,
    "resolved": 1
  }
}
```

不要过早计算“耗时”，除非任务事件里稳定有 timestamp。v3.3.0 可以先计算状态分布。

### 5.3 Candidate Funnel

用于回答：候选从生成到被采纳的漏斗如何？

字段建议：

```json
{
  "candidate_count": 12,
  "ready_candidate_count": 10,
  "local_candidate_count": 6,
  "provider_candidate_count": 4,
  "applied_candidate_count": 1,
  "failed_candidate_count": 0,
  "candidate_source_counts": {
    "local_review_intents": 6,
    "provider_review_patch": 4
  },
  "adoption_rate": 0.1,
  "provider_adoption_rate": 0.25,
  "local_adoption_rate": 0.0
}
```

计算：

```text
adoption_rate = applied_candidate_count / ready_candidate_count
provider_adoption_rate = applied_provider_candidate_count / ready_provider_candidate_count
local_adoption_rate = applied_local_candidate_count / ready_local_candidate_count
```

除数为 0 时返回 `null`，不要返回 0 误导用户。

### 5.4 Recommendation Adoption

用于回答：系统推荐有没有被采用？

字段建议：

```json
{
  "recommendation_report_count": 1,
  "recommended_task_count": 5,
  "top_recommendation_action": "generate_provider",
  "recommended_context_pack_count": 3,
  "saved_recommended_context_pack_count": 2,
  "manual_apply_recommended_count": 1,
  "recommendation_to_queue_item_count": 8,
  "recommendation_adoption_rate": 0.5
}
```

推荐采纳不要定义得太激进。

v3.3.0 可以定义为：

```text
recommendation_adoption_rate =
  completed action queue items created from recommendations
  / executable recommendation-backed queue items
```

manual apply 单独统计，不混入自动执行采纳率。

### 5.5 Action Queue Execution

用于回答：v3.2 的队列执行是否顺畅？

字段建议：

```json
{
  "queue_count": 3,
  "latest_queue_id": "queue-003",
  "action_item_count": 18,
  "completed_action_count": 8,
  "failed_action_count": 1,
  "blocked_action_count": 2,
  "manual_required_count": 4,
  "pending_action_count": 3,
  "provider_skipped_count": 2,
  "execution_success_rate": 0.89,
  "blocked_reasons": [
    {
      "reason": "Action queue is stale because the Recommendation Report changed.",
      "count": 1
    }
  ]
}
```

计算：

```text
execution_success_rate =
  completed_action_count / (completed + failed + blocked)
```

manual_required 不进入成功率，因为它不是自动执行项。

### 5.6 Provider Usage / Cost

用于回答：provider 花费是否可控？

字段建议：

```json
{
  "provider_call_count": 3,
  "total_tokens": 2450,
  "prompt_tokens": 1800,
  "completion_tokens": 650,
  "estimated_cost": null,
  "operations": {
    "review_sprint_action_provider_candidates": {
      "call_count": 2,
      "total_tokens": 1500
    }
  },
  "cost_per_applied_candidate": null,
  "tokens_per_ready_candidate": 245.0
}
```

如果没有价格表，`estimated_cost=null`。

不要臆造成本。

### 5.7 Quality Delta

用于回答：Sprint 是否让作品变好？

输入来源：

- Parent version SongPlan quality metadata。
- Applied child version SongPlan quality metadata。
- Project compare summary。
- Validator report。

字段建议：

```json
{
  "baseline_version_id": "v001",
  "latest_applied_version_id": "v003",
  "baseline_quality_overall": 87,
  "latest_quality_overall": 90,
  "overall_delta": 3,
  "dimension_deltas": {
    "structure": 0,
    "harmony": 2,
    "melody": 1,
    "arrangement": 4,
    "lyrics": 0
  },
  "validator_warning_delta": -2,
  "status": "improved"
}
```

如果没有 applied child version：

```json
{
  "status": "not_available",
  "reason": "No applied sprint candidate version found."
}
```

### 5.8 Manual Decision Metrics

用于回答：人的选择和系统建议的关系。

字段建议：

```json
{
  "manual_apply_count": 1,
  "applied_from_decision_recommendation_count": 1,
  "applied_from_top_ranked_candidate_count": 1,
  "applied_from_provider_count": 1,
  "applied_from_local_count": 0,
  "manual_override_count": 0
}
```

这里的“override”必须谨慎定义：

- 如果 applied candidate 不是 decision_report recommended_candidate_id，算 override。
- 如果没有 decision_report，不算 override，只算 unknown。

### 5.9 Risk / Readiness

用于回答：这轮是否能收尾？

字段建议：

```json
{
  "readiness": "needs_review",
  "ready_to_close": false,
  "blocking_conflict_count": 1,
  "open_high_priority_task_count": 2,
  "stale_task_count": 0,
  "failed_action_count": 0,
  "pending_provider_action_count": 1,
  "manual_required_apply_count": 1,
  "warnings": [
    "Two high-priority tasks are still open.",
    "One provider-safe action is pending."
  ]
}
```

readiness 枚举：

```text
ready_to_close
needs_review
needs_candidates
blocked
stale
no_data
```

## 8. 计算规则细化

### 8.1 Task status counts

读取 Sprint task_refs，只统计 included task。

缺失 task：

```json
{
  "missing_task_count": 1
}
```

不要因为一个 task 缺失导致整个 metrics 失败。

### 8.2 Candidate source detection

候选来源判断优先级：

```text
candidate.candidate_type == provider_review_patch
candidate.source.provider exists
  -> provider

candidate.candidate_type == local_review_intents
  -> local

else
  -> unknown
```

### 8.3 Applied candidate detection

应用状态来源：

- task.selected_candidate_id。
- candidate.status == applied。
- Project version edit metadata 中 review_task / review_candidate。

优先使用 task/candidate store。

Project version metadata 用于补充 provenance。

### 8.4 Recommendation adoption

从 action queues 统计：

- item.recommendation.report_hash 存在。
- item.status == completed。
- item.action 来自 recommendation map。

Context Pack save 也算 recommended context adoption。

manual apply 不算 automatic adoption，但可记录：

```json
{
  "manual_recommendation_followed": true
}
```

### 8.5 Provider usage 聚合

来源可能有：

- task `provider-usage.json`
- Project usage API 当前汇总
- provider snapshots in queue results

优先复用现有 provider usage report 逻辑，不要复制一套。

如果已有 `/api/projects/<project-id>/usage/provider`，metrics 构建可以调用同一底层 helper，而不是 HTTP 调自己。

### 8.6 Quality delta

寻找 baseline：

1. Sprint 中 task 的 parent_version_id。
2. 如果多个 parent_version_id，取出现最多的，另加 warning。
3. 如果没有 task parent，使用 Project selected/final version。

寻找 latest applied version：

1. Sprint task applied_version_id。
2. 按 Project version order 取最新。

如果两边都能读到 SongPlan：

- 读取 `quality.overall`。
- 读取 dimensions。
- 读取 validator warnings count。

如果缺 quality：

- 可以调用已有本地 quality 推断函数。
- 但不要写回 SongPlan，只用于 metrics report。

### 8.7 Readiness rules

建议规则：

```text
if no tasks:
  no_data
elif stale_task_count > 0:
  stale
elif blocking_conflict_count > 0 or failed_action_count > 0:
  blocked
elif open_high_priority_task_count > 0 or manual_required_apply_count > 0:
  needs_review
elif ready_candidate_task_count == 0 and open_task_count > 0:
  needs_candidates
elif open_task_count == 0 or completion_rate >= 0.8:
  ready_to_close
else:
  needs_review
```

这些规则必须写进代码附近的测试，避免后续改坏。

## 9. API 设计

### 9.1 Sprint metrics get

```text
GET /api/projects/<project-id>/review-sprints/<sprint-id>/metrics
```

行为：

- 如果 metrics-report.json 存在，返回当前 report。
- 如果不存在，生成一次并保存。
- 不改变业务状态。

返回：

```json
{
  "ok": true,
  "sprint": {},
  "metrics_report": {},
  "summary": {}
}
```

### 9.2 Sprint metrics refresh

```text
POST /api/projects/<project-id>/review-sprints/<sprint-id>/metrics/refresh
```

行为：

- 重新读取所有来源。
- 重建 metrics-report.json。
- append event：

```text
review_sprint_metrics_refreshed
```

返回同 get。

### 9.3 Project metrics get

```text
GET /api/projects/<project-id>/review-metrics
```

行为：

- 如果 review-metrics.json 存在，返回。
- 如果不存在，生成一次并保存。

### 9.4 Project metrics refresh

```text
POST /api/projects/<project-id>/review-metrics/refresh
```

行为：

- 刷新所有 Sprint metrics summary。
- 写 `review-metrics.json`。
- append project event：

```text
project_review_metrics_refreshed
```

### 9.5 Dashboard summary

可以不新增独立 API。Sprint detail 和 Project detail 返回中可以加入：

```json
{
  "metrics_summary": {}
}
```

但不要把完整 metrics report 塞进所有列表接口，避免响应过大。

## 10. WebUI 设计

### 10.1 Review Sprints Dashboard 面板

位置：

```text
Projects workspace
  -> Review Sprints
    -> Sprint detail
      -> Recommendations
      -> Action Queue
      -> Dashboard
```

Dashboard 面板应该包含：

- Refresh Metrics。
- Readiness badge。
- Task overview cards。
- Candidate funnel table。
- Action queue execution summary。
- Provider usage summary。
- Quality delta summary。
- Risks / Warnings。

### 10.2 页面布局

不要做花哨大屏。这个项目是本地创作工作台，布局应信息密集、可扫描。

建议布局：

```text
Readiness | Completion | Candidate Funnel | Provider Tokens

Task Status table
Candidate Source table
Action Queue table
Quality Delta table
Warnings list
Raw JSON details collapse/pre
```

### 10.3 指标卡

指标卡不要过大。每张卡显示：

- label
- value
- subtext

例如：

```text
Readiness
needs_review
2 open high-priority tasks
```

### 10.4 风险展示

warnings 应该非常显眼，但不要弹窗。

例如：

```text
Risks
- One provider-safe action is still pending.
- Two high-priority tasks are open.
- Quality delta is not available because no candidate has been applied.
```

### 10.5 Project Review Metrics

Project 页面可以显示一个简洁 summary：

- active sprint count
- latest readiness
- total provider tokens
- total applied candidates
- quality trend

不要把所有 Sprint 明细堆在 Project 列表里。

## 12. 安全与脱敏

### 12.1 不允许泄露

Metrics / Dashboard / Export 中不能出现：

- `sk-...`
- GitHub token。
- Bearer token。
- `api_key`
- provider raw response。
- 本机路径：
  - `C:\Users\...`
  - `D:\...`
  - `\\server\share\...`
  - `/Users/...`
  - `/home/...`
- SoundFont 本机路径。
- `.musicforge/provider.json` 内容。
- `.musicforge/renderer.json` 内容。

统一用：

```python
sanitize_metadata()
redact_sensitive_values()
sanitize_sensitive_text()
```

### 12.2 Metrics 只存 summary

不要把完整 candidate plan、provider prompt、provider response 写进 metrics。

只写：

- counts
- ids
- scores
- statuses
- summaries
- warning messages

### 12.3 Path policy

Metrics 不应新增任何下载接口。

如果要引用 artifact，用 logical id：

- project_id
- sprint_id
- task_id
- candidate_id
- queue_id
- version_id

不要写绝对路径。

```powershell
git push origin v3.3.0
```

如果 GitHub 443 连接失败，不要改 remote，不要把 token 写进 URL。可以用一次性 IP 覆盖：

```powershell
git -c http.curloptResolve=github.com:443:140.82.113.3 push origin master
git -c http.curloptResolve=github.com:443:140.82.113.3 push origin v3.3.0
```

这个参数只影响本次命令，不会写入配置。

- 优先用 GitHub 页面基于 `v3.3.0` 创建 Release。
- 如果本机有 `gh`：

```powershell
gh release create v3.3.0 --title "v3.3.0" --notes-file CHANGELOG.md
```

核验：

```powershell
git status --short --branch
git rev-parse HEAD

```

三者应一致。

## 17. 风险清单

### 风险 1：指标口径不清导致误导用户

应对：

- 每个指标有明确计算规则。
- 除数为 0 返回 null。
- 缺数据返回 not_available。
- README 简述核心口径。

### 风险 2：刷新 metrics 意外改变业务状态

应对：

- Metrics 模块只读业务对象。
- API 测试刷新前后 task/candidate/queue 状态不变。
- 不调用 provider。
- 不执行 action queue。

### 风险 3：导出过多细节导致泄密

应对：

- Export/Final Export 只写 summary。
- release-check 加 secret/path scan。
- 不复制 metrics-report 原文。

### 风险 4：历史项目兼容性

应对：

- 缺文件不报错。
- default empty report。
- tests 覆盖无 recommendation、无 queue、无 decision report。

### 风险 5：Dashboard 信息太多

应对：

- 顶部只放 4-6 个核心指标。
- 详细 JSON 放折叠或 pre。
- 风险列表优先级高于原始数据。

## 18. v3.3.0 完成定义

v3.3.0 完成后，用户应该能在 Studio 里完成以下判断：

```text
这个 Sprint 当前是否健康？
哪些 task 还没解决？
候选生成是否有效？
provider 是否值得继续用？
Action Queue 是否执行顺畅？
人工是否采纳了系统推荐？
作品质量是否提升？
当前是否接近可以收尾？
```

并且系统满足：

- 不自动 apply。
- 不调用 provider 生成新内容。
- 不改变业务状态。
- 指标可重建。
- 指标可解释。
- 指标脱敏。
- release-check 全绿。

做到这里，Review Sprint 就不只是“能组织反馈、能推荐动作、能执行安全动作”，而是能被复盘、被管理、被用于判断下一轮是否继续推进。

v3.4.0 才适合继续做 Provider Judge / 多模型评审，把候选质量评估进一步加强。但在那之前，必须先有 v3.3.0 这一层稳定的指标底座。

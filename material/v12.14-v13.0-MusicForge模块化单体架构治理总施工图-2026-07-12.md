# v12.14-v13.0 MusicForge 模块化单体架构治理总施工图

日期：2026-07-12

执行区间：v12.14.0 至 v13.0.0

当前稳定基线：v12.13.0

主题：停止功能堆叠，建立模块化单体、统一证据验证平台、统一生命周期与持久化、拆分接口层、收敛 Gate 和产品概念，并完成 v13.0 架构切换

## 1. 文档目的

这不是单个版本的功能施工图，而是从 v12.13.0 到 v13.0.0 的串行架构改造总计划。

开发必须严格按以下版本顺序推进：

1. v12.14：Architecture Baseline and Guardrails
2. v12.15：Verification Kernel
3. v12.16：Evidence and Lifecycle Kernel
4. v12.17：Persistence, Concurrency and Migration
5. v12.18：CLI, API and Web Interface Decomposition
6. v12.19：Evidence Graph, Policy Engine and Product Consolidation
7. v12.20：Release Check, CI, Documentation and Legacy Governance
8. v13.0：Modular Monolith Cutover and LTS

每一版必须完成：实现、定向测试、架构测试、release-check、自动 code review、修复 review 问题、提交、干净工作区复验、推送、annotated tag、GitHub Release。上一版没有完成远端发布闭环时，不得开始下一版。

## 3. 总体原则

### 3.1 采用模块化单体，不拆微服务

MusicForge 是 local-first Python 应用。v13.0 仍保持一个进程、一个安装包、一个本地工作区。禁止为了“解耦”引入网络微服务、消息队列或分布式事务。

### 3.2 先建立平台，再迁移业务

平台能力必须先有契约和测试，再迁移真实 v12 业务。禁止先批量移动文件，随后再补抽象。

### 3.3 使用组合，不建立万能基类

统一能力采用小型 service、protocol、dataclass 和纯函数组合。禁止创建包含几十个 hook 的 `BaseEverythingStore` 或 `BaseVerifier`。

### 3.4 兼容层只能单向转发

旧模块、旧 CLI、旧 API 可以保留兼容 facade，但 facade 只能转发到新实现，不得继续承载业务逻辑。任何新代码不得依赖旧 facade。

### 3.5 行为保持优先

v12.14-v12.20 原则上不新增产品功能。所有迁移必须通过旧实现与新实现的 differential tests，安全 blocker 不能降级成 warning。

### 3.6 不允许包内自证回退

现有外部 evidence、verification report、binding summary、history chain、runtime verification、current generation 和 immutable archive 边界必须保留。架构重构不能重新接受 package-internal self-attestation。

### 4.1 依赖方向

唯一允许的生产依赖方向：

```text
interfaces -> application -> domains -> platform
```

附加规则：

- `platform` 不能导入任何 domain 或 interface。
- domain 不能导入 `cli`、`server`、`webui` 或 `release_check`。
- domain 之间不得直接读取对方私有目录；跨域访问必须经过 application service 或公开 contract。
- `release_check` 可以调用公开 application/interface API 做集成测试，但生产模块不能依赖 `release_check`。
- compatibility facade 只能导入新模块，新模块不能反向导入 facade。
- 所有新循环依赖均为发布 blocker。

### 4.2 产品领域

固定为六个 bounded contexts：

| Context | 主要能力 |
|---|---|
| creation | SongRequest、composition、provider、renderer、MIDI/audio generation |
| studio | Project、editor、asset、reference、preview、version |
| quality | acceptance、review、Audio Lab、campaign、remediation |
| delivery | release、distribution、submission、rights、metadata |
| trust | release operations、portfolio governance、public trust、trust operations |
| program | unified command center、release train、unified release program、continuity |

以后禁止新增第七个“总控层”。需要跨域聚合时，使用 application service、Evidence Graph 和 Policy Engine。

## 5. 统一核心契约

### 5.1 EvidenceRef

所有外部证据统一使用版本化 `EvidenceRef`：

```json
{
  "schema_version": 1,
  "component_type": "...",
  "component_id": "...",
  "evidence_type": "...",
  "generation": 1,
  "package_type": "...",
  "zip_sha256": "...",
  "zip_size_bytes": 0,
  "manifest_hash": "...",
  "verification_report_hash": "...",
  "source_hash": "...",
  "signoff_hash": "...",
  "history_event_hash": "..."
}
```

匹配主键固定为：

```text
component_type + component_id + evidence_type + generation
```

禁止依赖 CLI 重复参数的顺序完成证据匹配。

### 5.2 PackageSpec

每类 ZIP package 必须通过 `PackageSpec` 声明：

- `package_type`
- 固定或规则化 allow-list
- required entries
- optional entries
- nested ZIP policy
- manifest schema
- external evidence requirements
- redaction policy
- trailing-data policy
- semantic verifier callback

### 5.3 VerificationReport

统一 report envelope 至少包含：

- `schema_version`
- `package_type`
- `status`
- `checks`
- `blockers`
- `warnings`
- `zip_sha256`
- `zip_size_bytes`
- `manifest_hash`
- `source_hash`
- `verified_at`
- `integrity_hash`

领域 verifier 只能增加 semantic checks，不能重新实现 ZIP envelope safety。

### 5.4 LifecycleSnapshot

签核、reset 和 generation 统一绑定：

- current source hash
- current report hash
- current package fingerprint
- policy hash
- signoff payload hash
- signoff hash
- history event hash
- generation
- previous generation root

### 5.5 DomainError

统一错误模型：

- `error_code`
- `message`
- `http_status`
- `retryable`
- `details`

CLI、API 和 Store 不得分别复制同一错误语义。

## 6. 强制串行开发与自动 Review 流程

每个版本都必须执行以下状态机：

```text
clean previous release
  -> implementation
  -> targeted tests
  -> architecture tests
  -> release-check profiles
  -> automated code review
  -> fix findings
  -> repeat tests and review
  -> commit
  -> clean-worktree GA verification
  -> push master
  -> annotated tag
  -> GitHub Release
  -> remote/tag/release consistency check
  -> next version
```

### 6.1 开工条件

- `HEAD == origin/master == previous_tag^{}`。
- GitHub Latest Release 等于上一版本。
- `git status --short --branch` 干净。
- 上一版本没有未关闭 P0/P1。
- 当前版本施工范围和非目标已写清楚。

### 6.2 开发态验证

每次重要修改后运行：

```powershell
python -m pytest <本版定向测试> -q
python -m pytest tests\test_architecture_boundaries.py tests\test_architecture_metrics.py -q
python -m song_agent.cli release-check --profile v12 --skip-tests --json
python -m song_agent.cli release-check --profile latest --skip-tests --json
python -m song_agent.cli doctor
git diff --check
git status --short --branch
```

从 v12.20 起，版本号对应 profile 改为 `v13-candidate`，并由 CI 执行分片测试。

### 6.3 自动 Review 要求

自动 reviewer 必须读取实际 diff 和相关调用链，不能只接受开发汇报。Review 至少检查：

- 是否突破依赖方向。
- 是否新增重复 ZIP/hash/history/redaction helper。
- 是否通过兼容 facade 反向依赖旧代码。
- 是否削弱 runtime verification 或 external binding。
- 是否存在包内自证、旧 report 放行、force 绕过。
- 是否存在签核后 mutation、删除文件绕过、reset proof 重签。
- 是否有跨进程 lost update、半提交和迁移失败风险。
- 是否引入新自由格式 `dict[str, Any]` 长期契约。
- CLI/API 返回码、`ok`、`status` 是否一致。
- 是否增加 mega-file 行数。
- 是否影响 release-check 性能预算。
- 是否包含迁移、回滚、兼容和弃用测试。

Review 判定：

- P0：立即停止，不得提交。
- P1：必须在当前版本修复并重新完整 review。
- P2：原则上当前版本修复；确实延期时必须写入 `docs/architecture/DEBT.md`，指定 owner、截止版本和阻断条件。
- P3：可以登记，但不得掩盖结构性问题。

### 6.4 提交和发布条件

- reviewer 明确给出 `no P0/P1`。
- 本版定向测试全绿。
- architecture tests 全绿。
- v12/latest/ga 功能项全绿；提交前只允许 `git.status` 因未提交失败。
- 不提交 `.musicforge/`、`runs/`、测试缓存和临时目录。
- 使用显式文件列表暂存，避免无检查的 `git add .`。
- commit 后工作区必须干净。
- 推送后重新执行 GA profile，不能继续容忍 `git.status` 失败。
- annotated tag 和 GitHub Release 必须解引用到同一 commit。

### 6.5 网络阻塞规则

如果 GitHub 网络阻塞：

- 可以保留本地 commit 和 annotated tag。
- 不得开始下一版本。
- 不修改 remote URL，不把 token 写入 URL、命令输出或仓库。
- 网络恢复后完成 master/tag/release 对齐，并重新跑干净工作区 GA。

### 6.6 Hotfix 规则

如果某版本发布后 reviewer 发现 P0/P1：

- 立即暂停后续版本。
- 发布 `vX.Y.1` hotfix。
- 必须加入 reviewer 复现的最强攻击/失败回归。
- hotfix 发布并复核通过后，才恢复总路线。

## 7. 版本依赖图

```text
v12.14 boundaries/cycles
   -> v12.15 verification kernel
      -> v12.16 lifecycle/evidence contracts
```

### 7.1 逐版本自动退出矩阵

每版必须在 `release_check_matrix` 注册一个新的架构 smoke。Smoke 不是重复跑整套业务，而是证明本版平台能力已迁移真实业务、旧边界没有被削弱、架构指标没有回退。

| Version | Required check id | Review 主焦点 | 建议 commit subject | Go 条件 |
|---|---|---|---|---|
| v12.14 | `v1214.architecture_guardrails_smoke` | import direction、cycles、mega-file ratchet | `refactor: establish architecture guardrails` | 边界测试全绿，接口循环消失 |
| v12.15 | `v1215.verification_kernel_smoke` | ZIP safety parity、external proof、full-resign | `refactor: centralize package verification` | active v12 verifier 使用统一 kernel |
| v12.16 | `v1216.lifecycle_kernel_smoke` | signoff/history/reset/generation parity | `refactor: centralize evidence lifecycle` | active v12 lifecycle 使用统一 primitives |
| v12.17 | `v1217.persistence_concurrency_smoke` | cross-process locking、transaction recovery、migration | `refactor: add transactional workspace persistence` | 并发和 crash tests 全绿 |
| v12.18 | `v1218.interface_registry_smoke` | CLI/API/UI compatibility、thin facades | `refactor: modularize application interfaces` | 三个 interface mega-file 达到上限 |
| v12.19 | `v1219.evidence_policy_smoke` | policy parity、identity matching、Gate hard blockers | `refactor: add evidence graph and policy engine` | GA/Release 由 policy 驱动 |
| v12.20 | `v1220.release_engineering_smoke` | check split、CI、budgets、deprecation catalog | `refactor: consolidate release engineering` | CI 全绿，hard budgets 生效 |
| v13.0 | `v130.modular_monolith_cutover_smoke` | legacy removal、migration、rollback、全架构指标 | `release: cut over modular monolith v13` | 最终 reviewer、full suite、migration 全绿 |

### 7.2 每版自动执行伪代码

```text
assert previous_release_is_remote_clean()
implement_current_version_only()

while True:
    run_targeted_tests()
    run_architecture_tests()
    run_version_smoke()
    run_v12_latest_ga_profiles()
    run_doctor_and_diff_check()
    findings = run_code_review_on_actual_diff()
    if findings.has_p0_or_p1:
        fix(findings)
        continue
    if findings.has_unresolved_p2_without_approved_debt:
        fix(findings)
        continue
    break

commit_explicit_files()
assert_worktree_clean()
push_master()
run_clean_worktree_ga()
create_and_push_annotated_tag()
create_github_release()
assert_remote_master_tag_release_match()
start_next_version()
```

任何自动化脚本如果不能确认某一步成功，必须停在当前版本并输出 blocker，不能把 unknown 当作 passed。

### 8.1 目标

建立真实架构基线、自动依赖门禁和代码规模 ratchet，并消除当前最明显的接口层循环依赖。此版本不迁移业务数据，不改产品行为。

### 8.2 新增内容

建议新增：

### 8.3 必做修改

1. 从 `server.py` 移出 `JobState`，让 `mix_render.py` 依赖 application model。
2. 从 `cli.py` 移出 `generate_request`，让 CLI 和 Server 都依赖 application service。

4. 禁止 `release_checks.py` 导入 Server 私有 helper；把 `_audio_campaign_release_track_coverage` 等移动到 application/domain service。

6. 建立 AST import boundary test。
7. 建立巨型文件 ratchet：现有行数作为上限，后续版本只能下降，不能增长。
8. 建立 duplicate security helper ratchet，禁止新增 `_raw_zip_entry_names`、`_is_safe_zip_entry`、`_zip_has_no_trailing_data` 等副本。
9. 更新 `docs/ARCHITECTURE.md` 和 README Project Layout，不再保留过时 MVP 图作为当前架构。

### 8.4 禁止项

- 不新增业务 Store、Board、Center、Gate 或 Archive。
- 不批量移动全部模块。
- 不修改现有 ZIP schema。
- 不修改外部 CLI/API 名称。
- 不引入微服务。

### 8.5 测试

- CLI generate/serve 回归。
- Server create/start/auth 回归。
- mix render 回归。
- release-check fixture 回归。
- import boundary test。
- source size ratchet test。
- 循环依赖检测，目标是生产层不再存在 CLI/Server/Domain 环路。

### 8.6 Review 阻断项

- domain 仍导入 `server.py` 或 `cli.py`。
- 新 application module 反向导入 interface。
- 为通过边界测试使用动态 import 掩盖真实依赖。
- 兼容 facade 内继续新增业务逻辑。
- mega-file 行数继续增长。

### 8.7 完成标准

- 当前架构文档和模块归属完整。
- `server -> cli`、`mix_render -> server`、`release_checks -> server private` 依赖消失。
- architecture tests 纳入 `v12`、`latest`、`ga`。
- 无产品行为变化。

## 9. v12.15.0 Verification Kernel

### 9.1 目标

统一 ZIP、manifest、hash、redaction、history envelope 和 verification report 生成，消除 verifier 安全基础设施分叉。

### 9.2 新增模块

- `song_agent/platform/verification/model.py`
- `song_agent/platform/verification/hashing.py`
- `song_agent/platform/verification/zip_security.py`
- `song_agent/platform/verification/manifest.py`
- `song_agent/platform/verification/redaction.py`
- `song_agent/platform/verification/history.py`
- `song_agent/platform/verification/external_bindings.py`
- `song_agent/platform/verification/engine.py`
- `song_agent/platform/contracts/evidence.py`
- `song_agent/platform/contracts/packages.py`

### 9.3 Verification Engine 固定能力

- raw central-directory entry 扫描。
- duplicate entry 检测。
- absolute path、drive path、`..`、raw backslash 检测。
- 大小写不敏感 `.musicforge/` 拒绝。
- nested ZIP allow/deny policy。
- trailing data 检测。
- fixed allow-list 与 manifest/files/index 三方一致。
- file hash、ZIP hash、ZIP size、manifest hash。
- package type。
- JSON/JSONL 读取错误分类。
- redaction scan。
- report integrity hash。
- external evidence identity 匹配。
- deterministic check id 和 blocker code。

### 9.4 首批迁移范围

必须迁移所有当前 v12 Program/Continuity active verifiers 的安全 envelope，至少包括：

- Unified Release Program
- Program Operations
- Program Handoff
- Program Vault
- Vault Operations
- Continuity
- Continuity Distribution
- Continuity Acceptance
- Continuity Acceptance Change
- Continuity Command Center
- Command Center Signoff
- Receiver Acceptance
- Receiver Acceptance Change Control

领域 semantic verifier 可以保留在原模块，但必须作为 `PackageSpec` callback 调用。旧公开函数名保留为 facade。

### 9.5 Differential tests

每个迁移 verifier 必须对以下输入比较旧/新结果：

- happy package。
- missing required entry。
- declared extra。
- undeclared extra。
- duplicate。
- dangerous path。
- raw backslash。
- `.MusicForge` 大小写变体。
- nested ZIP。
- trailing bytes。
- manifest spoof。
- redaction。
- wrong package type。
- stale external report。
- full-resign attack。

新 verifier 可以新增 blocker，但不能让旧 failed 场景变 passed。

### 9.6 删除要求

迁移模块中禁止继续定义：

- `_raw_zip_entry_names`
- `_is_safe_entry`
- `_is_safe_zip_entry`
- `_zip_has_no_trailing_data`
- 通用 `_sha256_file/_sha256_entry`
- 通用 `_verify_redaction`
- 通用 report `_counts`

领域专属 semantic helper 可以保留。

### 9.7 Review 阻断项

- Engine 为某个测试增加 bypass。
- PackageSpec 允许 package 自己扩展 allow-list。
- report 只信 ZIP 内 fingerprint。
- external proof 变成可选但 gate 仍显示 ready。
- 新旧 verifier blocker 差异没有说明。

### 9.8 完成标准

- active v12 verifier 共用一个 ZIP security implementation。
- active v12 verifier report 使用统一 envelope。
- 所有旧 CLI/API verifier 命令兼容。
- v12 security smoke 不丢任何信号。
- duplicate helper ratchet 明显下降。

## 10. v12.16.0 Evidence and Lifecycle Kernel

### 10.1 目标

统一 EvidenceRef、signoff、history chain、generation、Change Request、reset proof、immutable snapshot 和 archive 生命周期。

### 10.2 新增模块

- `song_agent/platform/lifecycle/signoff.py`
- `song_agent/platform/lifecycle/change_control.py`
- `song_agent/platform/lifecycle/generation.py`
- `song_agent/platform/lifecycle/archive.py`
- `song_agent/platform/lifecycle/event_ledger.py`
- `song_agent/platform/contracts/lifecycle.py`
- `song_agent/platform/contracts/evidence_manifest.py`

### 10.3 核心组件

- `SignoffService`
- `HistoryChain`
- `ChangeRequestService`
- `ResetService`
- `GenerationService`
- `ImmutableSnapshotGuard`
- `ArchiveBuilder`
- `ExternalEvidenceManifest`

这些组件必须是可组合对象，不得直接知道 Program、Audio、Trust 等领域名称。

### 10.4 强制语义

- 签核只能绑定当前 source/report/package/policy。
- signoff binding 在签核时独立落盘，archive 只能复制。
- history 缺失或损坏时，只要存在签核派生产物，就不能降级为 unsigned。
- reset 必须 approved、action-scoped、target/source 匹配、single-use。
- reset 后旧 generation 立即失效。
- successor signoff 必须使用新 generation 和新 evidence。
- 删除 signoff、archive、export 或 history 不能绕过 immutable state。
- `force=true` 不能绕过 integrity、runtime、stale、current-generation blocker。

### 10.5 迁移范围

先迁移 v12.9-v12.12 当前链路：

- Continuity Command Center
- Command Center Signoff
- Receiver Acceptance
- Receiver Acceptance Change Control

然后将 v12.3-v12.8 的生命周期操作接到同一 kernel，但外部文件布局保持兼容。

### 10.6 数据兼容

- 旧 history/binding/signoff 文件必须有 parser adapter。
- 首次读取旧格式时不能静默重写签核证据。
- 只有显式 migration 命令可以生成新格式副本。
- migration report 必须记录 source hash、target hash、schema version 和 rollback path。

### 10.7 测试

- 单 reset、双 reset、CR reuse。
- wrong action、wrong target、wrong source、resigned approval。
- history deletion、history reorder、history full-resign。
- signoff deletion、binding mutation、signed source mutation。
- generation mixing、old reviewer evidence reuse。
- differential tests 对比迁移前后 gate/verifier。

### 10.8 Review 阻断项

- 通用生命周期组件包含 domain-specific if/elif。
- Store 仍自行计算 history event hash。
- archive 时现算 signoff binding。
- reset 只改状态但不轮换 generation。
- migration 自动修改历史 signed evidence。

### 10.9 完成标准

- v12 active lifecycle 不再复制 hash-chain/reset/signoff 基础算法。
- EvidenceRef 主键不依赖参数顺序。
- 旧包和旧命令仍可验证。
- 所有签核不可变和 reset 回归全绿。

## 11. v12.17.0 Persistence, Concurrency and Migration

### 11.1 目标

解决 ThreadingHTTPServer、CLI/API 并发和多文件更新的 lost-update、半提交和迁移一致性问题。

### 11.2 权威数据边界

采用混合模型：

- SQLite 保存可变工作流状态、ID、current generation、lease、migration 和 transaction metadata。
- JSON/JSONL/ZIP 保存可移交、可审计、不可变 evidence snapshot。
- signed archive 文件一旦生成，不回写 SQLite 改变其内容。
- SQLite 不是公开 evidence package；离线 verifier 不依赖本机数据库。

### 11.3 新增模块

- `song_agent/platform/persistence/database.py`
- `song_agent/platform/persistence/repository.py`
- `song_agent/platform/persistence/unit_of_work.py`
- `song_agent/platform/persistence/locks.py`
- `song_agent/platform/persistence/migrations.py`
- `song_agent/platform/persistence/file_artifacts.py`
- `song_agent/platform/persistence/recovery.py`

数据库建议路径：

```text
.musicforge/state/musicforge.db
```

### 11.4 SQLite 要求

- 使用标准库 `sqlite3`。
- WAL mode。
- foreign keys enabled。
- busy timeout。
- 显式 transaction。
- migration table。
- schema version。
- 不把 token、本机绝对路径或私密 reviewer 文本写入索引。

### 11.5 File Unit of Work

多文件 evidence 更新必须：

1. 获取 workspace/process lock。
2. 在 staging directory 写全部候选文件。
3. 计算并验证所有 fingerprint。
4. 写 transaction intent。
5. 原子替换 current pointer 或 generation directory。
6. 提交数据库事务。
7. 写 commit marker。
8. 清理 staging。

启动时必须能识别并恢复未完成 transaction。

### 11.6 跨进程锁

- 同一 workspace 的 CLI 与 Server 必须共享锁语义。
- Windows 和 POSIX 都有实现。
- 锁包含 owner pid、operation、acquired_at、lease。
- stale lock 不能仅按时间自动删除，必须确认 owner 不存在或显式 recover。
- read-only verifier 不应长期占写锁。

### 11.7 迁移范围

优先迁移 v12.9-v12.12 mutable state。其他 129 Store 不在本版一次性迁移，但必须接入统一 lock facade，禁止继续新增独立进程内锁策略。

旧 JSON migration：

- 扫描现有 workspace。
- dry-run report。
- verified backup。
- import transaction。
- source file hash ledger。
- idempotent rerun。
- rollback plan。
- 旧文件保留为只读 legacy source，直到 v13.0 明确清理。

### 11.8 测试

- 两个 subprocess 同时修改同一对象，不能 lost update。
- CLI 与 HTTP 并发 reset/signoff，只有一个成功。
- write crash injection。
- database commit 前失败。
- file commit 后 database commit 前失败。
- restart recovery。
- migration rerun。
- migration rollback。
- backup verification failure 必须阻断。

### 11.9 Review 阻断项

- SQLite 和 JSON 同时被声明为同一可变字段的权威来源。
- 只用进程内 `RLock` 声称解决跨进程并发。
- 事务失败后留下可被 gate 读取的半成品。
- migration 自动删除旧文件。
- recovery 通过忽略 integrity failure 继续运行。

### 11.10 完成标准

- v12 active workflow 具备跨进程并发保护。
- 多文件更新有 transaction/recovery 测试。
- migration dry-run/backup/rollback 可用。
- 旧工作区无损兼容。

- v13.0 可以删除明确列入 catalog 的旧入口。
- archived evidence 的 read-only verification 支持不能因入口删除而消失。
- 任何 schema migration 都必须保留原始 hash 和 rollback evidence。

## 18. 失败与回退策略

### 18.1 行为不一致

如果新旧实现 differential test 不一致：

- 默认视为新实现缺陷。
- 不得用更新 golden snapshot 直接消除失败。
- 必须解释差异，若属于旧实现漏洞，先补 reviewer 复现和安全测试。

### 18.2 性能退化

- 超预算时输出 top slow checks。
- 不允许只调大 timeout。
- 优先拆 fixture、缓存 immutable source、减少重复 deep verify。
- 缓存 key 必须绑定所有可信输入 hash。

### 18.3 数据迁移失败

- 停止写入。
- 保留 transaction journal。
- 验证 pre-migration backup。
- 执行 rollback。
- 生成 failed migration report。
- 修复后从 clean backup 重试。

### 18.4 发布网络失败

- 保留本地 commit/tag。
- 不开始下一版。
- 网络恢复后对齐 remote/tag/release。
- 对齐后重新跑 GA。

## 19. 每版统一提交清单

开发在请求 reviewer 前必须提供：

- 本版目标与非目标。
- 修改文件清单。
- 新旧架构路径映射。
- 数据/CLI/API compatibility 说明。
- 安全边界说明。
- 定向测试命令和结果。
- architecture test 结果。
- release-check v12/latest/ga 结果。
- performance report。
- `git diff --check`。
- `git status --short --branch`。
- 未运行项目及原因。

reviewer 通过后，开发才可以提交。发布后必须再提供：

- commit SHA。
- origin/master SHA。
- annotated tag dereference SHA。
- GitHub Release URL 和 Latest 状态。
- clean-worktree GA 结果。
- clean git status。

## 20. 给开发的话

从 v12.14 开始，目标不再是继续发明新的 Board、Center、Archive 和 Gate。目标是把过去已经证明有效的安全语义沉淀成平台，让以后新增功能只需要声明 package、workflow、policy 和 interfaces，而不是复制一整套实现。

请严格串行执行本总图。每版都先完成真实迁移和回归，再做自动 review；review 没有明确通过前不要 commit，远端发布没有闭环前不要进入下一版。不要为了降低行数做纯机械拆分，不要为了兼容保留双写逻辑，不要为了测试速度跳过 runtime verifier，也不要把一个新的万能框架变成下一座巨型文件。

最终完成 v13.0 时，用户会安排一次新的全项目 review。届时判断标准不是“功能更多”，而是：边界清楚、证据安全规则只有一套、生命周期只有一套、并发写入可恢复、接口可注册、Gate 可声明、测试能在合理时间内给出可信结果，且旧 evidence 仍然可以离线验证。

# v12.2.0 Unified Release Program Final Handoff Board 项目级最终交接验收委员会与 Program 准出移交包施工图

> 建议下一版：v12.2.0  
> 当前稳定基线：v12.1.0  
> 核心目标：把 v12.0 的 Unified Release Program Board 和 v12.1 的 Program Operations Center 收敛成一个 Program 级最终交接层。v12.2 不再继续给 Program Operations 加零碎按钮，而是一次性补齐 Program Final Handoff、外部验收响应、Program Acceptance Evidence、Reviewer Decision Board、不可变交接 Archive、离线 verifier、Release/GA gate，使多个 Release Train 组成的 Program 可以真正交给业务、审查方或交付团队签收。

---

## 1. 背景

v12.0 已经把多个 Release Train Final Handoff 聚合成 Program：

- Program 有 train items、dependency graph、readiness matrix、risk register、exception register、gap plan。
- Program 可以签核并导出固定结构 ZIP。
- Program verifier 已经要求外部 Train Handoff evidence、signoff binding、current verification。
- v12 smoke 已覆盖 deferred-only、missing binding、declared extra、signoff full-resign 等核心风险。

v12.1 又在 Program 之上补了运营闭环：

- Program Change Request / approved single-use reset。
- Program Operations Runbook。
- Program Continuous Review。
- Program Lifecycle Audit。
- Program Operations Archive ZIP 和 offline verifier。
- Program reset 后不再被视为 current signed。
- Operations archive 构建期和离线 verifier 会校验 Program verification package_type。
- reset 后 archive export / ZIP 会 409，而不是生成一个必然离线失败的误导包。

这两版已经解决了“Program 能否签核”和“Program 签核后如何维护”的问题。

但真实交付还缺最后一层：

1. Program Board、Operations Archive、Lifecycle Audit、Change Control 仍然是内部治理视图。
2. 外部 reviewer / business owner / release owner 没有一个 Program 级响应包。
3. 多个接收方的 accepted / needs_changes / rejected 没有形成 Program 级 quorum 决策。
4. Program 最终交接包缺少 recipient guide、交付摘要、证据索引、风险说明、accepted evidence。
5. Release / GA gate 可以要求 Program clean，但不能证明“Program 已被外部接收方验收并最终交接”。

因此 v12.2 建议进入：

**Unified Release Program Final Handoff Board**

中文名：

**项目级最终交接验收委员会与 Program 准出移交包**

---

## 2. 版本定位

### 2.1 一句话

v12.2 是 Program 级最终交接层：把 signed Program、Program Operations、Lifecycle Audit 和外部验收响应收成一个可离线复验、可委员会签核、可交付接收的 Program Final Handoff。

### 2.2 和 v12.0 / v12.1 的关系

v12.0：

- 证明“这个 Program 当前可以签核”。

v12.1：

- 证明“这个 Program 签核后可维护、可复核、可安全重开、可审计”。

v12.2：

- 证明“这个 Program 已完成最终交接，外部接收方已经验收，交接包可以作为 Program 级准出证据”。

### 2.3 本版必须解决的问题

1. 生成 Program Final Handoff Report。
2. 生成 Program Evidence Inventory。
3. 生成 Program Recipient Guide。
4. 生成 Program External Review Pack。
5. 支持外部 reviewer response 导入。
6. accepted response 可生成 Program Acceptance Evidence。
7. needs_changes / rejected 只能生成 Change Request draft，不能自动 reset / approve / signoff。
8. Program Decision Board 支持 quorum、required roles、required organizations。
9. Program Final Handoff signoff 生成独立 binding sidecar 和 history hash chain。
10. Final Handoff Archive ZIP 固定结构、不可静默重建、可离线验证。
11. Release signoff / GA readiness 可以要求 Program final handoff accepted。
12. release-check 增加 v12.2 smoke。

### 2.4 本版不做什么

v12.2 不做以下内容：

- 不自动批准 Change Request。
- 不自动重开 Program signoff。
- 不自动替换 Train Handoff。
- 不自动修改 v12.0 Program Board 或 v12.1 Operations Archive。
- 不把底层 Program ZIP、Operations ZIP、Train ZIP 嵌入 Handoff ZIP。
- 不引入真实公钥基础设施或第三方 CA。
- 不做跨多个 Program 的 portfolio ranking。
- 不做公网发布、Portal、Transparency Feed。
- 不支持 Final Handoff signoff reset；如需 reset，后续 v12.3 单独设计 approved CR reset。

## 3. 核心设计原则

### 3.1 不信 Handoff ZIP 内部自证

Program Final Handoff verifier 不能只相信 ZIP 内的：

- `program-handoff-report.json`
- `evidence-inventory.json`
- `recipient-guide.md`
- `decision-board.json`
- `handoff-signoff.json`
- `handoff-history.jsonl`
- `manifest.json`

必须用外部证据反查：

- current Program ZIP
- current Program verification report
- external Program signoff binding
- Program Operations Archive ZIP
- Program Operations verification report
- Program Lifecycle / Operations summary
- External Review Pack verification report
- Accepted Evidence ZIP / verification report
- Response binding summary
- optional GA readiness report
- optional release-check report

如果启用 `require_current` / `require_accepted` / `require_signed`，缺少外部证据必须 failed。

### 3.2 外部 evidence manifest 是主入口

v12.2 不允许 verifier 靠 CLI repeat 参数顺序匹配证据。

主入口必须是 external evidence manifest：

```json
{
  "schema_version": 1,
  "program_id": "urp-...",
  "handoff_id": "uph-...",
  "items": [
    {
      "evidence_id": "program-current",
      "evidence_type": "unified_release_program",
      "component_id": "urp-...",
      "zip_path": "...",
      "verification_report_path": "...",
      "binding_path": "program-signoff-binding-summary.json"
    },
    {
      "evidence_id": "program-operations",
      "evidence_type": "unified_release_program_operations",
      "component_id": "urp-...",
      "zip_path": "...",
      "verification_report_path": "..."
    },
    {
      "evidence_id": "accepted-review-owner",
      "evidence_type": "program_accepted_evidence",
      "component_id": "uph-...",
      "zip_path": "...",
      "verification_report_path": "..."
    }
  ]
}
```

CLI 可以提供便捷 repeat 参数，但 Store / verifier 内部必须先归一化成 manifest，然后按：

- `evidence_type`
- `component_id`
- `handoff_id`
- `response_id`
- `reviewer_id`

匹配，不能按数组顺序。

### 3.3 Review response 不能由导入端补绑定

外部 reviewer response 必须显式携带：

- `review_pack_id`
- `review_pack_source_hash`
- `review_pack_zip_sha256`
- `review_pack_manifest_hash`
- `program_id`
- `handoff_id`
- `reviewer_id`
- `reviewer_role`
- `organization`
- `decision`
- `payload_hash`

导入端不能自动补这些字段。

缺少绑定字段：

- API 返回 400。
- CLI 返回 failed。
- 不创建 accepted evidence。

绑定错误：

- response 可落盘为 rejected import attempt，也可以直接拒绝。
- 但不能进入 quorum。
- 不能生成 accepted evidence。

### 3.4 Accepted Evidence 必须绑定原始 response

Accepted Evidence ZIP 不能只靠自己内部 summary 自证。

必须包含并验证：

- `response.json`
- `response-verification-report.json`
- `response-binding-summary.json`
- `original-response-public.json`
- `accepted-evidence-report.json`
- `accepted-evidence-binding-summary.json`

Verifier 必须从原始 response 和 binding summary 反推：

- reviewer role
- organization
- decision
- review pack source hash
- payload hash
- public projection hash

防止把 `technical_reviewer` 全量重签伪造成 `release_owner`。

### 3.5 签核 binding 必须在 signoff 时独立落盘

`program-handoff-signoff-binding-summary.json` 必须由 `signoff_handoff()` 创建时落盘。

不能在 export / zip / verifier 时从 `program-handoff-signoff.json` 现读现算。

必须绑定：

- `handoff_id`
- `program_id`
- `signoff_hash`
- `signoff_payload_hash`
- `history_event_hash`
- `decision_board_hash`
- `accepted_evidence_index_hash`
- `program_zip_sha256`
- `program_verification_hash`
- `operations_zip_sha256`
- `operations_verification_hash`
- `external_evidence_manifest_hash`
- `source_hash`

Archive verifier 在 `require_signed=true` 时必须要求外部 `program-handoff-signoff-binding-summary.json` proof。

### 3.6 签核 / export / ZIP 时序写死

v12.2 采用如下时序，避免实现歧义：

1. `refresh_handoff()` 在未签核状态下生成当前 handoff docs。
2. `export_review_pack()` 在未签核状态下生成给外部 reviewer 的 review pack。
3. `import_response()` 导入外部 response。
4. `create_accepted_evidence()` 只接受 accepted response。
5. `refresh_decision_board()` 基于 accepted evidence 计算 quorum。
6. `signoff_handoff()` 在 quorum passed 时生成：
   - `program-handoff-signoff.json`
   - `program-handoff-signoff-binding-summary.json`
   - `program-handoff-history.jsonl`
   - frozen handoff docs snapshot
7. 签核后允许一次 archive export / ZIP，但只能复制 frozen snapshot，不能重算 source docs。
8. 签核后 `refresh_handoff()`、`import_response()`、`refresh_decision_board()`、`signoff_handoff()` 均返回 409。
9. 删除 archive 目录或 ZIP 后，不能绕过签核状态重建不同内容；若允许重建，也必须逐字节等价于 frozen snapshot，否则 409。

推荐实现：

- signoff 后 `export_archive()` 允许运行，但先校验 frozen docs binding。
- `build_archive_zip()` 允许运行，但只能从 frozen archive manifest 构建。
- 如果 archive 已存在且 hash 不一致，409。

## 7. API 设计

新增路由：

```text
POST /api/unified-release-programs/<program_id>/handoff/refresh
GET  /api/unified-release-programs/<program_id>/handoff

POST /api/unified-release-programs/<program_id>/handoff/review-pack
POST /api/unified-release-programs/<program_id>/handoff/review-pack/zip
POST /api/unified-release-programs/<program_id>/handoff/review-pack/verify
GET  /api/unified-release-programs/<program_id>/handoff/review-pack/download

POST /api/unified-release-programs/<program_id>/handoff/responses/import
GET  /api/unified-release-programs/<program_id>/handoff/responses
GET  /api/unified-release-programs/<program_id>/handoff/responses/<response_id>

POST /api/unified-release-programs/<program_id>/handoff/accepted-evidence/<response_id>
POST /api/unified-release-programs/<program_id>/handoff/accepted-evidence/<evidence_id>/zip
POST /api/unified-release-programs/<program_id>/handoff/accepted-evidence/<evidence_id>/verify

POST /api/unified-release-programs/<program_id>/handoff/decision-board/refresh
GET  /api/unified-release-programs/<program_id>/handoff/decision-board

POST /api/unified-release-programs/<program_id>/handoff/signoff
POST /api/unified-release-programs/<program_id>/handoff/archive/export
POST /api/unified-release-programs/<program_id>/handoff/archive/zip
POST /api/unified-release-programs/<program_id>/handoff/archive/verify
GET  /api/unified-release-programs/<program_id>/handoff/archive/download
```

HTTP 语义：

- `400`：payload 缺字段、非法枚举、source_path 输入、response binding 缺失。
- `404`：Program / pack / response / evidence 不存在。
- `409`：stale、signed mutation、quorum failed、external evidence failed、archive mismatch。
- `200`：成功。

签核后：

- `refresh` -> 409
- `review-pack` -> 409

## 9. Verifier 规则

### 9.1 通用 ZIP 安全

- ZIP 存在。
- ZIP size 上限。
- entry count 上限。
- total uncompressed size 上限。
- duplicate entry failed。
- raw central directory entry name 检查。
- backslash path failed。
- absolute path failed。
- `..` path failed。
- `.musicforge/`、`.MusicForge/`、大小写变体 failed。
- nested `.zip` failed。
- manifest spoof failed。
- manifest.files[] 必须匹配固定 allow-list。
- file-index files[] 必须匹配固定 allow-list。
- redaction scan。
- JSON parse failure -> failed report，不抛 CLI 异常。

- `package_type == musicforge_unified_release_program_review_pack`

- review-pack-report hash
- review-pack-binding-summary hash

- reviewer role / organization / decision 从原始 response 反推
- response payload hash 匹配
- review pack source hash 匹配

必须校验：

- `package_type == musicforge_unified_release_program_handoff_archive`

## 20. 给开发的话

v12.2 不要做成“再多一个导出包”。它是 Program 级最终交接层，必须把 v12.0 的 Program Board 和 v12.1 的 Operations Archive 变成外部接收方能审、能签、能离线复验的最终证据。

实现时守住四条：

1. **外部 response 必须自带绑定，导入端不能补。** 缺字段就拒绝，source hash 不匹配就失败。
2. **Decision Board 只能信 accepted evidence 的外部 proof。** payload 里的 reviewer role / organization 只是 hint，不能作为 quorum 依据。
3. **签核 binding 必须 signoff 时独立落盘。** Archive / verifier 只能复制和校验，不能现算。
4. **Handoff verifier 不能信 ZIP 内部自洽。** 必须用 external evidence manifest、Program verification、Operations verification、accepted evidence verification 重新反推。

如果这四条守住，v12.2 就能把 v12 从“Program 运营系统”推进到“Program 级最终交付系统”。下一步再做 v12.3 时，才有资格考虑 Program Handoff 的 approved CR reset、Program portfolio 或公共发布视图。

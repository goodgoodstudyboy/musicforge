# v4.9.0 Acceptance Knowledge Base 验收修复知识库施工图

日期：2026-05-20

当前稳定基线：v4.8.1

目标版本：v4.9.0

建议版本主题：Acceptance Knowledge Base / 验收修复知识库

---

## 1. 背景

MusicForge 在 v4.7 和 v4.8 已经形成了完整的验收闭环：

```text
Acceptance Suite
  -> Human Review Pack
  -> Acceptance Analytics
  -> Acceptance Fix Sprint
  -> ReviewTask
  -> Recheck Suite
  -> Delta Report
  -> Closeout
  -> Release / Project / Final Export evidence
```

v4.8.1 修复了一个关键安全口径：stale Fix Sprint 不能被 force close，Release Signoff 也会二次检查 stale evidence。

现在系统已经能做到：

- 找出验收问题。
- 把问题组织成 Fix Sprint。
- 创建修复任务。
- 复验。
- 计算 delta。
- closeout。
- 把证据写进交付链路。

但还有一个明显缺口：

每一次 Fix Sprint 的经验没有沉淀。

也就是说，系统目前只知道“这次修完了”，但不知道：

- 哪类问题过去常见。
- 哪些修法对 hook 问题有效。
- 哪些 style 经常需要二次修复。
- 哪些 song_id 长期不稳定。
- 哪些 ReviewTask / edit / candidate 类型更容易带来 positive delta。
- 哪些 reviewer feedback 经常变成真实修复。
- 哪些问题被 waiver 过多，可能只是被绕过而不是被解决。

v4.9.0 要补的就是这个层：把验收和修复历史沉淀成一个本地、离线、可解释、可导出、可用于下一次修复建议的 Knowledge Base。

---

## 2. 版本定位

一句话定位：

> v4.9.0 把历史 Acceptance Analytics、Fix Sprint、ReviewTask、Recheck Delta 和 Human Review 结果沉淀成“问题-修法-效果”的本地知识库。

它不是新的生成器，也不是新的自动评审模型。

它是一个可追溯的经验层：

```text
issue_type + style + song_id + evidence
  -> past fix attempts
  -> observed delta
  -> effectiveness score
  -> next-time recommendation
```

---

## 3. v4.9 明确不做什么

本版不做：

- 不引入向量数据库。
- 不调用外部 LLM 生成知识。
- 不自动 apply fix。
- 不自动创建 Fix Sprint。
- 不自动关闭 Release。
- 不把 knowledge recommendation 作为强制 signoff gate。
- 不复制完整人工听审原文。
- 不导出原始 provider response。
- 不上传数据到云端。
- 不做真实音频生成、vocal、mixing、mastering。

本版允许：

- 本地扫描历史验收和修复产物。
- 生成 deterministic knowledge entries。
- 按 issue/style/song/project/release 查询知识。
- 生成 explainable recommendation。
- 将 KB summary 写入 Project Export / Release Export / Final Export。
- 在 Studio 中展示知识库、弱项画像、有效修法。
- 在创建 Fix Sprint 时显示相关历史经验。

---

## 4. 为什么 v4.9 应该做 Knowledge Base

如果 v4.8 是“修这一次”，v4.9 就是“让下一次修得更聪明”。

原因：

1. Fix Sprint 已经有 delta。
   delta 是最有价值的数据，因为它能说明某次修复到底有没有变好。

2. Human Review 已经进入系统。
   人工意见不能只停留在单次 suite 里，应该沉淀成问题类别和风格弱项。

3. Release Signoff 已经有 evidence。
   Knowledge Base 能告诉业务哪些风险是历史反复出现的。

4. v5 做真实音频前，需要一套质量记忆。
   否则接入更强生成能力后，问题定位会更困难。

推荐路线：

```text
v4.9.0  Acceptance Knowledge Base
v4.10.0 Knowledge-assisted Fix Planning / 知识辅助修复计划
v5.0.0  Real Audio / Vocal / Mixing Path
```

## 5. 核心用户故事

### 5.1 开发人员

开发人员希望：

- 看到某个 issue_type 过去怎么修。
- 知道哪些修复真的改善了 rating / readiness / issue count。
- 创建 Fix Sprint 时看到历史相似问题。
- 避免重复走无效修复路径。

### 5.2 Reviewer

Reviewer 希望：

- 看到某个风格是否长期不稳定。
- 看到 waiver 是否过多。
- 看到某个 Release 的问题是否是老问题。
- 看到修复闭环是否真正改善，而不是只关任务。

### 5.3 业务方

业务方希望：

- 知道系统质量是否有长期改善。
- 知道哪些风格已经稳定。
- 知道哪些风格还需要专项修复。

## 6. 新增概念

### 6.1 Knowledge Entry

知识库条目。

一条 entry 表示一个可追溯的经验：

```text
某类问题 + 某个目标范围 + 某次修复动作 + 修复前后效果
```

来源可以是：

- closed Acceptance Fix Sprint
- delta report
- ReviewTask resolution
- Human Review Pack import
- Acceptance Analytics issue taxonomy

### 6.2 Pattern

模式。

把多条 Knowledge Entry 聚合成更高层的规律：

- `hook` 问题在 `cn_pop` 中反复出现。
- `rap` 风格中 rhythm issue 常见。
- `generated_request` recheck 的改善可信度低于 project_version recheck。
- waiver 高的 issue_type 需要人工复听。

### 6.3 Effectiveness

修复有效性。

不是主观评分，而是基于 delta：

- readiness 是否改善。
- average rating 是否提升。
- issue count 是否下降。
- rejected / needs_fix 是否减少。
- ReviewTask 是否 resolved。
- recheck 是否 manual accepted。

### 6.4 Knowledge Recommendation

基于历史知识给下一次修复的建议。

它仍然只是 advisory：

- 不自动创建任务。
- 不自动修改歌。
- 不自动 signoff。

## 10. Effectiveness Score 设计

必须 deterministic。

建议分数：

```text
score = 0
+ 25 if readiness improved
+ 25 if latest status moved to accepted
+ 20 if rating_delta >= 2
+ 10 if rating_delta == 1
+ 15 if issue_count_delta <= -2
+ 8  if issue_count_delta == -1
+ 10 if all linked ReviewTasks resolved
- 20 if any non-waived item remains open
- 15 if recheck review is synthetic only
- 10 if waived_count > 0

clamp 0..100
```

Outcome status：

```text
effective: score >= 70
mixed:     score >= 40 and score < 70
ineffective: score < 40
unknown:  missing delta or missing recheck
```

## 12. API 设计

### 12.1 KB Refresh / Report

```text
GET  /api/acceptance/kb
POST /api/acceptance/kb/refresh
GET  /api/acceptance/kb/reports/<report-id>
```

POST refresh 行为：

- 扫描 closed Acceptance Fix Sprint。
- 读取 delta-report.json。
- 读取 closeout-report.json。
- 生成或更新 Knowledge Entries。
- 生成最新 Knowledge Report。

### 12.2 Entries

```text
GET /api/acceptance/kb/entries
GET /api/acceptance/kb/entries/<entry-id>
POST /api/acceptance/kb/entries/<entry-id>/hide
POST /api/acceptance/kb/entries/<entry-id>/unhide
```

hide 只影响默认列表，不删除文件。

### 12.3 Search

```text
GET /api/acceptance/kb/search?issue_type=hook&style=rap&song_id=rap_beat_001
```

搜索必须本地 deterministic：

- issue_type exact match
- style contains / normalized match
- song_id exact match
- outcome_status filter
- effectiveness score sort

### 12.4 Recommendation

```text
POST /api/acceptance/kb/recommend
```

payload：

```json
{
  "issue_types": ["hook", "rhythm"],
  "style": "rap",
  "song_id": "rap_beat_001",
  "project_id": "project-000001"
}
```

返回：

```json
{
  "recommendation": {
    "status": "available",
    "summary": "Past rap rhythm fixes improved after manual ReviewTask resolution and project_version recheck.",
    "matching_entry_count": 3,
    "top_entries": [],
    "suggested_next_actions": [
      "Create Acceptance Fix Sprint from fresh analytics.",
      "Prefer project_version recheck over generated_request recheck.",
      "Require manual review after fix."
    ],
    "manual_required": true
  }
}
```

## 16. 安全与脱敏

必须复用 `song_agent/redaction.py`。

KB 不能导出：

- 本机路径
- source_path
- provider raw response
- API key / token
- 完整人工 notes 原文
- 完整 Human Review Pack response

Entry 中只能保留：

- 短摘要
- ID
- hash
- issue_type
- style
- status
- score

任何 free text 字段：

- 先 sanitize。
- 最长 300 字符。

---

## 17. Source Hash / Stale

KB report source_hash 应基于：

- closed Fix Sprint summary
- fix-items summary
- delta report summary
- closeout report summary
- linked ReviewTask status summary

不基于：

- generated_at
- KB report 自己
- UI state
- event log timestamps

Entry source_hash 应基于对应 source artifacts。

如果 Fix Sprint delta 或 closeout 改变：

- old entry 标 stale。
- refresh 生成新 entry 或更新 entry。

建议 v4.9 先采用“更新同 entry_id”的策略，避免 entry 爆炸。

## 20. P1 风险清单

必须防：

- KB 把 stale Fix Sprint 当成有效经验。
- KB 把 force_closed 当成完全有效。
- KB 把 waiver 当成 fixed。
- KB 导出完整人工 notes。
- KB 泄露本机路径或 token。
- KB recommendation 自动创建任务。
- KB source_hash 因 generated_at 改变而抖动。
- KB 重复 refresh 生成大量重复 entry。
- KB search 返回 hidden entry。
- Release Export 带完整 entry payload。

---

## 21. Reviewer 检查重点

Reviewer 至少检查：

1. 只有 closed 且非 stale 的 Fix Sprint 才能成为 effective entry。
2. force_closed entry 有 penalty 或 warning。
3. waived item 不算 fixed。
4. effectiveness score deterministic。
5. refresh 两次不重复造 entry。
6. search / recommend 不自动创建任何任务。
7. Project / Release / Final Export 只带 summary。
8. redaction 覆盖 notes/path/token。
9. release-check v4.9 smoke 覆盖主链路。

```text
v4.10.0 Knowledge-assisted Fix Planning
```

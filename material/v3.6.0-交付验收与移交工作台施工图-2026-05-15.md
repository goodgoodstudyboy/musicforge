# v3.6.0 交付验收与移交工作台施工图

日期：2026-05-15

当前稳定基线：v3.5.1

目标版本：v3.6.0

定位：在 v3.5.1 已经完成 Review Sprint Closeout / Signoff / Delivery Readiness 的基础上，新增 Final Delivery QA / Handoff 层。v3.6.0 不再继续扩展候选生成、Provider Judge 或 Review Sprint 编排，而是把“最终交付包是否真的可交付”变成一套可本地验证、可复核、可审计、可导出的验收流程。

---

## 1. 背景

MusicForge 到 v3.5.1 已经具备了完整的本地音乐创作闭环：

- 能生成 SongPlan / MIDI / WAV / stems。
- 能维护 Project、Version、Final Export。
- 能创建 ReviewTask、ReviewCandidate、ReviewSprint。
- 能通过 Action Queue 推进安全动作。
- 能通过 Metrics、Recommendations、Provider Judge 辅助决策。
- 能通过 Closeout Gate 阻止未收口的 Sprint 被关闭。
- 能通过 Signoff 记录人工关闭与强制关闭原因。
- 能将 Review Sprint closeout/signoff 信息写入 Project Export 和 Final Export。

但现在仍缺最后一层：交付验收。

Final Export 已经会生成目录和 ZIP，但它本质上还是“打包动作”。它没有独立回答这些问题：

- Final Export 里的 `version_id` 是否就是 Project 当前 final version？
- Final Export 使用的版本是否和最新 Signoff 选择的版本一致？
- Final Export 中的 SongPlan、MIDI、WAV、stems 是否都存在且 hash 可复核？
- ZIP 是否真的对应当前 `final-export/manifest.json`？
- ZIP 是否包含所有应该包含的文件，且没有多余或危险路径？
- Closeout / Signoff / Quality Gate / Review Metrics 是否互相一致？
- Bundle 里是否仍有本机绝对路径、token、provider key、raw prompt 或 raw provider response？
- 交付前是否有人确认过最终包？
- 交付包是否可以给另一个人拿去验收，而不依赖当前机器状态？

v3.6.0 要补的是“交付验收和移交层”。

---

## 2. 一句话目标

v3.6.0 要让 Final Export 从“能打包”升级为“能被正式验收和移交”：

```text
Final Export Bundle
  -> Delivery QA Report
  -> Artifact Integrity Manifest
  -> Handoff Checklist
  -> Delivery Signoff Record
  -> Studio Delivery Workspace
  -> release-check smoke
```

核心不是生成更多音乐，而是让最终交付包具备可证明的完整性、一致性和可移交性。

---

## 3. 版本边界

### 3.1 v3.6.0 必须做

- 新增 Delivery QA Report。
- 新增 Final Export artifact integrity 检查。
- 新增 ZIP 与 manifest 一致性检查。
- 新增 Delivery Handoff Checklist。
- 新增 Delivery Signoff Record。
- 新增 API：
  - `GET /api/projects/<project-id>/delivery-qa`
  - `POST /api/projects/<project-id>/delivery-qa/refresh`
  - `GET /api/projects/<project-id>/delivery-signoff`
  - `POST /api/projects/<project-id>/delivery-signoff`
  - `POST /api/projects/<project-id>/delivery-signoff/reset`
- Studio Final Export tab 增加 Delivery QA / Handoff 面板。
- Project Export 接入 delivery QA/signoff summary。
- Final Export manifest 接入 delivery QA summary。
- Final Export ZIP 生成后能刷新 ZIP QA 状态。
- `release-check` 增加 v3.6 smoke。
- README / CHANGELOG / version bump。
- 提交、推送、tag、GitHub Release。

### 3.2 v3.6.0 可以做，但不强制

- standalone `delivery-qa.json` 下载。
- checklist template 配置。
- PDF/HTML 交付单。
- Delivery package name 自定义。
- Provider 生成面向客户的交付摘要。

这些可以放到 v3.6.1 或 v3.7.0。

### 3.3 v3.6.0 明确不做

- 不上传云端。
- 不发邮件。
- 不做团队账号和多人签核。
- 不做在线支付/订单/客户管理。
- 不做音频内容 AI 听感评价。
- 不自动把 Project 标记为商业发布。
- 不自动修复交付包，只报告问题。

## 4. 核心原则

### 4.1 Delivery QA 是验收器，不是生成器

Delivery QA 可以读取和检查：

- Project state。
- Project versions。
- Project Export。
- Final Export manifest。
- Final Export ZIP。
- Quality Gate result。
- Review Sprint Closeout / Signoff。
- artifact 文件 hash。

Delivery QA 不允许：

- apply candidate。
- 修改 SongPlan。
- 修改 Project final version。
- 修改 Review Sprint。
- 生成 Provider 请求。
- 修改原始 reference / asset。

### 4.2 Signoff 是审计事实

Delivery Signoff 和 Sprint Signoff 一样，是审计记录。

它可以被 reset，但 reset 必须：

- 写 event。
- 保留旧 signoff 到 history。
- 不静默覆盖。

### 4.3 QA 报告必须可重复生成

`delivery-qa.json` 是派生报告，可以 refresh。

但 Delivery Signoff 不随 refresh 自动覆盖。

### 4.4 交付验收必须离线可运行

v3.6.0 的所有 QA 检查必须本地完成。

不允许：

- 调 provider。
- 查 GitHub。
- 依赖网络。

### 4.5 导出必须脱敏

Delivery QA / Signoff / Final Export 都必须继续复用 `sanitize_metadata()` 和 `sanitize_sensitive_text()`。

不允许写入：

- provider key。
- access token。
- GitHub token。
- 本机绝对路径。
- UNC 网络路径。
- raw prompt。
- raw provider response。
- `.musicforge/provider.json` 内容。
- `.musicforge/renderer.json` 内容。

## 5. 数据结构

### 5.1 存储位置

建议放在 Project 级目录：

```text
.musicforge/projects/<project-id>/
  delivery-qa.json
  delivery-signoff.json
  delivery-signoff-history.jsonl
```

原因：

- Delivery QA 是 Project 交付层，不属于某个 Sprint。
- Final Export 目录可以重建，QA/signoff 不应该被删除。
- Signoff history 需要保留多次验收轨迹。

### 5.3 DeliverySignoffRecord

建议结构：

```json
{
  "schema_version": 1,
  "project_id": "project-001",
  "signed_at": "2026-05-15T00:00:00+00:00",
  "signed_by": "local-user",
  "decision": "approved_for_handoff",
  "delivery_qa_hash": "sha256...",
  "delivery_qa_status": "passed",
  "final_version_id": "v004",
  "final_export_sha256": "sha256...",
  "zip_sha256": "sha256...",
  "force": false,
  "override_reason": "",
  "notes": "Accepted after local playback and export QA.",
  "acknowledged_blockers": [],
  "acknowledged_warnings": []
}
```

字段说明：

- `decision` 初期只支持 `approved_for_handoff`。
- `force=true` 时 `override_reason` 必填。
- `delivery_qa_hash` 是 QA report 的 stable hash。
- `zip_sha256` 必须来自当前 QA report，不允许客户端传入。
- `final_version_id` 必须来自 Project final version 或 Final Export manifest。

### 5.4 DeliverySignoffHistory

每次 reset 或重签都写一行 JSONL：

```json
{
  "event": "delivery_signoff_reset",
  "created_at": "...",
  "previous_signoff": {},
  "reason": "Final export rebuilt after stem render."
}
```

## 6. Delivery QA Gate 规则

### 6.1 状态枚举

`DeliveryQAReport.status`：

```text
passed
warning
failed
stale
not_ready
```

`DeliveryQAReport.readiness`：

```text
ready_to_handoff
needs_export
needs_zip
needs_review
blocked
stale
no_data
```

### 6.2 Blocking checks

以下必须阻止普通 Delivery Signoff：

| check_id | 条件 |
|---|---|
| project_final_version | Project 没有 `final_version_id` |
| final_export_exists | `final-export/manifest.json` 不存在 |
| final_export_version_match | manifest.version_id 不等于 Project final_version_id |
| quality_gate_passed | manifest.quality_gate.status 不是 passed，除非已有 force final |
| closeout_signed | latest Review Sprint closeout 未 signed，且存在 Review Sprint |
| closeout_version_match | closeout/signoff selected_version_id 与 final_version_id 不一致 |
| required_artifacts_exist | required 文件缺失 |
| artifact_path_safe | manifest 文件路径不安全 |
| artifact_hash_valid | 已记录文件 hash 与实际文件不一致 |
| zip_exists | ZIP 不存在 |
| zip_manifest_match | ZIP entries 与 final-export manifest 不一致 |
| zip_hash_valid | manifest.zip.sha256 与当前 ZIP 不一致 |
| redaction_scan | QA 可见 JSON 中发现 token/path/raw provider 字段 |

### 6.3 Warning checks

以下只产生 warning，不阻止普通 Signoff：

| check_id | 条件 |
|---|---|
| audio_missing | WAV 未包含，但 MIDI 存在 |
| stems_missing | stems 未包含，但 Quality Gate 不要求 |
| stem_audio_partial | stem WAV 部分缺失 |
| forced_sprint_close | 存在 forced sprint close |
| high_warning_count | closeout warning_count > 0 |
| final_export_old | Final Export 生成时间早于最新 Project version updated_at |
| zip_large | ZIP 超过建议大小 |
| no_reference_summary | Project 有 references 但 Final Export 未包含 reference summary |

### 6.4 handoff_allowed

```text
handoff_allowed = status in {"passed", "warning"} and stale == false
```

普通 Delivery Signoff 必须 `handoff_allowed=true`。

Force Delivery Signoff 允许 gate failed，但必须：

- `force=true`
- `override_reason` 非空
- 记录 blockers/warnings。
- signoff.force=true。
- Project event 写 `delivery_force_signed`。

## 7. 新增模块建议

### 7.1 `song_agent/delivery_qa.py`

职责：

- 构建 Delivery QA Report。
- 计算 source hash。
- 检查 Final Export manifest。
- 检查 ZIP。
- 检查 artifact hash。
- 构建 Delivery Signoff。
- 提供 summary。

建议函数：

```python
def build_delivery_qa_report(
    *,
    project_id: str,
    project_document: ProjectDocument,
    project_dir: Path,
    project_export: dict | None = None,
    final_export_manifest: dict | None = None,
    now: str | None = None,
) -> dict: ...

def delivery_qa_source_hash(...) -> str: ...

def mark_delivery_qa_stale(report: dict, *, current_source_hash: str) -> dict: ...

def delivery_qa_summary(report: dict | None) -> dict: ...

def delivery_qa_allows_signoff(report: dict | None) -> bool: ...

def build_delivery_signoff_record(
    *,
    project_id: str,
    report: dict,
    payload: dict,
    now: str | None = None,
) -> dict: ...

def delivery_signoff_summary(record: dict | None) -> dict: ...
```

### 7.2 `ProjectStore` 增强

建议新增方法：

```python
def delivery_qa_path(self, project_id: str) -> Path: ...
def read_delivery_qa(self, project_id: str, default: dict | None = None) -> dict: ...
def write_delivery_qa(self, project_id: str, report: dict, *, now: str | None = None) -> dict: ...

def delivery_signoff_path(self, project_id: str) -> Path: ...
def read_delivery_signoff(self, project_id: str, default: dict | None = None) -> dict: ...
def write_delivery_signoff(self, project_id: str, record: dict, *, now: str | None = None) -> dict: ...
def reset_delivery_signoff(self, project_id: str, reason: str, *, now: str | None = None) -> None: ...
```

事件：

```text
delivery_qa_refreshed
delivery_signed
delivery_force_signed
delivery_signoff_reset
```

### 7.3 设计注意

Delivery QA 不应直接复用 Final Export 的 `files` 字段为真相。

它应该：

1. 读 manifest。
2. 对每个 manifest file 重新 resolve 到 `final-export/` 目录。
3. 确认 path 仍在 `final-export/` 内。
4. 重新 stat size。
5. 重新算 sha256。
6. 对 ZIP 重新打开检查 entry。
7. 对 JSON 可见内容做 redaction scan。

不要信任已落盘 manifest 中的 `path`、`size_bytes`、`sha256`。

## 8. API 设计

### 8.1 Get Delivery QA

```http
GET /api/projects/<project-id>/delivery-qa
```

行为：

- 如果没有 report，尝试构建一次。
- 如果有 report，计算 current source hash。
- 如果 hash 不一致，返回 stale report，不自动覆盖。
- 不生成 Final Export，不生成 ZIP。

响应：

```json
{
  "ok": true,
  "project_id": "project-001",
  "delivery_qa": {},
  "summary": {}
}
```

### 8.2 Refresh Delivery QA

```http
POST /api/projects/<project-id>/delivery-qa/refresh
```

行为：

- 重新同步 Project。
- 读取 Project Export。
- 读取 Final Export manifest。
- 读取 ZIP。
- 生成并写入 `delivery-qa.json`。
- 写 project event。

不允许：

- 自动 Final Export。
- 自动 Build ZIP。
- 自动 Delivery Signoff。

### 8.3 Get Delivery Signoff

```http
GET /api/projects/<project-id>/delivery-signoff
```

无 signoff：

```json
{
  "ok": true,
  "signoff": {},
  "summary": {
    "status": "not_signed"
  }
}
```

### 8.4 Create Delivery Signoff

```http
POST /api/projects/<project-id>/delivery-signoff
```

body：

```json
{
  "force": false,
  "override_reason": "",
  "signed_by": "local-user",
  "notes": "Accepted for handoff."
}
```

逻辑：

1. 读取 / 刷新 Delivery QA Report。
2. 如果 `handoff_allowed=false` 且 `force=false`，返回 409。
3. 如果 `force=true` 且 `override_reason` 为空，返回 400。
4. 如果已有 signoff，默认返回 409，不覆盖。
5. 写 `delivery-signoff.json`。
6. 写 Project event。
7. 返回 signoff + summary。

### 8.5 Reset Delivery Signoff

```http
POST /api/projects/<project-id>/delivery-signoff/reset
```

body：

```json
{
  "reason": "Final export rebuilt after adding WAV."
}
```

逻辑：

- 必须有 reason。
- 旧 signoff 写入 history。
- 删除或清空当前 signoff。
- 写 Project event。

`POST /final-export` 不自动 signoff。

- 如果已有 delivery QA，标记 stale 或刷新 summary。
- 不自动签核。

- ZIP 生成只更新 manifest.zip。
- 用户点 Refresh Delivery QA 后才得到最新 QA。

release-check 要覆盖这一点。

- 当前已有逻辑会清理 stale ZIP 时应继续保持。
- Delivery QA 必须检查 ZIP 是否与当前 manifest 一致。

建议检查：

- `manifest.zip.sha256` 是否等于当前 zip sha。
- `manifest.zip.entry_count` 是否等于实际 entry count。
- 实际 ZIP entry 集合是否等于 `final-export/` 当前文件集合。
- ZIP 中不能含绝对路径、`..`、空 entry、目录穿越。

## 12. 安全与边界

### 12.1 路径安全

Delivery QA 只允许读：

```text
.musicforge/projects/<project-id>/
.musicforge/projects/<project-id>/final-export/
.musicforge/projects/<project-id>/final-export.zip
```

Artifact path 必须：

- 是相对路径。
- resolve 后位于 `final-export/` 下。
- 不是 symlink。
- 不是目录穿越。

ZIP entry 必须：

- 是相对路径。
- 不含 `..`。
- 不以 `/` 开头。
- 不含 Windows drive prefix。
- 不含 NUL。

### 12.2 脱敏扫描

Delivery QA 要对以下 JSON 做二次扫描：

- `delivery-qa.json`。
- `delivery-signoff.json`。
- Final Export manifest summary。
- Project Export delivery summary。

检查内容：

- `sk-...`
- GitHub token 样式。
- `Bearer ...`
- Windows 盘符路径。
- UNC 路径。
- `api_key`
- `token`
- `secret`
- `raw_provider_response`
- `prompt`
- `provider_snapshot`

注意：字段名里出现 `token_count` / `provider_tokens` 是业务字段，可以允许；值里不能有真实 token。

### 12.3 并发

可能的并发：

- 用户同时点 Refresh Delivery QA。
- 用户生成 ZIP 时点 Refresh Delivery QA。
- 用户 signoff 时另一个请求 reset signoff。

要求：

- ProjectStore 使用已有 lock。
- 写 `delivery-qa.json` 原子替换。
- 写 signoff/history 在同一 lock 内完成。
- 已有 signoff 时普通 signoff 返回 409。
- reset 必须带 reason。

### 12.4 stale

- Project state。
- Project versions compact summary。
- Final Export manifest compact summary。
- ZIP sha/size/entry list。
- Quality Gate summary。
- Review Sprint closeout/signoff summary。

GET 发现 source hash 不一致：

- 返回 stale report。
- 不覆盖磁盘。

POST refresh：

- 重建并覆盖 `delivery-qa.json`。

## 19. 风险清单

### 风险 1：Delivery QA 和 Final Export 循环依赖

表现：

- Final Export manifest 想包含 delivery QA summary。
- Delivery QA 又要检查 Final Export manifest。

缓解：

- Delivery QA source hash 忽略 manifest 中的 delivery_qa / delivery_signoff summary 字段。
- Final Export 写 summary 时读取已有 delivery QA，不强制刷新。
- 用户生成 Final Export 后再 Refresh Delivery QA，再可选择重建 Final Export 更新 summary。

### 风险 2：ZIP 检查过严导致频繁失败

缓解：

- 明确提示“Rebuild ZIP, then refresh Delivery QA”。
- release-check 覆盖正常流程。
- warning 和 blocking 分清楚。

### 风险 3：Signoff 历史泄露本地信息

缓解：

- reset reason / notes / override reason 全部 `sanitize_sensitive_text()`。
- history 写入前 `sanitize_metadata()`。
- release-check 对 history 做 secret/path scan。

### 风险 4：QA 报告过大

缓解：

- `artifact_integrity.files` 只记录必要字段。
- 不写完整 Project Export。
- 不写完整 Final Export manifest。
- 不写 raw JSON 文件内容。

### 风险 5：用户误以为 Signoff 会自动发布

缓解：

- README 和 UI 写清楚：Delivery Signoff 只是本地交付验收，不上传、不发布、不同步外部平台。

## 21. 深度实现细节

这一节是给开发直接落代码用的。v3.6.0 的难点不在 UI，也不在 API 数量，而在“不要信任任何已经写在磁盘上的报告字段”。Final Export manifest、ZIP manifest、delivery QA report 都可能是旧的、半写的、污染的、或者和当前 Project state 不一致。

### 21.1 Delivery QA 的真相来源

Delivery QA 只能把以下内容当作真相：

| 数据 | 真相来源 | 说明 |
|---|---|---|
| Project final version | `project.json` 当前 state | 不信任客户端传入 |
| Project versions | `project.json` versions 列表 | 只取 compact summary |
| Final Export manifest | `final-export/manifest.json` 当前文件 | 需要二次校验 |
| Final Export files | 实际 `final-export/` 目录 stat/hash | 不信任 manifest size/hash |
| ZIP | 实际 `final-export.zip` 打开读取 | 不信任 manifest.zip |
| Closeout/Signoff | Project export 或 sprint store 当前文件 | 需要 summary 化 |
| Quality Gate | Final Export manifest summary + run 质量文件 | 不调用生成逻辑 |

不要把下面内容当作真相：

- HTTP body 里的 `version_id`。
- Final Export manifest 中记录的绝对路径。
- ZIP manifest 中记录的 entry count。
- 旧 `delivery-qa.json` 中记录的 hash。
- Studio 当前页面缓存。

### 21.2 Delivery QA source hash 规范

`source_hash` 用来判断 QA report 是否 stale。它必须稳定、可重复、跨平台尽量一致。

建议 source hash 输入：

```json
{
  "schema_version": 1,
  "project": {
    "project_id": "project-001",
    "final_version_id": "v004",
    "selected_version_id": "v004",
    "latest_version_id": "v004",
    "version_count": 4
  },
  "versions": [
    {
      "version_id": "v004",
      "status": "completed",
      "job_id": "job-004",
      "quality_score": 88,
      "updated_at": "..."
    }
  ],
  "final_export_manifest": {
    "version_id": "v004",
    "generated_at": "...",
    "quality_gate": {},
    "files": [
      {
        "kind": "midi",
        "path": "song.mid",
        "required": true,
        "exists": true
      }
    ],
    "review_sprint_closeout": {},
    "review_metrics": {},
    "review_judge": {}
  },
  "actual_files": [
    {
      "path": "song.mid",
      "size_bytes": 1234,
      "sha256": "..."
    }
  ],
  "zip": {
    "exists": true,
    "size_bytes": 12345,
    "sha256": "...",
    "entries": [
      {
        "path": "manifest.json",
        "size_bytes": 1234,
        "sha256": "..."
      }
    ]
  },
  "review_sprint_closeout": {},
  "delivery_signoff": {}
}
```

必须从 source hash 排除：

- `delivery_qa` summary。
- `delivery_signoff` summary。
- `generated_at` 如果它只是 QA report 自己的生成时间。
- 本机绝对路径。
- 临时文件名。
- JSON 字段顺序差异。

建议实现：

```python
def _stable_hash(value: Any) -> str:
    clean = sanitize_metadata(value)
    payload = json.dumps(clean, ensure_ascii=False, sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(payload.encode("utf-8")).hexdigest()
```

### 21.3 Artifact integrity 对账算法

Final Export manifest 中 `files` 字段只作为“期望清单”，不是事实清单。

建议流程：

```text
expected files = manifest.files where path is non-empty
actual files = recursively walk final-export/

for expected in expected files:
  validate relative path
  resolve final-export/path
  reject symlink
  reject path outside final-export/
  stat file
  sha256 file
  compare required/exists expectation

for actual in actual files:
  compute relative path
  validate safe path
  record size/hash
  if actual not in expected:
    warning or failed depending on kind
```

建议规则：

- `manifest.json`、`README.md`、`project-export.json`、`song-plan.json`、`song.mid` 是 required。
- `song.wav` 根据 `include_audio` 或 manifest 中 audio entry 判断。
- `stems/manifest.json` 如果 `quality_gate.require_stems=true`，则 required。
- stem MIDI/WAV 如果 manifest 声明存在，必须实际存在。
- 多出来的 `.tmp` 文件应 failed，因为说明写入流程未清理干净。
- 多出来的普通 `.json` 文件 warning，除非字段名或内容疑似敏感。

### 21.4 ZIP 对账算法

ZIP 检查必须打开实际 ZIP，不要只读 manifest.zip。

建议流程：

```text
actual_export_entries = all files under final-export/
zip_entries = all file entries inside final-export.zip

normalize both to posix relative path
reject unsafe zip entries
compare entry set
compare each entry sha256 with actual file sha256
compare zip sha256 with manifest.zip.sha256
compare zip entry_count with actual entry count
```

路径规范：

- `\` 转 `/`。
- 不允许空路径。
- 不允许 `..`。
- 不允许 `/manifest.json`。
- 不允许 `C:/...`。
- 不允许 `C:\...`。
- 不允许 `//server/share/...`。
- 不允许 NUL。
- 不允许目录 entry 参与文件对账。

ZIP entry mismatch 应该是 blocking，因为交付 ZIP 是最终移交对象。

### 21.5 Redaction scan 口径

Delivery QA 本身会生成很多 summary，容易把敏感字段重新带出来。

建议新增内部函数：

```python
def scan_delivery_payload_for_sensitive_values(payload: Any) -> list[dict[str, Any]]:
    ...
```

它不需要替换内容，只需要报告发现的问题。写盘前仍使用 `sanitize_metadata()`。

扫描对象：

- Delivery QA report。
- Delivery Signoff。
- Project Export delivery summaries。
- Final Export manifest delivery summaries。

检测策略：

| 类型 | 处理 |
|---|---|
| OpenAI key 样式值 | blocking |
| GitHub token 样式值 | blocking |
| Bearer token 值 | blocking |
| Windows 盘符路径值 | blocking |
| UNC 路径值 | blocking |
| `raw_provider_response` 字段 | blocking |
| `provider_snapshot` 字段 | blocking |
| `api_key` / `secret` / `token` 字段名 | blocking，白名单除外 |
| `provider_tokens` / `token_count` | 允许，数值型 |

白名单必须很小，不要为了测试方便扩大。

### 21.6 Signoff 状态机

Delivery Signoff 状态建议：

```text
not_signed
signed
force_signed
reset
```

API 行为：

| 当前状态 | 请求 | 结果 |
|---|---|---|
| not_signed | sign with QA passed | 200 signed |
| not_signed | sign with QA failed | 409 |
| not_signed | force sign without reason | 400 |
| not_signed | force sign with reason | 200 force_signed |
| signed | sign again | 409 |
| signed | reset without reason | 400 |
| signed | reset with reason | 200 reset, history appended |
| reset | sign again | 200 |

不要支持“覆盖签核”。如果以后需要 resign，必须单独设计。

### 21.7 Delivery QA 与 Final Export 的循环依赖处理

这是 v3.6.0 最容易做乱的地方。

推荐流程：

```text
1. POST /final-export
   -> build final-export/manifest.json
   -> manifest may include existing delivery summaries if any
   -> clear stale zip

2. POST /final-export/zip
   -> build final-export.zip
   -> update manifest.zip

3. POST /delivery-qa/refresh
   -> inspect final-export + zip
   -> write delivery-qa.json

4. POST /delivery-signoff
   -> read/refresh delivery QA
   -> write delivery-signoff.json

5. Optional POST /final-export again
   -> include delivery signoff summary in manifest
   -> clears old zip

6. POST /final-export/zip again
   -> package final signoff summary

7. POST /delivery-qa/refresh again
   -> verify final ZIP
```

release-check 不一定要做完整 7 步，但至少要覆盖：

- Final Export。
- ZIP。
- Delivery QA。
- Signoff。
- Rebuild Final Export 后 ZIP stale/mismatch。

| QA warning/passed，无 signoff | enabled | enabled | enabled | enabled | enabled | disabled |
| 已 signoff | enabled | enabled | enabled | disabled | disabled | enabled |
| QA stale | enabled | enabled | enabled | disabled | enabled | depends |

UI 不要把状态做得太花。核心要让用户看懂：

- 当前 Final Export 是否完整。
- 当前 ZIP 是否匹配。
- 当前是否允许交付签核。
- 如果不能签，哪个 blocker 阻止了。

建议在 QA failed 时显示第一条 blocking message：

```text
Blocked: Final Export ZIP does not match current manifest.
```

## 24. 兼容与迁移

v3.6.0 需要兼容老项目。

### 24.1 老 Project 没有 delivery 文件

行为：

- GET delivery-qa：构建 report 或返回 failed report。
- GET delivery-signoff：返回 `not_signed`。
- Project Export：delivery summaries 为空或 `not_signed`。
- Final Export：delivery summaries 为空。

不能要求用户重新创建 Project。

### 24.2 老 Final Export manifest 没有 zip 字段

行为：

- Delivery QA 报告 `zip_exists=false`。
- readiness = `needs_zip`。
- handoff_allowed=false。
- UI 提示 Build ZIP。

### 24.3 老 Sprint 没有 closeout/signoff

行为：

- 如果 Project 有 Review Sprints，但 latest sprint 未 signoff，Delivery QA blocking。
- 如果 Project 完全没有 Review Sprint，不能 blocking，因为早期版本没有 Sprint 流程。
- 可给 warning：`review_sprint_missing`。

### 24.4 老 Project 已有 final_version_id

行为：

- 可以直接生成 Final Export。
- Delivery QA 检查当前 final version。
- 不要求 Review Sprint。

## 26. 回滚与修复策略

v3.6.0 如果发布后发现问题，按问题类型处理：

### 26.1 QA 过严

表现：

- 合法交付包无法 sign。

处理：

- v3.6.1 放宽 warning/blocking 分类。
- 不要让开发临时绕过 gate。
- release-check 增加对应合法案例。

### 26.2 QA 过松

表现：

- 缺文件、ZIP mismatch、版本不一致仍能 sign。

处理：

- 立即 v3.6.1 修 blocking check。
- 新增最小复现测试。
- reviewer 复核 source hash 是否覆盖对应字段。

### 26.3 Signoff 被覆盖

表现：

- Refresh QA 或 Rebuild Final Export 覆盖了 delivery-signoff.json。

处理：

- P1 修复。
- Signoff 写入和 reset 只能走专用 API。
- 补 history 回归。

### 26.4 ZIP 安全问题

表现：

- ZIP entry 可以目录穿越。
- ZIP 可包含 final-export 外的文件。

处理：

- P1 修复。
- 禁止所有 unsafe entry。
- release-check 构造 polluted ZIP。

## 27. 开发不要做的事

开发中明确禁止：

- 不要把 Delivery QA 做成自动修复器。
- 不要在 QA refresh 里自动 build ZIP。
- 不要在 signoff 里自动 rebuild Final Export。
- 不要把完整 Project Export 嵌进 delivery-qa.json。
- 不要把 `delivery-signoff-history.jsonl` 打进 ZIP。
- 不要在 UI 里展示本机绝对路径。
- 不要让客户端传 `zip_sha256` 或 `final_export_sha256` 并直接信任。
- 不要为了测试直接改 `.musicforge/provider.json`。
- 不要提交 `.musicforge/`、`runs/`、`.playwright-mcp/`。

## 28. 开发完成后的自检清单

开发交付给 reviewer 前，必须自己逐项确认：

- `git status --short --branch` 没有临时目录。
- `python -m pytest -q` 全绿。
- `python -m song_agent.cli release-check` 全绿。
- `python -m song_agent.cli doctor` 通过。
- `git diff --check` 通过。
- `rg -n "sk-|github_pat_|ghp_|C:\\\\Users\\\\|raw_provider_response" song_agent tests README.md CHANGELOG.md material` 没有真实敏感信息。
- 新增 API 在 auth 开启时受保护。
- Delivery QA refresh 不调用 provider。
- Delivery QA failed 时普通 signoff 返回 409。
- force signoff 没 reason 返回 400。
- reset signoff 没 reason 返回 400。
- Project Export 和 Final Export 都有 delivery summary。
- ZIP mismatch 的测试真实构造了 mismatch，而不是只 mock 字段。

## 29. Reviewer 预期打回点

开发要提前规避这些常见打回点：

### 29.1 只检查 manifest，不检查实际文件

这会被打回。Delivery QA 必须 stat/hash 实际文件。

### 29.2 只检查 ZIP sha，不检查 entry

这会被打回。ZIP entry 集合必须和 final-export 文件集合对账。

### 29.3 Signoff 可重复覆盖

这会被打回。已有 signoff 再签必须 409，除非 reset。

### 29.4 Force sign 没有 blocker/warning 审计

这会被打回。forced signoff 必须记录 acknowledged blockers/warnings。

### 29.5 Project Export 泄露路径

这会被打回。所有 summary 都要二次脱敏。

### 29.6 release-check 只测 happy path

这会被打回。release-check 必须覆盖至少一个 failed QA 和一个 passed QA。

### 29.7 Delivery QA source hash 不包含 ZIP

这会被打回。ZIP 变化必须让 QA stale。

## 30. 给开发的执行提醒

这版不要追求“更智能”，要追求“交付可证明”。

开发时优先保证：

- 不信任 manifest 中的路径和 hash。
- 不信任 ZIP 中的 entry。
- Signoff 不被 refresh 覆盖。
- QA failed 不能普通签核。
- force sign 可审计。
- 导出不泄密。
- release-check 覆盖真实链路。

做到这里，MusicForge 就从“本地创作系统”进一步变成“本地可验收、可移交、可复核的音乐交付系统”。

## 0. 给开发的话

v9.6.1 已经把 Continuous Assurance 的核心证据链打稳：

- Assurance policy。
- Assurance run。
- Assurance archive ZIP。
- Assurance offline verifier。
- Hub gate `--require-continuous-assurance`。
- failed delivery verification 不再误通过。

v9.7 不要重写 v9.6。v9.7 要做的是把 Assurance Run 管起来：

```text
Assurance Policy
  -> Assurance Schedule
  -> Watch Queue
  -> due / overdue / stale / failed detection
  -> Drift Action Pack
  -> offline verifier
  -> Hub gate: require_assurance_watch_clear
```

你可以把它理解成：

> v9.6 回答“当前这一轮复核是否 passed”。  
> v9.7 回答“我们是否按计划持续复核？有没有过期未处理？有没有漂移后还没形成 action？”。

这版仍然不做后台定时器、不做 Windows Task Scheduler、不做自动签核、不做自动修复。它只做本地可触发、可导出、可验证的调度与处置证据。

## 1. 为什么需要 v9.7

v9.6 已经解决：

1. 当前 Hub / Control / Incident / Knowledge / Delivery evidence 是否仍匹配。
2. 当前 Assurance Run 是否 passed。
3. Assurance ZIP 是否可离线验证。
4. Hub gate 能否要求 Continuous Assurance passed。

但 v9.6 还是“手动跑一次”。它没有解决：

1. 下一次复核什么时候该跑。
2. 哪些 Hub 已经过期未复核。
3. 哪些 Assurance Run 已经 stale，但没有 action。
4. failed Assurance 是否被转换为可追踪处置项。
5. 多个 Hub / 多条 evidence 链路的复核状态能不能汇总。
6. 外部 reviewer 能不能拿到一份“保障计划执行情况”的离线包。
7. Hub gate 能不能要求“复核队列没有 overdue / blocking drift”。

v9.7 要补齐“持续保障运营”这一层。

## 5. 核心原则

### 5.1 Watch Queue 不做隐式修复

Watch Queue 只创建 action item，不直接修复。

允许 action type：

```text
refresh_assurance
rebuild_assurance_archive
verify_assurance_archive
refresh_hub_verification
open_incident_review
open_control_review
manual_change_request_required
manual_delivery_review_required
```

不允许 action type：

```text
approve_change_request
reset_signoff
close_incident
sign_control
sign_hub
submit_distribution
accept_submission
```

### 5.2 Watch 不能自证

Watch ZIP 不能只靠自己的 `watch-queue.json` 说 clear。

Verifier 必须反查：

- Assurance Archive ZIP。
- Assurance verification report。
- Hub ZIP。
- Hub verification report。
- 可选 Control Signoff / Incident / Knowledge verification report。

如果有人改 Watch ZIP，把 overdue 改 clear 并重签 manifest，必须 failed。

### 5.3 时间必须可控

所有 due / overdue 判定必须支持传入固定 `now`。

不要散落：

```python
datetime.now()
```

测试必须能构造：

- not_due。
- due_today。
- overdue。
- grace_window。

### 5.4 签核状态仍然不可变

v9.7 不改变 v9.5 / v9.6 的不可变签核模型。

如果 Watch Queue 发现已签核证据 stale，只能生成 action：

```text
manual_change_request_required
```

不能自动 reset。

### 5.5 导出包固定结构

Watch ZIP fixed allow-list：

```text
README.txt
trust-operations-assurance-watch-manifest.json
watch-queue.json
schedule-snapshot.json
assurance-run-index.json
drift-action-pack.json
external-verification-summary.json
watch-history.jsonl
```

不允许：

- extra txt。
- nested zip。
- duplicate entry。
- backslash entry。
- `.musicforge/`。
- manifest spoof。
- redaction pollution。

### 7.1 ID 规则

Queue：

```text
toawq-000001
```

Action：

```text
toaa-000001
```

并发要求：

- 使用 `RLock`。
- ID 分配在 lock 内。
- `mkdir(..., exist_ok=False)` 原子占位。

### 7.2 Source hash

WatchQueue source 必须绑定：

- schedule hash。
- assurance run index hash。
- external verification summary hash。
- action pack hash。

如果任意一项变，旧 Watch ZIP 不能被当作 current。

### 7.3 Stale 判定

Stale 来源：

- Schedule 变化。
- Assurance Run source hash 变化。
- Assurance verification report 变化。
- Hub verification report 变化。
- Watch queue 内 action 被篡改。
- 外部 Assurance ZIP hash 变化。

Stale 时：

- `export_watch()` 返回 409。
- `build_watch_zip()` 返回 409。
- verifier 可验证旧包，但 status 应 failed 或 stale。

## 8. Watch Queue 生成规则

### 8.1 找 Hub 范围

Schedule 支持：

```json
{
  "scope": {
    "hub_ids": ["hub-default"],
    "include_all_hubs": false
  }
}
```

v9.7 最小实现：

- `hub_ids` 显式列表。
- 如果空，则默认 `["hub"]` 或从已存在 Assurance runs 反推。
- `include_all_hubs` 可先支持 false。

不要为了 all hubs 大改 Hub Store。

### 8.2 找 latest Assurance Run

每个 Hub：

- 从 AssuranceStore list_runs(hub_id) 找最新 run。
- 优先使用 `refreshed_at` / `created_at`。
- 如果无 run：
  - row `due_status=missing`
  - readiness `blocked`
  - action `refresh_assurance`

### 8.3 验证 latest run

如果有 verification report：

- verification status passed -> ok。
- status failed -> blocked。
- report missing -> blocked if schedule requires verified。

### 8.4 due / overdue 判定

基于 latest run 的 verified/generated/created time。

算法：

```text
next_due_at = last_verified_at + interval_days
if now <= next_due_at:
  not_due
elif now <= next_due_at + grace_days:
  due
else:
  overdue
```

overdue 默认 blocking。
due 默认 warning。

### 8.5 drift 判定

Drift 来源：

- Assurance run stale。
- Assurance verification report 不匹配当前 archive。
- Hub verification report 不匹配当前 Hub ZIP。
- failed delivery evidence。
- open blocking incident。
- expired control exception。

v9.7 可以先通过现有 Assurance verification report 和 run summary 判断，不必重新实现所有 v9.6 细节。

### 8.6 action 生成

规则：

| 条件 | Action |
|---|---|
| missing run | refresh_assurance |
| due | refresh_assurance |
| overdue | refresh_assurance |
| run stale | refresh_assurance |
| verification report missing | verify_assurance_archive |
| archive missing | rebuild_assurance_archive |
| failed delivery | manual_delivery_review_required |
| open blocking incident | open_incident_review |
| control signoff stale | manual_change_request_required |

每个 action 都必须：

- 有 source hash。
- 有 severity。
- 有 manual_required。
- 默认 safe_to_auto_run=false。

v9.7 不执行 action，只产出 action pack。

### 10.2 Full resign 攻击

测试场景：

1. 生成 blocked Watch ZIP。
2. 修改 `watch-queue.json`：
   - status 改 clear。
   - due_count 改 0。
   - overdue_count 改 0。
3. 修改 `drift-action-pack.json`：
   - 删除 action。
4. 重算 queue / action / manifest。
5. 外部 Assurance verification report 不变。
6. verifier 必须 failed。

```text
toaw_watch_queue_semantics_match
toaw_action_pack_semantics_match
toaw_external_assurance_binding
```

### 10.3 Old report 攻击

测试场景：

1. Verify Watch ZIP A 得到 report A。
2. 重建 Watch ZIP B。
3. Hub gate 使用 ZIP B + report A。
4. 必须 failed。

## 18. 安全边界

### 18.1 不接受任意 source_path 上传

API 不要接受：

```json
{
  "source_path": "C:\\Users\\..."
}
```

如果需要外部 evidence，使用：

- 已知 store artifact。
- JSON report。
- base64。
- 明确 CLI 参数。

### 18.2 不泄露本机路径

Watch ZIP / verification report 不能出现：

- `C:\Users\...`
- `D:\...`
- UNC path。
- `.musicforge` 内部路径。
- `githubkey.txt`。
- token。

### 18.3 Watch 不可替代 Assurance

Watch passed 不等于 Assurance passed。

Hub gate 如果要求最终准出，建议组合：

```text
--require-continuous-assurance
--require-assurance-watch-clear
```

v9.7 docs 要明确这一点。

### 18.4 不做静默 mutation

Watch refresh 可以创建 queue。
Watch export/zip 可以创建 package。
但不允许：

- 改 Hub。
- 改 Control Signoff。
- 改 Incident。
- 改 Knowledge。
- 改 Delivery。

## 27. 风险清单

### 风险 1：Watch 变成“第二个 Assurance 自证包”

缓解：

- Verifier 必须要求外部 Assurance verification report。
- Hub gate 只信 Watch verification report，不信 Watch ZIP 内部 status。

### 风险 2：时间测试不稳定

缓解：

- 所有 due 逻辑支持传固定 now。
- 测试用固定时间。

### 风险 3：范围膨胀到后台调度

缓解：

- 明确 v9.7 不做 scheduler。
- 只做本地手动 refresh/run。

### 风险 4：Action 被误认为自动执行

缓解：

- `manual_required=true`。
- `safe_to_auto_run=false`。
- README 明确 action pack 不执行修复。

### 风险 5：长期 full pytest 超时

缓解：

- 定向测试覆盖。
- release-check v9/latest/quick。
- 不把超时说成通过。

## 28. 给开发的最后提醒

v9.7 的关键词是“持续保障运营”，不是“再生成一个 JSON 报告”。

实现时反复确认：

1. Watch clear 是不是从当前外部 Assurance / Hub evidence 反推出来的？
2. 如果有人把 Watch ZIP 里的 blocked 改成 clear 并重签，verifier 能不能挡住？
3. 如果 Assurance 过期、失败、stale，Watch 会不会生成明确 action？
4. Hub gate 是否只能接受当前 Watch verification report？

做到这四点，v9.7 就是有效推进。

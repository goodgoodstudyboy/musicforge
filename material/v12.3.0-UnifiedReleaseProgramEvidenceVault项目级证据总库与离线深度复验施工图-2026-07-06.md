# v12.3.0 Unified Release Program Evidence Vault 项目级证据总库与离线深度复验施工图

> 建议下一版：v12.3.0  
> 当前稳定基线：v12.2.1  
> 核心目标：把 v12.0 Program Board、v12.1 Program Operations、v12.2 Program Final Handoff 收敛成一个可长期保存、可离线深度复验、可交给外部审计方的 Program Evidence Vault。v12.3 不再继续给 Handoff Board 加零碎按钮，而是补齐 Program 级证据总库、nested package 深度验证、外部 anchor、防全量重签、Release/GA gate 和审计交接文档。

---

## 1. 背景

v12.0 到 v12.2 已经完成了 Program 级准出主线：

- v12.0 Unified Release Program Board：把多个 Release Train Handoff 组合成 Program，支持依赖、defer、risk、签核和 Program ZIP。
- v12.1 Unified Release Program Operations Center：补齐 Program 签核后的 Change Request reset、Operations Runbook、Continuous Review、Lifecycle Audit 和 Operations Archive。
- v12.2 Unified Release Program Final Handoff Board：补齐 Program 外部 Review Pack、Response、Accepted Evidence、Decision Board、Final Handoff signoff、Handoff Archive 和 Release/GA gate。
- v12.2.1 修复 rejected / needs_changes response 未阻断 Decision Board 的 P1，并补齐 Release / GA gate。

现在 Program 已经可以：

1. 创建。
2. 聚合多个 Train Handoff。
3. 完成 Program signoff。
4. 做 Program Operations 审计。
5. 完成 Program Final Handoff。
6. 被 Release / GA gate 强制要求。

但真实交付还缺一层“证据总库”：

1. Program ZIP、Operations Archive、Handoff Archive 分散在不同目录。
2. 外部审计方需要一次性拿到所有 Program 证据和验证说明。
3. 当前 Handoff Archive 不嵌入底层 ZIP，这是安全正确的，但也意味着长期归档时仍需额外保存底层包。
4. 如果半年后要复盘某个 Program，开发需要重新定位 Program ZIP、Operations ZIP、Handoff ZIP、external manifest、signoff binding、verification report。
5. 单个 verifier 能验证单个包，但缺少一个 Program 级 deep verifier 一次性复验全部证据链。
6. 当前 Program 证据包仍缺少外部 anchor，用来阻断“篡改 ZIP 后同步重签 ZIP 内部 manifest/report/index”的自证攻击。

因此 v12.3 建议进入：

**Unified Release Program Evidence Vault**

中文名：

**项目级证据总库与离线深度复验**

---

## 2. 版本定位

### 2.1 一句话

v12.3 是 Program 级证据总库：它把 signed Program、Program Operations、Program Handoff、外部 verification reports、signoff bindings、external evidence manifests、accepted evidence summaries 统一封存成一个固定结构 Vault，并提供深度离线 verifier 和外部 anchor。

### 2.2 和 v12.0 / v12.1 / v12.2 的关系

v12.0：

- 证明“这个 Program 当前可以签核”。

v12.1：

- 证明“这个 Program 签核后可维护、可 reset、可审计”。

v12.2：

- 证明“这个 Program 已被外部接收方最终交接验收”。

v12.3：

- 证明“这个 Program 的全部准出证据已经被封存、可离线深度复验、可长期审计、可交给第三方验证”。

### 2.3 本版必须解决的问题

1. 生成 Program Evidence Vault report。
2. 生成 package index，列出 Program / Operations / Handoff / accepted evidence 等证据包。
3. 生成 verification index，记录每个 nested package 的 runtime verification result。
4. 生成 proof index，列出 external evidence manifest、signoff binding、verification report 等外部证明。
5. 生成 chain-of-custody 文档，记录证据来源、封存时间、封存者、source hash。
6. 生成 replay plan，告诉审计方如何离线复验。
7. 生成 auditor guide，面向非开发审计人员说明包结构和验证命令。
8. 生成固定结构 Vault ZIP。
9. 生成 ZIP 外部 `vault-anchor.json`，绑定 Vault ZIP hash、manifest hash、package-index hash、verification-index hash、source hash。
10. 离线 verifier 支持 `--deep`，可重新调用 Program / Operations / Handoff / accepted evidence verifier。
11. Verifier 不信 ZIP 内部自证，必须能用外部 anchor 和 nested runtime verification 阻断 full-resign。
12. Release signoff / GA readiness 可要求 Program Evidence Vault passed。
13. release-check 增加 v12.3 smoke。

### 2.4 本版不做什么

v12.3 不做以下内容：

- 不创建新的 Program。
- 不修改 Program items。
- 不 reset Program signoff。
- 不 approve Change Request。
- 不导入新的 reviewer response。
- 不创建新的 Program Handoff Decision Board。
- 不替换 v12.0 / v12.1 / v12.2 的任何证据。
- 不做跨多个 Program 的 portfolio ranking。
- 不做公网发布、Portal、Transparency Feed。
- 不引入真实 PKI / 第三方 CA。
- 不把 Vault 当作签核源头；Vault 只是已签核证据的封存和深度复验层。

## 3. 核心设计原则

### 3.1 Vault 是封存层，不是决策层

Vault 不决定 Program 是否 ready。它只封存并复验已经完成的：

- Program signoff。
- Program Operations Archive。
- Program Final Handoff signoff。
- Accepted Evidence。
- External verification reports。

如果底层 Program / Operations / Handoff 不通过，Vault 必须 failed。

### 3.2 Vault 可以包含 nested ZIP，但必须固定 allow-list

v12.2 Handoff Archive 不嵌入底层 ZIP，这是为了避免交接包膨胀和内部自证。

v12.3 Vault 的目的不同：它是长期证据总库，因此允许包含 nested ZIP，但必须满足：

- nested ZIP 只能放在 `packages/` 下。
- 每个 nested ZIP 必须出现在 `package-index.json`。
- 每个 nested ZIP 必须有对应 verification report。
- 每个 nested ZIP 必须有明确 `package_type`。
- 不允许任意 `.zip` 进入其他目录。
- 不允许 `manifest.files[]` 声明额外文件绕过 fixed allow-list。

### 3.3 Verifier 必须深度复验，不信旧 verification report

Vault verifier 可以读取已落盘 verification report，但不能只信它们。

`--deep` 模式必须重新运行：

- `verify-unified-release-program-package`
- `verify-unified-release-program-operations-package`
- `verify-unified-release-program-handoff-package`
- `verify-unified-release-program-accepted-evidence-package`

然后比较：

- runtime status
- runtime ZIP sha256
- runtime manifest hash
- stored verification report hash
- package-index fingerprint
- verification-index fingerprint

### 3.4 必须有 ZIP 外部 anchor

Vault ZIP 里的 manifest/report/package-index/verification-index 都可以被攻击者同步重签。

因此 v12.3 必须生成 ZIP 外部 sidecar：

```text
vault-anchor.json
```

它不放进 Vault ZIP，落在：

```text
.musicforge/unified-release-programs/<program-id>/vault/vault-anchor.json
```

Verifier 在 `--require-anchor` 时必须传入：

```bash
--vault-anchor .musicforge/unified-release-programs/<program-id>/vault/vault-anchor.json
```

Anchor 绑定：

- `program_id`
- `vault_id`
- `vault_zip_sha256`
- `vault_zip_size_bytes`
- `vault_manifest_hash`
- `vault_source_hash`
- `package_index_hash`
- `verification_index_hash`
- `proof_index_hash`
- `chain_of_custody_hash`
- `created_at`
- `created_by`
- `anchor_payload_hash`
- `integrity_hash`

如果篡改 Vault ZIP 并沿用旧 anchor，verifier 必须 failed。

说明：如果攻击者同时替换 ZIP 和外部 anchor，本地纯离线校验仍无法提供真实世界不可抵赖性。后续版本可以做 Program Vault Registry / Transparency。v12.3 先解决“ZIP 内部自证全量重签”的本地防护。

### 3.5 签核后证据不可静默重建

如果 v12.2 Handoff 已 signed，Vault refresh/export/zip 不得触发任何 Handoff refresh/signoff。

Vault 可以读取 frozen evidence，但不能：

- 修改 Handoff report。
- 修改 Decision Board。
- 修改 Program Operations Archive。
- 重新签核 Program。
- reset Program。

底层 evidence stale 时，Vault refresh 只能 failed/block，不得修复。

## 7. Store 行为

### 7.1 refresh_vault()

输入：

```python
refresh_vault(program_id, payload)
```

必须传入或可从默认路径发现：

- Program ZIP
- Program verification report
- Program signoff binding
- Program external evidence manifest
- Operations Archive ZIP
- Operations verification report
- Handoff Archive ZIP
- Handoff verification report
- Handoff external evidence manifest
- Handoff signoff binding

行为：

1. 读取所有输入。
2. 运行 shallow verification。
3. 可选运行 deep verification。
4. 构建 source summary。
5. 构建 package index。
6. 构建 proof index。
7. 构建 verification index。
8. 构建 chain-of-custody event。
9. 写 `vault-report.json`。

失败规则：

- Program verification failed -> Vault failed。
- Operations verification failed -> Vault failed。
- Handoff verification failed -> Vault failed。
- Handoff 未 signed -> Vault failed。
- 缺 required package -> Vault failed。
- 缺 signoff binding -> Vault failed。
- package_type 不匹配 -> Vault failed。

### 7.2 export_vault()

输入：

```python
export_vault(program_id, payload)
```

行为：

1. 读取当前 `vault-report.json`。
2. 确认 Vault status 是 `passed`。
3. 确认 source hash 未 stale。
4. 复制固定文件到 `vault/export/`。
5. 复制 nested package ZIP 到 `packages/`。
6. 复制 proof sidecars 到 `proofs/`。
7. 写 `manifest.json`。

禁止行为：

- 不触发底层 Program refresh。
- 不触发 Operations refresh。
- 不触发 Handoff refresh。
- 不重签任何下游 signoff。

### 7.3 build_vault_zip()

行为：

1. 检查 export 目录存在。
2. 检查 manifest fixed allow-list。
3. 检查 nested packages 都在 package-index。
4. 创建 `unified-release-program-vault.zip`。
5. 运行 verifier。
6. 写 `unified-release-program-vault-verification-report.json`。
7. 写 ZIP 外部 `vault-anchor.json`。

关键要求：

- anchor 必须在 ZIP 创建后写，因为要绑定 ZIP hash。
- anchor 不进入 ZIP。
- build ZIP 后如果再次 build，必须重新生成 anchor。

### 7.4 verify_vault_zip()

Store 层 verify 调用：

```python
verify_unified_release_program_vault_package(
    zip_path,
    strict=True,
    deep=True,
    require_anchor=True,
    vault_anchor_path=...
)
```

返回：

```json
{
  "status": "passed",
  "package_type": "musicforge_unified_release_program_vault_verification",
  "zip_sha256": "...",
  "manifest_hash": "...",
  "vault_anchor_hash": "...",
  "blockers": [],
  "checks": []
}
```

## 8. Verifier 设计

### 8.1 固定 ZIP allow-list

Vault ZIP 顶层允许：

```text
manifest.json
vault-report.json
source-summary.json
package-index.json
verification-index.json
proof-index.json

replay-plan.json
auditor-guide.md
public-summary.json
packages/unified-release-program.zip

proofs/handoff-verification-report.json
proofs/handoff-signoff-binding-summary.json
proofs/handoff-external-evidence-manifest.json
proofs/accepted-evidence/*.json
```

不允许：

- 根目录任意额外文件。
- `.musicforge/` 或 `.MusicForge/`。
- `nested/`。
- `../`。
- 反斜杠路径。
- 绝对路径。
- 未列入 package-index 的 `.zip`。

### 8.2 必须检查 ZIP central directory 原始 entry name

沿用 v3.8.1 之后的规则：

- 不能只用 Python zipfile 归一化后的 filename。
- 必须解析或读取原始 entry name。
- `extra\name.txt` 必须 failed。

### 8.3 manifest.files 不能放行额外文件

Verifier 的 allow-list 不能来自 `manifest.files[]`。

正确规则：

```text
allowed_entries = fixed_static_entries + package_index.paths + proof_index.paths
```

`manifest.files[]` 只能用于 hash 对账。

### 8.4 deep verification

`--deep` 必须执行：

1. Program ZIP runtime verify。
2. Operations ZIP runtime verify。
3. Handoff ZIP runtime verify。
4. Accepted Evidence ZIP runtime verify。

每个 runtime verifier 的结果必须和：

- package-index
- verification-index
- proof-index
- stored verification report

一致。

### 8.5 anchor verification

`--require-anchor` 时：

1. `vault-anchor.json` 必须存在于 ZIP 外部。
2. anchor integrity hash 必须正确。
3. anchor 的 ZIP hash 必须等于当前 ZIP hash。
4. anchor 的 manifest hash 必须等于当前 ZIP manifest hash。
5. anchor 的 package-index hash 必须等于 ZIP 内 package-index hash。
6. anchor 的 verification-index hash 必须等于 ZIP 内 verification-index hash。
7. anchor 的 source hash 必须等于 ZIP 内 vault-report source hash。

缺 anchor 时：

- 如果 `--require-anchor`：failed。
- 如果未 require：warning。

### 8.6 redaction

扫描对象：

- 所有 JSON。
- 所有 Markdown。
- manifest。
- package-index。
- proof-index。
- public-summary。

必须拦截：

- `sk-...`
- GitHub token
- Bearer token
- Windows 盘符路径
- UNC 路径
- `/Users/...`
- `/home/...`
- `api_key=...`
- `raw_provider_response`

## 15. 安全边界

### 15.1 不允许 source_path 上传

所有 API 输入只接受已经存在的本地证据路径，不接受：

```text
source_path
local_path
file_path
```

如果 payload 出现这些字段，返回 400。

### 15.2 不保存本机绝对路径到 ZIP

Vault ZIP 内不允许出现：

- 本机绝对路径。
- 用户目录。
- workspace path。
- token 文件路径。

如果需要显示来源，必须脱敏成：

```json
{
  "source_kind": "unified_release_program",
  "component_id": "urp-000001",
  "path_redacted": true
}
```

### 15.3 不执行 destructive operation

Vault Store 不允许：

- 删除底层 Program。
- 删除底层 Handoff。
- 删除 accepted evidence。
- reset signoff。
- overwrite 外部证据。

### 15.4 Anchor 是 P1

没有 anchor 的 Vault 只能作为 warning 级本地快照，不能进入 Release / GA gate。

Release / GA gate 必须要求：

```text
require_anchor=true
```

## 20. 给开发的话

这一版不要再从 UI 开始，也不要先做“看起来很完整”的 ZIP。先做 verifier 和攻击复现。

最关键的三件事：

1. **Vault ZIP 不能自证。**  
   必须有 ZIP 外部 `vault-anchor.json`，Release/GA gate 必须要求它。

2. **nested ZIP 允许，但只能来自 package-index。**  
   不能因为这是 Vault 就放松 ZIP 安全。任何 unlisted `.zip`、反斜杠路径、`.MusicForge/`、declared extra 都必须 failed。

3. **deep verifier 必须真的重跑底层 verifier。**  
   不能只读 Program / Operations / Handoff 已经写好的 verification report。旧 report 可以作为对账材料，但 runtime verification 才是可信基础。

如果这三个点没做牢，v12.3 会被 reviewer 打回。先把 Store + verifier + release-check smoke 打稳，再接 CLI/API/Studio。

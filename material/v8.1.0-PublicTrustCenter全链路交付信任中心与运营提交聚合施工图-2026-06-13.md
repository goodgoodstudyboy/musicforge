# v8.1.0 Public Trust Center 全链路交付信任中心与运营提交聚合施工图

> 本文是给开发执行的 v8.1.0 施工图。当前稳定基线是 v8.0.2。v8.0.2 已经修复 Public Trust Center package fingerprint 全量重签伪造问题：Trust Center export 会写入 `data/package-verification-summaries/*.json`，这些 sidecar 来自底层 Registry / Portal / Transparency / Acknowledgement 已落盘 verification report；offline verifier 会用这些独立 sidecar 反查 `package-index`、`verification-index`、`public-package-verification-index`，不再只信 `trust-center-report.json.source` 自证。

v8.1.0 的目标不是再做一个新证明包，而是补完 v8.0 施工图里还没有落地的业务范围：把 Public Trust Center 从“Portfolio public proof 聚合门户”升级成“Release / Distribution / Submission / Operations / Portfolio Governance 全链路交付信任中心”。

一句话：

> v8.1.0 要让外部合作方打开一个 Public Trust Center ZIP，就能看到每个 Release 的交付状态、发行包状态、提交状态、运营签核状态、公开证明状态和风险缺口；同时离线 verifier 能确认这些摘要不是自洽伪造，而是绑定到当前 Release / Distribution / Submission / Operations / Portfolio verification evidence。

### 1.2 当前缺口

v8.0.2 的 Public Trust Center 主要聚合：

- Release 的浅层 signoff / export / ZIP 状态。
- Portfolio Governance public packages：Registry / Portal / Transparency / Acknowledgement。

它还没有完整聚合：

- Release metadata QA / export 状态。
- Audio review / mastering / encoded formats 状态。
- Rights clearance 状态。
- Format decision 状态。
- Distribution target / package / checklist / signoff / verifier 状态。
- Submission batch / package / external feedback / accepted 状态。
- Submission Evidence Archive / signoff / verifier 状态。
- Release Operations dashboard / runbook / signoff / archive / audit / reviewer pack 状态。
- Release Operations package verifier 绑定状态。
- 每个 Release 的综合 readiness matrix。
- 每个 Release 的 public-safe risk / missing evidence 列表。

这就是 v8.1.0 要补的业务范围。

## 2. v8.1.0 定位

### 2.1 它是什么

v8.1.0 是 Public Trust Center 的“全链路交付状态聚合层”。

它应该回答外部合作方或内部负责人最关心的问题：

1. 哪些 Release 已经 ready？
2. 哪些 Release 只是公开证明 ready，但 distribution/submission/operations 没 ready？
3. 每个 Release 的 Distribution package 是否已签核、已验证、符合 format decision / rights / encoded audio gate？
4. 每个 Submission batch 是否已签核、已提交、已接受、是否有 Submission Evidence Archive？
5. Release Operations 是否已签核、归档、审计、外部 reviewer pack 是否通过 verifier？
6. Portfolio Governance public proof 是否 current、accepted、transparent？
7. Trust Center ZIP 离开本地工作区后能否独立验收这些摘要？

### 2.2 它不是什么

v8.1.0 不做：

- 不复制 Release ZIP、Distribution ZIP、Submission ZIP、Operations ZIP、Portfolio ZIP。
- 不复制音频、封面、歌词、metadata 原文件。
- 不做新的 signoff。
- 不做新的 submission / accepted 状态写入。
- 不自动修复缺口。
- 不执行 runbook / action queue。
- 不调用 provider。
- 不上传平台。
- 不改变任何 Release / Distribution / Submission / Operations / Portfolio 状态。

Trust Center 仍然是只读发布入口。

## 6. Source 构建规则

### 6.1 build_source 主流程

`build_source()` 应保持：

1. 读取 config。
2. 确定 selection。
3. 读取 release summaries。
4. 读取 portfolio summaries。
5. 新增读取 delivery summaries。
6. 组合 source。
7. sanitize。

伪代码：

```python
releases = self._release_summaries(selection)
portfolios = self._portfolio_summaries(selection, profile=profile)
delivery = self._delivery_summaries(selection, releases=releases)
distribution = self._distribution_summaries(selection, releases=releases)
submission = self._submission_summaries(selection, releases=releases)
submission_evidence = self._submission_evidence_summaries(selection, submissions=submission)
operations = self._operations_summaries(selection, releases=releases)
readiness = self._delivery_readiness_matrix(...)
risks = self._delivery_risk_register(...)
```

### 6.2 不允许做的事

这些函数里禁止：

- `export_*()`。
- `build_zip()`。
- `signoff()`。
- `reset_signoff()`。
- `refresh_report(..., persist=True)`，除非该 Store 已有明确只读 `build_report(persist=False)`。
- 修改底层 JSON。

Public Trust Center refresh 可以写自己的 report，但不能写底层 domain 状态。

### 6.3 读取当前状态优先级

每个 domain 状态优先从当前已落盘 report/manifest/signoff/verifier report 读取。

建议优先级：

1. 当前 Store 的 `read_*()` / `summary()`。
2. 已落盘 manifest / verification report。
3. ZIP 存在性和 hash。
4. 如果缺失，标 `missing`。
5. 如果 integrity failed，标 `failed`。
6. 如果 source hash mismatch，标 `stale`。

## 11. Readiness 计算

### 11.1 Release readiness

```text
ready:
  release signoff signed/force_signed
  no critical delivery risk
  public proof passed if selected
  required policy domains passed

review_needed:
  optional domain missing/warning
  no critical risk

blocked:
  required domain failed/missing/stale
  redaction failed
  independent sidecar mismatch
```

### 11.2 Distribution readiness

`ready` 条件：

- target signed / force_signed。
- package ZIP exists。
- package verifier passed/warning。
- checklist passed or waived according to target policy。
- rights / format / encoded audio gates passed if manifest says required。

### 11.3 Submission readiness

`accepted` 条件：

- submission signed。
- submission package ZIP exists。
- submission verifier passed/warning。
- at least one accepted item or target status accepted if selected policy requires accepted。

### 11.4 Submission Evidence readiness

`signed` 条件：

- evidence report passed/warning。
- evidence signoff signed。
- evidence ZIP exists。
- evidence verifier passed/warning。

### 11.5 Operations readiness

`signed` 条件：

- operations report ready/passed。
- operations signoff signed/force_signed。
- operations archive exists and verifier passed if required。
- audit package exists and verifier passed if required。
- reviewer pack exists and verifier passed if required。

## 21. 给开发的话

这版不要再只补一个小字段。v8.0.2 已经把 Trust Center 的公开证明安全根收住了，v8.1.0 要补的是业务完整性：让 Trust Center 真正能代表一条 release 从交付、发行、提交、运营到公开证明的整体状态。

实现时要记住三条原则：

1. **只读聚合**：Trust Center 不能修改 Release / Distribution / Submission / Operations / Portfolio 的状态。
2. **独立绑定**：凡是会影响 readiness 的摘要，都不能只靠 `trust-center-report.source` 自证；要有独立 sidecar、manifest hash、verification report hash 或 signoff payload hash 来反查。
3. **公开安全**：所有导出的内容都必须是 public-safe 摘要，不能带本机路径、附件内容、账号、token、raw response、私密备注。

先把 v8.1 的 release-check smoke 写出来，再按 smoke 反推实现。实现完成后不要只跑定向测试，至少要跑 `release-check --profile v8 --skip-tests`、`latest --skip-tests`、`quick --skip-tests`、`doctor`、`git diff --check`。如果 full pytest 或完整 release-check 太久，可以说明耗时，但 v8.1 相关回归必须全部通过。

# v5.9.0 Submission Evidence Archive 平台提交证据归档与反馈对账施工图

日期：2026-06-02  
基线版本：v5.8.1  
目标版本：v5.9.0  
角色定位：Reviewer / Planner / Release Gate Designer  
项目：MusicForge / song-agent

---

## 1. 背景

MusicForge 现在已经不是一个单纯“生成 MIDI”的工具。到 v5.8.1 为止，系统已经有完整的本地发行交付链路：

- SongPlan / MIDI / WAV / stems / mix / mastering / encoded audio。
- Acceptance、Human Review、Audio Review、Audio Revision、Mastering QA、Encoded Audio Acceptance。
- Release Workspace、Distribution Package、Submission Package。
- Format Decision、Rights Clearance。
- Release / Distribution / Submission 的 signoff gate 和离线 verifier。

v5.8.1 刚刚把 Rights Clearance 的关键风险收住：

- 会自动聚合 Release track 的 Project version、Final Export、job artifact、asset/reference/context pack、editor clip/template、provider provenance。
- 如果项目实际用了 reference / asset / context pack，不能只声明 `original` 就通过。
- hidden / missing / stale 的素材来源会阻断 rights report。

现在剩下的缺口已经从“文件能不能交付”“权利能不能交付”，推进到了“交付之后有没有可审计的外部过程证据”。

现有 v4.3 Submission Workspace 已经能做这些事：

- 创建 Submission batch。
- 把 signed Distribution Target 放进 Submission。
- 生成 Submission Export / ZIP。
- Submission Signoff。
- 简单记录 submitted / feedback / accepted 状态。
- `verify-submission-package` 可以离线验证 Submission Package。

但现有 Submission 还偏“状态字段”，缺少真正的 evidence archive：

- 平台提交回执没有独立证据对象。
- 平台反馈、拒绝原因、补件要求、重新提交记录没有 round 结构。
- 截图、文本回执、CSV/JSON 回执等附件没有受控上传与 hash 保护。
- 不能清楚回答“这个 accepted 状态是基于哪条外部证据写入的”。
- 不能把提交后过程打成一个独立可携带审计包。
- 不能离线验证“提交包 + 后续平台反馈证据 + 接受证据”仍然一致。

所以 v5.9.0 建议做一个大跨步：

> Submission Evidence Archive：平台提交证据归档、反馈对账、重提交轮次、最终接受证据与离线验收包。

这一步依然不接真实 DSP / 发行商 API，不保存平台账号，不自动上传。它要做的是把人工在平台或发行商后台完成的提交、回执、反馈、重提、接受结果，本地记录成可审计、可导出、可防篡改、可离线验证的证据链。

---

## 2. v5.9.0 总目标

新增 Submission Evidence Archive，用来管理 signed Submission Package 之后的外部过程证据。

一句话目标：

> 一个 Submission Package 签核后，开发或业务人员可以把平台提交回执、反馈通知、重提记录、接受确认等证据录入系统；系统能对这些证据做 hash / source / stale / redaction / status reconciliation 校验，生成独立 Evidence Package ZIP，并支持离线 verifier 证明提交后证据没有被篡改。

v5.9.0 完成后，系统应该能回答：

- 这个 Submission 是什么时候提交的？
- 提交给哪个平台或目标？
- 平台返回的 submission id / reference id 是什么？
- 提交回执是由谁录入的？
- 反馈记录来自哪个 round？
- 哪条反馈导致了 needs_changes？
- 重提记录是否基于同一个 signed Submission Package？
- accepted 结果有没有外部证据支撑？
- 证据是否和当前 submission item / distribution ZIP / submission signoff 匹配？
- Evidence Package 离开本机 `.musicforge/` 后能否独立验证？

---

## 3. 非目标

v5.9.0 不做以下事情：

- 不接真实 DSP、发行商、PRO、版权库、分发平台 API。
- 不保存平台账号、密码、cookie、OAuth token、API key。
- 不自动上传音乐、metadata、artwork、合同或 ZIP。
- 不自动判定平台反馈是否合理。
- 不自动修复 rejected / needs_changes 的音乐、metadata、rights 问题。
- 不 OCR 平台截图。
- 不要求真实商业素材或真实平台回执参与测试。
- 不支持从服务器本地路径读取附件，API 只能接收上传内容。
- 不把原始平台后台 URL、带 token 的链接、本机路径、合同文件路径写进 export。
- 不把 Submission Package 本身重新签核为新的发行结果；Evidence Archive 是提交后的审计层。

## 4. 核心原则

### 4.1 Signed Submission Package 不可静默改写

v5.9 的证据是在 Submission Signoff 之后追加的过程证据。它不能绕过 v4.3 的签核不可变规则。

允许：

- 对 signed submission 追加 external evidence。
- 记录 submitted / feedback / accepted / rejected 等外部过程。
- 生成独立 Evidence Export / ZIP / Signoff。

不允许：

- 通过 Evidence Archive 改写原 Submission Package。
- 通过 Evidence Archive 重建 signed Submission Export。
- 在 Evidence Signoff 后继续静默追加证据。

如果需要新增证据：

- 原 Submission Package 不变。
- Evidence Signoff 必须 reset。
- 新证据进入新的 Evidence Report / Export / ZIP。

### 4.2 Evidence 必须绑定当前 signed package

每条 evidence 必须记录 source snapshot：

- `release_id`
- `submission_id`
- `item_id`
- `target_id`
- `package_id`
- `submission_signoff_hash`
- `submission_package_zip_sha256`
- `distribution_package_zip_sha256`
- `distribution_signoff_hash`
- `item_snapshot_hash`

如果这些源变化，旧 evidence 不能继续作为 current evidence。

### 4.3 外部状态不能只靠手填字段

现有 `record-submission`、`record-feedback`、`accepted` 只是状态更新。v5.9 后，它们必须背后产生 evidence record，或者要求已有 evidence id。

例如：

- submitted 状态必须有 `submission_receipt`。
- needs_changes 必须有 `platform_feedback`。
- accepted 必须有 `acceptance_confirmation`。
- rejected 必须有 `rejection_notice`。

### 4.4 本地证据可以详细，导出证据必须脱敏

本地 evidence 可以记录必要的原始说明，但导出必须只写 sanitized summary。

必须清理：

- 本机绝对路径。
- UNC / 网络共享路径。
- API key / token / Bearer token。
- 平台后台带 query / fragment 的 URL。
- 合同原文路径。
- provider raw response。
- 个人隐私字段。

### 4.5 附件只接受上传内容

所有附件 API 必须拒绝：

- `source_path`
- `local_path`
- `file_path`
- 任意让服务端读取本机文件的字段

只允许：

- `content_base64`
- `data_base64`
- 明确 `filename`
- 明确 `content_type`

## 8. Source Hash 口径

### 8.1 Evidence record source_hash

每条 evidence 的 `source_hash` 应该由以下内容组成：

- evidence type
- release id
- submission id
- item id
- round id
- source snapshot
- attachment ids + attachment sha256
- sanitized content fields

不能包含：

- `integrity_hash`
- 文件系统绝对路径
- 临时目录
- export path
- ZIP path

### 8.2 Report source_hash

Report source 应该包含：

- signed Submission Package hash
- Submission Signoff hash
- all non-archived evidence records
- all non-archived rounds
- attachment metadata and hashes
- current Submission item snapshot

不能包含：

- report 自身 hash
- report generated_at 之外的非决定性临时路径
- signoff history
- export zip path

### 8.3 Stale 规则

以下情况必须 stale：

- Submission signoff reset。
- Submission package zip sha256 改变。
- Submission item 的 target snapshot 改变。
- Distribution package zip sha256 改变。
- Distribution signoff hash 改变。
- Attachment sha256 与 metadata 不一致。
- evidence integrity_hash 不匹配。
- report source_hash 与当前 source state 不一致。

## 9. 状态对账规则

v5.9 必须新增 reconciliation check。

### 9.1 Item status 与 evidence 对账

如果 item.status 是：

- `submitted`：必须有 current `submission_receipt` 或 `resubmission_receipt`
- `feedback_received`：必须有 current `platform_feedback`
- `needs_changes`：必须有 current `needs_changes_notice`
- `accepted`：必须有 current `acceptance_confirmation`
- `rejected`：必须有 current `rejection_notice`
- `withdrawn`：必须有 current `withdrawal_confirmation`

不满足则 report failed。

### 9.2 accepted 不能越级

`accepted` 必须满足：

- Submission package signed。
- item 有 submitted-or-later evidence。
- latest accepted evidence source current。
- 没有更新的 needs_changes / rejected evidence。

### 9.3 needs_changes 要能回流

当录入 `needs_changes_notice` 时：

- item.status 变为 `needs_changes`
- report 显示 open issue
- Studio 提供 Create ReviewTask / Create Fix Note 按钮
- 如果已有同 item + same evidence hash 的 open task，返回 existing，不能重复创建

### 9.4 重提交 round

当 item 是 needs_changes 后，可以创建 `resubmission` round。

重提交必须：

- 引用前一条 needs_changes evidence。
- 记录 changed_summary。
- 记录 resubmission receipt。
- 将 item.status 更新为 `submitted` 或 `resubmitted`。

## 10. API 设计

所有 API 都挂在现有 Submission route 下。

### 10.1 Evidence 总览

```http
GET /api/releases/<release-id>/submissions/<submission-id>/evidence
```

返回：

```json
{
  "ok": true,
  "release_id": "release-000001",
  "submission_id": "sub-000001",
  "summary": {},
  "report_summary": {},
  "signoff_summary": {},
  "items": []
}
```

### 10.2 刷新报告

```http
POST /api/releases/<release-id>/submissions/<submission-id>/evidence/report/refresh
```

规则：

- 如果 submission 未签核，返回 409。
- 如果 package zip 缺失，返回 409。
- 如果 evidence integrity 失败，report failed。

### 10.3 上传附件

```http
POST /api/releases/<release-id>/submissions/<submission-id>/items/<item-id>/evidence/attachments
```

请求：

```json
{
  "filename": "receipt.png",
  "content_type": "image/png",
  "content_base64": "...",
  "kind": "screenshot",
  "created_by": "liuhuanji"
}
```

必须拒绝：

```json
{
  "source_path": "C:\\Users\\example\\Desktop\\receipt.png"
}
```

返回 400，且不能创建 attachment。

### 10.4 记录提交回执

```http
POST /api/releases/<release-id>/submissions/<submission-id>/items/<item-id>/evidence/submission-receipt
```

请求：

```json
{
  "platform_name": "Generic DSP",
  "external_reference": "DSP-SUB-123",
  "recorded_by": "liuhuanji",
  "occurred_at": "2026-06-02T00:00:00+08:00",
  "message": "Submitted in platform portal.",
  "attachment_ids": ["att-000001"]
}
```

行为：

- 创建 round-000001，如果还没有 round。
- 创建 evidence。
- 更新 item.status = `submitted`。
- 写 event。

### 10.5 记录平台反馈

```http
POST /api/releases/<release-id>/submissions/<submission-id>/items/<item-id>/evidence/feedback
```

请求：

```json
{
  "feedback_status": "needs_changes",
  "category": "metadata",
  "severity": "medium",
  "message": "Artist name does not match profile.",
  "external_reference": "DSP-FB-456",
  "recorded_by": "liuhuanji",
  "attachment_ids": ["att-000002"]
}
```

允许 `feedback_status`：

- `feedback_received`
- `needs_changes`
- `accepted`
- `rejected`

行为：

- 写 feedback evidence。
- 更新 item.status。
- 如果 needs_changes / rejected，report open issue。

### 10.6 记录接受确认

```http
POST /api/releases/<release-id>/submissions/<submission-id>/items/<item-id>/evidence/acceptance
```

要求：

- item 已 submitted 或 feedback_received。
- 有 current submission receipt。
- 没有更新的 unresolved needs_changes。

行为：

- 创建 acceptance evidence。
- 更新 item.status = `accepted`。
- 如果所有 item accepted，batch.status = `accepted`。

### 10.7 创建重提 round

```http
POST /api/releases/<release-id>/submissions/<submission-id>/items/<item-id>/evidence/resubmission-round
```

请求：

```json
{
  "based_on_evidence_id": "ev-000002",
  "changed_summary": "Fixed metadata artist name.",
  "recorded_by": "liuhuanji"
}
```

规则：

- based_on evidence 必须是 current needs_changes / rejected。
- 不能基于 stale feedback 创建 round。
- 创建 round 后仍需 record receipt。

### 10.8 Evidence signoff

```http
POST /api/releases/<release-id>/submissions/<submission-id>/evidence/signoff
```

请求：

```json
{
  "signed_by": "liuhuanji",
  "require_submitted": true,
  "require_accepted": true,
  "notes": "All platform submissions accepted."
}
```

规则：

- report 必须 current。
- `require_submitted=true` 时所有 active item 都必须 submitted-or-later。
- `require_accepted=true` 时所有 active item 都必须 accepted。
- stale / integrity failed 不能 force 绕过。
- force 只允许绕过 warning，不允许绕过 source/integrity/stale。

### 10.9 Evidence signoff reset

```http
POST /api/releases/<release-id>/submissions/<submission-id>/evidence/signoff/reset
```

请求必须有：

```json
{
  "reason": "new feedback evidence imported"
}
```

### 10.10 Evidence export / ZIP / verify

```http
POST /api/releases/<release-id>/submissions/<submission-id>/evidence/export
POST /api/releases/<release-id>/submissions/<submission-id>/evidence/export/zip
POST /api/releases/<release-id>/submissions/<submission-id>/evidence/verify
GET  /api/releases/<release-id>/submissions/<submission-id>/evidence/export.zip
```

## 15. 安全边界

### 15.1 附件上传

必须：

- 拒绝 source_path。
- 限制 filename 字符。
- 限制扩展名。
- 验证 content_type 与 header。
- 限制单附件大小，建议 10 MB。
- 限制每个 item 附件数量，建议 50。
- 限制整个 evidence package 附件总大小，建议 200 MB。

### 15.2 URL 处理

如果支持 URL 字段：

- 不导出 query。
- 不导出 fragment。
- 不导出 credential。
- `https://user:pass@example.com/path` 必须清理。
- token-like query 直接 redaction failed。

建议导出时只保留：

```json
{
  "safe_url_origin": "https://example.com",
  "safe_url_path_hint": "/submissions/<redacted>"
}
```

### 15.3 Sensitive scan

必须复用 `song_agent/redaction.py`。

扫描范围：

- manifest
- report
- signoff
- evidence json
- attachment json
- text attachment
- csv attachment
- README
- timeline

### 15.4 Signed evidence immutability

Evidence Signoff 后禁止：

- create evidence
- create attachment
- create round
- hide evidence
- export evidence
- zip evidence

如果需要变更：

- reset evidence signoff
- refresh report
- rebuild export
- rebuild zip
- sign again

## 16. 与现有 Submission API 的衔接

现有接口：

```text

POST /api/releases/<id>/submissions/<sub>/items/<item>/record-feedback
```

v5.9 有两种实现方式。

### 16.1 推荐方式

- `record-submission` 创建 `submission_receipt`
- `record-feedback` 创建 `platform_feedback`
- `accepted` 创建 `acceptance_confirmation`

旧接口 payload 不够的字段用默认值，但必须写 evidence。

### 16.2 更严格方式

旧接口只接受：

```json
{
  "evidence_id": "ev-000001"
}
```

然后基于 evidence 更新状态。

Reviewer 建议 v5.9 使用 16.1，兼容现有测试和 Studio；v6 之后再考虑把旧接口收紧成 explicit evidence id。

## 22. 风险清单

### 22.1 误把 evidence 当平台真实验证

v5.9 只是本地证据归档，不证明平台数据真实无误。

文档和 UI 必须说明：

- 系统记录人工输入和上传证据。
- 不连接平台 API。
- 不校验平台后台真实性。

### 22.2 上传截图泄露隐私

截图可能包含账号、邮箱、token、后台 URL。

控制：

- 限制类型和大小。
- 图片只做 hash，不做 OCR。
- 导出 attachment metadata，不默认导出图片内容？  

这里需要决策：

- 如果要可携带审计，必须导出图片内容。
- 但导出前应警告业务确认截图已脱敏。

建议 v5.9 允许导出图片内容，但 report 增加 warning：

```text
image_attachment_not_text_scanned
```

### 22.3 Evidence package 过大

如果包含 nested submission package 和截图，ZIP 会变大。

控制：

- 单附件 10 MB。
- 总附件 200 MB。
- verifier zip bomb limit。

### 22.4 旧接口兼容导致证据字段太少

旧 `record-submission` payload 只有 external_reference。

控制：

- 自动生成 minimal evidence。
- report warning：`minimal_evidence_without_attachment`。
- release-ready signoff 可选择 `require_attachment=true`，但 v5.9 先不强制。

### 22.5 Evidence 被后续 feedback 反向污染 stale

source hash 不应包含后验 evidence list 导致“录入反馈后之前 receipt stale”。

控制：

- 单条 evidence source 只绑定 package/item snapshot 和自身内容。
- report source 包含 evidence list。
- report stale 不等于单条 receipt stale。

- 哪条 accepted evidence 支撑最终状态。
- 外部审计包能否证明整个提交后过程没有被篡改。

两者关系：


## 25. 最终定义

v5.9.0 只有在下面这句话成立时才算完成：

> 一个 signed Submission Package 可以生成独立的 Submission Evidence Archive：记录提交回执、平台反馈、重提和接受确认；这些 evidence 绑定当前 signed package，能防 stale、防篡改、防路径泄露，并能导出 ZIP 到外部目录离线验证。

如果只是在 item 上多加几个状态字段，不算完成。

如果不能离线验证 evidence package，不算完成。

如果 accepted 状态没有 evidence 支撑，不算完成。

如果 source_path 可以读本机文件，不算完成。

如果 Evidence Signoff 后还能静默新增反馈，不算完成。

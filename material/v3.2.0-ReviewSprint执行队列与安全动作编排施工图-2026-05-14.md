# v3.2.0 Review Sprint 执行队列与安全动作编排施工图

日期：2026-05-14

当前稳定基线：v3.1.0

目标版本：v3.2.0

定位：在 v3.1.0 已经完成 Review Sprint Recommendation Report 的基础上，把“建议下一步做什么”升级为“可选择、可执行、可审计、可恢复的 Sprint Action Queue”。v3.2.0 只自动执行非破坏性动作，例如生成候选、刷新决策报告、保存推荐 Context Pack、刷新推荐报告；仍然不做自动 apply、不做自动 resolve、不做自动 close sprint。

---

## 1. 背景

v3.0.0 完成了 Review Sprint：

```text
ReviewTask list
  -> ReviewSprint
  -> conflict report
  -> batch local/provider candidate generation
  -> single task candidate apply
```

v3.1.0 完成了 Sprint Recommendation Report：

```text
ReviewSprint
  -> recommendation report
  -> recommended order
  -> recommended action per task
  -> context pack preview
  -> recommendation summary in compare/export/final export
```

现在系统已经能回答：

- 先处理哪个 task。
- 哪个 task 需要 inspect conflict。
- 哪个 task 适合 generate local candidates。
- 哪个 task 适合 generate provider candidates。
- 哪个 task 需要 refresh decision report。
- 哪个 task 可以考虑 apply ready candidate。
- 哪个 task 推荐保存 Context Pack。

但 v3.1.0 仍然停留在“报告层”。用户看到建议后，还需要手动去不同按钮里执行动作。下一步需要把推荐变成一个清晰的推进工作台：

```text
Refresh recommendations
  -> Create action queue
  -> Select safe actions
  -> Run selected actions
  -> Inspect results
  -> Refresh recommendations again
  -> Manually apply candidate when ready
```

这就是 v3.2.0 的目标。

---

## 2. 一句话目标

v3.2.0 要让 Review Sprint 从“智能推荐报告”升级为“可控执行面板”：

```text
Recommendation Report
  -> Action Queue
  -> Safe action execution
  -> Audit trail
  -> Updated Sprint state
  -> New recommendations
```

关键是“可控”，不是“全自动”。

系统可以自动做：

- 刷新 Recommendation Report。
- 保存推荐 Context Pack。
- 批量生成 local candidates。
- 批量生成 provider candidates。
- 刷新 ReviewTask Decision Report。
- 重新读取 Sprint summary / conflict report。

系统不可以自动做：

- apply candidate。
- resolve task。
- archive task。
- close sprint。
- final project。
- final export。

这些动作只能生成 `manual_required` 队列项，由用户在原有安全入口手动执行。

### 3.1 v3.2.0 必须做

- 新增 Sprint Action Queue 数据模型。
- 新增 ActionQueueStore。
- 支持从最新 Recommendation Report 创建 queue。
- 支持选择性执行 queue items。
- 支持安全动作：
  - refresh_recommendations
  - save_recommended_context_pack
  - generate_local_candidates
  - generate_provider_candidates
  - refresh_decision_report
  - refresh_conflicts
- 支持人工动作占位：
  - inspect_conflict
  - apply_ready_candidate
  - resolve_task
  - add_follow_up
  - skip_stale
  - skip_archived
- 每个 action item 需要状态：
  - pending
  - running
  - completed
  - failed
  - skipped
  - blocked
  - manual_required
- 支持 queue run：
  - run all safe pending actions
  - run selected item ids
  - stop on failure 可配置
- Queue 执行必须写 event stream。
- Queue 执行必须可重入：已 completed 的 item 默认不重复执行。
- Queue 执行必须可恢复：服务重启后不能丢状态。
- Queue 中 provider action 必须记录 provider usage。
- Queue 中 Context Pack action 必须重新校验 source hash / hidden。
- Queue 中 stale task 必须 blocked。
- Studio Review Sprints 增加 Action Queue 面板。
- Project Compare / Export / Final Export 增加 action queue summary。
- release-check 增加 v3.2 smoke。
- README / CHANGELOG / version bump。
- 提交、推送、tag、GitHub Release。

- Queue item retry。
- Queue item cancel。
- Queue diff：推荐报告变化后提示哪些 item 过期。
- Queue templates：例如 “cheap local first”、“provider heavy pass”。
- 批量把 recommended order 写回 Sprint task order。
- WebUI 里显示 provider usage 估算。

这些可以放 v3.2.1 或 v3.3.0。

### 3.3 v3.2.0 明确不做

- 不做 batch apply。
- 不做 auto apply。
- 不做 auto resolve。
- 不做 auto close sprint。
- 不做自动 final project。
- 不做自动 final export。
- 不做跨 Project action queue。
- 不做后台长期任务系统。
- 不做复杂工作流 DSL。
- 不做多用户权限系统。
- 不做 provider judge。
- 不做音频理解、BPM/key 自动识别、audio-to-MIDI。

## 4. 核心原则

### 4.1 推荐和执行必须分层

v3.1.0 的 Recommendation Report 是分析结果。

v3.2.0 的 Action Queue 是执行计划。

不要让 Recommendation Report 直接执行动作。必须经过显式 queue：

```text
recommendation-report.json
  -> create action queue
  -> user selects actions
  -> run selected safe actions
```

这样可以保证：

- 用户知道系统准备做什么。
- 每个动作都有状态。
- 执行结果可以追踪。
- 出错可以定位到 item。
- 后续可以做 retry / resume。

### 4.2 apply 永远走 ReviewTask 单条候选守卫

任何 `apply_ready_candidate` 都只能是 `manual_required`。

Queue 可以告诉用户：

```text
Task review-task-001 has ready candidate revcand-002.
Manual apply is recommended.
```

但 queue 不能调用：

```text
POST /api/projects/<project-id>/review-tasks/<task-id>/candidates/<candidate-id>/apply
```

真正 apply 仍由用户点击 ReviewTask candidate apply，并继续走现有守卫：

- task must be open。
- candidate status must be ready。
- task/candidate must be current。
- parent plan hash must match。
- selected_candidate_id 不能已有。
- needs_more_work / resolved / archived / stale 都不能 apply。

### 4.3 本地可验证优先

v3.2.0 的 queue engine 必须 deterministic。

Mock provider 可以用于 release-check，但真实 provider smoke 不作为必需验证。

所有核心判断必须能在本地用 pytest 和 release-check 跑通。

### 4.4 Queue item 必须最小化持久化

Queue item 可以保存：

- task_id
- recommended_action
- recommendation_rank
- recommendation_created_at
- target action payload summary
- context pack preview refs
- result summary
- error message

Queue item 不应保存：

- 明文 API key。
- provider raw response。
- 本机绝对路径。
- 任意可执行命令。
- 未校验文件路径。
- 大体积 song-plan 副本。

### 4.5 执行前必须重新校验

创建 queue 时的信息只是快照。执行 item 前必须重新校验：

- Sprint 是否仍然存在。
- Task 是否仍在 Sprint 内。
- Task 是否属于当前 Project。
- Task 是否 stale。
- Parent SongPlan hash 是否匹配。
- Candidate 是否仍 ready。
- Context Pack source refs 是否仍 current。
- Provider template 是否仍 enabled。
- Provider config 是否可用。

不要因为 queue 里写了 “generate_provider” 就直接信任。

## 5. 新增数据结构

### 5.1 存储目录

建议新增：

```text
.musicforge/projects/<project-id>/review-sprints/<sprint-id>/action-queues/
  queue-001/
    queue.json
    events.jsonl
  queue-002/
    queue.json
    events.jsonl
```

不建议把所有 queue 写到一个大 JSON 里。原因：

- 后续可以单独删除/归档 queue。
- 执行中只写当前 queue 文件，冲突面更小。
- event stream 按 queue 拆开更容易看。

```json
  "recommendation": {
    "report_created_at": "2026-05-14T...",

    "score": 87,
    "score_breakdown": {
      "priority": 25,
      "candidate_readiness": 20
    }
  },
  "input": {
    "strategies": ["balanced"],
    "render_midi": true
  },
  "result": {},
  "error": null,
  "started_at": null,
  "completed_at": null,
  "attempt": 0

```

### 5.4 safety 枚举

```text
auto_safe
provider_safe
manual_required
blocked
informational
```

含义：

- `auto_safe`：可以自动执行，不改变 Project final 决策，例如 local candidate generation、decision refresh。
- `provider_safe`：可以自动执行，但会调用 provider，必须用户显式允许。
- `manual_required`：不能自动执行，只给用户提示。
- `blocked`：当前状态不能执行。
- `informational`：纯提示，例如 inspect conflict。

### 5.5 action 枚举

内部 queue action 建议和 v3.1 recommendation action 分开命名。

```text
refresh_recommendations
refresh_conflicts
save_recommended_context_pack
generate_local_candidates
generate_provider_candidates
refresh_decision_report
inspect_conflict
manual_apply_candidate
manual_resolve_task
manual_add_follow_up
skip_stale_task
skip_archived_task
no_action
```

映射规则：

```text
v3.1 action                  -> v3.2 queue action
inspect_conflict             -> inspect_conflict
generate_local               -> generate_local_candidates
generate_provider            -> generate_provider_candidates
refresh_decision_report      -> refresh_decision_report
apply_ready_candidate        -> manual_apply_candidate
resolve                      -> manual_resolve_task
add_follow_up                -> manual_add_follow_up
skip_stale                   -> skip_stale_task
skip_archived                -> skip_archived_task
no_action                    -> no_action
```

Context Pack 是附加动作，不一定一一来自 recommendation action：

```text
if context_pack_preview has refs:
  create save_recommended_context_pack item
```

## 6. 新增模块建议

### 6.1 新增 `song_agent/review_sprint_actions.py`

职责：

- 数据类：
  - `SprintActionQueue`
  - `SprintActionItem`
- Store：
  - `ReviewSprintActionQueueStore`
- 构建：
  - `build_action_queue_from_recommendation_report(...)`
- 执行：
  - `run_action_queue(...)`
  - `run_action_item(...)`
- summary：
  - `action_queue_summary(...)`
  - `action_queue_export_summary(...)`
- 安全：
  - `ensure_action_item_current(...)`
  - `sanitize_action_queue(...)`

不要把执行逻辑全部塞进 `server.py`。`server.py` 只负责路由、读取 payload、调用 service。

### 6.2 Store 方法

```python
class ReviewSprintActionQueueStore:
    def __init__(self, sprint_dir: Path): ...

    def create_queue(self, queue: SprintActionQueue, *, now: str | None = None) -> SprintActionQueue: ...
    def read_queue(self, queue_id: str) -> SprintActionQueue: ...
    def list_queues(self, *, include_archived: bool = False) -> list[SprintActionQueue]: ...
    def update_queue(self, queue: SprintActionQueue, *, event: str | None = None, payload: dict | None = None) -> SprintActionQueue: ...
    def archive_queue(self, queue_id: str, *, now: str | None = None) -> SprintActionQueue: ...
    def append_event(self, queue_id: str, event: str, payload: dict, *, now: str | None = None) -> None: ...
    def read_events(self, queue_id: str) -> list[dict]: ...
```

ID 分配必须并发安全：

- 在锁内分配 queue id。
- 使用 `mkdir(..., exist_ok=False)` 原子占位目录。
- 写 JSON 使用现有原子写工具。

参考已经修过的 job/context pack 并发问题，不要重复踩坑。

### 6.3 Queue 构建函数

```python
def build_action_queue_from_recommendation_report(
    *,
    project_id: str,
    sprint: ReviewSprint,
    recommendation_report: dict[str, Any],
    name: str | None = None,
    settings: dict[str, Any] | None = None,
    now: str | None = None,
) -> SprintActionQueue:
    ...
```

构建逻辑：

1. 读取 `recommended_actions`。
2. 按 rank 创建 task action item。
3. 如果 action 有 `context_pack_preview`，额外创建 `save_recommended_context_pack` item。
4. 对 `apply_ready_candidate` / `resolve` / `add_follow_up` 创建 `manual_required` item。
5. 对 `skip_stale` / `skip_archived` 创建 `blocked` 或 `informational` item。
6. 计算 summary。
7. 保存 recommendation report hash。

Recommendation report hash 用于判断 queue 是否 stale：

```text
sha256(canonical_json(recommendation_report))
```

## 7. Action 执行设计

### 7.1 执行入口

支持两种执行：

```text
Run all eligible safe actions
Run selected item ids
```

默认只执行：

```text
auto_safe
```

Provider action 必须显式传：

```json
{
  "include_provider": true
}
```

不允许默认执行 provider action，原因：

- 会消耗 token。
- 可能触发外部服务。
- 输出不可完全 deterministic。

### 7.2 执行顺序

建议固定顺序：

```text
refresh_conflicts
refresh_recommendations
save_recommended_context_pack
generate_local_candidates
generate_provider_candidates
refresh_decision_report
manual/informational items
```

同类 action 内按：

```text
rank asc
priority desc
task order asc
item_id asc
```

### 7.3 并发策略

v3.2.0 建议先做串行执行。

原因：

- ReviewTask / Sprint / Project 都是本地文件系统。
- provider 调用有外部不确定性。
- 串行更容易恢复和审计。
- 目前系统价值是可控推进，不是极致速度。

可以在 settings 预留：

```json
{
  "max_concurrency": 1
}
```

但 v3.2.0 不必实现并发执行。

### 7.4 幂等规则

默认行为：

- `completed` 不重复执行。
- `running` 在服务启动恢复时改为 `interrupted` 或 `failed`，不要永远 running。
- `failed` 可以通过后续版本 retry；v3.2.0 可以先支持手动 rerun selected failed。
- `blocked` 只有刷新 recommendation / recreate queue 后才改变。

生成候选类 action：

- `generate_local_candidates` 默认 `skip_existing_ready=true`。
- `generate_provider_candidates` 默认 `skip_existing_provider=true`。

这样重复执行不会无限生成重复候选。

保存 Context Pack：

- 如果同一个 queue item 已创建 pack，则记录 `context_pack_id`，重复执行时直接返回 completed/skipped。
- 不要因为重复点击创建多个完全相同的 pack。

### 7.5 执行前状态校验

每个 item 执行前调用统一校验：

```python
ensure_action_item_current(
    project_id=project_id,
    sprint=sprint,
    task_store=task_store,
    item=item,
    recommendation_report=recommendation_report,
)
```

校验内容：

- queue project_id/sprint_id 匹配。
- sprint 仍然存在。
- sprint 未 archived。
- task_id 仍在 sprint。
- task.project_id 匹配。
- task 未 stale。
- task parent version 仍能读取。
- parent plan hash 匹配。
- recommendation report hash 匹配或 item 标记 stale。

对于 Context Pack：

- asset id 必须存在。
- asset 未 hidden。
- asset source hash 匹配。
- reference id 必须存在。
- reference 未 hidden。
- reference sha256 匹配。

对于 provider：

- provider config ready。
- prompt template enabled。
- payload 中 asset/reference refs 通过现有 snapshot/summary 函数。

## 8. API 设计

### 8.1 Queue 列表

```text
GET /api/projects/<project-id>/review-sprints/<sprint-id>/action-queues
```

返回：

```json
{
  "ok": true,
  "queues": [],
  "latest_queue": {}
}
```

### 8.2 创建 Queue

```text
POST /api/projects/<project-id>/review-sprints/<sprint-id>/action-queues
```

payload：

```json
{
  "name": "Local first pass",
  "refresh_recommendations": true,
  "settings": {
    "run_provider_actions": false,
    "run_context_pack_actions": true,
    "run_local_actions": true,
    "stop_on_failure": false
  }
}
```

行为：

- 如果 `refresh_recommendations=true`，先刷新 conflict + recommendations。
- 从最新 report 创建 queue。
- 不执行任何动作。

返回：

```json
{
  "ok": true,
  "queue": {},
  "summary": {}
}
```

### 8.3 Queue 详情

```text
GET /api/projects/<project-id>/review-sprints/<sprint-id>/action-queues/<queue-id>
```

返回：

```json
{
  "ok": true,
  "queue": {},
  "events": []
}
```

### 8.4 执行 Queue

```text
POST /api/projects/<project-id>/review-sprints/<sprint-id>/action-queues/<queue-id>/run
```

payload：

```json
{
  "item_ids": ["item-001", "item-003"],
  "include_provider": false,
  "rerun_failed": false,
  "stop_on_failure": false
}
```

行为：

- 只执行 selected item ids；为空则执行全部 eligible items。
- manual_required / blocked / informational 不执行。
- provider_safe 只有 `include_provider=true` 执行。
- 执行后返回完整 queue。

返回：

```json
{
  "ok": true,
  "queue": {},
  "results": [
    {
      "item_id": "item-001",
      "status": "completed",
      "result": {}
    }
  ]
}
```

建议 v3.2.0 先同步执行。动作通常是本地轻量操作，provider 候选生成也已有同步 API。若后续发现耗时过长，再在 v3.2.1 改后台 job。

### 8.5 归档 Queue

```text
POST /api/projects/<project-id>/review-sprints/<sprint-id>/action-queues/<queue-id>/archive
```

不删除文件，只设置：

```json
{
  "status": "archived",
  "archived_at": "..."
}
```

### 8.6 删除 Queue

v3.2.0 不建议做硬删除。

如果必须做，也必须：

- 只允许删除 `.musicforge/projects/<project-id>/review-sprints/<sprint-id>/action-queues/<queue-id>` 内路径。
- 使用 path boundary guard。
- 已执行过 action 的 queue 不允许 delete，只能 archive。

建议先不做。

## 9. Action 与现有 API 的对应关系

### 9.1 refresh_conflicts

等价于：

```text
POST /api/projects/<project-id>/review-sprints/<sprint-id>/conflicts/refresh
```

内部可直接调用已有 `_refresh_review_sprint_state(...)`。

### 9.2 refresh_recommendations

等价于：

```text
POST /api/projects/<project-id>/review-sprints/<sprint-id>/recommendations/refresh
```

内部可直接调用 `_refresh_review_sprint_recommendations(...)`。

### 9.3 save_recommended_context_pack

等价于：

```text
POST /api/projects/<project-id>/review-sprints/<sprint-id>/recommendations/<task-id>/context-pack
```

内部可复用 `_save_review_sprint_recommendation_context_pack(...)`，但注意：

- item result 写 `context_pack_id`。
- 如果 stale，item status = blocked，不要 failed。
- 如果 preview 无 refs，item status = skipped。

### 9.4 generate_local_candidates

可以复用已有 `_generate_review_sprint_local_candidates(...)`，但不要一次执行整个 sprint。

v3.2.0 更建议新增 task-scoped 内部 helper：

```python
_generate_review_task_local_candidates_for_queue(project_id, task_store, task, payload)
```

原因：

- Queue item 是 task 粒度。
- 如果调用 sprint-level generate，会影响多个 task，item result 不清晰。

如果开发为了省时间先复用 sprint-level generate，必须确保：

- item result 能标记实际 created candidate ids。
- 不会生成 queue 未选择 task 的候选。

更推荐做 task-level helper。

### 9.5 generate_provider_candidates

同理，不建议直接调用 sprint-level generate provider。

新增 task-scoped helper：

```python
_generate_review_task_provider_candidates_for_queue(
    project_id,
    task_store,
    task,
    payload,
)
```

要求：

- 使用现有 provider-review-candidates template。
- 使用 `_expand_context_pack_payload(...)` 后的 payload。
- provider usage 写入 task provider-usage。
- item result 写 provider usage summary，不写明文 key。
- asset/reference mark_used 正常执行。

### 9.6 refresh_decision_report

复用已有决策报告构建：


## 12. 安全与脱敏

### 12.1 不能泄露的内容

任何 queue / event / API / export 中都不能出现：

- `sk-...`
- GitHub token。
- Bearer token。
- api_key。
- provider raw response。
- 本机绝对路径：
  - `C:\Users\...`
  - `D:\...`
  - `\\server\share\...`
  - `/Users/...`
  - `/home/...`
- `.musicforge/provider.json` 具体内容。
- renderer soundfont 本机路径。

统一使用 `sanitize_metadata()` 和 `redact_sensitive_values()`。

### 12.2 路径安全

v3.2.0 不应该处理用户上传文件或任意 artifact 下载。

如果 queue result 需要记录 artifact：

- 只记录 logical id，例如 candidate_id、context_pack_id。
- 不记录绝对路径。
- 不提供新的文件下载入口。

### 12.3 Provider 安全

provider action：

- 必须复用现有 masked provider snapshot。
- usage report 只记录 token/cost summary。
- item result 里不能写 request body 全量。
- error 需要脱敏。

### 12.4 Stale guard

必须覆盖：

- 创建 queue 后，task parent SongPlan 改变。
- 创建 queue 后，asset hidden。
- 创建 queue 后，asset content/source hash 改变。
- 创建 queue 后，reference hidden。
- 创建 queue 后，reference sha256 改变。
- 创建 queue 后，recommendation report 被刷新。

推荐行为：

- 若 queue 的 recommendation report hash 与当前 report 不一致，queue 仍可查看，但执行 item 前 item blocked，提示 recreate queue。
- 也可以允许执行明确不依赖旧 report 的 `refresh_recommendations` item。

## 17. 风险清单

### 风险 1：Queue 执行绕过原有安全守卫

应对：

- 不重写 apply 逻辑。
- manual apply 不执行。
- local/provider generation 复用现有 ReviewTask helper。
- 每个 item 执行前 ensure current。

### 风险 2：Queue 创建后状态变化导致旧动作误执行

应对：

- 保存 recommendation report hash。
- 执行前比对当前 report hash。
- parent plan hash 不匹配则 blocked。
- asset/reference hash 不匹配则 blocked。

### 风险 3：Provider action 不小心默认执行

应对：

- provider item safety = provider_safe。
- run API 默认 include_provider=false。
- WebUI provider checkbox 默认 false。
- release-check 覆盖 provider 默认不执行。

### 风险 4：重复执行生成大量候选

应对：

- skip_existing_ready 默认 true。
- item completed 后默认不重跑。
- rerun_failed 单独开关。
- item result 记录 created_candidate_ids。

### 风险 5：文档和实际行为不一致

应对：

- README 只写已实现行为。
- CHANGELOG 清楚写“不自动 apply”。
- release-check 覆盖关键承诺。

## 18. v3.2.0 完成定义

v3.2.0 完成的标准不是“队列 UI 能看到”，而是下面闭环成立：

```text
用户创建 Sprint
  -> 刷新 Recommendations
  -> 创建 Action Queue
  -> 选择 safe actions
  -> 系统保存 Context Pack / 生成候选 / 刷新 Decision Report
  -> 用户看到执行结果
  -> 系统刷新 Sprint 状态
  -> 用户手动 apply candidate
  -> Compare / Export / Final Export 记录 queue summary
```

并且满足：

- apply 没有自动化。
- provider 没有默认自动调用。
- stale/hidden/source hash 被挡住。
- secret/path 不泄露。
- release-check 全绿。

做到这里，Review Sprint 就从“推荐层”进入“可控执行层”。后续 v3.3.0 才适合做 Sprint Dashboard / Metrics，把执行结果转成质量提升、候选命中率、provider 成本、采纳率等项目管理指标。

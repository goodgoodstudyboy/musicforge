# v4.7.0 Acceptance Analytics 验收数据分析与问题洞察施工图

日期：2026-05-20

当前稳定基线：v4.6.1

目标版本：v4.7.0

建议版本主题：Acceptance Analytics / Review Intelligence

---

## 1. 背景

MusicForge 已经走到一个很关键的阶段。

早期版本解决的是“能不能生成、能不能导出、能不能安全交付”。到 v4.x 后，系统已经有了完整的 Release / Distribution / Submission / Acceptance / Human Review 链路：

- v4.4.0 引入 Acceptance Suite，让开发可以批量生成代表性歌曲并做自动音乐体检。
- v4.4.1 收紧 synthetic auto-review 语义，明确它不是人工听审。
- v4.5.0 引入 Acceptance Profiles 和 Regression Songbook，把验收从随手测变成固定回归曲库。
- v4.5.1 强制 release-ready profile 覆盖完整 12 首内置 Regression Songbook，避免用 1 首歌冒充发布验收。
- v4.6.0 引入 Human Review Pack，让外部人工听审可以离线完成，再导入系统。
- v4.6.1 修复 Human Review Pack source hash 与 response import 的关键问题，确保 pack 不会因为自己的导入结果变 stale，同时拒绝 song_id mismatch。

现在的问题不再是“有没有验收”，而是：

- 多次验收之后，系统不知道整体质量趋势有没有变好。
- 开发人员不知道哪些 song_id 经常失败。
- 业务不知道哪些风格最弱，比如中文流行、说唱、电子、民谣、影视配乐等。
- 人工听审的 notes / tags / markers 没有被结构化汇总。
- Release Signoff 只能看某一次 suite 是否过关，看不到长期风险。
- ReviewTask、Human Review Pack、Acceptance Suite 之间已经有数据，但缺少一个分析层把它们串起来。

所以 v4.7.0 应该做一个大一点但仍然稳的跨步：把已经积累的验收数据变成可复用的质量情报。

---

## 2. v4.7.0 版本定位

v4.7.0 不做真实音乐生成能力的大跃迁，也不做自动修歌。它做的是验收分析层。

一句话定位：

> 把 Acceptance Suite、Human Review Pack、人工听审结果、音乐体检、ReviewTask 串成一个可追溯、可刷新、可导出、可用于后续修复冲刺的质量分析系统。

核心交付：

- Acceptance Analytics Report
- Songbook Heatmap
- Issue Taxonomy
- Reviewer / Review Source Summary
- Quality Trend
- Weakness Ranking
- Recommendation List
- Studio Analytics Dashboard
- CLI 离线分析入口
- Release Signoff 风险摘要接入
- release-check v4.7 smoke

---

## 3. v4.7.0 明确不做什么

这一版必须控制边界，避免把分析层做成又一个不可信的“自动评审 AI”。

本版不做：

- 不用 LLM 自动判断音乐好不好。
- 不调用外部 provider 做音乐质量评分。
- 不自动 apply edit。
- 不自动 close sprint。
- 不自动 signoff release。
- 不引入云端数据库。
- 不上传听审素材。
- 不做真实音频扒谱、混音、母带、vocal、MP3 转码。
- 不把 synthetic review 伪装成人工听审。
- 不把 Acceptance Analytics 作为强制发布 gate，默认只做 warning 和 evidence。

允许做：

- 基于已有结构化数据做 deterministic aggregation。
- 基于人工听审 tags / markers / status / rating / notes 做本地规则归类。
- 基于历史验收结果生成手动处理建议。
- 在 Studio 中展示趋势、弱项、建议。
- 将 analytics summary 写入 Release Export / Final Export / Signoff evidence。

---

## 4. 为什么 v4.7 应该先做 Analytics

v4.6 之后，有人可能会想直接进 v5，做真实音频、外部音乐模型、vocal 或混音。但现在还不适合。

原因：

1. 真实音频能力会显著增加不可控因素。
   如果没有验收分析层，后续真实音频质量波动很难定位。

2. 现在人工听审刚刚进入系统。
   如果不尽快把人工听审结构化，人工验收结果会散落在各个 suite、pack、case 里，后面越积越乱。

3. Regression Songbook 已经固定。
   现在正适合做 trend、heatmap、weakness ranking。再晚做会丢掉早期质量对比口径。

4. v4.8 可以基于 v4.7 的 recommendation 做 Acceptance-driven Fix Sprint。
   如果 v4.7 没有先把问题分析出来，v4.8 就只能凭感觉创建修复任务。

推荐路线：

```text
v4.7.0  Acceptance Analytics / Review Intelligence
v4.8.0  Acceptance-driven Fix Sprint / 验收问题驱动修复冲刺
v5.0.0  Real Audio / Vocal / Mixing Path
```

## 5. 核心用户故事

### 5.1 开发人员

开发人员希望知道：

- 最近几次验收是否变好了。
- 哪些内置 song_id 经常不通过。
- 哪些 issue 类型最多。
- 哪些风格在人工听审里评分最低。
- 哪些失败已经创建 ReviewTask，哪些还没有。
- 下一步应该优先修什么。

### 5.2 Reviewer

Reviewer 希望知道：

- release_candidate profile 是否稳定。
- 人工听审覆盖是否足够。
- synthetic review 是否被错误当成 release-ready 证据。
- Release Signoff 之前是否存在长期未处理的验收风险。

### 5.3 业务方

业务方希望看到：

- 当前音乐生成系统整体是否越来越稳定。
- 哪些风格已经可用。
- 哪些风格还不适合交付。
- 人工听审意见是否被系统记录并追踪。

## 6. 新增概念

### 6.1 Acceptance Analytics Report

验收分析报告。

它不是单个 suite 的报告，而是可以按 scope 聚合多个来源：

- global：全局验收数据
- project：某个 Project 相关验收
- release：某个 Release 绑定验收
- suite：单个 Acceptance Suite

### 6.2 Issue Taxonomy

问题分类体系。

把人工听审里的 tags、markers、notes 和自动体检 warning 归一到稳定类别。

建议内置类别：

```text
hook
melody
harmony
rhythm
arrangement
structure
lyrics
sound
mix
performance
rendering
metadata
workflow
other
```

注意：v4.7 的分类是 deterministic rule-based，不使用 LLM。

### 6.3 Songbook Heatmap

按 Regression Songbook 的 song_id 聚合：

- accepted count
- needs_fix count
- rejected count
- average rating
- latest status
- issue count
- recurring issue count
- manual review coverage
- synthetic only warning

### 6.4 Weakness Ranking

把 song_id、style、issue_type 排序，告诉开发优先修什么。

排序必须 deterministic，不能依赖随机分数。

### 6.5 Recommendation

分析报告产出的建议。

建议只做“下一步应该处理什么”，不能直接修改歌曲。

例如：

- create_review_task
- run_manual_review_again
- add_acceptance_case
- investigate_renderer
- create_fix_sprint_later
- block_release_until_manual_review

v4.7 可以允许用户显式点击 recommendation 创建 ReviewTask，但不能自动创建。

## 11. Issue Taxonomy 规则

### 11.1 输入优先级

分类来源按优先级处理：

1. structured tags
2. markers.label / markers.note
3. review status reason
4. health warnings
5. free-form notes

### 11.2 映射规则

建议先做一个小而稳定的词表。

```text
hook:
  hook, chorus, memorable, catchy, refrain, 副歌, 记忆点, 抓耳

melody:
  melody, tune, vocal line, bland melody, 旋律, 主旋律

harmony:
  chord, progression, key, modulation, harmony, 和弦, 调性

rhythm:
  rhythm, groove, beat, flow, timing, 节奏, 律动, 卡点

arrangement:
  arrangement, instrument, layer, build, drop, 编曲, 层次, 配器

structure:
  intro, verse, bridge, outro, length, transition, 结构, 段落, 转场

lyrics:
  lyric, words, rhyme, line, 歌词, 押韵, 文案

sound:
  sound, tone, timbre, synth, 声音, 音色

mix:
  mix, balance, loudness, clipping, muddy, 混音, 响度, 爆音

performance:
  performance, expression, human feel, 表现, 情绪, 人味

rendering:
  midi, wav, render, missing audio, soundfont, 渲染, 音频缺失

metadata:
  title, artist, credit, metadata, 元数据, 版权信息
```

### 11.3 规则约束

- 匹配必须大小写无关。
- notes 脱敏后再写入报告。
- 不要把完整人工 notes 原文大量复制进 analytics report。
- 多类别可同时命中。
- 没命中时归类为 other。
- tag 优先于文本猜测。

## 12. Scoring 设计

### 12.1 readiness_status

建议规则：

```text
blocked:
  rejected_count > 0
  or critical_issue_count > 0
  or release-ready suite missing manual coverage

needs_work:
  needs_fix_count > 0
  or open high severity recommendation exists

watch:
  accepted_count > 0 but manual coverage incomplete
  or recurring medium issues exist

ready:
  all latest release-ready cases accepted
  and manual coverage complete
  and no open high severity recommendations
```

### 12.2 weakness_score

建议 deterministic 分数：

```text
base = 0
+ 35 if latest_status == rejected
+ 25 if latest_status == needs_fix
+ 20 if average_rating < 3.0
+ 10 if average_rating >= 3.0 and average_rating < 4.0
+ min(issue_count * 4, 20)
+ min(recurring_issue_count * 8, 20)
+ 10 if manual_coverage_rate < 1.0
+ 10 if open_review_task_count > 0

weakness_score = min(base, 100)
```

排序：

1. weakness_score desc
2. latest_status severity desc
3. issue_count desc
4. song_id asc

### 12.3 trend

v4.7 不需要复杂统计模型。

按 suite generated_at / created_at 排序，记录：

- accepted_rate
- average_rating
- manual_coverage_rate
- issue_count
- readiness_status

趋势判断：

```text
improving:
  latest average_rating higher than previous and issue_count lower

regressing:
  latest average_rating lower or rejected_count increased

flat:
  otherwise
```

### 13.2 Scoped analytics

```text
GET /api/acceptance/suites/<suite_id>/analytics
POST /api/acceptance/suites/<suite_id>/analytics/refresh

POST /api/releases/<release_id>/acceptance-analytics/refresh

GET /api/projects/<project_id>/acceptance-analytics
POST /api/projects/<project_id>/acceptance-analytics/refresh
```

如果某些 scope 当前难以完整实现，可以先实现 global + suite + release，project scope 放到 v4.7.1，但文档和代码里要明确。

### 13.3 Report detail

```text
GET /api/acceptance/analytics/reports/<report_id>
```

### 13.4 Recommendation action

建议 v4.7 只做非常保守的 action：

```text
POST /api/acceptance/analytics/recommendations/<recommendation_id>/create-review-task
```

限制：

- 必须显式 POST。
- 必须有 project_id 或可解析到 Project。
- 不能自动 apply。
- 不能自动创建 candidate。
- 已存在相同 song_id + issue_type + open task 时返回 existing_task_id，不重复创建。
- 写入 analytics event。

如果没有稳定 Project 关联，返回 409。

## 14. CLI 设计

新增：

```text
python -m song_agent.cli acceptance-analytics
```

参数：

```text
--scope global|suite|release|project
--suite-id <id>
--release-id <id>
--project-id <id>
--json
--report-out <path>
--refresh
--fail-on blocked|needs_work|watch
```

示例：

```powershell
python -m song_agent.cli acceptance-analytics --scope global --refresh --json
python -m song_agent.cli acceptance-analytics --scope suite --suite-id suite-001 --report-out runs\analytics-suite-001.json
python -m song_agent.cli acceptance-analytics --scope release --release-id rel-001 --fail-on blocked
```

退出码：

- 0：report generated/read successfully and fail-on condition not triggered。
- 1：可预期错误，比如 suite 不存在、JSON 读取失败、schema 失败、fail-on 触发。
- 不应输出 traceback 给普通用户。

## 16. Release Signoff 集成

v4.7 不建议把 Analytics 作为强制 gate。

但 Release Signoff 应该记录 analytics evidence：

```json
{
  "acceptance_analytics": {
    "report_id": "analytics-...",
    "source_hash": "sha256:...",
    "readiness_status": "watch",
    "manual_coverage_rate": 1.0,
    "average_rating": 4.1,
    "top_weaknesses": [
      {
        "song_id": "rap_beat_001",
        "weakness_score": 62,
        "top_issues": ["rhythm", "hook"]
      }
    ],
    "warnings": []
  }
}
```

Signoff 行为建议：

- 没有 analytics report：warning，不阻断。
- analytics stale：warning，不阻断。
- readiness_status=blocked：正常 signoff 返回 409，除非 force signoff 且写明 override reason。
- readiness_status=needs_work：warning 或 409 需看当前 Release Signoff 已有 gate 规则。建议 v4.7 先 warning。

如果当前代码的 release signoff gate 已有严格机制，按现有风格接入，不要引入独立冲突规则。

## 18. 安全与脱敏

必须复用现有 redaction 工具。

重点检查：

- reviewer_name
- notes
- marker note
- source_note
- imported response payload
- suite title
- project title
- release title
- report-out path

Analytics report 内所有自由文本都要走 redaction。

限制：

- example_excerpt 最长 160 字符。
- recommendation.reason 最长 300 字符。
- warnings 文案不要包含绝对路径。
- source_summary 只记录 ID 和 hash，不记录原始文件路径。

## 19. Stale / Source Hash 设计

Analytics source hash 应该绑定事实来源，不绑定报告生成时间。

建议纳入：

- suite.json 内容摘要
- music-acceptance-report.json 内容摘要
- case review status / rating / review_mode / reviewer / tags / markers 摘要
- human review import response 摘要
- ReviewTask status 摘要
- Release acceptance binding 摘要

不纳入：

- analytics report generated_at
- analytics events.jsonl
- UI 展开状态
- report-out 文件路径

GET report 时应能返回：

```json
{
  "stale": true,
  "stale_reason": "source_changed"
}
```

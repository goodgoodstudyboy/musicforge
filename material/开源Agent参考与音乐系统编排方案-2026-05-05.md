# 开源 Agent 参考与音乐系统编排方案

日期：2026-05-05

## 结论

这个项目要做成一个完善系统，不能只做一个“prompt 转 MIDI”的脚本。更合理的方向是：以本地可验证的确定性流水线为内核，外层逐步接入多 agent、工具路由、质量评审、人工确认、断点续跑和本地/开源音乐工具。

参考开源 agent 后，建议采用这个总架构：

```text
用户 brief
  -> intent/brief normalizer
  -> planner graph
  -> specialist agents
  -> deterministic validators
  -> symbolic artifacts
  -> render tool adapters
  -> review/revision loop
  -> export package
```

第一阶段仍然坚持本地闭环：

```text
song_request.json -> song.json -> song.mid
```

但代码结构要提前给复杂编排留位置，避免以后重写。

## 调研过的开源项目和可吸收点

### LangGraph

地址：https://github.com/langchain-ai/langgraph

可吸收点：

- 状态图编排。
- durable execution。
- human-in-the-loop。
- checkpoint/resume。
- 短期工作记忆和长期持久记忆。
- 调试时能看 state transition。

对本项目的启发：

音乐生成天然是多阶段任务。不要让 LLM 一次性吐完整 MIDI，而是把歌词、结构、和声、旋律、节奏、编曲、校验、渲染拆成 graph nodes。每个节点输入/输出明确落盘。

建议：

- MVP 先不要强依赖 LangGraph。
- 先实现一个轻量 `RunState + pipeline steps + artifacts`。
- 等出现长任务、暂停恢复、人工插入修改，再评估是否接 LangGraph 或复刻其 checkpointer 思路。

### OpenAI Agents SDK

地址：https://github.com/openai/openai-agents-python

可吸收点：

- Agents as tools。
- Handoffs。
- Guardrails。
- Function tools。
- MCP server tool calling。
- Sessions。
- Human in the loop。
- Tracing。
- Sandbox/resumable execution。

对本项目的启发：

我们可以把 specialist agents 设计成可被 manager 调用的工具，而不是一开始就让多个 agent 自由聊天。

适合音乐项目的方式：

```text
ProducerAgent
  -> LyricAgent as tool
  -> HarmonyAgent as tool
  -> MelodyAgent as tool
  -> DrumAgent as tool
  -> CriticAgent as tool
```

最终用户只看到 ProducerAgent 的产物，不让内部 agent 直接面对用户。

### LlamaIndex AgentWorkflow

地址：https://docs.llamaindex.ai/en/stable/understanding/agent/multi_agent/

可吸收点：

- 多 specialist agent handoff。
- orchestrator agent 把 sub-agents 当工具。
- 自定义 planner。
- workflow state。
- streaming events。

对本项目的启发：

音乐生成可以支持三种编排层级：

```text
简单任务：固定 pipeline
中等任务：orchestrator 调 specialist tools
复杂任务：custom planner 先产出 plan，再按 plan 执行
```

这比“所有任务都多 agent 聊天”稳定。

### CrewAI

地址：https://github.com/crewaiinc/crewai

可吸收点：

- role-playing agents。
- Crews。
- Flows。
- 事件驱动 workflow。
- agent role/backstory/task 的声明式组织。

对本项目的启发：

它的 role/task 划分适合我们定义音乐岗位：

- Producer
- Lyricist
- Composer
- Arranger
- Drummer
- Bassist
- Mixing/Render Engineer
- Music Critic

但不建议 MVP 直接引入 CrewAI。原因是当前项目需要强确定性和低依赖，CrewAI 更适合后续实验多角色协作。

### Semantic Kernel / Microsoft Agent Framework

地址：https://github.com/microsoft/semantic-kernel

可吸收点：

- Sequential。
- Concurrent。
- Handoff。
- Group Chat。
- Magentic。
- 统一 orchestration interface。

对本项目的启发：

它给了一个很好的编排模式分类。我们可以在自己的系统里明确支持这些模式，而不必绑定 Semantic Kernel。

映射到音乐项目：

```text
Sequential：brief -> lyrics -> structure -> chords -> melody -> arrangement -> render
Concurrent：多个 agent 同时给旋律/和弦/鼓组方案
Handoff：从 composer handoff 到 arranger，再 handoff 到 renderer
Group Chat：风格策划会、审曲会
Magentic：复杂开放式任务，如“参考三首歌但避免抄袭，做一个完整 demo”
```

### PydanticAI

地址：https://github.com/pydantic/pydantic-ai

可吸收点：

- type-first agent。
- structured output。
- graph support。
- provider agnostic。
- observability。

对本项目的启发：

强类型是音乐 agent 的核心。`SongPlan`、`TrackPlan`、`NoteEvent`、`ChordEvent`、`DrumEvent` 都应该是严格数据合同。LLM 输出只能进入 schema，不能直接进入 renderer。

建议：

- 当前项目可以先继续用 dataclass，保持轻量。
- 如果 schema 复杂度上来，考虑引入 Pydantic，而不是直接引入 PydanticAI。

### Haystack

地址：https://github.com/deepset-ai/haystack

可吸收点：

- modular pipelines。
- routing。
- memory。
- retrieval。
- transparent architecture。
- agent workflows。

对本项目的启发：

后续如果要做风格库、参考曲分析、历史作品复用，可以借鉴 Haystack 的 context engineering 思路：

```text
style reference library
  -> retrieve relevant patterns
  -> inject into composer/arranger
  -> output structured plan
```

MVP 不需要 RAG，但目录和 state 要留出 `memory/`、`references/`、`reviews/`。

### DSPy

地址：https://github.com/stanfordnlp/dspy

可吸收点：

- programming, not prompting。
- modular AI systems。
- prompt/weight optimization。
- eval-driven improvement。

对本项目的启发：

等我们有一批生成样本和质量评分后，可以用 DSPy 思路优化 prompts。当前不需要引入，但要从一开始保留：

- prompt version。
- model version。
- input/output artifact。
- review scores。
- failure cases。

### MCP

地址：https://github.com/modelcontextprotocol/python-sdk

可吸收点：

- 工具协议标准化。
- tools/resources/prompts。
- stdio/SSE/streamable HTTP transport。
- structured tool output。
- MCP Inspector。

对本项目的启发：

后续本地音乐工具适合做成 MCP server 或 MCP-like tool adapter：

- MIDI renderer
- FluidSynth renderer
- MuseScore exporter
- music21 analyzer
- chord validator
- audio waveform analyzer
- DAW bridge

MVP 可以先用普通 Python function tools；等工具多了，再抽成 MCP。

### MusicAgent / Microsoft Muzic

地址：

- https://github.com/microsoft/muzic
- https://microsoft.github.io/muzic/musicagent/

可吸收点：

- 音乐领域 toolset。
- LLM planner。
- tool selector。
- task executor。
- response generator。
- 统一文本、MIDI、ABC、audio 等不同格式。

对本项目的启发：

这是最贴近本项目的参考。我们不要一上来做大而全工具集，但要采用它的核心思想：LLM 负责分析任务和选择工具，具体音乐处理由 deterministic tools 执行。

建议后续做：

```text
ToolRegistry
  -> SymbolicMidiTool
  -> FluidSynthTool
  -> MusicXMLTool
  -> ABCNotationTool
  -> AudioRenderTool
  -> ReferenceAnalysisTool
```

### AudioGPT

地址：https://github.com/AIGC-Audio/AudioGPT

可吸收点：

- speech/music/audio/talking-head 多工具集成。
- 以 LLM 统一调度多种音频任务。
- 可以把复杂音频任务拆到不同模型。

对本项目的启发：

不要把“音乐生成”限定为 MIDI。长期系统应支持：

- symbolic composition
- audio rendering
- vocal synthesis
- audio analysis
- sound effects
- stem separation

但 AudioGPT 依赖复杂，不能进 MVP。

### WavJourney

地址：https://github.com/Audio-AGI/WavJourney

可吸收点：

- compositional audio creation。
- 先生成 audio script，再调用不同音频模型。
- 适合故事化音频、旁白、音效、音乐组合。

对本项目的启发：

以后如果做“音乐 + 旁白 + 音效”的短视频/广播剧配乐，可以增加 `AudioScriptPlan`：

```text
scene timeline
  -> narration
  -> music cues
  -> sound effects
  -> render/mix
```

当前项目先专注 song/music，不引入。

### AudioCraft / MusicGen / JASCO

地址：https://github.com/facebookresearch/audiocraft

可吸收点：

- MusicGen 文本到音乐。
- JASCO 可用 chords、melodies、drum tracks 做条件。
- audio generation backend。

对本项目的启发：

我们当前路线是先做 symbolic MIDI。后续如果要接开源音频生成模型，最适合的方式不是替代 MIDI，而是把 `song.json/song.mid` 作为条件输入：

```text
SongPlan + MIDI guide
  -> audio model adapter
  -> wav
```

注意：模型权重许可证和本地 GPU 要单独评估。

### Amphion

地址：https://github.com/open-mmlab/Amphion

可吸收点：

- audio/music/speech generation toolkit。
- singing voice synthesis。
- voice conversion。
- text-to-audio。

对本项目的启发：

它更适合 0.5 之后的开放歌声后端调研。不要在 MIDI MVP 里引入。

### ChatMusician

地址：https://ezmonyi.github.io/ChatMusician/

可吸收点：

- ABC notation 作为纯文本音乐表示。
- LLM 直接理解/生成乐谱语言。

对本项目的启发：

`ABC` 可以成为 MIDI 之外的中间表示，尤其适合旋律草图、和弦 lead sheet、可读性调试。

建议后续增加：

```text
song.abc
song.musicxml
song.mid
```

### Text2MIDI

地址：https://github.com/AMAAI-Lab/Text2midi

可吸收点：

- 文本到 MIDI 的端到端模型路线。
- 说明用户确实需要 text-controlled symbolic music。

对本项目的启发：

可以作为后续模型 adapter，但不要替代我们的结构化 `SongPlan`。我们的优势应是可控、可审计、可编辑。

## 应该支持的编排模式

### 1. Fixed Sequential Pipeline

用途：MVP、本地验证、稳定交付。

```text
request
  -> normalize
  -> plan
  -> compose
  -> validate
  -> render
  -> package
```

特点：

- 最可控。
- 最好测试。
- 成本最低。
- 适合 CLI。

必须先实现。

### 2. State Graph

用途：复杂生成、断点续跑、人工插入。

```text
RunState
  brief
  lyrics
  structure
  harmony
  melody
  rhythm
  arrangement
  render
  review
```

每个节点只读写自己的 state slice，并落盘 artifact。

建议文件：

```text
song_agent/runtime.py
song_agent/state.py
song_agent/projectio.py
```

### 3. Manager with Agents as Tools

用途：模型接入后的主编排方式。

```text
ProducerAgent
  calls LyricAgent
  calls HarmonyAgent
  calls MelodyAgent
  calls ArrangementAgent
  calls CriticAgent
```

优点：

- manager 保持最终控制权。
- specialist 只处理边界清楚的小任务。
- 容易加 guardrails。

这应该是本项目最重要的多 agent 模式。

### 4. Handoff

用途：阶段所有权切换。

```text
BriefAgent -> ComposerAgent -> ArrangerAgent -> RenderEngineerAgent
```

适合用户在某个阶段做深入交互，比如“只修改副歌旋律”，这时可以 handoff 给 MelodyAgent。

MVP 不需要，但 Web Console 阶段需要。

### 5. Concurrent / Ensemble

用途：生成候选方案。

```text
HarmonyAgent A
HarmonyAgent B
HarmonyAgent C
  -> CriticAgent rank
  -> select best
```

适合：

- 多个 chord progression 候选。
- 多个 hook melody 候选。
- 多个 drum groove 候选。
- 多个 arrangement density 候选。

注意：

- 不能默认并发太多，会浪费 token。
- 只在关键 creative choice 上使用。

### 6. Evaluator-Optimizer Loop

用途：质量提升。

```text
generate
  -> validate
  -> critique
  -> revise
  -> validate
  -> stop when pass or max_rounds
```

本地 validator 负责硬规则，CriticAgent 负责软评价：

- 风格是否匹配。
- 主歌/副歌是否有对比。
- 旋律是否可唱。
- bass 是否贴合和声。
- drums 是否符合风格。

### 7. Group Chat / Creative Room

用途：高层创意讨论。

```text
Producer
Lyricist
Composer
Arranger
Critic
```

适合生成前的“策划会”，不适合每个音符都群聊。

输出必须是结构化共识：

```text
style brief
form
energy curve
instrumentation
risk notes
```

### 8. Planner-Executor

用途：开放式任务。

```text
Planner
  -> task list
Executor
  -> runs tools
Verifier
  -> checks artifacts
```

适合用户说：

```text
做一首适合短视频开头的 45 秒 city pop instrumental，
要有雨夜感，适合循环，副歌像霓虹灯亮起来。
```

Planner 先决定要不要歌词、要不要循环结构、要不要只出 instrumental。

### 9. Tool Router / Tool Selector

用途：接入多种音乐工具后自动选择。

```text
if target == midi:
  use MidiRenderer
if target == wav and soundfont exists:
  use FluidSynth
if target == score:
  use MusicXML/MuseScore
if target == abc:
  use ABC exporter
```

这部分借鉴 MusicAgent。

### 10. Human-in-the-loop

用途：关键节点确认。

建议人工确认点：

- brief normalization 后。
- song structure 后。
- 第一版 MIDI 后。
- critic 判定失败后。
- 接入真实 audio/vocal 模型前。

CLI 可以先通过 `--stop-after plan`、`--resume` 实现；Web Console 再做按钮。

### 11. Durable Execution / Resume

用途：长任务、中断恢复、避免重复花费。

每个 step 完成后落盘：

```text
runs/<run-id>/
  data/request.json
  data/brief.json
  data/song-plan.json
  renders/song.mid
  logs/events.jsonl
  data/run-summary.json
```

后续恢复时从已有 artifact 继续，不重复调用模型。

### 12. Blackboard / Shared State

用途：多 agent 共享事实。

不要让每个 agent 各自记忆。统一用 `RunState`：

```text
style_bible
section_map
chord_map
motif_bank
instrument_registry
review_notes
```

所有 agent 读写 state，所有写入都要 schema 化。

### 13. Batch Orchestration

用途：批量生成多个歌案。

参考 NovelForge 批量模式，后续可支持：

```text
material/song_proposals.csv
  -> batch
  -> queued jobs
  -> max_concurrent
  -> runs/<song-title-run-id>
```

第一阶段不做，但目录结构要兼容。

## 分阶段落地

### V0.1 Local Graph MVP

目标：

```text
song_request.json -> runs/demo/data/song-plan.json -> runs/demo/renders/song.mid
```

做：

- `RunState`
- `projectio`
- `SongPlan` validator
- deterministic composer
- MIDI renderer
- CLI `--out runs/demo`

不做：

- LLM。
- Web。
- audio model。
- group chat。

### V0.2 Provider + Structured Agent

目标：接入 OpenAI-compatible provider，但仍然可本地 fallback。

做：

- `openai_compatible.py`
- provider config/env。
- prompt versioning。
- `SongPlan.from_dict()` 硬校验。
- JSON 修复最多 1 到 2 轮。
- 失败产物落盘。

编排方式：

```text
Manager as code
  -> LLM structured output
  -> validator
```

### V0.3 Specialist Agents + Review Loop

目标：多角色开始发挥作用。

做：

- HarmonyAgent。
- MelodyAgent。
- ArrangementAgent。
- CriticAgent。
- Evaluator-Optimizer loop。
- 候选方案 ranking。

编排方式：

```text
ProducerAgent
  -> agents as tools
  -> CriticAgent
  -> RevisionAgent
```

### V0.4 Tool Registry + MCP-ready

目标：工具生态化。

做：

- `ToolRegistry`
- tool schema。
- render tools。
- analysis tools。
- 可选 MCP server。

编排方式：

```text
ToolRouter
  -> local Python tools
  -> optional MCP tools
```

### V0.5 Human Console + Batch

目标：可操作系统，而不是纯 CLI。

做：

- 本地 Web Console。
- run 列表。
- 播放 MIDI/audio。
- 修改 brief/structure。
- regenerate section。
- batch CSV。

编排方式：

```text
human-in-the-loop
durable execution
batch scheduler
```

### V0.6 Open Music Backends

目标：接入更强音乐能力。

候选：

- AudioCraft / MusicGen / JASCO。
- Amphion。
- ChatMusician / ABC。
- Text2MIDI。
- FluidSynth / MuseScore / REAPER。

原则：

- 只作为 adapter。
- 不替代 `SongPlan`。
- 所有输出必须可追溯到输入 artifact。

## 关键设计原则

### Artifact-first

每个节点必须有明确产物，不靠聊天历史当状态。

```text
data/brief.json
data/structure.json
data/harmony.json
data/song-plan.json
renders/song.mid
reviews/song-review.json
```

### Deterministic boundary

LLM 可以负责创意，但不能负责最终低层文件正确性。

LLM 可做：

- 风格理解。
- 歌词。
- 和声建议。
- 旋律意图。
- 编曲建议。
- revision suggestion。

确定性代码必须做：

- schema validation。
- beat/bar validation。
- note range validation。
- MIDI serialization。
- file layout。
- resume。

### Local-first

所有核心验收必须无网络可跑：

```powershell
python -m song_agent.cli examples\song_request.json --out runs\demo
python -m pytest -q
```

### Model-optional

真实模型只能提高质量，不能决定系统是否可运行。

### Tool isolation

渲染器、音频模型、DAW 控制都应该是工具 adapter，不应该散落在 pipeline 里。

### Reviewable outputs

每次生成必须留下：

- 输入。
- prompt。
- model config。
- 中间 JSON。
- validator 结果。
- MIDI 文件。
- review。
- summary。

## 不建议现在做的事

- 不要一开始引入 CrewAI/LangGraph/PydanticAI 全家桶。
- 不要让多个 agent 自由聊天后直接生成 MIDI。
- 不要直接接 AudioCraft/Amphion 作为 MVP。
- 不要把 Suno/Udio/Mureka 当核心后端。
- 不要跳过 `SongPlan`，直接让模型输出 MIDI。
- 不要先做 Web Console。
- 不要在没有 artifact/run state 的情况下做 batch。

## 给开发的新任务拆解

### 第一组：系统骨架

1. 新增 `song_agent/state.py`：定义 `RunState`、`StepStatus`、`ArtifactRef`。
2. 新增 `song_agent/projectio.py`：统一写 `runs/<run-id>/data`、`renders`、`logs`。
3. CLI 改为默认输出到 `runs/`，并保留用户 `--out`。

### 第二组：本地 graph runner

1. 新增 `song_agent/runtime.py`。
2. 支持固定 step list。
3. 每个 step 执行前后写 `events.jsonl`。
4. 支持 `--resume` 的最小版本：已有 artifact 则跳过对应 step。

### 第三组：音乐 schema 和 validator

1. 补 `SongPlan.from_dict/to_dict`。
2. 增加 `ChordEvent` 或明确 chords 表达。
3. 增加 `validate_song_plan`。
4. 增加测试覆盖非法 note、非法 bar、缺轨、越界。

### 第四组：deterministic composer

1. 固定生成 intro/verse/chorus/outro。
2. 固定 chord progression。
3. 生成 melody/chords/bass/drums。
4. 输出 `data/song-plan.json`。

### 第五组：MIDI renderer

1. 用 `mido` 或自写最小 MIDI writer。
2. melody/chords/bass/drums 分轨。
3. 写 tempo。
4. 写 GM drums。
5. 输出 `renders/song.mid`。

### 第六组：provider 和 agent 扩展

1. 增加 OpenAI-compatible provider。
2. 增加 structured JSON prompt。
3. 增加 `ProducerAgent` 作为 manager。
4. specialist agents 先用函数边界定义，不急着多模型。

### 第七组：review loop

1. 增加本地 review rules。
2. 增加 CriticAgent prompt。
3. 支持最多 N 轮 revise。
4. 每轮产物落盘为 `song-plan.v1.json`、`song-plan.v2.json`。

## 最终目标形态

最终这个项目应该像 NovelForge 自动写小说一样，形成自动作曲流水线：

```text
用户给一个音乐需求
  -> 系统补全 brief
  -> 多角色策划
  -> 结构化创作
  -> 本地校验
  -> MIDI/乐谱/音频渲染
  -> 自动审曲
  -> 可人工修改
  -> 可断点续跑
  -> 可批量生产
```

但落地顺序必须保持克制：

```text
本地可验证 MIDI
  -> provider structured output
  -> specialist agents
  -> review/revision
  -> tool registry/MCP
  -> Web/batch/audio models
```

这个顺序可以保证项目从第一阶段开始就是可运行、可测试、可审计的，而不是一个依赖模型运气的 demo。

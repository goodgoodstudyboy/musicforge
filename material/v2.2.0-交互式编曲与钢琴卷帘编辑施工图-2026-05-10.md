# MusicForge v2.2.0 施工图：交互式编曲与钢琴卷帘编辑

> 基线版本：v2.1.2  
> 规划日期：2026-05-10  
> 执行原则：所有功能先本地验证，通过测试后分阶段 commit，并及时 push 到 GitHub。  
> 范围判断：v2.2.0 不做完整 DAW、不做实时合成器、不做录音、不做音频扒谱。v2.2.0 的目标是把已经稳定的 Visual Editor Patch Engine 变成真正好用的可视化编曲界面。

---

## 1. 背景

MusicForge 现在已经从“自动生成一首 MIDI”推进到“项目化创作 + 版本管理 + 可视化编辑”。

截至 v2.1.2，核心能力是：

- Project 有版本树、变体、质量门禁、最终导出。
- Visual Editor 能对 Project Version 创建本地 patch preview。
- Editor preview 可以 Apply as Version，不覆盖父版本。
- v2.0.1 已修复 apply 不信任 preview `song-plan.json`。
- v2.1.1 已修复 section/track ID 在同一 patch 内漂移的问题。
- v2.1.2 已修复 note ID 在 track/section 结构变化后漂移的问题。
- release-check 已覆盖 v2.1 structure editor 主链路。

这说明底层 patch engine 已经可以承接更自然的交互了。

当前最大短板不再是后端能不能改，而是 Studio Editor 仍然偏表单化：

- section 是表格。
- track 是表格。
- note 是下拉框 + JSON 输入。
- range 编辑靠手写 beat 范围。
- 用户很难直观看到“这一段、这一轨、这个音符”。
- 用户很难连续做小修小改。

所以 v2.2.0 应该进入“交互式编曲编辑体验”。

---

## 2. v2.2.0 一句话目标

> 在 Studio 的 Project Editor 中新增 Arranger Timeline 和 Piano Roll，让用户可以通过点击、选择、拖动、微调、预览、撤销/重做来编辑 SongPlan，并继续使用现有 patch preview/apply/version 审计链路。

---

## 3. 为什么现在做这个

### 3.1 业务原因

自动生成音乐之后，用户一定会进入“局部调整”：

- 副歌再短一点。
- verse 能量低一点。
- melody 某几个音往上走。
- bass 提前半拍。
- drum 某一段密度减一点。
- chorus 复制一遍做 final chorus。

这些都不适合长期通过 JSON 输入完成。

### 3.2 工程原因

v2.1.2 已经把最危险的 identity 漂移收住了。现在做可视化层，风险比之前低很多：

- section/track/note ID 可以稳定引用。
- patch preview 可以本地验证。
- apply 只创建 child version。
- preview history 可审计。
- release-check 有基础链路。

### 3.3 产品节奏原因

如果现在直接上 arranger solver、MIDI import merge 或复杂 provider 自动编曲，会继续堆后端复杂度，但用户仍然缺少一个能看、能听、能修的工作台。

先把人工编辑工作台做好，后续自动建议、AI 编曲、MIDI 导入都可以落在同一个编辑界面里。

---

## 4. v2.2.0 做什么

v2.2.0 做 6 件事：

1. 新增非持久化 Editor Draft API，用于实时预览 patch 结果，不污染 editor preview history。
2. 新增 Editor View Model，把 SongPlan 转成适合前端渲染的 arranger / piano-roll 数据。
3. Studio Project Editor 新增 Arranger Timeline。
4. Studio Project Editor 新增 Piano Roll。
5. Studio Project Editor 新增本地 undo / redo / patch queue 操作。
6. release-check 增加 v2.2 interactive editor smoke。

---

## 5. v2.2.0 不做什么

本版不要膨胀。

明确不做：

- 不做浏览器实时合成器。
- 不做 WebAudio 混音台。
- 不做录音。
- 不做 MP3/FLAC 导入。
- 不做音频转 MIDI。
- 不做复杂 MIDI import merge。
- 不做 arranger constraint solver。
- 不做 provider 自动补全编辑建议。
- 不做多人协作。
- 不做云端存储。
- 不做完整 DAW 级别快捷键系统。

这些可以放到 v2.3+。

## 6. 用户故事

### 6.1 打开版本并看到结构

用户进入 Project -> Editor：

1. 选择 Parent Version。
2. 点击 Open。
3. 页面展示：
   - Song 基本信息。
   - section timeline。
   - track lanes。
   - 当前选中 track 的 piano roll。
   - patch queue。
   - Preview / Apply 控件。

### 6.2 编辑 section

用户可以：

- 点击 section block 选中 section。
- 通过按钮新增、复制、删除、移动、resize section。
- resize 后能看到后续 section 起点变化。
- notes 根据 policy 变化。
- patch queue 记录操作。

### 6.3 编辑 note

用户可以：

- 在 track 列表里选中 track。
- 在 piano roll 里看到 notes。
- 点击 note 选中。
- 对选中 note 执行：
  - move left/right。
  - transpose up/down。
  - quantize。
  - velocity scale。
  - delete。
  - 单音 update pitch/start/duration/velocity。
- 不需要手写 note_id。

### 6.4 预览并应用

用户可以：

- 点击 Draft Refresh，非持久化查看当前 patch 的结果。
- 点击 Preview，生成持久化 preview、MIDI。
- 试听或下载 MIDI。
- 点击 Apply as Version，生成 child Project Version。
- 之后 Project Compare / Export / Final Export 能看到 editor metadata。

### 6.5 撤销/重做

用户可以：

- Undo 最近一次操作。
- Redo 被撤销的操作。
- Clear Patch 清空草稿。
- 不影响已保存 preview 和已应用版本。

## 7. 总体技术方案

### 7.1 保持低依赖

当前项目是标准库 HTTP server + 单页 Studio UI。v2.2.0 继续保持：

- 不引入前端框架。
- 不引入构建工具。
- 不引入数据库。
- 不引入实时音频依赖。

前端建议用：

- HTML/CSS。
- 原生 JavaScript。
- SVG 或 CSS grid 渲染 timeline / piano roll。

优先推荐 SVG：

- 坐标稳定。
- note rectangle 容易点击。
- section block 容易定位。
- 适合 Playwright 检查 DOM。

### 7.2 核心原则

可视化层不直接改 SongPlan 文件。

所有编辑仍然走：

```text
editor-state -> patch draft -> draft API -> preview API -> apply as version
```

不允许前端绕过 patch engine 自己写 song-plan。

### 8.2 新增 Editor Draft API

现在 `POST /editor-preview` 会持久化 preview。v2.2.0 需要非持久化 draft。

新增：

```text
POST /api/projects/<project-id>/versions/<version-id>/editor-draft
```

请求：

```json
{
  "patch": {
    "schema_version": 1,
    "base_plan_hash": "...",
    "label": "Manual editor patch",
    "operations": []
  },
  "include_view": true,
  "include_diff": true
}
```

响应：

```json
{
  "ok": true,
  "project_id": "project-001",
  "version_id": "v001",
  "base_plan_hash": "...",
  "operation_count": 3,
  "summary": {
    "operation_count": 3,
    "changed_sections": ["verse"],
    "changed_tracks": ["melody"],
    "warnings": []
  },
  "view": {},
  "diff": {},
  "validator": {},
  "quality": {}
}
```

要求：

- 不创建 `.musicforge/projects/<id>/editor-previews/preview-*`。
- 不写 `runs/`。
- 不渲染 MIDI。
- 不改变 Project。
- 使用 `apply_editor_patch()` 计算。
- patch stale 返回 `409`。
- patch validation error 返回 `400`。

### 8.3 新增 Editor Diff Builder

建议新增：

```python
def build_editor_diff(parent: SongPlan, edited: SongPlan, patch: EditorPatch) -> dict:
    ...
```

最小字段：

```json
{
  "sections": {
    "added": [],
    "removed": [],
    "changed": [],
    "moved": []
  },
  "tracks": {
    "added": [],
    "removed": [],
    "renamed": [],
    "changed": []
  },
  "notes": {
    "added": 0,
    "removed": 0,
    "changed": 0,
    "moved": 0
  },
  "warnings": []
}
```

注意：

- 不要求做到 DAW 级 diff。
- 但要能让 Studio 显示“这次 patch 大概改了什么”。
- 这个 diff 也可以复用到 preview summary。

### 8.4 可选 API：Editor View

可以新增：

```text
GET /api/projects/<project-id>/versions/<version-id>/editor-view
```

也可以让 `editor-state` 继续作为基础 API。

建议新增 `editor-view`，原因：

- `editor-state` 更偏 patch identity。
- `editor-view` 更偏 UI 渲染。
- 后续 piano roll 可继续扩展 view，而不破坏 editor-state 语义。

## 9. 前端 Studio 方案

### 9.1 Project Editor 总体布局

把当前表单式布局升级为工作台式布局。

建议结构：

```text
Project Editor
├── top toolbar
│   ├── parent version select
│   ├── Open
│   ├── Preview
│   ├── Apply as Version
│   ├── Undo
│   ├── Redo
│   ├── Clear
│   └── Preview History
├── arranger timeline
│   ├── bar ruler
│   ├── section blocks
│   └── track overview lanes
├── editor split
│   ├── track list
│   └── piano roll
├── inspector
│   ├── selected section / track / note fields
│   ├── operation buttons
│   └── patch queue
└── draft / preview result
```

不要做营销式页面。它是工具界面，要紧凑、清晰、能重复操作。

### 9.2 Arranger Timeline

Timeline 用于操作 section。

显示：

- bar ruler。
- section block。
- section name。
- bars。
- chords 简短摘要。
- selected state。
- changed state。

交互：

- 点击 section：选中。
- Add Section：使用 inspector 表单。
- Duplicate Section：复制当前 section。
- Delete Section：删除当前 section。
- Move Left / Move Right：生成 `move_section`。
- Resize -1 / +1 bars：生成 `resize_section`。

v2.2.0 可以先不做真正鼠标拖拽。为了稳定，第一版可以用按钮微调：

- Move Left。
- Move Right。
- Shorten。
- Lengthen。

如果开发有余力，再做 drag。

原因：

- v2.1.2 刚修完 identity。
- 鼠标 drag 容易引入坐标和边界问题。
- 按钮微调更容易测试。

### 9.3 Piano Roll

Piano Roll 用于操作 note。

显示：

- 横轴 beat/bar。
- 纵轴 pitch。
- note rectangle。
- velocity 可以用透明度或小条表达。
- selected note 高亮。
- range selection 可以后置。

交互优先级：

P1：

- 选中 track。
- 显示该 track 所有 notes。
- 点击 note 选中。
- inspector 显示 pitch/start/duration/velocity。
- Update Note 生成 `update_note`。
- Delete Note 生成 `delete_notes`。
- Nudge Left/Right 生成 `move_notes`。
- Pitch Up/Down 生成 `transpose_notes`。

P2：

- Quantize selected/range。
- Scale Velocity selected/range。
- Add Note at current beat/pitch。
- 多选 notes。

P3：

- 鼠标拖动 note 改 start。
- 拖动边缘改 duration。
- 框选 range。

v2.2.0 的最低验收必须做到 P1，P2 尽量做，P3 可以作为增强项。

### 9.4 Patch Queue

当前 `projectEditorPatch` 已经是数组。

v2.2.0 要把它可视化：

- 每条 operation 一行。
- 显示操作类型、目标、摘要。
- 支持删除某一条 operation。
- 支持 Undo / Redo。
- 支持 Clear Patch。
- 显示 operation_count。

Undo / Redo 设计：

```text
projectEditorPatch = []
projectEditorRedo = []

add operation:
  patch.push(op)
  redo.clear()

undo:
  redo.push(patch.pop())

redo:
  patch.push(redo.pop())
```

不需要 server 持久化 undo/redo。

### 9.5 Draft Refresh

新增 Draft Refresh 逻辑：

- 用户每次点操作后，可以选择自动 draft 或手动 draft。
- v2.2.0 建议先手动 Draft Refresh，避免频繁请求。
- Draft 成功后刷新 arranger/piano roll 到 edited state。
- Draft 失败时显示错误，不清空 patch。

可选：

- 如果 patch 操作数少于 20，可以 debounce 500ms 自动 draft。
- 超过 20 个操作，改为手动。

v2.2.0 尽量复用现有 ops：

- `set_section_chords`
- `set_section_lyrics`
- `set_track_instrument`
- `add_section`
- `duplicate_section`
- `delete_section`
- `resize_section`
- `move_section`
- `add_track`
- `duplicate_track`
- `delete_track`
- `rename_track`
- `add_note`
- `update_note`
- `delete_notes`
- `move_notes`
- `transpose_notes`
- `quantize_notes`

不要为了 UI 方便直接新增一堆后端 op。

```json
}
```

但建议先用单音 `update_note.duration_beats` 完成 P1。

## 11. 安全和边界

### 11.1 不信任前端坐标

前端传来的 beat/pitch/duration 仍必须通过 patch engine 校验。

不要因为 UI 控件限制了范围，就省略后端校验。

### 11.2 Draft API 不写入持久目录

Draft API 不应该产生：

- preview 目录。
- runs 目录。
- MIDI。
- WAV。
- project event。

否则用户拖动或微调会制造大量垃圾。

### 11.3 Preview 才持久化

只有用户点击 Preview 时才写：

```text
.musicforge/projects/<project-id>/editor-previews/preview-*/
```

### 11.4 Apply 仍必须重算

Apply 继续使用 v2.0.1 规则：

- 不信任 preview `song-plan.json`。
- 从 parent plan + patch 重新计算 result。
- 再写 child version。

### 11.5 Identity 继续保护

新增 UI 和 Draft API 不能绕过 v2.1.2 的 identity 修复。

必须补测试：

- section 插入后 note 仍能选中。
- track 删除后后续 track 的 note 仍能选中。
- note update 后同一个 note_id 继续 move。
- note delete 后同一个 note_id 再操作会清晰失败。

## 17. 风险和处理

### 17.1 UI 复杂度风险

风险：

- 一次性做 drag、multi-select、range selection 容易失控。

处理：

- v2.2.0 先做按钮式微调和点击选择。
- drag 放增强项。

### 17.2 坐标和 beat 映射风险

风险：

- bar/beat 坐标换算错误会导致编辑错位。

处理：

- 所有前端生成的 beat 都通过后端 patch 校验。
- 单元测试覆盖 beats_per_bar。
- Piano roll 显示总 beat 和 bar ruler。

### 17.3 Preview 垃圾风险

风险：

- 用户每次小改都创建 preview，目录爆炸。

处理：

- Draft API 非持久化。
- Preview 按钮才持久化。

### 17.4 重复 note identity 风险

风险：

- 两个 note 完全同 pitch/start/duration/velocity 时，note key 可能重复。

处理：

- `_note_ids_by_key()` 已经用 list 管理同 key 多 ID。
- v2.2.0 需要新增重复 note identity 回归测试。

### 17.5 Studio 性能风险

风险：

- 一首歌 notes 太多时 SVG 卡顿。

处理：

- 沿用现有 editor note/track 上限。
- Piano roll 初版只显示当前 track。
- 单 track notes 超过阈值时显示 warning。

# v7.9.0 Release Portfolio Governance Attestation Transparency Acknowledgement 透明度日志外部确认回执闭环施工图

> 本文是给开发执行的 v7.9.0 施工图。当前稳定基线是 v7.8.1。v7.8.1 已修复 Transparency Feed verifier 只校验自洽而不校验语义的问题：`transparency_event_semantics_match` 会从 `current_public_state + source` 反推 expected events，`transparency_notice_semantics_match` 会从 package state/events 反推 expected notices，阻断 event / notice 全量重签伪造。

v7.9.0 的目标是把 v7.8 的公开证明透明度日志继续推进为“外部可确认、可导入、可验证、可追溯”的回执闭环。

一句话：

> v7.9.0 要让外部 reviewer / 合作方拿到 Transparency Feed / Change Notices 后，可以提交一个绑定当前 Transparency ZIP 的确认回执；系统能离线验证这个回执确实针对当前透明度包，记录 public-safe acknowledgement evidence，并在 needs_changes / rejected 时生成后续 Change Request 草稿，但不自动修改 Registry / Portal / Transparency / Accepted Evidence。

---

## 1. 背景

当前 v7 公开证明链路已经走到：

- v7.0：Final Board，组合治理最终委员会签核。
- v7.1：Evidence Vault，长期证据保险库。
- v7.2：Public Attestation，公开证明证书包。
- v7.3：Attestation Registry，公开证明登记册。
- v7.4：Attestation Portal Snapshot，静态门户快照。
- v7.5：Release Check Verification Matrix，发布验证矩阵。
- v7.6：Portal Review Response，外部审查响应导入。
- v7.7：Accepted Evidence，接受外部响应后生成公开摘要证据。
- v7.8：Transparency Feed，公开证明透明度日志和变更通知。
- v7.8.1：Transparency Feed 语义验证收紧，阻断全量重签伪造。

现在系统已经能做到：

```text
Evidence Vault
  -> Public Attestation
  -> Registry
  -> Portal
  -> Portal Review Pack / Response
  -> Accepted Evidence
  -> Transparency Feed
  -> Change Notices
  -> Transparency ZIP
  -> Offline Verifier
```

但 v7.8 做完后还有一个明显缺口：

1. Transparency Feed 能告诉外部方“公开证明状态发生了什么”，但还不能记录外部方是否已经看过、接受、质疑这些变更。
2. Portal Review Response 绑定的是 Portal review pack，不是 Transparency Feed / Change Notice。
3. Accepted Evidence 证明外部已经接受 Portal/Registry/Attestation 链路，但不证明外部已确认后续透明度变更。
4. 如果 Registry current entry 被 supersede，或 Accepted Evidence 被 archived，业务方需要一个外部确认记录来证明“对方已知晓这次透明度变化”。
5. 当前系统缺少针对 Transparency Feed 的 review pack、response import、acknowledgement evidence、offline verifier、Change Request draft。

v7.9 要补的是：

```text
Transparency Feed / Change Notices
  -> Transparency Acknowledgement Pack
  -> External Acknowledgement Response
  -> Response Verification
  -> Acknowledgement Evidence
  -> optional Change Request Draft
  -> Export / ZIP / Offline Verifier
```

这个层不是替代 v7.6 的 Portal Review Response，也不是替代 v7.7 的 Accepted Evidence。它专门处理“公开证明透明度日志和变更通知是否被外部确认”。

## 2. 业务定位

### 2.1 给谁用

v7.9 主要面向：

- 外部 reviewer：确认自己已经查看某个 Transparency Feed / Change Notice。
- 合作方 / 发行方：确认公开证明是否有变更，并回传 accepted / needs_changes / rejected。
- 业务负责人：留存“对方已经知道证明状态变化”的证据。
- 法务 / 审计：检查透明度变更是否已通知、是否有回执、回执是否绑定当前包。
- 开发 / reviewer：离线验证 Transparency acknowledgement 是否可伪造、可重放、可错绑。

### 2.2 解决什么问题

典型流程：

```text
1. 内部完成 v7.8 Transparency Feed。
2. Transparency Feed 显示：
   - Registry current entry changed
   - Accepted Evidence changed
   - Portal snapshot rebuilt
3. 内部把 Transparency Acknowledgement Pack 发给外部 reviewer。
4. 外部 reviewer 离线检查 pack，填写 response：
   - accepted：已确认当前公开证明变更。
   - needs_changes：发现某条 notice 表述有问题，需要修正。
   - rejected：不接受当前透明度状态，需要重新生成或撤销。
5. 系统导入 response。
6. 系统验证 response 绑定：
   - review_pack_id
   - review_pack_source_hash
   - transparency_zip_sha256
   - transparency_manifest_hash
   - transparency_feed_source_hash
   - notice_ids / event_ids
7. accepted 时生成 public-safe acknowledgement evidence。
8. needs_changes / rejected 时生成本地 Change Request draft，但不自动 approve/reset/signoff。
```

### 2.3 版本定位

v7.9 是 v7 公开证明链路的“外部确认层”。

它的核心价值不是生成更多 ZIP，而是把外部确认行为绑定到当前 Transparency Feed：

- 防止裸 JSON response 被系统自动补 source binding。
- 防止旧 Transparency ZIP 的 response 被重放到新 Transparency ZIP。
- 防止只改 response status 就伪装 accepted。
- 防止 response 声称确认 notices，但 notices 实际不属于当前 feed。
- 防止 acknowledgement evidence 只信公开 summary，而没有 verification sidecar。

## 3. v7.9.0 目标

新增 Release Portfolio Governance Attestation Transparency Acknowledgement。

核心能力：

1. 从当前 Transparency Feed / Transparency ZIP 生成外部确认包。
2. 确认包包含 public-safe feed summary、notice summary、event summary、verification summary，不嵌套任何 ZIP。
3. 新增外部 acknowledgement response schema。
4. 支持从 base64 导入 response JSON / response ZIP。
5. 导入时拒绝 `source_path` / `local_path` / `file_path`。
6. response 必须显式携带 source binding，不允许 importer 自动补齐。
7. response 必须绑定当前 acknowledgement pack 和当前 Transparency ZIP。
8. accepted response 可生成 acknowledgement evidence。
9. needs_changes / rejected response 可生成 Change Request draft。
10. acknowledgement evidence 可 export / zip / verify。
11. Registry / Portal / Transparency 可选接入 acknowledgement summary，但不能因 acknowledgement 失败而自动修改旧证据。
12. Studio 增加 Transparency Acknowledgement 面板。
13. CLI / API 接入。
14. release-check matrix 增加 `v79.attestation_transparency_acknowledgement_smoke`。
15. README / CHANGELOG / version bump 到 `7.9.0`。

---

## 4. 非目标

v7.9 不做：

- 不做在线签名平台。
- 不做邮件发送。
- 不做 webhook。
- 不自动 publish / revoke / supersede Registry entry。
- 不自动 archive Accepted Evidence。
- 不自动 refresh / rebuild Transparency Feed。
- 不自动 approve Change Request。
- 不自动 reset Final Board / Registry / Portal / Transparency immutability。
- 不把 reviewer 私密 notes 原文公开到 Portal。
- 不把 response attachments 放进公开 evidence，最多记录 public-safe摘要。
- 不接入真实电子签名服务。
- 不要求外部 reviewer 使用 MusicForge 客户端。
- 不把完整 Transparency ZIP 嵌套进 acknowledgement evidence ZIP。
- 不把 `.musicforge/`、provider key、本机路径、GitHub token、SoundFont path、renderer path 写入任何公开包。

## 7. 状态机

### 7.1 Pack 状态

```text
missing
  -> refreshed
  -> exported
  -> zipped
  -> verified
  -> stale
```

stale 条件：

- Transparency Feed source hash 改变。
- Transparency ZIP sha256 改变。
- Transparency verification report 改变。
- current public state hash 改变。
- profile 改变。

### 7.2 Response 状态

```text
imported
  -> verified
  -> accepted
  -> needs_changes
  -> rejected
  -> stale
  -> archived
```

`review_status` 来自外部 response。`verification_status` 来自本地 verifier。

只有：

```text
review_status == accepted
verification_status == passed
stale == false
```

才允许生成 acknowledgement evidence。

### 7.3 Evidence 状态

```text
missing
  -> current
  -> stale
  -> archived
```

stale 条件：

- response stale。
- pack source changed。
- Transparency source changed。
- response integrity mismatch。
- external response status 不是 accepted。

```json
{
  "portfolio_id": "...",

  "transparency": {
    "zip_sha256": "...",
    "zip_size_bytes": 123,
    "manifest_hash": "...",
    "feed_source_hash": "...",
    "feed_integrity_hash": "...",
    "verification_status": "passed",
    "event_semantics_status": "passed",
    "notice_semantics_status": "passed"
  },
  "public_state": {
    "public_state_hash": "...",
    "current_entry_id": "...",
    "current_certificate_id": "...",
    "portal_manifest_hash": "...",
    "accepted_evidence_manifest_hash": "..."
  },
  "notices": [
    {
      "notice_id": "...",
      "notice_type": "...",
      "integrity_hash": "..."
    }
  ],
  "events": [
    {
      "event_id": "...",
      "event_type": "...",
      "event_hash": "..."
    }
  ]
}
```

`pack.source_hash = stable_hash(pack_source)`。

### 8.2 Response Hash

`response_hash` 必须排除自身字段：

```text
response_hash
integrity_hash
imported_at
internal_status
```

导入时如果外部 response 已带 `response_hash`，可以校验；如果没带，本地可以计算内部 `integrity_hash`，但不能补 source binding。

### 8.3 Evidence Source

Evidence source：

```json
{
  "response_id": "...",
  "response_integrity_hash": "...",
  "review_pack_id": "...",
  "review_pack_source_hash": "...",
  "transparency_zip_sha256": "...",
  "transparency_manifest_hash": "...",
  "transparency_feed_source_hash": "...",
  "review_status": "accepted",
  "reviewed_notice_ids": ["..."],
  "reviewed_event_ids": ["..."]
}
```

Evidence verifier 必须从 response record 和 pack source 反查这些字段。

必须检查：

- `nested/` 大小写变体。
- nested `.zip` 大小写变体。

- 总 uncompressed size 上限。
- 单 entry size 上限。

检查项建议：


### 12.2 Manifest 绑定

必须检查：

- manifest files 全部存在。
- ZIP entry 不允许超出 manifest files + sidecar allowlist。
- 每个 file hash / size 匹配。
- manifest package_type 正确。
- manifest source_hash 匹配 pack/evidence source。
- sidecar source_hash 匹配主文档 source。

检查项建议：

```text
ack_manifest_package_type
ack_manifest_files_match_zip
ack_manifest_file_hashes
ack_manifest_source_hash
ack_manifest_sidecar_binding
```

### 12.3 Pack Source 绑定

必须检查：

- pack.source_hash == stable_hash(pack_source)。
- pack source 中的 Transparency verification summary status 为 passed。
- `transparency_event_semantics_match` passed。
- `transparency_notice_semantics_match` passed。
- pack 中 notices/events 与 sidecar summary 一致。
- pack 中 `response-template.json` 带齐 source binding 字段。

检查项建议：

```text
ack_pack_source_hash
ack_pack_transparency_verification_passed
ack_pack_event_notice_binding
ack_pack_response_template_binding
```

### 12.4 Response 绑定

导入时和 evidence verifier 都必须检查：

- `review_pack_id` 存在。
- `review_pack_source_hash` 存在。
- `transparency_zip_sha256` 存在。
- `transparency_manifest_hash` 存在。
- `transparency_feed_source_hash` 存在。
- response 中这些字段与当前 pack source 完全一致。
- `reviewed_notice_ids` 是当前 pack notices 子集。
- `reviewed_event_ids` 是当前 pack events 子集。
- accepted response 至少 review 了所有 warning / critical notices。
- needs_changes / rejected 必须至少包含 concern。
- response 不包含敏感值。

检查项建议：

```text

ack_response_pack_binding
ack_response_transparency_binding
ack_response_notice_subset
ack_response_event_subset
ack_response_status_allowed
ack_response_redaction_scan
```

### 12.5 Evidence 绑定

Evidence verifier 必须检查：

- evidence.source 反查 response record。
- response status accepted。
- response verification passed。
- evidence source hash 匹配。
- public_summary 不含敏感字段。
- evidence manifest 和 evidence document 一致。
- evidence 不能只信 public_summary。

检查项建议：

```text
ack_evidence_source_hash
ack_evidence_response_binding
ack_evidence_response_accepted
ack_evidence_public_summary_redaction
```

### 12.6 全量重签伪造防护

必须加入两类回归：

1. response full-resign：
   - 修改 response status 为 accepted。
   - 重算 response_hash / evidence / manifest。
   - 不修改 pack source。
   - verifier 必须 failed。

2. evidence full-resign：
   - 修改 evidence public_summary 中 reviewer / status。
   - 重算 evidence integrity / manifest。
   - response record 不一致。
   - verifier 必须 failed。

检查项建议：

```text
ack_response_semantics_match
ack_evidence_semantics_match
```

## 13. 安全边界

### 13.1 绝不自动补 source binding

这是 P1。

导入外部 response 时，不能像早期某些流程一样“帮外部 JSON 补 review_pack_id / source_hash”。

如果缺字段：

```text
review_pack_id
review_pack_source_hash
transparency_zip_sha256
transparency_manifest_hash
transparency_feed_source_hash
```

必须直接 400。

### 13.2 stale response 不能创建 evidence

如果导入后 pack 变了：

- response 可以留存。
- response summary 标 stale。
- 不允许 refresh evidence。
- 不允许 create Change Request。
- 不允许 export evidence。

### 13.3 rejected / needs_changes 不等于 accepted

`needs_changes` / `rejected` 只允许创建 Change Request draft。

不能：

- 生成 accepted acknowledgement evidence。
- 更新 Registry current。
- 更新 Portal accepted evidence summary。
- 更新 Transparency accepted summary。

### 13.4 public-safe

进入 pack/evidence/ZIP 的字段必须经过 redaction：

- `sk-...`
- GitHub token。
- Bearer token。
- Windows path。
- UNC path。
- local_path。
- source_path。
- raw provider response。
- renderer path。
- SoundFont path。
- `.musicforge` internal path。

### 13.5 不嵌套 ZIP

Acknowledgement pack/evidence ZIP 只能放 JSON/TXT/HTML-free README。

不允许嵌套：

- Transparency ZIP。
- Portal ZIP。
- Registry ZIP。
- Accepted Evidence ZIP。
- Evidence Vault ZIP。

## 21. 攻击复现清单

开发必须自己写脚本或测试复现以下攻击，并确认 failed：

### 21.1 Bare JSON 补绑定攻击

输入 response：

```json
  "review_status": "accepted",

}
```

预期：

```text

missing source binding
```

### 21.2 Old Transparency replay

用旧 Transparency ZIP 生成 response，刷新新 Transparency 后导入。

预期：

```text
verification failed 或 stale=true
cannot refresh evidence
```

### 21.3 Notice subset forgery

response 声称 review 了不存在的 notice：

```json
"reviewed_notice_ids": ["att-trans-notice-999999"]
```

预期 failed。

### 21.4 Accepted status forgery

把 `needs_changes` response 改成 `accepted`，重算 response hash。

预期 failed，因为 response semantics 与 imported/original/evidence binding 不匹配。

### 21.5 Evidence summary forgery

把 evidence public summary 改成 accepted reviewer，重算 evidence/manifest。

预期 failed，因为无法反查 response。

### 21.6 Manifest spoof

往 ZIP 增加 extra file，并改 manifest.zip.entries。

预期 failed，因为 verifier 不信 `manifest.zip.entries` 放行文件。

### 21.7 Backslash entry

手工构造：

```text
data\evil.json
```

预期 failed。

### 21.8 Case-insensitive internal path

手工构造：

```text
.MusicForge/internal.json
```

预期 failed。

# v5.4.0 Mastering QA 发行级母带响度与音频一致性施工图

日期：2026-05-29

角色定位：reviewer / planner

当前稳定基线：v5.3.1

目标版本：v5.4.0

---

## 1. 背景

v5.0.0 到 v5.3.1 已经完成了真实音频和人工修复闭环：

- v5.0.0：真实 WAV 基线、Audio Artifact、Release Audio QA。
- v5.1.0：逐曲人工音频听审证据。
- v5.2.0 / v5.2.1：Mix State、Mix Patch、Stem Health、当前 mix evidence 可信度。
- v5.3.0 / v5.3.1：Audio Revision Workbench，marker -> issue -> candidate -> A/B review -> apply -> recheck -> closeout。

系统现在已经能回答：

> 每首歌是否有真实 WAV？是否有人听过？听审发现的问题是否进入修复闭环？修复后是否重新听审？

但发行前还缺一个关键层：

> 这些歌作为一个 Release，响度、峰值、头尾静音、曲间一致性、音频格式和母带证据是否达到交付标准？

当前 `audio_health.py` 已有单个 WAV 的基础指标：

- duration
- sample rate
- channels
- bit depth
- peak
- RMS
- clipping ratio
- leading / trailing silence

但它还不是发行级 Mastering QA：

- 没有 Release Mastering Profile。
- 没有平台目标响度策略。
- 没有 track-to-track loudness consistency。
- 没有 album / EP 的曲间响度差异 gate。
- 没有 fade in / fade out / head-tail silence 策略。
- 没有母带候选和母带版本证据。
- `verify-release` 不能离线校验 mastering evidence。

v5.4.0 要补的就是这一层：**Mastering QA，发行级母带响度与音频一致性**。

---

## 2. 版本定位

v5.4.0 不是专业母带工作站，不做完整 DSP 插件链。

它要做的是一个本地 deterministic 的发行级音频验收层：

1. 定义 Mastering Profile。
2. 对 Release 每首 track 生成 Mastering Analysis。
3. 计算 release-level consistency report。
4. 支持 deterministic normalize / fade / trim 生成 Mastered Candidate。
5. 所有处理必须写入可审计的 Mastering Plan / Mastering Manifest。
6. 人工确认 mastered audio 后才能进入 Release Signoff。
7. Release Export / ZIP 带 mastering evidence。
8. `verify-release` 可离线验证 mastering evidence。

一句话：

> v5.3 解决“听审指出问题后怎么修”，v5.4 解决“修完后是否像一个可发行的音频产品”。

---

## 3. 明确不做

v5.4.0 不做以下内容：

- 不做专业插件链：EQ、compressor、limiter、multiband、reverb。
- 不做 AI 自动母带。
- 不做 LUFS-I 精准 EBU R128 / ITU-R BS.1770 完整实现。
- 不做真实 True Peak oversampling。
- 不做 MP3 / AAC / FLAC 多格式编码，这建议放 v5.5。
- 不做外部 DAW 工程导出。
- 不做自动替代人工听审。
- 不做自动签核。

v5.4 可以实现“近似 loudness hint / RMS-based loudness proxy”，但必须明确命名为 `loudness_proxy_db` 或 `rms_loudness_hint`，不能伪装成标准 LUFS。

---

## 4. 为什么现在做

现在系统已经能生成、听审、修复，但发行交付还会遇到这些实际问题：

- 同一个 EP 里第一首明显大，第二首明显小。
- 某首 clipping warning 被人工忽略，但发行包没有统一说明。
- 头部静音 5 秒，平台试听体验差。
- 尾部静音太长。
- 修复 candidate 通过了，但 release 级音频一致性没重新计算。
- 分发包里有 WAV，但不知道是不是经过最终 mastering pass。
- 用户不知道“当前 Release ZIP 是否可以直接给平台或客户”。

v5.4 的价值是把这些问题从主观感觉变成可审计的本地报告和 gate。

---

## 5. 总体目标

v5.4.0 完成后，系统应该支持：

1. 创建 / 管理 Mastering Profile。
2. 对 Release 执行 Mastering QA。
3. 每首 track 生成 Mastering Track Analysis。
4. Release 生成整体 Mastering Summary。
5. 检查：
   - format consistency
   - sample rate / bit depth / channel
   - duration
   - peak
   - RMS / loudness proxy
   - clipping
   - silence head/tail
   - track-to-track loudness delta
   - album average loudness proxy
6. 可选生成 Mastered Candidate：
   - normalize gain
   - fade in
   - fade out
   - trim leading silence
   - trim trailing silence
7. Mastered Candidate 必须人工 audio review 后才能设为 selected。
8. selected mastered output 可进入 Release Export。
9. Release Signoff 可要求 `require_mastering_qa=true`。
10. `verify-release --require-mastering` 可离线验证。

## 6. 核心概念

### 6.1 Mastering Profile

Mastering Profile 是发行目标音频标准。

建议落盘：

`.musicforge/mastering-profiles/<profile-id>/profile.json`

字段建议：

```json
{
  "schema_version": 1,
  "profile_id": "mprof-000001",
  "name": "Streaming Balanced",
  "target_type": "streaming",
  "sample_rate": 44100,
  "channels": 2,
  "bit_depth": 16,
  "target_loudness_proxy_db": -14.0,
  "loudness_tolerance_db": 2.0,
  "max_peak_dbfs": -1.0,
  "max_clipping_ratio": 0.001,
  "max_track_loudness_delta_db": 3.0,
  "max_leading_silence_seconds": 2.0,
  "max_trailing_silence_seconds": 4.0,
  "min_duration_seconds": 30.0,
  "max_duration_seconds": 600.0,
  "allow_warning_signoff": false,
  "created_at": "...",
  "updated_at": "...",
  "integrity_hash": "..."
}
```

内置 profiles：

- `streaming_balanced`
- `podcast_music_bed`
- `demo_review`
- `album_consistency`

注意：`target_loudness_proxy_db` 不是 LUFS。文案必须明确是 proxy。

### 6.2 Mastering Analysis

每次对 Release 跑 mastering QA，生成一个 analysis。

建议落盘：

`.musicforge/releases/<release-id>/mastering/analysis.json`

字段建议：

```json
{
  "schema_version": 1,
  "analysis_id": "mqa-000001",
  "release_id": "release-000001",
  "profile_id": "mprof-000001",
  "status": "failed",
  "generated_at": "...",
  "source_hash": "...",
  "tracks": [],
  "summary": {
    "track_count": 2,
    "passed_count": 1,
    "warning_count": 1,
    "failed_count": 0,
    "average_loudness_proxy_db": -15.2,
    "max_track_loudness_delta_db": 2.8,
    "max_peak_dbfs": -1.4,
    "clipping_track_count": 0
  },
  "blockers": [],
  "warnings": [],
  "recommendations": [],
  "integrity_hash": "..."
}
```

字段建议：

```json
  "project_id": "project-000001",
  "version_id": "v000004",
  "source_wav_sha256": "...",
  "format": {
    "sample_rate": 44100,
    "channels": 2,
    "bit_depth": 16,
    "duration_seconds": 184.2

    "peak": 0.84,

    "trailing_silence_seconds": 1.8
  },

  "warnings": [],
  "failures": []

```

### 6.4 Mastering Plan

Mastering Plan 是“要怎么处理”的可审计方案。

建议落盘：

`.musicforge/releases/<release-id>/mastering/plan.json`

字段建议：

```json
{
  "schema_version": 1,
  "plan_id": "mplan-000001",
  "release_id": "release-000001",
  "profile_id": "mprof-000001",
  "source_analysis_hash": "...",
  "actions": [
    {
      "track_id": "track-000001",
      "action": "gain_adjust",
      "gain_db": -1.5,
      "reason": "peak_margin"
    },
    {
      "track_id": "track-000001",
      "action": "fade_out",
      "duration_seconds": 2.0
    }
  ],
  "status": "draft",
  "integrity_hash": "..."
}
```

v5.4 允许 actions：

- `gain_adjust`
- `fade_in`
- `fade_out`
- `trim_leading_silence`
- `trim_trailing_silence`

不允许 actions：

- `compress`
- `limit`
- `eq`
- `reverb`
- `stereo_widen`

### 6.5 Mastered Candidate

Mastered Candidate 是处理后的音频候选。

建议落盘：

`.musicforge/releases/<release-id>/mastering/candidates/<candidate-id>/`

结构：

```text
candidates/
  mcand-000001/
    candidate.json
    plan.json
    tracks/
      track-000001.wav
      track-000002.wav
    analysis-after.json
```

字段：

- candidate_id
- release_id
- profile_id
- source_analysis_hash
- source_release_hash
- source_track_wav_hashes
- plan_hash
- output_track_hashes
- after_analysis_hash
- manual_review
- selected
- applied
- integrity_hash

## 8. Audio Metrics 计算要求

当前 `audio_health.py` 已有 peak / RMS。v5.4 可扩展如下：

### 8.1 peak_dbfs

```text
peak_dbfs = 20 * log10(max(peak, epsilon))
```

### 8.2 rms_dbfs / loudness_proxy_db

```text
rms_dbfs = 20 * log10(max(rms, epsilon))
loudness_proxy_db = rms_dbfs
```

必须命名为 `loudness_proxy_db`，不能叫 `lufs`。

### 8.3 dynamic range hint

简单定义：

```text
dynamic_range_proxy_db = peak_dbfs - rms_dbfs
```

用于 warning，不作为硬门禁。

### 8.4 silence trimming analysis

复用当前 leading / trailing silence 逻辑，但 v5.4 要支持 profile 级阈值。

### 8.5 release consistency

Release 级：

```text
max_track_loudness_delta_db = max(loudness_proxy_db) - min(loudness_proxy_db)
average_loudness_proxy_db = average(track loudness_proxy_db)
```

如果 delta 超过 profile 上限，Mastering QA warning 或 failed。

## 9. Mastering QA Gate

每首 track 检查：

- WAV 存在。
- WAV hash 与 Audio Artifact 当前一致。
- format 符合 profile。
- duration 在范围内。
- peak 不超过 profile `max_peak_dbfs`。
- clipping ratio 不超过 profile。
- leading silence 不超过 profile。
- trailing silence 不超过 profile。
- loudness proxy 在目标容差内。

Release 检查：

- 所有 track 都有 analysis。
- track-to-track loudness delta 不超过 profile。
- selected mastered candidate 如存在，必须 current。
- selected mastered candidate 必须 manual accepted。
- analysis / plan / candidate integrity ok。
- no redaction issue。

状态：

- `passed`
- `warning`
- `failed`

Signoff gate：

```json
{
  "require_mastering_qa": true,
  "mastering_profile_id": "mprof-000001"
}
```

规则：

- `failed` 不能签核。
- `warning` 默认不能签核，除非 profile `allow_warning_signoff=true` 或 signoff `force=true` 且写 reason。
- stale analysis 不能 force。
- tampered analysis / candidate 不能 force。

## 10. Mastered Candidate 处理规则

v5.4 可以实现本地 PCM 处理，不需要外部工具：

### 10.1 gain_adjust

对 PCM samples 乘以 gain：

```text
linear_gain = 10 ** (gain_db / 20)
```

必须防止溢出：

- 超过 sample range 时 clamp。
- 如果 clamp ratio 超阈值，candidate after_analysis failed。

### 10.2 fade_in / fade_out

线性 fade 即可：

- fade_in：前 N 秒从 0 到 1。
- fade_out：最后 N 秒从 1 到 0。

### 10.3 trim silence

只允许根据 analysis 的 leading/trailing silence 建议剪裁。

约束：

- 不允许把 track 剪到小于 profile `min_duration_seconds`。
- trim 后必须重新 analysis。
- trim 动作必须写入 plan。

### 10.4 不直接覆盖源文件

Mastered Candidate 先写入 candidate 目录。

只有用户 select + manual accepted 后，Release Export 才使用 mastered WAV。

不要覆盖 Project Final Export 的 `song.wav`。

## 16. 安全要求

### 16.1 Path guard

Mastering candidate 的 WAV 下载必须只允许：

`.musicforge/releases/<release-id>/mastering/candidates/<candidate-id>/tracks/<track-id>.wav`

禁止：

- absolute path
- `..`
- backslash
- UNC path
- symlink
- 指向其他 release / candidate 的文件

### 16.2 Source hash

Mastering Analysis source hash 绑定：

- release identity
- track order
- track project/version
- current Final Export manifest hash
- current `song.wav` hash
- current Audio Artifact hash
- current Audio Revision summary hash
- profile hash

只要上游变更，analysis stale。

### 16.3 Candidate source hash

Candidate source hash 绑定：

- analysis hash
- plan hash
- source track WAV hashes
- profile hash

只要上游变更，candidate stale。

### 16.4 Signed guard

Release 已签核后：

- 不能 analyze。
- 不能 plan。
- 不能 render candidate。
- 不能 review candidate。
- 不能 select candidate。
- 不能 reset mastering。

必须先 reset Release signoff。

### 16.5 Redaction

以下字段必须脱敏：

- profile notes
- analysis warnings
- recommendations
- candidate review notes
- override reason
- export summary

## 18. 分阶段实施

## 19. 验收标准

v5.4.0 完成后，开发必须证明：

1. Release 能选择 Mastering Profile。
2. Release Mastering Analysis 能分析每首 WAV。
3. Analysis 能检测 peak / clipping / silence / loudness proxy / track delta。
4. Plan 能生成 deterministic gain/fade/trim 动作。
5. Candidate 能生成真实 WAV，不是伪造占位音频。
6. Candidate after-analysis 可信。
7. Candidate 需要 manual review 才能 select。
8. Release Export 使用 selected mastered WAV。
9. Release Signoff `require_mastering_qa=true` passed。
10. ZIP 离线 `verify-release --require-mastering` passed。
11. 篡改 mastering summary / mastered WAV / candidate hash 后 verifier failed。
12. 上游 Audio Revision / Release Track / WAV 变化后 mastering analysis stale，signoff 409。

## 20. 风险清单

### 风险 1：把 loudness proxy 当 LUFS

禁止。所有字段和 UI 必须写 `loudness_proxy_db`，README 说明它不是标准 LUFS。

### 风险 2：候选处理破坏音频

gain/fade/trim 都要重新跑 analysis-after。clipping / duration failed 不能 select。

### 风险 3：Release Export 没用 mastered WAV

如果 selected mastered candidate 存在，export 必须使用 mastered WAV；否则 signoff 和 verifier 的证据没有意义。

### 风险 4：签核后重新生成 mastering

必须 409。Release signoff 后所有 mastering mutation 都要 blocked。

### 风险 5：stale analysis 被复用

source hash 必须绑定当前 WAV 和 Audio Revision summary。修复后重新 apply 版本，mastering 必须 stale。

### 风险 6：路径污染

candidate WAV download / export 都必须 path guard。

### 风险 7：测试用 fake WAV 误导业务

单测可以 fake WAV，但 release-check 必须明确验证：

- candidate WAV 是经过 mastering pipeline 处理后的输出。
- output hash 与 source hash 不同。
- analysis-after 指向 output hash。

---

## 21. 给开发的执行准则

1. 先实现 analysis，不要先做 UI。
2. 所有对象先定义 source_hash / integrity_hash。
3. 处理音频前先把 path guard 写好。
4. Candidate 不能直接覆盖原 release track WAV。
5. Signoff 和 verifier 必须同时做，不能只做在线 gate。
6. 每个 Phase 至少一个 commit。
7. 每个 Phase 完成后跑定向测试。
8. 发布前必须跑 full release-check。

# v6.6.0 Release Portfolio Governance Action Queue 组合治理动作队列与风险闭环施工图

日期：2026-06-05

当前稳定基线：v6.5.0

目标版本：v6.6.0

角色定位：reviewer / planner 交给开发执行

---

## 1. 背景

v6.5.0 已经完成 Release Portfolio Audit：

- 能跨多个 Release 生成 readiness ranking。
- 能生成 portfolio risk score。
- 能生成 trend report。
- 能生成 risk register。
- 能生成 deterministic recommendations。
- 能导出 Portfolio Audit ZIP。
- 能在外部目录离线验证 Portfolio Audit ZIP。
- 能通过 strict verifier 抓 duplicate entry、危险路径、反斜杠 entry、manifest spoof、redaction、missing reviewer/audit/archive evidence。

这让系统从“单个 Release 可审计”升级到了“多个 Release 可观察”。

但 v6.5.0 仍然停留在观察层：

- 它能告诉你哪些 Release 缺 Reviewer Pack。
- 它能告诉你哪些 Release 缺 Audit Verification。
- 它能告诉你哪些 Release 缺 Archive Verification。
- 它能告诉你哪些 Change Request 反复出现。
- 它能告诉你哪些 runbook 手工动作多。
- 它能告诉你哪些风险需要治理。

但是它不能把这些风险组织成一批可执行的治理动作。

所以 v6.6.0 应该往前迈一步：把 Portfolio Audit 的 risk register / recommendations 转成 **Portfolio Governance Action Queue**。

这版的核心不是“自动修复一切”，而是：

- 安全动作可以自动执行。
- 高风险动作只生成 manual_required。
- 每个动作都有来源、hash、状态、结果和审计记录。
- 队列能导出和离线验证。
- 队列不能绕过 Release / Distribution / Submission / Operations 的既有签核保护。

这会让系统从“发现组合风险”进入“治理组合风险”。

---

## 2. 一句话目标

v6.6.0 要实现：

> 从 Release Portfolio Audit 的风险和建议生成组合级 Governance Action Queue，让开发能按队列安全执行 refresh/export/verify 类动作，并把 signoff、reset、提交、人工判断等高风险事项明确列为 manual_required，形成可审计的治理闭环。

---

## 3. 当前缺口

v6.5.0 能回答：

- 风险在哪里？
- 哪些 Release 缺证据？
- 哪些趋势不好？
- 哪些 Release 不适合外部审查？

但不能回答：

- 这些风险下一步该按什么顺序处理？
- 哪些动作能安全自动跑？
- 哪些动作必须人工确认？
- 一轮治理动作执行后，哪些风险被减少？
- 治理动作是否改变了底层 Release evidence？
- 治理队列能不能被外部 reviewer 验证？

v6.6.0 要补这个缺口。

---

## 4. 非目标

v6.6.0 不做这些事：

- 不自动 signoff。
- 不自动 reset signoff。
- 不自动 approve Change Request。
- 不自动提交外部平台。
- 不自动 mark accepted。
- 不自动写人工听审。
- 不自动调用 provider。
- 不自动上传文件。
- 不自动生成真实音乐修改。
- 不跨 workspace 聚合。
- 不引入数据库。
- 不引入第三方依赖。

v6.6.0 只执行安全、可重复、可审计的本地治理动作。

## 9. Action 类型

### 9.1 Safe Actions

允许自动执行的动作必须满足：

- 本地。
- deterministic。
- 不写外部平台。
- 不写人工 review。
- 不 approve。
- 不 signoff。
- 不 reset。
- 不删除证据。
- 不绕过 signed/archived guard。

建议第一版支持：

```text
portfolio.refresh
portfolio.export
portfolio.zip
portfolio.verify

reviewer_pack.refresh
reviewer_pack.export
reviewer_pack.zip
reviewer_pack.verify

operations_audit.refresh
operations_audit.export
operations_audit.zip
operations_audit.verify

operations_archive.verify
runbook.refresh_report
```

说明：

- `reviewer_pack.*`、`operations_audit.*` 这类动作会更新 Release operations evidence，因此执行后 Portfolio Audit 很可能 stale。
- 这是预期行为。
- Queue 必须记录 `post_portfolio_refresh_required=true`。
- 可提供 `--refresh-portfolio-after-safe-actions`，但默认不强制。

### 9.2 Manual Required Actions

这些只生成待办，不自动执行：

```text
operations_signoff.sign
operations_signoff.reset
change_request.approve
change_request.review
release.archive
submission.record
submission.accept
human_review.perform
provider.call
external_upload.perform
process_rule.promote
portfolio_policy.change
```

### 9.3 Blocked Actions

这些动作如果遇到只读状态，要 blocked：

```text
reviewer_pack.export on signed/archived if underlying store forbids it
operations_audit.export on signed/archived if underlying store forbids it
operations_archive.verify when archive package missing
portfolio.export when source portfolio report stale before queue run
portfolio.zip when source portfolio report stale before queue run
```

不要吞掉底层 409。Queue item 要记录明确 message。

## 10. Queue 生成规则

Queue 从 Portfolio Audit 的：

- risk register
- recommendations
- release summaries
- trend findings
- gates

生成 action plan。

### 10.1 reviewer_pack_missing / reviewer_pack_required

生成：

```text
reviewer_pack.refresh
reviewer_pack.export
reviewer_pack.zip
reviewer_pack.verify
```

如果 Release 状态或底层 store 不允许 export，则该 item blocked。

### 10.2 audit_verification_missing / audit_required

生成：

```text
operations_audit.refresh
operations_audit.export
operations_audit.zip
operations_audit.verify
```

### 10.3 archive_verification_missing / archive_required

第一版只生成：

```text
operations_archive.verify
```

如果 archive export 不存在：

```text
manual_required: operations_archive.export_or_signoff_review
```

不要自动创建 Archive 或 Signoff。

### 10.4 change_control / repeated_change_requests

生成：

```text
manual_required: change_request.review
manual_required: process_rule_candidate.review
```

不要自动 approve / reset / promote。

### 10.5 manual_bottleneck

生成：

```text
manual_required: runbook_policy.review
```

如果只是 runbook summary stale，可以生成：

```text
runbook.refresh_report
```

### 10.6 integrity failed / redaction leak

生成：

```text
manual_required: evidence_integrity.rebuild_review
blocked: unsafe_to_auto_fix
```

不自动重建 corrupted evidence。

## 11. Queue Source Hash 和 Stale 规则

Queue 创建时必须绑定：

- portfolio_id
- portfolio report hash
- portfolio source hash
- trend report hash
- risk register hash
- action plan hash

Queue run 前必须检查：

- linked Portfolio Audit report 存在。
- report integrity OK。
- trend integrity OK。
- risk register integrity OK。
- queue.source_hash 与当前 portfolio source 匹配。
- Portfolio Audit report 不 stale。

如果不满足：

```text
409: Portfolio Governance Queue source is stale. Refresh Portfolio Audit and create a new queue.
```

### 11.1 执行中 source 变化的处理

安全动作可能会更新底层 Release evidence。

例如：

- reviewer_pack.verify 写入 verification report。
- operations_audit.verify 写入 verification report。

这会让 Portfolio Audit stale。

这是治理动作的正常结果，不应该让 queue 中途失败。

正确行为：

1. run-safe 开始前检查 source current。
2. 记录 `pre_source_hash`。
3. 执行 safe actions。
4. 记录 `post_source_hash`。
5. 如果 post_source_hash 与 pre_source_hash 不同：
   - `post_portfolio_refresh_required=true`
   - queue status 不能直接说 fully_resolved
   - execution report 写清楚“需要 refresh Portfolio Audit 后确认风险是否消失”。
6. 如果用户传 `--refresh-portfolio-after-safe-actions`：
   - 可以自动调用 Portfolio Audit refresh。
   - 记录新的 portfolio report hash。
   - 不自动创建第二轮 queue。

## 12. Duplicate Queue 规则

同一个 Portfolio Audit source hash，不应重复创建多个 open queue。

创建时：

- 如果已有 `draft|planned|running|safe_completed|manual_required|blocked` 的 queue，且 `portfolio_id + source_hash` 相同：
  - 返回 existing queue。
  - HTTP 返回 200 或 409 都可，但推荐 200 + `existing=true`，减少 Studio 重复点击造成困扰。
- 如果用户显式传 `force_new=true`：
  - 可以创建新 queue，但必须写 event：
    `duplicate_source_queue_created`。

release-check 要覆盖默认去重。

## 18. Redaction 规则

所有导出和 verifier 都必须复用现有 redaction 规则。

重点阻断：

- `C:\...`
- `D:\...`
- `\\server\share\...`
- `//server/share/...`
- GitHub token。
- OpenAI key。
- Bearer token。
- provider raw response。
- renderer SoundFont path。
- source_path / local_path / file_path。
- username home path。

Manual Action 文档也必须扫描。

## 19. 安全边界

必须明确：

- Queue 不会绕过底层 store 的 signed / archived guard。
- Queue 不会直接写 Release signoff。
- Queue 不会直接写 Change Request approval。
- Queue 不会直接写 human review。
- Queue 不会调用 provider。
- Queue 不会上传外部平台。
- Queue 不会删除证据。
- Queue 只执行 safe actions。
- Queue 运行前检查 portfolio source current。
- Queue 运行后如果 source drift，记录 refresh required。

## 20. 并发和原子写

Store 必须：

- 使用 RLock。
- ID 分配在锁内完成。
- 目录用 `mkdir(..., exist_ok=False)` 原子占位。
- JSON 使用现有 atomic write。
- ZIP 用临时文件再 replace。
- export 目录路径必须在 queue 目录内。
- archive 后只读。

并发测试建议：

- 24 个线程同时为同一个 portfolio create queue。
- 默认只得到一个 open queue。
- `force_new=true` 才能得到多个。

## 21. Release-check v6.6 smoke

新增：

```text
v6.6 portfolio governance queue smoke: ok
```

建议流程：

1. 创建两个 Release fixture。
2. 让其中一个缺 reviewer pack verification。
3. 创建 Portfolio Audit。
4. refresh，确认 report failed/warning。
5. 创建 Governance Queue。
6. 确认 action plan 包含 reviewer_pack safe actions 和 manual_required actions。
7. run-safe。
8. 确认 safe items completed。
9. 确认 manual_required 没被执行。
10. 确认 post_portfolio_refresh_required 为 true。
11. export governance queue。
12. build ZIP。
13. 外部临时目录 verify passed。
14. 篡改 action-plan -> failed。
15. 篡改 execution-report -> failed。
16. duplicate ZIP entry -> failed。
17. dangerous path -> failed。
18. backslash entry -> failed。
19. manifest spoof -> failed。
20. redaction pollution -> failed。
21. 创建相同 source queue 第二次返回 existing。
22. 底层 portfolio source 变化后旧 queue run-safe 返回 409。

输出示例：

```text
v6.6 portfolio governance queue smoke: ok, queue=pgq-000001, safe=4, manual=2, external=passed, stale=409, tamper=failed
```

## 29. Reviewer 重点检查

交付后重点看：

- Queue 是否不会自动 signoff/reset/approve/submit。
- run-safe 是否只执行 safe actions。
- stale source 是否 409。
- duplicate open queue 是否被挡住。
- manual_required 是否完整进入 manual-action-list。
- safe actions 改变底层 evidence 后是否记录 post_portfolio_refresh_required。
- export/zip 是否不复制大型包。
- verifier 是否不信 manifest.zip.entries。
- duplicate/backslash/dangerous/spoof/redaction 是否有负例。
- archive 后是否只读。
- release-check 是否覆盖 stale 和 tamper。
- Studio 是否没有高风险自动按钮。

## 30. 成功标准

v6.6.0 完成后，系统应该能回答：

- Portfolio Audit 发现的风险，下一步应该按什么队列处理？

- 哪些动作被阻断，为什么？
- 执行动作后 Portfolio Audit 是否需要刷新？
- 治理队列是否可以导出给 reviewer？
- 治理队列 ZIP 离开本机后是否能被独立验证？

如果这些问题能被本地 deterministic 数据回答，并且安全边界没有放松，v6.6.0 就达标。

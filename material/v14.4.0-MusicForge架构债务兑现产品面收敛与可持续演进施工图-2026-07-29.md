# MusicForge v14.4.0 架构债务兑现、产品面收敛与可持续演进施工图

日期：2026-07-29
状态：规划候选，需 reviewer 批准后实施
稳定基线：v14.3.5 / `131258b4bcf9786bc155e3327a64836bf5aca037`

## 1. 版本定位

v14.4.0 不是新功能版本，也不是继续修补 Explicit Any collector 的版本。

本版只做四件事：

1. 兑现已经延期到 v14.4.0 的 ARCH-014 与 TYPE-003。
2. 收敛过度扩张的产品能力、Store、Command、Route 和 evidence workflow。
3. 把跨 bounded-context 编排真正移入 application layer。
4. 缩短开发、review、测试和发布反馈周期，停止一个 reviewer finding 对应一个正式 patch release 的节奏。

v14.4.0 实施期间执行业务功能冻结。除修复 P0/P1、安全问题、数据损坏和兼容性回归外，不新增 Board、Center、Hub、Archive、Verifier、Store、CLI command、HTTP route 或 Studio panel。

v14.4.0 可以有多个内部 milestone 和 prerelease RC，但只发布一个稳定版。不得为了赶版本移动债务截止日期、抬高 ceiling、排除文件、删除测试或生成机械分片。

### 2.1 根因

项目当前不是“没有架构”，而是“有边界门禁，但产品和工作流数量没有收敛”。

主要根因：

- 过去每个新需求都倾向于新增一个 Store、Verifier、ZIP、Board 或 Center。
- 多个汇总层各自持久化状态，形成重复的状态权威。
- interface 和 domain 直接组合大量具体 Store，application layer 只覆盖少量 use case。
- bounded context 目录已经建立，但大量 context 仍直接依赖其他 context 的实现模块。
- `dict[str, Any]` 风格文档贯穿领域、接口和验证链，导致自研静态分析器承担了不应由产品仓库承担的编译器工作。
- 每个 collector finding 都成为一个正式 patch release 和一个永久 release-check ID。
- compatibility、historical checks、active product 和 release certification 同包交付，物理体积和认知成本没有分离。

## 3. 本版硬性原则

### 3.1 不允许的做法

- 不允许生成 `part_001.py`、`v144_*.py` 或按行数机械切文件。
- 不允许 `bind_globals()`、动态 import、通配 re-export 或文件级 mypy/Ruff suppression。
- 不允许通过移动函数但保留循环依赖来宣称模块完成拆分。
- 不允许增加 Any、module-size、coverage、complexity 或 performance ceiling。
- 不允许把 active 模块改标为 compatibility/legacy 来降低指标。
- 不允许删除安全攻击回归；只能整合运行入口。
- 不允许新增第二个状态权威来“统一”已有状态权威。
- 不允许把所有 Store 放进一个全局基类或配置驱动万能工作流。
- 不允许在 v14.4 稳定发布前连续发布 v14.4.x 来代替 prerelease review。

### 3.2 必须遵守的做法

- 每次拆分必须按业务职责、状态所有权或纯计算边界完成。
- 每个 mutable concept 只能有一个 authoritative store。
- Board、Center、Dashboard、Observatory 默认是 read model，不得重复拥有源状态。
- cross-domain workflow 必须由 application use case 编排。
- domain 之间只能通过 versioned contract、port 或 domain event 协作。
- 任何 public contract 变化必须有 compatibility test、migration 和 rollback。
- 每个 milestone 都要独立 review，所有 milestone 完成后才进入 RC。

## 4. 目标架构

```text
interfaces
    -> application use cases
        -> domain ports / domain services
            -> platform kernels

composition/bootstrap
    -> concrete domain stores and adapters

release_check
    -> public application/interface contracts
    -> test-only certification providers
```

### 4.1 六个 bounded context 保留

- Creation：歌曲生成、provider、render、edit intent。
- Studio：项目、素材、编辑器、试听视图。
- Quality：人工验收、音频质量、修复与认证。
- Delivery：Release、Distribution、Submission、Rights。
- Trust：公开证明、外部信任与运营审计。
- Program：跨 Release 的 program、train、continuity 编排。

不拆微服务。MusicForge 继续是本地优先的 modular monolith。

### 4.2 状态权威规则

每个能力必须标记为以下一种：

- `authority`：拥有可变状态和事务规则。
- `projection`：由权威状态计算出的只读视图。
- `evidence_package`：不可变导出和离线验证。
- `workflow`：application layer 编排。
- `compatibility_adapter`：无业务分支、无持久化写入。

同一业务概念不得同时存在两个 `authority`。

## 5. Milestone A：能力目录与功能冻结

新增机器可读 `capability-catalog.json`，覆盖：

- capability id、bounded context、owner。
- authority/projection/workflow/package/adapter 类型。
- Store、Verifier、CLI、API、Studio、schema、release-check 映射。
- public/internal、active/maintained/deprecated/archive 状态。
- source-of-truth、依赖 capability、替代能力。
- compatibility deadline、migration、rollback、tests。

### A 验收

- 约 130 个 Store 全部归类，无 unknown。
- 264 个 CLI 注册点和 117 个 API route 都能映射到 capability。
- 每个持久化目录只能映射到一个 authority。
- 新增 architecture gate：catalog 外的 Store/command/route/package 直接失败。
- v14.4 全程 command、route、Store、panel 总数不得增长。

## 6. Milestone B：ARCH-014 行为式拆分

### 6.1 优先队列

第一批必须处理最高风险模块：

1. `domains/trust/ga_readiness_verifier.py`
2. `domains/trust/ga_readiness.py`
3. `domains/trust/public_trust_center.py`
4. `domains/studio/song_editor.py`
5. `domains/quality/review_tasks.py`
6. `domains/delivery/release_verifier.py`
7. `domains/program/unified_release_program_continuity_command_center_acceptance.py`
8. `domains/quality/audio_revision.py`
9. `domains/program/unified_release_program_handoff.py`
10. `domains/quality/music_acceptance.py`

后续按 `max_lines`、fan-in、fan-out、change frequency 和 security criticality 排序处理剩余模块。

### 6.2 拆分模板

每个大模块只能拆成有稳定语义的部分：

- `model.py`：typed domain state，不做 I/O。
- `policy.py` 或 `semantics.py`：纯规则和决策。
- `repository.py`：单一状态权威的持久化适配。
- `service.py`：领域操作，不做跨域编排。
- `projection.py`：只读报告和 summary。
- `package.py`：PackageSpec 和导出布局。
- `verifier.py`：领域 semantic checks，ZIP envelope 使用 platform kernel。

不是每个模块都必须包含这些文件；只创建真实存在的职责。

### 6.3 ARCH-014 最终门禁

- `module_size_debt` 必须清空。
- 所有 active module 不超过 600 行。
- 所有新模块不超过 400 行。
- application use case 建议不超过 150 行。
- domain semantic module 建议不超过 300 行。
- 不允许只降低文件行数却增加 import cycle、global state 或 re-export fan-out。
- 每个拆分要有 differential behavior test。

## 7. Milestone C：TYPE-003 类型精度关闭

### 7.1 不再扩建自研 Python 分析器

schema 17 collector 在 v14.4 只作为迁移对照，不再新增跨过程语义。

目标是消除 active code 的 Explicit Any，而不是继续提高 collector 对任意 Python 程序的模拟能力。

### 7.2 类型迁移策略

1. 在 platform contracts 定义递归 `JsonValue` / `JsonObject`，禁止 `dict[str, Any]` 作为通用协议。
2. 外部 JSON 在 interface boundary 完成解析、校验和错误报告。
3. domain state 使用 dataclass、enum、TypedDict 或窄 Protocol。
4. evidence package schema 使用版本化 TypedDict 与 parser，不把原始 dict 贯穿业务层。
5. application use case 输入输出使用明确 command/result 类型。
6. 仅真正不可解释的第三方 payload 可停留在 interface adapter，并转换为 `object` 后显式缩窄。
7. 分 bounded context 启用 mypy `disallow_any_explicit = true`。
8. 最终对全部 active roots 启用 `disallow_any_explicit`，并保留 alias 攻击语料验证 mypy 语义结果。

### 7.3 Collector 退役条件

满足以下条件后，删除 4,000 行级自研 interprocedural collector：

- active Explicit Any 为 0。
- mypy 全 active roots 启用 `disallow_any_explicit`。
- 现有攻击语料在 mypy 门禁下全部失败。
- 简单 AST inventory 与 mypy 结果一致。
- collector removal 不删除攻击测试，只把预期执行器切换到 mypy/轻量 inventory。

### 7.4 TYPE-003 最终门禁

- Explicit Any：11,993 -> 0。
- affected files：461 -> 0。
- public ImplementationDocument：保持 0。
- raw `dict[str, Any]`：active code 0。
- untyped public function：0。
- 不新增 mypy exclude 或 per-file suppression。

## 8. Milestone D：真正的 bounded-context 边界

### 8.1 Cross-domain import

当前约 1,019 条 cross-domain import 不应全部被视为合理。

分类后执行：

- 共享 JSON/hash/redaction/path helper 下沉 platform。
- 跨域数据结构移动到 versioned contract，不移动业务行为。
- 跨域 Store 调用改为 application use case + port。
- read-only 汇总使用 projection contract。
- domain implementation 不得直接 import 另一 domain implementation。

### 8.2 Interface boundary

- CLI/API/Web handler 只能依赖 application commands/queries 和 platform contracts。
- 具体 Store 构造只允许出现在显式 bootstrap/composition modules。
- 现有 dependency catalog 要拆成按 bounded context 的 composition provider，不能成为新的 mega-file。
- interface handler 内直接 domain import 最终为 0。

### 8.3 D 验收

- domain implementation -> other domain implementation：0。
- contract/port import 单独计数并固定 allow-list。
- interface handler/command -> domain implementation：0。
- composition-root concrete import 独立披露，不和 handler 统计混淆。
- application layer 必须出现真实 use case 增长；不能通过 facade 转发伪造。
- production cycle、boundary violation 继续为 0。

## 9. Milestone E：Store 与工作流收敛

### 9.1 处理顺序

优先审计以下连续演化链：

- Release Operations -> Portfolio Governance -> Public Trust Center。
- Trust Operations Hub -> Unified Command Center -> Release Train。
- Unified Release Program -> Continuity -> Command Center -> Acceptance。
- Audio Campaign -> Certification -> Timeline -> Regression -> Observatory -> Action Queue -> Command Center。

对每条链回答：

1. 哪一个 Store 是状态权威？
2. 哪些对象只是 projection？
3. 哪些 signoff/reset/archive 可直接复用 lifecycle kernel？
4. 哪些 verifier 只是在重复 package envelope？
5. 哪些 CLI/API 只是同一操作的历史别名？

### 9.2 收敛目标

- active authoritative Store 数至少减少 15%。
- projection 不再单独维护可变副本。
- 所有 signoff/reset/history/archive 使用 lifecycle kernel。
- 所有 ZIP envelope 使用 Verification Kernel PackageSpec。
- 相同 evidence identity 不得在多个 Store 中独立计算。
- compatibility class 可以保留，但只能委托 canonical use case，不能写第二份状态。

## 10. Milestone F：release-check 与测试治理

### 10.1 Patch-level check 收敛

v14.2.2 至 v14.3.5 的 collector hotfix assertions 合并为一个版本化 attack corpus。

- 历史 check ID 保留在 full/nightly compatibility profile。
- `v14`、`latest`、`ga` 只运行当前 schema contract、attack corpus 和 final integration。
- 不因合并执行入口删除任何攻击样例。
- current profile 不再为每个 patch 永久增加一个 check。

### 10.2 测试金字塔

- unit：纯 policy/model/parser，无文件系统和 server。
- contract：schema、public API、CLI exit、package layout。
- security：ZIP、binding、tamper、full-resign、path/redaction。
- integration：每个 capability 只保留少量 happy path 和关键 failure path。
- legacy：只在 nightly/full，禁止被 current profile 间接重复执行。

### 10.3 性能目标

- 单 capability targeted suite：5 分钟内。
- PR fast lane：Linux 15 分钟内、Windows 20 分钟内。
- Quality workflow wall clock：30 分钟内。
- Nightly active + legacy + full：60 分钟内。
- `v14` current profile：120 秒内。
- `latest` / `ga`：各 300 秒内。
- 性能优化不得放宽安全 timeout 或跳过真实 verifier。

## 12. 发布流程改造

### 12.1 分支与版本

- v14.4 开发用 feature branches/PR 或明确的 milestone commits。
- milestone 完成后做内部 reviewer，不打正式 tag。
- 使用 `v14.4.0-rc.1`、`rc.2` 做最终候选；RC 不设 Latest。
- 外部 reviewer 对 RC 的 finding 在同一 v14.4.0 里修复。
- 只有 final reviewer package 通过后才创建 `v14.4.0` stable tag。

### 12.2 禁止 patch-release 驱动开发

正式 patch release 只用于：

- 已发布版本的 P0/P1。
- 数据损坏或安全漏洞。
- 明确的用户可见兼容性回归。

普通 reviewer finding 必须在 RC 阶段解决，不得预先发布再连续 supersede。

### 12.3 历史 tag

- 不强制覆盖本地/远端历史 tag。
- 生成一次 machine-readable tag inventory，记录差异和 canonical remote target。
- stable release 验证只 fetch/resolve 当前精确 tag。
- 任何历史 tag 修复必须单独审批，不与产品发布混合。

## 14. v14.4.0 发布硬门禁

以下任一项未满足，不得发布 stable：

- ARCH-014 未关闭。
- TYPE-003 未关闭。
- 任一 ceiling 被提高。
- 新增未登记 Store/command/route/panel/package。
- active module 超过 600 行。
- active Explicit Any 非 0。
- domain implementation 直接依赖其他 domain implementation。
- interface handler 直接依赖 domain implementation。
- authoritative Store 未归档 owner/source-of-truth。
- production cycle 或 compatibility inbound edge 非 0。
- current profile 仍按 patch 数线性增长。
- Quality/Nightly/final reviewer package 未绑定同一 final SHA。
- migration/rollback、public contract 或 package verifier 回归失败。

## 15. Reviewer 必查攻击与反退化场景

- 机械拆文件后通过 globals/re-export 恢复单体耦合。
- 新模块被 mypy/coverage/architecture exclude。
- Any 通过 alias、quoted annotation、factory、closure 或 dynamic import 洗白。
- `object` 被当成无校验 Any 使用。
- TypedDict 只改注解、不做 runtime parse。
- projection 写入第二份权威状态。
- compatibility adapter 重新出现业务分支。
- composition root 变成新的超大 service locator。
- 删除 security tests 来缩短 CI。
- 历史 check 从 current profile 删除后没有 nightly/full 承接。
- 为通过性能预算降低 verifier 深度或放宽 timeout。

## 16. v14.5 至 v15.0 路线

### v14.5：Product Surface Rationalization

- 基于 capability catalog 决定 core/advanced/deprecated。
- 合并重复 CLI/API/Studio workflow。
- authority Store 继续减少到不超过 80。
- 建立用户任务导向入口，隐藏内部 evidence plumbing。

### v14.6：Packaging and Test Separation

- active product、compatibility verification、developer certification 物理分包。
- 默认安装不携带 24K legacy monolith 和历史 smoke 实现。
- CI 使用按 capability 影响分析选择 fast tests，nightly 保持完整覆盖。

### v15.0：Public Surface Reset

- 删除完成 deprecation 周期的静态 facade、CLI alias 和 API route。
- 发布 migration assistant 和 contract diff。
- 只保留 core user journeys 与明确启用的 advanced governance capabilities。
- 重新建立更小的 LTS 基线，禁止恢复历史功能堆叠模式。

## 17. 给开发的执行说明

不要把这份施工图理解成“再拆一遍文件”。v14.2.0 已证明机械拆分会制造更难审计的系统。

开发顺序必须是：先识别状态权威和 use case，再定义 typed contract，然后移动行为，最后删除重复实现。每完成一个 vertical slice，就跑该 slice 的 unit/contract/security/differential tests 和 architecture gate；不要等 137 个模块一起改完才测试。

任何时候发现目标无法在不抬高 ceiling、不排除文件、不弱化测试的情况下完成，应停下来提交 reviewer 讨论，而不是再发明一层 Board、Center、collector 特例或 compatibility wrapper。

v14.4 的成功标准不是“所有检查又绿了”，而是代码和产品表面积真实下降、状态权威变少、依赖方向变清楚、类型可以由标准工具验证、下一位开发者能在有限时间内理解和修改系统。

# v4.12.0 Planning Rule Simulation 计划规则模拟与评分沙箱施工图

日期：2026-05-21

当前稳定基线：v4.11.1

目标版本：v4.12.0

建议版本主题：Planning Rule Simulation / 计划规则模拟与评分沙箱

---

## 1. 背景

v4.10.1 已经把 Acceptance Knowledge Base 接入 Fix Plan，让系统能用历史修复知识辅助创建下一轮修复计划。

v4.11.1 已经补上 Fix Plan Outcome Review，让系统能复盘一个 Fix Plan 执行后到底有没有效果，并且修正了 synthetic-only recheck 不能伪装成人工复验证据的问题。

现在链路已经是：

```text
Acceptance Analytics
  -> Acceptance Knowledge Base
  -> Fix Plan
  -> Fix Sprint
  -> Recheck / Delta / Closeout
  -> Fix Plan Outcome Review
```

但还有一个关键问题没有解决：

```text
下一次 Fix Plan 的评分规则应该怎么调？
```

现在系统能给出 calibration hints，但这些 hints 只是文字建议：

- high-score item 是否被高估。
- no_kb_history 是否被过度惩罚。
- waiver-heavy history 是否应该更高风险。
- mixed history 是否应该扣分。
- manual recheck 是否应该提高 confidence。

开发或业务还无法安全地试算：

- 如果调整 `no_kb_history` penalty，历史排序会不会更接近真实 outcome？
- 如果提高 waiver penalty，会不会更早暴露风险？
- 如果降低 mixed history penalty，会不会减少误判？
- 如果把 synthetic-only recheck 作为强 penalty，Release evidence 是否更稳？
- 如果改动规则，会影响多少历史 Fix Plan？

v4.12.0 要做的是“规则模拟沙箱”：允许开发在不修改生产 Planning Score 规则的前提下，用历史 Outcome Review 回放候选规则，计算模拟分数、排序变化、风险变化和规则建议。

---

## 2. 一句话目标

> v4.12.0 要新增一个本地 deterministic Planning Rule Simulation 层，用历史 Fix Plan Outcome Review 回放候选规则集，输出模拟报告、排序差异、风险变化和规则建议，但不自动改生产规则、不自动创建 Fix Plan、不自动执行修复。

---

## 3. 版本定位

v4.12.0 是 v4 质量闭环进入 v5 前的最后一个“规则治理”版本。

它不是：

- 不是新音乐生成能力。
- 不是新的 provider。
- 不是自动调参系统。
- 不是线上 A/B。
- 不是自动修改 `acceptance_fix_planning.py`。

它是：

- 本地规则沙箱。
- 历史 Outcome Review 回放器。
- 可审计的评分规则模拟报告。
- Release Signoff 的可选 evidence。
- 下一版是否进入 v5 的决策依据。

---

## 4. 本版不做什么

明确不做：

- 不自动修改 production planning rules。
- 不自动把模拟规则应用到 `AcceptanceFixPlanningStore`。
- 不自动创建新的 Fix Plan。
- 不自动创建 Fix Sprint。
- 不自动创建 ReviewTask。
- 不调用 provider / LLM / 外部 API。
- 不使用向量数据库。
- 不修改已有 Outcome Review。
- 不把完整 review notes、provider raw response、本机路径、token 写入报告。
- 不把模拟结果作为强制 Release 阻断，除非 payload 显式要求。

可以做：

- 保存 candidate rule set。
- 用历史 review 回放模拟 score。
- 计算排序 alignment 变化。
- 计算 evidence helpfulness 变化。
- 输出 rule recommendation。
- 导出脱敏 summary。
- 让 Studio 展示模拟对比。

---

## 5. 为什么现在做 v4.12

### 5.1 v4.11 之后有了足够的训练样本雏形

v4.11 的 Outcome Review 给了每个 Fix Plan 这些数据：

- planning_score。
- actual item outcome。
- plan effectiveness。
- ranking alignment。
- KB helpfulness。
- synthetic/manual recheck evidence。
- warnings。

这些数据不是机器学习训练集，但足够做 deterministic 回放模拟。

### 5.2 不能直接改生产规则

Acceptance Fix Planning 是决策前置层。

如果直接改规则，风险是：

- 新规则让低质量历史策略被高估。
- 一些 hidden/stale KB 被误用。
- synthetic-only 的改善被当作人工证据。
- waiver-heavy 的修复被过度奖励。

所以 v4.12 必须是沙箱：

```text
candidate rules -> simulation report -> reviewer 看报告 -> 以后再决定是否采用
```

### 5.3 v5 前需要决定质量规则是否稳定

进入真实音频后，生成和评审成本更高。

v4.12 的价值是回答：

```text
当前 Fix Planning 规则够不够稳？
如果不够，问题在哪里？
```

## 9. Rule Set Schema

```json
{
  "schema_version": "planning_ruleset.v1",
  "ruleset_id": "afprs-000001",
  "name": "Conservative Manual Evidence",
  "description": "Penalize synthetic-only and waiver-heavy history more strongly.",
  "status": "draft",
  "base_rules_version": "acceptance_fix_planning.v1",
  "weights": {},
  "penalties": {},
  "confidence": {},
  "bounds": {
    "min_score": 0,
    "max_score": 100,
    "high_score_threshold": 75
  },
  "source": {
    "created_from": "builtin",
    "template": "manual_conservative"
  },
  "created_at": "2026-05-21T00:00:00Z",
  "updated_at": "2026-05-21T00:00:00Z",
  "created_by": "developer"
}
```

### 9.1 内置模板

至少做 4 个：

```text
baseline
manual_conservative
kb_trust_light
waiver_strict
synthetic_strict
```

含义：

- baseline：尽量复刻 v4.10 production scoring。
- manual_conservative：更奖励人工复验。
- kb_trust_light：降低 KB 命中对分数的影响，避免历史噪声。
- waiver_strict：更重惩罚 waiver-heavy 和 force close。
- synthetic_strict：更重惩罚 synthetic-only outcome。

### 9.2 参数边界

必须 clamp：

- 权重：-50 到 100。
- multiplier：0 到 2。
- score：0 到 100。
- high_score_threshold：50 到 95。
- 文本字段长度限制。

非法输入返回 400。

## 12. Source Hash / Stale Guard

Simulation source hash 绑定：

- engine version。
- ruleset sanitized payload。
- selected Outcome Review ids。
- selected Outcome Review source hashes。
- selected Outcome Review summary hashes。
- item outcome hashes。
- scope。

Stale 条件：

- ruleset 改变。
- ruleset 被 archived。
- review 被 archived。
- review stale。
- review source hash 改变。
- review item_outcomes 改变。
- scope 不再匹配。

读取 simulation detail 时必须重新判断 stale。

如果 stale：

```json
{
  "status": "stale",
  "summary": {
    "stale": true
  },
  "warnings": ["source_changed"]
}
```

## 13. 模拟算法

### 13.1 输入

使用 Outcome Review 的 item_outcomes。

每个 item 有：

- baseline planning_score。
- severity。
- target issue/style/song。
- planned_knowledge risk/warnings/match_count。
- execution status。
- outcome evidence_status。
- observed_effectiveness_score。
- synthetic_only summary。
- waived/force_closed warnings。

### 13.2 重新打分

建议函数：

```python
simulate_item_score(item_outcome, ruleset, review_summary) -> dict
```

基础：

```text
score = baseline_planning_score
```

然后应用候选规则：

```text
+ manual_recheck_bonus if review.manual_recheck_confirmed
- synthetic_only_penalty if review.synthetic_only
- waiver_penalty if item.execution.waived
- force_close_penalty if item.execution.force_closed
- no_kb_history_penalty if planned_knowledge.match_count == 0
- ineffective_history_penalty if history_ineffective in planned_knowledge.warnings
- mixed_history_penalty if history_mixed_effectiveness in planned_knowledge.warnings
- high_risk_bonus if planned_knowledge.risk == high
+ effective_history_bonus/discount if helpful KB evidence
```

最后 clamp 到 0 到 100。

### 13.3 评估排序

按 simulated score 排序后，与 observed effectiveness 排序对比。

指标：

- simulated_alignment_score。
- baseline_alignment_score。
- alignment_delta。
- high_score_unsupported_count。
- low_score_supported_count。
- synthetic_high_score_count。
- waiver_high_score_count。

### 13.4 Rule Effect 汇总

输出全局 effects：

- synthetic_penalty_applied_count。
- waiver_penalty_applied_count。
- no_kb_penalty_applied_count。
- mixed_history_penalty_applied_count。
- ineffective_history_penalty_applied_count。
- manual_bonus_applied_count。

每个 effect 需要有：

- count。
- average_score_delta。
- affected_review_ids。
- affected_issue_types。

## 14. Recommendation 判定

### 14.1 candidate_better

满足：

- review_count >= 2 或 item_count >= 4。
- alignment_delta >= 5。
- simulated_high_score_unsupported_count 下降。
- 没有明显增加 low_score_supported_count。

### 14.2 candidate_mixed

满足：

- 有指标改善，但也有指标变差。
- 或 review_count 太少但趋势可用。

### 14.3 candidate_worse

满足：

- alignment_delta <= -5。
- high_score_unsupported_count 增加。

### 14.4 insufficient_data

满足：

- review_count < 1。
- item_count < 2。
- 全部 review stale。

### 14.5 blocked_by_stale_reviews

满足：

- 输入 review 大部分 stale。
- 或 required review stale。

## 19. Release Signoff Gate

新增可选 payload：

```json
{
  "require_planning_rule_simulation": true,
  "planning_simulation_id": "afpsim-000001"
}
```

Gate 规则：

如果 `require_planning_rule_simulation=true`：

- simulation 必须存在。
- simulation 不能 stale。
- simulation.status 不能是 `blocked`、`archived`。
- simulation scope 必须匹配当前 release，或 simulation review ids 都属于当前 release/project。

不要求：

- recommendation 必须 candidate_better。
- alignment_delta 必须大于 0。

如果 recommendation 是 `candidate_worse`：

- gate 可以 passed，但必须写 warning。
- force signoff 不需要特殊 override。

Signoff evidence：

```json
{
  "planning_rule_simulation": {
    "status": "passed",
    "simulation_id": "afpsim-000001",
    "ruleset_id": "afprs-000001",
    "recommendation": "candidate_mixed",
    "alignment_delta": 3,
    "stale": false
  }
}
```

## 20. 安全与脱敏

必须复用：

```python
sanitize_metadata()
sanitize_sensitive_text()
```

禁止输出：

- token。
- provider raw response。
- 本机路径。
- UNC 路径。
- 完整人工 review notes。
- renderer path。
- GitHub token。

Rule Set 文本字段长度：

- name: 120。
- description: 500。
- reason/suggestion: 400。

Simulation report：

- item target summary 只保留 song_id/style/issue_types/project_id/version_id。
- 不输出 full request。
- 不输出 full review notes。
- 不输出 local artifact path。

## 26. 风险清单

### 26.1 把模拟误当生产规则

风险：

- 用户以为 simulation 已经改变了 Fix Plan 打分。

要求：

- UI 文案明确 `simulation only`。
- API 不提供 activate。
- README 明确不改生产规则。

### 26.2 用 Outcome Review 的 score 反推过度

风险：

- Outcome Review 数据少，模拟结论不稳定。

处理：

- review_count / item_count 太少时 recommendation = insufficient_data 或 candidate_mixed。
- 不输出强结论。

### 26.3 synthetic-only 再次被当成人工证据

风险：

- v4.11.1 刚修过，v4.12 不能回退。

处理：

- simulation 输入必须使用 summary.synthetic_only。
- release-check 继续断言 synthetic penalty applied。

### 26.4 Export 泄露历史 item 明细

风险：

- simulation detail 包含历史 target。

处理：

- Release Export 只写 summary。
- Full report 只在本地 workspace。

### 26.5 stale guard 漏 ruleset

风险：

- ruleset 改后 simulation 仍 ready。

处理：

- source hash 绑定完整 ruleset sanitized payload。

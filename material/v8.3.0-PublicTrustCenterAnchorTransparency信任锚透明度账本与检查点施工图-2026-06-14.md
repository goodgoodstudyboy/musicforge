# v8.3.0 Public Trust Center Anchor Transparency 信任锚透明度账本与检查点施工图

> 本文是给开发执行的 v8.3.0 施工图。当前稳定基线是 v8.2.0。
>
> v8.2.0 已经把 v8.1.3 的 `public-trust-center.delivery-anchor.json` 升级成 Public Trust Center Anchor Registry，支持 register / publish / revoke / supersede / export / ZIP / offline verify，并且 `verify-public-trust-center-package` 已能通过 `--anchor-registry` 反查当前 PTC ZIP 是否绑定到当前已发布 anchor。
>
> v8.3.0 的目标，是继续解决 v8.2.0 剩下的信任根边界：如果攻击者能同时替换 PTC ZIP、delivery anchor、Anchor Registry ZIP，纯本地离线 verifier 仍不知道哪个 registry 才是“外部曾经看到过的当前版本”。v8.3.0 要新增 Anchor Transparency Ledger 与 Checkpoint，让外部方能保存一个很小的公开检查点，并用它反查 Anchor Registry 是否被整体替换。

---

## 1. 背景

v8.0 到 v8.2 已经形成了 Public Trust Center 的三层公开信任链：

1. Public Trust Center ZIP。
   - 聚合 Registry / Portal / Transparency / Acknowledgement。
   - 聚合 Release / Distribution / Submission / Evidence / Operations。
   - 生成 public-safe HTML、data JSON、manifest。
   - 离线 verifier 可验 ZIP 内部完整性和底层 verification summary。

2. Delivery Anchor。
   - 位于 PTC ZIP 外部。
   - 绑定 PTC ZIP hash、manifest hash、source hash、delivery fingerprint sidecar。
   - 解决“篡改 PTC ZIP 后整体重签内部 JSON”的问题。

3. Anchor Registry。
   - 管理当前 anchor entry。
   - 支持 published / superseded / revoked。
   - 支持本地 deterministic signature envelope。
   - 支持独立 ZIP 和 verifier。
   - `verify-public-trust-center-package` 可要求 registry current entry 匹配当前 PTC ZIP。

v8.2.0 的边界也很清楚：

- 如果只替换 PTC ZIP，不替换外部 anchor，verifier 会失败。
- 如果替换 PTC ZIP 和外部 anchor，但不替换 Anchor Registry，verifier 会失败。
- 如果同时替换 PTC ZIP、anchor、Anchor Registry ZIP，并且外部 verifier 只拿到这一组新文件，离线 verifier 无法判断这组文件是不是“真实历史上的当前版本”。

这个问题不是 v8.2.0 的 bug，而是所有离线信任锚都会遇到的外部见证问题。v8.3.0 要把“当前 Anchor Registry 状态”写入一个 append-only transparency ledger，并导出小型 checkpoint 文件。外部方只要保存 checkpoint，就能发现后续 registry 被整体替换、历史被重写或 current entry 被伪造。

---

## 2. v8.3.0 定位

一句话：

> v8.3.0 要新增 Public Trust Center Anchor Transparency Ledger 和 Checkpoint，把 Anchor Registry 的 publish / revoke / supersede 历史变成可追加、可导出、可离线复验、可由外部保存检查点的信任锚透明度层。

这版不是再扩展业务域，也不是做真实 CA。它是对 v8.2 Anchor Registry 的治理增强。

---

## 3. 不做什么

本版必须收住边界：

1. 不接入真实 CA、证书链、硬件密钥。
2. 不强制联网，不依赖 GitHub API 才能通过 verifier。
3. 不自动向 GitHub Pages、对象存储或第三方服务发布。
4. 不把 token、GitHub key、本机路径写入任何公开包。
5. 不改变 v8.2 Anchor Registry 的基本 register/publish/revoke/supersede API 语义。
6. 不把 `.musicforge/` 内部目录打进公开 ZIP。
7. 不允许 transparency verifier 信任同一个 ZIP 内自证字段。
8. 不自动 approve、signoff、reset、revoke 任何上游业务对象。
9. 不把 deterministic signature envelope 宣称为第三方强密码学签名。

## 6. Anchor Transparency Event

新增事件类型，覆盖 Anchor Registry 的关键状态变化：

```text
anchor_registered
anchor_published
anchor_superseded
anchor_revoked
anchor_registry_exported
anchor_registry_verified
checkpoint_created
transparency_exported
transparency_zip_built
```

事件结构建议：

```json
{
  "schema_version": 1,
  "event_id": "ptcat-event-000001",
  "center_id": "ptc-default",
  "sequence": 1,
  "event_type": "anchor_published",
  "created_at": "2026-06-14T...Z",
  "actor": "local",
  "reason": "Publish v8.3 trust center anchor",
  "anchor_entry_id": "ptcar-entry-000001",
  "anchor_hash": "sha256-or-stable-hash",
  "registry_hash": "stable_hash(registry_without_volatile_fields)",
  "registry_zip": {
    "zip_sha256": "...",
    "zip_size_bytes": 12345,
    "manifest_hash": "..."
  },
  "ptc_package": {
    "zip_sha256": "...",
    "zip_size_bytes": 12345,
    "manifest_hash": "...",
    "source_hash": "..."
  },
  "previous_event_hash": null,
  "event_hash": "stable_hash(event_without_event_hash)"
}
```

规则：

- `sequence` 必须从 1 开始递增。
- 每条事件必须包含 `previous_event_hash`。
- 第一条事件的 `previous_event_hash` 为 `null`。
- 后续事件的 `previous_event_hash` 必须等于上一条 `event_hash`。
- `event_hash` 必须覆盖除 `event_hash` 自身以外的所有字段。
- 不允许 verifier 只信 ledger summary，必须逐条重算。
- 导出 ZIP 里不能有重复 event_id / sequence。

## 7. Anchor Checkpoint

Checkpoint 是 v8.3 的核心。它是一个很小的 JSON，外部方可以保存、邮件传递、放到 GitHub Release 描述里，或手动贴到其他系统。

建议结构：

```json
{
  "schema_version": 1,
  "package_type": "musicforge_public_trust_center_anchor_checkpoint",
  "center_id": "ptc-default",
  "checkpoint_id": "ptc-anchor-checkpoint-000001",
  "created_at": "2026-06-14T...Z",
  "sequence": 7,
  "latest_event_hash": "...",
  "ledger_hash": "...",
  "current_entry_id": "ptcar-entry-000001",
  "current_anchor_hash": "...",
  "registry_hash": "...",
  "registry_zip_sha256": "...",
  "registry_manifest_hash": "...",
  "ptc_zip_sha256": "...",
  "ptc_manifest_hash": "...",
  "ptc_source_hash": "...",
  "signature": {
    "mode": "local_deterministic_envelope",
    "key_id": "musicforge-local-anchor-v1",
    "key_fingerprint": "...",
    "payload_hash": "...",
    "signature_hash": "..."
  },
  "integrity_hash": "stable_hash(checkpoint_without_integrity_hash)"
}
```

规则：

- checkpoint 必须绑定 ledger latest event。
- checkpoint 必须绑定当前 Anchor Registry package。
- checkpoint 必须绑定当前 PTC package fingerprint。
- checkpoint 不能从 ZIP 内 manifest 自证，必须能被 verifier 用 ledger / registry summary 重建。
- `ptc-anchor-checkpoint-current.json` 可以是最新 checkpoint 的副本，但 verifier 不能只信文件名，必须看 `checkpoint_id` 和 `sequence`。

## 9. 与 v8.2 Anchor Registry 的关系

v8.3 不应大改 v8.2 Store，但需要在几个关键点接入 transparency event：

1. `register_current_anchor()` 成功后可记录 `anchor_registered`。
2. `publish_entry()` 成功后记录 `anchor_published`。
3. `publish_entry(... supersede_current=True)` 成功后记录 `anchor_superseded` 和 `anchor_published`。
4. `revoke_entry()` 成功后记录 `anchor_revoked`。
5. `export_registry()` 成功后记录 `anchor_registry_exported`。
6. `verify()` 成功后记录 `anchor_registry_verified`，但只记录 verification summary，不要复制完整 report 造成循环依赖。

如果担心改动 v8.2 Store 风险高，可以先采用显式 refresh：

```python
transparency_store.refresh_from_anchor_registry(center_id)
```

最低要求：

- v8.3 release-check 必须能证明 registry 状态变化后旧 transparency export/ZIP 变 stale。
- 新 checkpoint 必须反映最新 registry 状态。

`anchor-transparency-report.json` 建议：

```json
{

  "package_type": "musicforge_public_trust_center_anchor_transparency_report",
  "center_id": "ptc-default",
  "status": "current|stale|failed",
  "source": {
    "registry_hash": "...",
    "registry_zip_sha256": "...",
    "registry_manifest_hash": "...",
    "registry_verification_status": "passed",
    "current_entry_id": "...",
    "current_anchor_hash": "...",
    "latest_event_hash": "...",
    "ledger_hash": "...",
    "checkpoint_id": "ptc-anchor-checkpoint-000001",
    "checkpoint_hash": "..."
  },
  "summary": {
    "event_count": 7,
    "published_count": 1,
    "revoked_count": 0,
    "superseded_count": 0,
    "latest_sequence": 7,
```

## 12. Offline Verifier

新增 CLI：

```bash
python -m song_agent.cli verify-public-trust-center-anchor-transparency-package path\to\public-trust-center-anchor-transparency.zip --strict --require-current-checkpoint --require-published-anchor --json
```

核心函数：

```python
verify_public_trust_center_anchor_transparency_package(
    zip_path: Path,
    *,
    strict: bool = False,
    checkpoint_path: Path | None = None,
    anchor_registry_path: Path | None = None,
    require_current_checkpoint: bool = False,
    require_published_anchor: bool = False,
    require_not_revoked: bool = False,
    json_output: bool = False,
) -> dict
```

必须检查：

1. ZIP 可打开。
2. ZIP entry path safe。
3. raw central directory 反斜杠检测。
4. duplicate entry 检测。
5. required entries 存在。
6. no extra entry，除非明确允许 sidecar。
7. no nested zip。
8. no `.musicforge` / `.MusicForge`。
9. manifest integrity。
10. manifest files hash 对账。
11. report integrity。
12. ledger event chain。
13. event sequence 连续。
14. latest event hash 与 report source 一致。
15. ledger hash 与 report / manifest 一致。
16. checkpoint integrity。
17. checkpoint source 与 ledger latest event 一致。
18. checkpoint source 与 registry summary 一致。
19. registry verification summary 是 passed。
20. registry current entry 与 checkpoint current entry 一致。
21. require published 时 current entry 必须 published。
22. require not revoked 时 current entry 不能 revoked。
23. 外部 `--checkpoint` 存在时，必须和 ZIP 内 checkpoint hash 一致。
24. 外部 `--anchor-registry` 存在时，必须和 transparency registry summary 一致。
25. redaction scan。
26. package_type 正确。

## 13. 反伪造测试必须覆盖

v8.3 不能只测 happy path。至少补这些攻击用例：

1. 篡改 ledger 第一条 event 后重算 event_hash，但不更新后续 previous hash，verifier failed。
2. 篡改整条 ledger 并全量重签 report / manifest，但不具备匹配 checkpoint，verifier failed。
3. 篡改 checkpoint current_anchor_hash 并重算 checkpoint integrity，但不匹配 ledger，verifier failed。
4. 篡改 registry-verification-summary 为 passed，实际 registry package 不匹配，带 `--anchor-registry` verifier failed。
5. 删除 checkpoint-current，但保留旧 checkpoint，require current failed。
6. revoked current anchor，require not revoked failed。
7. ZIP 增加 `../evil.txt` failed。
8. ZIP 增加 `foo\bar.json` failed。
9. ZIP 增加 `.MusicForge/internal.json` failed。
10. ZIP 重复 `anchor-transparency-manifest.json` failed。
11. ZIP 增加 nested `.zip` failed。
12. README 或 data 中污染 `sk-...` / `github_pat_...` / `C:\Users\...` failed。

## 14. PTC Verifier 接入

`verify-public-trust-center-package` 新增参数：

```bash
--anchor-transparency path\to\public-trust-center-anchor-transparency.zip
--anchor-checkpoint path\to\ptc-anchor-checkpoint-current.json
--require-anchor-transparency-current
--require-anchor-checkpoint
```

语义：

- 如果传了 `--anchor-transparency`，先 verify transparency ZIP。
- 如果传了 `--anchor-checkpoint`，必须用外部 checkpoint 反查当前 PTC ZIP。
- 如果 `--require-anchor-transparency-current`，必须有 transparency package 且 current checkpoint 匹配。
- 如果 `--require-anchor-checkpoint`，必须有外部 checkpoint 文件。
- 如果同时传 `--anchor-registry` 和 `--anchor-transparency`，三者必须一致：
  - PTC ZIP hash。
  - PTC manifest hash。
  - PTC source hash。
  - current anchor hash。
  - registry hash。
  - checkpoint hash。

PTC verifier 新增 check_id 建议：

```text
ptc_anchor_transparency_present
ptc_anchor_transparency_verification_status
ptc_anchor_transparency_checkpoint_current
ptc_anchor_checkpoint_present
ptc_anchor_checkpoint_ptc_zip_sha256
ptc_anchor_checkpoint_manifest_hash
ptc_anchor_checkpoint_source_hash
ptc_anchor_checkpoint_registry_hash
ptc_anchor_checkpoint_latest_event_hash
```

## 20. 安全规则

必须坚持已有安全模式：

- 所有公开 ZIP 均用 allow-list entries。
- 所有 verifier 都读 ZIP central directory raw names 检测反斜杠。
- 所有 JSON 输出走 redaction。
- 所有 path 都必须相对 export root。
- 禁止 source_path / local_path 作为公开证据输入。
- 禁止把 token 写入 remote URL、README、manifest、report。
- 不依赖文件名判断 current，必须看 hash / sequence / checkpoint。
- 不允许 `manifest.zip.entries` 放行额外文件。
- 不允许 verifier 信任同一个 ZIP 内被一起重签的 summary。

## 25. Reviewer 验收标准

Reviewer 重点看这些：

1. 是否仍然能“整体重签 ZIP 内所有 JSON”绕过。
2. checkpoint 是否真的来自 ledger latest event，而不是 report 自证。
3. PTC verifier 是否要求 external checkpoint 时真的失败于缺失 checkpoint。
4. Anchor Registry、Transparency、Checkpoint、PTC ZIP 四者 hash 是否互相绑定。
5. revoked current anchor 是否会阻断 require_not_revoked。
6. stale registry 是否阻断 transparency export/zip。
7. ZIP 安全边界是否完整。
8. release-check v8 profile 是否包含 v8.3。
9. README 是否明确 deterministic envelope 不是 CA 签名。
10. 工作区是否干净、版本是否一致、tag 是否指向 release commit。

## 26. 给开发的话

这版不要只追求“能生成一个新 ZIP”。真正要解决的是 v8.2 的信任边界：外部方需要一个可单独保存的小 checkpoint，用来反查 Anchor Registry 有没有被整体替换。所以实现时要始终问自己一个问题：

> 如果攻击者把 transparency ZIP 里的 report、manifest、data 全部重签一遍，但他没有外部 checkpoint 或没有匹配的 ledger chain，verifier 会不会失败？

如果答案不是明确失败，这版就没收住。

开发顺序建议按 Phase 1 到 Phase 6 来，不要先写 Studio。先把 Store、Ledger、Checkpoint、Verifier 和 release-check smoke 打牢，再接 UI。每完成一个可独立验收的小阶段就本地提交；最后再统一 bump 版本、更新 README/CHANGELOG、打 v8.3.0 tag 和 GitHub Release。

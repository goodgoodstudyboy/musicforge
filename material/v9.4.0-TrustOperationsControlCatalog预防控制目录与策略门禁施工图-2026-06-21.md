## 1. 背景

v9.0 建立了 Trust Operations Hub，把 Public Trust Center、Publication、Monitoring 等信任证据聚合成统一准出视图。

v9.1 把 Hub 扩展到 Release / Distribution / Submission / Submission Evidence / Release Operations，并补了只执行安全动作的 Runbook。

v9.2 做了 Incident Response：Hub blocker 可以变成事故，经过 triage、remediation、evidence、verify-fix、closeout、archive、ZIP、offline verifier。

v9.2.1 修复了事故 evidence 伪造问题：`add_evidence()` 必须反查当前 Hub delivery verification evidence。

v9.3 做了 Incident Knowledge / Regression Guard：关闭且验证过的事故可以沉淀成 Knowledge Entry，生成 Regression Guard，跑 guard，做 recurrence report，并进入 Hub gate。

v9.3.1 修复了 Knowledge ZIP 自证问题：Knowledge verifier 必须绑定外部 Incident Board ZIP，从真实 incident / closeout 事实重建 severity、component、root cause、recommended guard，不能只信 Knowledge ZIP 全量重签。

现在的问题是：

- v9.3 已经能回答“这个事故有没有防复发 guard”。
- 但还不能系统回答“我们目前有哪些必须长期执行的预防控制”。
- 也不能回答“这些控制是否覆盖了 Hub 当前所有高风险链路”。
- 更不能把这些控制作为一个独立的、可审计的 Control Catalog 交给外部或后续团队复验。

v9.4 要补的就是这一层。

## 2. v9.4 一句话目标

新增 Trust Operations Control Catalog：

```text
Trust Operations Hub / Incidents / Knowledge
  -> Control Catalog
  -> Control Policy Bundle
  -> Control Assessment Report
  -> Control Package ZIP
  -> Offline Verifier
  -> Hub gate: require_trust_controls
```

它要把“事故后补 guard”升级成“持续有效的预防控制体系”。

## 3. v9.4 的边界

### 3.1 必须做

- Control Catalog 数据模型和本地持久化。
- 从 v9.3 Knowledge Entry / Regression Guard 自动生成或推荐 Control。
- 内置一组 baseline controls，覆盖当前项目反复出现的高风险类别。
- Control Policy Bundle：把本次准出必须执行的 controls 固定成一个策略包。
- Control Assessment：基于当前 Hub、Incident Board、Knowledge、delivery evidence、publication monitoring 等证据评估 controls。
- Control Package export / ZIP / offline verifier。
- Hub verifier 新增 `--require-trust-controls`。
- API / CLI / Studio 基本入口。
- release-check v9.4 smoke。
- README / CHANGELOG / version bump。

### 3.2 不做

- 不接真实第三方 GRC 系统。
- 不做云端同步。
- 不自动 approve / signoff / reset。
- 不让 provider 或 LLM 判断控制是否通过。
- 不把 Control 当成能自动修业务问题的机器人。
- 不绕过 v9.2/v9.3 已有 evidence binding。
- 不弱化任何 verifier 的外部证据要求。

### 3.3 强约束

- 所有生成包必须固定 ZIP allow-list。
- 所有 verifier 必须能在离开 `.musicforge/` 的外部目录独立运行。
- 任何“require”门禁不能只信同一个 ZIP 内的 summary 自证。
- Control Assessment 必须绑定外部 Hub ZIP / Hub verification / Incident ZIP / Incident verification / Knowledge ZIP / Knowledge verification。
- 全量重签攻击必须有明确 regression。
- 签核、reset、提交、接受、provider、人工 review 都只能是 `manual_required`，不能自动执行。

## 8. 内置 baseline controls

v9.4 必须先内置一组控制，确保即使没有事故知识也有基本控制面。

建议最少 10 个：

### 8.1 external_evidence_binding

Delivery / Incident / Knowledge / Hub gate 必须绑定外部 verification report。

失败条件：

- required 外部 report 缺失。
- report status 不是 passed。
- report zip hash / size / manifest hash 与当前 ZIP 不一致。

### 8.2 fixed_zip_allowlist

所有信任包 verifier 必须固定 allow-list。

失败条件：

- ZIP 多出未声明文件。
- manifest.files 多出文件。
- package-index 多出文件。
- backslash entry。
- `.MusicForge/` 变体。
- nested ZIP 非允许项。

### 8.3 full_resign_semantic_guard

关键 summary 不能靠同 ZIP 全量重签自证。

失败条件：

- 没有独立 sidecar。
- 没有外部 source package。
- 不能从外部 facts 反推 current summary。

### 8.4 signed_immutability

签核后不能静默改 export / ZIP / report。

失败条件：

- 删除 signoff 文件后可以重建。
- 没有 history-based immutable guard。
- reset 不要求 approved Change Request。

### 8.5 delivery_ready_external

Hub delivery ready 必须覆盖 Release / Distribution / Submission / Evidence / Operations。

失败条件：

- not_configured 被当成 ready。
- same-type 多条 evidence 只检查第一条。
- component_id 不匹配。

### 8.6 incident_closeout_required

高风险 blocker 必须进入 Incident Board，并完成 closeout。

失败条件：

- critical/high blocker 无 incident。
- incident open。
- closeout 缺 fix evidence。
- closeout evidence 没绑定 Hub verifier facts。

### 8.7 incident_knowledge_guard_required

已关闭高风险 incident 必须进入 Knowledge 并有 passed Regression Guard。

失败条件：

- 高风险 incident 没 entry。
- entry 不匹配 external incident facts。
- guard 类型不匹配 recommended_guard。
- guard run failed / missing。

### 8.8 recurrence_monitoring_clean

Knowledge recurrence report 不能有 open recurrence。

失败条件：

- recurrence_count > 0。
- recurrence source stale。
- recurrence report integrity failed。

### 8.9 redaction_clean

所有公开/外部信任包必须无敏感信息。

失败条件：

- token。
- Bearer。
- Windows 路径。
- UNC 路径。
- 本机用户名路径。
- provider raw response。

### 8.10 release_check_matrix_current

当前 release-check profile 必须覆盖 v9 当前 smoke。

失败条件：

- v9 profile 没包含 v94 smoke。
- latest profile 没包含 v94 smoke。
- empty selection 假绿。
- expected warning 未被标注。

## 9. 从 Knowledge 自动派生 Controls

v9.3 的 Knowledge Entry 已经包含：

- incident_hash
- severity
- failure_mode
- root_cause
- preventive_pattern
- recommended_guard

v9.4 要新增：

```python
derive_controls_from_knowledge(hub_id)
```

规则：

1. 只从 active Knowledge Entry 派生。
2. hidden / archived entry 不派生。
3. entry 必须通过 v9.3.1 external fact binding。
4. critical/high entry 默认派生 required control。
5. medium entry 默认派生 warning control。
6. 每个 derived control 必须记录：
   - knowledge_entry_id
   - knowledge_entry_hash
   - incident_hash
   - recommended_guard_hash
   - source verification report hash

派生映射建议：

| failure_mode | control_type |
|---|---|
| missing_external_evidence | external_evidence_binding |
| stale_source_accepted | source_stale_guard |
| zip_full_resign | full_resign_semantic_guard |
| unsafe_artifact_path | path_safety_guard |
| signed_mutation | signed_immutability |
| duplicated_component_evidence | component_identity_binding |
| missing_regression | incident_knowledge_guard_required |

## 11. Offline Verifier

新增 CLI：

```powershell
python -m song_agent.cli verify-trust-operations-control-package `
  .musicforge/trust-operations-controls/hub/trust-operations-controls.zip `
  --strict `
  --require-policy-passed `
  --hub-package .musicforge/trust-operations-hubs/hub/trust-operations-hub.zip `
  --hub-verification-report .musicforge/trust-operations-hubs/hub/verification-report.json `
  --incident-board-package .musicforge/trust-operations-incidents/hub/trust-operations-incident-board.zip `
  --incident-board-verification-report .musicforge/trust-operations-incidents/hub/verification-report.json `
  --incident-knowledge-package .musicforge/trust-operations-knowledge/hub/trust-operations-knowledge.zip `
  --incident-knowledge-verification-report .musicforge/trust-operations-knowledge/hub/verification-report.json `
  --json
```

### 11.1 Verifier 必须检查

ZIP 层：

- can open。
- no duplicate entries。
- no backslash raw entry。
- no absolute path。
- no `..`。
- no `.musicforge` case-insensitive。
- no nested zip。
- fixed allow-list。
- manifest.files 等于 allow-list。
- file-index 如有，也必须等于 allow-list。

JSON 层：

- package_type 精确匹配。
- manifest integrity。
- catalog integrity。
- policy integrity。
- assessment integrity。
- results integrity。
- evidence binding integrity。
- blocker/manual action integrity。

外部绑定层：

- Hub ZIP sha256 / size / manifest hash 对齐 Hub verification report。
- Incident ZIP sha256 / size / manifest hash 对齐 Incident verification report。
- Knowledge ZIP sha256 / size / manifest hash 对齐 Knowledge verification report。
- Control assessment source 中的 hash 必须与外部 report 一致。
- evidence-bindings.json 中的 binding 必须能从外部 report 反查。

语义层：

- required critical/high controls 必须 passed 或 not_applicable。
- critical/high incident-derived controls 不能缺 guard。
- failure_mode 与 control_type 要匹配。
- derived control 必须匹配 external Knowledge Entry facts。
- policy 中 control_id 不能引用不存在 control。
- policy 不能重复 control。
- active required control 不能 hidden。

### 11.2 必须有 full-resign 回归

至少覆盖以下攻击：

1. 把 critical derived control 改成 low / optional，并重算 catalog、policy、assessment、manifest。
2. 把 failed control-result 改成 passed，并重算 report。
3. 删除 blocker-summary 中的 blocker，并重算所有 hash。
4. 把 evidence-bindings 指到另一个 package。
5. 加 benign extra txt，同步更新 manifest/files。
6. 把 Knowledge ZIP 中的 entry 降级，但沿用旧 Control ZIP。

预期都必须 failed。

## 18. 安全与审计红线

### 18.1 不允许自证

Control Package 里的 `assessment.source`、`summary`、`manifest` 都不能成为唯一真相。

Verifier 必须用外部证据反查：

- Hub ZIP。
- Hub verification report。
- Incident Board ZIP。
- Incident verification report。
- Knowledge ZIP。
- Knowledge verification report。

### 18.2 不允许同包全量重签绕过

任何 summary、result、blocker、manual action 的变更，即使重算了同包 hash，也必须被外部 facts 或 independent sidecar 拦住。

### 18.3 不允许签核后静默修改

v9.4 不引入 Control Signoff。  
如果未来 v9.5 引入 Control Signoff，必须基于 history 判定不可变，不能只看当前 signoff 文件是否存在。

### 18.4 不允许自动执行危险动作

Control Assessment 只能报告：

- passed
- failed
- warning
- manual_required

不能自动：

- reset signoff。
- approve change request。
- submit。
- accept。
- call provider。
- rewrite release/distribution packages。

## 28. 结论

v9.4 的价值不是再多一个 ZIP，而是让 MusicForge 从“发现问题后能修”走到“把问题沉淀为长期控制并在准出前持续验证”。

v9.2 是事故响应。  
v9.3 是防复发知识。  
v9.4 是预防控制目录和策略门禁。

开发时记住一条线：任何准出结论都不能只靠同一个包内自证，必须绑定外部事实、外部 verification report 和可复验的 source hash。
